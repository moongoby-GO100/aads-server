2. 문제점 — 무엇이 위험한가

#문제근거 (실측)사용자·운영 영향
P0본인확인 부재register() auth.py:140-184 에 인증 절차 없음. @aads.local 가짜 도메인으로 즉시 가입 성공. 87명 중 이메일 인증 3명실재하지 않는 사람이 계정을 만들 수 있고, 매장 담당자는 승인 화면에서 본인 여부를 확인할 근거가 없다. 근로계약·급여 통지가 미확인 주체에게 나간다
P0가입자마다 새 조직 생성가입 1건이 tenants 1행 + chat_workspaces 1행을 만든다(삭제 시 FK fk_chat_workspaces_tenant 로 확인). tenants 87 = users 87직원은 “내 매장”에 들어가야 하는데 자기 전용 빈 조직으로 들어간다. 데이터가 87개 조직으로 흩어지고, 매장 기준 집계·권한이 어긋난다
P0가입과 가입요청이 분리계정 생성은 /auth/register, 가입요청은 /employees/join-requests(yeoljeong_finance.py:385) 로 프론트가 두 번 호출두 번째 호출이 실패하면 계정만 있고 매장에 연결되지 않은 고아 계정이 남는다. 실제로 계정 87 대 요청 17의 격차가 이 구조와 무관하지 않다
P1비밀번호 복구 불가auth.py 라우트 전수 — register/login/impersonate/tenants/invites/me 뿐. 재설정 엔드포인트 없음비밀번호를 잊은 직원은 관리자 대리 로그인 외 방법이 없다. 운영 부담이 사람에게 전가된다
P1비밀번호 정책 불일치서버 min 6자(auth.py:49-54) vs 화면 minlength=8(index.html:4493)API 를 직접 호출하면 6자 비밀번호 계정이 만들어진다. 화면 규칙이 실제 보호선이 아니다
P1가입 폼이 받는 값이 API 에 없음폼은 지점·연락처·생년월일·주소를 수집(index.html:4482-4491)하나 RegisterRequest 는 email·password·name·organization_name·team_invites 만 받는다직원이 입력한 값이 가입 시점에 저장되지 않아 승인 화면에서 판단 근거가 비어 있다
P2테스트 계정 운영 DB 잔존saas_users 87명 중 e2e/test/probe 패턴 30명(34%), e2e-* 테넌트 7개사용자 수·전환율 등 운영 지표가 실제와 다르다. 정리 기준이 없으면 계속 쌓인다

3. 목표와 범위

목표

  • 직원이 휴대폰 본인확인을 거쳐 자기 매장에 소속된 상태로 가입을 마친다.
  • 가입 직후 화면에서 지금 어디까지 왔고 다음에 무엇이 열리는지 알 수 있다.
  • 비밀번호를 잊어도 사람 개입 없이 스스로 복구한다.
  • 관리자는 승인 화면에서 본인확인 여부를 보고 승인한다.

범위 밖 (이번 버전에서 하지 않는 것)

  • 소셜 로그인(카카오·네이버) — 본인확인 수단이 갖춰진 뒤 별도 검토.
  • 사업주(점주) 셀프 가입으로 새 사업자를 만드는 흐름 — 현재는 CEO/관리자가 개설한다.
  • ACCT 회계원장 계정 통합 — 통합 목표 M4 의 company 매핑이 선행돼야 한다.

4. 사용자 흐름 (설계)

단계사용자가 하는 일시스템이 하는 일
S1 계정이름·이메일·비밀번호 입력이메일 중복 즉시 확인, 비밀번호 8자 + 강도 표시. 아직 계정을 만들지 않는다(임시 세션에 보관)
S2 본인확인휴대폰 번호 입력 → 인증번호 6자리인증 성공 시에만 다음 단계 진입. 재발송 3회·유효 3분 제한
S3 매장 선택사업자 → 근무 매장 → 입사예정일 선택 후 제출한 트랜잭션으로 계정 생성 + 본인확인 기록 + 가입요청 생성. 개인 테넌트는 만들지 않는다
S4 대기진행 상황 확인, 필요 시 재요청5단계 추적 표시(계정→본인확인→승인→서류→계약). 담당자에게 알림 발송
S5 승인관리자가 승인/반려승인 시 tenant_memberships 연결 + join_request.status=approved 동시 반영. 본인확인 미완료 건은 승인 버튼 비활성

5. API 설계

엔드포인트구분내용
POST /auth/signup/verify-phone/request신규휴대폰 인증번호 발송. 응답에 verification_id·만료시각. 동일 번호 시간당 5회 제한
POST /auth/signup/verify-phone/confirm신규코드 검증 → 단기 signup_ticket 발급(30분)
POST /auth/register변경signup_ticket·branch_id·join_date 필수화. 티켓 없으면 4xx. 계정+가입요청을 한 트랜잭션으로 생성하고 개인 tenant 생성을 하지 않음. 비밀번호 최소 8자
PATCH /employees/join-requests/{id}변경승인 시 멤버십 연결까지 같은 트랜잭션에서 처리. 본인확인 미완료 건은 409
POST /auth/password/reset-request신규이메일 또는 휴대폰으로 재설정 링크. 존재하지 않는 계정도 동일 응답(계정 존재 노출 방지)
POST /auth/password/reset-confirm신규토큰 1회용·30분 만료. 성공 시 해당 사용자 기존 JWT 무효화(auth_revoked_tokens 활용)

  • password_reset_tokens (신규) — id, user_id, token_hash, expires_at, used_at, requested_ip.
  • yeoljeong_employee_join_requests — branch_id, join_date, phone_verified 스냅샷 컬럼 확인 후 보강.
