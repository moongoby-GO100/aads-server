1. 기획 — 시스템 개요 및 목표

1.1 시스템 정체성

AADS 채팅 시스템은 CEO(moongoby)가 자연어로 6개 프로젝트(AADS, KIS, GO100, SF, NTV2, NAS)를 통합 운영하는 Chat-First 인터페이스입니다. 단순 대화가 아니라, 코드 수정 · 배포 · DB 조회 · 서버 관리 · 리서치 · 팩트체크까지 50+ 도구를 실시간으로 호출하는 오케스트레이션 허브입니다.

1.2 핵심 설계 원칙

원칙설명구현
Chat-First모든 운영 액션이 채팅 메시지에서 시작24종 Intent 분류 → 도구 자동 바인딩
워크스페이스 분리프로젝트별 독립 시스템 프롬프트 · 역할 · 메모리25개 워크스페이스, role_key 기반 역할 전환
실시간 스트리밍LLM 응답을 토큰 단위 실시간 전달SSE + 30ms 토큰 버퍼 + heartbeat(3초)

멀티 모델Claude, GPT, Gemini, DeepSeek 등 30+ 모델OAuth 2토큰 폴백 + LiteLLM + OpenRouter

def route_model(message: str) -> str:
    complex_kw = ['설계', '분석', '개선안', '보고', '아키텍처', '전략', '검토', '평가']
    code       = ['수정해', '만들어', '추가해', '지시서', '코드', '고쳐']
    simple     = ['실행해', '결과', '상태', '확인', '스크린샷']
    
    if any(p in message for p in complex_kw): return 'claude-opus-4-6'     # $5/M in, $25/M out
    if any(p in message for p in code):       return 'claude-sonnet-4-6'   # $3/M in, $15/M out
    if any(p in message for p in simple):     return 'gemini-2.5-flash'    # $0.30/M in, $2.50/M out
    return 'claude-sonnet-4-6'  # 기본값

9. 현재 문제점 분석

9.1 Critical (P0)

P0 스트리밍 응답 실시간 DB 저장 미비 (반복 에러 21회)
현상: 스트리밍 중 서버 재시작/연결 끊김 시 부분 응답이 DB에 저장되지 않아 빈 버블 발생.
원인: chat_service.py의 producer-finally 경로에서 DB 쓰기 실패 시 3회 재시도(_FINALIZE_DB_RETRY_DELAYS)하지만, 타임아웃(0.5s/1s/2s)이 DB 부하 시 부족. Redis Stream 복구도 recovered_from_redis 92건으로 불완전.
영향: CEO가 "응답이 없다"고 반복 보고 (에러패턴 53회).
파일: app/services/chat_service.py — _retry_background_finalize_step()
P0 응답 버블 중복 생성 (세션 이동 후 보고 미출력 28회)
현상: 세션 전환 후 복귀 시 동일 응답이 2개 버블로 표시.
원인: (1) 프론트 useChatSession.ts의 selectSession에서 메시지 로드 후 스트리밍 상태 복구 시 중복 append. (2) 백그라운드 완료(_active_bg_tasks)와 폴백 복구(pollFallback)가 동시에 DB 저장.
영향: 화면 혼란, CEO 짜증 (experience_lessons 기록).
파일: src/hooks/useChatSession.ts, app/services/chat_service.py
P0 interrupted 메시지 2,288건 — 비정상 중단 비율 과다
현상: model_used='interrupted' 메시지가 전체 assistant 응답의 약 14.5%.
원인: CEO 인터럽트, OAuth 429 연속, Cloudflare 타임아웃, 클라이언트 탭 전환 등 복합 원인.
영향: 불필요한 비용 발생 + 사용자 경험 저하.
파일: app/services/chat_service.py — _save_interrupted_partial_message()

9.2 High (P1)

P1 _deleted_duplicate 인텐트 9,913건 — DB 오염
현상: 삭제 표시된 중복 메시지가 전체의 약 20%를 차지.
원인: dedup 로직이 "soft delete" (intent를 _deleted_duplicate로 변경) 방식으로, 실제 행은 삭제하지 않음.
개선: 일정 기간 경과 후 물리 삭제 또는 파티셔닝으로 분리.
P1 ceo_chat.py 단일 파일 2,097줄 — 유지보수 어려움
현상: Intent 분류, 모델 라우팅, LLM 호출, 비용 계산, 세션 관리가 한 파일에 혼재.
원인: Phase별 기능 추가가 누적.
개선: intent_classifier.py, llm_caller.py, cost_calculator.py로 분리.
P1 chat_service.py 8,147줄 — God Object
현상: CRUD, 스트리밍, 백그라운드 완료, 인터럽트, TODO, 토론, 복구가 하나의 모듈.
영향: 수정 시 사이드 이펙트 예측 어려움, 테스트 커버리지 부족.
개선: streaming_service.py, interrupt_service.py, recovery_service.py 분리.
P1 마크다운 렌더러 커스텀 구현 — 엣지 케이스 취약
현상: ChatBubble.tsx의 MarkdownContent가 정규식 기반 자체 파서.
원인: 중첩 목록, 복합 마크다운, HTML 엔티티 등 미지원.
개선: react-markdown + remark-gfm 라이브러리로 전환 검토 (번들 사이즈 트레이드오프).
