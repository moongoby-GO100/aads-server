ACCT-LAYOUT-004 · 2026-09-18 작성 · 통합 경영관리시스템(ACCT 회계원장 + 오비서 SaaS)
CEO 지시: "사용자가 여러 사업자를 관리할 때 각각 로그인해서 관리하는 건 불편하다 — 기획에 반영하라"

결론 3줄

1. 재로그인은 지금도 필요 없습니다. 전환 API(POST /auth/tenants/{id}/switch)는 이미 배포돼 있고 오늘 실호출로 200을 확인했습니다. 없는 것은 그 API를 쓰는 화면입니다.

2. 이미 35명이 두 개 이상 사업자에 소속돼 있습니다(전체 88명 중). 즉 이 문제는 앞으로의 가정이 아니라 지금 발생 중인 불편입니다.

3. 분리 단위는 tenant(계약) → company(사업자등록번호) 2층입니다. 사업자별 DB 분리는 하지 않습니다(RLS 유지).

핵심 진단. 백엔드는 멀티 사업자를 감당할 수 있는데, 화면이 "사용자 1명 = 사업자 1개"를 전제로 만들어져 있습니다. 그래서 두 번째 사업자를 보려면 로그아웃 → 재로그인밖에 길이 없었습니다. 고칠 지점은 인증이 아니라 화면과 스코프 전달 방식입니다.

2. 설계 — 왜 2층(tenant / company)인가

1층
tenant

계약·구독·결제·초대의 단위. 요금제가 붙고 사용량이 집계되는 곳. 세무사무소·프랜차이즈 본부가 여기에 해당합니다.

2층
company

사업자등록번호 1개 = 장부 1벌. 마감·시산표·부가세 신고가 이 축으로 떨어집니다. 라일론, 열정국밥 성신여대점이 여기입니다.

연결
membership

(user, tenant, company, role). company가 NULL이면 "그 tenant의 모든 사업자", 값이 있으면 "그 사업자만". 한 줄로 두 범위를 표현합니다.

왜 사업자마다 계정을 따로 만들지 않는가

안내용장점리스크판정
A. 사업자별 계정사업자 수만큼 로그인 계정구현 없음(현 상태)비밀번호 N벌, 알림 분산, 통합 손익 불가 — 지금 CEO가 지적한 그 불편폐기
B. 계정 1개 + 사업자 전환로그인 1회, 상단에서 전환이미 API 존재, 통합 뷰 가능스코프 누수 시 타 사업자 데이터 노출 → RLS로 차단권장
C. 계정 1개 + 전 사업자 동시 표시전환 없이 모든 사업자 합산만전환 조작 없음마감·전표 입력은 반드시 사업자 1개로 확정돼야 함(오귀속 위험)통합 대시보드에서만 부분 채택

권장은 B + C 부분 채택입니다. 조회·요약은 전 사업자 합산(C)을 허용하고, 쓰기(전표·마감·급여)는 반드시 현재 사업자 스코프에서만 허용합니다. 오늘 ACCT에서 source_file 17,776건이 귀속 근거 없이 남아 있는 상태를 보면, 쓰기 경로의 사업자 확정은 타협할 수 없습니다.

동작 규칙

  • 어디서나 같은 자리. 스위처는 모든 화면 좌상단에 고정합니다. 화면마다 위치가 달라지면 전환 자체를 못 찾습니다.
  • 최근 사용순 + 검색. 사업자가 5개를 넘어가면 목록은 스크롤이 됩니다. ⌘K로 바로 검색·전환합니다.
  • 배지로 할 일을 먼저 알린다. 전환하기 전에 어느 사업자에 미처리가 쌓였는지 목록에서 보입니다.
  • 전환 후 같은 화면을 유지한다. 매입자료를 보다가 전환하면 그 사업자의 매입자료로 갑니다(홈으로 튕기지 않음).
  • 권한 없는 메뉴는 숨기지 않고 비활성 + 사유 표시. "왜 안 보이지"가 문의의 대부분입니다.

사업자별 현황 — 카드를 누르면 그 사업자로 전환됩니다

쓰기는 여기서 막습니다. 통합 화면에서는 전표 등록·마감·급여 확정 버튼을 노출하지 않습니다. 합산 화면의 "등록" 버튼은 어느 사업자 장부에 들어갈지가 모호해서, 오귀속을 만드는 가장 쉬운 경로가 됩니다.

사업자 추가

  1. 사업자등록번호 입력 — 10자리. 국세청 진위확인 API로 상호·업태·과세유형을 자동 채웁니다. 중복 검사: 같은 번호가 이미 있으면 "추가" 대신 기존 사업자 참여 요청으로 분기합니다.
  2. 회계 장부 생성 — ACCT company 1행 + tenant_company 연결 1행을 만듭니다. 회계연도·기준통화·업종을 이때 확정합니다.
  3. 권한 부여 — 만든 사람에게 해당 company의 owner membership을 부여합니다. 현재 이 테이블이 0건이라 사업자 단위 권한이 사실상 없습니다 — 이 단계가 그 공백을 메웁니다.
  4. 수집 연동 — 카드·계좌·홈택스 연결(선택). 건너뛰어도 장부는 즉시 사용 가능합니다.
  5. 완료 — 스위처에 새 사업자가 붙고 자동 전환됩니다.
플랜 한도를 여기서 알린다. free 플랜은 사업자 1개까지입니다. 2개째를 만들 때 결제를 요구하지 말고, 먼저 "무엇이 늘어나는지"를 보여준 뒤 업그레이드를 제안합니다. 한도 초과는 생성 실패(500)가 아니라 402 + 업그레이드 안내로 처리합니다.

4. API 계약 — 이미 있는 것과 새로 필요한 것

엔드포인트용도상태
GET /api/v1/auth/tenants내 사업자 목록 + 현재 스코프있음(200 실측)
POST /api/v1/auth/tenants/{id}/switch전환 — 새 JWT 재발급있음(200 실측)
POST /api/v1/auth/tenants사업자 추가있음(201 실측)
POST /auth/tenants/{id}/invites · /members초대·멤버 조회있음
GET /api/v1/acct/companies현재 tenant의 사업자(company) 목록 + 배지 수치신규
POST /api/v1/acct/companies사업자 추가 2~3단계(company + tenant_company + membership)신규
GET /api/v1/acct/overview?scope=all통합 대시보드 합산신규
공통 헤더 X-Company-Idcompany 스코프 전달 → set_config('acct.company_id')신규

스코프 전달 경로 (쓰기 안전장치)

브라우저          JWT.tenant_id  +  X-Company-Id 헤더
   ↓
FastAPI 의존성    membership 조회로 (user, tenant, company) 권한 검증
   ↓              ── 권한 없으면 403, 여기서 끝 ──
PostgreSQL        set_config('acct.tenant_id', …) , set_config('acct.company_id', …)
   ↓
FORCE ROW LEVEL SECURITY  ← 앱이 실수해도 DB가 한 번 더 막는다

ACCT는 이미 37개 테이블 중 20개가 FORCE RLS입니다. 새 화면도 같은 방식에 태웁니다 — 사업자별 DB를 나누지 않는 이유가 이것입니다.
