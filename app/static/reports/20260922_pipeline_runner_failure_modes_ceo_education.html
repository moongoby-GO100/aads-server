1한 문장 정의

Pipeline Runner 실패란, AI 개발자에게 일을 시켰지만 코드 수정·검수·승인·배포 중 어느 한 문에서 멈춘 상태입니다.

일상 비유 공장으로 치면 "불량품"만 실패가 아닙니다. 원자재가 없어서 멈춘 것, 검사 장비가 고장난 것, 출하 승인서 번호가 안 맞은 것, 이미 같은 작업을 다른 사람이 하고 있어서 대기한 것도 모두 생산라인의 실패로 기록됩니다.

대표님이 알아야 할 핵심은 하나입니다. 실패라고 떠도 전부 코드가 나쁜 것은 아닙니다. 어떤 실패는 AI가 틀린 것이고, 어떤 실패는 검수 인프라·배포 게이트·동일 파일 충돌 같은 운영 장치가 멈춘 것입니다.

5코드 반려와 시스템 장애 구분법

보이는 문구무엇을 뜻하나대표님 판단다음 조치
REQUEST_CHANGES검수자가 "수정 필요"라고 판정코드 반려 가능성 높음반려 사유와 diff 확인 후 재작업
REVIEW_MODEL_NO_RESPONSE검수 모델이 답을 안 함코드 반려 아님자동 재검수 또는 검수 인프라 점검
REVIEW_MODEL_CONFIG_INVALID검수 모델 설정이 잘못됨코드 반려 아님모델 라우팅·설정 수정 후 재검수
PRESERVATION_HARD_GATE보존해야 할 파일·기능 삭제 위험작업물을 바로 믿으면 안 됨삭제 심볼과 보존 대상 대조
deploy_commit_sha_mismatch검수받은 커밋과 배포 대상이 다름배포하면 안 됨해당 SHA로 재검수 또는 배포 대상 고정
deploy_preflight_git_state작업장에 미정리 변경이 있음시스템 보호 장치 작동변경 소유권 분리 후 재배포
build_failed빌드가 깨짐코드·의존성·환경 모두 후보빌드 로그 첫 오류부터 확인
변경사항 0건실제로 바꾼 파일이 없음실패라기보다 "승인 대기 안 보냄"읽기전용이면 정상, 수정 작업이면 지시 재작성
대표님용 한 줄 판정법 REVIEW_MODEL_*는 검수 인프라 장애, REQUEST_CHANGES는 코드·산출물 반려, deploy_*는 배포 보호 장치, PRESERVATION_*는 삭제 방지 장치입니다.

6대표님 화면 문구별 대응

화면 문구오해하기 쉬운 점정확한 해석대표님이 물어볼 말
AI 리뷰 인프라 장애로 승인 보류AI가 코드를 못 짰다고 오해검수 모델이 응답 실패 또는 설정 오류"재검수 통과했나, 같은 SHA인가?"
AI 리뷰 통과운영 반영 완료로 오해검수만 통과. 배포·헬스는 별도"커밋·푸시·배포·헬스 각각 됐나?"
배포 완료 backend=OK서비스 전체 정상으로 오해백엔드 배포 확인. 화면·업무 플로우는 별도"화면 또는 API 검증 근거는?"
변경사항 0건으로 작업 종결작업 실패로만 오해읽기전용 진단이면 정상, 수정 지시면 미완료"이 작업은 읽기전용이었나?"
deploy_commit_sha_mismatch단순 배포 실패로 오해검수받은 코드와 배포 코드가 달라져 차단"검수 SHA와 배포 SHA를 보여 달라"
동일 파일 충돌 감지러너가 느린 것으로 오해같은 파일을 다른 작업이 만져서 보호 차단"선행 runner가 끝났나, depends_on 연결됐나?"

7우리 시스템에 적용된 곳

장치무엇을 막나실측 근거
AI 리뷰 게이트코드 품질 문제·보존 위험·검수 인프라 장애를 상태로 분리review_flag_category에 5종 값 확인
배포 preflightdirty worktree, fast-forward 충돌, SHA 불일치 배포deploy_preflight_git_state 9건, deploy_commit_sha_mismatch 2건
Runner Guard동일 파일 동시 수정[Runner Guard] 동일 파일 충돌 감지 로그 다수
보존 하드게이트삭제·기능 손실 위험PRESERVATION_HARD_GATE 6건
작업 상태 DB어떤 세션이 지시했는지, 현재 상태가 무엇인지 추적pipeline_jobs.chat_session_id, status, error_detail

즉 AADS는 "실패를 숨기는 시스템"이 아니라, 실패를 여러 문으로 쪼개 기록하는 시스템입니다. 문제는 대표님 화면에서 이 분류가 교육 없이 보이면 전부 같은 실패처럼 느껴진다는 점입니다.
