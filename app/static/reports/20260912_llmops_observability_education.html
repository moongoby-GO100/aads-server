🔭 01. LLMOps란 무엇인가 — MLOps와 무엇이 다른가

LLMOps(LLM Operations)는 대규모 언어모델을 실서비스에 배포·운영·모니터링·개선하는 데 필요한 실천 방법론 전체를 말합니다. MLOps(전통적 머신러닝 운영)에서 출발했지만, LLM은 근본적으로 다른 운영 난제를 갖고 있어 별도 분야로 분리되었습니다.

MLOps와 LLMOps, 무엇이 다른가

LLM 특유의 3대 운영 난제

1. 비결정성 (Non-determinism)

temperature, top_p 설정과 모델 내부 샘플링 때문에 동일 프롬프트도 응답이 매번 다릅니다. "어제는 됐는데 오늘은 안 된다"는 보고가 실제로 재현 불가능한 경우가 흔합니다. 관측 시스템은 단일 요청이 아니라 분포(distribution)로 품질을 봐야 합니다.

2. 무한 입력 공간

사용자가 입력할 수 있는 자연어 문장은 사실상 무한합니다. 테스트 케이스를 아무리 많이 만들어도 프로덕션에서 처음 보는 입력(edge case)이 계속 등장합니다. 사전 테스트만으로는 커버할 수 없고, 실서비스 트래픽을 지속적으로 관찰해야 합니다.

3. 조용한 품질 저하 (Silent degradation)

API는 200 OK를 반환하고 토큰도 정상 생성되지만, 답변 내용이 점점 부정확해지거나 형식이 깨지는 경우가 있습니다. 공급사가 백엔드에서 모델을 몰래 교체하거나(model routing), 프롬프트 한 줄을 수정했는데 다른 케이스가 깨지는 경우가 전형적입니다. HTTP 상태코드만 보는 헬스체크로는 절대 잡히지 않습니다.

+ 체인형 실패 전파

에이전트 파이프라인에서는 프롬프트→도구 호출→모델 응답→다음 단계 입력이 순차적으로 이어집니다. 중간 어느 한 단계의 미묘한 오류가 다음 단계로 전파되며 증폭되어, 최종 실패 지점만 보면 원인을 찾을 수 없습니다.

⚠️ 비개발자를 위한 요약 전통 소프트웨어는 "고장 나면 알람이 뜬다"가 기본 전제입니다. LLM 서비스는 "고장 나도 알람이 안 뜰 수 있다"가 기본 전제입니다. 그래서 LLMOps는 장애 탐지 자체를 별도로 설계해야 하는 분야입니다.

📊 02. 관측 3요소 재정의: 로그·메트릭·트레이스

전통적 관측가능성(Observability)의 3요소는 로그(Logs)·메트릭(Metrics)·트레이스(Traces)입니다. LLM 시스템에서는 이 3요소의 의미가 바뀝니다.

🧵 03. 트레이싱 실전: 스팬 구조와 OpenTelemetry GenAI 컨벤션

트레이싱은 요청 하나가 시스템을 통과하는 전체 경로를 스팬(span)이라는 단위로 쪼개어 기록하는 것입니다. 스팬은 시작 시각·종료 시각·부모 스팬 ID·속성(attributes)을 가지며, 부모-자식 관계로 트리 구조를 이룹니다.

LLM 에이전트 요청의 전형적인 스팬 트리

하나의 채팅 요청이 만드는 스팬 트리
Trace (root span): "사용자 질문 처리" — 전체 4.1초
├─ span: 프롬프트 조립 (0.05초)
│    └─ 시스템 프롬프트 + 대화 이력 + 메모리 주입
├─ span: RAG 검색 (0.8초)
│    └─ 벡터 DB 질의 → 관련 문서 5건 반환
├─ span: 모델 호출 #1 (1.2초)
│    ├─ 속성: gen_ai.request.model, input_tokens, TTFT
│    └─ 결과: 도구 호출 요청 (tool_call)
├─ span: 도구 실행 — DB 조회 (0.3초)
│    └─ 성공/실패, 반환 데이터 크기
├─ span: 모델 호출 #2 (1.6초)  ← 도구 결과를 받아 최종 응답 생성
│    └─ 속성: output_tokens, finish_reason, 비용
└─ span: 응답 스트리밍 전송 (0.15초)

이 구조의 핵심은, 전체 4.1초 중 어느 스팬이 병목인지를 한눈에 알 수 있다는 점입니다. 스팬 트리가 없으면 "4.1초 걸렸다"는 사실만 남고, 그 안에서 무슨 일이 있었는지는 로그를 뒤져야 합니다.

OpenTelemetry GenAI 시맨틱 컨벤션

OpenTelemetry(OTel)는 관측 데이터(트레이스·메트릭·로그)의 업계 표준 규격입니다. 특정 벤더에 종속되지 않고 수집기를 한 번 계측해두면 LangSmith·Langfuse·Datadog 등 어느 백엔드로도 데이터를 보낼 수 있는 것이 핵심 장점입니다. 여기에 생성형 AI 전용 속성 이름을 표준화한 것이 GenAI 시맨틱 컨벤션입니다.

프롬프트/응답 원문을 스팬에 넣을 것인가

초기 GenAI 컨벤션은 프롬프트·응답 전문을 스팬 속성에 직접 넣는 방식이었으나, 개인정보·기밀 노출 위험과 스팬 크기 폭증 문제로 최근에는 별도 로그 이벤트로 분리하고 스팬에는 참조 ID만 남기는 방식이 권장되는 추세입니다. 자체 구축 시에도 "원문은 접근 제어가 된 로그 저장소에, 트레이스에는 메타데이터만" 원칙을 따르는 것이 안전합니다.

지표정의왜 중요한가일반적 목표치
TTFT
(Time To First Token)		요청 전송 후 첫 토큰이 돌아오기까지 시간사용자가 체감하는 "반응성"의 핵심. 전체 응답이 느려도 TTFT가 짧으면 체감 대기시간이 줄어듦채팅형 서비스 < 1~2초
TPS
(Tokens Per Second)		토큰 생성 속도(첫 토큰 이후)답변이 길수록 체감 시간을 좌우. 스트리밍 UI에서는 "타이핑 속도"로 느껴짐모델·프로바이더별 상이, 일반적으로 20~100 TPS
p95 / p99 지연전체 요청의 95%/99%가 이 시간 안에 끝남평균값은 소수 극단치에 가려짐. SLA는 항상 p95/p99 기준으로 설정서비스 성격에 따라 결정, 평균의 2~5배가 흔함
토큰당 비용입력/출력 토큰 단가 × 사용량 (+캐시 할인)모델 선택·프롬프트 길이·캐싱 전략이 직접 비용에 반영됨모델·캐시 히트율에 따라 10배 이상 차이
도구 성공률에이전트가 호출한 도구(함수·API)가 정상 응답한 비율도구 실패는 전체 응답 실패로 이어지거나, 모델이 잘못된 정보로 답변을 지어내는(hallucination) 원인이 됨99%+ 권장
재시도율1차 호출 실패 후 재시도가 발생한 비율재시도가 늘면 지연·비용이 배로 늘어남. 급증 시 공급사 장애의 선행 신호평상시 1~3% 이하
폴백 발생률주 모델 실패로 대체 모델/계정으로 전환된 비율폴백 자체는 정상 동작이지만, 급증하면 주 모델 공급사 이상 신호추세 감시 대상 (절대값보다 변화율이 중요)

지표를 어떻게 잘라서 봐야 하는가

  • 모델별 — 같은 서비스 안에서도 라우팅되는 모델이 다르면 지연·비용·성공률이 전혀 다름
  • 엔드포인트/기능별 — 단순 질의응답과 도구 호출을 포함한 에이전트 작업은 지연 분포가 완전히 다름
  • 시간대별 — 공급사 트래픽이 몰리는 시간대(미국 업무시간 등)에 지연이 구조적으로 늘어나는 경우가 흔함
  • 테넌트/사용자군별 — 특정 사용자의 비정상적으로 긴 프롬프트가 전체 평균을 왜곡할 수 있음
⚠️ 평균의 함정 "평균 응답시간 1.2초"라는 보고를 받았을 때, p95가 8초라면 20명 중 1명은 8초를 기다리고 있다는 뜻입니다. 반드시 p95/p99를 함께 보고받아야 하며, 평균만 보고하는 대시보드는 경영 의사결정에 오히려 위험합니다.

원인 1: 공급사 모델 버전 교체

원인 2: 프롬프트 변경의 부작용

특정 케이스를 고치려고 시스템 프롬프트를 수정했는데, 그 수정이 전혀 다른 케이스의 동작을 깨뜨리는 경우입니다. 프롬프트는 코드처럼 버전 관리·회귀 테스트 없이 수정되는 경우가 많아 가장 흔한 원인입니다.

원인 3: RAG 인덱스 노후화

검색 대상 문서가 갱신되지 않거나, 임베딩 모델이 바뀌었는데 기존 인덱스를 재생성하지 않으면 검색 결과의 관련성이 서서히 떨어집니다.

📡 07. 스트리밍(SSE) 장애 유형과 관측 포인트

대부분의 LLM 채팅 서비스는 SSE(Server-Sent Events)로 토큰을 실시간 스트리밍합니다. 일반 HTTP 요청과 달리 "연결은 됐지만 중간에 멈췄다"는 상태가 존재하기 때문에 일반적인 성공/실패 이분법으로는 장애를 포착하지 못합니다.

SSE 특유의 장애 유형

장애 유형증상사용자 체감관측 포인트
연결은 성공, 스트림 중단첫 토큰까지는 오는데 중간에 끊김답변이 문장 중간에서 멈춤스트림 시작 이후 마지막 토큰까지의 간격(inter-token gap) 모니터링
TTFT는 정상, TPS 급락첫 토큰은 빠른데 이후 토큰 생성이 느려짐"타이핑"이 뚝뚝 끊기는 느낌토큰별 타임스탬프 기록 → 구간별 TPS 계산
프록시/게이트웨이 타임아웃nginx 등 중간 프록시가 장시간 유휴 연결을 강제 종료긴 답변 생성 중 갑자기 연결 끊김 에러프록시 idle timeout 설정과 실제 응답 소요시간 비교 관측
백프레셔로 인한 큐 지연서버가 동시 스트림을 과도하게 열어 신규 요청이 큐에서 대기"로딩 중"이 유난히 길게 유지대기열 길이, 큐 대기시간을 별도 지표로 계측
부분 응답 후 폴백 전환주 모델이 스트리밍 도중 실패해 폴백 모델로 재시작답변 스타일이 문장 중간에 바뀌거나 처음부터 다시 나옴폴백 전환 이벤트를 트레이스에 명시적으로 기록

SSE 관측을 위한 최소 계측 항목

  • 연결 수립 시각, 첫 토큰 시각, 마지막 토큰 시각 — TTFT와 총 스트리밍 시간을 모두 계산 가능
  • 토큰 간 최대 간격 — 긴 침묵 구간이 있었는지(중단 위험 신호)
  • 스트림 종료 사유 — 정상 종료(stop) / 클라이언트 연결 끊김 / 서버 타임아웃 / 에러
  • 동시 활성 스트림 수 — 서버 자원 사용량과 직결, 백프레셔 트리거 판단 근거
🔴 흔한 함정: "에러율 0%"의 착시 스트림이 중간에 끊겨도 서버 로그상으로는 "연결 정상 수립, HTTP 200"만 남고 별도 계측이 없으면 에러로 집계되지 않는 경우가 많습니다. 스트림 종료 사유를 반드시 별도 필드로 기록해야 진짜 장애율을 알 수 있습니다.

🛡️ 08. 장애 대응 설계 — 서킷브레이커·레이트리밋·폴백·백프레셔

관측은 문제를 "보는" 것이고, 장애 대응 설계는 문제가 생겼을 때 시스템이 "스스로 방어"하게 만드는 것입니다. 4가지 핵심 패턴을 정리합니다.

서킷브레이커 (Circuit Breaker)

특정 모델/서버가 연속 실패하면 일정 시간 동안 아예 호출을 차단해, 이미 죽은 대상에 계속 요청을 보내 자원을 낭비하거나 장애를 악화시키는 것을 막습니다. closed(정상)→open(차단)→half_open(시험 호출)의 3상태 전이가 표준 패턴입니다.

레이트리밋 (Rate Limiting)

공급사 API의 분당 요청 한도(RPM)·토큰 한도(TPM)를 초과하지 않도록 자체적으로 속도를 제한합니다. 한도 초과(429) 자체가 실패로 집계되어 재시도 폭주를 유발할 수 있어, 사전에 속도를 조절하는 편이 안전합니다.

모델 폴백 체인

주 모델 실패 시 대체 모델로 자동 전환합니다. 단순히 "다른 모델을 부른다"가 아니라, 같은 등급의 모델로 전환할지(품질 유지) 더 저렴한 모델로 전환할지(가용성 우선) 정책을 명확히 정해야 합니다.

큐잉 · 백프레셔

동시 요청이 처리 용량을 초과하면 무작정 다 받아들이지 않고 대기열에 넣거나(큐잉) 신규 요청을 거부합니다(백프레셔). 이렇게 하지 않으면 모든 요청이 조금씩 느려지다가 전체가 타임아웃되는 "혼잡 붕괴(congestive collapse)"가 발생합니다.

  • 동일 에러 해시(fingerprint) 기준으로 그룹화 — 발생 횟수만 누적, 알림은 최초 1회 + 임계치 초과 시

🔀 10. 프롬프트·모델 버전 관리와 카나리/블루그린 배포

전통 소프트웨어는 코드만 버전 관리하면 되지만, LLM 서비스는 프롬프트와 모델 버전도 코드와 동등하게 버전 관리 대상입니다. 둘 다 응답 품질에 직접 영향을 주면서도, 코드 리뷰 프로세스 밖에서 수정되는 경우가 흔합니다.

프롬프트 버전 관리가 필요한 이유

  • 프롬프트를 코드에 문자열로 하드코딩하면 변경 이력이 git diff에 묻혀 리뷰 없이 넘어가기 쉬움
  • 프롬프트를 별도 레지스트리(버전 태그 포함)로 관리하면, "어느 버전이 어떤 성능이었는지" 추적 가능
  • 롤백이 코드 배포 없이 즉시 가능해짐 (프롬프트 버전 포인터만 되돌리면 됨)

카나리 배포 vs 블루그린 배포

방식동작 원리장점단점
카나리 배포신규 버전에 트래픽 일부(예: 5%)만 먼저 보내고, 지표를 보며 점진적으로 비율을 늘림문제 발생 시 영향 범위가 작음, 실사용자 데이터로 검증 가능두 버전을 동시에 운영해야 하므로 구성 복잡도 증가, 점진적 확대에 시간 소요
블루그린 배포신규 버전(Green)을 별도로 완전히 띄운 뒤, 준비되면 트래픽을 한 번에 전환. 이전 버전(Blue)은 즉시 롤백 가능하도록 대기전환이 순간적이라 다운타임이 사실상 0, 롤백이 매우 빠름카나리처럼 "일부만 먼저 검증"은 안 됨 — 전환 전 검증에 더 의존
💡 LLM 서비스에서의 조합 모델/프롬프트 품질 검증은 카나리 방식(일부 트래픽으로 점진 검증)으로, 인프라(코드·컨테이너) 배포는 블루그린 방식(무중단 전환)으로 조합하는 것이 일반적입니다. 다음 장(AADS 사례)에서 실제 구현을 살펴봅니다.

11-1. 서킷브레이커 — app/services/circuit_breaker.py

AADS-132로 도입된 서킷브레이커는 closed → open → half_open 3상태 전이를 circuit_breaker_state 테이블에 저장하며 서버 단위로 동작합니다. 소스 확인 결과 정책은 다음과 같습니다.

  • 임계치: 연속 실패 3회(FAILURE_THRESHOLD = 3) 도달 시 open 전환
  • 쿨다운: open 상태 5분(COOLDOWN_MINUTES = 5) 경과 후 half_open으로 전환, 시험 호출 1건만 허용
  • fail-open 설계: DB 연결 자체가 실패하면 차단하지 않고 통과시킴(except Exception: return True) — 관측 시스템 장애가 서비스 장애로 전이되지 않도록 하는 방어적 설계
  • 알림 연동: open 전환 시 _send_alert()가 텔레그램으로 "🔴 서킷브레이커 OPEN" 메시지를 발송 (실패해도 조용히 무시 — graceful degradation)

실측 조회 결과, 현재 서버 114/211/68 모두 state=closed, failure_count=0으로 정상 상태입니다. DB 실측 2026-09-12

🕳️ 12. AADS 관측 공백과 개선안

11장의 실측 결과를 바탕으로, 이 문서 작성 과정에서 실제로 확인된 관측 공백과 개선 방향을 정리합니다. 모두 위 장에서 직접 조회·확인한 내용에 근거합니다.

공백 1: claude_api_fallback이 4,000회 이상 반복되는데 상태가 계속 "pending"

error_log 실측 결과, "claude-opus → samegrade fallback 전환" 패턴이 4,149회 누적되었는데도 resolution_type이 여전히 pending입니다. auto_recoverable=false로 자동복구 대상도 아닙니다. 이는 "계정 교차 폴백"이 사실상 상시적으로 발생하는 상태이면서도, 이를 정식으로 해결하거나 최소한 "정상 동작으로 확인됨(dismissed)" 처리하는 절차가 없다는 뜻입니다.

개선안: claude_api_fallback 발생률을 별도 대시보드 지표로 승격하고(9장의 "폴백 발생률" 지표), 임계치(예: 시간당 N회) 초과 시에만 알림을 울리도록 해 pending 상태로 방치되는 대량의 로우데이터와 "실제 조치가 필요한 급증"을 구분해야 합니다.

공백 2: tool_metrics 도구가 24시간 집계에서 0건 반환

이 문서 작성 중 tool_metrics MCP 도구를 실행한 결과 total_calls: 0이 반환되었습니다. 같은 시간대에 다른 MCP 도구(read_remote_file, query_database 등)는 다수 호출되고 있었으므로, 도구 사용량 자체가 0이라기보다 집계 파이프라인이 해당 호출들을 포착하지 못하고 있을 가능성이 있습니다. 원인은 이 조사만으로는 특정할 수 없어 미검증으로 남깁니다.

개선안: tool_metrics 데이터 소스(어느 테이블/로그를 집계하는지)를 코드 레벨에서 재확인하고, MCP 도구 호출이 실제로 그 소스에 기록되는지 엔드투엔드로 검증이 필요합니다.

공백 3: monitored_services의 타 서버 데이터가 장기간 미정리 상태로 보임

watchdog 대상 테이블 실측 조회에서, contabo116(AADS 운영 서버) 외 다른 프로젝트 서버(contabo14 등) 소속 서비스 다수가 consecutive_failures 값 10만 회 이상으로 last_status=fail 상태로 남아 있는 레코드가 확인되었습니다. 이는 AADS 자체 헬스와는 무관하지만, 하나의 watchdog 체계가 여러 프로젝트 서버를 함께 감시하는 구조에서 더 이상 감시가 필요 없거나 실패가 고착된 레코드를 정리하는 절차가 없다면 진짜 이상 신호와 "만성적으로 죽은 것으로 알려진" 레코드가 뒤섞여 보인다는 신호입니다. 이 문서는 AADS 서버68 범위 밖의 원인까지 단정하지 않으며, 정확한 원인(모니터링 대상 서버가 실제로 운영 종료되었는지, 감시 설정 오류인지)은 미검증입니다.

개선안: 프로젝트별 watchdog 감시 목록에 "활성/비활성" 플래그를 두어, 더 이상 운영하지 않는 서버는 감시에서 명시적으로 제외하고, consecutive_failures가 비정상적으로 큰(예: 1만 회 초과) 레코드는 별도로 검토 대상 목록에 올리는 배치 점검을 추가.

공백 4: 운영 문서와 소스 코드 주석 간 폴백 경로 설명 차이

11-4에서 확인한 대로, anthropic_client.py 코드 주석은 "Gemini/DeepSeek 폴백 제거(2026-09-06)"를 명시하지만 이 문서를 준비하며 참고한 운영 규칙 요약본에는 "Gemini/DeepSeek는 LiteLLM 프록시 경유" 문구가 남아 있었습니다. 둘 중 어느 쪽이 현재 실제 운영 정책인지는 llm_fallback_chains DB 테이블의 실제 값까지 대조해야 확정할 수 있어, 이 문서에서는 단정하지 않습니다.

개선안: 코드 주석·DB 설정·운영 문서 3곳의 폴백 정책 설명이 실제로 일치하는지 정기(예: 월 1회) 대조 점검을 도입해, "문서는 옛날 정책을, 코드는 새 정책을 말하는" 드리프트를 조기에 잡아낼 것.
