PART 01

CH 1모델은 똑똑한데, 시스템은 왜 바보가 될까?

핵심: 모델 한 번의 정답률과 서비스 전체의 신뢰성은 다른 문제입니다. AI 엔지니어의 일은 모델을 숭배하는 것이 아니라 불확실성을 제한하는 시스템을 만드는 것입니다.

  • 1.1 전통적인 소프트웨어와 AI 시스템의 결정적 차이 — 같은 입력에 같은 결과가 보장되는 코드와, 분포·컨텍스트·샘플링에 따라 결과가 흔들리는 모델을 구분합니다.
  • 1.2 결정론적 시스템 vs. 확률론적 시스템 — 확률 출력은 제거 대상이 아니라 계약·검증·재시도 정책으로 관리할 대상입니다.
  • 1.3 AI 엔지니어링의 본질은 통제다 — 좋은 프롬프트보다 실패 범위, 승인 조건, 롤백 경로를 먼저 설계합니다.
  • 1.4 핵심 정리 — 모델 품질과 시스템 품질을 별도 지표로 봅니다.
AADS 적용모델 응답을 곧바로 배포하지 않고 지시서 → 러너 → 리뷰 → 승인 → 블루그린 검증으로 감싸는 구조가 이 장의 핵심입니다. 아직 부족한 점은 각 단계의 성공 기준이 전 세션에서 동일하지 않다는 것입니다.
PART 01

CH 2AI 시스템 장애의 대부분은 모델 밖에서 시작된다

핵심: 오답이 보이면 모델부터 바꾸기 쉽지만 실제 장애는 입력 데이터, 검색, 프롬프트 조립, 도구, 권한, 캐시, UI 병합에서 더 자주 발생합니다.

  • 2.1 실제 현장에서 가장 자주 터지는 장애 유형 — 타임아웃, 낡은 데이터, 잘못된 검색, 도구 계약 불일치, 부분 실패를 계층별로 분류합니다.
  • 2.2 왜 성능 지표는 정상인데 서비스는 망가질까? — 모델 평균 점수는 특정 사용자 흐름의 실패나 끝단 통합 오류를 숨길 수 있습니다.
  • 2.3 침묵하는 장애가 가장 위험한 이유 — HTTP 200이지만 내용이 잘못된 경우처럼 에러가 없는 실패가 가장 늦게 발견됩니다.
  • 2.4 '모델은 무죄다'라는 관점 — 모델 교체 전에 데이터·검색·도구·렌더링 경로를 순서대로 배제합니다.
  • 2.5 핵심 정리 — 장애를 컴포넌트가 아닌 사용자 결과 기준으로 판정합니다.
AADS 적용“최종응답이 DB에는 있는데 화면에서 사라짐”은 모델 문제가 아니라 SSE 병합·세션 전환·렌더 필터 문제일 수 있습니다. 따라서 DB 저장, 이벤트 전송, 클라이언트 보존을 각각 검증해야 합니다.
PART 02

CH 3데이터 파이프라인은 단순한 ETL이 아니다

핵심: 데이터 파이프라인은 자료를 옮기는 배관이 아니라 모델이 무엇을 사실로 보고 어떤 결정을 내릴지 만드는 의사결정 장치입니다.

  • 3.1 데이터 파이프라인 = 의사결정 생성기 — 수집·필터·정규화·집계 방식이 모델의 결론을 선행 결정합니다.
  • 3.2 행동을 위한 스트리밍, 진실을 위한 배치 — 즉시 행동은 스트림, 정합성 복구와 기준 데이터는 배치로 역할을 나눕니다.
  • 3.3 파이프라인 설계가 모델의 사고 구조를 고정시키는 방식 — 어떤 필드를 버리고 어떤 순서로 컨텍스트에 넣는지가 모델의 관찰 범위를 만듭니다.
  • 3.4 '나중에 고치자'가 통하지 않는 이유 — 잘못 쌓인 데이터와 피드백은 이후 재학습·평가·감사까지 오염시킵니다.
  • 3.5 핵심 정리 — 모델 변경보다 데이터 계약을 먼저 버전 관리합니다.
AADS 적용project_handover_entries를 정본으로 두고 Markdown을 파생물로 보는 원칙, 프롬프트 provenance를 적용 여부의 최종 근거로 보는 원칙이 데이터 계약 사례입니다.
PART 02

CH 4데이터는 생각보다 훨씬 쉽게 망가진다

핵심: 컬럼 구조가 깨지는 것뿐 아니라, 필드의 의미가 변하거나 신뢰할 수 없는 문서가 맥락에 섞이는 것도 데이터 부패입니다.

  • 4.1 정형 데이터의 부패: 스키마 드리프트 vs. 시맨틱 드리프트 — 형식 변화와 의미 변화를 따로 감시해야 합니다. 타입이 같아도 뜻이 바뀔 수 있습니다.
  • 4.2 비정형 데이터의 부패: 컨텍스트 포이즈닝 — 검색 문서 안의 악성 지시나 오래된 규칙이 모델의 행동을 바꿀 수 있습니다.
  • 4.3 데이터 관측 가능성: 코드가 아니라 데이터를 테스트하라 — 코드 테스트만으로 부족하며 결측률, 분포, 신선도, 중복, 출처를 검사합니다.
  • 4.4 핵심 정리 — 데이터 품질을 운영 지표로 승격합니다.
AADS 적용메모리·워크스페이스 preload·세션 지시가 동시에 들어오므로 출처 우선순위와 최신 시각이 필수입니다. 프롬프트 provenance와 DB 실측을 최종 근거로 삼아야 합니다.
PART 02

CH 5잘못된 피드백 루프는 AI 시스템을 천천히 죽인다

핵심: 모델의 출력을 다시 학습·검색·평가 데이터로 넣으면 오류와 편향이 스스로 증폭될 수 있습니다.

  • 5.1 피드백 루프의 구조 해부 — 출력 → 사용자 반응 → 수집 → 재사용의 각 단계에서 선택 편향을 찾습니다.
  • 5.2 자기 강화적 편향 — 많이 노출된 답이 더 많은 반응을 얻고 다시 더 신뢰받는 순환을 경계합니다.
  • 5.3 피드백 루프를 끊는 방법 — 인간 검수, 홀드아웃 데이터, 시간 지연, 원천 데이터 재확인으로 독립성을 만듭니다.
  • 5.4 피드백은 위험이자 자산이다: 암묵적 신호와 데이터 플라이휠 — 클릭·수정·재시도는 가치 있는 신호지만 의도를 확정값으로 오해하면 안 됩니다.
  • 5.5 핵심 정리 — 피드백은 출처·품질·편향을 기록할 때만 자산입니다.
AADS 적용자동 진화 메모리가 과거 AI 답변을 다시 사실로 취급하면 오류가 강화됩니다. DB·코드·로그로 검증된 사실과 모델이 생성한 관찰을 분리하고 confidence를 독립 근거 수로 올려야 합니다.
PART 03

CH 6생성형 AI는 API가 아니라 확률 엔진이다

핵심: API가 성공했다는 것은 호출이 처리됐다는 뜻이지, 내용이 정확하거나 안전하다는 뜻이 아닙니다.

  • 6.1 토큰, 확률, 샘플링: LLM이 텍스트를 만드는 방법 — 출력은 후보 토큰의 확률 분포에서 순차 선택되므로 온도와 샘플링이 변동성을 만듭니다.
  • 6.2 컨텍스트 윈도우: LLM의 유한한 작업 기억 — 모델의 작업 기억은 유한하며 오래된 정보·중요 지시가 잘리거나 묻힐 수 있습니다.
  • 6.3 생성형 AI 기반 시스템의 고유한 위험들 — 환각, 지시 충돌, 비결정성, 긴 문맥 열화, 프롬프트 주입을 시스템 위험으로 봅니다.
  • 6.4 핵심 정리 — 호출 성공과 작업 성공을 분리합니다.
AADS 적용채팅이 길어질수록 최초 역할을 잊는 현상은 컨텍스트 관리 문제입니다. EducationLead 같은 역할은 대화 기억이 아니라 role_key와 컴파일된 프롬프트 자산으로 매 호출에 재주입해야 합니다.
PART 03

CH 7예측 불가능한 모델 위에 안정적인 시스템을 만드는 법

핵심: 하나의 완벽한 프롬프트가 아니라 여러 겹의 안전장치로 실패 확률과 피해 범위를 줄입니다.

  • 7.1 레이어 1: 모델 파라미터 통제: 확률의 폭을 줄이기 — 작업 성격에 맞게 온도·최대 출력·중단 조건을 제한합니다.
  • 7.2 레이어 2: 구조화된 출력 강제: '형식만큼은 결정론적으로' — JSON Schema 같은 형식 계약으로 파싱 실패와 누락을 줄입니다.
  • 7.3 레이어 3: 생성-검증-수정 루프: 자기 교정 아키텍처 — 초안과 검수를 분리하고 실패 원인을 다음 수정 입력으로 사용합니다.
  • 7.4 레이어 4: 결정론적 로직 분리: LLM에게 맡기지 말아야 할 것 — 권한·금액·상태 전이·삭제 조건은 LLM이 아닌 코드가 판정합니다.
  • 7.5 레이어 5: 검증 인프라: 모델의 출력을 다층적으로 검증 — 스키마, 규칙, 테스트, 독립 리뷰, 실제 헬스를 단계별로 쌓습니다.
  • 7.6 안전망의 비용: 신뢰성과 지연 시간의 트레이드오프 — 검증이 늘면 지연과 비용이 증가하므로 위험 등급별 깊이를 다르게 합니다.
  • 7.7 핵심 정리 — 중요한 작업일수록 모델에게 맡기는 범위를 줄입니다.
AADS 적용Pipeline Runner의 지시서 포맷, 자동 리뷰, 승인, SHA 확인, 블루그린 헬스가 다층 안전망입니다. 리뷰 모델 무응답은 코드 반려와 분리해야 하며, 검증 인프라 실패를 품질 실패로 오판하면 안 됩니다.
PART 04

CH 8모델에게 올바른 맥락을 제공하는 기술

핵심: RAG의 품질은 벡터 검색 하나가 아니라 청킹, 재정렬, 출처, 시간, 질의 분해, 멀티모달 정합성의 합입니다.

  • 8.1 청킹: 가장 먼저 다듬어야 할 곳 — 문서 구조와 질문 단위가 맞도록 의미 경계를 보존합니다.
  • 8.2 검색 결과는 좋은데 응답이 이상한 이유 — 검색 결과의 순서·중복·상충·프롬프트 배치를 점검합니다.
  • 8.3 단일 검색으로는 답할 수 없는 질문들 — 복합 질문은 분해하고 여러 근거를 결합해야 합니다.
  • 8.4 벡터 검색 너머의 맥락 설계 — 키워드, 메타데이터, 그래프, 재정렬, 규칙 필터를 조합합니다.
  • 8.5 텍스트를 넘어서: 멀티모달 시스템의 맥락 설계 — 이미지·표·음성은 텍스트 변환 손실과 시간/좌표 정렬을 관리합니다.
  • 8.6 맥락이 시간에 따라 썩는 문제 — 최신성, 유효기간, supersedes 관계를 기록합니다.
  • 8.7 맥락의 품질을 측정하는 법 — 검색 재현율과 최종 답변 근거성을 별도로 평가합니다.
  • 8.8 핵심 정리 — 좋은 맥락은 관련성·신뢰성·최신성·충분성을 모두 갖춥니다.
AADS 적용active_project, 최근 handover, 코드·DB 실측, 세션 역할을 한꺼번에 넣되 서로의 우선순위를 정해야 합니다. 오래된 메모리보다 현재 DB와 git 상태를 우선하는 이유입니다.
PART 04

CH 9모델이 외부 세계와 상호작용하는 구조

핵심: 도구 호출은 텍스트 생성과 달리 실제 세계를 바꾸므로 명확한 계약, 최소 권한, 중복 방지, 실패 의미가 필요합니다.

  • 9.1 도구 스키마가 모호하면 잘못된 행동이 실행된다 — 인자 이름·단위·허용값·오류를 모호하지 않게 정의합니다.
  • 9.2 읽기 도구와 쓰기 도구는 위험도가 완전히 다르다 — 조회 실패와 결제·삭제·배포 실패의 위험은 다르므로 승인 수준을 나눕니다.
  • 9.3 최소 권한 원칙: 도구에도 적용된다 — 작업에 필요한 서버·경로·행위만 열어 피해 반경을 제한합니다.
  • 9.4 AI 시대에도 멱등성은 변하지 않는다 — 같은 요청이 재전송돼도 한 번만 반영되도록 키와 상태 전이를 설계합니다.
  • 9.5 도구 실패가 추론을 붕괴시키는 방식 — 빈 결과, 타임아웃, 권한 거부를 “대상 없음”으로 해석하지 않게 오류를 구조화합니다.
  • 9.6 프레임워크보다 원칙이 먼저다 — 프레임워크가 바뀌어도 계약·권한·감사·롤백 원칙은 남습니다.
  • 9.7 핵심 정리 — 도구 결과는 관찰이며 성공 여부는 후속 검증으로 확정합니다.
AADS 적용같은 Idempotency-Key가 동일 실패를 되돌려준 409 사례는 멱등성의 정상 동작이지만 UX는 새 키로 재시도하도록 안내해야 합니다. 또한 승인 없는 배포·재시작·삭제를 금지하는 것은 최소 권한 설계입니다.
PART 04

CH 10자율적으로 판단하고 행동하는 시스템을 설계하는 법

핵심: 모든 문제를 자율 에이전트로 만들 필요가 없습니다. 예측 가능한 워크플로로 풀 수 있는 일은 워크플로가 더 싸고 안전합니다.

  • 10.1 에이전트를 만들지 않는 기술: 워크플로 다섯 패턴 — 순차·분기·병렬·라우팅·평가 루프처럼 통제 가능한 패턴을 먼저 선택합니다.
  • 10.2 계획이 잘못되면 나머지 전부가 잘못된다 — 실행 전에 범위·의존성·완료 기준을 검증합니다.
  • 10.3 멀티스텝에서 불확실성은 곱해진다 — 단계가 늘수록 작은 실패 확률이 누적되므로 체크포인트를 둡니다.
  • 10.4 아무도 트윗하지 않는 이야기: 비용과 안전의 현실 — 반복 사고와 도구 호출은 토큰뿐 아니라 실제 변경 위험을 키웁니다.
  • 10.5 체크포인팅과 롤백: 처음부터 다시 하지 않는 설계 — 중간 상태를 저장하고 마지막 안전 지점부터 재개합니다.
  • 10.6 싱글 에이전트와 멀티 에이전트: 언제 무엇을 선택하는가? — 역할 분리가 검증 이득을 줄 때만 멀티 에이전트를 씁니다.
  • 10.7 자율성의 경계를 설계하라 — 읽기, 제안, 승인 필요 실행, 금지 실행을 명시합니다.
  • 10.8 능력의 분리: 에이전트에게 권한을 주기 전에 — 계획·코드·리뷰·배포 권한을 한 주체에 몰지 않습니다.
  • 10.9 읽기 도구가 공격 통로가 될 때 — 문서 안의 악성 지시를 데이터로 취급하고 시스템 명령과 격리합니다.
  • 10.10 핵심 정리 — 자율성은 능력이 아니라 검증 가능성에 맞춰 부여합니다.
AADS 적용CEO → PM → 개발자 → QA → Ops 역할 분리는 검증 독립성을 위한 것입니다. 다만 같은 모델·같은 맥락을 공유하면 이름만 다른 단일 에이전트가 될 수 있으므로 산출물·권한·평가 기준도 분리해야 합니다.
PART 05

CH 11AI 시스템은 배포되는 순간부터 비용이 된다

핵심: 비용은 모델 단가만이 아니라 입력 길이, 출력 길이, 재시도, 검증 호출, 지연, GPU 유휴 시간의 합입니다.

  • 11.1 추론의 두 단계: 프리필과 디코드 — 긴 입력을 읽는 비용과 새 토큰을 생성하는 비용의 성격을 나눕니다.
  • 11.2 지연 시간, 비용, 품질: 세 가지는 동시에 만족되지 않는다 — 세 목표를 동시에 최대화할 수 없으므로 작업별 우선순위를 정합니다.
  • 11.3 프롬프트 캐싱: 프리필을 건너뛰는 설계 — 반복되는 긴 지시를 재사용해 입력 처리 비용을 줄입니다.
  • 11.4 출력을 줄이는 것이 가장 효과적인 비용 레버다 — 중복 설명과 무제한 로그를 줄이는 것이 가장 직접적인 절감 수단입니다.
  • 11.5 모델 라우팅과 캐스케이딩: 요청마다 적절한 모델을 고르는 법 — 단순 작업은 저비용 모델, 실패·고위험 작업은 강한 모델로 승격합니다.
  • 11.6 배치 처리: 실시간이 아니어도 되는 작업을 분리하라 — 즉시 응답이 필요 없는 평가·요약·인덱싱은 묶어서 처리합니다.
  • 11.7 시맨틱 캐싱: 모델 호출 자체를 건너뛰는 설계 — 의미상 같은 질의의 검증된 답을 재사용하되 최신성 조건을 둡니다.
  • 11.8 에이전트 비용을 구조적으로 관리하는 법 — 최대 단계, 최대 도구 호출, 중단 기준을 작업 계약에 넣습니다.
  • 11.9 온프레미스와 셀프 호스팅: 다른 세계의 최적화 — API 단가 대신 GPU 용량·운영 인력·가용성·전력 비용을 봅니다.
  • 11.10 비용 최적화의 올바른 순서 — 측정 → 불필요 호출 제거 → 출력 축소 → 캐시 → 라우팅 → 인프라 변경 순으로 접근합니다.
  • 11.11 핵심 정리 — 품질 검증을 없애는 비용 절감은 실패 비용을 뒤로 미루는 것입니다.
AADS 적용저비용 조회(DB·코드·로그)를 먼저 하고, 동일 웹 검색과 LLM 검수를 반복하지 않으며, 단순 조회는 소형 모델로 보내는 정책이 직접 연결됩니다. 비용 보고에는 실제 측정값이 없으면 “미측정”이라고 써야 합니다.
PART 05

CH 12감이 아니라 측정으로: 평가 주도 개발

핵심: “좋아 보인다”가 아니라 대표 실패 사례와 성공 기준을 먼저 만들고 변경 전후를 같은 평가셋으로 비교합니다.

  • 12.1 에러 분석: 모든 평가의 출발점 — 실패를 유형화해 가장 큰 오류 묶음부터 고칩니다.
  • 12.2 평가의 3레벨 — 구성요소, 엔드투엔드, 운영 결과를 각각 평가합니다.
  • 12.3 골든 데이터셋: 작게 시작해 살아있게 유지한다 — 작고 대표적인 검증 사례로 시작해 실제 장애를 계속 추가합니다.
  • 12.4 LLM 심판을 신뢰하게 만드는 절차 — 명확한 루브릭, 복수 평가, 인간 표본 검수로 심판 편향을 통제합니다.
  • 12.5 기준은 진화한다: 기준 표류 — 제품·사용자·정책 변화에 맞춰 평가셋과 임계값을 버전 관리합니다.
  • 12.6 평가·가드레일·관측 가능성의 관계 — 평가는 품질을 재고, 가드레일은 위험을 막고, 관측은 운영 중 변화를 찾습니다.
  • 12.7 핵심 정리 — 평가를 릴리스 뒤가 아니라 구현 전 계약으로 둡니다.
AADS 적용Pipeline Runner 리뷰 점수 하나만으로 품질을 확정하면 안 됩니다. 단위 테스트, 계약 테스트, 실제 route/API, 화면 캡처, 5분 P0/P1 모니터링을 위험에 맞춰 조합해야 합니다.
PART 05

CH 13관측되지 않는 AI 시스템은 이미 실패했다

핵심: 사용자 오류를 재현하려면 한 세션 안에서 모델 호출, 검색, 도구, 토큰, 지연, 오류를 하나의 트레이스로 연결해야 합니다.

  • 13.1 AI 관측 가능성의 기본 단위: 세션, 트레이스, 스팬 — 사용자 대화, 한 번의 작업 흐름, 개별 호출 단위를 계층적으로 연결합니다.
  • 13.2 무엇을 기록하고 무엇을 측정해야 하는가? — 입력/출력 버전, 모델, 프롬프트, 도구 결과, 비용, 지연, 오류, 승인자를 기록합니다.
  • 13.3 품질이 조용히 떨어지는 것을 잡는 법 — 기준셋 점수, 재시도율, 사용자 수정률, 검색 근거성을 시간축으로 감시합니다.
  • 13.4 장애를 체계적으로 분류하는 프레임워크 — 모델, 데이터, 검색, 도구, 오케스트레이션, UI, 인프라로 나눠 대응 주체를 정합니다.
  • 13.5 알림 설계: '모든 것에 알림'은 '어떤 것에도 알림이 없는' 것과 같다 — 모든 오류가 아니라 사용자 영향과 긴급도에 따라 알립니다.
  • 13.6 관측 가능성은 처음부터 설계해야 한다 — 나중에 로그를 붙이면 요청 간 연결 ID와 핵심 맥락이 이미 사라집니다.
  • 13.7 핵심 정리 — 로그가 많음과 원인 추적이 가능함은 다릅니다.
AADS 적용session_id, job_id, release SHA, trace/span을 연결해야 “누가 어떤 지시로 어떤 커밋을 배포했는가”를 역추적할 수 있습니다. 타 세션 작업을 현재 세션 보고에 섞지 않는 것도 관측 경계의 문제입니다.
PART 05

CH 14AI 엔지니어는 무엇을 다르게 판단해야 하는가?

핵심: 좋은 AI 엔지니어는 최신 도구를 많이 아는 사람보다, 어디부터 의심하고 무엇을 코드로 고정하며 언제 자동화를 멈출지 아는 사람입니다.

  • 14.1 좋은 AI 엔지니어는 문제를 어디서부터 의심하는가? — 증상 직전 변경과 데이터·검색·도구·UI 경계를 우선 확인합니다.
  • 14.2 차이를 만드는 세 가지 렌즈 — 불확실성, 실패 반경, 검증 가능성으로 설계를 봅니다.
  • 14.3 좋은 AI 엔지니어는 해결책의 순서를 의식적으로 고른다 — 재현 → 범위 축소 → 저비용 원인 배제 → 수정 → 회귀 검증 순서를 지킵니다.
  • 14.4 자동화의 경계선은 검증 가능성이다 — 결과를 독립적으로 검증하고 되돌릴 수 있는 범위까지만 자동화합니다.
  • 14.5 도구보다 오래가는 원칙 — 프레임워크보다 계약, 권한, 버전, 테스트, 관측, 롤백이 오래갑니다.
AADS 적용 결론“AI에게 더 잘하라고 지시”하는 것보다 반복 실패를 게이트·스키마·테스트·상태 머신으로 옮기는 것이 중요합니다. 규칙 위반이 두 번 반복되면 문서 경고가 아니라 코드 차단으로 승격해야 합니다.

APPENDIX A 현업 AI 엔지니어 인터뷰

  • Interview 1 숫자의 이유를 찾다: AI 에이전트 기반 실험 지표 진단 팟을 리드하며 — 숫자 자체보다 변화 원인을 추적하는 질문법을 확인하는 항목입니다.
  • Interview 2 AI는 완성되지 않는다, 도메인을 만나기 전까지는 — 범용 모델이 실제 업무 규칙·사용자·데이터를 만날 때 필요한 보정이 무엇인지 묻는 항목입니다.
  • Interview 3 안 되는 이유를 끝까지 추적하는 일 — 증상을 모델 탓으로 돌리지 않고 데이터·도구·통합 경계까지 원인을 좁히는 태도를 확인하는 항목입니다.
  • Interview 4 “나중에 만들자”가 쌓이면 시스템이 무너진다 — 관측·테스트·데이터 계약 같은 기술부채를 언제 상환해야 하는지 묻는 항목입니다.
