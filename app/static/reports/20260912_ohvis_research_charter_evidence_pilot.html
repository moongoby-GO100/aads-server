1. Research Charter

이 연구가 무엇을 주장하고, 무엇을 주장하지 않는지를 먼저 고정한다.

1.1 연구 형태

항목내용
연구 방법론설계과학 연구(Design Science Research) + 단일 조직 종단 사례연구(longitudinal case study)
분석 단위자율 AI 개발 사이클 1건 = 지시 → 러너 실행 → AI 자동검수 → 승인/반려 → 커밋 → 배포
관측 창2026-07-24 ~ 2026-09-12 (OHVIS 명시 커밋 최초~최근) [Git 로그]
사례 조직1개 조직 · 6개 서비스(AADS/KIS/GO100/SF/NTV2/NAS) · 3개 서버
산출물(artifact)증거 기반 폐쇄루프 멀티에이전트 개발·운영 체계(OHVIS)

1.2 주장 범위 선언

주장한다

  • 인간 1인(CEO)이 다수 AI 에이전트를 지시–검수–승인 루프로 운영하는 구조를 실제 프로덕션에서 7주 이상 지속 운용했다.
  • 그 루프의 각 단계가 DB에 원장으로 남아 사후 감사·재현이 가능하다.
  • 이 구조를 다른 조직이 복제할 수 있도록 설계 원리·실패 모드·가드레일을 문서화할 수 있다.

주장하지 않는다 (현 단계)

  • 생산성·품질·비용의 인과적 개선 효과 — 관찰 데이터만으로는 인과 추론이 불가능하다.
  • 모델 라우팅 전략의 우월성 — 무작위 배정이 없으므로 선택 편향이 통제되지 않는다.
  • 타 조직 일반화 — 단일 조직·단일 의사결정자 사례다.

1.3 완료 기준 (이 Charter가 "끝났다"고 판정하는 조건)

  1. 모든 핵심 주장이 Evidence Manifest(§3)에서 검증 가능한 locator를 갖는다.
  2. 데이터셋 파일럿이 유출 0건으로 재현 가능하다. → §4·§5에서 충족
  3. rejected_done 라벨 의미가 사람 판정으로 확정된다. → 미완
  4. rater A/B 이중 라벨 + Cohen's κ 보고. → 미완

5. 비식별 · 안전성 검증

연구 데이터 반출은 "안 넣었다"가 아니라 "넣고 나서 다시 찾아봤다"로 증명한다.

5.2 의사식별자

case_id·session_pseudo·commit_pseudo·parallel_group은 SHA-256(salt|kind|value) 앞 16자다. salt는 컨테이너 /root/.ohvis_research_salt(권한 0600)에 보관하며 데이터셋 디렉터리와 git 어디에도 포함하지 않는다. salt 없이는 재식별이 불가능하고, salt가 있으면 동일 표본을 재현할 수 있다.

5.3 자체 재스캔 결과

✅ leak_clean: true — 잔존 유출 0건

추출기는 JSONL을 디스크에 쓴 뒤 다시 읽어 16종 유출 패턴으로 전수 재스캔한다. 1건이라도 탐지되면 exit 2로 실패해 산출물 배포를 차단한다.

이번 실행의 redaction 적중은 조직 도메인/계정 일반화 8건뿐이었다 (aads.newtalk.kr 2, newtalk.kr 3, moongoby 3). 키·토큰·PII 적중은 0건이었다.

5.4 운영 안전성

  • DB 접근은 SELECT 단일 쿼리다. INSERT/UPDATE/DELETE/DDL이 코드에 존재하지 않는다.
  • 연결 직후 SET TRANSACTION READ ONLY를 시도한다.
  • 원문 instruction·logs·git_diff 전문은 반출하지 않고 길이만 지표화한다.
  • API·Docker·nginx·활성 러너를 변경하지 않는다.

6. 라벨링 프로토콜 (rater A/B)

자동 라벨은 가설이 아니라 초안이다. 사람 판정 없이는 성공률을 보고하지 않는다.

⚠️ 최우선 쟁점 — rejected_done

전체 820건 중 683건(83.3%)이 rejected_done이다. 코드는 이를 done·approved와 같은 종료군으로 집계하지만 (app/api/admin.py:51, app/api/pipeline_runner.py:821), 명칭은 "반려 후 종료"를 뜻한다. 이 한 라벨의 해석이 논문 결론 전체를 좌우한다. 따라서 자동 확정하지 않고 needs_human_adjudication=true로 표시해 사람 판정으로 넘긴다.

6.1 절차

  1. codebook 작성 — outcome 4범주 + failure_mode 6범주의 포함/제외 기준과 경계 사례를 문서화한다.
  2. 독립 라벨링 — rater A, rater B가 서로의 판정을 보지 않고 30건 전부를 라벨링한다.
  3. 일치도 측정 — Cohen's κ를 계산한다. κ < 0.60이면 codebook을 수정하고 재라벨링한다.
  4. 불일치 조정 — 3인 판정 또는 합의로 확정하고 label_disagreement에 기록한다.
  5. 확정 후에만 빈도·비율·성공률을 산출한다.
