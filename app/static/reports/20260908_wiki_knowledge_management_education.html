2026년 지식화의 정답은 하나의 위키나 하나의 벡터DB가 아닙니다. 실무 최적 구조는 원문 보존 + 근거 청크 + LLM Wiki + 지식그래프 + 벡터/키워드 검색 + 평가/보안 게이트를 결합하는 방식입니다.

1. 핵심 용어

용어쉽게 말하면CEO가 기억할 판단 기준
지식화문서, 대화, 로그, 코드, 검색 결과를 재사용 가능한 사실·절차·판단 규칙으로 바꾸는 작업"저장했다"가 아니라 "다음 실행 품질이 좋아졌는가"로 판단합니다.
RAG질문이 들어올 때 관련 문서 조각을 찾아 LLM에 넣는 방식빠르고 단순하지만, 매번 다시 조립하므로 장기 누적 지식에는 약합니다.
Hybrid Search키워드 검색, 벡터 검색, 메타데이터 필터를 같이 쓰는 방식운영 시스템은 벡터 검색만 쓰면 위험합니다. 프로젝트·날짜·권한 필터가 필수입니다.
GraphRAG문서 안의 사람·파일·시스템·원인·결과 관계를 그래프로 만들고 탐색하는 RAG"왜 반복되는가", "무엇과 연결됐는가" 같은 질문에 강합니다.
LLM WikiLLM이 원문을 읽고 지속적인 위키 페이지와 링크로 컴파일하는 방식반복 질문·장기 프로젝트·경영 판단에 유리하지만, 자동 갱신과 출처 검증이 없으면 썩습니다.
Temporal Knowledge Graph사실이 언제 유효했고 언제 폐기됐는지 시간까지 가진 지식그래프운영 지식은 "예전에는 맞았지만 지금은 틀림"이 많으므로 시간성이 중요합니다.
Context Engineering모델에게 넣을 지시·문서·메모리·도구 결과를 상황별로 설계하는 기술프롬프트보다 넓은 개념입니다. 좋은 답은 좋은 컨텍스트 컴파일에서 나옵니다.
MCPAI 앱이 외부 도구와 자료를 표준 방식으로 연결하는 프로토콜도구 연결은 MCP로 표준화하되, 권한·감사는 AADS DB 정책으로 통제해야 합니다.
Eval검색·답변·인용·정책 준수 품질을 반복 측정하는 테스트 체계지식화의 성공은 "느낌"이 아니라 정확도, 인용률, 최신성, 재발률로 봐야 합니다.

2. 최신 기술 지도

기본Vector RAG

문서를 청크로 자르고 임베딩해 벡터DB에서 의미적으로 가까운 조각을 찾습니다. OpenAI Retrieval 문서는 vector store가 semantic search의 인덱스 역할을 하며, semantic search가 키워드가 거의 겹치지 않아도 의미상 가까운 결과를 찾을 수 있다고 설명합니다.

잘 맞는 경우: FAQ, 정책 문서, 단일 사실 찾기, 문서량이 많고 자주 바뀌는 경우.

주의: 유사한 문서가 최신 문서라는 보장은 없습니다. 반드시 project, source_type, published_at, sensitivity 필터가 필요합니다.

실무 필수Hybrid Search

BM25/키워드 검색, 벡터 검색, SQL exact lookup, 권한/날짜/프로젝트 필터를 조합합니다. 운영 지식에서는 "GO100", "#310", "deploy_runs id=130"처럼 정확히 일치해야 하는 질의가 많으므로 벡터만으로는 부족합니다.

AADS 권장: 정확한 ID·날짜·상태는 SQL, 넓은 의미 검색은 벡터, 원인·영향은 그래프, 최신 외부 사실은 웹/공식문서로 분리합니다.

관계형 지식GraphRAG

Microsoft GraphRAG는 그래프 커뮤니티 리포트와 local/global search를 사용합니다. 넓은 데이터셋의 주제 요약이나 여러 사건의 관계 파악에 강합니다.

잘 맞는 질문: "최근 채팅 장애가 반복된 공통 원인은?", "GO100 주문 차단과 #310 전략카드는 어떤 관계인가?"

주의: 단일 사실 조회에는 과할 수 있습니다. GraphRAG는 모든 질문의 기본값이 아니라 관계형·다중 hop 질문에 써야 합니다.

경량 그래프LightRAG

LightRAG는 그래프 구조와 벡터 표현을 함께 사용하며, 저수준/고수준 검색을 결합하는 dual-level retrieval을 제안합니다. 대형 GraphRAG보다 가볍고 증분 업데이트 관점이 강합니다.

AADS 적용: 매일 쌓이는 채팅, HANDOVER, 러너 결과를 빠르게 그래프/벡터에 반영하는 구조에 적합합니다.

장기 지식LLM Wiki / OpenWiki

Karpathy의 LLM Wiki는 raw document를 매번 검색하는 대신 LLM이 지속적인 Markdown wiki를 만들고 유지하는 패턴입니다. LangChain OpenWiki는 코드베이스나 개인 지식용 Markdown wiki를 작성·유지하는 CLI로 등장했습니다.

장점: 반복 설명 감소, 프로젝트 온보딩 개선, cross-reference 유지, 사람이 검수 가능.

한계: 자동 생성 위키는 틀릴 수 있습니다. claims, source manifest, stale policy, reviewer gate가 필요합니다.

시간성Temporal KG / Graphiti

Zep Graphiti는 대화, 비즈니스 데이터, 문서를 temporal context graph로 만들고, 사실이 바뀌면 오래된 사실을 무효화합니다. vector, full-text, graph traversal을 결합하는 점이 중요합니다.

AADS 적용: 서버명, 배포 슬롯, runner 상태, CEO 결정처럼 시간에 따라 바뀌는 운영 지식에 반드시 필요합니다.

연결 표준MCP

2026-07-28 MCP 사양은 LLM 앱과 외부 데이터·도구를 표준 방식으로 연결합니다. Resources, Prompts, Tools 개념이 있어 wiki page, runbook, DB 조회, 브라우저, 파일 읽기 도구를 같은 표면으로 노출할 수 있습니다.

AADS 적용: 모든 프로젝트 도구를 MCP-like schema로 통일하고, active_project와 승인 정책을 강제해야 합니다.

검증RAG/Eval/Trace

LangSmith RAG 평가와 OpenAI Evals는 정답 정확도뿐 아니라 groundedness, retrieval relevance, grader 기준을 분리해 측정합니다.

AADS 적용: "좋은 답변"을 수동 감으로 보지 말고, 검색 근거 적합도와 답변 인용 충실도를 각각 측정해야 합니다.

보안OWASP / NIST

OWASP LLM Top 10 2025는 prompt injection, sensitive information disclosure, data/model poisoning, excessive agency, vector/embedding weaknesses를 주요 위험으로 제시합니다. NIST AI RMF는 AI 시스템의 설계·개발·사용·평가 전 생명주기 리스크 관리를 강조합니다.

AADS 적용: 외부 문서 ingestion 전 sanitizer, secret scan, trust score, 권한 필터, destructive action gate가 필수입니다.

4. 효과적이고 효율적인 지식화 파이프라인

단계해야 할 일효율화 포인트검수 기준
1. 수집채팅, 파일, 커밋, 로그, DB row, 외부 URL, PDF, 이미지 OCR을 원문으로 보존중복 URL/파일 hash로 재수집 방지source_uri, checksum, accessed_at 존재
2. 정화HTML 노이즈 제거, prompt injection 제거, secret scan, PII 라벨링수집 직후 자동 sanitizer 적용위험 문구·시크릿 미포함
3. 분해문서를 evidence chunk, fact 후보, entity, relation으로 분해구조화 문서는 heading 기반, 코드는 symbol 기반 chunkchunk가 너무 작거나 크지 않음
4. 색인BM25, vector, graph edge, SQL metadata를 모두 구축query type별 색인 선택project/date/sensitivity 필터 가능
5. 컴파일LLM Wiki page, summary, source manifest, 관련 링크를 생성변경된 source만 증분 컴파일claim마다 출처 연결
6. 승격fact -> lesson -> procedure -> policy -> skill로 승격반복 성공/실패만 승격해 노이즈 억제confidence, reviewer, evidence_level 존재
7. 적용프롬프트, runbook, tool policy, UI, 코드 개선에 반영skill search로 필요한 것만 로딩compiled_prompt_provenance 또는 trace로 확인
8. 평가retrieval recall, groundedness, citation coverage, stale rate 측정대표 질문 세트 자동 회귀기준 미달 시 자동 개선 후보 생성

예시 3. 교육자료를 지식화하는 방식

1. HTML/Markdown 보고서를 source로 저장
2. 각 장을 evidence chunk로 분해
3. 핵심 claim을 memory_facts로 승격

8. 검증 지표와 CEO 완료 판정법

지표의미권장 기준왜 중요한가
Source Coverage답변 claim 중 출처가 붙은 비율운영 보고 90% 이상근거 없는 단정 방지
Retrieval Recall정답에 필요한 근거를 검색했는가핵심 질문 세트 85% 이상좋은 생성보다 좋은 검색이 먼저
Citation Support인용한 출처가 해당 claim을 실제로 지지하는가중요 보고 95% 이상출처 장식 방지
Stale Fact Rate폐기된 사실이 답변에 섞인 비율고위험 운영 0%날짜·상태가 바뀌는 시스템에서 치명적
Query Cost질문당 토큰/도구 비용질문 유형별 budget 설정위키가 항상 RAG보다 싸지는 않음
Time To AnswerCEO가 답을 받기까지 걸린 시간상태조회 3초, 분석형은 단계 보고운영 의사결정 속도
Repeat Error Rate같은 오류가 다시 발생한 비율error_book 등록 후 감소 추세지식화가 실제 행동을 바꿨는지 확인
Promotion Precision승격한 기억이 실제로 유용한 비율저품질 memory 자동 강등기억이 많을수록 노이즈 관리가 중요

CEO가 보고 받을 때 확인할 5문장

1. 이 답변의 원문 출처는 어디입니까?

2. 현재 상태 수치는 DB/로그에서 방금 조회했습니까?

3. 이 지식은 어느 프로젝트와 어느 시점까지 유효합니까?

4. 이 결론에 반대되는 과거 지식이나 충돌 사실은 없습니까?

5. 다음번 같은 질문에서 더 빨라지도록 wiki/fact/skill/error book에 무엇을 남겼습니까?

def compile_context(question, project, intent, risk):
    if asks_current_state(question):
        return sql_lookup(project, question) + recent_logs(project)

    if asks_code_behavior(question):
        return code_search(question) + wiki_pointer(project, "code")

    if asks_relationship_or_root_cause(question):
        return temporal_graph_search(project, question) + error_book(project)

    if asks_broad_education_or_strategy(question):
        return wiki_search(project, question) + official_sources(question)

    if asks_external_latest(question):
        return official_web_search(question, accessed_at_kst=now())

    return hybrid_rag(project, question, filters={
        "project": project,
        "sensitivity": allowed_for_user(),
        "valid_at": now()
    })
