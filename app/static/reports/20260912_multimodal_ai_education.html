🌐 01. 멀티모달 AI란 무엇인가 — 2026년 9월 지형

멀티모달 AI(Multimodal AI)란 텍스트 하나만이 아니라 이미지·영상·음성·문서·3D 등 서로 다른 "형태(modality)"의 정보를 함께 입력받아 이해하거나, 반대로 그런 형태로 결과물을 생성할 수 있는 AI를 말합니다. 2023~2024년까지는 "텍스트 모델에 이미지 이해 기능을 얹은" 수준이었다면, 2026년 9월 현재는 프론티어 3사(Anthropic·Google·OpenAI) 모두 이미지·문서 이해를 기본 탑재하고, 이미지·영상·음성·음악 생성은 별도 특화 모델로 갈라져 있는 "코어 모델 + 위성 생성 모델" 구조가 정착했습니다.

👁️ 02. 비전 입력 이해 — 이미지·문서·차트를 읽는 방법

비전 지원 모델은 이미지를 받으면 내부적으로 작은 타일(patch)로 쪼개 이를 텍스트 토큰과 같은 "토큰" 형태로 변환한 뒤 언어모델에 함께 넣습니다. 즉 이미지 한 장도 결국 "토큰 뭉치"로 과금되며, 해상도가 높거나 이미지 장수가 많을수록 토큰 소모(=비용)가 커집니다. 정확한 타일 크기·토큰 환산 공식은 제공사·모델별로 다르고 수시로 바뀌므로 본 문서에서는 구체적 환산표를 확정값으로 제시하지 않고 "미검증"으로 남겨두며, 실제 예산 산정 시 각사 공식 문서의 최신 계산기를 사용해야 합니다.

이미지 이해 vs 문서(PDF) 이해 vs 차트/표 이해

유형모델이 하는 일실무 함정
일반 이미지사물 인식, 장면 설명, 스타일 판단브랜드 로고·유명인 식별은 정책상 회피되도록 설계된 경우가 많음(4장 참조)
문서(PDF/스캔본)레이아웃을 고려한 텍스트 추출, 표 구조 인식다단 레이아웃·손글씨·저해상도 스캔에서 정확도 급락
차트/그래프축·범례를 읽어 수치를 추정정확한 숫자를 "추정"하는 것이므로 그래프에서 읽은 숫자를 의사결정 근거로 바로 쓰면 위험 — 반드시 원본 데이터와 대조 필요
차트 오독 위험비전 모델은 막대그래프의 정확한 수치를 "읽는" 것이 아니라 "추정"합니다. 재무 차트, KPI 대시보드 스크린샷을 AI에게 분석시킬 때는 반드시 원본 수치 데이터(CSV/DB)를 함께 제공하거나, 결과를 원본과 대조 검증해야 합니다.

실무 팁

  • 고해상도 캡처: 작은 글씨가 포함된 UI 스크린샷은 원본 해상도 그대로, 불필요하게 축소하지 않는다.
  • 크롭: 분석 대상이 이미지의 일부라면 미리 크롭해서 보내면 토큰(=비용)도 줄고 정확도도 올라간다.
  • 대비/화질: 스캔 문서는 그레이스케일 대비를 높이면 텍스트 인식률이 개선되는 경우가 많다.
📌 CEO 체크포인트
  1. 재무·매출 차트를 AI에게 "읽혀서" 보고받는 경우, 반드시 원본 수치와 대조된 값인지 확인을 요구한다.
  2. 이미지 분석 비용이 예상보다 크다는 보고를 받으면 해상도·크롭 최적화가 되어 있는지 먼저 확인을 지시한다.
  3. 손글씨·저해상도 문서가 많은 업무는 비전 모델 단독이 아니라 사람 검수를 포함한 이중 확인 프로세스를 요구한다.

📄 03. OCR·문서 파싱 — 클라우드 vs 로컬

문자를 이미지에서 뽑아내는 방법은 크게 두 갈래입니다. 하나는 비전 LLM에게 "이 이미지의 글자를 읽어줘"라고 프롬프트로 요청하는 방식이고, 다른 하나는 전통적인 OCR 엔진(패턴 인식 기반)을 별도로 돌리는 방식입니다. 전자는 문맥을 이해하며 정리된 형태로 답을 주지만 토큰 비용이 들고, 후자는 빠르고 저렴하지만 문맥 이해 없이 글자만 뽑아냅니다.

AADS 실측 — 로컬 OCR 브릿지 구조

AADS는 app/core/local_ocr_bridge.py와 app/api/local_media_router.py를 통해 클라우드 비전 API가 아니라 CEO의 PC에 설치된 로컬 에이전트(PC Agent, 127.0.0.1:8102)에 OCR 실행을 위임하는 구조를 쓰고 있습니다. 요청은 /api/v1/local/ocr로 들어와 PC Agent의 route-execute 엔드포인트로 전달되고, 결과는 text / confidence / language 필드로 반환됩니다. 언어 기본값은 kor+eng(한글+영어 동시 인식)입니다. 이 구조는 API 토큰 비용이 들지 않는 대신, PC Agent가 연결되어 있지 않으면(agent_id 없음) 즉시 실패하는 단일 장애점이 됩니다.

방식비용정확도 특성가용성 리스크

🎨 04. 이미지 생성·편집 — 모델 지형과 비용 구조

🧪 09. 비전 기반 QA·UI 검증 자동화

화면(UI)이 의도대로 보이는지 자동으로 검증하는 방법은 크게 두 가지입니다. 하나는 스크린샷을 픽셀 단위로 비교하는 결정론적(deterministic) 방식이고, 다른 하나는 비전 LLM에게 "이 화면이 정상으로 보이나요?"라고 판단을 맡기는 방식입니다. AADS는 두 방식을 모두 구현해 두었습니다.

실측 ① — Playwright + 픽셀 diff (app/services/visual_qa.py, 341줄)

Playwright로 헤드리스 브라우저를 띄워 지정 페이지를 스크린샷 촬영한 뒤, Pillow의 ImageChops.difference로 현재 화면과 기준(baseline) 이미지를 픽셀 단위 비교합니다. 코드 실측 결과 차이 픽셀 비율이 1.0% 미만이면 "일치(match)"로 판정하며, 불일치 시 차이를 10배 증폭한 diff 이미지를 별도 저장합니다. 이 방식은 비전 LLM 토큰을 전혀 쓰지 않아 비용이 거의 없고 결과가 항상 재현 가능(deterministic)합니다.

실측 ② — Claude Vision 기반 판단형 QA (model_routing_preferences, visual_qa 라우트)

DB 라우팅 테이블에는 visual_qa 라우트가 anthropic / claude-vision을 기본값(notes: "Visual QA without Google")으로 등록되어 있습니다. 이는 "레이아웃이 자연스러운가", "디자인 의도와 맞는가"처럼 픽셀 비교로는 판단할 수 없는 주관적·맥락적 평가에 쓰이는 것으로 보이며, 픽셀 diff와는 별개의 목적입니다.

실측 ③ — 정적 코드 스캔 QA (app/services/design_qa_scorer.py, 796줄)

이 서비스는 비전 모델을 전혀 쓰지 않고, 변경된 소스 코드를 정규식으로 스캔해 접근성 힌트(aria-*, alt=, focus/focus-visible)와 반응형 폰트 스케일링(vw/vh/vmin/vmax 단위 사용) 여부를 점수화합니다. 총점 90점 이상 "승인 후보", 80점 이상 "조건부 승인", 70점 이상 "수정 필요", 미만 "반려"로 등급을 매깁니다(코드 실측, SCORING_VERSION = "static-v1").

✅ 픽셀 diff / 정적 스캔이 유리한 경우

회귀 테스트처럼 "이전과 똑같아야 한다"가 기준일 때. 비용이 거의 없고 결과가 항상 동일하게 재현된다.

⚠️ 비전 LLM 판단이 필요한 경우

"디자인이 좋아 보이는가"처럼 정답이 하나가 아닌 주관적 평가. 비용이 들고 같은 화면도 실행마다 판단이 미세하게 달라질 수 있다.

📌 CEO 체크포인트
  1. UI 회귀 테스트 보고를 받을 때 "픽셀 diff로 통과했다"인지 "비전 LLM이 괜찮다고 판단했다"인지 구분해서 보고받는다 — 신뢰 수준이 다르다.

🔥 12. AADS 실측 ② 이미지 생성 35만 건 실패의 교훈

11장에서 확인한 image / gemini 조합의 실패 352,173건을 error_message 기준으로 세분화하면, R-KEY 규칙("API 키를 하드코딩하지 마라, 유출 시 영구 비활성화된다")이 왜 존재하는지를 숫자로 보여주는 사례가 나타납니다.

재시도 폭풍(Retry Storm)의 비용

키가 정지되거나 크레딧이 고갈된 뒤에도 35만 건 이상의 호출이 계속 시도되었다는 것은, 실패가 감지된 즉시 해당 경로를 차단하는 서킷 브레이커(circuit breaker)가 없었거나 늦게 작동했다는 뜻입니다. API 호출 자체는 실패해도 네트워크 요청·로깅·재시도 스케줄링에는 인프라 비용이 들고, 장애 원인 파악도 로그가 뒤섞여 더 어려워집니다.

이미 조치된 사실도 확인됨DB 실측 결과 현재 image, edit_image, video 라우트의 Google/Gemini 항목에는 모두 "Google/Gemini commercial routes disabled by CEO policy 2026-09-02 KST"라는 메모가 달려 비활성화되어 있습니다. 즉 CEO가 이미 정책적으로 해당 경로를 차단한 상태이며, 이번 35만 건 실패 데이터는 그 차단 조치 이전 기간(2026-05-15~정책 시행일)의 누적 기록으로 보입니다. 현재 시점 기준으로는 같은 실패가 반복되지 않도록 막혀 있는 것으로 실측됩니다.
📌 CEO 체크포인트
  1. 키 정지·크레딧 고갈 같은 "복구 불가능한" 오류가 감지되면 자동으로 해당 라우트를 즉시 차단하는 서킷 브레이커 로직이 모든 미디어 라우트에 적용되어 있는지 점검을 지시한다.
  2. 2026-09-02 정책 차단 이전 35만 건 규모의 실패가 쌓이는 동안 알림(텔레그램 등)이 왜 조기에 CEO에게 도달하지 않았는지 원인 조사를 요구한다.
