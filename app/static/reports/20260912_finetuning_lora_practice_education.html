🎓 01. 파인튜닝이란 무엇인가

파인튜닝(Fine-tuning)은 이미 대규모로 사전학습(pretraining)된 언어 모델의 가중치를 추가 데이터로 다시 학습시켜, 특정 도메인·과제·말투에 맞게 조정하는 작업입니다. 모델을 "처음부터 만드는 것"이 아니라 "이미 잘 만들어진 모델을 우리 업무에 맞게 미세 조정"하는 것입니다.

💡 CEO를 위한 한 줄 정의 파인튜닝 = 범용 AI를 "우리 회사 전용 AI"로 바꾸는 재학습 작업. 프롬프트 작성보다 비싸고 느리지만, 반복적으로 같은 형식·톤·판단 기준이 필요한 업무에서 장기적으로 비용과 품질 이득을 줍니다.

1-1. LLM 커스터마이징의 스펙트럼

회사 업무에 AI를 맞추는 방법은 여러 단계가 있으며, 아래로 갈수록 비용·기술 난이도·효과가 모두 커집니다.

대부분의 업무는 프롬프트 엔지니어링이나 RAG만으로 해결됩니다. 파인튜닝은 이 두 가지로도 해결되지 않는, "모델의 기본 행동 패턴 자체"를 바꿔야 하는 경우에만 검토합니다.

1-2. 파인튜닝이 실제로 바꾸는 것

출력 형식·톤

매번 같은 포맷(JSON 구조, 보고서 양식, 존댓말 정책)을 지시 없이 자동으로 따르게 함

도메인 어휘·판단 기준

업계 전문 용어, 사내 코드명, 반복적인 분류·판정 기준을 모델이 "체화"하게 함

추론 비용·속도

긴 시스템 프롬프트·few-shot 예시를 매 호출마다 넣지 않아도 되어 토큰 비용 절감

소형 모델의 특화 성능

작은 모델(7B~13B)을 특정 과제에 파인튜닝하면 훨씬 큰 범용 모델을 능가하는 경우가 있음(QLoRA 논문 사례, Dettmers et al., 2023)

파인튜닝은 새로운 지식을 주입하는 방법이 아닙니다. "최신 정보"나 "회사 내부 문서 검색"이 목적이면 RAG가 정답이며, 파인튜닝으로 이를 해결하려 하면 비용만 크고 효과는 낮습니다(2장에서 상세 비교).

✅ CEO 체크포인트
  • 우리 팀이 원하는 것이 "AI가 새 정보를 알게 하는 것"인지 "AI가 항상 같은 방식으로 행동하게 하는 것"인지 구분했는가
  • 프롬프트·RAG로 먼저 시도해보았는가 (파인튜닝은 항상 마지막 옵션)
  • 파인튜닝 1회 학습 비용이 아니라, 데이터 제작+검증+재학습까지 포함한 총비용을 파악하고 있는가

⚖️ 02. 해야 하는 경우 vs 하면 안 되는 경우

파인튜닝은 "언제 효과적인가"보다 "언제 하면 안 되는가"를 먼저 아는 것이 중요합니다. 업계에서 가장 흔한 실패는 RAG나 프롬프트로 해결 가능한 문제를 파인튜닝으로 풀려다 시간과 비용만 태우는 경우입니다.

✅ 파인튜닝이 맞는 신호

  • 같은 유형의 요청이 수천~수만 건 반복된다
  • 정답 형식·기준이 명확하고 일관되다(라벨링 가능)
  • 양질의 학습 데이터를 수백~수천 건 이상 확보(또는 확보 가능)하다
  • 프롬프트 엔지니어링으로 6개월 이상 시도했지만 한계에 부딪혔다
  • 추론 비용·지연시간이 비즈니스에 실질적 영향을 준다

❌ 파인튜닝을 피해야 할 신호

  • 요구사항이 자주 바뀐다(주기적 재학습 부담)
  • 필요한 지식이 계속 갱신되어야 한다(뉴스, 재고, 가격)
  • 학습 데이터가 편향되었거나 라벨이 일관되지 않다
  • 답변의 근거·출처 제시가 법적/규제 요건이다
  • 아직 프롬프트/RAG를 충분히 시도하지 않았다
⚠️ 업계 통설(공식 통계 아님, 실무 경험 기반) 많은 LLM 실무 가이드(Hugging Face, OpenAI 자체 파인튜닝 모범사례 문서 등)가 공통적으로 강조하는 원칙: "프롬프트 엔지니어링 → RAG → 파인튜닝" 순서로 시도하고, 앞 단계에서 목표 품질에 도달하면 파인튜닝을 건너뛰라는 것입니다. 파인튜닝을 먼저 시도했다가 실패하는 사례의 상당수는 애초에 프롬프트/RAG로 해결 가능한 문제였습니다.
✅ CEO 체크포인트
  • 이 업무가 "지식 문제"(RAG로 해결)인지 "행동 패턴 문제"(파인튜닝으로 해결)인지 팀과 명확히 구분했는가
  • 같은 요청이 월 몇 건 발생하는지, 파인튜닝 없이 처리 시 비용이 얼마인지 수치로 파악했는가
  • 학습 데이터 100건 미만 상태에서 파인튜닝을 먼저 제안받았다면 반려하고 데이터 확보를 먼저 요구했는가

🧬 03. 학습 방식 계보

오늘날 상용 LLM(GPT, Claude, Gemini 계열)은 단일 학습 과정이 아니라 여러 단계를 거쳐 만들어집니다. 파인튜닝을 이해하려면 이 전체 계보 속에서 어느 단계에 해당하는지 알아야 합니다.

LLM 학습 단계 계보
① 사전학습 (Pretraining)
   인터넷 텍스트 수조 토큰으로 "다음 단어 맞추기" 학습
   → 결과물: 베이스 모델 (지식은 있지만 지시를 따르지 않음)
        │
        ▼
② SFT (Supervised Fine-Tuning, 지도 파인튜닝)
   사람이 작성한 "질문-모범답안" 쌍으로 지시 따르기 학습
   → 결과물: 지시를 따르는 모델 (아직 선호도 미반영)
        │
        ▼
③ 선호학습 (Preference Learning)
   RLHF: 사람이 답변 여러 개를 순위 매김 → 보상모델 학습 → 강화학습(PPO)
   DPO : 보상모델·강화학습 없이 선호 쌍(A>B)으로 직접 최적화 (Rafailov et al., 2023)
   GRPO: 그룹 내 상대 점수로 베이스라인 추정, 별도 크리틱 모델 불필요 (Shao et al., 2024, DeepSeekMath)
   → 결과물: 더 안전하고, 더 도움되고, 사람이 선호하는 답변을 하는 모델
        │
        ▼
④ 강화 파인튜닝 (Reinforcement Fine-Tuning, RFT)
   채점 가능한 과제(수학, 코딩, 규칙 기반 판정)에 대해 보상 함수로 직접 강화학습
   OpenAI가 API로 제공하는 최신 파인튜닝 방식 (2026-09 기준 공식 지원)
   → 결과물: 특정 과제에서 정답률 자체가 향상된 모델

3-1. 단계별 비교

단계데이터 형태목적기업이 직접 하는 경우
사전학습비정형 텍스트 수조 토큰범용 언어능력·지식 습득거의 없음 (수백만~수천만 달러 소요)
SFT질문-모범답안 쌍지시 따르기, 형식 학습가장 흔함 (기업 파인튜닝의 대부분)

💡 대부분의 기업 파인튜닝 = SFT 이 문서에서 다루는 "파인튜닝 실무"는 대부분 SFT + LoRA/QLoRA 조합을 의미합니다. DPO·GRPO·RFT는 이미 SFT된 모델을 한 단계 더 다듬는 고급 기법으로, 데이터 제작 난이도와 인프라 요구사항이 훨씬 높습니다.
✅ CEO 체크포인트
  • 우리가 필요한 것이 SFT(형식·지시 학습)인지, DPO(톤·선호도 조정)인지 구분했는가
  • "강화학습으로 정답률을 높인다"는 제안을 받았다면, 채점 함수(무엇이 정답인지 자동 판정하는 로직)가 실제로 설계 가능한 과제인지 확인했는가
  • 사전학습(모델 자체 제작)은 사실상 우리 규모에서 비현실적이라는 점을 팀 전체가 공유하고 있는가

🔧 04. PEFT 기법 비교

PEFT(Parameter-Efficient Fine-Tuning, 파라미터 효율적 파인튜닝)는 모델 전체가 아니라 일부 파라미터만 학습하여 GPU 메모리와 학습 비용을 크게 줄이는 기법군입니다. 오늘날 기업 파인튜닝의 사실상 표준입니다.

🎛️ 05. LoRA 핵심 하이퍼파라미터

LoRA는 원래 가중치 행렬 W를 고정하고, 저랭크(low-rank) 행렬 A·B의 곱(BA)만 학습해 W에 더합니다. 이때 결과 품질을 좌우하는 4가지 핵심 설정값이 있습니다. 비개발자도 이 4가지의 "의미"만 이해하면 팀의 제안을 검증할 수 있습니다.

하이퍼파라미터의미낮을 때높을 때실무 권장 범위
rank (r)저랭크 행렬의 "폭". 학습 가능한 표현력의 크기파라미터 적음, 과적합 위험 낮음, 복잡한 패턴 학습 어려움표현력 커짐, VRAM·학습시간 증가, 과적합 위험 상승8~64 (단순 형식학습: 8~16, 복잡한 도메인 지식: 32~64)
alpha (α)LoRA 업데이트의 스케일(강도) 조절 계수. 실제 적용 강도는 보통 α/r 비율로 결정원본 모델 영향력 유지, 변화 미미학습된 패턴이 강하게 반영, 불안정 위험보통 r과 동일하거나 2배(예: r=16 → α=16~32)
target modules어느 레이어(Q/K/V/O, FFN 등)에 LoRA를 적용할지 선택Attention의 Q,V만 적용 시 파라미터 최소, 성능 제한적모든 선형 레이어(Q,K,V,O,gate,up,down)에 적용 시 성능 향상, VRAM 증가전체 선형 레이어 적용이 최근 표준(품질 우선 시)
learning rate가중치 업데이트 보폭학습 느림, 수렴 안 될 수 있음발산·불안정, 원본 능력 손상(카타스트로픽 포게팅 위험 상승)1e-4~2e-4 (LoRA는 Full FT보다 10배가량 높은 학습률 사용이 일반적)
💡 비개발자를 위한 비유 rank는 "얼마나 섬세하게 조정할 수 있는 다이얼의 개수", alpha는 "그 다이얼을 실제로 얼마나 세게 돌릴지"에 해당합니다. target modules는 "모델의 어느 부위를 조정 대상에 포함할지"이고, learning rate는 "한 번에 얼마나 크게 돌릴지"입니다. 다이얼이 너무 많고(rank↑) 세게 돌리면(alpha·lr↑) 원래 잘하던 것까지 망가질 위험이 커집니다.

5-1. 흔한 설정 실수

  • rank를 무작정 크게 설정 — "크면 좋겠지" 식으로 rank=128 이상을 쓰면 Full FT에 근접한 VRAM을 요구하면서도 LoRA의 이점(빠른 학습, 낮은 과적합)을 잃음
  • target modules를 Q,V만으로 제한 — 원 LoRA 논문의 초기 실험 설정을 그대로 따라 하는 경우가 많으나, 최근 실무에서는 모든 선형 레이어 적용이 더 나은 결과를 내는 경우가 많음(과제·모델에 따라 다름)
  • learning rate를 Full FT 기준값(1e-5 수준) 그대로 사용 — LoRA는 학습 파라미터가 훨씬 적어 더 높은 학습률이 필요. 너무 낮으면 학습이 사실상 진행되지 않음
✅ CEO 체크포인트
  • 팀이 제시한 rank·alpha 값의 근거(과거 실험 결과, 벤치마크)를 물어보았는가
  • "기본값 그대로 썼다"는 답변이 나온다면, 최소 1회 이상 rank·target modules를 바꿔 비교 실험을 요구했는가
  • 학습 결과가 기대에 못 미칠 때, 데이터 문제인지 하이퍼파라미터 문제인지 구분해서 보고받고 있는가

🧪 07. 합성 데이터 생성과 위험

실제 데이터가 부족할 때, 다른 LLM(예: 상위 모델)으로 학습 데이터를 합성 생성(synthetic data generation)하는 방법이 널리 쓰입니다. 비용 효율은 높지만 두 가지 핵심 위험이 있습니다.

7-1. 모델 붕괴 (Model Collapse)

⚠️ 모델 붕괴란 AI가 생성한 데이터로 AI를 계속 학습시키면, 세대를 거듭할수록 데이터의 다양성이 줄고 분포의 "꼬리(rare/특이 케이스)"가 사라지는 현상입니다. 결과적으로 모델이 점점 더 획일적이고 반복적인 출력을 내게 됩니다. 이 현상은 학계에서 이론적·실증적으로 논의되고 있는 문제이며, 합성 데이터의 비중이 높을수록, 세대를 반복할수록 위험이 커진다는 것이 공통된 지적입니다.
  • 완화 방법: 합성 데이터와 실제(사람이 작성/검수한) 데이터를 혼합하고, 실제 데이터 비중을 일정 이상 유지
  • 완화 방법: 합성 데이터를 그대로 쓰지 않고, 사람이 샘플링 검수 후 사용
  • 완화 방법: 매 학습 라운드마다 새로운 실제 데이터를 추가 투입

7-2. 라이선스 문제

위험 유형내용대응
생성 모델 약관 위반일부 상용 LLM 제공사는 자사 모델 출력을 "경쟁 모델 학습에 사용 금지"로 약관에 명시합성 데이터 생성에 사용할 모델의 이용약관(Usage Policy)을 사전 확인
원천 데이터 저작권크롤링한 웹 텍스트·이미지에 저작권이 있는 경우 파인튜닝 데이터로 사용 시 분쟁 소지라이선스가 명확한 데이터(공개 라이선스, 자체 생성 데이터) 우선 사용
개인정보 포함실제 고객 상담 로그 등을 합성 데이터 생성 프롬프트에 그대로 투입 시 정보 유출 위험익명화·가명처리 후 사용(개인정보보호법 준수)
✅ CEO 체크포인트
  • 합성 데이터를 생성하는 데 사용한 모델의 이용약관이 "그 출력을 학습에 재사용"하는 것을 허용하는지 확인했는가
  • 합성 데이터와 실제 데이터의 비율이 어느 정도인지, 실제 데이터 없이 100% 합성으로만 학습하지 않는지 확인했는가
  • 합성 데이터 생성 프롬프트에 실제 고객·직원 개인정보가 포함되지 않았는지 검토했는가

🚨 10. 실패 패턴과 진단법

10-1. 카타스트로픽 포게팅 (Catastrophic Forgetting)

정의 새로운 과제를 학습하는 과정에서 기존에 잘 하던 다른 과제의 능력을 잃어버리는 현상. LLM 연속 파인튜닝 맥락에서 실증적으로 연구되어 온 문제입니다(예: Luo et al., "An Empirical Study of Catastrophic Forgetting in Large Language Models During Continual Fine-tuning", arXiv:2308.08747).
  • 증상: 파인튜닝 후 목표 과제는 잘하지만, 일반 상식 질문이나 범용 대화 품질이 눈에 띄게 저하됨
  • 원인: 지나치게 높은 학습률, 너무 많은 epoch, 좁고 편향된 데이터셋
  • 진단: 파인튜닝 전후로 범용 벤치마크(예: MMLU류 일반 지식 평가)를 함께 비교 측정
  • 완화: 학습률 낮추기, LoRA rank 축소, 데이터셋에 일반 대화 샘플 일부 혼합, 조기 종료(early stopping)

10-2. 과적합 (Overfitting)

  • 증상: 학습 데이터의 질문은 완벽히 답하지만, 표현만 살짝 바뀐 새 질문에는 엉뚱한 답을 함. 학습 손실(loss)은 계속 낮아지는데 검증 손실은 어느 시점부터 다시 올라감
  • 원인: 데이터 부족, 지나친 epoch 반복, rank가 데이터 규모 대비 과도하게 큼
  • 진단: 학습/검증 손실 곡선을 반드시 함께 모니터링. 두 곡선이 벌어지기 시작하는 지점이 과적합 시작점
  • 완화: 데이터 증강, 조기 종료, rank·epoch 축소, dropout 적용

10-3. 데이터 누출 (Data Leakage)

  • 증상: 테스트 세트 점수가 비정상적으로 높게 나오지만 실제 운영 환경에서는 품질이 그만큼 나오지 않음
  • 원인: 같은 문서에서 파생된 샘플이 학습·검증·테스트 세트에 중복 분산, 중복제거 미실시
  • 진단: 세트 간 문서 ID 중복 여부를 프로그램으로 검사(수작업 확인 불가)
  • 완화: 6장의 분할 원칙(문서 단위 분할) 준수, 유사도 기반 중복 검사 도구 사용

🎯 13. AADS/GO100/SF 후보 업무 판단

조건 1: 반복 빈도

조건 2: 형식 일관성

조건 3: 데이터 가용성

조건 4: 안정성

🗺️ 14. 실전 로드맵

Phase 1: 문제 정의 (1주, 비용 $0)

목표: 파인튜닝이 정말 필요한지 검증
  1. 2장 판별표로 파인튜닝 적합 여부 판정
  2. 프롬프트 엔지니어링만으로 목표 품질에 도달하는지 최소 2주 시도
  3. RAG로 해결되는 부분과 파인튜닝이 필요한 부분을 분리

Phase 2: 데이터 파일럿 (2~3주, 비용 $500~2,000, 약 69~276만원)

목표: 소규모 데이터로 효과 검증
  1. 6장 파이프라인으로 200~500건 파일럿 데이터셋 제작
  2. QLoRA로 7B 오픈소스 모델 소규모 학습(클라우드 GPU 수 시간)
  3. 10장 진단법으로 과적합·포게팅 여부 점검
  4. Go/No-go 결정 — 효과 없으면 여기서 중단

Phase 3: 본 학습·평가 (3~6주, 비용 $2,000~10,000, 약 276~1,380만원)

목표: 실사용 가능한 모델 확보
  1. 데이터셋을 목표 규모(수천 건)로 확장, 검증 절차 강화
  2. rank·target modules·learning rate 비교 실험(5장)
  3. 11장 평가 절차(정량+정성+A/B) 수행
  4. 버전 관리 체계 구축

Phase 4: 배포·운영 (지속)

목표: 안정적 운영과 지속 개선
  1. 카나리 배포 → 전면 배포(11장)
  2. 운영 중 피드백 수집 → 재학습 데이터로 축적
  3. 분기 단위 재학습 검토(요구사항 변화 반영)
  4. 추론 비용을 기존 API 대비 정기 비교, ROI 추적
