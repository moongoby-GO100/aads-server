🖥️ 01. LLM 서버란 무엇인가

LLM 서버는 대규모 언어 모델(Large Language Model)을 실행하여 텍스트를 생성하는 추론(inference) 서비스를 제공하는 서버입니다. ChatGPT 같은 서비스의 뒷단에서 실제로 모델이 돌아가는 서버가 바로 LLM 서버입니다.

핵심 구성 요소

모델 가중치 (Weights)

수십억~수천억 개의 파라미터를 담은 파일. GPU VRAM에 올려야 추론 가능. 7B 모델 ≈ 14GB(FP16), 70B 모델 ≈ 140GB(FP16)

추론 엔진 (Inference Engine)

모델을 로드하고 토큰을 생성하는 소프트웨어. vLLM, TGI, llama.cpp, TensorRT-LLM 등

API 서버

외부 요청을 받아 추론 엔진에 전달하고 결과를 반환. OpenAI 호환 API가 표준

GPU 하드웨어

모델 연산을 수행하는 핵심 장치. VRAM 용량이 올릴 수 있는 모델 크기를 결정

🎯 02. 왜 자체 LLM 서버가 필요한가

✅ 자체 서버의 장점

  • 데이터 보안 — 민감 데이터가 외부로 전송되지 않음
  • 비용 절감 — 대량 사용 시 API 과금보다 저렴 (월 50만 토큰 이상)
  • 커스터마이징 — 도메인 특화 파인튜닝 자유
  • 무제한 사용 — Rate limit 없음, 24시간 가용
  • 지연시간 — 내부 네트워크로 응답 속도 향상
  • 규제 준수 — 금융/의료/공공 데이터 처리 요건 충족

❌ 자체 서버의 단점

  • 초기 투자 — GPU 서버 $10,000~$300,000+ (약 1,380만~4.14억원+)
  • 운영 부담 — 장비 관리, 업데이트, 장애 대응 인력 필요
  • 모델 품질 — 최상위 상용 모델(GPT-4o, Claude Opus) 대비 성능 차이
  • 확장성 — 트래픽 급증 시 GPU 추가 시간 필요
  • 전력/냉각 — GPU 서버 1대당 1~4kW 전력, 전용 냉각 필요
💡 판단 기준 월 API 비용이 GPU 서버 월 감가상각(서버가격÷36개월) + 전기 + 인건비를 초과하면 자체 서버가 유리합니다.
일반적으로 월 $3,000~5,000 이상 (약 414~690만원) API 비용을 쓰는 조직이 자체 서버 전환을 검토합니다.

6-3. 핵심 기술 용어

Tensor Parallelism (TP)

하나의 모델을 여러 GPU에 나눠 올리는 방식. 70B 모델을 40GB GPU 4장에 분산. --tensor-parallel-size 4

PagedAttention

vLLM의 핵심 기술. GPU 메모리를 OS의 가상 메모리처럼 페이지 단위로 관리하여 KV 캐시 낭비를 90% 이상 줄임

Continuous Batching

요청이 완료될 때마다 새 요청을 즉시 투입. 기존 배치 방식 대비 처리량 2~5배 향상

KV Cache

이전 토큰의 Key-Value를 저장해 중복 연산 방지. 긴 컨텍스트일수록 VRAM 소모 증가. 128K 컨텍스트는 VRAM 수십 GB 필요

Speculative Decoding

작은 모델이 초안을 빠르게 생성하고, 큰 모델이 검증만 수행. 레이턴시 2~3배 단축

Flash Attention

어텐션 연산을 타일 단위로 분할해 GPU HBM 접근을 최소화. 메모리 사용 O(N²) → O(N) 감소

from transformers import AutoModelForCausalLM, AutoTokenizer, BitsAndBytesConfig
from peft import LoraConfig, get_peft_model, prepare_model_for_kbit_training
from trl import SFTTrainer, SFTConfig

# 1. 4bit 양자화 설정
bnb_config = BitsAndBytesConfig(
    load_in_4bit=True,
    bnb_4bit_quant_type="nf4",
    bnb_4bit_compute_dtype="bfloat16",
    bnb_4bit_use_double_quant=True,
)

# 2. 모델 로드
model = AutoModelForCausalLM.from_pretrained(
    "meta-llama/Llama-3.1-8B-Instruct",
    quantization_config=bnb_config,
    device_map="auto",
)
model = prepare_model_for_kbit_training(model)

# 3. LoRA 설정
lora_config = LoraConfig(
    r=16,                    # 랭크 (8~64, 높을수록 정밀)
    lora_alpha=32,           # 스케일링
    target_modules=["q_proj", "k_proj", "v_proj", "o_proj"],
    lora_dropout=0.05,
    bias="none",
    task_type="CAUSAL_LM",
)
model = get_peft_model(model, lora_config)

# 4. 학습
trainer = SFTTrainer(
    model=model,
    train_dataset=dataset,       # 준비된 데이터셋
    args=SFTConfig(
        output_dir="./output",
        num_train_epochs=3,
        per_device_train_batch_size=4,
        learning_rate=2e-4,
        bf16=True,
        logging_steps=10,
    ),
)
trainer.train()

⚙️ 14. 양자화와 최적화

양자화(Quantization)는 모델 가중치의 정밀도를 줄여 VRAM 사용량과 연산량을 낮추는 기법입니다. FP16(16비트) → INT4(4비트)로 줄이면 크기가 약 1/4로 줄어듭니다.

14-1. 양자화 방식 비교

방식비트크기 감소품질 손실속도 향상도구
FP16 (기준)16bit1×없음1×기본
FP88bit~2×거의 없음~1.5×TensorRT-LLM
INT8 (GPTQ)8bit~2×미미~1.3×AutoGPTQ
INT4 (GPTQ)4bit~4×소~1.5×AutoGPTQ, GGUF Q4
Q4_K_M (GGUF)4.8bit 혼합~3.5×소 (최적 밸런스)~1.4×llama.cpp
AWQ4bit~4×소~2× (vLLM 최적)AutoAWQ
EXL22~6bit 혼합변동비트 수에 비례~1.5×ExLlamaV2
GGUF Q2_K2.6bit~6×대 (권장 안 함)~1.6×llama.cpp
💡 양자화 선택 가이드
  • VRAM 넉넉 → FP16 그대로 (품질 최고)
  • VRAM 부족, 서빙 → AWQ 4bit + vLLM (속도·품질 균형)
  • VRAM 부족, 개인 → GGUF Q4_K_M + llama.cpp (가장 범용)
  • NVIDIA 전용 최적화 → FP8 + TensorRT-LLM (최고 성능)

14-2. 기타 최적화 기법

Flash Attention 2/3

어텐션 연산 메모리를 O(N²)→O(N)으로 줄이고 속도 2~3배 향상. 대부분의 엔진에 기본 탑재

KV Cache 양자화

KV 캐시를 FP8/INT8로 양자화해 긴 컨텍스트 VRAM 절감. vLLM --kv-cache-dtype fp8

Chunked Prefill

긴 프롬프트를 청크 단위로 처리해 TTFT(첫 토큰 레이턴시)와 메모리 균형

지식 증류 (Distillation)

큰 모델의 출력으로 작은 모델을 학습. 70B → 7B로 80~90% 성능 유지하면서 10배 빠르게

🗺️ 18. 실전 구축 로드맵

Phase 1: 실험 (1~2주, 비용 $0~100, 약 0~13.8만원)

목표: 로컬에서 LLM을 돌려보고 가능성 확인
  1. 기존 PC/Mac에 Ollama 설치
  2. ollama run llama3.1:8b로 7B 모델 대화
  3. API 서버 모드로 기존 앱에 연동 테스트
  4. 성능·품질 판단 (응답 속도, 정확도, 한국어 품질)

Phase 2: 파일럿 (2~4주, 비용 $500~3,000, 약 69~414만원)

목표: 실제 비즈니스 태스크에 적용
  1. 클라우드 GPU(RunPod/Vast.ai)에서 vLLM + 70B 모델 구동
  2. 사내 데이터로 QLoRA fine-tuning 실험
  3. RAG 파이프라인 구축 (사내 문서 벡터화)
  4. 비용·품질 측정, API 대비 ROI 비교

Phase 3: 프로덕션 (1~3개월, 비용 $5,000~50,000, 약 690~6,900만원)

목표: 안정적인 서비스 운영
  1. 온프레미스 또는 전용 클라우드 GPU 서버 확보
  2. LiteLLM 게이트웨이 + vLLM 워커 아키텍처 구축
  3. 모니터링 (Prometheus + Grafana + DCGM) 구성
  4. 보안 (TLS, API 키, 입출력 필터링, 감사 로그) 적용
  5. 자동 스케일링, 장애 복구, 백업 설정

Phase 4: 고도화 (지속)

목표: 도메인 특화, 비용 최적화, 품질 향상
  1. 도메인 continued pretraining 또는 fine-tuning 정기 수행
  2. 사용자 피드백 기반 DPO/RLHF 적용
  3. 모델 경량화 (지식 증류, 양자화 최적화)
  4. 하이브리드 라우팅 (자체 + 상용 API) 최적화
  5. A/B 테스트, 모델 버전 관리, 품질 대시보드
