1. 요약

바이브코딩은 "AI에게 자연어로 코딩을 맡기는 방식"입니다. 하지만 운영 서비스에서는 말만 잘하는 AI보다 무엇을 해도 되는지 막는 게이트, 실행을 기록하고 재개하는 하네스, 상태 흐름을 관리하는 그래프, 도구 호출 표준, 관측과 평가, 배포/장애 운영 체계가 더 중요합니다.

LangGraph 여러 단계 AI 작업을 그래프로 연결하고 중단 후 재개하게 하는 런타임 부분 적용: `StateGraph` 8개 노드, PM interrupt 확인 승인 대기, 재시도, 배포 모니터링을 같은 흐름으로 묶어야 한다
LangChain LLM, tool, message, middleware를 표준 방식으로 연결하는 계층 부분 적용: core/provider/MCP adapter 있음, full `langchain` import는 운영 컨테이너에서 False 도구 권한과 모델 라우팅을 표준화해야 한다
LangSmith LLM 실행 trace, 품질 평가, 비용/지연 관측 플랫폼 호환 기반 적용: `langsmith` import 가능, 내부 trace 테이블 존재, 외부 SaaS 전송은 opt-in 실패 trace를 평가 데이터로 바꿔 재발을 줄여야 한다
Ops 코드가 실제 서비스에서 안전하게 돌아가게 하는 배포/모니터링/롤백 체계 적용 중: blue/green, deploy_runs, deploy_phase_events, runner queue 원칙 존재 완료 보고는 배포와 헬스, 모니터링 근거까지 있어야 한다

2. 전체 지도: AI 바이브코딩 운영 체계

CEO가 "이 기능 만들어줘"라고 말하면 AI가 코드를 쓰는 것만으로는 부족합니다. 운영 수준에서는 아래 6단계가 한 번의 작업 단위로 묶여야 합니다.

1. 요청자연어 지시, 목표, 금지사항, 완료조건
2. Gate읽기/쓰기/배포/금융/인증/파괴 위험 분류
3. Harnessrun id, 프롬프트, 도구, 비용, 검증 계약 생성
4. GraphPM -> 개발 -> QA -> Judge -> Ops 상태 전이
5. Tracetool call, 오류, 비용, 산출물, 평가 기록
6. Ops커밋, 푸시, 배포, 헬스, 롤백, HANDOVER

CEO 관점의 핵심 질문

질문 나쁜 답 좋은 답
AI가 알아서 해도 되는가? "모델이 똑똑하니까 됩니다." "read는 자동, write/deploy/financial/auth는 승인 필요, destructive는 차단입니다."
중간에 끊기면 어떻게 되는가? "다시 물어보면 됩니다." "graph_run_id/checkpoint/trace/task 상태로 이어서 재개합니다."
완료됐다는 걸 어떻게 믿는가? "AI가 완료라고 했습니다." "변경 파일, 테스트, DB 상태, 배포 상태, 화면/API 검증, HANDOVER가 있습니다."

3. Hermes Gate

Hermes Gate는 여기서 Hermes식 self-improving agent 패턴에 붙는 승인 게이트로 설명합니다. Hermes Agent 계열은 작업 경험을 스킬로 만들고, 그 스킬을 다음 작업에 재사용하는 방향입니다. 이때 위험한 점은 "AI가 배운 절차"가 곧바로 파일쓰기, 배포, 금융주문, 로그인 자동화에 연결될 수 있다는 것입니다.

따라서 Hermes Gate의 본질은 "AI가 학습한 것을 실행하기 전에 위험도를 분류하고, 필요한 경우 사람 승인을 받는 장치"입니다.

위험도 게이트 예시

위험 tier 예시 권장 결정 CEO 승인 필요
read 파일 읽기, SELECT DB 조회, 헬스체크, wiki 검색 allow 보통 불필요
write 파일 patch, 문서 갱신, 비파괴 DB upsert approve 필요
deploy blue/green 배포, nginx cutover, standby sync approve 필요
auth 로그인, CAPTCHA, OTP, Credential Vault respond/approve 필요
financial 주문 제출, 브로커 조작, 송금 approve 필수
destructive DROP, TRUNCATE, force push, shutdown reject 승인해도 차단

실전 예시

CEO: "GO100 장초반 전략이 왜 진입을 안 했는지 확인하고 고쳐줘."

Gate 판정:
1. DB/로그 조회: read -> 자동 수행 가능
2. 코드 수정: write -> 변경 파일과 롤백 가능성 확인 후 진행
3. 실제 주문 로직 변경 또는 주문 실행: financial -> CEO 명시 승인 전 차단
4. 배포: deploy -> blue/green 계약과 승인 필요

OHVIS 적용 현황

항목 적용 상태 근거
Risk policy registry 적용 `app/services/ohvis_harness.py`의 `RISK_POLICIES`가 read/write/deploy/auth/financial/destructive를 정의
Hermes recommend endpoint 적용 `POST /api/v1/ohvis/harness/hermes/recommend`가 recall -> select_skill -> execute_with_gate -> learn 흐름 반환
스킬 승인/버전 DB 기반 적용 `ops_skill_library`, `ops_skill_versions`, `ops_skill_runs` 테이블 존재. enabled skill 9개 [DB 조회]
외부 Hermes Agent 런타임 미탑재 현재 구현은 Hermes 패턴 흡수이며 외부 런타임에 배포/DB/금융 권한을 주지 않는 guardrail을 둠
CEO 검수 문장

"이 작업의 risk tier를 무엇으로 분류했는지, 승인 없이 실행한 tool이 있는지, destructive 작업은 차단됐는지 보고해라."

4. Harness

하네스는 모델의 안전벨트와 계기판입니다. 모델이 답을 만드는 것만 보면 "그럴듯한 문장"만 보입니다. 하네스가 있으면 어떤 프롬프트와 어떤 도구로, 어떤 상태에서, 어떤 비용과 오류를 내며 실행했는지 남습니다.

하네스가 포함해야 할 것

구성요소 역할 OHVIS 예시
Run ID 작업 1건을 끝까지 추적하는 고유 ID `graph_run_id`, `session_id`, `ohvis_task_id`, `pipeline_jobs` 연결 목표
Prompt contract L1~L5 규칙, 프로젝트, 역할, intent를 확정 `prompt_assets`, active_project, CEO 통합지시 레이어
Tool policy 사용 가능한 도구와 승인 필요 도구를 분리 `RISK_POLICIES`, AADS MCP tools, Runner submit/status
State 진행 중/대기/승인/실패/완료 상태 저장 `ohvis_tasks` 총 296건, running 44건 [DB 조회]
Trace 입력, 출력, tool call, latency, error 기록 `ohvis_harness_traces` 39건 [DB 조회]
Knowledge 과거 결정/장애/성공사례를 다음 실행에 재사용 `ohvis_wiki_pages` 1,693건, `memory_facts` 기반 fallback

실전 예시

좋지 않은 바이브코딩:
"채팅 최종응답이 사라져. 고쳐줘."

하네스 있는 바이브코딩:
"채팅 최종응답 사라짐을 재현하고,
chat_turn_executions, SSE stream, final message persist, UI render filter를 분리해 trace로 남겨라.
수정 후에는 API fallback과 화면 캡처 근거를 보고해라."

OHVIS 적용 현황

파일/테이블 의미 판정
`app/services/ohvis_harness.py` 하네스 상태, skill search, wiki search, Hermes recommendation을 하나의 API 계약으로 노출 적용
`app/api/ohvis_harness.py` `/status`, `/policies`, `/skill-find`, `/wiki/search`, `/hermes/recommend` 라우트 제공 적용
`migrations/158_ohvis_harness_skill_wiki_foundation.sql` skill, wiki, error book, trace foundation 테이블 생성 및 seed 적용
`app/services/ohvis_harness_trace.py` trace 실패가 본 작업을 깨지 않도록 비치명적 기록 helper 제공 적용
전체 실행 강제성 모든 chat/task/runner/deploy가 아직 하나의 run id로 강제 연결되지는 않음 보강 필요

5. LangGraph

LangGraph는 AI 작업을 "순서 있는 그래프"로 만드는 도구입니다. 일반 챗봇은 한 번 답하고 끝나지만, 운영 AI는 요구사항 정리, 설계, 개발, 테스트, 검수, 배포, 모니터링, 승인 대기를 오갑니다. 이 흐름은 선형 채팅보다 그래프가 맞습니다.

쉬운 비유

LangGraph는 공장 생산라인의 컨베이어와 검사대입니다. PM이 요구사항을 정리하고, 개발자가 만들고, QA가 테스트하고, Judge가 승인/반려하며, DevOps가 배포 준비를 합니다. 실패하면 다시 개발자로 돌려보낼 수 있습니다.

OHVIS 그래프 구조

START
  -> pm_requirements
  -> supervisor
  -> architect 또는 developer
  -> qa
  -> judge
  -> devops
  -> END

fail이면 judge -> developer 재작업
researcher는 supervisor에서 온디맨드 호출
LangGraph 기능 무엇을 해결하나 OHVIS 적용
StateGraph 작업 단계를 노드와 엣지로 연결 `app/graph/builder.py`에서 Native `StateGraph` 사용
Conditional edge 성공/실패/승인 여부에 따라 다음 단계 변경 route_after_pm/supervisor/developer/qa/judge/devops 사용
Interrupt 사람 승인을 받고 같은 상태에서 재개 `app/agents/pm.py`에서 `interrupt()` 사용. 전체 tool HITL 표준화는 보강 필요
Checkpoint 서버 재시작/중단 후 상태 복구 `compile_graph(checkpointer=None)` 인자 존재. 운영 전체 강제 적용은 보강 필요
Persistence thread-scoped memory와 long-term memory 분리 DB/메모리 기반은 있으나 graph run과 완전 결합 전

CEO 지시 예시

"이 작업은 LangGraph 흐름으로 PM 요구사항 -> Developer 수정 -> QA 테스트 -> Judge 검수 -> Ops 배포대기까지 나누고,
각 단계 상태와 실패 시 재시도 경로를 보고해라."

6. LangChain

LangChain은 모델과 도구를 연결하는 표준 계층입니다. CEO 관점에서는 "AI가 어떤 도구를 어떤 형식으로 호출하는지", "OpenAI/Anthropic/Gemini 같은 모델을 어떻게 바꾸는지", "고위험 tool 호출 전에 어떤 middleware가 끼어드는지"를 다루는 층입니다.

LangChain을 쓰는 이유

문제 LangChain 계층이 주는 해법 OHVIS 예시
모델마다 메시지 형식이 다름 HumanMessage, AIMessage, SystemMessage 같은 공통 형식 agent 파일들이 `langchain_core.messages` 사용
도구 호출 schema가 제각각임 tool interface와 agent runner 표준화 `langchain-mcp-adapters` 의존성, MCP tool lazy loading 패턴
모델 교체와 fallback이 어려움 provider package로 OpenAI/Anthropic/Google 연결 `langchain-openai`, `langchain-anthropic`, `langchain-google-genai` 의존성
위험 tool 승인 정책이 흩어짐 middleware로 approve/edit/reject/respond를 통일 OHVIS는 정책 registry는 있으나 runtime middleware 일괄 강제는 보강 필요

운영 컨테이너 import 확인

{'langgraph': True,
 'langchain_core': True,
 'langchain_mcp_adapters': True,
 'langsmith': True,
 'langfuse': True,
 'langchain': False}

의미: OHVIS 운영 컨테이너에는 LangChain Core/Provider/MCP adapter 계열이 적용되어 있습니다. 다만 `langchain` 메타 패키지 전체가 import 가능한 상태는 아니므로, "LangChain 전체 도입 완료"가 아니라 "LangChain Core/Provider/MCP 기반 부분 도입"이라고 보고하는 것이 정확합니다.

CEO 지시 예시

"이 에이전트는 active_project별 tool allowlist와 risk middleware를 먼저 구성하고,
읽기 도구와 쓰기/배포/금융 도구를 분리해 LangChain-style tool contract로 보고해라."

7. LangSmith

LangSmith는 AI가 실제로 무엇을 했는지 보는 관측/평가 시스템입니다. 일반 로그가 "에러가 났다"를 보여준다면, LangSmith식 trace는 "어떤 프롬프트, 어떤 도구, 어떤 모델 출력 때문에 에러가 났는지"를 보여줍니다.

LangSmith가 필요한 순간

상황 LangSmith식으로 남겨야 할 것 재발 방지 연결
최종응답이 사라짐 stream event, persisted final message, UI render filter, tool wait span 동일 trace를 eval case로 저장해 회귀 테스트
러너가 승인 대기에서 멈춤 job status, reviewer result, approval payload, elapsed time stale detector와 알림 기준 개선
배포가 된 줄 알았는데 운영에 없음 commit SHA, pushed SHA, deploy_run_id, image digest, routed health 완료 보고 gate를 deploy certification 이후로 이동

OHVIS 적용 현황

항목 상태 근거
LangSmith package 운영 컨테이너 import 가능 `docker exec aads-server python3 -c ...` 결과 `langsmith=True`
Langfuse 관측 기존 적용 `app/core/langfuse_config.py`가 trace 생성과 LiteLLM callback 설정을 graceful degradation 방식으로 구현
LangSmith-compatible 내부 trace 기반 적용 `ohvis_harness_traces` 39건 [DB 조회]
외부 LangSmith SaaS 전송 opt-in/미확정 현재 교육자료 기준으로 외부 전송 활성 설정은 확인하지 않음. 데이터 반출 리스크 때문에 기본 off가 적절
Trace -> Dataset -> Eval -> 개선 PR 보강 필요 실패 trace를 자동 평가셋으로 승격하는 제품 루프는 아직 완전 폐쇄되지 않음

CEO 지시 예시

"이번 장애 trace를 단순 로그가 아니라 eval case로 저장해라.
다음 배포부터 같은 증상이 재현되면 배포 인증이 실패하도록 gate를 걸어라."

8. Ops

Ops는 "만든 코드가 운영 서비스에 안전하게 반영되는 전체 과정"입니다. 바이브코딩의 가장 큰 실패는 코드 생성까지는 빠른데, 커밋/푸시/배포/검증/롤백/문서기록이 빠져서 실제 서비스가 불안정해지는 것입니다.

AADS/OHVIS Ops 핵심 규칙

규칙 뜻 CEO 검수 포인트
Blue/Green 기본 새 슬롯 후보를 먼저 띄우고 헬스 통과 후 라우팅 전환 `deploy.sh bluegreen` 사용 여부
One image per release SHA 한 커밋 SHA당 이미지 한 번만 빌드 이미지 SHA와 Git SHA 일치 여부
Candidate health before lock nginx lock은 라우팅 직전 짧게만 잡음 build/install 중 lock 점유 금지
Same-digest standby active/standby 슬롯이 같은 이미지 digest를 가져야 함 대기 슬롯 동기화 검증
Rollback on routed-health failure 전환 후 외부 헬스가 실패하면 즉시 이전 라우팅 복구 rollback path 존재 여부
5분 P0/P1 monitoring 전환 직후만 보고 완료가 아니라 5분 모니터링 뒤 인증 완료 보고 시점이 인증 이후인지 확인
