🔍 01. RAG란 무엇이고 왜 필요한가

RAG(Retrieval-Augmented Generation, 검색 증강 생성)는 LLM이 답을 만들기 전에 외부 지식 저장소(문서, DB, 사내 위키 등)에서 관련 정보를 먼저 검색하고, 그 검색 결과를 프롬프트에 넣어 답변을 생성하게 하는 방식입니다. LLM은 학습 시점까지의 지식만 알고 있고, 회사 내부 문서나 실시간 정보는 전혀 모릅니다. RAG는 이 한계를 "모델을 다시 학습시키지 않고" 외부 지식을 주입해서 해결합니다.

1-1. LLM 지식 확장의 세 가지 방법 비교

회사 데이터를 LLM에 반영하는 방법은 크게 세 가지입니다. 셋 중 무엇을 쓸지는 "데이터가 얼마나 자주 바뀌는가", "출처 인용이 필요한가", "문서량이 얼마나 되는가"로 결정됩니다.

판단 기준RAG파인튜닝롱컨텍스트(긴 프롬프트)
데이터 최신성실시간 반영 가능 (문서만 갱신)재학습 필요 (수일~수주 소요)매 요청마다 최신 문서 첨부 가능

구축 난이도중간 (파이프라인 구축 필요)높음 (GPU, 데이터셋, 튜닝 전문성)낮음 (프롬프트에 넣기만 하면 됨)

💡 실무 판단 가이드 사내 문서가 수백 건을 넘고 매일/매주 갱신되며 답변에 출처가 필요하다면 RAG가 정답입니다. 응답의 말투·형식을 통일하거나 특정 전문용어를 자연스럽게 쓰게 하려면 파인튜닝을 병행합니다. 문서가 수십 건 이하로 적고 매번 다르다면 굳이 RAG 인프라를 구축하지 말고 롱컨텍스트로 프롬프트에 직접 넣는 것이 훨씬 간단하고 저렴합니다. 실무에서는 "RAG + 가벼운 파인튜닝"을 함께 쓰는 하이브리드 구성이 흔합니다.

1-2. RAG가 해결하는 세 가지 핵심 문제

최신성 문제

LLM은 학습 시점 이후 사건을 모릅니다. RAG는 문서만 업데이트하면 즉시 최신 정보로 답변합니다.

비공개 데이터 문제

사내 계약서, 인사 규정, 고객 DB 등은 LLM이 학습한 적 없는 데이터입니다. RAG로 검색 대상에 포함시킵니다.

환각(hallucination) 문제

근거 문서 없이 LLM이 그럴듯하게 지어내는 것을 방지합니다. 다만 검색이 부정확하면 환각은 여전히 발생합니다(11장 참고).

✅ CEO 체크포인트
  • 우리 회사 데이터가 매일·매주 바뀌는가? 그렇다면 RAG가 파인튜닝보다 유지보수가 쉽다.
  • 답변에 "어느 문서에서 나온 정보인지" 출처가 필요한가? 그렇다면 RAG만 가능하다.
  • 전체 참고 문서가 수백 건 이하인가? 그렇다면 RAG 인프라 구축 전에 롱컨텍스트 방식부터 검토한다.

  • RAG 도입을 "LLM 선택 문제"로만 보지 말 것 — 파이프라인 8단계 전체가 품질을 결정한다.
  • 담당팀에게 "어느 단계까지 구현했는지" 8단계 기준으로 진행 상황을 보고받는다.
  • 문제가 생기면 LLM보다 먼저 검색(리트리버) 단계부터 의심한다 — 실무에서 가장 흔한 병목이다.

📥 03. 문서 수집과 파싱

RAG 품질의 절반은 "원본 문서를 얼마나 깨끗하게 텍스트로 뽑아내는가"에서 결정됩니다. 특히 표, 이미지, 다단 레이아웃이 섞인 문서는 단순 텍스트 추출로는 구조가 깨집니다.

3-1. 문서 유형별 파싱 난이도

표가 많은 PDF (재무제표 등)높음표를 마크다운/구조화 형태로 보존해야 함LlamaParse, Docling, Unstructured.io

✅ CEO 체크포인트
  • 사내 문서 중 표·스캔본이 몇 %인지 파악한다 — 비중이 높으면 파싱 단계에 예산을 더 배정한다.
  • "파싱 품질 샘플 검수"를 담당자에게 요청한다 — 원본과 추출 텍스트를 눈으로 비교해봐야 함.
  • OCR이 필요한 문서량이 크면 로컬 OCR(비용 없음) vs 비전 LLM OCR(정확도 높으나 비용 발생) 중 선택을 결정한다.

✂️ 04. 청킹 전략 비교

청킹(Chunking)은 긴 문서를 검색 가능한 작은 단위로 자르는 작업입니다. 청크가 너무 크면 관련 없는 내용이 섞여 검색 정확도가 떨어지고, 너무 작으면 문맥이 끊겨 LLM이 이해하기 어렵습니다.

4-1. 네 가지 청킹 전략

고정 길이 (Fixed-size)

문자/토큰 수 기준으로 일정하게 자름 (예: 500토큰 + 10~20% 오버랩). 구현이 가장 간단하지만 문장·표 중간이 잘릴 위험이 있음.

문단 기반 (Recursive/Paragraph)

문단→문장 순서로 경계를 우선 존중하며 분할. LangChain의 RecursiveCharacterTextSplitter가 대표적. 실무 기본값.

의미 기반 (Semantic Chunking)

인접 문장들의 임베딩 유사도를 계산해 유사도가 급격히 떨어지는 지점에서 자름. 주제가 바뀌는 지점을 자동으로 찾아줌. 계산 비용이 더 듦.

계층형 (Hierarchical / Parent-Child)

작은 청크로 정밀하게 검색하되, LLM에는 그 청크가 속한 더 큰 상위 문단(부모)을 함께 전달. "Small-to-big retrieval"이라 불림.

4-2. 문서 유형별 권장 청킹

문서 유형권장 전략이유
법률/계약서문단 기반 + 계층형조항 단위 의미가 훼손되면 법적 리스크. 조항 번호를 청크 경계로 강제.
소스코드함수/클래스 단위 (AST 기반)함수 중간이 잘리면 코드 의미가 파괴됨.
FAQ / Q&A 문서질문-답변 쌍 단위Q와 A가 한 쌍으로 검색되어야 함.
대화 로그 / 상담 기록대화 턴(turn) 단위 + 세션 묶음발화 맥락 보존.
기술 매뉴얼 / 사내 위키제목(heading) 기반 섹션 분할 + 계층형섹션 구조가 이미 의미 단위와 일치.
재무제표 / 표 중심 문서표 단위 별도 청크(행 단위 자연어화)표를 텍스트로 뭉개면 숫자 의미 소실.
뉴스/블로그/일반 문서고정 길이 또는 문단 기반구조가 단순해 정교한 전략이 불필요.
💡 실무 기본값 특별한 이유가 없다면 256~512 토큰, 오버랩 10~20%의 문단 기반 청킹으로 시작하는 것이 스윗스팟입니다. 이후 평가(10장 RAGAS)를 돌려보고 문제 있는 문서 유형만 의미기반/계층형으로 바꾸는 점진적 접근을 권장합니다.
✅ CEO 체크포인트
  • 우리 문서의 절반 이상이 법률/계약/재무제표류라면 "고정 길이 청킹"만으로는 부족하다고 판단한다.
  • 처음부터 완벽한 청킹 전략을 요구하지 말 것 — 기본값으로 시작 후 평가 지표로 개선하는 것이 정상 과정이다.
  • 담당팀에 "청크 경계에서 문장이 잘리는 사례가 있는지" 샘플 점검을 요청한다.

🧬 05. 임베딩 모델 선택 기준

임베딩(Embedding)은 텍스트를 의미를 담은 숫자 벡터(예: 768개 또는 1536개의 숫자 목록)로 바꾸는 작업입니다. 의미가 비슷한 문장은 벡터 공간에서 가까운 위치에 놓입니다. 검색은 결국 "질문 벡터와 가장 가까운 청크 벡터 찾기"입니다.

5-1. 선택 기준

차원 수

벡터의 숫자 개수. 높을수록 표현력↑이지만 저장공간·연산비용도 비례해 증가. 768~1536차원이 실무에서 흔한 범위.

한국어·다국어 성능

영어 중심으로 학습된 모델은 한국어 뉘앙스를 놓치는 경우가 많음. 다국어 벤치마크(MTEB 등) 한국어 세부 점수 확인 필요.

최대 입력 길이

가격 / 자체 호스팅 가능 여부

🗄️ 06. 벡터DB 비교

벡터DB는 임베딩 벡터를 저장하고 "질문 벡터와 가장 가까운 벡터들"을 빠르게 찾아주는 저장소입니다. 선택 기준은 이미 쓰고 있는 인프라, 데이터 규모, 운영 인력 여력입니다.

🕸️ 07. 인덱스 알고리즘 (HNSW · IVF)

벡터 수가 많아지면 모든 벡터와 일일이 거리를 계산하는 것(전수 탐색)은 느려집니다. 인덱스 알고리즘은 "완벽하진 않지만 거의 정확하고 훨씬 빠른" 근사 최근접 이웃(ANN) 탐색을 가능하게 합니다.

7-1. HNSW (Hierarchical Navigable Small World)

벡터들을 여러 층의 그래프로 연결해두고, 상위 층에서 큰 걸음으로 대략적인 위치를 찾은 뒤 하위 층으로 내려가며 정밀 탐색하는 방식입니다. 현재 pgvector, Qdrant, Milvus, Weaviate 대부분이 기본 인덱스로 채택하고 있습니다.

파라미터의미값을 올리면
M각 노드가 유지하는 그래프 연결 수정확도↑, 메모리↑, 인덱스 구축 시간↑
ef_construction인덱스 구축 시 탐색 폭구축 시간↑, 인덱스 품질↑(검색 정확도에 영향)
ef_search검색 시 탐색 폭검색 정확도↑, 검색 속도↓ (요청 단위로 조정 가능)

7-2. IVF (Inverted File Index)

벡터 공간을 k-means 클러스터링으로 여러 구역(클러스터)으로 나눈 뒤, 검색 시 질문과 가까운 일부 클러스터만 탐색하는 방식입니다. 구축이 빠르고 메모리를 덜 쓰지만, 일반적으로 HNSW보다 같은 속도 대비 정확도가 낮은 경향이 있습니다. PQ(양자화)와 결합한 IVF-PQ는 메모리를 크게 절감합니다.

파라미터의미값을 올리면
nlist클러스터(구역) 개수세밀한 분할, 구축 시간↑
nprobe검색 시 탐색할 클러스터 수정확도↑, 검색 속도↓
💡 언제 무엇을 쓰나 데이터가 자주 추가/삭제되고 검색 정확도가 중요하면 HNSW(실무 기본값), 데이터가 매우 크고(수억 건) 메모리가 제약이면 IVF-PQ 계열을 검토합니다. pgvector는 두 방식(HNSW, IVFFlat) 모두 지원하며 대부분 HNSW가 기본 권장값입니다.
✅ CEO 체크포인트
  • "정확도 vs 속도"는 트레이드오프임을 이해한다 — 무조건 빠른 것이 좋은 것이 아니다.
  • 검색이 부정확하다는 보고를 받으면 인덱스 파라미터(ef_search 등)를 조정했는지 먼저 확인한다.
  • 인덱스 알고리즘 선택은 벡터DB 선택과 세트로 결정되므로 6장과 함께 검토한다.

🔀 08. 하이브리드 검색과 리랭킹

8-1. 하이브리드 검색 (BM25 + 벡터)

벡터 검색은 "의미"는 잘 찾지만 고유명사·제품코드·숫자 같은 정확한 키워드 매칭에는 약할 수 있습니다. BM25(전통적 키워드 검색 알고리즘)는 정확한 단어 일치에 강합니다. 두 방식을 함께 쓰고 RRF(Reciprocal Rank Fusion) 같은 방법으로 순위를 합산하는 것이 하이브리드 검색입니다.

벡터 검색이 강한 경우

  • 동의어·의역된 질문 ("환불" ↔ "돈 돌려받기")
  • 문맥적 유사성

BM25가 강한 경우

  • 제품코드, 모델명, 정확한 숫자
  • 희귀 고유명사

8-2. 리랭커 (Cross-encoder Reranking)

1차 벡터 검색(bi-encoder)은 질문과 문서를 각각 독립적으로 벡터화해 빠르게 top-50~100개를 뽑습니다. 이후 Cross-encoder 리랭커는 질문-문서를 한 쌍으로 묶어 훨씬 정밀하게 재채점해 최종 top-5~10개로 좁힙니다. 대표 제품: Cohere Rerank, BGE-reranker(오픈소스), Jina Reranker.

✅ 리랭커 적용 효과 리랭커를 추가하면 일반적으로 Recall@k·NDCG(10장)가 눈에 띄게 개선됩니다. 대신 쿼리당 지연시간과 API 비용이 늘어나므로, "정확도가 중요한 서비스(법률·의료·재무)"에는 적용하고 "빠른 응답이 우선인 캐주얼 챗봇"에는 생략하는 식으로 선택적으로 적용하는 것이 일반적입니다.
✅ CEO 체크포인트
  • 검색 대상 문서에 제품코드·모델번호가 많다면 벡터 검색만으로는 부족하다 — 하이브리드 검색을 요구한다.
  • 답변 정확도가 비즈니스 리스크에 직결되는 영역(법무·재무)에는 리랭커 적용을 우선순위로 지시한다.
  • 리랭커는 추가 비용·지연이 발생하므로 모든 질의에 일괄 적용할지, 중요 영역만 선택 적용할지 결정한다.

🚀 09. 최신 기법: GraphRAG · Agentic RAG · ColBERT

9-1. GraphRAG

Microsoft가 제안한 방식으로, 문서에서 엔티티(인물·조직·개념)와 그들 간의 관계를 추출해 지식그래프를 만들고, 이를 커뮤니티(주제 클러스터)별로 요약해둡니다. "전체 문서에서 반복되는 주요 트렌드는?" 같은 전역적(global) 질문에 일반 RAG보다 강합니다. 단, 구축 비용과 복잡도가 훨씬 높습니다.

9-2. Agentic RAG

LLM 에이전트가 검색 과정 자체를 스스로 판단합니다. 검색 결과가 불충분하면 질문을 다시 써서 재검색(query rewriting)하거나, 여러 단계를 거쳐 검색하는 멀티홉(multi-hop) 검색을 수행하고, 검색 결과의 관련성을 스스로 평가해 추가 검색 여부를 결정합니다. ReAct 패턴(추론→행동→관찰 반복)이 대표적 구조입니다.

9-3. Late Interaction (ColBERT)

일반 임베딩은 문서 전체를 하나의 벡터로 압축(single-vector)하지만, ColBERT류의 Late Interaction 방식은 문서의 각 토큰을 별도 벡터로 유지하고, 검색 시 질문 토큰들과 문서 토큰들 간 유사도를 토큰 단위로 계산해 합산(MaxSim)합니다. 정밀도가 높지만 저장공간과 연산량이 단일 벡터 방식보다 훨씬 많이 듭니다.

기법강점비용/복잡도적합한 경우
GraphRAG전역적 질문, 관계 추론매우 높음대규모 문서 집합의 종합 분석 리포트
Agentic RAG복잡한 다단계 질문, 자기 검증높음 (LLM 호출 횟수 증가)단순 검색으로 답이 안 나오는 복합 질문
ColBERT / Late Interaction정밀한 토큰 단위 매칭높음 (저장공간)정밀도가 최우선인 전문 검색
⚠️ 최신 기법 = 항상 정답은 아니다 세 기법 모두 일반 RAG보다 비용·복잡도가 높습니다. 기본 RAG(청킹+임베딩+HNSW+리랭커)로 평가 지표(10장)가 충분히 나오지 않을 때 단계적으로 도입을 검토하는 것이 순서입니다. 처음부터 GraphRAG를 도입하는 것은 대부분의 조직에 과잉 투자입니다.
✅ CEO 체크포인트
  • "전역적 요약/트렌드 질문"이 자주 필요한 업무인지 먼저 파악한 뒤 GraphRAG 도입을 검토한다.
  • Agentic RAG는 LLM 호출 횟수가 늘어 비용이 커진다는 점을 인지하고 예산 검토를 요구한다.
  • 최신 기법 도입 전 "기본 RAG로는 왜 안 되는지" 담당팀에게 구체적 실패 사례를 먼저 요구한다.

📊 10. RAG 품질 평가

"느낌상 답을 잘하는 것 같다"는 평가 기준이 될 수 없습니다. RAG는 검색 품질과 생성 품질을 각각 정량적으로 측정해야 개선이 가능합니다.

10-1. 검색 품질 지표

지표의미해석
Recall@k정답 문서가 상위 k개 검색 결과에 포함된 비율가장 기본적인 지표. k값(예: @5, @10)을 명시해야 함
MRR (Mean Reciprocal Rank)첫 정답이 몇 번째 순위에 나왔는지의 역수 평균정답이 "얼마나 상위에" 나오는지 측정
NDCG (Normalized DCG)순위별 가중치를 반영한 랭킹 품질 점수여러 개의 관련 문서가 있을 때 순서 품질까지 평가

10-2. 생성 품질 지표 (RAGAS 프레임워크)

Faithfulness (충실성)

생성된 답변이 검색된 문서 내용에 근거하는지 측정. 낮으면 환각(hallucination) 발생 가능성이 높다는 뜻.

Answer Relevancy (답변 관련성)

생성된 답변이 실제로 사용자의 질문에 부합하는지 측정.

Context Precision

검색된 문서 중 실제로 답변에 필요한 문서의 비율 — 낮으면 노이즈가 많다는 뜻.

Context Recall

정답을 만드는 데 필요한 정보가 검색된 문서에 실제로 포함되었는지 측정.

✅ 평가 없이는 개선도 없다 RAG 시스템을 배포하기 전, 최소 수십~수백 개의 "질문-정답 문서-정답" 세트(골든 데이터셋)를 만들어 Recall@k와 RAGAS 지표를 베이스라인으로 측정해야 합니다. 이후 청킹 전략, 임베딩 모델, 리랭커 적용 여부를 바꿀 때마다 같은 지표로 비교해야 "개선되었다"고 판단할 근거가 생깁니다.
✅ CEO 체크포인트
  • "RAG 도입 완료" 보고를 받을 때 Recall@k, faithfulness 수치를 함께 요구한다 — 숫자 없는 완료 보고는 검증 불가.
  • 골든 데이터셋(정답 세트) 구축을 초기 예산·일정에 반드시 포함시킨다.
  • faithfulness가 낮다는 보고를 받으면 LLM 문제가 아니라 검색 단계 문제일 가능성을 먼저 검토하게 한다.

🚧 11. 실패 패턴과 트러블슈팅

실패 패턴증상원인대응

🚨 가장 흔한 실무 함정 "검색이 안 되는 것"과 "LLM이 답을 못 만드는 것"을 구분하지 않고 LLM만 교체하는 경우가 매우 흔합니다. 문제가 생기면 먼저 "검색된 문서 자체를 사람이 확인"해서 애초에 정답 문서가 검색됐는지부터 확인해야 합니다. 검색이 안 됐다면 LLM을 아무리 바꿔도 소용없습니다.
✅ CEO 체크포인트
  • RAG 답변 오류 보고 시 "검색된 문서가 정답을 포함했는지" 먼저 확인하도록 프로세스를 못박는다.
  • "모른다"고 답할 수 있는 프롬프트 설계가 되어 있는지 확인한다 — 없으면 환각 위험이 상시적이다.
  • 문서 갱신 후 실제로 답변이 바뀌는지 주기적으로 샘플 테스트하도록 요구한다.

🔐 12. 증분 갱신 · 삭제 · 멀티테넌시

12-1. 증분 갱신

문서 전체를 매번 재임베딩하면 비용과 시간이 낭비됩니다. 실무에서는 문서의 해시값(지문)을 비교해 변경된 부분만 재청킹·재임베딩하는 증분 갱신 파이프라인을 구축합니다.

12-2. 삭제 처리

문서가 삭제/폐기되면 검색 결과에서도 사라져야 합니다. 소프트 삭제(tombstone 플래그만 표시 후 검색 시 필터링)와 하드 삭제(실제 벡터 제거)가 있으며, HNSW 인덱스는 삭제가 잦으면 그래프 품질 저하로 주기적 재구축이 필요할 수 있습니다.

12-3. 멀티테넌시(권한별 필터링)

여러 고객사/부서/사용자가 하나의 벡터DB를 공유할 때, 검색 결과가 자신이 접근 권한이 있는 문서로만 제한되어야 합니다.

공유 인덱스 + 메타데이터 필터

  • 비용 효율적 (인덱스 하나로 운영)
  • pgvector는 Row-Level Security로 안전하게 구현 가능

테넌트별 완전 격리 인덱스

  • 보안 격리는 강력하나 테넌트 수만큼 인프라 비용 증가
  • 대규모 B2B SaaS에서 주로 채택
🚨 필터링 누락은 곧 데이터 유출 멀티테넌시 필터링을 검색 로직에서만 구현하고 DB 레벨에서 강제하지 않으면, 코드 버그 하나로 다른 회사/부서의 기밀 문서가 검색 결과에 섞여 나올 수 있습니다. 가능하면 DB 레벨(Row-Level Security 등)에서 이중으로 강제하는 것이 안전합니다.
✅ CEO 체크포인트
  • 여러 부서/고객사 데이터를 한 벡터DB에 담을 계획이라면 권한 필터링을 DB 레벨에서 이중 검증하도록 요구한다.
  • 문서 삭제 요청(예: 고객 정보 파기 요청) 시 벡터DB에서도 실제로 삭제되는지 확인 절차를 만든다.
  • 증분 갱신 파이프라인 유무를 확인한다 — 없으면 매번 전체 재임베딩 비용이 발생하고 있을 수 있다.

💡 AADS의 이원화 메모리 아키텍처 (확인된 구조) ① 구조화된 사실/선호(CEO 지시, 도구 전략 등) → ai_observations, 비-벡터 규칙 기반 필터링+가중치 정렬.
② 자유 형식 사실/대화 기억(memory_facts, chat_messages 등) → pgvector + HNSW 벡터 유사도 검색.
두 방식을 용도에 맞게 나눠 쓰는 하이브리드 구조로 실제 운영되고 있음을 코드와 스키마로 확인했습니다.

14-3. 코드 의미검색 도구 (semantic_code_search)

AADS 환경에는 semantic_code_search라는 MCP 도구가 실제로 등록되어 있어 그 존재는 확인됩니다. 그러나 이번 조사에서는 원격 명령 실행 도구가 연결 오류를 반복해 해당 도구의 내부 구현 파일(사용 임베딩 모델, 코드 청킹 방식, 인덱스 갱신 주기 등)을 열람하지 못했습니다. 이 항목은 전면 미검증이며, 정확한 내용은 담당 개발자 확인이 필요합니다.

✅ CEO 체크포인트
  • AADS가 이미 pgvector 기반 RAG를 7.5만 건 이상 규모로 실운영 중이라는 사실을 담당팀과 공유·재확인한다.

3. 품질 개선정확도·환각률 개선하이브리드 검색(BM25+벡터) 추가, 리랭커 적용, 청킹 전략 세분화
4. 스케일업 판단규모 대응pgvector 한계 도달 시 Qdrant/Milvus 전환 검토, 증분 갱신 파이프라인 구축
5. 운영화지속 가능한 운영모니터링 대시보드, 멀티테넌시 권한 필터링, 정기 평가 재측정
💡 처음부터 완벽을 추구하지 않는다 RAG는 "한 번에 완성"되는 시스템이 아니라 평가 지표를 보며 반복 개선하는 시스템입니다. 1~2단계를 빠르게 통과해 실제 사용자 피드백과 정량 지표를 확보하는 것이, 처음부터 GraphRAG·Agentic RAG 같은 고급 기법을 설계하는 것보다 훨씬 안전한 접근입니다.
