1. 결론 요약

오비스는 CEO의 한 문장을 "대화"가 아니라 실행 계약으로 해석합니다. 메시지가 들어오면 ①66종 인텐트 중 하나로 확정하고 → ②그 인텐트에 맞춰 시스템 프롬프트를 5개 레이어로 조립하고 → ③모델을 4단 우선순위로 정하고 → ④인텐트별 도구 묶음을 붙여 실행하고 → ⑤4중 검증 게이트를 통과해야 답이 화면에 남습니다.

모델별 차이의 실체는 "프롬프트가 달라서"가 아니라 "실행 백엔드가 달라서"입니다. 프롬프트 자산 154개 중 모델별 변형(model_variants)을 실제로 쓰는 자산은 0건이고, 모델별 L5 자산 14개 중 현재 운영 모델(claude-opus-5)에 실제로 붙는 것은 provider 단위 1건뿐입니다 [DB 실측]. 차이는 전부 ㉮백엔드 경로(CLI 릴레이 / Codex 릴레이 / Agent SDK / LiteLLM) ㉯도구 호출 횟수 ㉰thinking 지원 여부에서 발생합니다.

2. 오비스에서 "지시"는 무엇인가 — 5종 분류

CEO께서 채팅창에 쓰신 한 줄은 오비스 안에서 서로 다른 5개 경로 중 하나로 갈라집니다. 겉보기에는 같은 채팅이지만 저장 위치·권한·되돌리기 방법이 전부 다릅니다.

#지시 종류무엇인가어디에 남는가실행 주체되돌리기
①대화 지시채팅창에 직접 쓰는 평문 지시. 오비스가 인텐트로 해석해 그 자리에서 도구를 돌린다chat_messages + chat_executions현재 세션(이 대화)턴 중단 / 추가 지시로 정정
②지시서(DIRECTIVE)>>>DIRECTIVE_START … >>>DIRECTIVE_END 블록. 러너에게 넘기는 공식 작업 계약directive_drafts / directive_lifecycle / pipeline_jobsPipeline Runner (독립 프로세스)검수 반려 → reset + 피드백
③절대 지시(규칙)"앞으로 항상 ~하라" 형태. 다음 턴부터 시스템 프롬프트에 상주 주입된다prompt_assets / CEO-DIRECTIVES / <ceo_rules> 블록모든 세션·모든 모델자산 비활성화(enabled=false)
④승인 결정응답 하단 카드의 승인/거부 버튼. 이미 제안된 다음 단계를 발동시킨다agent_permission_requestslive_trading_guard 게이트 통과 후 도구승인 취소 / 만료
⑤중단·정정 지시스트리밍 중 끼어드는 추가 지시. 다음 턴 앞에 [이전 추가 지시]로 주입된다interrupt_queue → 다음 턴 메시지진행 중 턴을 인터럽트자동 소비(1회성)
핵심 구분 — ①은 지금 이 대화가 처리하고, ②는 다른 프로세스에 위임하며, ③은 앞으로의 모든 대화를 바꿉니다. "이거 시켜"는 ②로, "앞으로 이렇게 해"는 ③으로 가야 하는데 둘 다 같은 채팅창에서 입력되기 때문에, 오비스는 인텐트 분류 단계에서 이 갈림길을 판정합니다. 잘못 갈리면 "시켰는데 안 했다"(②가 ①로 처리됨) 또는 "말했는데 또 그런다"(③이 ①로 처리됨)가 발생합니다.
