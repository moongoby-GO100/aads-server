설계 결론

오비스는 사용자의 자연어 목표를 받아 스스로 계획하고, 계정·레시피·권한을 사전점검한 뒤 안전한 범위는 즉시 실행한다. 질문은 실행을 막는 정보가 없을 때만 한 번 묻고, 답을 받으면 저장된 체크포인트에서 재개한다. 계정 승인, 레시피 승인, 실제 외부행위 승인은 서로 독립이며 절대 합쳐 쓰지 않는다.

1. 사용자와 핵심 여정

2. Ask Only When Blocked 대화 계약

  1. 먼저 판단: 의도, 대상 사이트, 출력물, 위험등급, 계정/레시피/권한 보유 여부를 내부적으로 확인한다.
  2. 가능한 것은 실행: READ와 정책상 허용된 WRITE_INTERNAL은 자동 실행하고 증거를 남긴다.
  3. 막힐 때만 질문: 한 blocker당 질문 1회, 2~3개 선택지, 권장안 우선. 이미 받은 값은 재질문하지 않는다.
  4. 체크포인트 재개: resume_token, checkpoint_id, idempotency_key로 마지막 안전 지점부터 이어간다.
  5. 완료 보고: 결과, 변경 내용, 증거, 실패/보류, 후속 제안을 구분한다.
사용자: "쿠팡에서 열정국밥에 쌈장 주문해줘"
오비스: 상품 검색과 조건 비교는 자동 수행
→ 계정 없음: "쿠팡 계정이 없습니다. 권장: Vault에 안전 등록 / 현재 브라우저에서 직접 로그인 / 중단"
→ 레시피 없음: 단계·권한·위험·증거가 담긴 dry-run을 제시하고 등록 승인 요청
→ 결제 직전: 상품·판매자·수량·총액·배송지·결제수단을 보여주고 IRREVERSIBLE 승인 요청
→ 승인 후: 같은 idempotency_key로 한 번만 주문하고 주문번호·증거를 보고

3. 세 종류 승인 — 상호 대체 금지

승인대상언제효력/비효력
A. 계정 저장·사용Vault 저장, 도메인×계정×레시피 scope계정 최초 등록·범위 확대로그인 사용만 허용. 레시피 등록이나 구매를 허용하지 않음
B. 레시피 등록·갱신예상 단계, 변수, 권한, 위험 단계, 증거 정책신규 학습, UI 변경 복구 후 버전 증가실행 절차만 신뢰. 외부 쓰기·결제를 허용하지 않음
C. 실제 행위외부 제출, 광고 예산 변경, 주문·결제·삭제·계약행위 직전해당 run/step 1회만 허용. 계정/레시피 범위를 넓히지 않음

5. 계정 미등록·레시피 미등록 흐름

5.1 계정

  1. Credential Broker가 Vault를 조회한다.
  2. 없으면 비밀값을 채팅으로 요구하지 않고, 안전 등록 세션·현재 브라우저 직접 로그인·중단 3개를 제시한다.
  3. Vault만 암호화 저장하고 채팅·로그·레시피·스크린샷에는 마스킹한다.
  4. 도메인×계정×레시피 scope와 만료시간을 A 승인으로 고정한다.
  5. 로그인 테스트 후 세션을 저장하고 원래 checkpoint에서 재개한다.

5.2 레시피

  1. Intent Planner가 dry-run을 만들고 단계, 입력 변수, 권한, 위험 단계, 증거를 표시한다.
  2. B 승인을 받아 버전 v1로 등록한다.
  3. 사이트 UI 변경 감지 시 자동 복구 초안을 만들되, v2 갱신은 다시 B 승인을 받는다.
  4. READ 반복 실행은 2회차부터 llm_calls=0을 목표로 한다.

9. 보안·신뢰 경계

  • 웹 페이지와 모델 출력은 모두 불신 입력이다. 허용된 레시피/도구/도메인으로만 실행한다.
  • Vault는 비밀의 유일한 저장소다. URL query, JSON 중첩값, 헤더, 스크린샷 OCR까지 마스킹한다.
  • READ → WRITE_INTERNAL → WRITE_EXTERNAL → IRREVERSIBLE 등급을 낮출 수 없다.
  • 최종 주문·결제는 preview hash와 실제 DOM/금액이 다르면 승인을 폐기한다.
  • recipe_run_steps와 증거 메타데이터는 append-only로 운영한다.
  • 도메인 이탈, 새 탭, 다운로드, 파일 업로드는 별도 정책 검사를 거친다.
