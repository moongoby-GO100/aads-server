문제와 현재 판정

현재 관리자 화면에서 직원 가입을 승인해도 계약조건을 입력하는 경로가 이어지지 않는다. 기존 화면으로 이동하라는 안내는 사용자가 정상 업무를 완료할 수 있다는 증거가 아니다. 이번 산출물은 기획·설계·PRD·목업이며 운영 구현 또는 배포 완료를 의미하지 않는다.

운영 로그인 후 현재 화면에 양재혁 직원의 승인 상태가 표시되는지, 실제 계약 작성이 가능한지는 이번 기획 작업에서 다시 검증하지 않았다. 과거 메시지의 가입·승인 정보는 현재 운영 실측과 구분한다.

대상 사용자와 권장안

대표·승인 권한이 있는 인사 담당은 승인 직후 계약을 작성한다. 점포 담당은 자신에게 허용된 회사·점포만 처리한다. 직원은 자신의 계약을 확인하고 서명하며 서명본을 내려받는다.

권장: 현재 V4.1 관리자 화면의 기존 직원·급여 메뉴를 유지하고, 직원 행/상세에 계약 작성 버튼을 추가한다. 같은 직원·회사·점포 문맥에서 작성 패널을 열고 계약·인사증빙에도 같은 편집기를 제공한다. 두 진입점은 하나의 계약 편집기와 API를 사용한다.

안내용판단
A현재 화면에 계약 작성·서명요청·상태 확인 통합권장. 승인 다음 행동이 같은 업무 문맥에서 이어짐

첫 실행·반복 사용·실패 복구

첫 실행: 직원·급여 → 직원 현황 → 승인 직원 행 → 계약 작성 → 조건 입력 → 미리보기 → 저장 → 서명요청.

반복 사용: 직원 상세 또는 계약·인사증빙 → 현재 상태 확인 → 저장 전/미요청 계약 수정, 요청 중 계약 알림 재전송, 서명 완료 계약 PDF 확인. 서명 완료 원본을 덮어쓰지 않는다.

실패 복구: 누락 필드는 해당 입력으로 이동, 저장 실패는 입력 보존·재시도, 세션 만료는 재로그인 후 대상 권한 재확인·사용자 확인 후 복구, 알림 실패는 계약의 요청 상태와 분리하여 재알림. 다른 회사로 문맥 변경 시 미저장 경고와 권한 재조회.

권한·다점포 원칙

같은 직원이 여러 점포에서 근무하더라도 가입 승인 연결과 계약 당사자는 구분한다. 직원+사업자+점포별 승인 연결을 화면에서 명시하며, 서로 다른 사업자의 계약을 자동 합치거나 동일 조건으로 복제하지 않는다. 다점포 근무 정보는 입력 보조로 제시하되 계약조건 확정은 관리자가 한다. 실제 직원의 시급·요일·기간을 추정해 채우지 않는다.

계약 유형은 현재 서비스의 지원 유형과 일치시킨다. 고용 형태를 임의로 프리랜서로 바꾸거나 공제율을 자동 결정하지 않는다. 실제 계약 조항·법적 적정성은 기존 템플릿의 검토 상태를 확인하고 별도 확정한다.

구현 순서와 검토 게이트

1. 이 기획·설계·PRD·목업을 CEO에게 보고한다. 승인본으로 자동 승격하지 않는다.

2. 기획 확인 후 격리 worktree의 하나의 구현 작업으로 직원 진입점·계약 편집기·상태 표시를 연결한다. 중단된 작업 산출물은 원복하지 말고 diff를 확인하여 재사용 여부를 판단한다.

3. 권한·회사 격리·API 실패·중복 요청 회귀와 현재 관리자 화면의 Playwright 증거를 확보한다.

4. 검수한 SHA로 카페24 origin 앱 릴리스 경로를 사용한다. AADS API 배포를 오비서 배포로 대체하지 않는다. 후보 health, immutable image, 라우팅 실패 롤백, 같은 digest 동기화와 최소 5분 P0/P1 감시를 충족한다.

5. 지정된 시험 회사·직원 정보를 담당의 기존 지시에서 확보하고 가입 승인→작성→직원 서명→PDF를 검증한다. 양재혁 직원의 계약을 임의 생성하거나 대신 서명하지 않는다.

계약 편집기

단계 1 대상 확인: 승인 직원 연결을 서버에서 조회하고 회사·점포를 명시한다. 미승인 대상, 접근 불가 대상에는 작성 버튼을 비활성화하고 필요한 다음 행동을 표시한다.

단계 2 조건 입력: 가입/사업자 마스터의 기존 데이터로 본인·사용자 기본정보를 채우고 누락 항목을 표시한다. 관리자는 계약 유형, 계약 작성일, 입사일·계약기간, 직무·근무 장소, 임금 산정 방식·금액·지급일, 요일별 근무/휴게·주간시간, 수당·보험·수습·기타 조항을 검토한다. 유형별 필수 필드는 서비스 validator를 따른다. 일정이 점포마다 다르면 별도 행으로 명확히 입력하며 서로 다른 사용자 사업자의 조건은 하나로 합치지 않는다.

단계 3 미리보기: 입력 스냅샷과 원본 템플릿 버전을 연결한다. 미리보기에서 돌아와 수정하면 이전 미리보기는 무효화된다. 서버 저장 성공 전에는 서명요청을 허용하지 않는다.

단계 4 요청·관리: 저장 결과의 계약 ID를 기준으로 요청한다. 요청됨·알림 실패·PDF 생성 실패를 같은 성공 표시로 묶지 않는다. 링크 복사는 실제 요청 응답 링크가 있을 때만 제공하며 이메일/SMS 전달 완료와 구분한다.

상태 모델

편집중은 UI 상태이고 저장 여부와 별개다. 실제 서버 계약 상태 문자열은 service 반환값을 기준으로 매핑한다. 아래는 사용자 표시 상태다.

작성 필요 → 입력 중 → 저장 완료 → 서명 요청됨 → 서명 완료 → PDF 준비/보관

알림: 미실행/전송 성공/전송 실패 별도 축. PDF: 미생성/생성중/준비/실패 별도 축. 만료·취소가 서버에서 지원되는지 확인하지 않은 상태에서 실제 취소 버튼을 만들지 않는다. 서명본 수정은 원본 덮어쓰기 없이 새 계약/버전 정책을 먼저 확정한다.

PDF 실패서명 완료 유지, 준비/복구 안내서명 snapshot으로 재생성, 원본 보존

프로덕션 민감정보를 일반 localStorage에 장기 저장하지 않는다. 세션 복구용 초안은 짧은 수명·사용자/tenant 연결·최소 필드로 설계하고 서버 초안 저장 지원 여부를 먼저 확인한다. 목업의 브라우저 저장은 가상 데이터에 한정한다. 서명 토큰·개인정보는 로그·캡처에 노출하지 않는다.

모바일·접근성

좁은 화면은 직원 행을 카드로 바꾸고 편집 패널은 한 열로 표시한다. 핵심 버튼은 최소 44px 높이, label/오류를 연결하고 키보드 이동·focus 복원을 제공한다. 저장·요청 고정 하단 영역이 내용을 가리지 않도록 여백을 둔다. 뒤로가기나 앱 재실행 시 사용자·회사 문맥 재검증 후 복구한다.

변경 후보와 경계

구현 후보는 현재 관리자 파일, 필요한 modules/*, 기존 계약 service/API의 필수 연결, 관련 회귀 테스트이다. 실제 변경 목록은 구현 diff로 확정한다. 이번 기획은 해당 운영 파일을 수정하지 않는다. 무관한 dirty 파일, 실제 직원·조직 데이터, 진아서버, 라일론 자료는 변경 대상이 아니다.

제품 목표

가입 승인 다음에 관리자가 현재 화면을 떠나지 않고 계약을 작성하며, 요청 결과와 직원 서명·PDF 상태를 같은 직원 문맥에서 확인한다. 메뉴를 찾기 위해 기존/현재 관리화면을 왕복하는 흐름을 없앤다.

대상: 대표·권한 있는 인사/점포 담당, 본인 계약에 접근하는 직원.

범위: 직원 계약 진입점·조건 입력·미리보기·저장·서명요청·재알림·서명본 상태/다운로드·실패 복구.

제외: 전체 관리자 화면 재설계, 자동 법률 판정, 실제 직원 조건 임의 확정, 계약 일괄 생성, 공제·급여 전면 개편, 외부 유료 발송 구매.

사용자 시나리오

대표: 가입 승인을 완료했다 → 승인 직원 행에 계약 작성이 보인다 → 회사·점포가 고정된 입력 패널에서 조건을 확정한다 → 미리보기 후 저장한다 → 서명을 요청하고 발송 결과를 확인한다.

인사 담당: 계약 목록에서 요청 대기와 알림 실패를 구분한다 → 실패한 알림을 재전송하거나 실제 링크를 공유한다 → 직원 서명 완료 후 서명본 PDF를 확인한다.

직원: 자신에게 발급된 링크로 로그인한다 → 자기 계약과 조건을 확인한다 → 동의 및 자필서명을 제출한다 → 완료 상태와 서명본을 확인한다. 링크 만료나 권한 문제면 요청 관리자와 복구 행동을 안내한다.

작업과 게이트

G0: 기획·설계·PRD·목업 저장 및 보고(이번 요청).

G1: CEO 기획 확인 후 구현 작업 범위/충돌 프리플라이트.

G2: 구현·회귀·현재 화면 증거·검수.

G3: 기존 승인 범위와 변경 SHA를 대조하여 카페24 릴리스.

G4: 시험 계정으로 운영 관리자·직원 E2E 및 5분 감시.

G0를 G2/G4 완료로 표시하지 않는다. 기획 검토 전에 중단된 runner-6ed52003은 자동 승인·재실행하지 않는다. 산출물 잔존 여부는 별도 diff로 확인하여 보존한다.

미확정과 담당 확인

  • Developer: 공용 editor의 기존 폼 재사용 경계, 실제 router/query 파라미터, 수정 payload, 다중 worker 요청 보호, 세션 초안 복구 방식.
  • HRPayrollLead: 기존에 전달받은 시험 직원·회사, 다점포 근무와 계약 당사자, 실제 조건/템플릿 검토. CEO에게 같은 정보를 재요청하지 않는다.
  • Ops: 카페24 앱 릴리스 경로의 준비·승인·현재 배포 상태와 롤백 가능한 digest.

성공률·처리시간 목표는 운영 데이터가 없어 수치로 추정하지 않는다. 최초 검증 후 측정한 값을 근거로 개선한다.
