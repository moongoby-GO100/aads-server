🔌 01. MCP란 무엇인가 — Tool Calling 표준화의 배경

MCP(Model Context Protocol)는 Anthropic이 2024년 11월 공개한 개방형 프로토콜로, LLM 애플리케이션이 외부 데이터 소스와 도구에 연결하는 방식을 표준화합니다2026-09-13 KST 스펙 원문 확인. 공식 스펙(2026-07-28판)은 MCP를 "애플리케이션이 언어 모델에 컨텍스트를 공유하고, AI 시스템에 도구와 기능을 노출하며, 조합 가능한 통합·워크플로를 구축하는 표준화된 방법"으로 정의합니다. 메시지 포맷은 JSON-RPC 2.0을 사용하며, 프로그래밍 언어 지원을 표준화한 LSP(Language Server Protocol)에서 영감을 받았다고 공식 스펙에 명시되어 있습니다. 스펙은 참여 주체를 Host(연결을 시작하는 LLM 앱)·Client(호스트 안의 커넥터)·Server(컨텍스트와 기능을 제공하는 서비스) 세 가지로 정의합니다.

MCP 이전에는 각 AI 애플리케이션마다 데이터베이스 연동, 파일 접근, 검색 API 호출 방식이 제각각이었습니다. N개의 AI 애플리케이션과 M개의 외부 시스템이 있으면 이론상 N×M개의 커스텀 연동 코드가 필요했습니다. MCP는 "AI용 USB-C"에 비유되곤 하는데, 하나의 표준 인터페이스만 구현하면 그 인터페이스를 지원하는 모든 애플리케이션·도구와 연결될 수 있기 때문입니다. 즉 도구 제작자는 "MCP 서버" 하나만 만들면 되고, AI 애플리케이션(호스트)은 "MCP 클라이언트" 하나만 구현하면 수많은 MCP 서버에 연결할 수 있습니다.

⚙️ 02. Tool Calling 원리 — LLM은 도구를 어떻게 "호출"하는가

Anthropic 공식 문서 — Tool use with Claude는 Tool Calling을 이렇게 설명합니다2026-09-13 KST 원문 확인: "Tool use(함수 호출이라고도 함)는 Claude가 개발자가 정의했거나 Anthropic이 제공하는 함수를 호출할 수 있게 합니다. Claude는 사용자 요청과 도구 설명을 근거로 언제 도구를 호출할지 스스로 결정합니다." 중요한 점은, LLM이 실제로 코드를 "실행"하는 것이 아니라는 것입니다. LLM은 "이 도구를 이 인자로 불러야 한다"는 구조화된 요청(JSON)을 텍스트로 생성할 뿐이고, 그 요청을 실제로 실행하는 것은 호출 측 애플리케이션(클라이언트 도구) 또는 Anthropic 인프라(서버 도구)입니다.

Tool Calling 왕복 흐름 (클라이언트 도구 기준)
① 사용자: "서울 날씨 알려줘"
② 앱 → Claude: tools=[get_weather 스키마] + 사용자 메시지
③ Claude → 앱: stop_reason="tool_use", tool_use{name:"get_weather", input:{location:"서울"}}
④ 앱: 실제 날씨 API를 호출해 결과를 얻음 (Claude는 관여하지 않음)
⑤ 앱 → Claude: tool_result{tool_use_id, content:"12도, 맑음"}
⑥ Claude → 앱: 최종 자연어 답변 "서울은 현재 12도로 맑습니다"

이 흐름에서 도구는 실행 위치에 따라 두 종류로 나뉩니다. 클라이언트 도구(Client tools)는 개발자가 정의한 도구와 bash·text_editor 같은 Anthropic 표준 스키마 도구를 포함하며, 실제 실행은 호출 측 애플리케이션에서 이뤄집니다. 서버 도구(Server tools)는 web_search, web_fetch, code_execution, tool_search 등으로, Anthropic 인프라에서 직접 실행되어 개발자가 별도 실행 코드를 작성할 필요가 없습니다(platform.claude.com — tool-use/overview, 2026-09-13 KST 재확인. 초판이 적은 docs.claude.com 주소는 현재 platform.claude.com으로 이전되었습니다.).

도구 호출 여부 판단은 기본값 tool_choice: {"type":"auto"}일 때 매 턴마다 Claude가 스스로 결정합니다. 요청이 도구의 설명된 기능과 맞아떨어지고 답이 이미 컨텍스트에 없을 때 도구를 호출하며, 안정적인 지식 질문·창작·일상 대화에는 직접 답합니다. tool_choice를 any(도구 중 하나는 반드시 호출)나 tool(특정 도구 강제 호출)로 바꿔 이 판단을 개발자가 강제할 수도 있습니다.

📐 03. 도구 스키마 설계 — 이름·설명·JSON Schema

도구 정의는 세 가지 필수 요소로 구성됩니다: name(도구 이름), description(도구 설명), input_schema(JSON Schema 형식의 파라미터 정의). MCP 공식 스펙(2026-07-28)은 도구 이름 규칙을 다음과 같이 명시합니다: 길이는 1~128자, 대소문자를 구분하며, 허용 문자는 영문 대소문자·숫자·밑줄(_)·하이픈(-)·점(.)뿐이고 공백·쉼표 등 특수문자는 허용되지 않으며, 서버 내에서 고유해야 합니다.

Anthropic의 도구 설계 공식 가이드(docs.claude.com/agents-and-tools/tool-use/define-tools, 2026-09-12 확인)는 "설명의 품질이 도구 성능을 좌우하는 단연 가장 중요한 요소"라고 명시하며, 도구가 무엇을 하는지, 언제 써야(또는 쓰지 말아야) 하는지, 각 파라미터의 의미와 동작 방식, 중요한 제약 조건까지 설명에 담아야 한다고 권고합니다. 권장 분량은 도구당 최소 3~4문장이며 복잡한 도구는 더 길게 써야 합니다.

❌ 나쁜 설명 (공식 문서 예시)

{
  "name": "get_stock_price",
  "description": "Gets the stock price
    for a ticker.",
  "input_schema": {
    "type": "object",
    "properties": {
      "ticker": {"type": "string"}
    }
  }
}

✅ 좋은 설명 (공식 문서 예시)

{
  "name": "get_stock_price",
  "description": "Retrieves the current
    stock price for a given ticker.
    Must be valid NYSE/NASDAQ symbol.
    Returns latest trade price in USD.
    Use when user asks about current
    price only — no other company info.",
  "input_schema": {...}
}

공식 가이드는 추가로 네 가지 원칙을 제시합니다. ① 관련 작업을 하나의 도구로 통합하라 — create_pr·review_pr·merge_pr을 따로 만들기보다 action 파라미터를 가진 도구 하나로 묶으면 선택 모호성이 줄어듭니다. ② 이름에 네임스페이스를 부여하라 — github_list_prs, slack_send_message처럼 서비스명을 접두어로 붙이면 도구가 많아져도 구분이 쉬워지고, 특히 11장에서 다룰 Tool Search 사용 시 중요합니다. ③ 응답은 고신호 정보만 반환하라 — 불투명한 내부 참조 대신 슬러그·UUID 같은 안정적 식별자를 쓰고, 다음 단계 추론에 필요한 필드만 남기라는 것입니다. 불필요하게 큰 응답은 컨텍스트를 낭비하고 핵심 파악을 어렵게 만듭니다. ④ 복잡한 입력에는 input_examples(선택 필드)로 유효한 예시 입력을 함께 제공할 수 있습니다.

MCP 도구 정의의 확장 필드 (2026-07-28 스펙)

MCP 최신 스펙은 도구 정의에 다음 필드를 추가로 규정합니다(공식 문서 실측): title(표시용 사람이 읽는 이름, 선택), icons(UI 표시용 아이콘 배열, 선택), outputSchema(도구가 반환할 구조화 결과의 JSON Schema, 선택), annotations(도구 동작을 설명하는 부가 속성). 스펙은 "신뢰할 수 있는 서버에서 온 것이 아니라면 annotations를 신뢰해서는 안 된다(untrusted)"고 명시해 도구 설명·주석이 프롬프트 인젝션 경로가 될 수 있음을 경고합니다.

실무 팁파라미터가 없는 도구를 정의할 때 inputSchema를 null로 두면 안 됩니다. MCP 스펙은 {"type":"object","additionalProperties":false}(빈 객체만 허용, 권장) 또는 {"type":"object"}(임의 객체 허용) 중 하나를 명시적으로 쓰도록 규정합니다.

🏗️ 04. MCP 아키텍처 — Host·Client·Server 3단 구조

MCP 공식 스펙(2025-06-18/2026-07-28 공통)은 통신 참여자를 세 가지 역할로 정의합니다. Host는 연결을 시작하는 LLM 애플리케이션(예: Claude Desktop, AADS 자체, Claude Code)입니다. Client는 Host 애플리케이션 내부에 있는 커넥터로, 하나의 Host가 여러 Server에 연결하기 위해 여러 Client 인스턴스를 가질 수 있습니다. Server는 컨텍스트와 기능을 제공하는 서비스입니다.

Server가 Client에 제공할 수 있는 기능은 세 가지입니다: Resources(사용자나 모델이 사용할 컨텍스트·데이터), Prompts(사용자를 위한 템플릿 메시지·워크플로), Tools(AI 모델이 실행할 함수). 반대로 Client가 Server에 제공할 수 있는 기능도 있는데, 2025-06-18 스펙에서는 Sampling(서버 주도 에이전틱 동작·재귀적 LLM 호출), Roots(서버가 URI·파일시스템 경계를 조회), Elicitation(서버가 사용자에게 추가 정보를 요청) 세 가지가 명시되어 있었습니다. 2026-07-28 최신 스펙 개요 문서에서는 이 중 Elicitation만 "Clients may offer" 목록에 남아 있었으나(2026-09-12 실측), 사이드바 문서 구조에는 Roots·Sampling 페이지가 여전히 존재해 완전히 폐지된 것인지 개요 문서 요약이 축약된 것인지는 미검증입니다 — 실제 도입 시 해당 버전의 변경 로그(changelog) 원문 확인이 필요합니다.

연결은 lifecycle(생명주기) 단계를 거칩니다: Client가 initialize 요청으로 지원 가능한 capability(기능)를 서버에 알리고, 서버가 자신의 capability로 응답하며, 이후 실제 요청·알림을 주고받습니다. 서버가 tools capability를 지원한다면 {"capabilities":{"tools":{"listChanged":true}}}처럼 선언해야 하며, listChanged:true는 도구 목록이 바뀔 때 서버가 클라이언트에게 알림(notification)을 보낼 것임을 뜻합니다.

🚇 05. Transport 계층 — stdio·SSE·Streamable HTTP

MCP 스펙의 Transports 절은 JSON-RPC 메시지를 주고받는 "전송(Transport)" 방식을 표준으로 두 가지 정의합니다: stdio와 Streamable HTTP. 스펙 원문은 "클라이언트는 가능한 한 stdio를 지원해야 한다(SHOULD)"고 권고합니다2026-09-13 KST 원문 확인.

Transport동작 방식적합한 상황
stdio클라이언트가 서버를 서브프로세스로 실행. 서버는 표준입력(stdin)으로 JSON-RPC 메시지를 읽고 표준출력(stdout)으로 응답. 메시지는 줄바꿈으로 구분되며 내부에 줄바꿈을 포함할 수 없음. stderr는 로깅용으로만 사용 가능로컬 프로세스, 파일시스템 접근 등 같은 머신에서 실행되는 도구

Streamable HTTP에는 보안 요구사항이 명시되어 있습니다: 서버는 DNS 리바인딩 공격을 막기 위해 모든 연결의 Origin 헤더를 검증해야 하며(MUST), 로컬 실행 시 모든 인터페이스(0.0.0.0)가 아닌 localhost(127.0.0.1)에만 바인딩해야 한다(SHOULD)고 스펙이 경고합니다. 또한 세션 관리를 위해 서버가 초기화 시점에 Mcp-Session-Id 헤더로 세션 ID를 발급할 수 있고, 클라이언트는 이후 모든 요청에 이 헤더를 포함해야 합니다.

Anthropic의 Claude API MCP 커넥터(Messages API에서 별도 MCP 클라이언트 구현 없이 원격 MCP 서버에 직접 연결하는 기능, 베타 헤더 mcp-client-2025-11-20)는 스펙의 전체 기능 중 도구 호출(tool calls)만 지원하며, 서버는 반드시 HTTPS로 공개되어야 하고 Streamable HTTP와 SSE 두 transport를 모두 지원하지만 로컬 stdio 서버는 직접 연결할 수 없다고 공식 문서에 명시되어 있습니다2026-09-13 KST 원문 확인.

🔁 06. 에이전트 루프 설계 — ReAct와 멀티턴 도구 호출

단발성 도구 호출(질문 1회 → 도구 1회 → 답변)과 달리, 에이전트 루프(Agent Loop)는 모델이 도구 결과를 보고 다시 판단해 다음 도구를 호출하는 과정을 여러 차례 반복하는 구조입니다. 이는 2022~2023년 학계에서 제안된 ReAct(Reasoning + Acting) 패턴 — "생각(reasoning) → 행동(도구 호출) → 관찰(결과) → 다시 생각" 순환 — 이 업계 표준 구현 패턴으로 자리잡은 것입니다. Claude의 응답이 stop_reason: "tool_use"인 동안 호출 측은 도구를 실행하고 결과를 돌려주는 것을 반복하며, 모델이 더 이상 도구가 필요 없다고 판단하면 최종 stop_reason: "end_turn" 텍스트 응답을 냅니다.

에이전트 루프 (ReAct 패턴)
┌─────────────────────────────────────────────┐
│  ①생각: "무엇을 해야 하는가"                    │
│       ↓                                      │
│  ②행동: 도구 호출 (tool_use)                    │
│       ↓                                      │
│  ③관찰: 도구 결과 수신 (tool_result)             │
│       ↓                                      │
│  ④재판단: 목표 달성? ──아니오──┐                 │
│       │예                    │                │
│       ▼                     (①로 복귀)         │
│  최종 답변 반환 (end_turn)   └────────────────┘  │
└─────────────────────────────────────────────┘

2026-07-28 MCP 스펙은 여기에 MRTR(Multi Round-Trip Requests, 다중 왕복 요청)이라는 새로운 패턴을 공식화했습니다. 서버가 tools/call 요청에 즉시 결과를 주는 대신 InputRequiredResult(추가 입력 필요 응답)로 응답할 수 있고, 이 경우 클라이언트는 elicitation/create 같은 방식으로 사용자에게 정보를 요청한 뒤, 같은 도구 호출을 inputResponses와 requestState를 포함해 재시도합니다. 예: GitHub 로그인이 필요한 도구를 호출했는데 로그인 정보가 없으면, 서버가 "GitHub 사용자명을 알려달라"는 입력 요청을 반환하고 클라이언트가 사용자에게 물어본 뒤 재호출하는 식입니다. 이때 재시도 요청의 JSON-RPC id는 최초 요청과 반드시 달라야 한다고 스펙이 명시합니다.

에이전트 루프 설계에서 실무적으로 중요한 두 가지는 턴 예산(turn budget)과 도구 목록 캐싱입니다. 루프가 무한히 반복되지 않도록 최대 턴 수·최대 비용 상한을 두는 것이 필수인데, AADS CLAUDE.md에도 "LLM 15회/task"라는 명시적 상한이 CEO 절대 규칙으로 규정되어 있습니다. 또한 2026-07-28 스펙은 tools/list 응답에 ttlMs(캐시 유효 시간)와 cacheScope(캐시 범위) 필드를 신설해, 클라이언트가 도구 목록을 매번 새로 요청하지 않고 캐싱해 지연시간과 프롬프트 캐시 적중률을 높일 수 있게 했습니다. 스펙은 "서버는 결정적(deterministic)인 순서로 도구를 반환해야 한다(SHOULD)"고도 명시하는데, 이는 동일한 도구 목록이 매번 다른 순서로 오면 LLM 프롬프트 캐시가 깨지기 때문입니다.

📌 CEO 체크포인트

  2. 턴 예산이 없는 에이전트 루프는 무한 반복·과금 폭주 위험이 있으므로, 상한이 없다는 보고를 받으면 즉시 추가를 지시한다.
  3. "AI가 중간에 추가 정보를 물어봤다"는 보고는 버그가 아니라 MRTR 같은 정상 설계 패턴일 수 있음을 이해하고, 어떤 패턴인지 구분해서 보고받는다.

⚡ 07. 병렬 툴 호출 — 언제, 어떻게 동시에 부를 것인가

Claude 응답 하나에 여러 tool_use 블록이 동시에 담길 수 있습니다. Anthropic 공식 문서(2026-09-12 확인)는 "API는 실행 순서를 규정하지 않는다 — 동시 실행(Promise.all, asyncio.gather), 도구가 나온 순서대로 순차 실행, 또는 그 조합 중 무엇을 택할지는 호출 측의 결정"이라고 명시합니다. 판단 기준은 도구의 성격입니다: 독립적이고 읽기 전용인 작업은 병렬 실행이 지연시간을 줄이는 데 안전하고, 부작용이 있거나 상태를 공유하거나 순서 의존성이 있는 도구는 순차 실행이 낫습니다.

✅ 병렬화 적합

여러 파일 동시 읽기, 여러 도시 날씨 동시 조회, 여러 DB 테이블 스키마 동시 조회 — 서로 영향을 주지 않는 조회성 작업

❌ 병렬화 부적합

파일 쓰기 후 그 파일을 읽는 작업, 레코드 생성 후 그 ID로 업데이트하는 작업 — 순서·상태 의존성이 있는 작업

병렬 호출을 사용할 때 지켜야 할 형식 규칙이 있습니다: 여러 tool_use에 대한 tool_result는 각각 별도 메시지가 아니라 하나의 user 메시지 안에 모두 담아 함께 보내야 하며, 그 메시지 안에서 tool_result 블록은 어떤 텍스트 콘텐츠보다도 앞에 와야 합니다. 공식 트러블슈팅 가이드는 이 규칙을 어기고 도구 결과를 별도 메시지로 쪼개 보내는 것이 "Claude에게 병렬 호출을 하지 말라고 가르치는" 가장 흔한 실수라고 지적합니다. 만약 순차 실행 중 앞선 호출이 실패해 뒤 호출을 아예 실행하지 않았다면, 그 호출에도 is_error: true와 짧은 사유를 담은 tool_result를 반드시 반환해야 합니다.

// 올바른 형식 — 결과를 하나의 메시지에 모아 반환
[
  {"role": "assistant", "content": [tool_use_1, tool_use_2]},
  {"role": "user", "content": [tool_result_1, tool_result_2]}
]

// 잘못된 형식 — 병렬 호출을 억제시킴
[
  {"role": "assistant", "content": [tool_use_1, tool_use_2]},
  {"role": "user", "content": [tool_result_1]},
  {"role": "user", "content": [tool_result_2]}
]

병렬 호출 빈도를 높이고 싶다면 시스템 프롬프트에 "독립적인 여러 작업을 수행해야 할 때는 순차적으로 하지 말고 관련된 모든 도구를 동시에 호출하라"는 지침을 추가하는 것을 공식 문서가 권장합니다. 다만 Claude Fable 5.1처럼 긴 에이전트 루프(커스텀 코딩 에이전트, bash/텍스트 에디터 하네스 등)에서는 다음 읽기 작업이 암묵적으로만 유추되는 상황에서 병렬 호출 빈도가 낮아질 수 있다고 공식 문서가 안내하며, 이 경우 전용 배치 지침을 프롬프트에 추가하도록 권고합니다.

AADS의 병렬 처리 실측 사례

AADS는 spawn_parallel_subagents 도구를 통해 여러 서브에이전트를 asyncio.gather로 동시 실행하는 구조를 갖추고 있습니다(CLAUDE.md AADS-190 Phase 2 기록, 2026-03-10). 이는 "독립적인 여러 조사·읽기 작업을 병렬화하라"는 위 공식 권고를 그대로 구현한 사례입니다. 13장에서 이 도구의 실제 호출 건수(45건)를 실측 데이터로 제시합니다.

🛡️ 08. 오류·재시도 설계 — isError·백오프·Graceful Degradation

MCP 스펙은 도구 실행 결과에 isError 불리언 필드를 두어, 도구가 "프로토콜 수준에서는 정상 호출됐지만 도구 자체 로직이 실패했음"을 모델에게 알리도록 설계했습니다. 이는 JSON-RPC 자체의 오류(잘못된 도구 이름, 잘못된 인자 등 프로토콜 오류)와는 다른 층위입니다 — 프로토콜 오류는 JSON-RPC 표준 오류 응답으로, 도구 실행 실패는 정상적인 결과 객체 안의 isError: true로 표현됩니다. Claude API의 MCP 커넥터도 동일하게 mcp_tool_result 블록에 is_error 필드를 둡니다.

// 도구 실행 자체는 실패했지만 정상적인 결과 객체로 반환되는 예
{
  "jsonrpc": "2.0", "id": 2,
  "result": {
    "content": [{"type": "text", "text": "파일을 찾을 수 없습니다: /etc/passwd"}],
    "isError": true
  }
}

재시도 설계의 핵심 패턴은 지수 백오프(Exponential Backoff)와 Graceful Degradation(우아한 성능 저하)입니다. 지수 백오프는 재시도 간격을 2⁰초, 2¹초, 2²초...처럼 지수적으로 늘려, 일시 장애 시 상대 서버에 부하를 몰아주지 않으면서도 복구를 기다리는 기법입니다. Graceful Degradation은 도구·서버 연결이 실패해도 전체 시스템이 죽지 않고 "일부 기능 없이도" 계속 동작하도록 설계하는 원칙입니다.

AADS 실제 재시도·Graceful Degradation 구현 (코드 실측)

AADS의 MCP 클라이언트 매니저(app/mcp/client.py, 2026-09-12 코드 직접 확인)는 이 두 원칙을 다음과 같이 실제 구현하고 있습니다.

  • 2단 재시도 구조: 서버 1개당 ping 실패 시 2 ** attempt초 간격으로 최대 3회 재시도, 그래도 전체 서버가 하나도 응답하지 않으면 5초 간격으로 전체 재시도를 다시 최대 3회 반복(코드 원문: for attempt in range(3) 내부 재시도 + for global_attempt in range(3) 전체 재시도).
  • SSE 특유의 ping 방식: 일반 GET으로 응답 본문을 기다리면 SSE는 무한 스트림이라 타임아웃까지 블로킹되므로, httpx.AsyncClient.stream()으로 헤더만 확인하고 본문은 읽지 않는 방식을 사용 — 상태 코드 200/405/406을 "연결 가능"으로 판정.
  • Graceful Degradation 3단계: ① 개별 서버 연결 실패 시 해당 서버만 제외하고 나머지로 진행 ② 상시 가동 서버가 하나도 없어도 self._initialized = True로 표시해 서버 전체가 크래시하지 않고 "도구 없이" 계속 기동 ③ get_tools() 호출 자체가 예외를 던지면 빈 리스트를 반환해 상위 로직이 깨지지 않게 함.
logger.warning("mcp_no_servers_available") self._initialized = True # graceful degradation: 서버 없어도 동작
설계 원칙이 코드가 보여주는 핵심 원칙은 "MCP 서버 연결 실패가 AADS 전체 서비스 장애로 번지지 않아야 한다"는 것입니다. 도구 하나가 없으면 그 도구를 쓰는 기능만 축소되고, 나머지 서비스는 정상 동작합니다.
📌 CEO 체크포인트
  1. 외부 연동(MCP 서버, API 등) 실패가 전체 서비스 중단으로 이어지는 설계인지, 아니면 해당 기능만 축소되는 설계인지 신규 기능 검토 시 반드시 확인한다.
  2. 재시도 로직에 상한(최대 횟수)이 없으면 무한 재시도로 인한 리소스 낭비·장애 은폐 위험이 있으므로 상한 설정 여부를 점검한다.
  3. "도구 호출이 실패했다"는 보고에서 프로토콜 오류(연결 자체 실패)인지 도구 로직 오류(isError)인지 구분해서 원인 분석을 요구한다.

🔒 09. 권한·보안 경계 — 동의·화이트리스트·민감 경로 차단

MCP 공식 스펙은 "Security and Trust & Safety" 섹션에서 4대 핵심 원칙을 명시합니다(2025-06-18/2026-07-28 공통 확인). ① 사용자 동의와 통제: 사용자는 모든 데이터 접근·작업에 명시적으로 동의해야 하고 무엇이 공유되는지 통제권을 가져야 한다. ② 데이터 프라이버시: 호스트는 사용자 데이터를 서버에 노출하기 전 명시적 동의를 얻어야 하고, 동의 없이 리소스 데이터를 다른 곳에 전송해서는 안 된다. ③ 도구 안전성: 도구는 임의 코드 실행을 의미하므로 신중히 다뤄야 하며, 신뢰할 수 있는 서버가 아니라면 도구 동작에 대한 annotations는 신뢰할 수 없는 것으로 간주해야 하고, 호스트는 어떤 도구를 호출하든 명시적 사용자 동의를 얻어야 한다. ④ LLM 샘플링 통제: 서버가 재귀적으로 LLM을 호출하는 Sampling 기능은 사용자가 허용 여부·실제 전송될 프롬프트·서버가 볼 수 있는 결과를 통제해야 한다.

스펙 자체는 이 원칙들을 프로토콜 수준에서 강제할 수는 없다고 인정하며, 구현체(호스트 애플리케이션)가 견고한 동의·인가 플로우를 구축하고, 보안 함의를 명확히 문서화하고, 적절한 접근 통제와 데이터 보호를 구현할 것을 권고(SHOULD)합니다. 즉 MCP 보안은 프로토콜이 아니라 이를 구현하는 각 애플리케이션의 책임입니다.

AADS는 두 가지 방향의 MCP 보안 경계를 코드로 실제 구현하고 있습니다(app/core/mcp_server.py 직접 확인, 2026-09-12).

  • 화이트리스트 노출: AADS가 자신의 REST API를 MCP 도구로 노출할 때(fastapi-mcp 사용), _EXPOSED_OPERATIONS 리스트에 health_check, submit_directive, 아젠다 CRUD(add_agenda, list_agendas, decide_agenda 등) 등 명시적으로 지정한 operation만 MCP 도구로 노출됩니다. 목록에 없는 엔드포인트는 자동 노출되지 않습니다.
  • 경로 블랙리스트: _EXCLUDED_PATH_PREFIXES로 /api/v1/auth, /api/v1/debug, /api/v1/admin, /api/v1/stream 네 경로 그룹을 명시적으로 제외합니다. 이는 인증·디버그·관리자·스트리밍 엔드포인트가 실수로 AI 모델에게 도구로 노출되는 것을 막는 방어선입니다.
  • graceful 비활성화: MCP_ENABLED=false 환경변수 하나로 전체 MCP 서버 마운트를 끌 수 있고, fastapi-mcp 라이브러리가 설치되지 않았거나 마운트 중 예외가 발생해도 앱 전체가 죽지 않고 경고 로그만 남깁니다.

반대 방향(AADS가 클라이언트로서 외부 MCP 도구를 호출하는 경우)의 보안 경계는 이 교육자료 작성에 사용된 도구들의 설명문에서도 직접 확인할 수 있습니다. 예를 들어 write_remote_file 도구 설명은 ".env/.ssh/credentials 등 민감 파일 차단, 최대 1MB"라고 명시하고, query_database류 도구는 "SELECT만 허용, DML/DDL 차단"이라고 명시합니다. 이는 CLAUDE.md의 R-KEY(API 키 보안) 절대 규칙(API 키를 소스코드에 하드코딩 금지, .env 경유만 허용)이 도구 설계 단계에서부터 강제되고 있는 사례입니다.

주의할 함정MCP 스펙은 "annotations는 신뢰할 수 없는 서버라면 믿지 말라"고 경고합니다. 즉 외부(제3자) MCP 서버를 연결할 때, 그 서버가 제공하는 도구 설명 텍스트 자체에 악의적 지시문이 숨어 있을 수 있는 프롬프트 인젝션 경로가 됩니다 — 검증되지 않은 MCP 서버를 그대로 연결하는 것은 새로운 공격 표면을 여는 것과 같습니다.

📉 10. 툴 과다의 함정 — 컨텍스트 오염과 선택 정확도 저하

도구 개수가 늘어나면 세 가지 문제가 동시에 발생합니다. ① 토큰 비용 증가 — 2장에서 본 것처럼 모든 도구의 이름·설명·스키마가 매 요청마다 입력 토큰으로 청구됩니다. ② 선택 정확도 저하 — 후보 도구가 많아질수록 모델이 이름과 설명만 보고 올바른 도구를 골라내야 하는 부담이 커지고, 비슷한 이름·기능의 도구가 섞여 있으면 오선택 확률이 올라갑니다. ③ 컨텍스트 오염(Context Rot) — 실제로는 쓰이지 않을 도구 설명들이 컨텍스트 윈도우를 차지해 정작 중요한 정보(사용자 지시, 이전 대화)의 상대적 비중을 희석시킵니다.

Anthropic MCP 커넥터 공식 문서(2026-09-12 확인)는 이 문제를 명시적으로 언급합니다: "도구가 많을 때(여러 서버에 걸쳐 수십 개) Claude는 도구 이름과 설명을 기반으로 선택한다. 명확하고 구체적인 도구 설명이 선택 정확도를 높인다. 큰 도구 집합에서는 관련 도구만 쿼리별로 노출되도록 Tool Search Tool과 함께 defer_loading을 활성화하는 것을 고려하라." 정확히 몇 개부터 문제가 시작되는지에 대한 절대적 임계값은 공식 문서에서 숫자로 확인하지 못했으므로 미검증이며, 다만 Tool Search Tool 자체의 공식 설명이 "수천 개(thousands)의 도구를 다루기 위한" 기능이라고 표현하는 것으로 볼 때, 업계는 "수십~수백 개 이상" 구간부터 선택 문제가 실질적으로 대두된다고 간주하는 것으로 추정됩니다(추정치, 미검증).

실측 관찰 — 이 문서를 만드는 이번 작업 자체가 사례였다

흥미롭게도, 이 교육자료를 작성하는 이번 작업 세션 자체가 "툴 과다" 문제의 실사례였습니다. 작업 시작 시점에 시스템이 제공한 "미로딩 도구(deferred tools)" 목록을 직접 세어본 결과 총 143개였고(비MCP 제어 도구 5개 + mcp__aads-tools__ 접두어 도구 138개), 이 도구들은 이름만 노출되고 파라미터 스키마는 별도로 요청해야 로딩되는 방식이었습니다. 실제로 첫 시도에서 ToolSearch(query="select:read_remote_file,list_remote_dir,query_database,fetch_url,write_remote_file")처럼 도구 이름을 쉼표로 나열해 한 번에 스키마를 불러오려 했으나 "No matching deferred tools found" 오류가 반환되어, 결국 도구 이름 하나씩 개별 키워드 검색으로 다시 요청해야 했습니다. 이는 11장에서 다룰 "Tool Search/Deferred Loading" 개념이 이론이 아니라 실제로 이 작업 도중 직접 겪은 UX 마찰(friction)이었다는 뜻입니다.

🔍 11. 대응 전략 — Tool Search와 Deferred Loading

10장의 문제에 대한 업계 표준 해법은 점진적 노출(Progressive Disclosure)입니다: 모든 도구의 전체 스키마를 처음부터 컨텍스트에 다 올리는 대신, 필요할 때만 관련 도구를 찾아 로딩하는 방식입니다. Anthropic은 이를 Tool Search Tool이라는 서버 도구로 공식 제공하며, 공식 설명은 "수천 개의 도구를 온디맨드로 발견·로딩해 다룰 수 있게 한다"입니다.

Claude API의 MCP 커넥터에서는 이 메커니즘이 defer_loading 설정으로 노출됩니다(2026-09-12 공식 문서 실측). MCP 툴셋(mcp_toolset) 설정에서 도구별로 enabled(활성화 여부)와 defer_loading(초기 로딩 지연 여부)을 지정할 수 있고, defer_loading: true인 도구는 도구 설명이 모델에게 처음부터 전송되지 않고, Tool Search Tool을 통해 필요할 때만 검색되어 로딩됩니다.

{
  "type": "mcp_toolset",
  "mcp_server_name": "google-calendar-mcp",
  "default_config": {
    "enabled": false,
    "defer_loading": true
  },
  "configs": {
    "search_events": {"enabled": true, "defer_loading": false},
    "list_events":   {"enabled": true}
  }
}
// search_events: 즉시 노출 / list_events: 지연 로딩 / 나머지: 비활성화

설정 병합 우선순위는 configs(도구별 개별 설정) > default_config(세트 전체 기본값) > 시스템 기본값 순입니다. 공식 문서는 "여러 MCP 서버에 걸쳐 수십 개 도구가 있는 대규모 환경에서는 defer_loading과 Tool Search Tool을 함께 써서 쿼리별로 관련 도구만 노출하는 것을 고려하라"고 명시적으로 권고합니다.

MCP 프로토콜 자체도 이 방향을 뒷받침하는 신설 기능을 2026-07-28 스펙에 담았습니다: tools/list 응답에 페이지네이션(cursor/nextCursor)과 캐싱 힌트(ttlMs, cacheScope)를 추가해, 도구 수가 많은 서버도 한 번에 전체를 내려받지 않고 필요한 페이지만, 그것도 캐시 가능한 형태로 가져올 수 있게 했습니다.

10장 사례와의 연결 — 이번 세션의 대응 방식

10장에서 겪은 실패(다중 이름 select 쿼리 불가)에 대한 실제 대응은, 개별 도구명마다 ToolSearch를 키워드 검색으로 재호출하는 것이었습니다. 이는 원리상 Tool Search Tool의 "필요한 것만 찾아서 로딩"이라는 개념과 동일한 패턴이며, 구현 세부사항(다중 이름 배치 조회 지원 여부)에서 이 시스템의 ToolSearch가 Anthropic 공식 Tool Search Tool과 정확히 동일한 구현체인지는 미검증이지만, "선요약 목록 + 필요시 상세 로딩"이라는 설계 사상은 동일하게 확인됩니다.

설계 원칙 요약도구가 많아질 때의 정답은 "도구를 줄이는 것"이 아니라 "한 번에 보여주는 범위를 줄이는 것"입니다. 전체 목록은 서버에 그대로 두고, 모델에게는 이름 수준의 가벼운 목록만 먼저 주고, 실제로 필요한 도구의 상세 스키마만 그때그때 불러오는 것이 핵심입니다.

① 서버 역할 — app/core/mcp_server.py

fastapi-mcp 라이브러리(요구 버전 >=0.3.0, ImportError 시 graceful 비활성화)로 AADS의 기존 FastAPI 엔드포인트를 자동으로 MCP 도구로 노출합니다. 화이트리스트(_EXPOSED_OPERATIONS)에는 health_check, infra_check, project_docs, submit_directive, list_workspaces 및 CEO 아젠다 관리 6종(add_agenda, list_agendas, get_agenda, update_agenda, decide_agenda, search_agendas)이 등록되어 있어 총 15개 operation이 화이트리스트로 관리됩니다. 제외 경로(_EXCLUDED_PATH_PREFIXES)는 /api/v1/auth, /api/v1/debug, /api/v1/admin, /api/v1/stream 4개입니다. MCP_ENABLED 환경변수(기본값 true)로 전체 기능을 켜고 끌 수 있습니다.

② 클라이언트 역할 — app/mcp/client.py, config.py

AADS는 langchain-mcp-adapters의 MultiServerMCPClient로 외부 MCP 서버 7개에 연결하도록 설정되어 있습니다. app/mcp/config.py 코드 원문 주석은 "상시 가동 4개: Filesystem, Git, Memory, PostgreSQL / 온디맨드 3개: GitHub, Brave Search, Fetch"라고 설명하지만, 실제 ALWAYS_ON_SERVERS 상수를 코드에서 직접 확인한 결과 ["filesystem", "git", "memory"] 3개만 포함되어 있고 postgres는 MCP_PORTS 딕셔너리와 get_mcp_connections()에는 정의되어 있지만 ALWAYS_ON_SERVERS·ON_DEMAND_SERVERS 어느 목록에도 포함되어 있지 않습니다. 이는 주석(문서화)과 실제 상수 목록 사이의 불일치를 코드 레벨에서 실측 확인한 것이며, 의도된 설계 변경인지 누락된 버그인지는 이번 조사 범위에서 확인하지 못해 미검증입니다.

⚖️ 14. 나쁜 도구 설계 vs 좋은 도구 설계 5쌍

예시 1 — 이름 짓기

❌ 나쁜 예

do_thing, process, handle — 무엇을 하는지 이름만으로 알 수 없음

✅ 좋은 예

github_list_open_prs, slack_send_message — 서비스명 접두어 + 동작이 이름에 그대로 드러남(3장 네임스페이스 원칙)

예시 2 — 설명문

❌ 나쁜 예

"Gets the stock price for a ticker." (공식 문서의 나쁜 예시 그대로)

✅ 좋은 예

"NYSE/NASDAQ 상장 종목의 현재가를 USD로 반환. 현재/최근 가격 질문에만 사용하고 기업 정보 등 다른 데이터는 반환하지 않음"(공식 문서의 좋은 예시 그대로)

예시 3 — 도구 분리 수준

❌ 나쁜 예

create_pr, review_pr, merge_pr, close_pr를 전부 별도 도구로 등록 — 도구 개수만 늘고 선택 모호성 증가

✅ 좋은 예

manage_pr(action: "create"|"review"|"merge"|"close", ...) 하나로 통합 — 도구 수 감소, 10장의 컨텍스트 오염 완화

예시 4 — 응답 설계

❌ 나쁜 예

DB row 전체(내부 컬럼, 타임스탬프, 불필요 메타데이터 수십 개 필드)를 그대로 JSON으로 반환

✅ 좋은 예

다음 판단에 필요한 필드(안정적 식별자, 상태값, 핵심 수치)만 추려 반환 — 공식 가이드 "고신호 정보만" 원칙

예시 5 — 오류 처리

❌ 나쁜 예

실패해도 isError 표시 없이 빈 문자열이나 null만 반환 — 모델이 성공한 것으로 오인

✅ 좋은 예

isError: true + 사람이 읽을 수 있는 실패 사유 텍스트 반환 — 모델이 재시도·대안 판단 가능(13장에서 확인한 AADS의 error_detail 미기록 사례가 이 원칙 위반의 실제 사례)

공통 패턴좋은 도구 설계는 모두 ①이름만 봐도 기능이 짐작되고 ②설명이 구체적 사용 조건까지 담고 ③관련 기능이 과도하게 쪼개져 있지 않고 ④응답이 다음 판단에 필요한 정보만 담고 ⑤실패를 명확히 신호(isError)로 전달합니다. 13장에서 실측한 AADS의 error_detail 전량 NULL 사례는 예시 5의 나쁜 패턴에 해당하는 실제 개선 대상입니다.
