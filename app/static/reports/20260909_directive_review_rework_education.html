멀티 에이전트 운영

CEO의 의도를 여러 AI가 나누어 수행하면서, 결과를 검증하고 필요한 부분만 다시 지시하는 시스템을 이해하고 설계하는 교육자료입니다.

권장안은 ‘하나의 업무 원장과 통제된 상태 전이 위에서 여러 전문 에이전트가 일하는 구조’입니다. 담당 AI의 완료 발언만으로 다음 단계가 열리지 않게 하고, 요구사항·산출물 버전·검증 근거가 일치할 때만 진행합니다. 아래 아키텍처와 파동엔진 예시는 교육용 제안이며 운영 구현 완료 보고가 아닙니다.

읽는 순서

처음에는 01 → 05 → 10 → 11장을 읽고 버튼을 눌러 보십시오. 구현을 지시할 때는 07~09·12~16·18~20장을 사용하십시오. 논문 결과는 해당 실험의 근거이며, AADS의 성능으로 환산하지 않습니다.

01. CEO가 이해할 핵심

사람 조직에서 CEO가 “파동엔진을 공용 모듈로 만들라”고 지시하면 기획자가 요구사항을 정리하고, 설계자가 인터페이스를 정하며, 개발자가 구현하고, 검수자가 증거를 확인합니다. 누락이 있으면 기획으로, 구현 오류면 개발로, 정책 결정이 필요하면 CEO에게 돌아갑니다. 멀티 에이전트 오케스트레이션은 이 업무 흐름을 소프트웨어로 관리하는 일입니다.

여러 AI가 같은 대화에 참여하는 것만으로 이 구조가 완성되지는 않습니다. 무엇을 맡겼는지, 어떤 버전을 검수했는지, 누가 승인했는지, 재작업이 원래 범위를 벗어나는지를 시스템이 보존해야 합니다. AI는 계획·생성·분석을 맡고, 서버는 권한·상태·중복 방지·완료 조건을 강제하도록 나누는 것이 이 자료의 설계 원칙입니다.

CEO의 질문시스템이 내놓아야 하는 답필요한 증거
내 의도를 정확히 이해했나?원문 → 요구사항 ID → 제외 범위가 연결됨승인된 요구사항 버전과 추적표
누가 무엇을 하고 있나?담당·의존성·현재 단계·마지막 진행이 보임작업 원장, heartbeat, 실행 이벤트
틀리면 알아서 고치나?실패 원인별 재작업, 한도 초과 시 중단결함 보고와 새 시도 ID
정말 끝났나?산출물·검수·승인·운영 인증을 구분해시가 연결된 테스트와 배포 원장

추천 구조는 연구의 단일 결론이 아니라, SOP 기반 협업·실패 분류 연구·실제 하네스 운영 사례를 AADS 업무에 맞게 결합한 설계 판단입니다. [1] [3] [7]

결과가 다른 연구를 함께 읽는 방법

이 요청과 직접 연결되는 연구: VMAO. 계획 → 의존성에 따른 병렬 실행 → 전체 결과 검증 → 누락에 대한 재계획 → 종합이라는 순환 구조를 제시합니다. 완료된 결과를 보존하면서 부족한 질문을 재실행하거나 새 질문을 추가한다는 점이 ‘확인 후 재지시’에 해당합니다. 단, 시장 조사 답변을 대상으로 한 연구이므로 코드 통합·실매매·운영 배포의 안전성을 입증한 자료는 아닙니다. [16]

논문의 자원 한도·개선 정체에 따른 종료는 답변 종합 시점의 결정입니다. 본 교육자료의 운영 설계에서는 이를 중단 사유로 기록하고, 필수 검사가 남아 있으면 ‘미완료’로 보고합니다. 또한 이전 결과를 재사용하기 전에 입력·계약 버전이 여전히 유효한지 검사하는 것은 AADS에 권장하는 추가 설계입니다. 높은 종합 평가만으로 필수 결함을 상쇄해서는 안 됩니다.

독립된 여러 주제를 찾는 조사에서는 분업이 문맥 용량을 늘려 줍니다. 반면 공유 저장소의 기능들은 서로의 변경을 이해해야 하므로 조정 비용이 생깁니다. Anthropic의 조사 사례와 CooperBench의 협업 문제는 서로 모순이라기보다 분해 가능성·공유 상태·평가 대상이 다른 사례입니다. AADS에서는 같은 문제 묶음으로 단일 실행과 멀티 실행을 비교해야 도입 효과를 판단할 수 있습니다. [4] [6]

‘AI가 AI를 검수한다’는 것 자체도 정확성 보장은 아닙니다. MAST의 검증 실패 관점과 하네스 사례를 종합하면, 자연어 점수보다 먼저 실행 가능한 검사와 증거 접근을 제공해야 한다는 설계 판단을 내릴 수 있습니다. 통과 기준은 평가자가 작업 중 임의로 낮추지 못하게 버전으로 고정합니다. [3] [7]

05. 권장 전체 구조

좁은 화면에서는 도식을 좌우로 움직여 읽을 수 있습니다.

업무 원장은 조직의 공식 장부와 같습니다. 대화창에 ‘수정 완료’가 보이더라도 원장에 산출물과 검증 근거가 없으면 다음 단계로 넘어가지 않습니다. 반대로 브라우저 연결이 끊겨도 원장과 실행 환경이 살아 있으면 업무는 유지되고, 다시 접속했을 때 같은 작업을 복원합니다.

DB 트랜잭션은 상태 변경을 보호하고, 객체 저장소나 Git은 산출물을 보관하며, 실행 큐는 실제 작업을 처리합니다. 이벤트 알림은 상태 변화를 전달하는 수단이고, 최종 사실 확인은 원장을 기준으로 합니다. 이 분리는 특정 LLM 제품에 종속되지 않는 본 자료의 권장 설계입니다.

역할 분리는 반드시 서로 다른 회사의 모델을 뜻하지 않습니다. 같은 모델이라도 별도 문맥·도구 권한·증거 접근·평가 기준을 부여할 수 있습니다. 다른 모델을 쓰면 관점이 달라질 수 있지만, 서로 독립적이거나 정답을 보장한다고 가정할 수 없습니다. 검수자는 개발자의 설명보다 원 요구사항과 실제 산출물을 먼저 봅니다.

07. 업무 지시를 ‘계약’으로 만든다

“완벽하게 만들어”라는 지시는 검사하기 어렵습니다. “닫힌 봉만 입력받아 해당 시점까지의 정보로 시그널을 산출하고, 매매행동 필드를 출력하지 않으며, 같은 입력·버전에서 같은 결과를 재현하라”는 지시는 검사할 수 있습니다. 자유 형식의 CEO 지시는 유지하되, 하위 업무에는 정형 계약을 함께 전달합니다.

09. 상태·승인·완료를 분리한다

채팅창의 ‘완료’는 최소한 무엇이 완료됐는지 설명해야 합니다. 문서 제출, 코드 검수, 운영 반영은 다른 사건입니다. 아래 상태명은 AADS 전체의 현재 스키마가 아니라 권장 논리 모델입니다.

    부분 재실행의 조건

    실패한 노드만 무조건 다시 실행하면 안 됩니다. 어떤 입력 산출물이 바뀌었는지 보고 그 산출물을 소비한 하위 노드의 검증을 무효화해야 합니다. 반대로 입력 해시·계약·테스트 기준이 그대로인 독립 결과는 보존할 수 있습니다. 재작업 그래프는 ‘실패 노드 + 변경 영향이 있는 후속 노드’로 계산합니다.

    중단 규칙: 같은 실패의 반복, 새 근거 없는 평가 반복, 재작업 한도·시간·비용 한도 도달, 권한 충돌은 종료 또는 에스컬레이션 사유입니다. 한도는 전체 트리 예산에도 적용해야 하며, 하위 에이전트를 새로 만드는 방식으로 초기화하면 안 됩니다. 한도 도달 뒤 자동 PASS나 자동 배포로 넘어가는 경로를 금지합니다.

    13. 연결 끊김·중복 실행·충돌에서 복구하기

    장기 업무의 실패는 LLM 추론만의 문제가 아닙니다. 작업을 실행한 뒤 응답만 유실되거나, 이전 worker가 뒤늦게 살아나거나, 두 실행자가 같은 작업을 가져갈 수 있습니다. 상태 영속화와 데이터 무결성 기술을 함께 설계해야 합니다.

    문제기술적용 방법남는 한계
    채팅·프로세스 중단Checkpoint + 영속 원장완료한 단계·입력 버전·미완료 행동을 저장메모리 전용 저장은 프로세스 재시작에 취약
    같은 작업 중복 수신Idempotency key + UNIQUE업무·시도·행동 키를 서버가 생성하고 중복 차단같은 키로 다른 입력 제출 시 충돌 반환 필요
    상태 저장과 큐 발행 사이 장애Transactional Outbox상태와 이벤트를 같은 트랜잭션에 기록, 별도 발행발행은 중복될 수 있어 소비자 Inbox도 필요
    이전 worker가 늦게 결과 제출Lease + owner epoch현재 소유자·세대·임대 유효성 확인 후 확정외부 시스템도 fencing 또는 멱등 계약을 받아야 함
    같은 파일·API 의미 충돌Worktree + 소유 범위 + 통합 게이트작업별 변경 격리, 공용 계약 변경은 순서 제어worktree만으로 논리 충돌이 해결되지는 않음
    이벤트 순서 역전State version / CAS예상 이전 버전이 맞을 때만 상태 변경충돌 시 재조회 후 재판정 필요
    외부 행동은 성공, 응답 유실조회·재조정 / Reconciliation외부 참조 ID로 실제 효과 확인 후 재시도 결정확인 전 성공·실패 어느 쪽도 단정 불가

    Checkpoint 개념은 LangGraph 공식 문서, DB 잠금은 PostgreSQL 공식 문서 참조. Outbox·Inbox·CAS·fencing의 조합은 본 자료의 권장 시스템 설계이며 특정 프레임워크가 자동 제공한다는 의미가 아닙니다. [10] [15]

    서버가 강제해야 하는 상태 갱신 예

    -- 교육용 의사 SQL: 실제 AADS 테이블·마이그레이션이 아님
UPDATE task_attempts
SET state = 'SUBMITTED', version = version + 1, artifact_hash = :hash
WHERE attempt_id = :attempt
  AND state = 'RUNNING'
  AND version = :expected_version
  AND owner_instance = :worker
  AND owner_epoch = :epoch
  AND lease_expires_at > CURRENT_TIMESTAMP;
-- 변경 행이 1이 아니면 결과 확정 거부 후 원장 재조회.
-- 산출물 메타데이터·상태 이벤트를 동일 트랜잭션에 기록.
-- 외부 파일은 먼저 불변 객체로 저장하고 미참조 객체는 별도 정리.

    이 DB 조건은 오래된 worker가 DB를 변경하지 못하도록 할 뿐, 이미 실행한 외부 행동을 취소하지는 못합니다. 배포·주문 같은 외부 효과는 대상 시스템의 멱등키·승인·참조 원장·보상 절차를 별도로 사용해야 합니다. 모든 환경에 대한 ‘Exactly-once 보장’으로 표현하지 않습니다.

    안전한 재개 순서

    1. 현재 작업 상태·유효 소유자·마지막 성공 이벤트를 읽습니다.
    2. 미완료 행동의 외부 효과가 있었는지 확인합니다.
    3. 산출물 해시와 요구사항 버전이 유지되는지 확인합니다.
    4. 새 owner epoch로 권한을 확보하고 필요한 행동만 재개합니다.
    5. 사용자 화면에는 보존된 결과와 재개 지점을 표시합니다.

    LangGraph의 interrupt는 사람 입력을 기다렸다가 같은 thread의 상태로 재개하는 도구입니다. 체크포인터·thread 식별·부작용의 안전성·재개 시 동작은 배포 환경에서 검증해야 하며, 함수를 넣었다는 사실만으로 안전한 복구를 증명할 수 없습니다. [11]

    14. 지식·보안·문맥을 어떻게 전달할 것인가

    모든 대화를 전달하지 말고 필요한 근거를 전달한다

    하위 에이전트에는 원 의도의 필수 조항, 담당 요구사항, 입력 산출물의 위치·해시, 관련 결정, 금지사항, 검수 기준을 보냅니다. 긴 대화의 요약만 보내면 요구사항이 누락될 수 있고, 모든 대화를 보내면 다른 프로젝트 내용과 불필요한 데이터가 섞일 수 있습니다. 요약은 탐색용으로 쓰고 결정의 원문과 검증 근거는 참조로 유지합니다.

    저장 영역보존 내용갱신 기준
    실행 상태현재 단계·시도·소유자·재개 위치서버 상태 전이

    검증된 지식재현된 실패 원인·승인된 ADR·운영 절차검수 후 승격, 적용 범위·만료·출처 기록
    가설·반성 메모개선 추정·실패 후보·다음 실험검증 전 사실로 재사용하지 않음

    Reflexion은 피드백을 기억해 다음 시도에 반영하는 방법을 보여줍니다. 운영에서는 이 아이디어에 검증·범위·만료 정책을 추가해야 잘못된 추론이 장기 규칙으로 굳는 것을 막을 수 있습니다. 프롬프트나 검수 기준을 자동 수정한 경우 새 버전을 별도 평가한 뒤 승격하도록 설계합니다. [2]

    지시와 외부 자료의 경계

    웹페이지·README·검수 의견·도구 출력은 분석 대상 데이터입니다. 그 안에 “승인 절차를 무시하라”는 문장이 있어도 권한이 되지 않습니다. 에이전트별 접근 범위를 서버에서 제한하고, 문서 작성자는 배포 자격증명을 받지 않으며 검수자는 원본 자료를 읽되 운영 변경 권한은 갖지 않도록 합니다.

    프로젝트·고객별 데이터 접근을 나누고, 외부 모델에 보낼 입력과 trace에는 필요한 정보만 남깁니다. 모델 호출 본문·도구 출력·에러 로그에 비밀값이 들어가지 않게 마스킹과 보존 정책을 적용합니다. 멀티 에이전트가 로컬 CLI로 실행되어도 외부 모델 호출의 데이터 경계는 별도 검토 대상입니다. 계정별 보존·학습 설정은 이 교육자료에서 확인하지 않았습니다.
