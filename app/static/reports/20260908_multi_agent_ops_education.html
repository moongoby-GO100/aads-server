핵심 결론

멀티 에이전트는 "AI를 여러 개 띄우면 좋아진다"가 아닙니다. 효과가 나는 조건은 일을 독립 하위작업으로 나눌 수 있고, 각 에이전트의 권한과 산출물 계약이 명확하며, 추적/검증/중단/재개가 운영 시스템에 박혀 있을 때입니다.

AADS/OHVIS는 이미 LangGraph 8-agent 그래프, Pipeline Runner, 병렬 그룹, 작업 락, OHVIS Harness/Wiki API, 하네스 트레이스 테이블을 보유하고 있습니다. 다만 현재는 위키 링크/소스/Error Book 데이터가 비어 있어 지식화와 자동 검수 루프를 더 강하게 닫아야 합니다.

1. 멀티 에이전트란 무엇인가

에이전트는 LLM이 도구, 메모리, 파일, 브라우저, DB, 코드 실행 등을 사용하면서 여러 단계로 목표를 달성하는 실행 단위입니다. 멀티 에이전트는 이 실행 단위를 여러 개로 나누어 한 명은 지휘하고, 다른 에이전트들은 조사, 구현, 검수, 배포, 문서화처럼 전문 역할을 맡는 구조입니다.

구분설명예시CEO 판단 기준
단일 에이전트한 모델 루프가 전체 업무를 처리파일 1개 수정, 짧은 로그 요약빠르고 싸지만 긴 작업에서 맥락 소실 위험이 큼
워크플로코드가 다음 단계를 고정요구사항 정리 -> 구현 -> 테스트 -> 보고예측성과 감사성이 높음
멀티 에이전트여러 전문 에이전트가 분업PM, 개발자, QA, Ops, Researcher병렬성과 전문성은 높지만 조정 비용이 생김
하네스에이전트를 감싸는 실행 장치상태, 도구권한, 재시도, 체크포인트, 추적하네스 없이는 운영 시스템이 아니라 데모에 가까움

CEO가 기억해야 할 한 줄

멀티 에이전트의 핵심은 "몇 개를 띄웠나"가 아니라 "누가 무엇을 책임지고, 언제 멈추며, 어떤 근거로 완료를 판정하는가"입니다.

2. 핵심 운영 패턴

CEO 지시 | v Orchestrator / Supervisor |-- Research Agent: 최신자료, 코드 근거, DB 근거 수집 |-- Developer Agent: 제한된 worktree에서 코드/문서 변경 |-- QA Agent: 테스트, 린트, 화면/API 검증 |-- Reviewer/Judge: 완료 기준과 리스크 판정 |-- Ops Agent: 승인 후 배포, 헬스체크, 모니터링 | v 최종 보고: 변경 파일 + 검증 + 커밋/푸시/배포 상태 + 미완료 항목
패턴작동 방식좋은 경우위험
Orchestrator-Worker중앙 지휘자가 하위 에이전트에게 작업을 분배하고 결과를 합침조사, 분석, 보고서, 복수 프로젝트 상태 점검지휘자 지시가 모호하면 하위 작업 중복과 누락이 발생
Supervisor상위 에이전트가 전문 에이전트를 도구처럼 호출최종 답변 소유자를 하나로 유지해야 할 때중앙 병목과 비용 증가
Handoff전문가에게 대화 주도권을 넘김지원, 영업, 법무, 기술처럼 담당자 전환이 자연스러운 업무인수인계 정보가 부족하면 맥락 손실
Swarm에이전트들이 서로 다음 담당자에게 넘김동적으로 문제가 바뀌는 상담/조사누가 최종 책임자인지 흐려질 수 있음
Parallel Sectioning독립 영역을 나누어 동시에 실행여러 소스 조사, 다중 서버 헬스체크, 독립 파일 검토공유 파일 수정에는 충돌 위험
Debate/Voting여러 에이전트가 다른 관점으로 답하고 판정자가 선택고위험 의사결정, 보안·법무·아키텍처 검토토큰 비용이 빠르게 증가
Evaluator-Optimizer생성자와 평가자가 반복하여 품질을 올림문서, 코드, 프롬프트, 데이터 추출 품질 개선평가기준이 약하면 자기만족 루프가 됨
Blackboard/Artifact각 에이전트가 결과를 파일/DB/아티팩트에 쓰고 참조만 전달긴 보고서, 코드 패치, 데이터 분석아티팩트 스키마와 버전 관리가 없으면 오염됨

4. 멀티 에이전트 운영 스택

1. 지시·분해 계층

CEO 지시를 TASK_ID, 우선순위, 범위, 완료조건, 금지사항으로 바꿉니다. 좋은 분해는 "서로 다른 파일/서버/자료"처럼 독립성이 높은 단위로 나누는 것입니다.

2. 오케스트레이션 계층

LangGraph, OpenAI Agents SDK, AutoGen, CrewAI 같은 런타임이 단계와 에이전트 호출을 관리합니다. 운영에서는 LLM 결정과 코드 결정의 혼합이 필요합니다.

3. 상태·체크포인트 계층

중단, 재시작, 타임아웃, 승인 대기 후에도 이어가려면 run_id, checkpoint, owner lease, heartbeat, progress log가 필요합니다.

4. 도구·권한 계층

MCP, 내부 tool registry, SSH, DB, Git, 브라우저, PC Agent를 에이전트가 사용합니다. 도구별 read/write/deploy/auth/financial/destructive 등급이 있어야 합니다.

5. 관측성 계층

trace, span, tool call, token, cost, latency, retry, error, final artifact를 남깁니다. LangSmith, Langfuse, OpenTelemetry GenAI 규약이 여기에 해당합니다.

6. 검증·평가 계층

테스트, lint, health, 화면 캡처, DB 전후 검증, LLM-as-judge, 사람 승인, 회귀 데이터셋을 연결합니다. 최종 상태 평가가 특히 중요합니다.

운영 계약 예시

작업 입력:
  project: AADS
  priority: P1
  target_files: ["app/api/pipeline_runner.py", "tests/unit/test_pipeline_runner_script_guards.py"]
  risk_tier: write
  parallel_group: "runner-ui-docs-20260908"

오케스트레이터 판단:
  - 같은 파일을 만지는 작업은 depends_on으로 직렬화
  - 다른 문서/조회 작업은 parallel_group으로 병렬 허용
  - 배포/DB/금융/인증은 승인 게이트에서 중단

완료 조건:
  - 변경 파일 목록 기록
  - 테스트 통과
  - HANDOVER 업데이트
  - 커밋/푸시/배포 상태를 사실대로 보고

예시 B. 코드 수정

코드 수정은 조사와 다릅니다. CooperBench와 ChainSWE 계열 결과처럼 여러 에이전트가 같은 코드 영역을 만지면 조정 실패가 늘어납니다. 따라서 AADS에서는 다음 원칙이 맞습니다.

좋은 분할:
  - Agent 1: 원인 분석만 수행, 파일 수정 없음
  - Agent 2: 단일 파일 패치 수행
  - Agent 3: 테스트와 코드리뷰 수행
  - Ops: 승인 후 배포만 수행

나쁜 분할:
  - Agent 1, 2, 3이 같은 파일을 동시에 수정
  - 테스트 없이 각자 "완료" 보고
  - worktree 격리 없이 main 작업트리에서 동시 작업
  - 최종 책임자가 없이 결과를 합침

8. AADS/OHVIS 권장 로드맵

우선순위조치기대효과검증 기준
P0 멀티 에이전트 작업 지시서에 target_files, parallel_group, depends_on, risk_tier, success_criteria를 필수화 공유 코드 충돌과 완료 착각 감소 새 runner job의 대상 파일 추출률, 충돌 차단 로그, 승인 전 diff 기록
P0 trace schema를 OpenTelemetry/LangSmith 호환으로 정리하고, 하위 에이전트별 span을 저장 실패 원인 추적 가능 한 작업에서 root trace, agent span, tool span, error span이 모두 조회됨
P1 OHVIS Wiki link/source/error_book 자동 적재 반복 실패와 반복 조사를 줄임 wiki_sources, wiki_links, wiki_error_book이 실제 실행 후 증가
P1 작업 유형별 에이전트 수 예산표 도입 토큰 비용 통제 작업 size별 평균 cost, tool call, latency 추적
P1 Evaluator/Judge를 단순 리뷰가 아니라 최종 상태 평가로 전환 코드/DB/화면/배포 반영 불일치 감소 완료 보고가 테스트·DB·화면·헬스 중 필요한 근거를 포함
P2 멀티 에이전트 벤치셋 구축 모델·프롬프트·하네스 변경의 품질 영향 측정 대표 작업 20개 이상, 회귀 성공률과 비용 비교표

왜 멀티 에이전트가 필요한가?병렬 가능성, 전문성, 컨텍스트 초과, 도구 다양성이 근거로 제시됨"많이 띄우면 빨라집니다" 같은 추상 답변
각 에이전트 책임은 무엇인가?역할, 입력, 출력, 금지행동, 완료조건이 분리됨모든 에이전트가 같은 일을 함
충돌 방지는 어떻게 하나?target_files, depends_on, worktree, lock, merge gate가 있음공유 main에서 직접 병렬 수정
실패하면 어디서 재개하나?checkpoint, progress log, HANDOVER, task state가 있음처음부터 다시 실행
비용은 어떻게 제한하나?size별 agent count, tool call cap, token budget, stop rule이 있음하위 에이전트 수 제한 없음
완료 판정은 무엇인가?테스트, DB, API, 화면, health, trace, 문서기록 중 필요한 근거가 있음모델이 "완료"라고 말한 것만 있음
