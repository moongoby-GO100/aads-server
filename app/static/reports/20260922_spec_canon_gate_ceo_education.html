1한 문장 정의

기획 정본화 게이트란, AI가 코드를 고치기 전에 "그 기능의 기획서가 확정돼 있는지"를 시스템이 대신 확인하고, 확정 안 됐으면 착수를 막는 자동 검문소입니다.

일상 비유 공사장에 인부를 보내기 전에, 설계도가 승인됐는지·최신판인지·도장이 찍혔는지를 경비실에서 먼저 확인하는 것과 같습니다. 경비실이 없으면 인부는 일단 벽부터 세웁니다. 나중에 설계도가 나오면 벽을 허물어야 합니다.

여기서 "인부"는 Pipeline Runner(지시를 받아 코드를 고치는 AI)이고, "설계도"는 docs/specs/ 아래의 세 문서(spec.md · plan.md · tasks.md)이며, "경비실"이 오늘 만든 게이트입니다.

2용어 풀이 — 6개만 알면 된다

용어일상 언어로우리 시스템에서
정본(正本)"이게 진짜 원본이다"라고 한 곳만 정해 둔 문서docs/specs/<프로젝트>/<슬라이스>/ 안의 세 파일
슬라이스(slice)기능 한 덩어리. 화면 하나, 버튼 하나 단위obys-v4/approve, obys-v4/account-detail 등 33개
spec / plan / tasks무엇을 만들까 / 어떻게 만들까 / 무엇부터 할까세 문서가 한 세트. 하나라도 없으면 미완성 취급
게이트(gate)통과 검사대. 조건 미달이면 못 지나감지시서를 러너에게 넘기기 직전에 끼어드는 코드
append-only덧붙이기만 하고 지우지 않기검사 결과를 tasks.md 끝에 계속 쌓아 흔적을 남김
converge(수렴)"다 만들었나?"를 기획서와 맞대보며 좁혀가는 것구현 산출물 ↔ ## 완료 기준 대조를 최대 3회 반복
용어를 용어로 설명하지 않기 "정본화"는 어려운 말이 아닙니다. "기획서를 여러 군데 흩어 놓지 말고 한 곳만 진짜로 정하자"가 전부입니다. 흩어져 있으면 AI가 어느 것을 보고 만들었는지 대표님이 확인할 수 없습니다.

3왜 필요했나 — 게이트가 없을 때 생기는 일

게이트 이전에는 순서가 이랬습니다.

지시 → AI가 코드 수정 → 커밋 → 검수 → 배포
                ↑
        기획서를 봤는지 아무도 확인 안 함

이 구조의 문제는 틀린 것을 빨리, 잘 만든다는 점입니다. AI는 지시가 모호해도 멈추지 않고 그럴듯한 답을 만듭니다. 기획이 확정되지 않았다는 사실은 코드가 이미 배포된 뒤에야 드러납니다.

게이트 이후 순서는 이렇게 바뀌었습니다.

지시 → [문1] 기획서 읽고 미해결 사항 검사 → 있으면 "구현 금지" 문구를 지시서에 삽입
     → [문2] 세 문서 버전이 서로 같은지 대조
     → AI가 코드 수정 → [문3] 완료기준과 산출물 대조 → tasks.md에 기록
     → 커밋 → 검수 → 배포
핵심 전환 "AI가 기획서를 읽도록 부탁하는 것" → "기획서 상태를 코드가 검사하는 것". 규칙 문서에만 적힌 규칙은 AI가 어깁니다. AADS 운영 문서(R-ERRBOOK)에도 "두 번 이상 어긴 규칙은 코드 차단으로 옮긴다"고 적혀 있고, 오늘 한 일이 정확히 그 이행입니다.

문3의 3회 상한

  • ## 완료 기준 아래 불릿만 읽어 산출물과 키워드로 대조합니다.
  • 회차는 <!-- converge-iteration: N -->로 tasks.md에 기록되고 지우지 않습니다.
  • 통과하면 ## STATUS: Converged (날짜), 미달이면 needs_retry.
  • 3회에 도달하면 ## CONVERGE 상한 도달 (3회) — CEO 검토 필요, 자동 append 중단을 남기고 멈춥니다. 무한 반복을 코드가 차단합니다.

5실제로 이렇게 동작한다

대표님이 이렇게 지시했다고 가정합니다.

TASK_ID: OBYS-APPROVE-001
승인 화면 버튼 정렬을 고쳐라. 정본: docs/specs/obys-v4/approve
  1. 경로 인식 — 게이트가 지시서에서 docs/specs/obys-v4/approve를 찾아냅니다. 경로를 안 쓰고 obys-v4-approve처럼 슬라이스 ID만 써도 인식합니다.
  2. 읽기 전용 검사 — 세 문서를 읽습니다. 고치지 않습니다.
  3. 결과 삽입 — 문제가 있으면 지시서 끝에 ## ANALYZE GATE 결과 (자동 교차검사, 읽기전용 — AADS-analyze-gate) 절이 붙습니다.
  4. 착수 또는 정지 — "구현 금지"가 붙었으면 러너는 코드를 건드리지 않고 보고만 씁니다. 그 보고가 대표님 승인 대기로 올라옵니다.
  5. 구현 후 — 문3이 완료기준과 대조해 빠진 항목을 tasks.md에 덧붙입니다.
대표님이 화면에서 보게 되는 변화 지시가 "조용히 잘못 진행"되는 대신, 승인 대기 카드에 "기획이 아직 확정 안 됨"이 이유와 함께 올라옵니다. 즉 게이트의 산출물은 코드가 아니라 대표님의 결정 요청입니다.

7적용 안 된 곳과 그 이유

교육자료는 "된 것"만 적으면 절반입니다. 아래는 아직 안 되는 것입니다.

#안 되는 것이유영향
1GO100 · SF · NTV2 · KIS 는 게이트가 사실상 발동 안 함이 프로젝트들은 docs/specs/ 정본이 0건. 게이트는 지시서에 정본 경로가 언급될 때만 동작정본 없는 프로젝트는 예전 방식 그대로 — 기획 미확정 착수 가능
2게이트가 원격 서버 저장소를 읽지 못함코드가 "이 서비스와 함께 배포된 저장소"만 읽도록 고정(Path(__file__).parents[2])KIS/GO100(서버 14), SF/NTV2(서버 114) 정본은 검사 대상 밖
3미달 시 자동 재작업이 안 됨코드 주석에 "AADS_CONVERGE_AUTO_RESUBMIT=1 도입 시 여기서 재제출한다" — 미구현이라고 명시빠진 항목은 기록만 되고, 다시 시키는 건 사람 몫
4완료기준 대조가 키워드 수준문3은 단어 토큰을 맞대보는 "단순·재현 가능한" 방식(코드 주석 원문)표현이 다르면 실제로 했는데 미달로 잡히거나 그 반대일 수 있음 → 3회 상한과 CEO 검토가 안전장치
5헤더 누락은 막지 않음"헤더 없음"은 보고만 하도록 의도적으로 설계새 슬라이스가 헤더 없이 생기면 버전 대조가 사실상 비활성
가장 중요한 한 줄 오늘 만든 문은 AADS 저장소의 obys-v4 33개 슬라이스에만 실효가 있습니다. 나머지 5개 프로젝트에 같은 보호를 주려면 그 프로젝트에 정본 문서부터 만들어야 합니다 — 코드를 더 짜는 일이 아니라 기획을 정리하는 일입니다.

AI 보고를 받을 때 던질 질문 3개

  1. "그 작업, 정본 경로가 지시서에 있었나?" — 없었다면 게이트는 아예 동작하지 않았습니다.

  3. "tasks.md에 converge-iteration이 몇 번 찍혔나?" — 3회면 자동 중단 상태이고 대표님 검토가 필요합니다.
