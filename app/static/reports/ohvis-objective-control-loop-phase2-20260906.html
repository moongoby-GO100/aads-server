📋 Executive Summary

CEO 질문: "목표가 수립되어 실행되면 결과와 완료, 큰 목표와 세부 목표 완료까지 결과 관리·진행 관리·시간축에서의 다음 단계 진행 판단이 필요하지 않은가?"

결론: 맞습니다. 현재 AADS에는 이 루프가 구조적으로 부재합니다. DB 실측 결과 목표(goal)/마일스톤(milestone) 테이블이 없고, 계획(project_plans)→작업(ohvis_tasks)→루프(ohvis_loops) 간 FK 연결이 없으며, success_condition 필드는 존재하지만 평가 코드가 없습니다. 학술 논문 12편과 산업 구현 6패턴을 교차 분석한 결과, 6개 컴포넌트를 추가하면 "목표 달성까지 자동 진행"이 가능합니다.

3. 필요한 아키텍처: Objective Control Loop (OCL)

핵심 구조: 목표(Goal) → 마일스톤(Milestone) → 작업(Task/Loop) → 결과(Result) → 완료판정(Judge) → 상태전이(State Machine) → 다음단계 트리거(Auto-Advance) → 회고(Retrospective)

이 루프가 시간축 위에서 돌아야 합니다: 각 단계에 예상소요시간/마감일이 있고, 지연 감지 시 자동 에스컬레이션되며, 완료 시 다음 마일스톤이 자동으로 활성화됩니다.

3-1. 6개 필수 컴포넌트

P0 — 필수

① Goal State Machine

역할: 목표의 상태를 결정론적으로 관리

상태 흐름:

draft → planned → in_progress → (blocked ⇄ in_progress) → verifying → completed → archived

핵심: Guard 함수가 전이를 통제 (LLM 호출 없이 순수 코드). 15회/task 예산에 영향 없음

학술 근거: HDDL 2.1 (HTN+시간 제약), LongCoT (단일 LLM으로 장기 판단 불가 → 외부 상태머신 필수)

산업 근거: directive_lifecycle UPSERT 패턴 확장, Temporal durable execution 경량 버전

난이도: Low Postgres 테이블 + Python transitions 클래스

P0 — 필수

② Hierarchical Goal Decomposition

역할: 큰 목표 → 마일스톤 → 세부 작업으로 계층 분해

데이터 모델:

goals (id, title, status, parent_goal_id, project, deadline, progress_pct)
milestones (id, goal_id FK, title, status, weight, order, estimated_hours)

핵심: adjacency list (parent_id)로 무한 깊이 지원. weight 기반 bottom-up 진행률 자동 계산

학술 근거: HiP (3-tier decomposition), Project Synapse (LangGraph 기반 supervisor 분해)

산업 근거: GitHub Projects parent-issue/sub-issue progress rollup (프로덕션 검증 완료)

난이도: Low–Med 테이블 설계 + Postgres trigger

P0 — 필수

③ Execution Binding (FK Chain)

역할: 실행 결과를 목표/마일스톤에 자동 귀속

구현:

ohvis_tasks.milestone_id FK → milestones.id
ohvis_loops.milestone_id FK → milestones.id
pipeline_jobs.milestone_id FK → milestones.id

핵심: 작업/루프/파이프라인 생성 시 milestone_id 지정. "이 작업이 어떤 목표에 기여하는가"를 추적 가능

학술 근거: VMAO (DAG 기반 sub-question→parent 귀속), Agent-as-a-Judge (계층적 요구사항 추적)

난이도: Low ALTER TABLE + FK 추가

P1 — 중요

④ Completion Judge (완료 판정)

역할: 마일스톤/목표의 "진짜 완료" 여부를 판정

2-tier 판정:

  • Tier 1 (코드): 선언적 완료 조건 — "모든 필수 sub-task = completed AND P0 실패 = 0" → LLM 호출 없음
  • Tier 2 (LLM): 의미적 판정 — "이 결과가 목표 의도를 실제로 달성했는가?" → 1회 LLM 호출

핵심: Tier 1으로 80% 자동 판정, Tier 2는 모호한 경우만. success_condition 필드를 실제로 평가하는 코드 추가

학술 근거: Agent-as-a-Judge (궤적 기반 완료 판정, LLM-as-Judge 대비 정확도 우위), VMAO (completeness_score ≥ threshold → advance)

산업 근거: Devin 2.0 plan-then-confirm gate, Mind-Tool (desired-state vs current-state 비교)

난이도: Medium DSL 설계 + LLM 판정 프롬프트

P1 — 중요

⑤ Temporal Progression (시간축 관리)

역할: 마감일, 예상 소요시간, 지연 감지, 적응적 재스케줄링

구현:

milestones.estimated_hours, milestones.deadline, milestones.started_at
Watchdog Job: elapsed vs estimate 비교 → at_risk / overdue 이벤트

핵심: 1.5x 예상시간 초과 시 at_risk, 마감일 임박 시 escalation. Temporal.io 도입 없이 Postgres cron + 기존 Watchdog 확장

학술 근거: HDDL 2.1 (시간 제약 HTN), H-RePlan (local retry → global replan 2-tier 에스컬레이션)

산업 근거: Temporal durable execution 패턴의 경량 Postgres 구현 (신규 인프라 불필요)

난이도: Low–Med 기존 watchdog 확장

P1 — 중요

⑥ Auto-Advance Engine (자동 진행)

역할: 마일스톤 완료 시 다음 마일스톤을 자동 활성화하고 작업을 생성

구현:

Postgres LISTEN/NOTIFY on milestone.status = 'completed'
→ advance_to_next_milestone(goal_id) → create_tasks_for_milestone()

핵심: 이벤트 드리븐(LISTEN/NOTIFY) + 폴링 폴백(5분 sweep). 실패 시 bounded retry (3회) → blocked → CEO 알림

학술 근거: SAGA (에피소드 완료 → 교훈 추출 → 다음 에피소드 자동 시작), BCER (Brain→Reflector bounded recovery)

산업 근거: 기존 watchdog "10회 연속 실패 → 텔레그램" 패턴을 목표 레벨로 일반화

난이도: Medium 이벤트 버스 + completion criteria DSL

5. 제안 데이터 모델

5-1. 신규 테이블

-- ① Goal Registry
CREATE TABLE strategic_goals (
    id              UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    project         VARCHAR(20) NOT NULL,           -- AADS/KIS/GO100/SF/NTV2/NAS
    parent_goal_id  UUID REFERENCES strategic_goals(id),  -- 계층 (NULL = 최상위)
    title           TEXT NOT NULL,
    description     TEXT,
    status          VARCHAR(20) NOT NULL DEFAULT 'draft',
        -- draft → planned → in_progress → blocked → verifying → completed → archived
    priority        VARCHAR(10) DEFAULT 'P2',       -- P0/P1/P2/P3
    progress_pct    NUMERIC(5,2) DEFAULT 0,         -- bottom-up 자동 계산
    deadline        TIMESTAMPTZ,
    estimated_hours NUMERIC(8,2),
    started_at      TIMESTAMPTZ,
    completed_at    TIMESTAMPTZ,
    created_by      VARCHAR(50),                    -- CEO/system/agent
    success_criteria JSONB,                         -- Tier 1 선언적 조건
    created_at      TIMESTAMPTZ DEFAULT NOW(),
    updated_at      TIMESTAMPTZ DEFAULT NOW()
);

-- ② Milestones (Goal 하위)
CREATE TABLE goal_milestones (
    id              UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    goal_id         UUID NOT NULL REFERENCES strategic_goals(id),
    title           TEXT NOT NULL,
    status          VARCHAR(20) NOT NULL DEFAULT 'pending',
    weight          NUMERIC(5,2) DEFAULT 1.0,       -- 진행률 가중치
    sort_order      INT NOT NULL DEFAULT 0,
    estimated_hours NUMERIC(8,2),
    deadline        TIMESTAMPTZ,
    started_at      TIMESTAMPTZ,
    completed_at    TIMESTAMPTZ,
    success_criteria JSONB,
    auto_advance    BOOLEAN DEFAULT true,           -- 완료 시 다음 자동 진행
    created_at      TIMESTAMPTZ DEFAULT NOW(),
    updated_at      TIMESTAMPTZ DEFAULT NOW()
);

ALTER TABLE ohvis_tasks     ADD COLUMN milestone_id UUID REFERENCES goal_milestones(id);
ALTER TABLE ohvis_loops     ADD COLUMN milestone_id UUID REFERENCES goal_milestones(id);
ALTER TABLE pipeline_jobs   ADD COLUMN milestone_id UUID REFERENCES goal_milestones(id);
ALTER TABLE project_tasks   ADD COLUMN milestone_id UUID REFERENCES goal_milestones(id);

-- ④ Goal State Transitions (감사 로그)
CREATE TABLE goal_transitions (
    id              UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    goal_id         UUID REFERENCES strategic_goals(id),
    milestone_id    UUID REFERENCES goal_milestones(id),
    from_status     VARCHAR(20),
    to_status       VARCHAR(20) NOT NULL,
    trigger_type    VARCHAR(30),  -- auto_advance / ceo_manual / judge_verdict / timeout
    trigger_detail  JSONB,
    actor           VARCHAR(50),  -- system / ceo / agent_id
    created_at      TIMESTAMPTZ DEFAULT NOW()
);

-- ⑤ Completion Verdicts
CREATE TABLE completion_verdicts (
    id              UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    target_type     VARCHAR(20) NOT NULL,  -- goal / milestone
    target_id       UUID NOT NULL,
    tier            INT NOT NULL,           -- 1=코드판정, 2=LLM판정
    verdict         VARCHAR(20) NOT NULL,   -- passed / failed / partial
    score           NUMERIC(5,2),
    reasoning       TEXT,
    evidence        JSONB,                  -- 판정 근거 (쿼리결과, 파일경로 등)
    cost_usd        NUMERIC(8,4),
    created_at      TIMESTAMPTZ DEFAULT NOW()
);

6. 기존 AADS 자산 재활용

기존 자산현재 용도OCL에서의 재활용
ohvis_loops.success_condition필드만 존재, 평가 코드 없음→ Tier 1 완료 판정의 조건 저장소로 활성화. check_safety_limits()에 평가 로직 추가
ohvis_tasks.ohvis_judgement개별 작업 판정→ 마일스톤 레벨로 집계. 모든 sub-task 판정이 passed면 마일스톤 Tier 1 통과
watchdog 규칙서비스 헬스 감시, 10회 실패 → 텔레그램→ 목표 레벨 at_risk/overdue 감지 + 텔레그램 CEO 알림으로 확장
memory_recall.py (AADS-186E)5섹션 메모리 빌더, 에이전트 완료 시 discovery 기록→ 목표 완료 시 Retrospective 자동 추출 + 다음 목표에 주입 (SAGA 패턴)
agent_orchestrator.py인메모리 DAG 스케줄러→ milestone 단위 DAG를 DB에 저장하도록 확장. 서버 재시작에도 유지
FLOW 프레임워크Find→Layout→Operate→Wrap up→ 마일스톤 4단계 템플릿: Find=조사, Layout=설계, Operate=실행, Wrap=검증
pipeline_runner코드 수정/배포 자동화→ milestone_id 귀속으로 "어떤 목표를 위한 코드 작업인가" 추적

핵심: 완전히 새로 만드는 것이 아니라, 기존 7개 자산에 목표 계층을 연결하는 것입니다.
