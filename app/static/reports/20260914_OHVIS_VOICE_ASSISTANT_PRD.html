1. 요약과 판정

판정: 구현 가능하다. 단, 성립 조건이 하나 있다 — 음성 담당 세션은 "조회하지 않는다".

CEO께서 제시한 구조(음성담당 ↔ 오케스트레이터 ↔ 시스템·러너)는 오비스의 현재 자산으로 대부분 조립된다. 신규 개발보다 배선(wiring)에 가깝다. 다만 음성 담당이 질문을 받고 나서 DB를 뒤지기 시작하면 설계가 무너진다. 음성의 제한 시간은 1.5초이고, 조회 한 번이 그 예산을 통째로 먹는다.

CEO 요구설계상 해법상태
현황을 상시 실시간 보유스냅샷 루프(60초, SQL 집계 전용)가 만들어 두고 음성 담당은 1행만 읽음신규
음성 담당이 1차 정제해 보고Haiku 4.5 + L4 음성 포맷 에셋(3문장·숫자 3개·질문 종료)신규 에셋 1건
질문을 실시간으로 오케스트레이터에 전달음성 담당이 의도 분류 후 오케스트레이터 세션에 위임(내부 큐)신규
준비되는 동안 빠르게 현황 보고프리앰블 발화 + 스냅샷 기반 중간 응답신규
오케스트레이터가 각 담당에 작업 지시pipeline_runner_submit_batch (parallel_group / depends_on)기존
작업 현황을 실시간 데이터로 체크pipeline_jobs + ohvis_tasks + trace기존
중간보고 → 음성 전달상태 전이 이벤트 → 음성 담당 요약 → TTS신규
완료 순차 보고 + 종합 보고지시 추적 테이블(voice_directive_track)로 부모-자식 집계신규 1테이블
작업1 진행 중 작업2 추가 지시같은 추적 트리에 형제 노드로 추가, 독립 완료 보고신규

2. 문제 정의 — 왜 전담 세션인가

지금의 CEO 채팅 세션은 깊이에 최적화돼 있다. 8섹션 보고서, 표, 커밋 해시, 검증 로그. 화면으로 읽을 때는 옳지만 귀로 들을 때는 전부 잡음이다. 그리고 무엇보다 느리다.

실측된 3가지 장애 요인

#사실근거음성에서의 결과
1현황 질문 1건에 DB 조회 6회본 세션 직전 턴 실측응답까지 10초 이상 → 고장으로 인식
2ohvis_harness_traces 22,830건 중 latency_ms 채워진 건 0건DB 집계음성 지연을 측정조차 못 함
3ohvis_tasks 좀비 5건(running 표기, 실제 정지)상태·갱신시각 대조음성으로 틀린 숫자를 보고하게 됨

3번이 가장 위험하다. 화면 보고는 CEO가 스크롤해서 되짚지만, 귀로 들은 숫자는 검증 없이 그대로 신뢰된다.

전담 세션이 해결하는 것

  • 포맷 분리 — 같은 사실을 귀용으로 압축. 채팅 세션의 보고 규칙과 충돌하지 않게 스코프로 격리한다.
  • 속도 분리 — 음성 담당은 조회하지 않고 이미 계산된 것만 읽는다.
  • 권한 분리 — 음성 담당은 읽기 전용. 쓰기는 전부 오케스트레이터를 거친다. 오인식이 배포를 부르지 않게 만드는 구조적 차단이다.

설계 원칙 3가지

  1. 음성 담당은 계산하지 않는다. 집계는 루프가, 판단은 오케스트레이터가 한다. 음성 담당은 말로 바꾸는 일만 한다.
  2. 쓰기 권한은 한 곳에만 둔다. 오케스트레이터만 러너를 부른다. 음성 담당에 쓰기 도구를 주지 않는 것이 최선의 안전장치다.
  3. 모든 지시는 추적 트리에 들어간다. 작업1 진행 중 작업2가 와도 형제 노드로 붙고, 완료는 각각, 종합은 트리 단위로 보고한다.

4. 역할과 권한 매트릭스

CEO께서 "역할과 권한이 엄청 중요하다"고 하신 부분이다. 권한은 프롬프트로 부탁하는 것이 아니라 도구 목록으로 강제한다.

능력A. 음성 담당B. 오케스트레이터C. 러너 워커
스냅샷 읽기✅ (유일한 상시 소스)✅—
DB 조회(SELECT)⚠️ 1회 한정(스냅샷 미스 시)✅ 제한 없음✅
RAG 검색✅ top-3, 300자 상한✅ top-10✅
지시서 생성❌✅❌
러너 제출❌ 도구 미보유✅❌
파일 쓰기·커밋·푸시❌ 도구 미보유⚠️ 승인 후✅ 격리 worktree
배포·재시작❌⚠️ CEO 화면 승인 필수❌
TTS 발화✅ 유일❌❌
CEO에게 질문✅ (예/아니오 1개)간접(음성 담당 경유)❌

핵심 규칙 — 음성 담당 세션의 도구 화이트리스트에 쓰기 계열 도구를 아예 넣지 않는다. 프롬프트에 "하지 마라"라고 쓰는 것으로는 부족하다. 오인식 한 번이 배포를 부르면 되돌릴 수 없다. (참고: AADS 운영 원칙 R-ERRBOOK — "두 번 이상 어긴 규칙은 코드 차단으로 옮긴다.")

비용 원칙: 음성 담당은 호출 빈도가 가장 높고 출력이 가장 짧다. 여기에 Opus를 쓰면 비용이 역전된다. Haiku 기본 + 필요 시 승격이 CEO 비용 효율 원칙(LLM 15회/task, 비용 효율 최우선)과 맞는다.

승격 규칙 (자동)

if 질문이 스냅샷 필드로 답 가능        -> Haiku 4.5   (도구 0회)
elif 단일 프로젝트 + RAG 1회            -> Haiku 4.5   (도구 1회)
elif 교차 프로젝트 / 원인 추론 필요      -> Sonnet 5    (승격, 프리앰블 발화)
elif 배포·장애·비용 판단                -> Opus 5      (오케스트레이터로 위임)

8. 프롬프트 엔지니어링

prompt_assets에 L4 에셋 1건을 추가하고 workspace_scope·role_scope·intent_scope로 음성 세션에만 적용한다. 기존 채팅 보고 규칙(8섹션)과 충돌하지 않는다.

너는 귀로 듣는 보고를 한다. 화면 보고 규칙(8섹션·표·헤딩)은 이 세션에 적용하지 않는다.

1. 3문장 이내. 첫 문장은 결론.
2. 숫자는 최대 3개. 소수점·퍼센트 소수 자리는 반올림해 말한다.
3. 읽지 않는 것: 표, URL, 커밋 해시, 파일 경로, UUID, 영문 약어 나열.
   필요하면 "자세한 건 화면에 띄웠습니다"로 넘긴다.
4. 마지막 문장은 CEO가 예/아니오로 답할 수 있는 질문 하나. 선택지는 2개를 넘기지 않는다.
5. 모르면 "확인이 필요합니다"라고 말한다. 추정을 확정처럼 말하지 않는다.
6. 스냅샷이 90초보다 오래됐으면 "조금 전 기준입니다"를 붙인다.
7. 지시를 받으면 실행하지 말고 오케스트레이터에 넘긴다. 넘겼다는 사실만 보고한다.
