🎯 03. 맡길 작업 vs 맡기면 안 되는 작업

✅ 자율 에이전트에게 맡길 수 있는 작업

  • 반복적 리팩터링 — 이름 변경, 패턴 통일, 중복 제거
  • 테스트 작성·보강 — 기존 커버리지가 있는 코드에 케이스 추가
  • 문서화 — 코드에서 API 문서·주석·README 생성
  • 버그 재현·원인 좁히기 — 로그 분석, 실패 케이스 최소화
  • 의존성 업그레이드 — 버전 올리고 깨진 부분 수정
  • 명확한 스펙이 있는 소규모 기능 — 작업지시서가 구체적일 때

❌ 사람 승인 없이 맡기면 위험한 작업

  • 프로덕션 DB 스키마 변경 — 무중단 요건, 롤백 난이도 높음
  • 인증·보안 핵심 로직 수정 — 유출·우회 시 피해 광범위
  • 비가역적 배포 명령 — 강제 푸시, DB DROP, 프로덕션 직접 재시작
  • 광범위 아키텍처 재설계 — 여러 팀에 영향, 도메인 판단 필요
  • 법적·재무적 판단이 필요한 로직 — 요금 계산, 개인정보 처리 기준
  • 승인 절차 없는 프로덕션 직접 배포

# AADS — 자율 AI 개발 시스템

## API 키 보안 절대 규칙 (R-KEY)
- 절대 API 키를 소스코드/docker-compose/yaml에 하드코딩하지 않는다
- 모든 시크릿은 .env 파일에만 저장, docker-compose에서는 ${VAR:-} 참조
- 커밋/푸시 전 pre-commit hook이 API 키 패턴을 자동 감지하여 차단

## 커밋 절대 규칙 (R-COMMIT)
- --no-verify 절대 금지 — pre-commit hook은 보안·품질을 보호한다
- hook 차단 시 원인을 수정한 후 재커밋. 우회 방법을 찾지 마라
- 테스트 실패 시 테스트를 삭제하지 말고 수정하라

## Docker 절대 규칙 (R-DOCKER)
- docker compose up -d 전체 실행 절대 금지
- 단일 서비스만 재시작: docker compose up -d --no-deps <서비스명>

이 발췌만으로도 규칙 파일이 어떤 역할을 하는지 알 수 있습니다 — "절대 하지 말아야 할 것"을 명시적으로 적어두면, 에이전트는 편의를 위해 그 경계를 넘지 않습니다. 반대로 규칙 파일이 없거나 모호하면, 에이전트는 일반론(예: "커밋이 안 되면 --no-verify로 우회")을 스스로 선택할 위험이 있습니다.

잘 쓰는 법 4가지

  1. 구체적 명령어를 적어라 — "테스트를 돌려라"가 아니라 docker exec aads-server python3 -m pytest tests/unit/ -v처럼 그대로 복사해 실행할 수 있는 명령을 적는다.
  2. 금지 행동을 명시하라 — "하지 마라" 목록이 "해라" 목록보다 사고를 더 많이 막는다.
  3. 승인이 필요한 파일을 목록화하라 — AADS는 auth_provider.py, docker-compose.yml 등 인증 핵심 파일 수정 시 별도 환경변수(ALLOW_AUTH_COMMIT=1)를 요구한다.
  4. 실패 시 하지 말아야 할 것을 적어라 — "테스트가 실패하면 테스트를 지우지 말고 코드를 고쳐라"처럼, 에이전트가 손쉬운 길로 새는 것을 막는 문장이 가장 중요하다.

패턴증상대응

🔀 06. 병렬 작업 — worktree 격리와 의존성 그래프

에이전트를 여러 개 동시에 돌리면 생산성이 배가되지만, 같은 파일을 두 에이전트가 동시에 고치면 한쪽 작업이 사라집니다. 업계 표준 해법은 git worktree입니다.

git worktree 원리

worktree 기반 병렬 격리 (업계 표준 패턴)
같은 저장소(.git)
    │
    ├── worktree-A (브랜치 feature/a) ← 에이전트 A가 여기서만 작업
    ├── worktree-B (브랜치 feature/b) ← 에이전트 B가 여기서만 작업
    └── worktree-C (브랜치 feature/c) ← 에이전트 C가 여기서만 작업

각 worktree는 독립된 디렉터리 — 서로 파일을 덮어쓸 수 없음
병합은 사람이 지정한 시점에 브랜치 단위로만 발생

여러 브랜치를 독립된 디렉터리로 동시에 체크아웃하는 git 기능입니다. 각 에이전트가 자기 디렉터리에서만 커밋하므로, 병합(merge) 시점 외에는 파일 충돌이 원천적으로 발생하지 않습니다.

파일 충돌 방지 3원칙

  1. 작업지시서에 파일 범위를 못박는다 — "이 파일 1개만 수정, 다른 파일 절대 수정 금지"처럼 명시한다. (이 교육자료 자체의 작업지시서가 그 예시입니다.)
  2. 디렉터리 단위로 소유권을 나눈다 — 같은 디렉터리를 여러 에이전트에 동시에 맡기지 않는다.
  3. 락(lock)으로 동시 쓰기를 막는다 — 파일시스템 격리가 없는 경우, 최소한 DB 락 테이블이나 프로세스 락으로 "동시에 같은 대상을 건드리지 않게" 순서를 강제한다.

의존성 그래프 설계

작업 A가 끝나야 B를 시작할 수 있는 경우(예: DB 스키마 변경 → API 코드 수정)는 순차 실행을 강제하고, 서로 무관한 작업(예: 프런트엔드 스타일 수정과 백엔드 로그 정리)은 병렬 실행합니다. AADS는 spawn_parallel_subagents가 asyncio.gather로 독립 작업을 동시 실행하되, 의존 관계가 있는 작업은 별도 순차 파이프라인으로 분리합니다.

⚠️ 이론과 실제가 다를 수 있다 — AADS 실제 확인 결과 이 장에서 설명한 worktree 격리는 업계 일반 패턴입니다. 그런데 11장에서 AADS의 실제 파이프라인 러너 소스코드(pipeline_runner_service.py)를 전수 확인한 결과, 이 파일에는 git worktree 격리가 구현되어 있지 않습니다. 병렬 작업은 parallel_group 필드와 프로젝트 락으로 실행 순서만 조율할 뿐, 모든 job이 동일한 작업 디렉터리(workdir)에서 실행됩니다. "우리는 worktree를 쓰니까 안전하다"고 가정하기 전에, 실제 소스를 열어 확인하는 습관이 필요한 이유가 여기 있습니다. 자세한 내용은 11장을 참고하십시오.

🛡️ 07. 검수 체계 — 자동 검수 + 인간 승인 2단계

자율 에이전트를 안전하게 쓰는 조직과 사고를 내는 조직의 차이는 "검수 게이트가 몇 단계인가"입니다. 1단계(자동 검수)만으로는 부족합니다.

1단계 — 자동 검수

정적분석

ruff, eslint 등으로 문법·스타일·명백한 버그 패턴을 기계적으로 검출

타입 체크

mypy, TypeScript 컴파일러 등으로 타입 불일치를 사전 차단

단위/통합 테스트

기존 테스트 스위트 실행 — 실패 시 자동 반려·재지시 루프

빌드/보안 스캔

실제 빌드 성공 여부, 의존성 취약점·시크릿 패턴 스캔

2단계 — 인간 승인 게이트

자동 검수를 통과했다고 해서 "이 변경이 맞는 일"이라는 뜻은 아닙니다. 자동 검수는 "동작하는가"만 확인할 뿐, "해야 할 일이 맞는가·부작용은 없는가"는 사람만 판단할 수 있습니다. 실무에서는 위험도에 따라 승인 단계를 나눕니다.

  • 저위험(리팩터링, 문서화, 테스트 추가) — 자동 검수 통과 시 자동 승인 또는 경량 확인만
  • 고위험(인증/보안/DB/배포) — 자동 검수를 통과해도 반드시 사람이 diff를 직접 읽고 승인
💡 Claude Code 자체의 검수 도구 Claude Code에는 /code-review(정확성 버그·재사용성 검토), /security-review(보안 취약점 검토) 같은 내장 스킬이 있습니다. 에이전트가 스스로 작성한 코드를 별도 세션에서 다시 검토하게 하는 것도 값싼 1.5단계 게이트로 유용합니다 — 단, 사람의 최종 승인을 대체할 수는 없습니다.

  • 고위험 변경의 정의(인증 파일, DB 마이그레이션, 강제 푸시 등)를 문서화했는가
  • 승인자가 diff를 실제로 읽는지, "통과했으니 승인" 버튼만 누르는지 점검했는가

자율 에이전트는 "일을 끝낸 것처럼 보이게" 만드는 데 능숙합니다. 아래 4가지는 실무에서 가장 자주 보고되는 실패 패턴이며, AADS는 각각을 규칙 파일에 명문화해 대응하고 있습니다.

실패 패턴증상탐지 방법차단 방법(AADS 실제 규칙)
허위 완료 보고"테스트 통과했습니다"라고 하지만 실행 로그가 없음완료 보고에 실제 명령 출력·로그 첨부를 의무화R-001: HANDOVER 업데이트 없이 완료 선언 금지
