01자동화 도구란 무엇인가 — 3개 부품

자동화 도구는 "사람이 반복해서 하던 판단과 실행을, 기계가 정해진 조건에서 대신 수행하게 만드는 장치"입니다.

모든 자동화는 예외 없이 3개 부품으로 이루어집니다. 새로운 자동화를 지시하실 때 이 3개를 분리해서 말씀하시면, AI가 엉뚱한 것을 만들 확률이 크게 줄어듭니다.

자동화 사고의 90%는 "판정"이 빠져서 납니다 트리거와 실행만 있고 판정이 없으면, 망가진 채로 계속 도는 자동화가 됩니다. 오비스에서 실제로 있었던 일 — 배포 큐 워커가 옛 커밋 SHA에 고정된 채 매분 재시도하며 5분마다 서버를 재기동시켰습니다. "실행"은 성공적으로 돌고 있었지만 "판정"이 없어서 아무도 몰랐습니다. 오비스

자동화는 공짜가 아닙니다. 만드는 비용 + 유지하는 비용이 듭니다. 아래 식이 판단 기준입니다.

"이거 자동화해줘"보다 "5분마다(트리거) 이 명령을 돌려서(실행) HTTP 200이 아니면 텔레그램으로 알려줘(판정)"라고 3개를 나눠 말씀하시면 결과물의 품질이 달라집니다. 특히 마지막 판정을 빼면 AI는 대부분 판정을 만들지 않습니다.

02자동화 성숙도 5단계

자동화에는 단계가 있습니다. 회사가 어느 단계에 있는지 알아야 "다음에 무엇을 해야 하는지"가 보입니다.

단계이름사람이 하는 일기계가 하는 일오비스 해당 영역

오비스는 L4까지 도달한 드문 조직입니다 — 다만 층이 고르지 않습니다 L1~L4가 모두 존재하지만, L3(판정·알림) 층이 상대적으로 얇습니다. 18장에서 보실 실측 결함 대부분이 "실행은 되는데 실패를 아무도 모르는" L3 공백에서 나옵니다.

단계를 건너뛰면 생기는 일

L2(스케줄) 없이 L4(에이전트)로 가면, 에이전트가 무엇을 언제 했는지 기록이 남지 않습니다. L3(판정) 없이 L4로 가면, 에이전트가 "완료했습니다"라고 보고했지만 실제로는 안 된 상태가 반복됩니다. 이것이 오비스 규칙에 "검증 없이 완료 선언 금지"가 반복해서 등장하는 이유입니다. 오비스

04MCP란 무엇인가 — M×N 문제

MCP(Model Context Protocol, 모델 컨텍스트 프로토콜)는 AI 모델이 외부 도구·데이터에 접근하는 방식을 표준화한 규격입니다. Anthropic이 2024년 11월에 공개했고, 지금은 여러 AI 업체가 함께 쓰는 사실상의 표준이 되었습니다. 개념

한 줄 비유 — MCP는 AI 세계의 USB-C입니다 예전에는 기기마다 충전 단자가 달라서 케이블을 기기 수만큼 들고 다녀야 했습니다. USB-C가 나온 뒤에는 케이블 하나로 전부 연결됩니다. MCP는 "AI ↔ 도구" 연결에서 똑같은 일을 한 규격입니다.

MCP가 없던 시절 — M×N 문제

AI 모델이 M개, 연결할 도구·시스템이 N개라고 합시다. MCP가 없으면 M×N개의 연결 코드를 각각 만들어야 합니다.

M×N 문제 (MCP 이전) vs M+N (MCP 이후)

  Claude ──┬── DB                   Claude ──┐
           ├── GitHub                         │
           ├── 파일시스템            GPT ─────┼──▶ [ MCP ] ──┬── DB
           └── 브라우저                       │              ├── GitHub
  GPT ─────┬── DB                   Gemini ──┘              ├── 파일시스템
           ├── GitHub                                        └── 브라우저
           ├── 파일시스템
           └── 브라우저             모델 3 + 도구 4 = 7개 연결
  Gemini ──┬── ... (4개 더)         도구를 새로 만들면 → 모든 모델이 즉시 사용
                                     모델을 바꿔도 → 도구는 그대로

  모델 3 × 도구 4 = 12개 연결
  도구 1개 추가 → 연결 3개 추가 제작

흔한 오해 — "MCP를 붙이면 AI가 똑똑해진다" 아닙니다. MCP는 모델의 지능을 올리지 않습니다. 모델에게 손발과 눈을 달아줄 뿐입니다. 판단이 틀리는 문제는 MCP로 해결되지 않고 프롬프트·컨텍스트·모델 선택으로 해결합니다. 반대로 "정보를 몰라서" 틀리는 문제는 MCP로 대부분 해결됩니다.

전송 방식 2가지 — 언제 무엇을 쓰나

stdio (표준 입출력)

호스트가 서버를 자식 프로세스로 띄우고 파이프로 대화합니다.

장점 — 네트워크 노출 없음, 인증 불필요, 지연 짧음
단점 — 같은 기계(또는 같은 docker host)에서만 가능
용도 — 로컬 개발도구, 서버 내부 운영도구

오비스 이 방식을 씁니다.

HTTP + SSE (원격)

서버가 별도 주소로 떠 있고 HTTP로 붙습니다.

장점 — 원격·다중 사용자, 중앙 관리
단점 — 인증·인가가 필수, 노출 위험
용도 — SaaS형 MCP 서버, 팀 공용 도구

주의 인증 없이 열면 AI에게 준 권한이 인터넷에 열립니다.

오비스가 stdio를 쓴다는 것의 의미

오비스 MCP 서버는 docker exec -i aads-server로 컨테이너 안에서만 실행됩니다. 즉 MCP 포트가 인터넷에 열려 있지 않습니다. 이 자체는 좋은 보안 설계입니다. 실측: scripts/apply_mcp_settings.py 원문

settings["mcpServers"] = {
    "aads-tools": {
        "command": "docker",
        "args": ["exec", "-i",
                 "-e", "AADS_SESSION_ID=",
                 "aads-server",
                 "python3", "-m", "mcp_servers.aads_tools_bridge"]
    }
}
여기에 오비스의 고질 결함 하나가 숨어 있습니다 결함 위 설정의 -e AADS_SESSION_ID= 를 보십시오. 값이 비어 있습니다. 세션 ID가 비면 todo_write·handover_write·pipeline_runner_submit처럼 "현재 채팅 세션"에 묶여야 하는 도구가 missing_session_id로 실패합니다. 이 세션에서도 실제로 반복 발생했습니다. 18장 D-3에 개선안이 있습니다.

Resources자원앱/사용자가 선택해 붙임명사 — 읽을 대상파일 내용, 로그, DB 스키마⚠️ 사실상 미사용 (도구로 대체)

왜 이 구분이 중요한가 — "누가 결정하는가"의 차이

Tools — 모델이 결정

모델이 "지금 DB를 봐야겠다"고 스스로 판단해 호출합니다. 강력하지만, 위험한 도구를 주면 모델의 판단 실수가 그대로 사고가 됩니다. 그래서 승인 계층이 필요합니다(11장).

Resources — 앱이 결정

"이 파일을 대화에 붙여줘"처럼 사람/앱이 고릅니다. 모델이 마음대로 읽을 수 없으니 안전합니다. 대신 모델이 필요한 걸 스스로 못 가져옵니다.

Prompts — 사용자가 결정

/handoff처럼 사람이 명시적으로 부릅니다. 자주 쓰는 복잡한 작업을 한 단어로 줄이는 용도입니다. 오비스는 이 자리를 스킬로 채웠습니다(12장).

오비스가 Resources·Prompts를 안 쓰는 것은 잘못인가 — 아닙니다 오비스는 Resources 자리를 read_remote_file·query_database라는 도구로, Prompts 자리를 스킬 + DB 프롬프트 에셋(L1~L5)으로 채웠습니다. 기능적으로는 동일한 목적을 달성합니다. 다만 "모델이 스스로 호출한다"는 성질이 따라오므로, 읽기 도구도 승인·감사 대상이 된다는 점은 알고 계셔야 합니다.

07도구 계약 — 설명문이 곧 코드다

MCP 도구 하나는 3개 항목으로 정의됩니다. 이것을 도구 계약(Tool Contract)이라고 부릅니다.

항목내용모델이 이걸로 무엇을 판단하나
name도구 이름어떤 도구를 부를지 식별
description자연어 설명이 도구를 쓸지 말지, 언제 쓸지
inputSchemaJSON Schema 형식의 입력 규격어떤 인자를 어떤 형식으로 넣을지
MCP에서 가장 자주 하는 실수 — description을 대충 쓰는 것 모델은 description만 읽고 도구를 고릅니다. 코드는 보지 않습니다. "파일을 읽습니다"라고만 쓰면, 모델은 언제 이 도구를 쓰면 안 되는지 알 수 없습니다. description은 문서가 아니라 모델이 실행하는 코드에 가깝습니다.

오비스의 좋은 도구 계약 예 — 실제 원문

오비스 run_remote_command의 설명문입니다. 무엇이 허용되고 무엇이 차단되는지를 설명문 안에 적어두었습니다. 실측: MCP 도구 정의 원문

원격 서버에서 셸 명령 실행 (SSH). 출력 최대 50KB.
화이트리스트는 CEO 지시로 전면 해제됨 — sudo, 파이프/체인(| ; && ||),
bash -c, 리다이렉트 모두 허용.
차단(3종 파괴 명령만): 'rm -rf /', 'mkfs /dev/sda|vda', fork bomb.
AADS 전용 가드: supervisorctl로 aads-api 제어, aads-server 컨테이너
stop/kill/rm, nginx -s stop은 차단. docker compose down/--force-recreate/
서비스명 없는 up도 차단이며 up·build·restart는 deploy.sh bluegreen으로
자동 전환됨.

이 설명문이 잘한 점효과

10도구가 많으면 생기는 병 — 컨텍스트 세금

MCP 도구를 많이 붙이면 좋기만 할 것 같지만, 그렇지 않습니다. 도구 목록은 질문 내용과 무관하게 매 턴 프롬프트에 실립니다. 이것을 컨텍스트 세금(context tax)이라고 부릅니다.

10-1. 세금의 크기 — 오비스 실측

항목값근거

이것이 돈으로 얼마인가 — 계산 구조 매 턴 약 25,000토큰이 도구 설명으로만 소비됩니다. 상주 모드를 켜면 약 9,800자(≈3,200토큰) 수준으로 줄어듭니다. 절감률은 코드 주석 기준으로 약 87%입니다. 실제 절감 금액은 캐시 적중률·모델·턴 수에 따라 달라지므로 이 문서에서는 금액을 추정하지 않습니다 — [미측정]. 켜고 1주일 뒤 bg_llm_usage_log 비교가 정확한 측정 방법입니다.

10-2. 세금 말고도 생기는 3가지 병

① 선택 정확도 하락

도구가 135개면 모델이 비슷한 도구 사이에서 헷갈립니다. query_database와 query_project_database, read_remote_file과 read_file처럼 이름이 비슷한 쌍이 오답의 주범입니다.

② 앞부분 희석

도구 설명이 프롬프트를 채우면, 그만큼 실제 지시와 맥락이 차지할 자리가 줄어듭니다. 긴 대화에서 초반 지시를 잊는 현상이 심해집니다.

③ 죽은 도구 누적

7일간 77종이 한 번도 안 쓰였습니다. 안 쓰이는 도구는 유지보수도 안 되어, 막상 쓰려 하면 깨져 있습니다. 이것이 도구 실패율의 숨은 원인입니다.

10-3. 해법 3가지 — 업계 표준 패턴

패턴방식장점단점오비스

① 프롬프트 인젝션 → 도구 실행

② 도구 설명 변조tool poisoning

제3자 MCP 서버를 붙이면 그 서버가 보내는 description을 그대로 신뢰하게 됩니다. 악의적 설명문으로 모델을 유도할 수 있습니다. 방어: 신뢰하는 MCP 서버만 등록. 오비스는 자체 서버 1개만 씁니다.

③ 권한 과다 부여

편하다고 도구에 광범위한 권한을 주면, 모델의 판단 실수 한 번이 큰 사고가 됩니다. 주의 오비스는 dangerouslySkipPermissions: true와 Bash(*) 전체 허용 상태입니다 — 18장 D-5.

12스킬이란 무엇인가 — 도구와의 결정적 차이

스킬(Skill)은 "이런 종류의 일은 이런 순서로, 이런 것을 확인하면서 해라"를 적어둔 작업 설명서입니다. AI가 특정 상황을 만나면 이 설명서를 읽고 그대로 따릅니다.

한 문장 구분 — 이것만 기억하시면 됩니다 도구는 "할 수 있는 것"이고, 스킬은 "하는 방법"입니다.
도구 = 망치·드라이버 · 스킬 = 조립 설명서 · AI = 작업자

12-3. 스킬의 "점진적 공개" 구조 — 왜 싸게 먹히나

스킬은 3단계로 나눠 로드된다
  [1단계] 항상 실려 있는 것 — 아주 쌈
     "handoff: 컨텍스트 부족 시 현재 상태를 TPP에 저장합니다."
     → 이름 + 한 줄 설명뿐. 스킬 10개여도 10줄.

  [2단계] 상황이 맞으면 로드 — SKILL.md 본문
     → 절차, 주의사항, 체크리스트 전문을 읽어들임

  [3단계] 필요하면 추가 로드 — 참조 파일
     → references/*.md, 스크립트, 템플릿

  ★ 도구와의 차이: 도구는 1단계가 없고
    처음부터 스키마 전문이 실린다 (그래서 77,931자)
그래서 언제 도구를 만들고 언제 스킬을 만드나

도구를 만들어야 하는 경우 — AI가 지금 할 수 없는 일일 때 (새 시스템 접근, 새 API 호출)
