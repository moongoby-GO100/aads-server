# 채팅 추가지시(인터럽트) 큐 — PRD·설계

- 작성: 2026-09-16 KST
- 대상: `aads-server` (`app/core/interrupt_queue.py`, `app/services/chat_service.py`, `app/routers/chat.py`), `aads-dashboard` (`src/app/chat/page.tsx`)
- 관련 문서: `docs/prd/20260916_CHAT_STREAM_RENDER_PRD.md` (같은 버블의 **렌더** 계약. 큐 계약은 이 문서가 정본이고 저기에 다시 적지 않는다)

## 0. 왜 쓰나

대표님 질문 둘에서 시작했다.

> "추가지시를 연속으로 계속 여러 번 넣으면 어떻게 되나?"
> "순차적으로 응답에 반영되면 해당 응답 상단으로 보내면 되는 건가?"

답을 코드로 확인해 보니, 답변보다 먼저 고쳐야 할 것이 세 개 나왔다.
**화면의 "취소"가 취소를 하지 않고**, **같은 문구를 두 번 보내면 화면엔 한 건인데 실제로는 두 건이 들어가고**,
**하루 전에 흘린 지시가 오늘 답변에 끼어들 수 있다.** 이 문서는 그 셋을 고치는 설계다.

## 1. 지금 무슨 일이 일어나나 (실측)

| 구간 | 실제 동작 | 근거 |
|---|---|---|
| 접수 | `POST /chat/sessions/{id}/interrupt` → `chat_messages(intent='queued_interrupt')` 저장 + 프로세스 큐 push | `routers/chat.py:3525-3552` |
| 소비(도구 있음) | 도구 루프 경계에서 큐 전체 pop → `"\n".join` 으로 **user 메시지 한 개**로 병합 | `model_selector.py:3133-3154` |
| 소비(도구 없음) | 스트림 종료 직전 최대 2패스 수거 → 답변 전체 재작성(`stream_reset`) | `chat_service.py:13381-13460` |
| 수거 상한 | 프로세스 큐 pop 은 **무제한**, DB 복구만 `limit=5` | `chat_service.py:2148-2172` |
| 결속 | 소비 시점에 지시 행에 `execution_id`/`generation_id` 를 찍어 응답과 묶음 | `chat_service.py:2068-2093` |

7일 실측 분포 — 한 실행이 삼킨 추가지시 건수: 1건 ×12, 2건 ×1, 3건 ×1, **10건 ×1**.
즉 "연속으로 여러 번"은 이미 실제로 일어나고 있고, 상한 `5` 를 넘겨 본 적이 있다.

## 2. 설계 결정

### 2.1 연속 입력은 **묶음 1회 반영**을 유지한다

N건을 1건씩 순차 재작성하면 응답을 N번 다시 쓰게 된다 — 비용·시간이 N배이고 `stream_reset` 이 N번 떠서
화면이 N번 갈아엎힌다. 지금처럼 다음 반영 지점에서 **그때까지 쌓인 전부를 한 번에** 넣는다.
대신 대표님이 "몇 건이 어디로 들어갔는지" 를 볼 수 있어야 한다(2.3).

### 2.2 취소는 서버까지 간다

취소는 화면에서 지우는 일이 아니라 **접수를 무르는 일**이다.
아직 소비되지 않은 행의 `intent` 를 `interrupt_cancelled` 로 바꾸고, 프로세스 큐에서도 뺀다.
이미 소비된 것(`interrupt_applied` 이후)은 되돌리지 않는다 — 이미 모델이 읽었다. 화면에 그렇게 말한다.

### 2.3 원문 버블은 움직이지 않는다 — 응답 **상단에 요약줄**을 단다

"해당 응답 상단으로 보내면 되나"에 대한 답은 **아니오, 참조만 올린다** 이다.

| 안 | 내용 | 판정 | 이유 |
|---|---|---|---|
| 1안 | 지시 원문 버블을 응답 위로 실제 이동 | 비권장 | `created_at` 순서와 DOM 순서가 어긋나 스크롤 앵커·중복제거가 깨진다. 소비 전에는 대상 응답이 확정조차 안 된다 |
| 2안 | 원문은 제자리, 응답 **상단**에 `↳ 반영된 추가지시 N건` 요약줄(펼치면 전문, 클릭 시 원문 점프) | **채택** | 순서 불변, N건 전부 노출, 이미 있는 `execution_id` 결속을 그대로 쓴다 |
| 3안 | 1건씩 순차 재작성 | 비권장 | 2.1 참조 |

기존에도 칩이 하나 있었으나 **응답 하단 메타 영역**에 있었고 첫 건으로만 점프했다(`page.tsx:3527-3545`).
읽는 사람이 답을 읽기 **전에** "이 답은 지시 3건을 먹었다"를 알아야 하므로 상단으로 옮기고 전체를 편다.

## 3. 상태 기계

```
(접수)  queued_interrupt
   ├─ 취소 ─────────────→ interrupt_cancelled   (수거 대상에서 영구 제외)
   ├─ 수거 ─────────────→ interrupt_applied     (execution_id/generation_id 스탬프)
   │                          └─ 응답 최종 저장 ─→ interrupt_completed
   └─ 스트림이 먼저 끝남 ─→ (다음 턴 수거) recovered_interrupt
```

- 수거 대상 조건: `intent IN ('', 'queued_interrupt')` **AND** 해당 행에 연결된 실행이 없음 **AND** `created_at > NOW() - INTERVAL '30 minutes'`
- 30분은 "스트림이 죽어서 다음 턴에 되살리는" 정상 복구(최근 7일 `recovered_interrupt` 44건)를 살리면서,
  하루 전 지시가 오늘 답변에 끼어드는 것은 막는 값이다. 그보다 오래된 행은 수거하지 않고 `interrupt_expired` 로 내린다.

## 4. API

| 메서드 | 경로 | 동작 |
|---|---|---|
| POST | `/chat/sessions/{id}/interrupt` | (기존) 접수. **30초 내 동일 문구는 새 행을 만들지 않고 기존 행 id 를 반환**(`duplicate=true`) |
| POST | `/chat/sessions/{id}/interrupt/cancel` | 미소비 추가지시 취소. body 없으면 그 세션의 미소비 전체, `message_ids[]` 지정 시 해당 건만 |

취소 응답: `{cancelled: n, already_applied: m, contents: [...]}`.
`already_applied > 0` 이면 화면은 "n건 취소, m건은 이미 반영되어 취소 불가"로 말한다.

## 5. 화면

1. 대기 칩 `📋 대기 N건` 의 `✕ 취소` → 취소 API 호출. 성공해야 로컬 큐를 비운다. 실패하면 칩을 남기고 경고를 띄운다.
2. `Ctrl+Z` → 마지막 1건만 취소 API 호출(입력창으로 되돌림).
3. 응답 버블 **상단**에 `↳ 반영된 추가지시 N건` 줄. 클릭하면 접힘/펼침, 각 항목 클릭 시 원문 버블로 점프.
4. 취소된 지시 버블은 회색 + `취소됨` 배지로 남긴다. 지우지 않는다 — 대표님이 보낸 기록이다.

## 6. 하지 않는 것

- 지시 원문 버블의 물리적 재정렬(2.3 1안).
- 소비된 지시의 취소(모델이 이미 읽었다).
- 프로세스 큐를 Redis 로 옮기는 일 — 이번 범위 밖. 5번 결함(일반 전송 경로 미저장)과 함께 다음 차수.
