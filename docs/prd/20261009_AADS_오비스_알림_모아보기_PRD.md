- 작성: CEO 통합지시 세션 8bf0405a, 2026-10-09 KST
- 지시 원문: "이것도 기획 설계 PRD 작성 저장하고 각 담당에게 구현 지시해" (알림 모아보기 페이지)
- 우선순위: P2 (전사 우선순위 GO100 → NTV2 → ACCT → 오비스 중 오비스)

- 저장소 파일: `docs/prd/20261009_AADS_오비스_알림_모아보기_PRD.md`. 백엔드 구현 러너가 이 본문 그대로 커밋한다.

## 1. 기획

### 1.1 문제
알림이 네 군데에 흩어져 있다. 그래서 놓친 승인이나 실패를 찾으려면 채팅을 거슬러 올라가야 한다.

| 출처 | 지금 보이는 곳 | 실측 (2026-10-09 10:2x KST) [DB 조회] |
|---|---|---|
| 시스템 경보 `alert_history` | `/decisions`, `/` 홈 | 전체 10,234건, 미확인 4,471건 (warning 2,724 · info 1,134 · CRITICAL 367 · WARNING 190 · critical 56). 심각도 대소문자 표기가 섞여 있다 |
| 막지 않고 알린 변경 `agent_permission_requests` tier=notify | `/approvals` | 최근 30일 `notified` 1,153건 |
| 승인 대기 `agent_permission_requests` tier=approve, decision=pending | `/approvals` | 최근 30일 119건 |
| 러너 이벤트 `pipeline_runner_events` | 채팅창 메시지로만 보이고, 모아 보는 화면이 없다 | 최근 7일 이벤트 중 job_terminal 642 · ai_review_result 510 · approval_requested 449 |
| 시안 검토 알림 `ohvis_notifications` | `/approvals` 일부 | 0건. 테이블은 있으나 아직 쓰이지 않는다 |

### 1.2 대상 사용자
- 1순위: CEO. 하루에 여러 번, 모바일 위주로 들어와 "지금 내가 처리할 것"을 본다.
- 2순위: 담당 세션 운영자(관리자). 자기 프로젝트의 실패와 경보를 본다.

### 1.3 목표와 비목표
- 목표: 하나의 화면에서 "처리 필요 → 경보 → 변경 알림 → 러너 진행"을 우선순위대로 보고, 확인 처리하고, 원래 화면으로 한 번에 이동한다.
- 비목표: 알림을 새로 만드는 쪽(생산자) 변경, 웹 푸시 구조 변경, 알림 삭제, 자동 확인 처리.

### 1.4 사용자 경로
- 첫 진입: 상단 종 아이콘(미확인 "처리 필요" 수 배지)을 누르면 `/inbox`의 "처리 필요" 탭이 기본으로 열린다.
- 반복 사용: 탭별 미확인 수를 확인한다. 항목을 누르면 원래 화면(승인 카드, 채팅 세션, 러너 상세)으로 간다. 돌아오면 그 항목은 확인 처리돼 있다.
- 실패 복구: API가 실패하면 탭별로 "다시 불러오기"를 띄운다. 한 출처가 실패해도 나머지 출처는 표시하고, 실패한 출처 이름을 배너로 보여 준다. 세션이 만료되면 로그인 후 같은 탭으로 돌아온다.

## 2. 설계

### 2.1 분류 (탭)
| 탭 | 들어가는 것 | 정렬 |
|---|---|---|
| 처리 필요 | 승인 대기(approve/pending), 러너 approval_requested 중 아직 결정되지 않은 것, 러너 job_terminal 중 status=error이고 후속 성공 작업이 없는 것, 경보 CRITICAL 미확인 | 오래된 것 먼저 (방치 시간 강조) |
| 경보 | `alert_history` 전체. 심각도는 소문자로 정규화한다 | 최신 먼저 |
| 변경 알림 | notify/notified, `ohvis_notifications` | 최신 먼저 |
| 러너 진행 | job 단위로 묶은 최신 상태 1행(시작·리뷰·승인·종결) | 최신 먼저 |

### 2.2 묶기와 소음 줄이기
- 러너: 이벤트를 행 단위로 보여 주지 않고 `job_id` 하나당 카드 1개만 둔다. 카드에는 최신 상태를 표시한다. model_attempt_*, cli_* 같은 내부 이벤트는 노출하지 않는다.
- 경보: 같은 (project, category, title)이 24시간 안에 반복되면 1행으로 묶고 "N회"로 표시한다. 묶음을 확인 처리하면 그 안의 전부가 확인된다.

### 2.3 API (aads-server, 신규 `app/api/inbox.py`, prefix `/api/v1/inbox`, 관리자 인증)
| 메서드 | 경로 | 설명 |
|---|---|---|
| GET | `/inbox/summary` | 탭별 {total, unread}. 종 아이콘 배지에 쓴다. 출처별 실패는 `degraded_sources[]`로 돌려준다 |
| GET | `/inbox?tab=&project=&severity=&unread_only=&cursor=&limit=` | 통합 목록. 항목 공통 스키마는 {source, source_id, tab, project, severity, title, summary, occurred_at_kst, count, read, link, actions[]} |
| POST | `/inbox/read` | body {items:[{source, source_id}]}. 확인 처리하며, 여러 번 호출해도 결과가 같다 |
| POST | `/inbox/read-all` | body {tab, before}. 그 탭에서 `before` 시각 이전 항목을 확인 처리한다 |

- `link`는 대시보드 경로다. 승인은 `/approvals?focus=<id>`, 러너는 `/chat?session=<session_id>&job=<job_id>`, 경보는 `/decisions?alert=<id>`.
- 확인 상태 저장:
  - `alert_history`는 기존 `acknowledged`/`acknowledged_at` 컬럼을 쓴다.
  - notify 알림은 기존 `/approvals/{id}/acknowledge`와 같은 의미(`decision='acknowledged'`)로 처리한다.
  - `ohvis_notifications`는 `read_at`을 쓴다.
  - 러너 카드는 신규 테이블 `ohvis_inbox_read_marks(tenant_id uuid, user_id text, source text, source_id text, read_at timestamptz, PRIMARY KEY(tenant_id,user_id,source,source_id))`에 기록한다. 마이그레이션은 `CREATE TABLE IF NOT EXISTS`로 만들고 DROP은 금지한다.
- "처리 필요"의 승인 대기는 확인 처리를 해도 사라지지 않는다. 승인·반려가 결정돼야 빠진다. 확인 처리는 배지 수에서만 뺀다.
- 성능: 목록 p95는 500ms 이하. 출처별 쿼리는 병렬로 돌리고, 출처당 타임아웃은 2초다. 하나가 실패해도 나머지 결과는 돌려준다.

### 2.4 화면 (aads-dashboard, 신규 `src/app/inbox/page.tsx`)
- 상단: 탭 4개와 미확인 수, 프로젝트 필터(GO100/NTV2/ACCT/AADS…), "미확인만" 토글.
- 항목 카드: 프로젝트 배지, 심각도 색, 제목, 요약 1줄, KST 시각(`MM-DD HH:mm`), 묶음 수, [열기]·[확인] 버튼. 내부 ID는 카드 본문에 노출하지 않는다.
- 탭 상단에 [모두 확인] 버튼을 두고, 누르면 확인창을 띄운다.
- 전역 내비게이션에 종 아이콘과 `/inbox/summary` 배지를 둔다. 60초마다 갱신하고, 화면이 보이지 않을 때는 갱신을 멈춘다.
- 모바일: 한 손 조작, 버튼 터치 영역 44px 이상, 긴 제목은 2줄에서 자른다.
- 빈 상태: "처리할 알림이 없습니다". 오류 상태는 출처별 배너와 [다시 불러오기]로 처리한다.
- 비관리자가 접근하면 401로 로그아웃시키지 않는다. 대신 권한 없음 안내를 보여 준다(10/07 비관리자 401 결함 수정과 같은 원칙).

## 3. 완료 기준
1. 백엔드 단위 테스트: 탭 분류, 러너 job 묶기, 경보 24시간 묶기, 확인 처리 멱등, 출처 하나 실패 시 degraded 응답, 비관리자 403. `bash scripts/run_unit_tests.sh` 결과 PASS.
2. 대시보드 테스트: 탭 전환, 확인 처리 후 배지 감소, 오류 배너, 비관리자 처리. typecheck도 통과해야 한다.
3. 화면 검증: 운영 배포 후 `/inbox` 로그인 화면을 캡처한다. 이 검증 계획은 `E2E_VERIFY: url=/inbox selectors=[data-testid=inbox-tab-action],[data-testid=inbox-badge]`이다. 배포 전에는 미리보기 화면 캡처로 대신한다.
4. 실측 대조: summary의 경보 미확인 수가 `SELECT count(*) FROM alert_history WHERE NOT acknowledged`와 같아야 한다.
