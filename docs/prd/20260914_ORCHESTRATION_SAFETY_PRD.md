## 1. 완료 판정 — 담당 신고 + 주도 확인

### 지금 무엇이 막히는가

`check_milestone_completion` 은 `goal_task_links` 의 상태로 판정한다.
#310 의 링크는 `milestone_id NULL`, `task_type chat_session` 이라
**마일스톤에 묶인 작업이 0건**이고 `no_linked_tasks` 가 돌아온다.

담당이 끝내도 완료되지 않고, 답은 했으니 재알림도 안 간다. **조용한 영구
정지다.**

### 흐름

    ① 담당이 도구로 신고      report_milestone_done(milestone_id, evidence)
    ② 상태 → 'review'         완료가 아니다. 확인 대기다.
    ③ 주도 세션에 확인 요청    근거와 함께 전달
    ④ 주도가 판정              confirm_milestone(id, ok=true|false, reason)
       ok  → completed, 다음 마일스톤 착수
       no  → in_progress 로 되돌리고 사유를 담당에게
    ⑤ 주도가 30분간 답 없으면  재알림, 3회 뒤 대표님께

### 근거를 요구한다

    evidence: {
      summary:  "무엇을 했고 결과가 무엇인가",
      numbers:  {"before": ..., "after": ...},   완료 기준이 숫자면 필수
      refs:     ["커밋 sha", "리포트 경로", "잡 id"]
    }

근거 없는 완료는 나중에 "그때 진짜 됐던 건가" 에 답이 없다. 그리고
근거를 적게 하면 담당이 스스로 한 번 더 본다.

**완료 기준에 숫자가 있으면 `numbers` 를 필수로 받는다.** 서술형 기준은
주도가 읽고 판정한다.

### 주도 자신의 마일스톤

주도가 맡은 마일스톤(예: 3번 손실원 진단)은 주도가 자기를 확인할 수 없다.
**대표님께 올라간다.** 자기 확인은 확인이 아니다.

## 2. 실패 상태

    milestones.status   pending | in_progress | review | completed
                        | failed | blocked

| 상태 | 뜻 | 누가 |
|---|---|---|
| `review` | 담당이 끝냈다고 신고, 확인 대기 | 담당 |
| `failed` | 제대로 했는데 **결과가 음성** | 주도 확인 |
| `blocked` | 진행 자체가 막힘 (답 없음·의존성) | 스케줄러 |

`failed` 와 `blocked` 를 나누는 이유 — 음성 결과는 **다음 마일스톤을 다시
짜야 한다는 신호**고, 막힘은 **사람이 봐야 한다는 신호**다. 대응이 다르다.

`failed` 가 되면 목표는 멈추지 않는다. 주도에게 "4번이 음성이다. 다음을
다시 짜라" 가 가고, 주도는 `propose_milestone_add` 로 대안을 올린다.

A/B 에서 **둘 다 failed** 면 그 seq 전체가 failed 다. 비교 마일스톤은
건너뛴다 — 고를 것이 없다.

## 3. 비용 상한

CEO 절대 규칙: "LLM 15회/task, 비용 효율 최우선".

    goals.cost_limit_usd      기본 GOAL_COST_LIMIT_USD (기본 20)
    goals.cost_spent_usd      누적. chat_messages.cost 를 목표 단위로 합산

실측 근거: 어시스턴트 메시지 1건에 1.06 USD. 담당이 한 마일스톤에서
도구를 127회 부른 기록이 있다. 담당 8명 × A/B 면 곱해진다.

### 임계

    80%   주도 채팅창에 경고
    100%  **새 지시를 멈추고 대표님께 텔레그램.** 진행 중인 것은 끝까지 둔다.

100% 에서 진행 중인 것을 끊지 않는 이유 — 끊으면 쓴 비용이 버려진다.
멈출 것은 **다음 지시**다.

대표님이 상한을 올리시면 즉시 재개한다.

## 4. 부하 연동

오늘 실측: contabo14 부하 **29** (코어 8), 주범은 백테스트 4개 동시 실행.
오케스트레이션은 그것을 설계로 한다(A/B).

    지시 직전에 대상 담당의 작업 서버 부하를 본다
    부하 / 코어 > GOAL_DISPATCH_MAX_LOAD_RATIO (기본 2.0) 이면 **미룬다**

미루는 것이지 취소가 아니다. 다음 주기에 다시 본다. `dispatch_count` 를
올리지 않는다 — 부하 때문에 미룬 것을 재시도로 세면 한도가 헛되이 닳는다.

부하는 `monitored_services` 와 같은 SSH 경로로 읽고 **60초 캐시**한다.
2~3분마다 도는 사이클이 매번 SSH 를 걸면 그 자체가 부하다.

## 5. 기한

    goals.deadline          목표 기한
    milestones.due_date     마일스톤 기한

    지나면   주도 채팅창 + 대표님 텔레그램. **멈추지는 않는다.**

멈추지 않는 이유 — 기한은 약속이지 차단이 아니다. 자동으로 멈추면
대표님이 모르시는 사이에 목표가 죽는다. 알리고 대표님이 정하신다.

#310 은 **거래일 기준**이다. 주말·공휴일은 세지 않는다.

## 6. 롤백

실매매 반영(6번) 뒤 5거래일 관찰이 끝인 설계였다. 나빠지면 되돌릴 절차가
없다.

    반영 시  rollback_ref 를 기록한다 (되돌릴 커밋·설정 스냅숏)
    관찰 중  일일 누적수익이 기준선보다 나쁜 날이 **연속 2일**이면
             → 주도 채팅창 + 대표님 텔레그램 + 되돌리기 제안
    되돌림   대표님 승인 후 실행. 자동 롤백은 하지 않는다.

**자동 롤백을 하지 않는 이유** — 시장이 나쁜 날과 전략이 나쁜 것을 기계가
구분하지 못한다. 알리고 대표님이 정하신다.

## 7. 담당별 수동 제어 — 대표님 손잡이

대표님 지시: "각 참여세션의 상태를 반영하고 각각에 내가 수동으로 멈추면
계속하기 재시작 버튼등을 반영".

### 세 가지 (+ 하나)

| 버튼 | 하는 일 |
|---|---|
| **멈춤** | 이 담당에게 **새 지시를 보내지 않는다.** 진행 중 응답은 끝까지 둔다 |
| **계속하기** | 멈춤을 푼다. 밀린 지시가 있으면 다음 주기에 나간다 |
| **재시작** | 발송 기록(`dispatch_count`)을 지우고 처음부터 다시 지시한다 |
| 지금 중단 | 진행 중인 응답을 강제 종료 (`/chat/sessions/{id}/stop`) |

**멈춤이 응답을 끊지 않는 이유** — 끊으면 지금까지 한 것이 사라진다.
2026-09-14 내가 배포로 두 번 끊어서 운영인프라담당의 조사가 두 번 날아갔다.
정말 지금 끊어야 하면 `지금 중단` 을 따로 누른다.

전체 정지와 다르다. 전체 정지는 목표 전체를 세우고, 이건 **한 담당만**
세운다. 파동엔진이 엉뚱한 길로 가는데 데이터엔진은 잘 하고 있으면
파동엔진만 세워야 한다.

### 저장

    owner_pause(goal_id, session_id, paused_at, paused_by, reason)

목표 단위다. 같은 담당이 두 목표에 참여하면 한쪽만 멈출 수 있어야 한다.

`goal_dispatch` 가 발송 직전에 본다. 멈춘 담당은 건너뛰고 `dispatch_count`
를 올리지 않는다.

    │                                                        │
    │ [ ⏸ 멈춤 ]  [ ↻ 재시작 ]  [ ■ 지금 중단 ]  [ 💬 의견 ]│

멈춘 카드는 회색으로 내리고 **멈춘 이유를 같이 적는다.** 이유 없이 멈춘
카드는 사흘 뒤에 왜 멈췄는지 아무도 모른다.

`재시작` 은 확인을 한 번 받는다 — 지금까지 한 것을 버리고 처음부터다.

## 8. 합격 기준

1. 담당이 근거와 함께 신고하면 마일스톤이 `review` 가 되고 주도에게 간다.
2. 주도가 확인하면 `completed`, 반려하면 `in_progress` 로 돌아간다.
3. 주도가 30분간 확인하지 않으면 재알림, 3회 뒤 대표님께.
4. 주도 자신의 마일스톤은 대표님께 올라간다.
5. 음성 결과는 `failed` 가 되고 주도에게 "다시 짜라" 가 간다.
6. 목표 비용이 상한의 80%에서 경고, 100%에서 새 지시가 멈춘다.
7. 대상 서버 부하가 임계를 넘으면 지시가 미뤄지고 재시도 한도가 닳지 않는다.
8. 기한이 지나면 알리되 멈추지 않는다.
9. 실매매 반영 뒤 연속 2일 악화면 되돌리기가 제안된다. 자동 실행은 없다.
10. 담당별 멈춤·계속하기·재시작이 동작하고, 멈춤이 진행 중 응답을 끊지 않는다.
11. 멈춘 카드에 이유가 표시된다.

## 9. 하지 않는 것

- **자동 롤백** — 시장이 나쁜 날과 전략이 나쁜 것을 기계가 구분 못 한다
- **기한 초과 자동 중단** — 대표님이 모르시는 사이 목표가 죽는다
- **비용 초과 시 진행 중 작업 강제 종료** — 쓴 비용이 버려진다
- **담당 자기 확인** — 자기 확인은 확인이 아니다
