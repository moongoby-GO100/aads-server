## 1. 한 줄 요약

채팅 아티팩트 패널 '문서파일' 탭의 「정본 문서 N건」 목록에 **상태 3단계 배지(초안 / 검토 대기 / 승인됨, 반려 별도)** 와 **역할별 처리 버튼**을 붙인다. 검토 대기 문서는 목록에서 본문을 열어 보고 그 자리에서 승인하거나 사유를 적어 반려한다. 승인 규칙(검토 상태만 승인, 사람 로그인만 승인)은 서버가 이미 강제하므로 화면은 그 규칙을 **그대로 비추기만** 한다.

> 숫자는 시간이 지나면 바뀐다. 화면은 숫자를 하드코딩하지 않고 서버 응답으로 센다.

### 2-1. 지금 화면의 문제 3가지
1. **검토 대기를 못 알아본다.** 검토로 올라간 문서도 「초안」으로 보인다(`approved` 불리언만 받음). CEO 가 "무엇을 승인해야 하는지" 를 이 탭에서 알 수 없다.
2. **처리하려면 화면을 떠나야 한다.** 승인은 채팅 하단 카드(해당 문서를 이번 턴에 조회했을 때만 뜸) 또는 `/docs` 정본 화면에서만 된다.
3. **개정 단위로 나열돼 헷갈린다.** 같은 문서의 옛 개정도 줄로 남고, 옛 개정은 영원히 「초안」이다. 옛 개정은 승인할 수 없는데(`latest_revision_id` 가 달라 409) 승인 가능해 보인다.

## 3. 대상 사용자와 경로

| 사용자 | 정의(서버 판정 기준) | 이 탭에서 하는 일 |
|---|---|---|
| **CEO 승인자** | 사람 로그인 + 활성 멤버십 + (테넌트 admin/owner 또는 내부 관리자, 또는 프로젝트 `approve` 권한) — `can_approve` 가 true | 검토 대기 문서 열람 → 승인 / 반려 |
| **PM 검토자** | 채팅 세션의 역할이 PM·정본관리자 계열이거나 CEO 통합지시 세션 | 초안을 '검토로 올리기'. 올린 뒤에는 대기 일수 확인만 |
| **일반 세션 사용자** | 위 둘이 아닌 조회 권한자 | 상태 배지·대기 건수·사유 열람만. 버튼 없음 |

> 서버 규칙을 그대로 쓴다: 승인 가능 여부는 화면이 추측하지 않고 `GET …/documents/{key}` 응답의 `approval_card.can_approve` 를 따른다. 프로젝트 `approve` 권한을 받은 비관리자도 승인할 수 있다는 점이 지시서의 "CEO·관리자만" 과 다르다 — 권한 부여는 CEO 가 한 것이므로 서버 규칙을 유지한다(결정 필요 D-1).

### 3-1. 첫 진입
1. 문서파일 탭을 열면 「정본 문서 N건」 머리줄에 **`검토 대기 K건`** 칩이 생긴다(K=0 이면 칩 없음).
2. 승인자는 칩을 눌러 `검토 대기만 보기` 로 좁힌다(다시 누르면 전체).
3. 줄을 누르면 **링크로 새 화면을 열지 않고 그 자리에서 펼쳐진다**(상세는 §5). 기존 「문서 열기」 링크는 펼친 안에 남겨 둔다(`onOpenDocument`).
4. 검토 대기가 하나도 없고 승인자라면 「승인할 문서가 없습니다」 한 줄(빈 상태).

### 3-2. 반복 사용
- 60초마다 기존 폴링이 목록을 다시 받는다. 펼쳐 둔 줄과 입력 중인 반려 사유는 폴링으로 지워지지 않는다(키: `project/document_key/revision_id`).
- 승인·반려 직후 해당 줄은 새 상태 배지로 바뀌고, 필터가 `검토 대기만` 이면 줄이 사라지며 K 가 줄어든다. 처리한 줄의 결과(승인 시각)는 토스트 한 줄로 4초 남는다.

### 3-3. 실패 복구
§7 에 따른다. 원칙은 하나다: **어떤 실패든 화면은 서버 상태를 다시 읽고(`GET …/documents/{key}`) 그 결과로 줄을 다시 그린다**(서버의 `approval_card` 계약: POST 후·네트워크 실패 후에도 GET 새로고침).

## 4. 상태 배지와 버튼 매트릭스

### 4-1. 배지 (표시 상태는 서버가 계산해 내려준다)
| 배지 | 조건 | 색(기존 DocBadge 톤) |
|---|---|---|
| 초안 | 해당 개정의 마지막 상태 이벤트 없음(`created`/`revised` 만) | `draft` |
| 검토 대기 | 마지막 상태 이벤트 `review`, 최신 개정, 승인 포인터가 아님. 옆에 `N일 대기` | `review`(액센트 테두리) |
| 승인됨 | 해당 개정이 `approved_revision_id` | `approved`(액센트 채움) |
| 반려 | 마지막 상태 이벤트 `rejected`(신규, §6) | 경고색 테두리 |
| 이전 판본 | 최신 개정이 아님(`revision_id ≠ latest_revision_id`) | 흐린 테두리 — **줄 맨 뒤로 접어서** 표시 |
| 보관 | 마지막 상태 이벤트 `archived` | `archived`(취소선) — 정본 화면 소관, 이 탭은 배지만 |

- 한 문서의 **최신 개정 한 줄이 기본 줄**이다. 이전 판본은 `이전 판본 N개` 로 접어 두고 펼치면 흐리게 보인다(승인·검토 버튼 없음). 목록 건수 「정본 문서 N건」은 **문서 수**(개정 수 아님)로 센다.

### 4-2. 역할 × 상태 버튼
| 상태 \ 사용자 | CEO 승인자 | PM 검토자 | 일반 세션 사용자 |
|---|---|---|---|
| 초안 | (버튼 없음) 「PM 이 검토로 올려야 승인할 수 있습니다」 | **[검토로 올리기]** (사유 10자 이상) | (없음) |
| 검토 대기 | **[승인]** **[반려…]** (본문 열람 후 활성) | (없음) 「승인 대기 N일」 | (없음) |
| 승인됨 | (없음) 승인자·시각 표시 | (없음) | (없음) |
| 반려 | (없음) 사유 표시 | (없음) 사유 표시 + 「새 개정을 등록하면 초안으로 돌아갑니다」 | (없음) 사유 표시 |
| 이전 판본 / 보관 | (없음) | (없음) | (없음) |

- 한 사람이 승인자이면서 PM 세션이면 위 두 열의 버튼을 둘 다 가진다(상태가 다르므로 겹치지 않는다).
- **승인됨에는 버튼이 없다.** 보관·되돌리기는 `/docs` 정본 화면 소관이다(범위 밖).
- 권한이 없는 버튼은 숨기지 않고 **비활성 + 이유 한 줄**로 둘지가 선택지다. 권장: 숨김. 이유: 일반 세션 사용자에게 눌러도 안 되는 버튼은 노이즈이고, 이유 문구는 상태 줄에 이미 있다(위 표의 「…」 문구).

## 5. 목록 상단과 줄 펼침

### 5-1. 목록 상단
```
정본 문서 12건   [검토 대기 6]  [전체]
```
- `검토 대기 K` 칩 = 서버 응답에서 `status=review` 이고 최신 개정인 문서 수. 칩은 필터 토글이다(`aria-pressed`).
- 필터는 탭 안에서만 유효하고 저장하지 않는다(새로 열면 전체).

### 5-2. 일괄 승인 — 권장: **하지 않는다(개별 승인만)**
| 안 | 장점 | 단점 |
|---|---|---|
| **A. 개별 승인만 (권장)** | 승인은 `revision_id + expected_generation` 한 쌍에 묶인 판정이다. 문서마다 본문을 열람한 뒤 승인한다는 현행 카드 계약과 일치. 실수 승인의 되돌림은 보관+새 개정뿐이라 비싸다 | 6건이면 6번 누른다 |
| B. 열람 완료분 일괄 승인 | 클릭 수 감소 | 열람 여부는 클라이언트만 안다(서버 검증 불가). 한 번의 오조작이 여러 정본에 퍼진다. 부분 실패(409 섞임) 보고 UI 가 필요 |
| C. 전체 일괄 | 가장 빠름 | 열람 없는 승인을 구조적으로 허용 — 현행 규칙 위반 |

근거: 검토 대기 6건, 일 처리량이 수 건 수준이라 클릭 절약의 이득이 작다. 일괄은 이후 검토 대기가 하루 10건을 넘고 문서 등급(§9) 구분이 생긴 뒤 'D1 은 일괄 가능' 같은 조건부로 재검토한다(후속, 이번 범위 밖).

### 5-3. 줄 펼침 — 승인 전 확인 내용
펼친 영역 순서(위→아래):
1. **무엇을**: 제목 · `project · document_key` · **개정 번호 + 버전**(예: 개정 3 · v1.2.0) · 종류(제품 요구사항 등)
2. **누가·왜**: 작성 출처(세션이면 세션 요약 라벨, 러너면 `runner-xxxxxxxx`) · 작성 사유(`change_summary`) · 검토로 올린 사람·시각(KST)·대기 일수
3. **무엇이 바뀌었나**: 직전 개정이 있으면 `개정 2 → 3`, 글자 수 증감(본문 diff 는 범위 밖, 정본 화면 링크 제공)
4. **본문 열람**: `내용 보기 · 승인할 본문 확인` 접이식(`<details>`). 서버 `…/content?revision=N` 로 가져온다(최대 262,144바이트, 스크롤 영역 최대 높이 320px).
5. **버튼 줄**: [승인] [반려…] [정본 화면에서 열기]

### 5-4. 열람 없이 승인 — **금지(클라이언트 강제)**로 결정
- [승인] 은 본문 접이식을 연 뒤에만 활성화한다(현행 `CanonicalApprovalCards` 와 동일 계약). 활성 조건이 불일치하면 한글 안내 「본문을 먼저 열어 확인하세요」.
- 한계를 숨기지 않는다: 서버는 "열람했는가" 를 알 수 없다. 서버가 보장하는 것은 **판본 고정**뿐이다(`revision_id` 는 불변, `expected_generation` 불일치 시 409). 열람 여부 서버 기록이 필요하면 `viewed_at` 이벤트를 추가해야 하는데 이번엔 하지 않는다(결정 D-2).

| **S2** 신규 | `POST /api/v1/projects/{p}/documents/{key}/reject` — 본문 `{revision_id, expected_generation, reason}`(`reason` 10자 이상, `credential` 패턴 거부). 승인과 같은 인가(`_require_human_approver` + `_authorize(approve)`)·같은 잠금. 마지막 상태가 `review` 가 아니면 409 `revision_not_in_review`. `project_document_heads.generation + 1`, 이벤트 `rejected` 기록 | 반려 기능 |
| **S2-DB** 마이그레이션 | `project_document_events_action_check` 에 `'rejected'` 추가 + `note text NULL` 컬럼 추가. 이벤트는 불변 트리거가 UPDATE/DELETE 를 막으므로 **컬럼 추가만** 가능하고 기존 행은 건드리지 않는다 | 사유 저장 |
| **S2-영향** 변경 | 상태 조회 SQL 의 `action IN ('review','approved','archived')` 5곳(`canonical_documents.py`)·`canonical_document_tools.py:36`·`canonical_review_digest.py:31` 에 `'rejected'` 추가. 안 하면 반려 후에도 마지막 상태가 `review` 로 읽혀 **반려한 문서가 계속 승인 대기로 보인다.** `review_revision_in_tx` 는 마지막이 `rejected` 이면 409 `revision_already_decided` | 상태 계산 일관성 |
| **S3** 신규 | `POST /api/v1/chat/sessions/{session_id}/canonical-documents/{project}/{key}/review` — 본문 `{reason}`(10자 이상). 세션 역할을 `_review_role_denial`(PM·CEO 통합지시 세션만)로 서버에서 판정한 뒤 `review_revision_in_tx` 호출. 이벤트 `note` 에 사유 | PM 제한을 **HTTP 경로에도** 건다. 기존 `POST …/review` 는 `/docs` 화면이 쓰므로 바꾸지 않는다(결정 D-3) |
| **S4** 선택 | `POST …/review` 에 선택 필드 `reason` → 이벤트 `note` 저장. 현재 채팅 도구의 사유는 `logger.info` 에만 남고 DB 에 없다 | 감사 기록 완결 |

> 지시서 검증 항목 "PRD 의 API 경로가 서버에 실제 존재" — §6-1 의 7개는 모두 존재(근거는 보고 RESULT 의 grep). S1~S4 는 **미존재(신규/변경 제안)** 로 표기했다.

### 6-3. 감사 기록
- 승인·검토·(신규)반려 모두 `project_document_events(tenant_id, project_key, head_id, revision_id, action, actor_id, created_at[, note])` 에 남는다. `actor_id` 는 사람 사용자 id 또는 `chat:<세션8자>`(채팅 도구).
- 화면 표시: `승인: <표시 이름> · 2026-10-28 15:40 KST`. 이름 해석 불가면 원문 id. 서버가 `status_actor_label` 로 내려준다(S1).
- 이벤트 테이블은 불변이므로 승인 취소는 없다(보관 + 새 개정).

## 7. 실패 복구 — 실제 서버 응답 기준

> 지시서의 "422 검토 상태 아님" 은 **서버 실제와 다르다.** 검토 상태가 아닌 판본의 승인은 **409** `revision_not_in_review` 다(`canonical_documents.py:667`). 422 는 요청 본문 검증 실패(`invalid_project_key`, `expected_generation`<1, UUID 형식)에서만 나오며, 화면이 서버 값을 그대로 보내므로 정상 경로에서는 나오지 않는다. 아래는 실제 코드 기준이다.

| 상황 | 서버 응답 | 화면 문구 | 다음 행동 |
|---|---|---|---|
| 로그인 만료 | 401 | 로그인이 만료되었습니다. 다시 로그인한 뒤 새로고침하세요. | [로그인] 링크(`/login?next=%2Fchat`), 입력한 반려 사유는 유지 |
| **403 권한 없음** | 403 `project_access_denied` | 이 프로젝트의 문서 승인 권한이 없습니다. | 버튼 숨김 + 줄 상태 갱신. 「권한 요청은 관리자에게」 |
| 403 사람 로그인 아님 | 403 `human_login_required` | 사람 계정으로 로그인해야 승인할 수 있습니다. | [로그인] |
| 403 멤버십 비활성 | 403 `active_membership_required` | 이 조직의 멤버십이 활성 상태가 아닙니다. | 관리자 문의 |
| **409 상태 변경됨** (다른 사람이 먼저 처리·새 개정 등록) | 409 `generation_conflict` | 다른 변경이 먼저 반영되었습니다. 최신 내용을 확인했습니다. | 줄을 최신으로 다시 그리고 **펼침·열람 상태 초기화**(재열람 후 재승인) |
| 이미 같은 개정이 승인됨 | **200** `idempotent: true` | 이미 승인된 문서입니다. (승인자·시각) | 성공 취급, 줄을 승인됨으로 |
| **검토 상태 아님** (초안으로 보이는데 눌렀거나 반려됨) | 409 `revision_not_in_review` | 검토 상태의 문서만 승인할 수 있습니다. 문서 상태가 바뀌었습니다. | 줄 새로고침. 초안이면 「PM 이 검토로 올려야 합니다」 |
| 이미 결정된 판본을 검토로 | 409 `revision_already_decided` | 이미 승인 또는 보관된 판본이라 검토로 되돌릴 수 없습니다. | 줄 새로고침 |
| 문서 없음 | 404 `document_not_found` | 문서가 없거나 제거되었습니다. | 줄 제거 후 목록 새로고침 |
| **네트워크 실패/시간 초과** | 응답 없음 | 처리 결과를 확인하지 못했습니다. 상태를 다시 확인합니다. | **자동으로 GET 재조회** → 승인됐으면 성공 처리, 아니면 [다시 시도]. 이중 클릭 방지: 요청 중 두 버튼 모두 비활성 |
| 서버 오류 | 5xx | 서버 오류입니다. 잠시 후 다시 시도하세요. | 재조회 후 [다시 시도] |

공통 규칙: 요청 중에는 두 버튼을 비활성화하고 「처리 중…」을 표시한다. 오류 문구는 줄 안 버튼 바로 위에 `role="alert"` 로 둔다. 응답 본문 URL 은 `[URL]` 로 가린다(`CanonicalDocuments.problemOf` 와 동일).

## 8. 모바일 (390px)
- 모든 버튼·칩·접이식 요약: **높이 44px 이상, 가로 44px 이상**(`min-height:44px`).
- 버튼 줄은 `flex-wrap`. 폭이 모자라면 [승인] 이 첫 줄 전체, [반려…] 와 [정본 화면에서 열기] 가 다음 줄에 쌓인다. 가로 스크롤 없음.
- 한 손 조작: [승인] 은 줄 펼침 영역의 **맨 아래**에 두어 엄지 영역에 놓는다. 위험 동작인 [반려…] 는 승인과 **8px 이상 떨어뜨린다**. 반려 사유 입력은 하단 시트(화면 아래에서 올라옴)로 열고 [취소]/[반려 확정] 이 시트 하단에 고정된다.
- 제목은 두 줄까지 말줄임 없이 줄바꿈(`word-break: break-all` 유지).

## 9. 같은 날 PRD·설계(문서 3등급 + 교차 회사 검토)와의 연결 지점

충돌하지 않게 이 기획은 **등급·교차 검토를 구현하지 않고 자리만 둔다.**

| 연결 | 이 기획의 처리 |
|---|---|
| 응답 필드 `doc_tier`, `review_state`(`not_required/pending/blocked/passed/rejected`), `author_model` (설계 §6-2) | S1 응답에 **나중에 추가해도 깨지지 않는다**(필드 추가만). 화면은 모르는 필드를 무시. 줄에 `등급` 배지 자리를 비워 둔다 |
| D1 은 승인 대상에서 제외(FR-13) | 서버가 D1 을 `review_state=not_required` 로 내리면 이 탭은 [검토로 올리기]/[승인] 을 **숨긴다**. 그 전까지는 모든 종류가 같은 흐름 |
| D2·D3 는 교차 검토 통과 후에만 '검토로 올리기'(FR-12) | S3 는 `review_revision_in_tx` 를 쓰므로 설계 §6-3 이 그 함수 안에 게이트를 넣으면 **패널 경로도 같은 게이트를 지난다.** 거절 시 409 `cross_review_required` + 한글 사유 → 이 탭은 §7 의 일반 409 문구 대신 서버가 준 한글 사유를 그대로 보여 준다 |
| 설계 `project_document_reviews`(검토 기록 별도 테이블) | 반려(S2)와 **용어가 겹친다**: 모델 교차 검토의 '반려'(`review_state=rejected`)와 CEO 의 '반려'(이벤트 `rejected`)는 다른 개념. 화면 배지는 CEO 반려=**반려**, 교차 검토 실패=**검토 반려(모델)** 로 구분 표기 제안(결정 D-4) |
| 이벤트 `action` CHECK 변경 | 설계의 DB 변경은 개정 테이블·검토 기록 테이블이라 events CHECK 와 겹치지 않는다. 마이그레이션 파일명 날짜로 순서 충돌만 피하면 된다 |

## 10. 완료 판정 기준 (후속 구현 러너용)

| 번호 | 기준 | 측정 |
|---|---|---|
| AC-1 | 문서파일 탭에서 검토 대기 문서가 「검토 대기」 배지로 보이고 칩 K 가 서버 집계와 같다 | 단위 시험 + 같은 정의 SQL 대조 |
| AC-2 | 승인자가 열람 없이는 [승인] 이 비활성이고, 열람 후 승인하면 이벤트 `approved` 1건이 `actor_id`·`created_at` 과 함께 생긴다 | 브라우저 시험 + `SELECT … FROM project_document_events WHERE action='approved' ORDER BY id DESC LIMIT 1` |
| AC-3 | 초안/승인됨/이전 판본/반려 줄에는 [승인] 이 없다. 일반 세션 사용자 화면에 버튼이 하나도 없다 | 역할×상태 매트릭스 시험(§4-2 전 칸) |
| AC-4 | 반려는 사유 10자 미만이면 서버 422·화면 비활성, 성공 시 이벤트 `rejected` + `note`, 이후 해당 개정은 검토 큐·검토 대기 칩에서 빠진다 | 서버 단위 시험 + 큐 SQL |
| AC-5 | §7 의 403/409(`generation_conflict`, `revision_not_in_review`)/네트워크 실패 각각 문구와 재조회가 나온다 | 모킹 E2E 5장면 |
| AC-6 | PM 이 아닌 세션이 S3 를 호출하면 403 이고 이벤트가 생기지 않는다 | API 시험 |
| AC-7 | 390x844 에서 가로 스크롤 0, 버튼 높이 ≥ 44px | Playwright 측정 |
| AC-8 | 기존 `approved` 필드와 기존 `POST …/approve`·`…/review` 응답이 변하지 않는다(하위호환) | 기존 시험 `tests/unit/test_canonical_documents.py`, `test_session_documents.py`, `test_canonical_document_review_tool.py` 통과 |

## 11. 후속 구현 러너 분할 (의존 관계)

```
R1 서버(S1+S2+S2-DB+S2-영향)  ──┐
R2 서버(S3, S4)  (R1 이후, 같은 파일군) ─┤

```

| 러너 | 저장소 | 범위 | 의존 |
|---|---|---|---|
| R1 | aads-server | S1 응답 필드, 반려 API + 마이그레이션 + 상태 SQL 7곳, 시험 | 없음. **먼저 배포**(필드 추가만이라 구 대시보드 영향 없음) |
| R2 | aads-server | S3 세션 검토 엔드포인트, S4 사유 저장 | R1 (마이그레이션의 `note` 컬럼) |
| R3 | aads-dashboard | `ChatArtifactPanel.tsx` 정본 목록 컴포넌트 분리(`CanonicalSessionDocs`), `api.ts` 호출 3개(reject·세션 검토·기존 approve), `canonicalDocumentWorkflow.ts` 에 `reject` 전이 추가 | R1(필수), R2(검토 버튼만) |
| R4 | 둘 다 | 실계정 없이 모킹 E2E + 실제 이벤트 확인(승인 1건은 CEO 가 직접) | R3 |

- R1 은 마이그레이션이 있어 `ALLOW_AUTH_COMMIT` 대상은 아니지만 DB 변경이므로 CEO 승인 후 점검 창구에서 적용한다.
- R3 은 `ChatArtifactPanel.tsx` 가 3,200줄이 넘는 단일 파일이므로 **새 파일로 분리**하고 패널에는 호출 한 줄만 남긴다(병행 러너 충돌 방지).
- 승인 동작 자체의 실사용 검증은 사람 로그인이 필요하므로 러너가 승인을 눌러 볼 수 없다(서비스 키는 403). R4 는 모킹으로 검증하고, 실승인은 CEO 의 첫 사용이 곧 검증이다.
