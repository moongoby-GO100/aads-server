# 마일스톤 수립 위임 — PRD·설계

- 작성 2026-09-14 KST · 배경은 [기획서](../plans/20260914_MILESTONE_PROPOSAL_기획서.md)
- 범위: 도구 1개 + 승인 경로 + 화면. 새 승인 테이블을 만들지 않는다.

## 1. 흐름

    ① 초안 전달     주도 세션에 마일스톤 초안 + 근거를 넣는다
    ② 검토·보완     주도가 실측으로 검증하고 고친다
    ③ 세트 제안     propose_milestones(...) — 6건을 하나로 올린다
    ④ 게이트        direction_guard 가 막고 승인 요청 1건을 만든다
    ⑤ 대표님 결정   /approvals 에서 한 번에 승인 또는 거절(사유 필수)
    ⑥ 반영          승인 → 한 트랜잭션으로 등록 → 스케줄러가 1번 지시
                    거절 → 사유가 주도에게 전달, 주도가 고쳐 다시 올린다

## 2. 도구 규격

    propose_milestones(
      goal_id     : str    목표 id
      milestones  : list   [{title, owner_role_key, completion_criteria,
                             sequence, description?}]
      rationale   : str    왜 이 구성인가 (대표님이 읽으실 글)
    ) -> {"proposed": 6, "approval_request_id": "...", "status": "pending"}

**도구는 등록하지 않는다. 제안만 한다.** 등록은 승인 뒤 서버가 한다.
주도가 직접 `db_safe_write` 로 넣으려 하면 `direction_guard` 가 막는다 —
우회로가 없어야 게이트가 의미를 갖는다.

검증은 제안 시점에 한다. 잘못된 세트를 대표님 화면까지 올리지 않는다.

| 검사 | 거절 사유 |
|---|---|
| 1~12건 | 개수 범위 밖 |
| `sequence` 중복·빠짐 | 순서가 1..N 연속이 아님 |
| `owner_role_key` 가 그 목표에 묶인 담당인가 | 묶이지 않은 담당 |
| `completion_criteria` 비어 있음 | 완료 기준 없는 마일스톤 |
| 이미 마일스톤이 있는 목표 | 세트 제안은 최초 1회 |

**완료 기준을 필수로 둔 이유** — 없으면 스케줄러가 완료를 판정할 수 없어
그 마일스톤에서 영원히 멈춘다. 오늘 고친 "조용한 멈춤" 과 같은 부류다.

## 2-2. 진행 중 추가 — `propose_milestone_add`

세트 제안은 최초 1회다. **그런데 진행 중에 새 마일스톤이 필요해지는
경우가 더 많다.** 3번(손실원 진단)의 결과가 예상 밖이면 거기서 갈린다 —
예를 들어 손실원이 데이터 정합성으로 나오면 "정합성 복구" 가 4번 앞에
들어가야 한다.

    propose_milestone_add(
      goal_id     : str
      after       : int | "end"   어느 마일스톤 뒤에 넣을 것인가
      milestones  : list          1~5건
      rationale   : str           **무엇이 바뀌어서 지금 필요한가**
    ) -> {"approval_request_id": "...", "status": "pending"}

`rationale` 이 세트 제안 때보다 더 중요하다. 세트는 "이렇게 하겠습니다"
지만 추가는 **"계획이 틀렸으니 바꾸겠습니다"** 다. 무엇을 새로 알았는지
적지 않으면 대표님이 판단하실 근거가 없다.

### 순서 다시 매기기

중간에 끼우면 뒤가 밀린다. 한 트랜잭션 안에서 다시 매긴다.

    기존   1 측정복구(완료)  2 기준선(완료)  3 진단(진행중)  4 개선안  5 검증  6 반영
    추가   3번 뒤에 "정합성 복구"
    결과   1 ✓  2 ✓  3 진행중  4 정합성복구(신규)  5 개선안  6 검증  7 반영

### 막는 것

| 검사 | 거절 사유 |
|---|---|
| 완료된 마일스톤 앞에 끼우기 | 이미 끝난 것 앞에 넣을 수 없다 |
| 진행 중 마일스톤 앞에 끼우기 | 담당이 지금 일하는 중이다. 뒤에 넣거나 되돌리기를 써라 |
| 1~5건 범위 밖 | 한 번에 다섯 건을 넘으면 그건 재설계다 — 세트로 다시 논의 |
| `rationale` 30자 미만 | 무엇이 바뀌었는지 적지 않은 추가 |
| 완료 기준 없음 | 세트 제안과 같다 |

**진행 중 마일스톤 앞에 못 끼우는 이유** — 담당이 이미 그 일을 하고 있는데
앞에 다른 것을 넣으면 순서가 뒤집힌 채로 계속 일한다. 정말 앞이 먼저여야
하면 `rewind` 로 되돌린 뒤 넣는다. 그건 별개 결정이다.

### 화면 — 무엇이 바뀌는지 보여야 한다

추가는 **기존 계획과의 차이**가 핵심이다. 새 것만 보여 주면 대표님이
어디에 들어가는지 모르신다.

    ┌─ 마일스톤 추가 ───────────────── 전략카드담당 · 방금 ─┐
    │ #310 전략카드 일일 누적수익 3% 확보 — 1건 추가        │
    │                                                       │
    │ 무엇이 바뀌었나                                       │
    │ 3번 진단에서 손실의 62%가 진입 시그널이 아니라        │
    │ 분봉 결손 구간의 잘못된 신호에서 나왔다. 개선안        │
    │ 도출 전에 정합성부터 복구해야 한다.                    │
    │                                                       │
    │  1 측정 복구        ✓ 완료                            │
    │  2 기준선 확정      ✓ 완료                            │
    │  3 손실원 진단      ● 진행 중                         │
    │ ▸4 정합성 복구      + 신규   데이터엔진담당            │
    │  5 개선안 도출      · 4번이었음                       │
    │  6 교차 검증        · 5번이었음                       │
    │  7 실매매 반영      · 6번이었음                       │
    │                                                       │
    │          [ 승인 — 추가하고 순서 조정 ]  [ 거절 ]      │
    └───────────────────────────────────────────────────────┘

`+ 신규` 는 초록, 밀려난 것은 회색으로 `· N번이었음` 을 붙인다.
**밀려난 것을 표시하지 않으면 순서가 조용히 바뀐다.**

## 2-3. A/B — 두 갈래를 나란히 돌리고 숫자로 고른다

대표님 지적: "마일스톤의 A/B는 없나?"

**없었다.** 마일스톤은 `sequence_order` 로 일렬이고, 전진 로직이
`ORDER BY sequence_order LIMIT 1` 로 **한 번에 하나만** 착수한다.

### 왜 필요한가

#310 의 3번(손실원 진단)이 끝나면 개선안이 하나로 좁혀지지 않는다.
예를 들어 손실이 진입 시그널과 체결 양쪽에 걸쳐 있으면:

    A  파동엔진 — 진입을 15초 당긴다
    B  실매매엔진 — 분할 체결로 슬리피지를 줄인다

하나만 고르면 다른 가능성을 **버리는 것**이다. 그런데 어느 쪽이 나은지는
해 보기 전에는 모른다. 둘 다 백테스트로 돌려 **같은 기준선에 대고 재는**
것이 맞다.

### 구조

같은 `sequence_order` 에 `variant` 가 다른 마일스톤을 둔다.

    seq 4  variant A   진입 시점 당기기      파동엔진담당
    seq 4  variant B   분할 체결             실매매엔진담당
    seq 5  variant —   A/B 비교·채택         백테스트엔진담당

전진 로직이 바뀐다. **같은 seq 의 변형을 전부 함께 착수한다.**

    기존   ORDER BY sequence_order LIMIT 1
    변경   가장 낮은 pending seq 를 찾고, 그 seq 의 **모든** 행을 착수

그 seq 는 **모든 변형이 끝나야** 완료다. 하나만 끝나고 넘어가면 비교할
대상이 없다.

### 비교 기준을 먼저 못 박는다

이것이 A/B 의 핵심이다. 제안 시점에 `ab_criterion` 을 필수로 받는다.

    ab_criterion: "동일 20거래일 기준선 대비 실현 누적수익 개선폭.
                   동률이면 최대 낙폭이 작은 쪽."

**나중에 정하면 진 쪽이 지표를 문제 삼는다.** 승률로 보면 A 가 낫고
손익비로 보면 B 가 나은 상황이 실제로 흔하다. 기준을 먼저 적어 두지
않으면 그때부터 기준 논쟁이 시작되고, 그건 데이터가 아니라 말싸움이다.

기준이 숫자로 판정 가능하면 **비교 마일스톤에서 자동으로 채택**된다.
판정이 애매하거나 기준이 서술형이면 대표님 결정으로 올라간다.

### 막는 것

| 검사 | 거절 사유 |
|---|---|
| 변형이 2~3개 밖 | 4갈래는 비교가 아니라 난사다 |
| `ab_criterion` 없음 | 기준 없는 A/B 는 나중에 말싸움이 된다 |
| 변형들의 담당이 같음 | 한 담당이 자기 안 둘을 비교하면 비교가 아니다 |
| 비교 마일스톤이 없음 | 돌리기만 하고 고르지 않으면 둘 다 남는다 |
| 실매매 반영 단계에서 A/B | 실매매는 갈래를 나누지 않는다. 검증 뒤 하나만 간다 |

**마지막이 중요하다.** 백테스트는 두 갈래를 돌려도 되지만 실제 주문은
안 된다. 돈이 두 갈래로 나간다.

### 화면

    ┌─ 마일스톤 추가 (A/B) ─────────── 전략카드담당 · 방금 ─┐
    │ #310 — 4번을 A/B 두 갈래로                            │
    │                                                       │
    │ 무엇이 바뀌었나                                       │

    │ 나왔다. 하나로 좁힐 근거가 없어 둘 다 검증한다.       │
    │                                                       │
    │ 채택 기준 (먼저 못 박음)                              │
    │ 동일 20거래일 기준선 대비 실현 누적수익 개선폭.       │
    │ 동률이면 최대 낙폭이 작은 쪽.                         │
    │                                                       │
    │  3 손실원 진단     ● 진행 중                          │
    │ ▸4 A 진입 당기기   + 신규   파동엔진담당              │
    │ ▸4 B 분할 체결     + 신규   실매매엔진담당            │
    │ ▸5 A/B 비교·채택   + 신규   백테스트엔진담당          │
    │  6 교차 검증       · 5번이었음                        │
    │  7 실매매 반영     · 6번이었음                        │
    │                                                       │
    │       [ 승인 — A/B 등록 ]   [ 거절 ]                  │
    └───────────────────────────────────────────────────────┘

진행 중에는 두 갈래가 나란히 보인다.

    4  A 진입 당기기    ● 작업 중    파동엔진담당    도구 22회
    4  B 분할 체결      ● 작업 중    실매매엔진담당  도구 9회
    5  A/B 비교·채택    ○ 대기       — 두 갈래가 끝나야 시작

채택 뒤에는 진 쪽이 **버려지지 않고 남는다.**

    4  A 진입 당기기    ✓ 채택      +1.8%p
    4  B 분할 체결      ✗ 미채택    +0.4%p

미채택을 지우지 않는 이유 — 나중에 "그때 B 는 왜 안 했지" 를 물으면
숫자가 남아 있어야 답이 된다. 지우면 같은 안을 반년 뒤에 다시 시도한다.

### 스키마

    milestones.variant        text    NULL | 'A' | 'B' | 'C'
    milestones.ab_criterion   text    변형이 있는 seq 의 채택 기준
    milestones.ab_result      jsonb   {"chosen": "A", "metrics": {...}}

## 2-4. 진행 중 의견·수정 요청

대표님 지적: "마일스톤 진행중에 의견제시 또는 수정 요청을 할수 있나?"

**부분적으로 된다.** 채팅창에 입력하시면 담당이 응답 중이어도 중간
메시지로 들어간다(`push_interrupt`). 그런데 네 가지가 빠져 있다.

| 빠진 것 | 결과 |
|---|---|
| 마일스톤에 기록되지 않는다 | 나중에 "왜 방향이 바뀌었지" 를 설명 못 한다 |
| 의견인지 수정 요청인지 구분이 없다 | 담당이 참고로 흘려도 알 수 없다 |
| 반영했는지 확인할 길이 없다 | 조용히 무시돼도 모른다 |
| 완료 기준이 바뀐 것이 안 남는다 | 나중에 "왜 통과됐지" 에 답 못 한다 |

### 두 종류를 나눈다

    의견 (note)        참고하라. 담당이 판단해서 반영하거나 반영하지 않는다.
                       **반영 여부와 이유를 답해야 한다.**
    수정 요청 (change) 반드시 반영하라. 완료 기준이나 범위가 바뀐다.
                       **바뀐 기준이 마일스톤에 기록된다.**

구분이 필요한 이유 — 의견을 수정 요청처럼 다루면 담당이 판단을 멈추고
받아쓰기만 한다. 반대로 수정 요청을 의견처럼 다루면 대표님이 바꾸라고
하신 것이 조용히 무시된다.

### 흐름

    ① 대표님이 현황판 카드 또는 채팅창에서 남긴다
    ② 담당이 응답 중이면 `push_interrupt`, 아니면 새 메시지로 전달
    ③ `milestone_notes` 에 기록
    ④ 담당이 **반영 결과를 답한다** — 안 하면 지시와 같은 재알림(30분/3회)
    ⑤ 수정 요청이면 `completion_criteria` 를 갱신하고 **이전 값을 남긴다**

④가 핵심이다. 의견을 남겨 놓고 담당이 아무 말 없으면 반영된 것인지
못 본 것인지 알 수 없다. 지시와 같은 추적을 건다.

### 완료 기준이 바뀌면 이전 값을 남긴다

    completion_criteria  "기준선 대비 누적수익 +1%p 이상"
                      ↓ 대표님 수정 요청
    completion_criteria  "기준선 대비 누적수익 +1%p 이상, 최대 낙폭 악화 없음"
    criteria_history     [{"at": "...", "was": "...", "by": "ceo",
                           "why": "낙폭이 늘면 3% 를 지켜도 못 쓴다"}]

이력이 없으면 나중에 그 마일스톤이 왜 통과됐는지 설명할 수 없다.
기준을 느슨하게 바꿔서 통과시킨 것과 근거가 생겨 바꾼 것이 구분되지 않는다.

### 화면

현황판 카드에서 바로 남긴다. 창을 열지 않으셔도 된다.

    │ ☑ 완료 기준도 함께 고친다                             │
    │ ┌───────────────────────────────────────────────────┐ │
    │ │ 기준선 대비 누적수익 +1%p 이상, 최대 낙폭 악화 없음│ │
    │ └───────────────────────────────────────────────────┘ │
    │                          [ 취소 ]  [ 전달 ]           │
    └───────────────────────────────────────────────────────┘

남긴 뒤 카드에 표시가 붙는다. 담당이 답하면 사라진다.

    ┌ 파동엔진 관리자                              작업 중 ┐
    │ 4A 진입 시점 당기기            2분 전 · 도구 22회    │
    │ ✏ 수정 요청 1건 — 응답 대기 12분                     │
    └───────────────────────────────────────────────────────┘

### 스키마

    milestone_notes(
      id, milestone_id, kind,          -- 'note' | 'change'
      body, criteria_before, criteria_after,
      created_by, created_at,
      delivered_at, dispatch_count,
      answered_at, answer_excerpt
    )
    milestones.criteria_history  jsonb

### 막지 않는 것

**대표님 의견에는 승인이 필요 없다.** 대표님이 승인자다. 방향 게이트는
주도가 바꾸려 할 때 걸리는 것이지 대표님께 걸리는 것이 아니다.

## 3. 저장

새 테이블을 만들지 않는다. `agent_permission_requests` 를 쓴다.

    action_type      'propose_milestones'
    action_summary   "#310 마일스톤 6건 제안 — 측정 복구부터"
    approval_scope   {"goal_id": "...", "rationale": "...",
                      "milestones": [ ... 6건 전문 ... ]}
    risk_level       'high'
    decision         'pending' → 'approved' | 'rejected'
    reason           거절 사유 (거절 시 필수)

`approval_scope` 가 jsonb 라 세트를 통째로 담는다. 승인 시 여기서 읽어
등록하므로, **제안 이후 주도가 내용을 바꿔치기할 수 없다.**

## 4. 승인 처리

    POST /approvals/{id}/decide?decision=approved
      → approval_scope 에서 읽어 한 트랜잭션으로 milestones INSERT
      → 1번 마일스톤을 in_progress 로 (나머지는 pending)
      → 주도 세션에 "승인됨 — 1번 착수" 통보

    POST /approvals/{id}/decide?decision=rejected&reason=...
      → 등록하지 않는다
      → 주도 세션에 거절 사유 전달 → 주도가 고쳐 다시 올린다

**원자성이 중요하다.** 셋만 들어가고 나머지가 실패하면 목표가 반쯤 세워진
채로 남고, 스케줄러는 그것을 정상으로 보고 3번부터 지시를 넣는다.

## 5. 화면 설계

### 승인 대기 — `/approvals`

세트는 접어서 보여 주고, 펼치면 전문이 나온다. 마일스톤은 **순서와
연결이 전부**라서 하나씩 보면 구조가 안 보인다.

    ┌─ 마일스톤 제안 ─────────────────────── 전략카드담당 · 3분 전 ─┐
    │ #310 전략카드 일일 누적수익 3% 확보 — 마일스톤 6건            │
    │                                                                │
    │ 왜 이 구성인가                                                 │
    │ 측정이 막혀 있어 기준선을 잡을 수 없다. 전략 개선보다          │
    │ 수집·스냅샷 복구가 먼저다. 3번에서 손실원이 갈려야 4번의       │
    │ 담당이 정해진다 — 미리 정하면 엉뚱한 곳을 판다.                │
    │                                                                │
    │ 1  측정 복구          운영인프라담당    ▸ 완료기준 보기        │
    │ 2  기준선 확정        백테스트엔진담당  ▸                      │
    │ 3  손실원 진단        전략카드담당      ▸                      │
    │ 4  개선안 도출        (3번 결과가 정함) ▸                      │
    │ 5  교차 검증          백테스트엔진담당  ▸                      │
    │ 6  실매매 반영        실매매엔진담당    ▸ 대표님 승인 필요     │
    │                                                                │
    │            [ 승인 — 6건 등록 ]   [ 거절 ]                      │
    └────────────────────────────────────────────────────────────────┘

**거절을 누르면 사유 입력이 먼저 뜬다.** 사유 없는 거절은 받지 않는다 —
주도가 왜 거절됐는지 모르면 같은 것을 다시 올린다.

    ┌─ 거절 사유 ───────────────────────────┐
    │ 주도에게 그대로 전달됩니다.            │
    │ ┌────────────────────────────────────┐ │
    │ │ 6번을 4·5번 검증 전에 두지 마라.   │ │
    │ └────────────────────────────────────┘ │
    │              [ 취소 ]  [ 거절하고 전달 ]│
    └────────────────────────────────────────┘

### 승인 뒤 `/goals`

마일스톤이 생기고 1번이 파랗게 진행 중이 된다. 담당 현황판의
운영인프라담당이 `지시 없음` → `응답 대기` → `작업 중` 으로 바뀐다.

### 빈 상태

제안이 없으면 `/approvals` 의 이 영역은 그리지 않는다. 빈 상자는
"고장인가" 를 먼저 의심하게 만든다.

## 6. 합격 기준

1. 주도가 `propose_milestones` 로 6건을 올리면 승인 요청이 **1건** 생긴다.
2. 주도가 `db_safe_write` 로 직접 넣으려 하면 막힌다.
3. 완료 기준이 빈 마일스톤이 섞이면 제안 자체가 거절된다.
4. 승인하면 6건이 한 번에 등록되고 1번이 `in_progress` 가 된다.
5. 거절하면 등록되지 않고 사유가 주도 세션에 남는다.
6. 등록 직후 다음 스케줄러 주기에 운영인프라담당에게 지시가 나간다.
7. 진행 중 추가 제안이 **완료·진행 중 마일스톤 앞**을 가리키면 거절된다.
8. 추가가 승인되면 뒤 마일스톤의 순서가 한 트랜잭션으로 다시 매겨지고,
   승인 화면에 **밀려난 것**이 표시돼 있었다.
9. 같은 `sequence_order` 의 A/B 변형이 **동시에** 착수되고, 둘 다 끝나야
   다음으로 넘어간다.
10. `ab_criterion` 없는 A/B 제안은 거절된다.
11. 채택 뒤 미채택 변형이 숫자와 함께 남는다 — 지워지지 않는다.
12. 진행 중 마일스톤에 의견을 남기면 담당에게 전달되고, **답이 없으면
    30분 뒤 재알림**이 간다.
13. 수정 요청으로 완료 기준이 바뀌면 **이전 값과 이유가 이력에 남는다.**

## 7. 하지 않는 것

- 자동 승인 — 주도가 스스로 승인하면 게이트가 무의미하다
- 승인 없이 초안 등록 — 초안은 제안이지 결정이 아니다
- **마일스톤 삭제와 순서 변경** — 추가와 달리 이미 한 일을 지우거나
  담당의 작업 순서를 뒤집는다. 되돌리기(`rewind`)로 충분한 경우가 대부분이고,
  정말 지워야 하면 대표님이 화면에서 직접 하시는 편이 안전하다.
  주도에게 줄 권한이 아니다.
