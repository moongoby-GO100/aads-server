# 채팅 스트리밍 렌더 — PRD·설계

- 작성 2026-09-16 KST
- 범위: **응답이 화면에 그려지는 방식**(대시보드 클라이언트). 서버 지연은
  [채팅 반응성 PRD](20260914_CHAT_RESPONSIVENESS_PRD.md) 가 다룬다.
- 대상 파일: `aads-dashboard/src/app/chat/page.tsx`,

  `src/features/chat/rendering/contentPerformancePolicy.ts`

## 0. 왜 쓰나

대표님 보고(2026-09-16 01:0x KST):

> 응답글이 계속 자연스럽게 이어서 기록되고 수정되는 게 아니라,
> 있던 게 접혔다 다시 한 번에 생기는 과정이다 보니
> 응답 중 확인하기가 불편하다.

첫 토큰이 언제 오느냐(반응성)는 고쳤는데, **온 뒤에 어떻게 보이느냐**는
아무도 안 봤다. 서버는 토큰을 제때 보내고 있었다.

## 1. 무엇이 그렇게 만들었나 (실측)

| # | 증상 | 코드 | 값 |
|---|---|---|---|
| 1 | 덩어리로 튀어나옴 | `page.tsx` `_flushDrain()` | 최소 간격 450ms, 12,000자 넘으면 900ms |
| 2 | 있던 글이 접힘 | `page.tsx` `LIVE_STREAM_RENDER_LIMIT` | 8,000자 초과 시 앞부분을 잘라 버림 |
| 3 | 완료 순간 재구성 | `responseOverview` 가 `!isVisiblyStreaming` 조건 | 완료 시 개요 패널이 본문 위에 삽입 |
| 4 | 갱신이 더 늦어짐 | `startTransition(() => setStreamBuf(...))` | 전환 업데이트라 React 가 뒤로 미룸 |

1번과 4번이 "한 번에 생김", 2번이 "있던 게 접힘" 이다. 3번은 마지막
한 번의 들썩임이다.

빈도 — 24시간 어시스턴트 메시지 540건 중 8,000자 초과 **23건**, 그중
12,000자 초과 **22건**. 평균 2,474자. 짧은 답은 멀쩡하고 **대표님이
실제로 읽는 긴 보고만 정확히 이 경로를 탄다.**

### 원인이 아닌 것 (확인함)

- **버블 remount 아니다.** `finalizeAssistantMessage` 가 `render_id` 를
  보존한다(AADS-BUBBLE-FLASH-P0). React key 는 안 바뀐다.
- **마크다운 절단 아니다.** `planMarkdownRender` 는 분류만 하고 자르지 않는다.

## 2. 왜 그런 값이 들어가 있었나

셋 다 앞선 사고의 대응책이다. 되돌리기 전에 그것부터 적는다.

- 8,000자 창 — `AADS-BUBBLE-FLASH-P1`. 긴 본문을 매번 다시 파싱하면
  느려지니 꼬리만 그렸다.
- 450/900ms — 같은 이유. 재파싱 횟수를 줄이려고 간격을 벌렸다.
- 둘 다 `AADS-SCROLL-JUMP` 와 얽혀 있다. 높이가 급변하면 화면이 위로 튄다.

**그래서 값만 되돌리면 옛 문제가 돌아온다.** 구조를 바꿔야 한다.

## 3. 설계 — 앞은 얼리고 꼬리만 그린다

재파싱 비용이 본문 길이에 비례하는 것이 근본 원인이다. 그것을 끊는다.

```
[ 확정 블록 1 ][ 확정 블록 2 ][ 확정 블록 3 ][  살아 있는 꼬리  ]
   한 번 파싱     한 번 파싱     한 번 파싱     매 갱신마다 파싱
   (memo)        (memo)        (memo)        (~1KB)
```

- 빈 줄(블록 경계)에서 끊고, **코드펜스 안에서는 끊지 않는다.**
- 한 번 정해진 경계는 **다시 움직이지 않는다** — 그래서 앞 블록의
  `text` prop 이 불변이고 `React.memo` 가 재파싱을 막는다.
- 꼬리만 매 갱신 다시 파싱한다. 본문이 20,000자든 비용은 꼬리 길이다.

이러면 앞부분을 잘라낼 이유가 사라진다 → **8,000자 창을 없앤다.**
높이는 단조 증가만 하므로 스크롤도 위로 튀지 않는다.

### 경계 규칙

| 상황 | 처리 |
|---|---|
| 빈 줄, 펜스 밖, 앞 블록이 최소 길이 이상 | 여기서 끊는다 |
| 코드펜스 열린 상태 | 안 끊는다 (펜스가 닫힐 때까지 꼬리에 둔다) |
| 표 | 표 안에는 빈 줄이 없으므로 통째로 꼬리에 있다가 함께 확정 |
| 순서 목록이 경계에 걸림 | CommonMark `start` 속성이 번호를 유지한다 |
| 전체가 최소 길이 미만 | 전부 꼬리 (분할 안 함) |

최소 블록 길이는 1,200자. 너무 잘게 쪼개면 DOM 노드만 늘고,
너무 크면 재파싱 비용이 안 준다.

**완료된 메시지는 분할하지 않는다.** 최종 렌더는 지금처럼 본문 하나를
통으로 파싱한다 — 화면에 남는 최종 결과는 기존과 100% 동일하다.

## 4. 갱신 주기

| 값 | 전 | 후 |
|---|---|---|
| 드레인 타이머 | 250ms | **100ms** |
| 최소 플러시 간격 | 450ms / 900ms(12k 초과) | **90ms** (길이 무관) |
| 업데이트 우선순위 | `startTransition` | 즉시 반영 |

초당 2.2회(긴 답은 1.1회) → **초당 10회**. 사람 눈에 "이어서 써지는" 것으로
보이는 하한이 대략 초당 8회다.

`startTransition` 을 뺀 이유 — 전환 업데이트는 React 가 다른 일에 밀리면
뒤로 미룬다. 긴 대화일수록 실제 간격이 450ms 보다 더 벌어졌다. 스트리밍
텍스트는 미룰 대상이 아니다.

## 5. 하지 않는 것

- **토큰 단위 즉시 렌더** — 초당 수십 회 파싱은 저사양 기기에서 렉이 된다.
  100ms 는 "부드럽게 보이는 하한" 과 "파싱 비용" 의 접점이다.
- **최종 렌더 경로 변경** — 완료된 메시지는 건드리지 않는다. 회귀 범위를
  스트리밍 중으로 한정한다.
- **가상 스크롤 도입** — 별개 과제다. 이번 범위가 아니다.

## 6. 합격 기준

1. 12,000자 이상 응답에서 **첫 문단이 끝까지 화면에 남는다** (앞부분 소실 0).
2. 갱신이 초당 8회 이상 — 문단이 아니라 줄 단위로 늘어난다.
3. 완료 순간 스크롤 위치가 바뀌지 않는다.
4. 스트리밍 중 프레임 드랍이 체감되지 않는다(긴 대화 + 20,000자 응답 기준).
5. 회귀 없음 — `BUBBLE-FLASH-P0/P1`, `SCROLL-JUMP-P1/P2` 재발 없음.
6. `typecheck` / `lint:chat` / `test:chat:security` 전부 통과.

## 7. 되돌리기

커밋 1건 `git revert`. 스키마·API·서버 변경이 없어 되돌림에 부작용이 없다.
되돌리면 8,000자 창과 450/900ms 가 그대로 돌아온다.

## 8. 남은 것 (이번 범위 밖)

- 완료 시 개요 패널 삽입으로 인한 마지막 들썩임(표 1의 3번) — 개요를
  스트리밍 중에도 디바운스 계산해 자리를 미리 잡는 방식. P1.
- 4초마다 `message.content` 를 동기화하는 경로와 100ms 플러시의 역할
  분리 — 지금은 두 곳이 같은 버블에 쓴다. P2.
- 모바일 기기별 간격 분기 — PC 와 증상이 갈리는지 확인 후 판단.

## 9. 추가 — 도구 구간에는 본문이 아예 없다 (2026-09-16 10:2x 대표님 지적)

> 너도 지금 버블에 도구 사용 화면만 나오는데, 도구 사용 시 응답 내용이
> 없어서 이렇게 보여지는 건가?
> `AI가 응답을 생성 중입니다....(도구 16회 호출 중)`

맞다. 1~5절은 **텍스트가 오는데 어떻게 그려지느냐**의 문제였고, 이것은
**텍스트 자체가 없는 구간**의 문제다. 원인이 다르므로 따로 적는다.

### 9.1 무엇이 일어나나

모델이 도구를 부르는 동안에는 `delta`(텍스트) 이벤트가 나오지 않는다.
`tool_use` / `tool_result` 만 흐른다. 그래서 `state["content"]` 가 빈 문자열로
남고, 서버는 그 자리를 한 줄로 채운다.

```python
# app/services/chat_service.py:5185 (수정 전)
display_content = (content + streaming_note) if content \
    else "⏳ _AI가 응답을 생성 중입니다... (도구 {tool_count}회 호출 중)_"
```

실측 — 이 세션 직전 턴(2026-09-16 10:18 KST)은 **도구 67회에 본문 496자**다.
48시간 동안 도구 10회 이상을 쓴 어시스턴트 메시지 340건의 평균 도구 수는
**71.1회**다. 긴 조사 턴은 대부분 이 구간을 길게 지난다. [DB 조회]

정리하면 **버그가 아니라 구조**다. 다만 그 구간의 화면이 불친절했다.

### 9.2 왜 불편했나 (진짜 결함은 여기)

라이브 진행 패널(`page.tsx` 도구 로그)은 `maxHeight: 180px` + `overflowY: auto`
인데 **아래로 따라 내려가지 않았다.** 기록은 뒤에 붙는데 스크롤은 맨 위에
멈춰 있으니, 16건이 쌓이면 화면에는 처음 5~6건만 보이고 **지금 하는 일은
접힌 아래에 있다.** 본문이 없는 구간에서 유일한 정보가 낡은 상태로 멈춰 있던 셈이다.

### 9.3 조치

| # | 대상 | 내용 |
|---|---|---|
| 1 | `page.tsx` 도구 패널 | 새 기록이 붙을 때마다 **최신 줄로 자동 스크롤** |
| 2 | `page.tsx` 도구 패널 | 본문이 없는 동안 높이 180px → **340px** (그 구간엔 이게 전부다) |
| 3 | `chat_service.py:5185` | 본문이 빌 때 플레이스홀더에 **`최근: <도구명>`** 추가 |

3번은 새로고침·세션 이동 후 DB 본문을 읽는 경로에 적용된다 — 라이브 SSE가
끊긴 뒤 남는 문구가 숫자 하나에서 "무엇을 하는 중인지"로 바뀐다.

### 9.4 하지 않는 것

- **도구 구간에 가짜 본문을 만들어 넣지 않는다.** 서버가 "무엇을 하는 중"이라고
  문장을 지어 본문에 쓰면, 그 문장이 최종 응답에 섞이거나 모델이 실제로 한
  말과 어긋난다. 진행 상황은 본문이 아니라 진행 패널의 몫이다.
- **모델에게 도구마다 한 줄씩 쓰게 강제하지 않는다.** 토큰 비용이 늘고, 실제로
  지켜지지 않는다(프롬프트로만 거는 규칙은 지켜지지 않는다 — R-ERRBOOK 3항).

### 9.5 합격 기준

1. 도구 10회 이상 도는 턴에서, 패널이 **항상 최신 도구 줄을 보여준다**.
2. 본문이 없는 동안 패널이 340px까지 쓰이고, 본문이 붙으면 180px로 돌아간다.
3. 새로고침 후 진행 중 버블 문구에 `최근: <도구명>` 이 보인다.
4. `typecheck` 통과, 기존 스트리밍 테스트 회귀 없음.
