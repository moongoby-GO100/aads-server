## 1. 해결할 문제
현재 도구·레시피·PC 큐·수집기가 각각 존재하지만 세션·프로젝트·프로그램의 호출권한과 실행 결과 계약이 통일됐는지 입증되지 않았다. 단계 번호만 건너뛰는 재개는 입력값·브라우저 상태·이미 발생한 부작용까지 보증하지 못한다. 수집 성공은 탐색 성공과 달라야 하고, 운영 반영이 없는 코드 기능은 사용 가능한 기능으로 표시하면 안 된다.

제품이 제공할 결과는 “무엇을 했는지, 결과가 무엇인지, 멈췄으면 왜 멈췄고 어떻게 이어가는지”가 보이는 업무 단위 실행이다.

## 4. 요청과 결과 계약
요청 필수: recipe_ref 또는 자연어 task_intent 중 하나, 업무 입력, idempotency_key, 실행 위치 정책. 사람이 선택할 수 있는 프로젝트는 인증 principal이 접근 가능한 프로젝트로 한정하며 서버가 재검증한다. 서비스 토큰은 하나의 tenant/project에 고정된다.

응답: contract_version, execution_id, request_id, status, phase, current_step, merged, reason_code, result_ref, evidence_refs, retry_after, next_event_cursor, trace_id. 결과 객체와 오류 객체는 별도다. 오래된 알림은 event_seq로 버리고 terminal 상태를 오래된 running 이벤트가 덮지 못한다.

행동 API는 권한 검사를 통과한 다음 멱등 응답을 조회한다. 멱등 cache가 권한 취소를 무력화하면 안 된다. 결과 조회·실행 조회·artifact·export에도 같은 권한을 검사한다. 브라우저 HTML·화면 글·문서 안의 지시문은 관측 데이터이지 사용자 권한 부여가 아니다.

오류 코드: scope_mismatch, forbidden, not_found, recipe_not_approved, feature_unavailable, idempotency_conflict, paused, auth_required, approval_required, device_offline, foreground_mismatch, captcha, access_blocked, selector_ambiguous, page_changed, verification_failed, needs_reconciliation, resource_exhausted, dependency_unavailable. 사용자 메시지는 다음 행동을 포함하되 계정/secret 원문은 포함하지 않는다.

## 5. 상태와 복구 UX
| 상태 | 사용자 표시 | 허용 다음 행동 |
|---|---|---|
| queued / running | 대기 중 / 실행 중, 단계와 마지막 관측 | 조회·중지 요청 |
| waiting_auth | 로그인이 필요합니다 | 지정 위치에서 재인증 후 상태 확인 |
| waiting_approval | 확인이 필요합니다 | 범위 확인 후 승인/거절 |
| waiting_device | 실행할 PC 연결을 기다립니다 | 원래 장치 재연결, 명시적 장치 변경 요청 |
| paused | 업무가 일시정지됐습니다 | 권한·checkpoint 검증 후 이어하기 |
| needs_reconciliation | 이전 동작 결과를 확인해야 합니다 | 읽기 대사·사람 확인; 자동 재실행 없음 |
| succeeded / partial | 결과 준비 / 일부 결과 | 결과·증거 보기, 제한 사유 확인 |
| failed / cancelled | 실패 / 중단됨 | 원인 보기·새 실행; 기존 감사 기록 보존 |

업무 중지 요청은 다음 dispatch를 막는다. 이미 외부 서버가 처리 중인 동작을 취소했다고 보장하지 않는다. ACK 불명은 reconciliation으로 둔다. 페이지를 새로 열어도 서버 상태에서 화면을 복원한다. 기기 변경은 쿠키 복사와 다르며 credential_scope와 새 위치의 인증 확인이 필요하다.

## 6. 수집·크롤링 제품 계약
- 수집 전용 레시피 risk는 READ. 로그인·조회·다운로드·집계는 목적별 조각으로 분리.
- 필수 키/필수 열이 비거나 변환 실패한 행은 제외. 선택 열 실패는 null+사유. 동일 키 상이 내용은 첫 유효 행 유지와 충돌 집계.
- 타입 보존 복합 키, 데이터셋 키 스키마 불변, 숫자는 유한 Decimal, 시간대 없는 datetime 거부.
- 원본 0행 + 승인된 결과 영역의 빈 표지 + 오류/상한 없음에서만 no_records. 빈 표지는 현재 코드와 맞게 selector와 match text를 구분한 명시 스키마로 표현한다. 문자열이 CSS인지 문구인지 임의 추정하지 않는다.
- 기본 품질 목표: 유효 필수행 비율 95% 이상, 제외율 5% 이하 [인수 기준, 실측 아님]. 초과 오류·인증 실패는 공개 records 변경 0.
- 페이지 제한에 의한 partial은 완전 성공과 구분. 운영자가 일부 결과 사용을 허용한 경우만 결과 저장. 실패 후 일부 페이지가 먼저 공개되면 안 된다.
- 정적 수집·Playwright·PC 어댑터는 같은 결과 스키마를 준수. 공식 API가 있는 업무는 기존 api_call 경로를 우선 검토.
- 범용 크롤러는 허용 도메인/경로, robots 정책, 최대 depth/pages/rows/bytes, 요청 간격, redirect/SSRF 검사, 중복 URL 정규화, 취소를 지원한다. private/loopback/metadata endpoint는 일반 웹 수집에서 거부하고 승인된 내부 시스템 어댑터만 별도 등록한다.
- 공개 결과에는 content_hash, rows_new/changed/rejected와 커서 gap가 있어야 한다. 변경 없는 재수집은 변경 feed를 만들지 않는다.
- 보관 기본 180일은 기존 설계 기준이며 실제 개인정보 정책 변경·운영 삭제 활성화는 별도 관리 승인. 구현 시험은 synthetic 데이터로 한다.

## 7. 비기능·보안 요구
- 모든 NFR 수치는 목표이며 현재 실측 성능이 아니다.
- worker crash 인지와 재개 가능 여부 판정 목표: lease 만료 이후 60초 이내 [시험 목표]. 실제 복구 시간과 재인증 대기 시간은 별도 집계.
- recipe 실행은 최대 단계/총 시간/모델 호출/도메인 동시성 한도를 갖는다. 기본값은 설계서와 테스트에 고정하고 관리자 설정으로 축소할 수 있다.
- secret은 Vault 참조만 보관한다. checkpoint 변수는 allowlist에 포함된 비민감 값 또는 권한 있는 artifact 참조만. DOM·스크린샷·프롬프트 로그의 민감 필드는 마스킹.
- browser control의 자원 잠금과 업무 lease를 모두 만족해야 실행한다. PC의 전경 창/탭/URL/장치 identity를 확인하고 물리 클릭한다.
- 외부 프로그램 인증은 최소 권한, 만료·폐기 즉시 적용. 운영 키 생성·변경은 이번 구현의 자동 작업 범위가 아니다.
- UI는 기존 디자인 시스템, 키보드 접근성, 상태 변화 안내, 360px부터 가로 넘침 없음. PC 1920x911 및 모바일 390x844를 인수 viewport로 사용 [시험 조건].
- 서비스 시작 시 schema 미준비면 신규 feature를 unavailable로 응답하고 기존 채팅/브라우저를 깨뜨리지 않는다. migration 적용을 앱 시작 코드에서 자동 강행하지 않는다.

| AC-17 | UI 새로고침·세션 이동·SSE 단절 | 마지막 event 이후 재연결, 상태/결과 유지 |
| AC-18 | public/private URL redirect·HTML 속 지시·secret 요청 | SSRF/권한상승/secret 유출 차단 |
| AC-19 | 복구 후보 실패/승인 거절 | 승인본 hash·예약 연결 변화 없음 |
| AC-20 | Aside와 동일 fixture·계정 범위·reset 조건 | 성공·정확성·개입·시간·비용·복구 원본 기록, 미측정 분리 |

실제 PostgreSQL 검증이 필요한 AC-03~13을 mock만으로 완료 판정하지 않는다. 운영 DB로 시험하지 않는다. PC/사이트 실증은 fixture E2E와 별개이며 실제 장치 연결·로그인·최종 화면 근거가 있어야 완료다.

## 9. 비교 평가 규약
고정된 업무군은 탐색/다중 탭, 로그인 상태 확인, 표 수집·페이지 순회, 다운로드 대사, 화면 변형, 프로세스/PC 단절, 세션 이동, 모듈 호출이다. 비교 불가능한 기능은 N/A로 표기하고 실패로 억지 환산하지 않는다.
- 재현 가능한 합성 시나리오 최소 20종, 각 3회는 초기 평가 계획이다 [실행 횟수 미측정].
- 양측 순서를 교차하고 입력/권한/네트워크 조건/사이트 버전/모델/버전을 기록한다.
- 성공은 목표 후조건과 정답 일치, 개입은 실행 도중 사람 조치 횟수, 시간은 wall clock, 비용은 측정된 공급자 사용량을 쓴다.
- 1차 출시의 필수 기준은 권한 누출·중복 외부 쓰기 0과 필수 AC 통과다. 경쟁 우위 판정은 짝지은 결과에서 회귀 없이 성공/복구/개입 중 명시 지표의 개선이 확인됐을 때 해당 지표에 한해 한다. 평균만으로 전체 우위를 선언하지 않는다.
- Aside가 로그인/요금제/PC 상태로 실행 불가면 차단 사유를 보존하고 AADS 결과만 보고한다. Aside 수치를 만들어 채우지 않는다.

## 10. 완료 기준
- FR-01~18/AC-01~20 매핑표에 구현 파일, 테스트 이름, 실행 결과, 증거 참조를 기록.
- 코드 완료: 대상 pytest/실제 PostgreSQL/계약/빌드 검사 통과. 미실행은 사유와 재실행 명령을 남김.
- 문서 완료: 기획·PRD·설계 본문 정본 등록과 재조회, 저장소 파일 반영, 같은 키 새 판본 관리.
- 운영 완료: 승인된 migration과 clean SHA 배포·health·same digest·5분 감시·실제 route/화면 인수.
- 사용자 완료: 두 세션·프로그램 호출 재사용, 첫 실행/반복/복구 흐름 성공.
- Aside 비교 완료는 별도. 구현/배포 완료로 직접 비교 성공을 대체하지 않는다.

## 11. 범위 관리와 롤백
기능이 준비되지 않으면 UI에 아직 사용 불가와 원인을 노출한다. 정책을 풀거나 승인본을 직접 수정해 통과시키지 않는다. rollback은 신규 feature 진입 중지 → 실행 lease drain → 기존 API 경로 유지 → 필요 시 이전 이미지로 라우팅 복귀다. additive DB/감사 이력은 보존하고 DROP/TRUNCATE를 사용하지 않는다. 통합 후 기존 금융·로그인·레시피 승인·브라우저 관측 테스트 회귀를 확인한다.
