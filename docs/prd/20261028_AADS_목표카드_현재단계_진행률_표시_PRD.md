# 목표 카드 현재 단계 진행률·진행 상태 표시 PRD

- document_key: `aads-goal-card-current-milestone-prd`
- 프로젝트: AADS · 작성일: 2026-10-28 · 상태: 초안 4판(마일스톤 클릭 시 업무 계층 펼침 CM-14 추가. 3판: 운영 화면 실캡처 대조)
- 목업: `docs/design/mockups/20261028_goal_current_milestone/` (manifest.json)

## 1. 배경과 문제

목표 카드(`/goals`)와 채팅 목표띠 드롭다운은 목표 전체 진행률만 보여 준다. 지금 어느 단계(마일스톤)가 얼마나 왔고 왜 멈췄는지는 목표를 열어야 보인다.

실측(2026-10-28 08:2x KST, 운영 DB):

| 항목 | 값 |
|---|---|
| 진행 중 단계 | 61개 |
| 하위 작업(work_items)이 있는 단계 | 24개 (39%) |
| 완료 체크리스트가 있는 단계 | 1개 |
| 러너 작업이 연결된 단계 | 14개 |
| 진행 중 단계의 하위 작업 상태 | 초안 92 · 준비 26 · 완료 19 · 진행 17 · 막힘 10 · 검토 1 |

→ 모든 단계에 %를 붙이면 37개 단계는 근거 없는 숫자가 된다. 근거가 있는 단계만 %를 보여 준다.

## 2. 대상 사용자와 경로

| 구분 | 내용 |
|---|---|
| 대상 | 대표님(목표 전체 관리), 목표 주도·담당 세션 |
| 첫 진입 | `/goals` 목록 또는 채팅 상단 목표띠를 열면 카드마다 현재 단계 한 줄이 바로 보인다 |
| 반복 사용 | 15초 자동 갱신으로 진행률·상태가 바뀌는 것을 본다 |
| 실패 복구 | 막힘·답 대기·담당 없음이면 상태를 눌러 사유와 "다시 보내기"·"담당 지정"을 바로 실행 |
| 조회 실패 | 현재 단계 값을 못 받으면 줄을 숨기고 기존 카드 그대로 보인다(빈칸·0% 표시 금지) |

## 3. 요구사항

| ID | 요구사항 | 완료 기준 |
|---|---|---|
| CM-1 | 목표 카드 하단에 현재 단계 한 줄: `M{순번} {단계 제목} · {진행률} · 진행: {상태}` | `/goals`·목표띠 드롭다운 캡처에 표시 |
| CM-2 | 현재 단계 = 진행 중 단계 중 순서가 가장 앞선 것. 여러 개면 `외 N개` | 진행 중 단계 3개인 목표에서 `외 2개` |
| CM-3 | 하위 작업이 있으면 `작업 완료/전체 (%)`, 진행 중이 있으면 `· 진행 N` 과 작은 막대 | 2/6(33%)·진행 2 예시 일치 |
| CM-4 | 하위 작업이 없으면 % 와 막대를 숨기고 `단계 순번/전체` 만 표시 | 0% 막대가 나오지 않음 |
| CM-5 | 진행 상태는 서버 progress_state 7종 그대로. 색: 막힘·답했으나 진행 없음=빨강, 답 대기·담당 없음=주황, 진행중=파랑, 멈춤·대기=회색 | 7종 렌더 테스트 |
| CM-6 | 상태를 누르면 사유·막힌 시각(KST)·다시 보내기·담당 지정(기존 GoalStuckActions) 펼침 | 클릭 테스트 |
| CM-7 | 모바일(390px)은 두 줄로 줄바꿈, 버튼 터치 44px 이상 | 390x844 캡처 |
| CM-8 | 내부 식별자(UUID·progress_state 원문) 노출 금지 | 캡처 검수 |
| CM-9 | 서버: 목표 목록·for-session 응답에 `current_milestone` 추가(기존 필드 유지). 목표 전체를 한 번에 묶어 조회 | 운영 DB 실행 200ms 이하 |

`current_milestone` 형식:

```json
{"milestone_id": "...", "sequence": 2, "total": 5, "title": "...",
 "items_done": 2, "items_in_progress": 2, "items_total": 6,
 "progress_state": "awaiting_reply", "progress_reason": "...", "other_in_progress": 0}
```

## 3-1. 적용 화면 (2판 추가)

| ID | 화면 | 요구사항 | 완료 기준 |
|---|---|---|---|
| CM-10 | 채팅 목표 버튼(목표띠 드롭다운) | 목록의 각 목표 아래에 CM-1 과 같은 현재 단계 한 줄. 접힌 버튼에는 1순위 목표의 `M순번 · 진행 상태` 만 | 드롭다운 캡처 |
| CM-11 | 오른쪽 목표 현황 패널(GoalPanel) | 맨 위 "지금 단계" 카드: 단계 제목·하위 작업 진행률 막대·진행 상태·사유·막힌 시각·다시 보내기·담당 지정. 그 아래 단계 목록: 단계마다 상태 점·하위 작업 완료/전체·검토 대기 표시 | 패널 캡처 |
| CM-12 | 진행률 표기 분리 | 목표 진행률을 `확정 X%` 로 쓰고, 보고는 했지만 확인 전인 단계가 있으면 `· 검토 대기 N단계` 를 함께 표시. 0% 라도 검토 대기가 있으면 0% 만 단독 표시 금지 | 확정 0%·검토 대기 4 예시 캡처 |

### 진행률 0% 와 주도 세션 보고가 다른 이유 (2026-10-28 실측)

- 목표 진행률은 `확인 완료(completed)` 단계 수 ÷ 전체 단계 수다(app/services/goal_manager.py `_update_goal_progress`). 담당이 완료를 보고해 `검토 대기(review)` 인 단계는 0 으로 센다.
- 주도 세션은 보고한 단계까지 진행으로 말한다. 그래서 같은 목표가 세션에서는 25%, 목표띠·목록에서는 0% 로 보인다.
- 실측: 진행 중 목표 중 검토 대기 단계가 있는 목표 18개(검토 대기 단계 28개), 그중 6개가 화면에 0% 로 표시. 예: "GO100 실매매 파이프라인 개선" 단계 6개 중 4개 검토 대기 · 확정 0개 → 0%. 가장 오래된 검토 대기는 2026-09-21 보고.
- 결정: 확정 진행률 계산식은 바꾸지 않는다(검토 전 단계를 완료로 세지 않음). 대신 CM-12 로 검토 대기를 함께 보여 주고, 검토 대기 단계 처리는 별도 정리 대상으로 둔다.

## 3-2. 운영 화면 대조 (3판, 2026-10-28 13:2x KST 실캡처)

운영 `/chat`(대시보드 `3bd1eaf`)에 E2E 로그인해 서버 Playwright 로 목표 버튼·펼친 목록·오른쪽 목표 패널을 캡처하고 화면 글자를 덤프했다(`live_before_text.json`). 2판까지는 이 대조 없이 작성해, 이미 있는 기능을 새 기능처럼 적은 줄이 있었다.

| CM-14 | 오른쪽 패널 마일스톤 | 마일스톤 줄 전체(높이 44px 이상, ▶/▼ 표시)를 누르면 그 바로 아래로 Epic→Story→Task 를 펼친다. 각 항목에 한글 상태·작업 완료/전체를 보여 준다. 업무가 없으면 빈 칸 대신 "아직 업무가 없습니다 — 진행률은 단계 순번으로만 보입니다"와 "주도에게 업무 등록 요청" 버튼을 보여 준다. 처음 열 때는 현재 단계만 펼친다. 지금 운영 화면에서는 카드를 눌러도 반응이 없고 카드 아래 작은 "▶ 업무 계층" 줄만 펼쳐진다(`GoalMilestoneWork.tsx` SectionShell) | 마일스톤 줄 클릭 테스트, 업무 0건 상태 렌더 테스트, 1440·390 캡처 |

2판 이전 보고의 정정: "채팅 목표 버튼 목록에 단계 이름이 이미 있다"는 틀렸다. 펼친 목록에는 단계 이름이 없다(위 표). "오른쪽 패널 단계마다 다시 보내기가 있다"는 조건부다(막힘·담당 없음일 때만).

## 4. 범위 밖

- 하위 작업이 없는 37개 단계에 하위 작업을 채우는 일(목표 계층 정리로 별도 진행).
- 목표 전체 진행률 계산식 변경(확정 기준 유지).
- 검토 대기 단계 28개의 확인 처리(별도 정리).

## 5. 리스크

- 업무 계층 실측(2026-10-28 13:4x KST): 진행 중·막힌 목표의 미완료 단계 524개 중 업무가 등록된 단계는 160개(30.5%). 펼쳐도 비어 있는 단계가 대부분이므로 CM-14 의 빈 상태 안내가 필수다. 완료된 단계인데 하위 작업이 0/6 인 사례도 있다("오비스 UI/UX" M1) — 단계 완료 시 하위 작업 상태를 맞추는 일은 범위 밖, 화면에는 ⚠ 로 표시.

| 리스크 | 대응 |
|---|---|
| 하위 작업 없는 단계가 61%라 `단계 n/m` 만 보이는 카드가 많다 | R-GOAL-HIER 계층 정리를 병행 |
| 목록 응답 지연 | 묶음 조회, 반영 전 운영 DB 실행 시간 측정 |
| 진행 칩·처리 순서는 이미 운영 반영(대시보드 `3bd1eaf`) | 그 위에 덧붙이고, 기존 GoalPanel 테스트(진행 상태 7종·UUID 미노출)를 깨지 않는다 |
| 모바일에서 목표 버튼 진입 경로가 캡처되지 않음 | 구현 전에 390px 진입 경로를 확인하고, 없으면 CM-7 범위에 진입 버튼을 포함 |
