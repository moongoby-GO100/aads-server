# 채팅 반응성 — PRD·설계

- 작성 2026-09-14 KST · 배경은 [기획서](../plans/20260914_CHAT_RESPONSIVENESS_기획서.md)
- 범위: 첫 토큰 앞당기기 + 중간 지시 즉시 반영

## 1. 첫 토큰을 Auto-RAG 보다 먼저

### 지금

    [질문] → 임베딩 2.5초 → Auto-RAG 검색 → 프롬프트 조립 → 모델 → 첫 글자
             ────────────── 화면은 비어 있다 ──────────────

### 바꾼 뒤

    [질문] → 프롬프트 조립(임베딩 없이) → 모델 → **첫 글자**
                └ Auto-RAG 는 따로 돌아 준비되면 뒤에 붙는다

근거가 첫 문장에 필요한 경우는 드물다. 대개 답을 시작한 뒤 중간에 쓰인다.

### 어떻게 붙이나

두 가지 중 하나다.

| 방식 | 장점 | 단점 |
|---|---|---|
| **A. 대기 상한** | 구조가 단순하다 | 상한만큼은 여전히 기다린다 |
| B. 두 번째 턴에 주입 | 완전히 안 기다린다 | 이번 답에는 근거가 없다 |

**A 를 쓴다.** 상한을 짧게 둔다(`AUTO_RAG_WAIT_MS`, 기본 700ms).
그 안에 끝나면 이번 턴에 붙고, 늦으면 **버리지 않고 다음 턴에 붙인다.**

700ms 인 이유 — 임베딩이 캐시에 있거나 짧은 질문이면 그 안에 끝난다.
실측에서 짧은 문장은 0.1초였다. 긴 질문만 다음 턴으로 밀린다.

**버리지 않는 것이 중요하다.** 버리면 그 질문에 대한 근거가 영영 안 붙는다.

### 사용자에게 보이는 것

늦게 붙는 경우에만 한 줄 남긴다.

    (근거 검색이 늦어 이번 답에는 반영되지 않았습니다. 다음 답부터 반영됩니다.)

**조용히 빼지 않는다.** 근거 없이 답한 것을 대표님이 모르시면 안 된다 —
오늘 하루 고친 것이 전부 그런 종류였다.

## 2. 중간 지시를 돌고 있는 턴에 넣는다

### 지금 왜 안 되나

    sdk_query(prompt=..., options=...)   일회성. 시작하면 넣을 수 없다.

`agent_sdk_service` 에 인터럽트 처리가 **0줄**이다. 큐에 쌓였다가 다음 턴
앞에 붙는다. 턴이 2~61분이니 최악은 한 시간 뒤다.

### 바꾸는 법

SDK 0.2.152 `ClaudeSDKClient` 에 `query` 와 `interrupt` 가 있다.
연결을 열어 두고 **도는 중에 메시지를 보낼 수 있다.**

    client = ClaudeSDKClient(options)
    await client.connect()
    await client.query(prompt)
    async for message in client.receive_response():
        ...
        # 매 메시지 사이에 인터럽트를 확인해 바로 넣는다
        if has_interrupt(session_id):
            await client.query(f"[대표님 추가 지시] {text}")

### 넣을 때 규칙 셋

**① 죽이지 않는다.** `interrupt()` 로 턴을 끊지 않는다. 20분치 작업이
사라진다 — 오늘 배포로 두 번 그런 일이 있었고 그때마다 조사가 날아갔다.
**이어서 반영**하게 한다.

**② 우선순위를 적는다.** "대표님 지시가 기존 작업과 충돌하면 대표님
지시를 우선한다" 를 함께 넣는다. LiteLLM 경로에 이미 있는 문구를 맞춘다.

**③ 화면에 알린다.** `interrupt_applied` 이벤트를 보낸다. 넣었는지
대표님이 아셔야 한다. 조용히 넣으면 무시된 것과 구분이 안 된다.

### 실패하면 예전 방식으로

`ClaudeSDKClient` 연결이 안 되면 **일회성 `query()` 로 떨어진다.**
중간 주입만 못 할 뿐 대화는 돈다. 반응성을 얻으려다 채팅을 못 쓰게 만들면
안 된다.

`CHAT_SDK_BIDIRECTIONAL=false` 로 끌 수 있다.

## 3. 계측으로 확인한다

이미 넣은 `chat_turn_timing` 으로 전후를 비교한다.

    first_token_ms   ① 이 줄이면 줄어야 한다
    rag_ms           Auto-RAG 가 별도로 도는지
    relay_ms         ② 가 여기에 영향을 주면 안 된다

**숫자로 확인하기 전에는 좋아졌다고 말하지 않는다.**

## 4. 합격 기준

1. Auto-RAG 가 700ms 안에 안 끝나면 첫 토큰이 먼저 나온다.
2. 늦은 근거는 **버려지지 않고** 다음 턴에 붙는다.
3. 근거가 빠진 답에는 그 사실이 한 줄 남는다.
4. 응답 중 보낸 지시가 **그 턴 안에서** 반영된다.
5. 인터럽트가 진행 중 작업을 죽이지 않는다.
6. `interrupt_applied` 가 화면에 뜬다.
7. 양방향 연결이 실패하면 기존 방식으로 떨어지고 대화는 계속된다.
8. `first_token_ms` 중앙값이 전보다 작다 — 숫자로 확인한다.

## 5. 하지 않는 것

- Auto-RAG 끄기 — 근거가 붙는 것이 이 채팅의 값어치다
- 인터럽트 시 턴 폐기 — 20분치 작업이 사라진다
- 임베딩을 원격으로 — 대화 경로에 네트워크 왕복을 더하는 것이 나은지
  재 보지 않았다. 백필과 대화는 요구가 다르다
