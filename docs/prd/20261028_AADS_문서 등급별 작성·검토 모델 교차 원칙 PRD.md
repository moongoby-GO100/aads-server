## 2. 대상 사용자와 경로

| 사용자 | 하는 일 | 필요한 것 |
|---|---|---|
| CEO(대표님) | 설정 화면에서 등급 기준·검토 모델 순서를 정하고, D2·D3 정본을 승인한다 | 정본 목록에서 "이 문서가 어떤 등급이고 누가 썼고 누가 검토했는지" 한눈에 |
| PM 세션 | 문서를 정본에 등록하고, 검토 통과한 것을 '검토'로 올린다 | 등급이 자동 산정되고, 검토 모델이 자동 지정되며, 막히면 이유를 안다 |
| 러너 | 지시서를 받아 문서·코드를 작성한다. 작성 모델이 기록된다 | 작성 모델 ID 가 서버 쪽에서 신뢰할 수 있는 값으로 남는다 |

### 2-1. 첫 실행
1. CEO 가 설정 → 모델 → 러너 모델 우선순위에서 '코드 검수' 3줄(경량·보통·상위)과 '문서 작성·검토' 블록을 처음 본다. 값은 현재 DB 값에서 시작하며 저장 전 미리보기로 예시 문서 3건의 행선지를 본다.
2. 저장하면 이후 등록되는 문서부터 등급·검토 모델이 적용된다. **기존 388건은 소급 적용하지 않는다**(§7).

### 2-2. 반복 사용
- PM 이 문서를 등록하면 서버가 등급을 계산해 응답에 `doc_tier` 를 돌려준다. 검토 요청 시 검토 모델이 자동 지정된다.
- D1 은 검토 모델 1개가 통과시키면 기록으로 끝난다(승인 불필요). D2·D3 는 검토 통과 후 PM 이 '검토'로 올리고 CEO 가 승인한다.

### 2-3. 실패 복구
| 상황 | 화면·동작 |
|---|---|
| 반대편 회사 모델이 모두 사용 불가 | 검토 상태 `차단(교차 불가)` + 알림. 같은 회사 모델로 **조용히 대체하지 않는다**. CEO 가 모델을 추가/복구하거나 명시적으로 예외 승인 |
| 50,000자 초과 | `분할 권고`로 반려. 검토 큐에 올라가지 않으며 사유가 한글로 표시 |
| 검토가 반려됨 | 작성자에게 반려 사유 전달. 새 개정을 등록하면 등급·검토를 다시 계산 |
| 작성 모델을 알 수 없음(구버전 클라이언트, 출처 없음) | 등급은 계산하되 `작성 모델 미상` 표시, 검토는 어느 회사든 반대편을 고르지 못하므로 **두 회사 각 1개**로 검토(안전 쪽) |

## 3. 등급 정의 (CEO 확정안)

결정일: 2026-10-29. 근거: CEO 2026-10-29 권장안 승인.

| 등급 | 기준 | 작성 1순위 | 검토 | 승인 |
|---|---|---|---|---|
| D1 가벼움 | report·reference 이면서 15,000자 이하 | 러너 S 순서 | 다른 회사 경량 모델 1개 | 정본 승인 대상에서 제외(등록·기록은 유지) |
| D2 보통 | plan·design·spec·tasks 이면서 15,000자 이하 | 러너 M 순서 | 다른 회사 상위 모델 1개 | PM 이 검토로 올리고 CEO 가 승인 |
| D3 중요 | prd·contract·architecture 또는 15,000자 초과(목표 연결 조건은 기본 off) | 러너 L·XL 순서 | 반대 회사 상위 모델 1 + 작성 회사의 작성 모델과 다른 상위 모델 1, 둘 다 통과 | PM 이 검토로 올리고 CEO 가 승인 |
| 분할 권고 | 50,000자 초과 | — | 검토 전에 나눠 쓰도록 반려 | — |

- 글자 수 = 저장된 본문의 유니코드 글자 수(`char_length`, 공백·줄바꿈 포함).
- 여러 조건에 걸리면 **더 높은 등급**이 이긴다. 분할 권고는 등급보다 먼저 적용된다.
- `tasks`는 D2로 확정했다. 목표 연결 여부는 입력으로 받되 등급 반영 플래그 기본 off.
- 15,000자·50,000자는 설정값이며 15,000자 기준은 2주 측정 후 재조정한다.
- 코드 검수도 같은 원칙: AI_REVIEW 를 작업 크기별 경량(XS·S) / 보통(M) / 상위(L·XL) 3줄로 나누고, 실제 작성 모델의 반대편 회사를 1순위로 둔다.

## 4. 기능 요구사항 (FR)

### 4-1. 기록 (M1)
- **FR-1** 개정 등록 시 `doc_tier`, `author_model`, `author_provider` 를 개정 행에 함께 저장한다(개정 행은 불변이므로 등록 시점에 확정).
- **FR-2** `author_model` 은 클라이언트 입력을 그대로 믿지 않는다. `source_task_id` 가 러너 job 이면 `pipeline_jobs.actual_model` 에서, 채팅 세션이면 세션의 실제 호출 모델에서 서버가 채운다. 채울 수 없으면 `unknown`.
- **FR-3** `author_provider` 는 모델 ID 접두사로 판별한다: `claude-`·`claude:` → `anthropic`, `codex:` → `openai`, 그 밖은 `other:<접두사>`. 판별 불가는 `unknown`.
- **FR-4** 검토 결과(검토 모델, 회사, 판정, 시각, 사유)는 별도 추가 전용 기록에 쌓는다. 한 개정에 검토가 여러 번(D3 는 2회, 재시도) 붙을 수 있다.

### 4-2. 등급 자동 산정 (M2)
- **FR-5** 등급은 서버가 `(kind, 글자 수, 목표 연결 여부)` 로 계산한다. 클라이언트가 보낸 등급 값은 무시한다.
- **FR-6** 기준값(15,000자·50,000자)은 코드 상수가 아니라 설정값으로 둔다. 기본값은 CEO 확정안 그대로.
- **FR-7** 등록 응답, 목록, 상세, 검토 큐에 `doc_tier` 가 포함된다. 기존 필드는 유지한다(하위호환).
- **FR-8** 개정이 바뀌면 등급을 다시 계산한다(글자 수가 커져 D2→D3 이 될 수 있다). 이전 개정의 등급은 그대로 남는다.

### 4-3. 교차 검토 강제 (M3)
- **FR-9** **첫 번째 교차 검토자(`cross` 역할)**만 작성 모델과 다른 회사에서 고른다. D3 두 번째 검토자는 작성 회사의 작성 모델과 다른 상위 모델로 고른다(FR-11). 해당 등급 설정 순서를 위에서부터 보되 같은 회사 항목은 건너뛰고 다음 순위(반대편 회사)를 쓴다.
- **FR-10** 반대편 회사 모델을 하나도 못 고르면 검토를 **차단**하고 알림을 보낸다. 같은 회사로 대체하지 않는다.
- **FR-11** D3 는 두 회사 상위 모델이 각각 검토하고 **둘 다 통과**해야 '검토 통과'가 된다. 하나라도 반려하면 반려.
- **FR-12** 검토 통과 전에는 PM 의 '검토로 올리기'(`canonical_document_review`)가 거절된다. 거절 사유는 한글.
- **FR-13** D1 은 검토 통과 후 승인 단계를 만들지 않는다. 정본 목록에는 남고(R-DOC '모든 문서 등록' 유지), 승인 대기 큐에는 나타나지 않는다.
- **FR-14** 50,000자 초과는 검토 큐에 들어가지 않고 `분할 권고` 로 반려된다.
- **FR-15** 코드 검수는 작업 크기로 경량/보통/상위 목록을 고르고, 실제 작성 모델의 반대편 회사 모델을 1순위로 한다. 반대편 모델이 없으면 기존처럼 같은 목록 순서로 진행하되 `교차 불가` 를 기록한다(코드 검수는 차단하지 않는다 — §9-6).

### 4-4. 설정 화면 (M4)
- **FR-16** '러너 모델 우선순위'에서 '코드 검수'를 크기별 3줄(경량/보통/상위)로 나눠 보여 준다. 화면 문구는 업무명, 내부 키(`AI_REVIEW_LIGHT` 등)는 보조 표기.
- **FR-17** '문서 작성·검토' 새 블록에 D1/D2/D3 행마다 기준(종류·글자 수·목표 연결), 작성 순서, 검토 모델, 승인 방식을 보여 준다.
- **FR-18** 각 행에 '교차 회사 확인' 배지: ✅ 다른 회사 / ⚠️ 같은 회사 → 자동 교체될 모델 표시.
- **FR-19** 저장 전 미리보기로 예시 문서 3건이 어떤 등급·검토 모델로 가는지 보여 준다.
- **FR-20** 정본 문서 화면(목록·상세)에 등급 배지와 '작성 모델 / 검토 모델·결과'를 표시한다.
- **FR-21** 모바일 390px 폭에서 가로 스크롤 없이 쓸 수 있다(행은 카드로 쌓임).

| M1 기록 필드 | 개정에 `doc_tier`·`author_model`·`author_provider`, 검토 기록 테이블, 작성 모델 서버 채움 | AC-1 |
| M2 등급 자동 산정 | 등급 함수, 응답·목록·상세에 `doc_tier`, 기존 388건은 읽기 시 계산(저장 안 함) | AC-2, AC-3 |
| M3 교차 검토 강제 | 검토 모델 선택 알고리즘, D3 이중 검토, 차단·알림, 코드 검수 3분할 | AC-4~AC-7 |
| M4 설정 화면 | '코드 검수' 3줄, '문서 작성·검토' 블록, 교차 배지, 미리보기, 정본 화면 배지 | AC-8, AC-9 |

각 단계는 앞 단계 없이도 되돌릴 수 있게 나눈다(롤백은 설계 문서 §8). 기존 388건은 M2 에서 "읽기 시 계산"만 하고 소급 검토는 하지 않는다.

## 8. 비용 측정 계획

D3 이중 검토 비용은 **미측정**이다. 추정치를 만들지 않고 측정한다.

| 측정 항목 | 방법 | 기간 |
|---|---|---|
| 등급별 문서 수/일 | 개정 등록 시 `doc_tier` 집계 | M2 배포 후 2주 |
| 검토 1회당 입력·출력 토큰, 소요 시간, 비용 | 러너 job 의 `total_cost`·`duration_seconds` 를 검토 기록과 연결 | 2주 |
| D3 이중 검토 추가 비용 | D3 의 (검토 2회 합계) − (검토 1회 기준) | 2주 |
| 반려율·재검토 횟수 | 검토 기록 판정 집계 | 2주 |
| 교차로 새로 잡힌 문제 | 같은 회사 검토에서 놓치고 반대편이 지적한 건수(표본 20건 수동 확인) | 2주 |

- 2주 후 15,000자 기준, D1 승인 제외 범위, 월 비용 상한을 재조정한다. **상한값은 측정 전에 정하지 않는다**(§9-3).
- 임시 안전장치: 하루 D3 검토 건수가 설정 상한을 넘으면 CEO 에게 알리고 큐에 쌓는다(상한 숫자는 §9-3 에서 결정).

결정일: 2026-10-29. 근거: CEO 2026-10-29 권장안 승인.

## 10. 위험

| 위험 | 대응 |
|---|---|
| 작성 모델 기록이 부정확하면 교차 판정이 틀린다 | 서버 채움(FR-2), 미상 표시, AC-1 로 감시 |
| D3 비율이 높아 비용·지연이 커진다 | §9-2 결정, §8 측정, 일일 상한 알림 |
| 반대편 회사 모델 장애로 문서가 쌓인다 | 차단 알림 + 모델 추가 안내. 같은 회사 조용한 대체는 금지 |
| 구버전 대시보드가 새 size 행을 모르는 이름으로 보여 준다 | 설계 §6 하위호환(기존 6개 size 유지, 새 행은 추가만) |
| 개정 불변 트리거 때문에 검토 결과를 개정 행에 못 쓴다 | 검토 기록 별도 테이블(설계 §5) |
