# 오비서 원천 DB 조회 확장 및 자료 확인 계약

## 문제와 사용자 흐름

라일론 자료는 ACCT `source_file` 아래 JSON 전표(`atom_record`)와 엑셀 셀(`atom_sheet`/`atom_cell`)로 나뉜다. JSON 매출 조회가 비어 있어도 엑셀 자료는 존재한다. 기존 카드·통장·세무 화면은 오비서의 별도 원장만 읽었으므로 실제 ACCT 원천을 보지 못했다.

대표님은 기존 오비서에 로그인하고 조직·사업자를 선택한다. 카드/통장/매입/매입처/세무증빙 메뉴에서 원천 내역을 조회하고, 날짜·상태·검색·이전/다음 페이지로 좁힌 뒤 건별 상세를 연다. 각 메뉴의 `원천 자료·연결 현황` 버튼에서는 업무별 파일 목록, 엑셀 시트, JSON 회계 원문을 조회한다. 오류는 빈 성공으로 바꾸지 않고 오류와 재조회 경로를 표시한다. 조직 전환은 기존 인증·멤버십 검증 경로를 유지한다.

## 구현 계약

| 구분 | 연결 및 동작 | 제한/완료기준 |
|---|---|---|
| 매출·매입·매입처 | 기존 ACCT 매입매출전표 및 오비서 자체 원장 | JSON 매출 0건을 전체 매출 0원으로 단정하지 않는다 |
| 카드 | `cd_ctrade` 보유 거래, 일반전표형 카드도 포함 | 카드번호를 추정하지 않는다. 원천 카드코드만 제공 |
| 통장 | 실제 입출금액과 날짜·전표번호가 있는 거래 | 전일잔액/19000101/식별자 없는 스냅샷을 거래 합계에서 제외. 계좌 식별자 미확정은 명시 |
| 세무증빙 | 매입매출전표와 카드 원천의 합집합, 전표키 중복 제거 | 전자세금계산서 번호/세부유형 우선. ty_trade=2만으로 현금영수증이라 하지 않는다 |
| 상태·합계 | 원천 합계(제외·보류 포함), 확정 원천 금액 구분 | 미확인·보류·제외를 확정으로 표시하지 않는다 |
| 전체 목록 | ACCT SQL에서 검색·상태 필터, 집계 후 페이지 제한 | 2,000건 밖 자료도 페이지/건별 상세로 조회한다. 자체 원장은 선두에 별도 합산 |
| 원천 목록 | 현재 사업자의 current 파일 전부 페이지 조회 | 파일 수/셀 수를 거래 건수로 간주하지 않는다 |
| 원문 시트 | 파일→시트→빈 행을 생략한 원본 행 단위 페이지 | 원본 행 번호 유지. 식별번호/이메일 가림. 수식 실행 없음 |
| JSON 원문 | 허용된 회계 필드만 조회, 원본 rec_idx 페이지 | 스냅샷 중복이 존재하므로 실적 집계에 직접 더하지 않는다 |

모든 API는 로그인 사용자의 오비서 사업자 소유권을 먼저 확인하고 ACCT tenant/company 범위를 서버에서 결정한다. 파일·시트 ID를 직접 바꾸어도 같은 소유권 조건을 다시 적용한다. DB 조회 실패는 502, 미소유 원문은 404로 구분한다. 신규 DB 스키마/원천 쓰기는 없다.

## 합계에 넣지 않는 자료와 남은 업무

매출 폴더에는 월별 집계, 정산차이, 잔액, 수수료, 금액만 있는 단일 열 파일이 있다. 이를 모두 일별 매출로 만들면 거래일·취소·주문번호·사업자/브랜드 귀속을 발명하고 중복 합산하게 된다. 이번 원문 보기는 이 자료를 열어 확인하는 기능이며 거래 정규화 완료를 뜻하지 않는다.

- 일별 매출 완성: 채널별 거래일·주문/취소 ID가 보존된 정본을 확보하고 브랜드 귀속, 취소 반영, 중복키를 대조한 후 전용 적재기를 적용한다.
- 통장 계좌별 완성: 원천 스냅샷과 실제 계좌 마스터의 검증된 연결이 필요하다. 없는 계좌번호를 파일명에서 만들어 쓰지 않는다.
- 홈/미수금/미매칭/급여/재고/세무신고 등은 이번 JSON 조회 확장으로 ACCT 업무처리가 완성되지 않는다. `source-coverage.routes`는 실제 연결 범위를 반환한다.
- 파일 등록만 있고 셀/회계 JSON이 없는 이미지·PDF 등은 구조화 원문 없음으로 남긴다.
- 위하고 추가 다운로드, 원천 자체 수정, 전표 승인/마감/역분개는 이번 구현에 포함되지 않는다.

## 검증 및 배포

단위 검증은 증빙 오분류, 취소 상태, 출금 부호, 소유권, SQL 입력, 희소 셀 페이지, 식별번호 마스킹, 2,000건 이후 페이지/상세를 포함한다. 실제 ACCT SQL과 API 집계·건별 ID를 비교하고, Playwright로 PC/모바일 목록→상세 및 파일→시트를 확인한다. 검사 대상은 준비된 코드와 운영 코드를 구분해 기록한다.

배포는 정확한 커밋의 clean worktree에서 `deploy.sh bluegreen`, 한 SHA 한 이미지, 후보 health, 짧은 nginx 잠금, DB 실행 소유권, 동일 이미지 standby, 공개 경로, 5분 P0/P1 관제 순서로 인증한다. 오비서 sidecar와 정적 파일 bind mount도 같은 검증된 파일로 반영해야 한다. 다른 세션의 파일은 덮어쓰지 않는다. 실패 시 이전 인증 이미지와 변경 전 오비서 마운트 파일로 복구한다.

핸드오버 정본: `AADS / verification / obys-source-reflection-direct-20260923`. 최종 검증 수치·커밋·배포 판정은 해당 DB 기록을 따른다.
