- document_key: `aads-goal-retry-accounting-acceptance`
- 작성: 2026-10-14 · 짝 문서: 진단 보고 `aads-goal-retry-exhaustion-analysis`
- 상태: **명세만. 구현·테스트 코드 작성·배포는 하지 않았다.** 이 문서는 나중 구현 작업의 완료 기준이다.
- 대상 모듈: `app/services/goal_failure_retry.py` (읽기 전용 참조), 연관 `next_step_proposals.py`, `chat_service.enqueue_next_step_reaction`, `deferred_reaction_freshness.py`

## 1. 용어

| 용어 | 정의 |
|---|---|
| 제안(proposal) | 재작업 후보 예약과 카드/대기열 생성 시도. 지금의 `retry_candidates` 항목 |
| 고유 후보 | 마일스톤 안에서 고유한 queue_id 또는 card_id |
| 실행(execution) | 재작업 러너 job이 **실제로 시작**된 것. 키는 러너 job id |
| 계보(lineage) | `failed_task_id` 하나. 같은 실패를 잇는 후보·실행의 묶음 |
| 제안 한도 | 카드 없는 제안 실패의 10분 backoff와 계보당 3회. 현행 유지 |
| 실행 한도 | 계보당 실제 실행 상한. 기본 2, 상한 2 유지 |

실행 시작 시점은 구현 전에 확정이 필요한 결정 항목이다.

- 안 A(권장): 러너 job이 `started_at`을 얻는 시점. 이미 DB 컬럼이 있고 job id로 멱등 키를 잡기 쉽다.
- 안 B: 재작업을 위한 첫 모델 호출 직전. AGENTS.md 규칙 5("실제 모델 호출 직전에만 증가")에 더 가깝지만 호출 경계를 새로 정의해야 한다.

## 2. 불변 조건 (바꾸지 않는다)

1. 전역 anti-loop, 작업당 LLM 호출 상한, 비용 한도, 승인 절차를 유지한다.
2. 상한 2를 늘리지 않는다(`min(2, …)` 유지). 무조건 상한 증가는 개선안이 아니다.
3. 실패 증거(`retry_candidates`, 큐 행, 오류 문구, `failed_task_id`)를 삭제하지 않는다. 격리는 이력 영역으로 옮기는 것이다.
4. 모든 조회·갱신은 `tenant_id` 조건을 유지한다.
5. 동시 호출에서 같은 실행을 두 번 세지 않는다.
6. 이미 완료된 마일스톤·목표의 status를 이 기능이 되돌리지 않는다.

## 3. 목표 동작

1. **제안과 실행을 따로 센다.** 제안은 현행 backoff·3회 제한, 실행은 계보당 최대 2회.
2. **고유 키로 센다.** 같은 queue_id/card_id가 여러 번 반환돼도 고유 후보는 1이다.
3. **실행 한도는 시작 시 원자적으로 차감한다.** 같은 job id의 중복 claim은 한 번만 차감한다. 보류 → 시작 사이의 어느 단계에서도 미리 차감하지 않는다.
4. **차감하지 않는 사건:** 대기(pending)·claim·릴레이 슬롯 대기·의존성 대기(blocked_dependency)·cancelled·skipped_stale·만료·승인만 받은 상태·범위 파서 같은 제출 단계 거절.
5. **계보별 독립 예산.** 서로 다른 `failed_task_id`는 서로의 실행 한도를 쓰지 않는다.
6. **유효 승계 선검사.** 제안 전에 같은 마일스톤에 활성 후속 job이 있거나 이미 완료된 승계가 있으면 재제출하지 않는다.
7. **죽은 큐 재사용 금지.** 15분 중복막이가 종결 상태(`skipped_stale`/`failed`/`cancelled`)의 큐를 반환하면 새 후보로 합산하지 않거나 새 키로 새 큐를 만든다. 재사용 여부(`created=false`)를 후보 기록에 남긴다.
8. **지시문과 stale 가드가 충돌하지 않는다.** 재작업 지시문에 들어 있는 실패 job id는 "이미 종결됐으니 건너뛸 대상"으로 판정하지 않는다.
9. **완료된 마일스톤의 소진 문구는 현재 blocker가 아니다.** 이력으로 보존하고 현재 차단·목표 blocked 판정에서는 제외한다.
10. **사용자 문구.** `고유 후보 N · 실제 실행 M/2 · 남은 한도 K · 다음 행동 …` 4가지를 모두 표시한다.

## 4. 수용 테스트

각 시나리오는 구현 작업에서 자동 테스트로 옮겨야 한다. 이 문서에서는 테스트를 만들지 않았다.

| ID | 입력 | 기대 결과 |
|---|---|---|
| T1 | 같은 queue_id가 한 계보에서 2번 후보로 기록됨 (이번 M9 형태) | 고유 후보 1, 실행 0, 남은 실행 한도 2, `retry_exhausted` 아님 |
| T2 | 대기열이 `skipped_stale`(`stale_jobs`, 의존성 취소)로 끝남 | 실행 0, 한도 차감 없음, 후보는 이력에 `skipped_stale`로 남음 |
| T3 | 승인 카드만 `approved`, 러너 job 미생성 | 실행 0 |
| T4 | 재작업 러너 job 1개가 모델 시작(안 A: `started_at` 설정) | 실행 1, 남은 1 |
| T5 | 같은 job id에 대해 시작 알림/claim이 2번 | 실행 1 (멱등) |
| T6 | 계보 X에 실행 2회 소진, 같은 마일스톤에 새 실패 Y 발생 | Y는 독립 예산으로 0/2에서 시작, X는 2/2 |
| T7 | 같은 계보에 활성(진행 중) 후속 job 존재 | 재제출 0, 사유 `successor_active`, 후보 신규 생성 없음 |
| T8 | 완료된 승계(`superseded_by` + 완료 증거) 존재 | 소진 판정·소진 문구 없음 |
| T9 | 소진 문구가 남은 `completed` 마일스톤 | 현재 blocker 0, 목표 blocked 판정 제외, 이력에 문구·후보 보존, 증거 삭제 없음 |
| T10 | 테넌트 A의 후보 데이터와 같은 id 패턴이 테넌트 B에 존재 | 서로 카운트·갱신·표시 격리 |
| T11 | 재작업 지시문 본문이 종결된 실패 job id만 담고 있음 | stale 가드가 건너뛰지 않음 (현행은 `stale_jobs`로 건너뜀) |
| T12 | 15분 안에 `dedupe_key`가 같은 종결 큐가 존재 | 새 후보로 세지 않거나 새 큐 생성. 고유 후보는 늘지 않음 |
| T13 | 범위 파서 거절로 시작 전 error (최초 제출 `runner-050876df` 형태) | 실행 0, 사유 `submit_rejected`, 재작업 실패와 구분 표시 |
| T14 | `GOAL_FAILED_LINK_RETRY_MAX=99` | 실행 상한은 2 유지 |
| T15 | 두 워커가 같은 마일스톤에서 동시에 차감 시도 | 상한 초과 없음 (락 또는 UNIQUE 제약) |
| T16 | 사용자 문구 렌더링 | 고유 후보·실제 실행·남은 한도·다음 행동이 모두 있고, 실행 0이면 "실행 없음"이 명시됨 |

## 5. 데이터 설계 방향 (권고, 비구속)

- 실행 장부: `(tenant_id, milestone_id, lineage, execution_key)`에 UNIQUE를 둔 별도 테이블 또는 evidence 하위 구조. `execution_key`는 러너 job id. UNIQUE 충돌이 곧 중복 claim 방지(T5, T15).
- 후보 항목에 `queue_reused`, `terminal_at`, `terminal_reason` 필드를 추가하고 합산 기준은 "고유 queue/card 중 살아 있는 것".
- 소진 판정은 `실행 수 >= 상한` 하나로만 한다. 제안 개수는 판정에 쓰지 않는다.
- 이력 격리: 현재 blocker를 위한 필드(현행 `dispatch_note`)와 역사 기록을 분리한다.

## 6. 기존 완료·승인 판정과의 경계

- 이미 completed인 마일스톤·목표를 다시 열지 않는다.
- 승인 포인터·시크릿·기존 완료 판정은 이 명세 범위 밖이다.
- 과거 데이터 정리(소진 문구 52건, blocked 목표 14개)는 구현과 별도 승인 작업이다. 비완료 46건은 마일스톤별로 실제 실행 근거를 확인한 뒤에만 다룬다.

## 7. 승인 필요 항목
