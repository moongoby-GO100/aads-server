## 1. 설계 원칙

1. **새 엔진을 만들지 않는다.** 실행·녹화·등록·승인·Vault·예약은 이미 있다. 이번 작업은 그 위에 "초안(draft)" 한 층과 사용자 카드를 얹는다.
2. **등록 계약은 그대로.** 결과 화면 확인(`screen_verified`) 없이 등록되는 경로를 만들지 않는다.
3. **비밀값은 Vault 밖으로 나오지 않는다.** 초안 테이블에는 자격증명 **id 참조만** 둔다.
4. **사용자 문장과 내부 상태를 분리한다.** 상태 머신은 내부 코드, 화면 문장은 표시 사전에서 만든다(FR-27 용어 숨김을 테스트로 강제).
5. **기존 경로 회귀 0.** `smart_browser list/run/register_e2e`, 오비스 녹화 API, `/browser-tasks` 는 손대지 않거나 하위 호환만 추가한다.

## 3. 전체 구조

```
 사용자(채팅/홈/오비스)
   │  "쿠팡이츠 어제 매출 받아줘, 매일 아침"
   ▼
 [대시보드] AutomationDraftCard (카드1·2·3·완료·실패)      ←── SSE (기존 채팅 스트림)
   │  REST /api/v1/automation-drafts/*
   ▼
 [aads-server] automation_draft_service  ── 상태 머신 (automation_drafts)
   │      ├─ intent_parser      : 문장 → {사이트, 할 일, 결과, 주기} (LLM 1회, call_llm_with_fallback)
   │      ├─ credential_linker  : 도메인 → agent_vault_credentials id / credential-requests 발급
   │      ├─ demo_runner        : 서버 레인 실행 + WorkRecipeRecorder 수집 + guard 멈춤
   │      ├─ fragment_splitter  : 단계 → 로그인/이동/조회 조각, 기존 승인 조각 재사용
   │      └─ approval_notifier  : 승인자 알림·재알림·만료
   ▼
 기존 work_recipe.registration → work_recipes (승인 후)  ──  scheduler(cron) → orchestrator.run_directive
```

LLM 호출 상한: 초안 1건당 의도 해석 1회 + 재시연 수정 최대 2회 = **3회**(R-AUTH: `call_llm_with_fallback` 만 사용).

## 4. 상태 머신

| 상태 | 뜻 (화면 문장) | 다음 상태 | 전이 조건 |
|---|---|---|---|
| `intent_draft` | 이렇게 이해했어요 | `intent_confirmed` / `cancelled` | 카드 1 [맞아요] |
| `intent_confirmed` | 로그인 연결 | `credential_ready` / `credential_waiting` | 저장된 로그인 매칭 또는 로그인 불필요 / 안전 입력 요청 발급 |
| `credential_waiting` | 로그인 정보를 기다리는 중 | `credential_ready` / `expired` | Vault 요청 `submitted` / 30분 경과 |
| `credential_ready` | 대신 해 보는 중 | `demonstrating` | 자동 |
| `demonstrating` | 대신 해 보는 중 | `result_review` / `paused_risk` / `failed` | 결과 도달 / 쓰기 단계 감지 / 실패·5분 초과 |
| `paused_risk` | 확인이 필요해요 | `demonstrating` / `result_review` / `cancelled` | 사용자 [진행] / [여기까지만] / [취소] |
| `result_review` | 이 결과가 맞나요? | `registering` / `revising` | [맞아요] / [아니에요] |
| `revising` | 다시 해 보는 중 | `demonstrating` / `manual_record` | 재시연(초안당 최대 2회) / [직접 보여줄게요] |
| `manual_record` | 직접 보여주세요 | `result_review` | 기존 녹화 finish |
| `registering` | 저장 중 | `pending_approval` / `active` | registration 생성 / 자동 승인 정책 해당 |
| `pending_approval` | 확인 기다리는 중 | `active` / `rejected` / `expired` | 승인 / 반려 / 14일 |
| `active` | 사용 가능 | `broken` / `paused` | 실행 실패 분류 / 사용자 멈춤 |
| `failed` | 실패 (원인별 문장) | `credential_ready` / `demonstrating` / `cancelled` | 복구 버튼 |

규칙: 전이는 `automation_draft_service.transition(draft_id, from, to, actor, reason)` 한 곳에서만. `from` 이 현재 상태와 다르면 409(동시 클릭·중복 탭 방지).

## 5. 데이터

새 마이그레이션 `migrations/20261014_automation_drafts.sql` (멱등, `IF NOT EXISTS`):

```sql
CREATE TABLE IF NOT EXISTS automation_drafts (
  id              uuid PRIMARY KEY DEFAULT gen_random_uuid(),
  tenant_id       uuid NOT NULL,
  owner_user      text NOT NULL,              -- 요청자 (채팅 세션이 아니라 사람)
  session_id      uuid,                       -- 시작한 채팅 세션 (없을 수 있음: 홈 버튼)
  title           text NOT NULL,              -- 화면 이름 "쿠팡이츠 어제 매출 받기"
  intent_text     text NOT NULL,              -- 사용자가 쓴 원문
  intent          jsonb NOT NULL DEFAULT '{}',-- {site_name, url, domain, task, output, schedule}
  aliases         text[] NOT NULL DEFAULT '{}', -- 반복 사용 매칭 문구 ("어제 매출", "배달 매출")
  state           text NOT NULL,
  credential_id   uuid,                       -- agent_vault_credentials.id 참조만. 비밀값 금지
  credential_request_id uuid,                 -- 안전 입력 요청 id
  lane            text NOT NULL DEFAULT 'server', -- server | pc
  max_risk        text,                       -- schema.RISK_LEVELS
  demo_attempts   int  NOT NULL DEFAULT 0,
  recording_ref   jsonb NOT NULL DEFAULT '{}',-- 수집 단계(비밀값은 {{secret.*}} 참조로만)
  evidence        jsonb NOT NULL DEFAULT '{}',-- {final_screenshot_url, preview_rows(≤5), screen_verified}
  registration_ids uuid[] NOT NULL DEFAULT '{}',
  recipe_names    text[] NOT NULL DEFAULT '{}',
  schedule_job_id text,
  failure_code    text,                       -- auth_failed|challenge|blocked|layout_changed|empty_result|transient
  created_at      timestamptz NOT NULL DEFAULT now(),
  updated_at      timestamptz NOT NULL DEFAULT now()
);
CREATE INDEX IF NOT EXISTS automation_drafts_tenant_state ON automation_drafts (tenant_id, state, updated_at DESC);

CREATE TABLE IF NOT EXISTS automation_draft_events (
  id          bigserial PRIMARY KEY,
  draft_id    uuid NOT NULL REFERENCES automation_drafts(id) ON DELETE CASCADE,
  event_type  text NOT NULL,   -- PRD 8절 목록
  from_state  text,
  to_state    text,
  actor       text,
  detail      jsonb NOT NULL DEFAULT '{}', -- 비밀값 금지 (저장 전 마스킹 검사)
  created_at  timestamptz NOT NULL DEFAULT now()
);
```

- 롤백: 두 테이블은 신규라 `DROP` 대신 기능 플래그 `AUTOMATION_DRAFTS_ENABLED=false` 로 입구만 닫는다(R: DROP 금지).
- `aliases` 는 `resolve_recipe` 확장에 쓴다(7절).

## 6. API

모두 테넌트 인증, 응답에 `card` (화면 문장·버튼 목록)를 함께 돌려 프론트가 문장을 만들지 않게 한다.

| 메서드 | 경로 | 요청 | 결과 |
|---|---|---|---|
| POST | `/api/v1/automation-drafts` | `{intent_text, session_id?}` | 초안 + 카드 1 |
| PATCH | `/api/v1/automation-drafts/{id}/intent` | `{site?, task?, output?, schedule?}` | 카드 1 갱신 |
| POST | `/api/v1/automation-drafts/{id}/confirm-intent` | `{expected_state}` | 카드 2 또는 진행 화면 |
| POST | `/api/v1/automation-drafts/{id}/credential` | `{credential_id}` 또는 `{request_new:true}` | 진행 화면 또는 안전 입력 카드(`requestId`) |
| POST | `/api/v1/automation-drafts/{id}/demo` | `{expected_state}` | `202` + 진행은 SSE `automation_draft.progress` |
| POST | `/api/v1/automation-drafts/{id}/risk-decision` | `{decision: proceed\|stop_here\|cancel}` | 진행 계속/결과 확인 |
| POST | `/api/v1/automation-drafts/{id}/review` | `{ok: bool, reason_code?, note?}` | 등록 진행 / 재시연 |
| POST | `/api/v1/automation-drafts/{id}/manual-record` | — | 기존 녹화 시작(`recording_id`) |
| POST | `/api/v1/automation-drafts/{id}/schedule` | `{kind: once\|daily\|weekdays\|weekly, hour, minute, day_of_week?}` | 예약 id |
| GET | `/api/v1/automation-drafts/{id}` | — | 현재 상태 + 카드 (앱 재실행 복구) |
| GET | `/api/v1/automations` | `?status=` | 통합 목록 (`work_recipes`+`ovis_recipes`+`browser_recipes` 조회 뷰 + 초안) |
| POST | `/api/v1/automations/{key}/run` | — | 즉시 실행 |
| POST | `/api/v1/automations/{key}/pause` · `/resume` | — | 예약 멈춤/재개 |

에이전트용 도구 `automation_draft`(action=start/confirm/credential/demo/review/status)도 같은 서비스를 부른다. 채팅에서 대표님이 기존 `smart_browser` 를 부르는 경로는 그대로 둔다.

## 7. 핵심 로직

### 7.1 의도 해석 (intent_parser)
- 입력 문장 → `{site_name, url, task, output_kind(table|file|screen), schedule}` JSON. LLM 1회.
- 도메인 후보: ① 문장 안 URL ② 기존 `work_recipes.domain` 이름 사전(예: 쿠팡이츠→store.coupangeats.com) ③ LLM 제안. ③만 있으면 카드 1에서 사용자가 반드시 확인.
- 주기 문장("매일 아침") → 기본 09:00 KST, 카드 1에서 수정.

### 7.2 로그인 연결 (credential_linker)
- `agent_vault_credentials` 를 도메인으로 조회 → 1개면 표시명만 보여 주고 [이 계정으로]. 2개 이상이면 고르기.
- 목록 필터 미매칭을 Vault 전체 부재로 단정하지 않는다(서브도메인·로그인 도메인 차이 고려: `store.` / `login.`).
- 없으면 `/agent-vault/credential-requests` 발급 → 채팅에 `VaultCredentialCard` 삽입. 30분 미제출 시 `expired`.

### 7.3 대신 시연 (demo_runner)
- 서버 레인으로 실행하고 `WorkRecipeRecorder` 로 단계를 모은다. 비밀번호 칸은 `{{secret.password}}` 참조로 기록, 화면 캡처 전 입력칸 마스킹.
- 단계 계획은 의도 + 기존 같은 도메인 레시피(있으면)에서 시작한다. 처음 보는 사이트는 페이지 스냅샷 기반 탐색(기존 브라우저 도구 사용), 단계 수 상한 25.
- 매 단계 실행 **전** guard 판정: `WRITE_EXTERNAL` 이상이면 `paused_risk` 로 멈춤. 사용자 [진행]은 시연 중에만 유효하고, 등록 후 실행에는 여전히 승인 게이트가 걸린다.
- 진행 이벤트를 사용자 문장으로 변환: `navigate`→"○○ 화면으로 가는 중", `fill`(로그인)→"로그인하는 중", `click`→"'매출' 메뉴를 누르는 중", `download`→"파일을 받는 중".
- 실패 분류: 로그인 후 URL 이 로그인 페이지로 되돌아옴 → `auth_failed`; CAPTCHA·OTP 신호 → `challenge`; 403·Access Denied → `blocked`; 셀렉터 못 찾음 → `layout_changed`; 결과 0행 → `empty_result`; 네트워크·타임아웃 → `transient`(자동 1회 재시도).
- 로그인 반복 제출 금지: `auth_failed`·`challenge` 후에는 재시도하지 않는다.

### 7.4 결과 확인과 등록 (fragment_splitter)
- [맞아요] → `evidence.screen_verified=true`, 최종 캡처 URL, 미리보기 ≤5행.
- 단계 분할: 첫 로그인 제출 성공 지점까지 = 로그인 조각, 목적 화면 도달까지 = 이동 조각, 이후 = 조회 조각. 조각 이름은 `{domain_slug}_{nn}_{purpose}` (기존 `coupangeats_01_open_login` 규칙과 같음).
- 재사용: 같은 도메인·같은 credential 의 승인된 로그인 조각이 있으면 그 이름·버전을 선행 조각으로 연결하고 새로 등록하지 않는다(AC-06).
- 각 조각을 `registration.request_registration(..., requested_by=owner_user)` 로 등록. `requested_by` 에 채팅 세션 id 가 아니라 **사람**을 넣어 지표(대표님 외 사용자 수)를 셀 수 있게 한다.

### 7.5 반복 사용 매칭 (`resolve_recipe` 확장)
- 현재: 지시에 도메인 또는 정확한 레시피 이름이 있어야 매칭.
- 확장: 승인된 자동화의 `title` · `aliases` 와 지시를 비교(정규화 후 부분 일치 + 날짜어 제거). 후보 1개 → 실행, 2개 이상 → 고르기 카드, 0개 → "새 자동화로 만들까요?".
- 기존 도메인·이름 매칭 우선순위는 유지(회귀 방지 테스트).

### 7.6 승인 알림 (approval_notifier)
- registration `pending` 생성 시: 홈 배지 카운트 + 인박스 항목 + 텔레그램 1건(기존 `send_telegram`/`notify_channel` 경로).
- 스케줄러 매시: 48시간 경과 & 재알림 0회 → 재알림 1회. 14일 경과 → 초안 `expired` (registration 은 그대로, 요청자 [다시 요청]).
- 자동 승인(정책 D1, 기능 플래그 `AUTOMATION_AUTO_APPROVE_READ`): `max_risk=READ` 이고 같은 도메인 승인 이력이 있을 때만 `decide_registration(decision='approve', decided_by='policy:read_same_domain')`.

### 7.7 예약
- `ceo_chat_tools_scheduler` 의 cron(KST)으로 `orchestrator.run_directive(title)` 를 호출. 승인 전이면 예약을 만들되 비활성, 승인 시 활성.
