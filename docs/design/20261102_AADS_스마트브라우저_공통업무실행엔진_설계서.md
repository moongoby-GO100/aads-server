## 1. 결정과 재사용 경계
독립 브라우저를 새로 만드는 대신 공통 ApplicationService를 기존 WorkRecipe/BrowserTask/PC queue 위에 둔다. 신규 영속 실행 원장은 업무 의도를 관리하고, 기존 browser_tasks는 화면·승인·이벤트 표현을 담당한다. 서로의 상태를 별도로 바꿔 두 개의 진실을 만들지 않는다.

| 기존 경로 | 재사용 | 보강 |
|---|---|---|
| app/services/work_recipe/schema.py, player.py, executor.py | 승인 레시피·12종 동작·verify·secret 입력 | 승인 hash 고정, checkpoint 변수 복원, effect journal, 결과 staging |
| browser_task_gateway.py / browser_permission_policy.py | browser_tasks·화면·기존 승인 token | 실행 ID 연결, project scope 재검사, 일관된 event projection |
| pc_agent_collection_queue.py | owner_instance/owner_epoch PC queue | execution lease와 장치 자원 lease 동시 검증 |
| collection_dataset_store.py / api/collection_datasets.py | dataset/run/record 모델 | project/read scope, 단일 실행 commit, content hash·cursor |
| browser_recipe_recovery.py / smart_browser_learning.py | 실패 분류·화면 변화·후보 | 후보 별도 보관, 제한 시험·승격 승인 |
| 기존 scheduler·tool executor·dashboard | 예약·MCP·채팅 카드·브라우저 화면 | 같은 서비스 호출과 중단 복구 UX |

조회한 player는 resume_checkpoint 이전 step을 건너뛰며 변수 복원 보장이 없다. collection upsert는 step별 transaction이고 마지막 관측시간 기반 API다. 따라서 기존 코드를 보존하되 신규 경로에서 이 결함을 해결한다. 금융·BANKING 업무를 신규 엔진으로 자동 이전하지 않는다.

## 2. 구성과 파일 소유권
논리 흐름: MCP/REST/SDK/예약 → 인증 ContextFactory → WorkEngineService → PostgreSQL 상태/dispatch outbox → worker → WorkRecipeAdapter → 기존 Playwright/PC adapter → 후조건·artifact → checkpoint/수집 commit → event stream/UI.

신규 제안 패키지 app/services/smart_browser_engine/:
- contracts.py: Request/Ticket/Result/Error/Observation/ActionPlan/Checkpoint DTO와 contract_version=1.
- context.py, policy.py: 신뢰된 principal·tenant·project·scope 해석. request body를 인증 근거로 쓰지 않음.
- repository.py, leases.py: 트랜잭션·멱등 요청·epoch·자원 소유권·event_seq.
- service.py: submit/get/list/pause/resume/cancel/result. 모든 입구 공통.
- worker.py, adapters.py: 실제 dispatch, 기존 player 호출, PC queue binding.
- effects.py, checkpoints.py: 부작용 journal, 재개·대사.
- collection.py, scheduler.py: staging·원자 공개·예약 중복 조정.
- observation.py, planner.py, recovery.py, crawler.py: 관측·제한된 계획·후보·읽기 수집.
- app/api/smart_browser_executions.py: /api/v1/smart-browser/executions.
- sdk/python/aads_smart_browser/: 원격 SDK; app 내부 모듈과 이름/의존 분리.
구현 시 동등한 기존 모듈이 있으면 해당 모듈을 확장하고 매핑을 specs에 남긴다. 신규 분산 큐/별도 승인 체계를 만들지 않는다.

## 3. 인증·공유·승인
ExecutionContext는 tenant_id, project_key, principal_id/type(user|service), scopes, recipe_allowlist, dataset_allowlist, origin_session_id, trace_id를 갖는다. 외부 입력으로 구성하지 않고 현재 사용자 membership/project grant 또는 검증된 service principal로 생성한다.
- 작업 실행 execute, 상태/결과/이벤트/파일 read, 예약 schedule, 취소/재개 control을 각각 검사한다. 빈 allowlist는 전체 허용이 아니라 거부다.
- 다른 세션에서도 같은 권한이면 조회·재사용 가능. origin_session_id는 감사 필드이며 실행 소유권이나 권한을 부여하지 않는다.
- 같은 tenant의 project 간 공유는 명시 share grant(대상 project·recipe/dataset·read/execute 범위)만. 기본은 project 격리. tenant 간 공유는 제공하지 않는다.
- 레시피 버전/hash·credential_scope·origin·lane·device·action 요약을 고정한다. 입력이 selector, domain, credential scope, risk를 덮어쓸 수 없다.
- 기존 승인 token을 사용하되 승인과 실제 effect intent를 한 번 연결한다. 승인 token을 consume한 뒤 crash해도 다른 동작에 재사용하지 않는다.
- 결과 cache 조회보다 권한 재검사를 먼저 한다. revoke/만료 시 이미 발급한 execution_id·artifact_ref도 접근 불가.
- 서비스 인증은 기존 제한된 인증 체계를 우선 재사용한다. 없다면 hash만 저장하는 만료/폐기 가능한 scoped credential 어댑터와 관리 경로를 구현하되 실제 운영 키 발급·secret 설정은 수행하지 않는다. 사용자 토큰·monitor key를 외부 프로그램에 나눠 주지 않는다.
- secret은 Vault reference만 영속 저장. 실제 입력은 실행 직전 resolve, 로그·checkpoint·artifact에 평문 금지. DOM/화면/다운로드 내용도 비신뢰 관측이며 계획 권한을 바꾸지 못한다.

## 4. 영속 모델과 제약
실제 기존 스키마를 조사한 뒤 additive migration을 작성한다. 이름은 다음 계약을 기본으로 하되 중복 테이블이면 기존 모델을 확장한다.

| 모델 | 필수 필드 | 제약 |
|---|---|---|
| sb_executions | id, tenant_id, project_key, principal_id, request_hash, recipe_id/version/hash, inputs_safe, credential_refs, lane/device/resource_key, status/reason, owner_instance/epoch, lease_expires_at, event_seq, cancel_requested, limits, result_ref, timestamps | scope 포함 조회; terminal 역전 금지 |
| sb_execution_requests | tenant/project/principal/idempotency_key, request_hash, execution_id, created_at | UNIQUE(scope, principal, key); 같은 key+다른 hash 409 |
| sb_attempts | execution_id, attempt_no, owner_instance/epoch, started/finished, reason | UNIQUE(execution, attempt_no); claim 대기는 attempt 증가 안 함 |
| sb_step_journal | execution_id, step_id, recipe_hash, command_id, effect_class, state, payload_hash, approval_ref, observation_ref, result_ref, owner_epoch | UNIQUE(execution, step_id, effect_generation); command_id 중복 금지 |
| sb_checkpoints | execution_id, seq, recipe_hash, verified_step, safe_values/artifact_refs, context_fingerprint, postconditions, evidence_ref, created_at | 검증 완료 단계만; checkpoint 원문 불변 |
| sb_execution_events | execution_id, event_seq, type, safe_payload, created_at | UNIQUE(execution,event_seq), 실행 상태와 같은 transaction |
| sb_dispatch_outbox | id, execution_id, expected_epoch, command_id, state, payload_ref, next_at | state 변경과 원자 기록; 중복 delivery 허용·중복 effect 금지 |
| collection_run_staging | execution_id, dataset_id, record_key, fields, content_hash, source_order | 공개 API 조회 제외; 바이트/행 상한 |
| collection_changes | dataset_id, change_seq, record_key, operation, content_hash, fields snapshot, run_id | UNIQUE(dataset,seq), append-only feed |

browser_task_id는 execution과 연결한다. 현재 browser gateway token/task FK를 유지한다. run은 여러 attempt를 가지며 resume으로 새 execution을 만들지 않는다. 새 요청으로 retry할 때만 새 execution_id를 발급하고 parent_id를 남긴다.

원하는 중복 병합은 별도 resource_key + semantic request fingerprint로 제한한다. 단지 같은 사이트라는 이유로 다른 입력·계정 업무를 합치지 않는다. dataset 실행은 진행 중 UNIQUE active binding 또는 DB row lock으로 원자 병합한다. 일반 실행은 idempotency key로 중복 제거하고 서로 다른 key는 정책상 같은 업무일 때만 병합한다.

lease 기본값(시험 시작값): TTL 30초, heartbeat 10초, 만료 후 재개 가능 판정 60초 이내. 관리자 설정은 유효 범위 검증; 측정 성과 아님. event_seq는 실행 row를 잠근 상태에서 증가시킨다. 브라우저 대기 동안 DB connection/transaction을 점유하지 않는다.

## 5. 상태 머신·부작용·재개
상태: queued → running → succeeded|partial|failed|cancelled. running에서 waiting_auth/waiting_approval/waiting_device/paused/needs_reconciliation으로 전이 가능. waiting/paused는 조건 충족 시 queued로 재진입하며 같은 execution을 유지한다. terminal 상태를 resume하지 않는다. needs_reconciliation은 결과 대사 없이 queued로 전이할 수 없다.

claim: FOR UPDATE SKIP LOCKED → owner_epoch 증가·lease 갱신·attempt 원장. 모든 heartbeat/state/event/checkpoint/dataset commit은 owner_instance+epoch+미만료 lease 조건 UPDATE RETURNING을 확인한다. 실패하면 stale_owner이고 후속 effect를 보내지 않는다.

실행 한 단계:
1. 현재 권한·정지 여부·레시피 hash·자원 lease·페이지 시작 조건 확인.
2. risk classifier와 기존 승인 token 검증. READ 표기만으로 click/api_call을 무조건 안전 분류하지 않는다.
3. effect intent와 dispatch outbox를 transaction으로 저장. command_id, payload_hash, 승인 참조를 고정.
4. 최종 어댑터가 현재 fence·device/session/foreground를 다시 검증하고 durable command receipt를 취득한 뒤 동작. 같은 command_id는 이미 dispatch 중/완료이면 재전송해 실행하지 않음.
5. 후조건을 읽기로 확인하고 evidence를 남긴 뒤 journal verified, checkpoint, event를 원자 commit.
6. 화면 변화/인증 만료/불명 결과는 해당 waiting 또는 reconciliation 상태로 전환.

DB fencing만으로 이미 외부 서버에 전달된 요청을 취소할 수 없다는 한계를 명시한다. fence 확인과 effect 사이 race도 DB만으로 exactly-once라 주장하지 않는다. PC/브라우저 command gateway의 durable receipt와 자원 잠금, 미확정 command 대사를 함께 사용한다. 새 worker는 dispatched/unknown intent를 발견하면 READ라도 실제 effect_class에 따라 대사하며 외부 쓰기는 자동 재실행 0회다.

journal 상태: prepared → dispatching → acknowledged → verified, 또는 unknown/rejected. crash가 dispatching 이후 발생했으면 provider transaction ID·사이트 결과 조회·승인된 후조건으로 수행 여부를 확인한다. 확인 불가면 needs_reconciliation + 사용자 조치. 명시적 사람 결정은 evidence와 함께 별도 감사 이벤트로 보존한다.

재개 검증: recipe hash·credential scope·lane/device·입력 hash와 checkpoint를 비교, 비민감 save_as 값/권한 artifact를 복원, secret은 다시 resolve. 시작 URL/인증/후조건이 유효할 때만 다음 단계. 기기 변경은 별도 요청·권한 검사·새 인증이며 쿠키를 자동 복사하지 않는다. 중지 요청은 다음 dispatch를 막고 이미 진행 중인 effect는 결과 확정 또는 reconciliation까지 기록한다.

## 6. 수집·커서·크롤링
기존 extract/paginate를 다시 만들지 않는다. 새 경로는 step별 upsert 대신 전체 execution의 staging에 저장하고 최종 verify 후 공개한다.
- 필드 schema v1: name, type(text/int/decimal/bool/date/datetime), required, key, nullable, normalize. key 필드 순서/타입 schema는 dataset 생성 후 불변.
- 변환 → 필수/key 검사 → 민감정보 검사 → canonical key → 중복 판정. 필수 실패는 행 제외+사유, 선택 실패는 null+사유.
- key encoding은 필드명·명시 타입·정규값 배열의 UTF-8 canonical JSON hash. 문자열 NFC, 숫자 유한 Decimal, datetime timezone 필수/UTC, bool과 int를 구별. 구분자 연결을 쓰지 않는다.
- 같은 key에 다른 내용이면 source_order 첫 유효 행을 보존하고 collision 수 집계. 무조건 마지막 값으로 덮어쓰지 않는다.
- no_records는 raw_rows=0, errors=0, 제한 미도달, 명시된 empty_marker 확인일 때만. empty_marker={selector, text?, match:exact|contains}로 CSS와 문구를 구분한다. 행이 있지만 모두 탈락한 것은 실패다.
- 기본 reject 비율 >5%면 전체 실패. 5% 경계는 분모 raw_rows와 rejected_rows를 사용한다. no_records는 분모 0을 별도로 취급.
- 모든 대상 dataset을 정렬한 순서로 transaction lock → 최신 fence 검사 → stage merge → 변경 feed와 run summary → checkpoint/terminal 공개. 여러 페이지/추출 단계 중 하나 실패하면 public records 변경 0.
- 메모리 상한: 페이지별 staging 500행 batch, 총 10,000행/20MiB 정규화 데이터, 페이지 100개/depth 3, crawl URL 1,000개, 전체 10분을 초기 테스트 기본값으로 둔다. 상한 도달은 partial(reason=limit_reached), allow_partial=false 기본이면 공개하지 않는다. batch 수치는 성능 실측이 아니다. 큰 blob은 artifact 참조. byte quota는 요청 전에/수신 중/저장 직전 검사한다.
- content_hash는 관측시각을 제외한 정규 fields에서 계산. 변경 없는 수집은 last_seen만 갱신, change_seq 증가 없음. 신규/변경은 dataset row counter를 같은 transaction에서 증가시키므로 commit 순서와 cursor가 어긋나지 않는다.
- 변경 feed는 snapshot payload를 남긴다. current records만 join해 과거 seq에 미래 값을 반환하지 않는다.
- cursor는 tenant/project/dataset/filter/schema_version/high_watermark/last_seq를 인증한 opaque token이다. 최초 조회 때 high watermark 고정, seq > last AND seq <= high로 keyset pagination. 이후 새 poll은 새 watermark. 다른 dataset/권한 cursor 거부.
- full snapshot과 change feed 분리. 보관 만료로 cursor 아래 이력이 없으면 410 cursor_expired/gap=true와 full_snapshot 복구 경로. current-record snapshot은 DB snapshot 또는 immutable export manifest로 일관성 보장.
- 크롤링: 허용 origin/path, robots 정책 확인, URL 정규화/fragment 제거/중복 제거, redirect 매 hop 및 최종 연결 IP 검사, private/loopback/link-local/metadata/IPv6 mapped 우회 차단. 내부 시스템은 별도 승인된 adapter. robots 미확인 시 unrestricted로 간주하지 않는다. 로그인·CAPTCHA·Access Denied에서 우회 반복 금지.
- HTML 지시문·숨은 prompt·클립보드 지시는 관측 데이터이며 추가 domain/secret/외부 전송을 허용하지 않는다.

## 7. REST·MCP·SDK 계약
모든 입구는 service의 동일 DTO를 사용하며 자체 권한/저장 로직을 중복 구현하지 않는다.

| 메서드/경로 | 계약 | 권한 |
|---|---|---|
| POST /smart-browser/executions | recipe_ref 또는 task_intent, inputs, location, limits, idempotency key. 202 ticket; 병합은 merged=true | execute |
| GET /smart-browser/executions 및 /{id} | project 허용범위 목록/상태. 없는 권한의 resource는 존재 은닉 | read |
| GET /{id}/events?after=N | durable event_seq 이후 SSE/JSON. Last-Event-ID 지원, gap이면 snapshot 후 재연결 | read |
| POST /{id}/pause,resume,cancel | expected_event_seq, reason, command idempotency key. 충돌 409. resume 대사 검증 | control |
| GET /{id}/result | 상태+result_ref+evidence. 실패는 빈 성공 배열로 위장하지 않음 | read |
| GET /collection-datasets/{key}/changes 및 /snapshot | cursor, limit 기본500/최대1000, next_cursor, high_watermark, gap | read + dataset allowlist |
| POST /collection-datasets/{key}/run,schedule | 공통 submit, cron/timezone, overlap 정책. 자동 활성화 금지 | execute/schedule |
| GET /artifacts/{id} 또는 기존 동등 endpoint | tenant/project/read 재검사, 짧은 수명 다운로드 | read |

요청 예: {"contract_version":1,"recipe_ref":{"id":"uuid","version":"1.0.0","hash":"sha256"},"inputs":{"period":"2026-10"},"location":{"lane":"server","device_id":null},"limits":{"max_pages":20}}
Idempotency-Key는 헤더 또는 MCP/SDK 인자, secret 참조값은 credential_refs 계약으로만. 인증 tenant/project는 서버가 결정하되 user가 선택한 project selector를 grant에 대조한다. request_hash는 semantic 입력+버전+location+limit을 정규화해 계산한다.

ticket 예: {"contract_version":1,"execution_id":"uuid","request_id":"uuid","status":"queued","merged":false,"next_event_cursor":0,"trace_id":"uuid"}
error 예: {"error":{"code":"needs_reconciliation","message":"이전 동작 결과를 확인해야 합니다","retryable":false,"retry_after":null,"next_action":"inspect_result"},"execution_id":"uuid"}

MCP: smart_browser_run/status/resume/cancel/result, collection_dataset_list/records/changes. 기존 smart_browser 도구와의 naming 충돌은 tool registry에서 확인하고 alias로 호환한다. 임의 session_id 입력으로 다른 세션 권한을 얻지 못한다.
Python 내부 모듈: await WorkEngineService.submit(context, request).
원격 SDK: AsyncSmartBrowserClient(base_url, credential_provider, project).submit/get/wait/events/pause/resume/cancel/result/changes. SDK는 DB·app import 없이 설치 가능. 네트워크 timeout 후 submit 재전송은 같은 key만, mutating 요청을 새 key로 자동 재시도 금지. wait timeout은 실행 취소와 다르다. TLS 검증 기본 ON. 429/503은 제한 backoff+jitter/Retry-After, 401/403/409는 자동 반복 금지.
공개 artifact CSV는 =,+,-,@와 제어문자 기반 수식 주입 방어. 파일명/path traversal·raw HTML 노출 금지. 원본과 안전 export는 별도 참조.

## 8. 관측·계획·복구
Observation v1: origin,url,document_revision,tab/frame refs, DOM/AX 요약, screenshot_ref, visible controls와 안정 target_ref, page_state(auth/captcha/access_blocked/ready), timestamp, redaction manifest.
Planner output은 action 후보 하나 또는 bounded plan, 목표 후조건, evidence ref, risk, confidence가 있는 schema다. schema 오류·모호한 target·새 domain·승인 범위 변화는 dispatch 전 차단.
실행 순서: 승인 레시피→의미 locator(role/name/label/test-id)→DOM/AX 후보→필요할 때 이미지 관측. 관측 이후 page_revision이 바뀌면 좌표를 재사용하지 않고 재관측한다. PC는 device/session/foreground/URL 일치 후 1회 물리 클릭하고 재관측.
기본 budget: 50개 action, 10분, LLM 8회, 동일 selector 복구 후보 최대2회, READ 일시오류 재시도2회. 쓰기/인증 제출의 불명 결과 재시도0회. 비용 상한 설정 시 중앙 usage 합산; 측정 불가면 미측정으로 표시하고 무제한 루프 허용 안 함.
LLM 호출은 기존 중앙 라우터/정책을 사용한다. 외부 LLM 직접 API, ANTHROPIC_API_KEY 직결 금지. fallback에도 동일 ActionPlan validator와 permission gate.
복구 후보는 기존 approved hash를 바꾸지 않는 새 revision/draft. fixture와 사이트별 계약 검사 후에만 승인 요청. 실제 화면 성공 전 register_e2e 금지. 실패 후보는 원본 레시피와 예약을 변경하지 않는다.
Coupang/Coupang Eats 로그인은 기존 submit_mode/login_contract와 Vault scope를 유지. 마우스 클릭은 해당 계정·사이트·device 시작 조건 확인 후 1회. 서버 성공을 PC 성공으로 기록하지 않는다.

## 9. 사용자 화면과 오류 복구
기존 dashboard 스마트브라우저/자동화 route를 source 탐색 후 확장한다. 첫 화면: 업무 입력, 실행 중 업무, 지난 결과. Settings는 계정/장치/권한/관리자 한도. 내부 ID는 상세 진단에만.
- 첫 실행: 업무 입력→계정·실행 위치 요약→권한 확인/필요한 승인→실행 카드→결과 표/파일/화면→반복 실행 제안.
- 반복: 승인 recipe 검색, 최근 input 복원, 이번 대상 확인, ticket 반환. 예약과 수동 실행이 겹치면 “이미 진행 중인 업무 보기”.
- 복구: 원인+마지막 성공 단계+화면 evidence+한 개의 주 CTA. auth→다시 로그인, device→연결 확인, approval→검토, reconciliation→결과 확인, transient→이어하기.
- SSE reconnect는 snapshot과 event_seq 대조. React state보다 서버 snapshot 우선, event 중복/역순 무시, reload/session change 후 복원.
- 모바일 390x844/최소360px·PC1920x911, keyboard/focus, 스크린리더 상태 안내, 큰 터치 영역. 승인 대기/실패를 색만으로 표현하지 않음.
- API schema/feature가 준비되지 않으면 사용 불가 원인만 표시하고 가짜 성공/자동 fallback 실행 금지.
모든 화면 변경은 실제 캡처와 route·login 사용 여부·console/network 오류를 기록. mock backend E2E는 운영 인수와 구분한다.

## 11. 관측·배포·롤백
trace_id→execution→attempt→command→artifact 연결. latency는 queue/action/LLM/사용자대기/commit 분리, 비용은 provider usage 존재 시만 계산, 측정 없음은 null. unknown effect·stale owner 거부·권한 위반·duplicate dispatch·cursor gap·staging bytes를 계측한다. P0는 권한 유출/중복 외부 쓰기/secret 노출, P1은 실행 상실·잘못된 성공·복구 불가.
신규 schema readiness 검사와 feature flag 기본 off. migration 파일은 approve manifest에 포함하고 실제 운영 적용은 별도 승인. 앱 시작 시 자동 ALTER 금지.
운영 릴리스는 clean committed/pushed SHA→승인 migration→SHA당 단일 image→candidate --no-build→health→짧은 nginx lock/cutover→routed health 실패 즉시 rollback→same digest standby→5분 P0/P1 감시. deploy.sh의 drain/DB fence 정책 준수.
롤백: 신규 submit 진입 중지→실행 drain/reconciliation 보존→이전 route/image→additive 테이블 보존. DROP/TRUNCATE/감사 삭제나 active API 직접 restart 금지.
도입 완료는 실제 migration·API·서로 다른 세션/SDK·화면·사이트 후조건까지. push_only 완료를 운영 완료로 바꾸어 보고하지 않는다.

## 12. 문서 및 완료 증거
기획·PRD·설계는 같은 document_key에서 새 판본 관리, 승인 상태 직접 변경 금지. D0가 이 정본 본문을 지정 파일로 그대로 mirror하고 sha256를 대조한다. 구현 변경이 계약을 바꾸면 새 판본과 호환성 영향표를 등록한다.
최종 traceability는 FR/AC별 implementation_path, test_name, command, exit_code, artifact_ref, tested_sha, environment, status(pass/fail/not_run), not_run_reason을 가진다.
Aside 직접 비교는 oby-ceo의 실제 AI 응답 가능 상태와 초기 조건부터 기록한다. 이번 문서는 Aside 실행·우월성 검증 완료가 아니다. 정답 fixture 성과와 실사이트/PC 성과를 분리한다.
핸드오버는 AADS/project_handover_entries에 runner:<job_id> 또는 안정 entry_key로 저장·재조회. HANDOVER.md는 수정하지 않는다.
