# 러너 재시작 시 작업 이어가기 기획

- document_key: `aads-runner-resume-interrupted-job-plan`
- 종류: 기획(plan) · 상태: 초안 · 작성: 2026-11-04 KST
- 관련: `aads-runner-pool-relay-distribution-execution-plan`(러너 풀)

## 1. 문제

러너를 재시작하면(릴리스·설정 반영·장애) 실행 중 작업은 사라지지 않고 대기열로 돌아간다. 하지만 **처음부터 다시** 한다.

- 코드: 다시 시작할 때 `/tmp/aads-wt-<작업ID>` 가 있으면 지우고 origin/main 에서 새 작업 폴더를 만든다(`WORKTREE_CLEAN ... base=origin/main`). AI(Claude CLI)도 새 대화로 시작한다.
- 2026-11-04 실측:
  - contabo42 재시작으로 되돌아간 `runner-9b48ed0c` 가 빈 폴더에서 다시 시작했다.
  - 116 릴리스 때 실행 중이던 3건이 모두 처음부터 다시 시작했다.
- 최근 30일 재시작 재대기: **작업 11건(13회)** — AADS 7, GO100 4. 같은 기간 `process_died`·`timeout_max_runtime` 로 끝난 작업이 15건 더 있다.
- 비용: 되돌아간 작업마다 그때까지의 AI 작업 시간·토큰을 다시 쓴다. 러너 풀(여러 서버)이 되면서 재시작·이동이 늘어날 수 있다.

## 2. 목표

| ID | 목표 | 기준 |
|---|---|---|
| R1 | 재시작으로 되돌아간 작업이 **이전 변경분 위에서** 다시 시작 | 재개된 작업의 첫 단계에 이전 diff 가 적용돼 있음 |
| R2 | 다른 서버가 이어받아도 동작(러너 풀) | 116 에서 멈춘 작업을 42 가 이어받아 재개 |
| R3 | 안전: 이어받은 변경도 기존과 똑같이 테스트·AI 검수를 통과해야 함 | 검수·승인 경로 무변경 |
| R4 | 실패하면 지금처럼 처음부터 | 재개 실패 시 자동 폴백, 사유 기록 |

## 3. 설계

### 3.1 멈출 때 — 진행분 저장

러너가 종료 신호를 받아 작업을 대기열로 돌리는 지점(`cleanup` 의 shutdown requeue)에서, 작업 폴더에 변경이 있으면 저장한다.

1. `git -C <작업폴더> add -A` 후 diff 를 만든다. 대상은 추적·미추적 파일 모두이고, 러너 산출물(`.runner_full_diff.patch`·`RESULT-*.md`)은 뺀다.
2. 저장 위치는 **DB**: 새 테이블 `pipeline_job_checkpoints`(job_id, base_sha, patch, patch_sha256, files, bytes, model, attempt, host, created_at).
   - 모든 러너 서버가 같은 DB 를 보므로 다른 서버가 이어받을 수 있다(R2).
   - 크기 상한(예: 2MB)을 넘으면 저장하지 않고 처음부터로 폴백한다.
3. 기존 `[RUNNER_SHUTDOWN_REQUEUE]` 표시에 `checkpoint=<id>` 를 함께 남긴다.
4. 종료 시간 안에 끝나도록 저장 단계에 시간 상한(예: 10초)을 둔다. 넘으면 저장 없이 재대기한다.

### 3.2 다시 시작할 때 — 이어받기

작업 폴더를 만드는 단계(`WORKTREE_CLEAN` 직전)에서 그 작업의 최신 체크포인트가 있으면 다음 순서로 이어받는다.

1. 체크포인트의 `base_sha` 로 작업 폴더를 만든다. 원래 시작했던 기준이므로 diff 가 깨끗하게 적용된다.
2. `git apply --index` 로 diff 를 적용하고, sha256 이 일치하는지 확인한다.
3. origin/main 이 그사이 많이 앞섰으면 기존 stale_base 처리(겹치지 않으면 새 기준으로 옮겨 붙이기)에 맡긴다. 이 경로는 지금도 승인 단계에서 쓰인다.
4. AI 에게 주는 지시 앞에 **"이전 시도에서 아래 파일을 이미 수정했다. 이어서 완료하라"** 와 변경 파일 목록·요약 diff 를 붙인다. AI 대화 자체는 새로 시작하지만 작업 결과는 이어받는다.
   - Claude CLI 의 세션 이어하기(`--resume`)는 세션 파일이 그 서버에만 있어 다른 서버로 옮길 수 없으므로 쓰지 않는다.
5. 이벤트 `job_resumed_from_checkpoint`(checkpoint id, 파일 수, 바이트)를 남긴다. 작업 결과 보고에도 "이어받음"을 표시한다.

### 3.3 폴백 (R4)

다음 중 하나면 지금처럼 처음부터 하고, 사유를 이벤트로 남긴다.

- 체크포인트 없음 또는 24시간 초과
- `git apply` 실패 또는 sha256 불일치
- 지시서가 바뀐 경우(instruction_hash 불일치)

### 3.4 범위

- 1차: **러너 종료로 인한 재대기**만. 원인이 분명하고 작업 폴더가 온전하다.
- 2차(관찰 후): `process_died`. 프로세스가 비정상 종료해 폴더 상태가 불완전할 수 있어, 테스트가 이전에 통과했던 시점만 저장하는 등의 조건을 따로 정한다.
- 제외: 시간 초과(`timeout_max_runtime`). 같은 방식으로 다시 하면 또 초과할 수 있다.

### 3.5 정리

- 작업이 끝나면(done·error·rejected) 체크포인트를 지운다.
- 남은 것은 7일 뒤 정리 작업이 지운다.
- 116 디스크 부담이 없도록 DB 에만 둔다(평균 diff 는 수십 KB 수준으로 예상).

## 4. 구현 범위와 일정

| 항목 | 내용 | 소요 |
|---|---|---|
| DB | `pipeline_job_checkpoints` 테이블 + 정리 작업 | 0.5일 |
| 저장 | shutdown requeue 경로에 저장 단계(시간 상한) | 0.5일 |
| 이어받기 | 작업 폴더 생성 단계에 적용 + 지시 앞부분 | 1일 |
| 테스트 | 실제 git 저장소로 저장→다른 폴더 적용, 폴백 4종, 다른 서버 이어받기 시뮬레이션 | 0.5일 |
| 릴리스 | runner-live 릴리스(116) + 42·원격 러너 동기화, 관찰 | 0.5일 |
| **합계** | | **작업일 약 3일** |

## 5. 기대 효과와 한계

- 효과: 재시작·릴리스 때 진행분 손실을 줄인다. 러너 풀에서 서버 간 이동도 안전해진다. 재시작을 미루지 않아도 되므로 러너 릴리스를 더 쉽게 할 수 있다.
- 한계:
  - AI 대화 맥락(무엇을 왜 했는지)은 이어지지 않고 결과물(diff)만 이어진다. 새 AI 가 diff 를 읽고 판단한다.
  - 중간 상태가 잘못된 방향이었다면 그것을 이어받을 수 있다. 다만 기존 테스트·AI 검수가 그대로 걸러낸다.

## 6. 결정 필요 사항

1. 1차 범위(러너 종료 재대기만)로 착수할지
2. 체크포인트 보관 기한(권장 24시간 재개, 7일 삭제)

## 7. 용어

- **체크포인트**: 작업 도중의 변경분(diff)과 그 기준 커밋을 저장한 것.
- **재대기(requeue)**: 러너가 멈출 때 실행 중이던 작업을 대기열로 되돌리는 것.
- **폴백**: 이어받기가 안 될 때 원래 방식(처음부터)으로 되돌아가는 것.
