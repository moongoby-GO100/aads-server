## 3. 설계

### 3.1 러너 풀 (R1·R2·R3)

```
오비스 채팅(116) ─▶ 작업 DB(116 pipeline_jobs)
                        │
     ┌──────────────────┴──────────────────┐
  42 러너(코딩·테스트·커밋·push)        116 러너(소량 + 배포 전담)
     │ 승인 후: push 까지만 하고                 ▲
     │ DEPLOY_ONLY 릴리스 작업을 등록 ──────────┘ 116 만 DEPLOY_ONLY(AADS)를 가져가 블루/그린 배포
```

1. **배포 위임(R2)** — 러너에 `RUNNER_DEPLOY_DELEGATE=1` 인 서버(42)는:
   - 승인된 AADS 작업을 배포하지 않고 커밋·push 까지만 한다(기존 PUSH_ONLY 경로).
   - push 한 SHA 로 `DEPLOY_ONLY: true` 릴리스 작업을 같은 대화 세션에 등록한다(원 작업 ID·SHA 를 본문에 기록).
   - 원 작업은 "배포 위임됨" 상태 기록과 함께 끝내고, 결과는 릴리스 작업이 이어 보고한다.
2. **릴리스 작업 라우팅** — `DEPLOY_ONLY` 작업은 배포 서버만 가져간다.
   - 위임 서버(42)의 작업 선택 조건에 `AND NOT (DEPLOY_ONLY 헤더)` 를 더한다(기존 `DEPLOY_ONLY_HEADER_SQL` 재사용).
   - 116 은 지금처럼 AADS 의 DEPLOY_ONLY 를 처리한다.
3. **한가한 서버 우선(R3)** — 작업을 가져가기 직전에 자기 서버의 `/proc/pressure/cpu` some avg60 을 읽어 기준(`RUNNER_CLAIM_MAX_PSI`, 기본 40)을 넘으면 이번 주기에는 새 작업을 가져가지 않는다(진행 중 작업·배포는 영향 없음). 기준은 서버별 `runner_host_policy` 에 둘 수 있게 한다.
4. **42 설치(대기 상태로 먼저)**:
   - 저장소: aads-server·aads-dashboard 복제(GitHub 배포 키), 커밋 훅·서명 훅 설치.
   - DB: 116 PostgreSQL(5433) 로 SSH 터널(systemd, 자동 재연결).
   - 인증: lease push 대상에 42 추가.
   - 테스트: docker 설치, 테스트용 이미지(`aads-server:<sha>`)는 116 에서 `docker save | load` 로 전달하거나 42 에서 빌드, `.testdeps` 복제.
   - 러너: 116 운영 러너(`/root/aads/runner-live`)와 같은 릴리스를 설치. systemd 유닛은 **비활성**으로 둔다.
5. **전환**: 42 상한 2 → 하루 관찰 → 4 → 116 상한 10 → 3 → 42 상한을 실측 보며 상향(최대 약 15).

### 3.2 AI 실행 중계 분산 (C1)

1. 42 에 `claude_relay_server.py` 를 같은 방식으로 설치한다(포트 8199, 메시 IP 만 허용).
   - 인증: lease 로 받은 토큰 사용. 계정 슬롯 동시 사용 한도는 두 중계의 합계가 기존 한도(24)를 넘지 않게 나눈다(시작: 116=16, 42=8).
2. API 에 중계 목록 `CLAUDE_RELAY_URLS`(쉼표 구분)를 추가한다. 비어 있으면 기존 `CLAUDE_RELAY_URL` 한 대로 동작한다(하위 호환).
   - 선택: 각 중계의 `/health/relay-capacity`(이미 있음) 여유가 큰 쪽.
   - 장애: 연결 실패·타임아웃이면 다음 중계로 넘긴다.
   - 세션 고정: 같은 대화의 이어지는 실행(세션 재개)은 처음 실행한 중계로 보낸다(CLI 세션 파일이 그 서버에 있음).
3. 인증 핵심 파일(`auth_provider.py`, `model_selector.py`, `claude_relay_server.py`) 수정은 `ALLOW_AUTH_COMMIT=1` 규칙을 따른다.
4. API 반영은 블루/그린 배포가 필요하다. 오늘 API 배포 2건이 116 CPU 포화로 상태 점검에 실패했으므로, 러너 이전(3.1)으로 116 부하를 먼저 낮춘 뒤 배포한다.

## 5. 위험과 대응

| 위험 | 대응 |
|---|---|
| 위임 배포 중간에 끊겨 원 작업과 릴리스 작업 상태가 어긋남 | 릴리스 작업 본문에 원 작업 ID·SHA 를 남기고, 116 배포 결과를 원 작업 세션에 보고 |
| 42 테스트 이미지와 116 운영 이미지 불일치 | 테스트 전 릴리스 SHA 기준 이미지 digest 비교, 다르면 116 이미지 전달 |
| 계정 슬롯 과다 사용 | 두 중계 동시 한도 합계 ≤ 기존 24, 러너 풀 상한 합계 ≤ 20 으로 시작 |
| 42 의 SSH 가 인터넷에 비밀번호 로그인 허용 상태 | 대표님 PC 키 접속 확인 후 방화벽(메시·PC IP 만)·비밀번호 로그인 차단 |
| 중계 세션 재개가 다른 서버로 감 | 세션 고정 규칙, 실패 시 새 세션으로 재시작 |

## 6. 용어

- **러너**: 대표님이 지시한 개발 작업을 받아 코드 수정·테스트·커밋·배포까지 자동으로 돌리는 작업자.
- **AI 실행 중계(claude-relay)**: 채팅이 Claude·Codex 를 CLI 로 실행할 때 거치는 서버 프로그램. 이 기획에서 붙인 이름이다.
- **PUSH_ONLY / DEPLOY_ONLY**: 커밋·push 만 하는 작업 / 이미 push 된 버전을 배포만 하는 작업. 러너에 이미 있는 구분이다.
- **PSI**: CPU 를 기다리느라 작업이 지연된 시간의 비율.
- **lease(인증 출입증)**: 116 이 원격 러너 서버에 주기적으로 나눠 주는 임시 인증 토큰.
