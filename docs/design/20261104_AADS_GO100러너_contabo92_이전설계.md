## 2. 작업 위치와 배포·재기동 위치 나누기

### 2.1 현재 GO100 승인 후 경로 (저장소 코드 실측)

`deploy_job()` 의 `GO100)` 분기가 하는 일은 다음과 같다. 모두 러너와 같은 호스트에서 로컬로 실행된다.

1. push — 격리 워크트리에서 `git push origin <sha>:main` (GitHub)
2. API 재기동 — `backend/` 변경이 있고 재기동 금지 구간(`GO100_RESTART_FREEZE_WINDOWS`, 기본 `0850-0910 1515-1530`)이 아닐 때만 `systemctl restart go100`
3. 프론트 — `frontend/` 변경이 있으면 push 한 SHA 로 `/opt/go100/frontend-release-*` clean 워크트리 생성 → `deploy_frontend_blue_green.sh --apply`(내부에서 `go100_deploy_gate.sh` 의 장중 차단·dirty 차단·일회용 토큰 검사) → 번들 신선도 판정 → 오래된 릴리스 워크트리 정리
4. 헬스체크 — `http://localhost:8002/health` 예산 180초, 프론트 `https://go100.newtalk.kr/auth/login`
5. 실패 시 롤백 — `git revert` + push, `systemctl restart go100`

**백엔드 코드가 `/root/kis-autotrade-v4` 실행 경로에 반영되는 방식 (R2 실측, 2026-11-04 09:5x KST).**

- 러너 코드에는 push 한 SHA 를 런타임 작업트리에 반영하는 단계가 **없다.** `is_remote_project GO100` 이 참이라 `deploy_git_preflight` 는 `DEPLOY_PREFLIGHT_SKIP` 으로 건너뛰고(그 안의 `merge --ff-only` 도 push 보다 앞이다), push 이후 `GO100)` 분기는 `systemctl restart go100` 만 부른다. 즉 로컬 모드의 재기동은 "작업트리에 이미 있는 코드"를 다시 띄울 뿐, current_sha 가 그 안에 있는지는 확인하지 않는다.
- contabo14 `go100.service` 는 `WorkingDirectory=/root/kis-autotrade-v4`, `ExecStart=…/venv/bin/gunicorn` — 작업트리의 파일을 그대로 실행한다. 작업트리 HEAD 는 `20d69e3e`(채팅 마무리 커밋), 로컬 `origin/main` ref 는 `c6edd5f2` 이고 `504 behind / 25 ahead`, 미커밋 변경 605건이다. fast-forward 로는 맞출 수 없는 갈라진 상태다.
- GO100 저장소에 `scripts/auto_sync_deploy.sh`(`git pull origin $BRANCH --ff-only` 후 필요한 영역 배포)가 있으나 root crontab 에는 등록돼 있지 않았고(`grep -c auto_sync` = 0), 위 갈라진 상태에서는 ff-only 가 성립하지 않는다. 지금 이 스크립트가 백엔드 반영 경로인지는 **확인하지 못했다.**
- 결론: 로컬 모드의 "반영"은 러너 코드가 보증하지 않는다(기존 공백, 이번 작업이 바꾸지 않음). 원격 모드는 이 공백을 그대로 넘기지 않고 §2.2.2 의 검증으로 막는다.

지시서가 언급한 `deploy-go100.sh`(5분 `MONITOR_SECONDS=300` 감시 포함)와 `live_release_pin_guard.sh` 는 GO100 저장소 origin/main 에 있지만 **러너는 지금 이 둘을 부르지 않는다.** 러너의 API 재기동은 `systemctl restart go100` 직접 호출이고, 헬스 감시는 180초 예산이다. 또 "미체결 주문 0건 확인" 은 러너 경로에도 `deploy-go100.sh` 에도 없다(GO100 저장소 `git grep` 실측, 관련 문자열은 보고서용 스크립트 2개에만 있음). 이 공백은 원격화와 별개로 지금도 있다 — §8 승인 항목 6.

### 2.2 원격 경로 (이번에 구현)

`scripts/pipeline-runner.sh` 에 `go100_deploy_call` 을 추가했다.

```
GO100_DEPLOY_SSH_HOST=""            # 기본: 비어 있음 → "$@" 를 그대로 실행(지금과 동일)
GO100_DEPLOY_SSH_HOST=contabo14     # 설정 시: ssh contabo14 'bash -s' 로 실행
GO100_DEPLOY_SSH_TIMEOUT=2700       # 호출별 기본 상한(초). 호출마다 GO100_DEPLOY_CALL_TIMEOUT 으로 덮어씀
GO100_DEPLOY_SSH_CONNECT_TIMEOUT=15
```

| 단계 | 호출 | 원격 상한 |
|---|---|---|
| 운영 호스트 SHA 확인(재기동 전·후) | `go100_deploy_call go100_runtime_has_sha $GO100_REPO_DIR <sha> <backend 경로…>` | 60초 ×2 |
| API 재기동 | `go100_deploy_call systemctl restart go100` (SHA 확인 통과 시에만) | 180초 |
| 프론트 디렉터리·BG 스크립트 존재 확인 | `go100_deploy_call test -d/-f …` | 60초 |
| 릴리스 워크트리 정리(2회) | `go100_deploy_call go100_prune_release_worktrees …` | 300초 |
| 릴리스 워크트리 생성 | `go100_deploy_call go100_create_frontend_release_worktree …` (원격 저장소에 SHA 가 없으면 원격에서 `git fetch origin main`) | 2700초 |
| BG 배포 | `go100_deploy_call env GO100_RELEASE_WORKDIR=… GO100_RUNTIME_WORKDIR=… bash …/deploy_frontend_blue_green.sh --apply` | 2700초 |
| 번들 신선도 | `go100_deploy_call verify_go100_bundle_fresh …` (통신 실패는 `go100-frontend:ssh_failed`/`timeout`) | 60초 |
| 백엔드 헬스체크·롤백 헬스 | `go100_deploy_call curl … localhost:8002/health` | 30초 |
| 롤백 재기동 | `go100_deploy_call systemctl restart go100` | 180초 |

설계상 지킨 것.

- **같은 코드를 원격에서 실행한다.** 함수는 `declare -f` 로 보내므로 원격용 사본이 따로 없다.
- **장중 정책 환경변수는 그 명령에만 넘긴다.** 러너 프로세스에 export 된 `GO100_INTRADAY_*`, `GO100_ALLOW_INTRADAY_DEPLOY`, `GO100_DEPLOY_COMPONENT` 만 원격 스크립트 첫머리에서 export 한다. `GO100_GATE_SKIP`·`GO100_ALLOW_DIRTY_DEPLOY` 같은 비상 우회는 넘기지 않는다 — 필요하면 운영 호스트에서 직접 건다.
- **종료코드·로그.** 원격 명령의 종료코드를 그대로 돌려준다. 0 이 아니면 `GO100_DEPLOY_REMOTE host=… rc=… reason=remote_rc|timeout_Ns|ssh_failed cmd=…` 를 stderr 와 `runner.log` 에 남긴다. 원격 stdout/stderr 는 그대로 흘려보내므로 기존 리다이렉트(`>"$_fe_bg_outf" 2>&1`, `2>"$_fe_release_errf"`)와 분류(`go100_fe_bg_classify`)가 바뀌지 않는다. 원격 `log` 는 stderr 로만 써서 stdout 캡처(워크트리 경로·신선도 결과)를 더럽히지 않는다. 이 정의는 `printf '%s\n' '…'` 한 줄로 낸다 — heredoc 본문에 `log() {` 줄을 두면 커밋 hook(`dup_guard.py` sh-dup-func)이 로컬 `log()` 재정의로 오탐해 승인 커밋이 막힌다(runner-9d5a90bf). stderr 전용·`tee`/`LOG_DIR` 미사용은 회귀 테스트가 생성된 원격 스크립트 텍스트로 확인한다.
- **stdin 보호.** 명령과 `exit` 를 스크립트 마지막 한 줄에 두고 `</dev/null` 을 붙인다. 원격 명령이 stdin 을 읽어도 스크립트를 먹지 않는다.
- **타임아웃.** `timeout --kill-after=15` 로 감싼다. ssh 는 `BatchMode=yes`, `ServerAliveInterval=30`, `ServerAliveCountMax=4`.

#### 2.2.1 통신 실패 처리 (R2)

원격 모드에서 `go100_deploy_call` 이 124·137(시간 초과)·255(ssh 실패)를 돌려주면 "명령 결과"가 아니라 "확인하지 못함"이다. 판정 도우미 `go100_deploy_comm_failed`(원격 모드에서만 참)와 `go100_deploy_comm_label`(`timeout` | `ssh_failed`)로 구분한다.

| 단계 | 통신 실패 시 | 비고 |
|---|---|---|
| API 재기동 | `_build_fail += go100-api:ssh_failed\|timeout` | 아래 §2.2.2 |
| `test -d frontend` | `go100-frontend:ssh_failed\|timeout` — 프론트 단계를 건너뛰지 않고 실패로 기록 | rc=1(없음)만 기존처럼 조용히 건너뜀 |
| `test -f` blue-green 스크립트 | `go100-frontend:ssh_failed\|timeout` | rc=1 은 기존 `bluegreen_script_missing` |
| 릴리스 워크트리 생성 | 기존 `release_worktree_failed` (원래부터 실패 처리) | |
| BG 배포 | 라벨을 `go100-frontend:ssh_failed\|timeout` 으로 덮어씀(기존에는 `bg_failed_unclassified`) | |
| 번들 신선도 | `go100-frontend:ssh_failed\|timeout` (기존에는 `active_slot_unknown`) | |
| 릴리스 워크트리 정리(prune) 2회 | **의도적으로 `\|\| true` 유지** | 정리 작업이며 결과가 배포 성공 여부를 바꾸지 않는다. 통신 실패는 `GO100_DEPLOY_REMOTE … reason=` 로 runner.log 에 남는다 |
| 백엔드 헬스체크 | 기존대로 통신 실패 = 헬스 실패(예산 180초 안에 5초 간격 재시도) | 일시 끊김은 재시도로 흡수, 계속되면 롤백 경로 |

`_build_fail` 이 비어 있지 않으면 헬스체크가 통과해도 `status=error, phase=build_fail` 이다(기존 최종 판정 블록, 변경 없음). **로컬 모드(`GO100_DEPLOY_SSH_HOST` 빈 값)는 `go100_deploy_comm_failed` 가 항상 거짓이라 분기·종료코드·`|| true` 의미가 그대로다.**

#### 2.2.2 원격 코드 반영 검증 — fail-closed (R2)

원격 모드의 API 재기동은 `go100_remote_api_restart <sha> <접두> [검증 경로…]` 한 곳을 지난다.

1. 운영 호스트에서 `go100_runtime_has_sha $GO100_REPO_DIR <sha> <경로…>` 를 실행한다. 두 가지를 모두 만족해야 0 이다.
   - (a) `git cat-file -e <sha>^{commit}` 와 `git merge-base --is-ancestor <sha> HEAD` — SHA 가 HEAD 에 포함된다.
   - (b) **지정 경로의 작업트리 내용이 SHA 트리와 같다.** `git ls-tree -r <sha> -- <경로>` 의 (모드, blob 해시)를 `git hash-object --stdin-paths` 로 계산한 실제 파일 해시와 비교한다. `git diff` 는 쓰지 않는다 — 인덱스의 assume-unchanged/skip-worktree 와 stat 캐시를 믿기 때문이다(테스트 `test_r4_*`). 디렉터리 경로는 `find` 로 파일 시스템을 직접 훑어, SHA 트리에 없는 파일이 하나라도 있으면(추적 여부·ignore 무관, `__pycache__` 제외) 5 로 막는다. (a) 만으로는 실행 파일이 그 내용이라는 보장이 없다: HEAD 가 배포 SHA 인 채 해당 파일을 구버전으로 미커밋 수정한 경우, 배포 커밋을 후속 커밋이 revert 한 경우 모두 (a) 는 0 이다(리뷰어 재현, 테스트 `test_r3_*` 로 고정). SHA 에서 삭제되는 경로가 추적되지 않은 파일로 남아 있어도 미반영으로 본다.
   - 검증 경로는 러너가 계산한 배포 변경 파일 중 `backend/` 로 시작하는 것이다(`go100_backend_verify_paths`). 변경 목록을 못 구했거나 `backend/` 파일이 없으면 `backend/` 전체를 비교한다(보수적). 롤백은 같은 경로를 `rollback_sha`(revert 커밋)와 비교한다. 경로를 하나도 못 받으면 4 로 막힌다(fail-closed).
   - **경로 밖(운영 작업트리의 무관한 미커밋 변경 605건)은 보지 않는다.** 읽기 전용이며(`ls-tree`·`hash-object` 만 쓰고 인덱스를 갱신하지 않으며 `--literal-pathspecs`) reset·checkout·pull·fetch·merge·clean 을 쓰지 않는다.
   - 반환: 0 반영, 1 객체 없음/HEAD 에 미포함, 2 저장소 아님, 3 SHA 형식 오류, 4 검증 경로 없음, 5 지정 경로 내용이 SHA 와 다름, 6 비교 불가.
   - 한계: 파일 내용이 SHA 와 같다는 것이지, 떠 있는 프로세스가 그 파일을 다시 읽었다는 증명은 아니다. 프로세스 기동 시각·릴리스 SHA 파일 대조는 승인 항목 8 의 반영 방식이 정해진 뒤 넣는다.
2. 0 이 아니면 **재기동 명령을 보내지 않는다.** 통신 실패면 `ssh_failed`/`timeout`, 내용 불일치(5)면 `remote_code_mismatch`, 그 외는 `remote_sha_not_applied`.
3. 0 이면 `systemctl restart go100`. 실패는 `restart_failed`(통신 실패면 `ssh_failed`/`timeout`).
4. 재기동 뒤 같은 검사(같은 경로)를 한 번 더 한다. 실패하면 `remote_sha_lost`.
5. 배포는 `current_sha`, 롤백은 `rollback_sha`(접두 `rollback`)로 부른다. 롤백이 막히면 재기동하지 않고 `ROLLBACK_REMOTE_RESTART_NOT_DONE` 로그·채팅 알림·`review_feedback`(`remote_restart=…`)에 남기며 수동 복구를 요청한다.

**현재 운영 상태로는 이 검사가 통과하지 않는다.** contabo14 작업트리 HEAD(`20d69e3e`)는 `origin/main` 에서 갈라져 있어 새 SHA 가 HEAD 의 조상이 아니다(§2.1). 즉 GO100_DEPLOY_SSH_HOST 를 켜도 백엔드 재기동은 막히고 `go100-api:remote_sha_not_applied`(또는 내용이 다르면 `remote_code_mismatch`)로 기록된다 — **"원격 백엔드 반영 미구현 — 2단계 승인 항목"**(§8 항목 8). 프론트 경로는 릴리스 워크트리를 push 한 SHA 로 새로 만들어 쓰므로 이 제약과 무관하다.
