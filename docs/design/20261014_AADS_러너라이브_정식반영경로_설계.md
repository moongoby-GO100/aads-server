- document_key: `aads-runner-live-release-apply-path`
- 작업: AADS-RUNNER-LIVE-RELEASE-APPLY-PATH-20261014 (CEO 사전 승인: 다음단계 2, 2026-10-14 16:46 KST)
- 상태: 구현 완료(재시작을 lease 트랜잭션 안으로 이동한 재작업판) · **운영 설치 전**(설치는 별도 CEO 승인 사항)
- 대상 파일: `scripts/runner_live_update.sh`, `scripts/runner_live_release_prepare.sh`, `scripts/restart_local_runner.sh`(`--lease-held`), `scripts/install_runner_live_controller.sh`(설치, §5)

## 1. 왜 필요한가

운영 `runner-live`(`/root/aads/runner-live`)는 10-08 의 `de0591c8` 에 멈춰 있다. 10-06 에 설치한 컨트롤러가
"어떤 경우에도 DEFER 만" 하는 HOLD 전용이라 정식으로 전진시킬 길이 없었다. HOLD 의 헤더 주석이 요구한 것이 이 구현이다:
정확한 release/old-SHA 검증, dirty 검사, 두 maintenance lease, 새 PID/소스 검증.

## 2. 구조

```
timer(5분) -> /usr/local/sbin/aads-runner-live-update (경로 고정, 인자/환경변수 없음)
  1. 고정 companion 의 sha256 핀 검증 (바이트를 읽어 그 바이트만 실행)
  2. preflight == AWARE ?              아니면 DEFER BOOTSTRAP_REQUIRED / PREFLIGHT_UNKNOWN
  3. /etc/aads/runner-live-release.json 없음 -> DEFER RELEASE_MANIFEST_MISSING_AUTO_APPLY_DISABLED   (기본값, 변경 없음)
  4. manifest 검증 -> 사전 검사 -> busy 확인 -> [lease 구간] 파일 교체 -> 재시작 -> 새 PID 검증
  5. lease 해제 -> 새 데몬 actor 기록이 RUNNING + source_sha256 일치 (최대 180초) -> APPLIED
     실패하면 [두 번째 lease 구간] old SHA/companion 복구 + 재시작 -> ROLLED_BACK
```

기존 `runner_maintenance_transaction`(admission EX → lifetime EX → quiescent) 를 그대로 재사용한다. 새 잠금은 없다.

### 2.1 manifest 스키마 (schema=1)

```json
{
  "schema": 1,
  "release_sha": "<40자 hex>",
  "expected_old_sha": "<40자 hex, 현재 runner-live HEAD>",
  "companion_sha256": "<64자 hex, release_sha 의 scripts/runner_busy_lib.sh>",
  "controller_sha256": "<64자 hex, release_sha 의 scripts/runner_live_update.sh>",
  "created_at": "2026-10-14T16:53:00Z",
  "approved_by": "ceo"
}
```

- 파싱은 python3 `json` 만 쓴다(eval/source 없음). 키 집합이 정확히 일치해야 하며 중복 키·여분 키·`NaN` 은 거부한다.
- 파일은 root 소유, 모드 0644 이하(`& ~0644 == 0`), 심볼릭 링크 금지, 경로의 모든 부모가 root 소유·비쓰기(sticky 제외) — companion 검증과 같은 기준.
- `release_sha == expected_old_sha` 는 무의미한 적용이라 거부한다.
- 위반은 전부 `DEFER reason=RELEASE_MANIFEST_INVALID`.

### 2.2 사전 검사 (아무것도 바꾸기 전, 순서대로)

| 순서 | 검사 | 실패 시 |
|---|---|---|
| 1 | manifest 형식 | `RELEASE_MANIFEST_INVALID` |
| 2 | 실행 중인 컨트롤러 sha256 == `controller_sha256` | `CONTROLLER_SHA_MISMATCH` |
| 3 | `companion_sha256` 가 컨트롤러에 박힌 핀 목록에 있음 | `COMPANION_PIN_MISMATCH` |
| 4 | `release_sha` 가 origin/main 조상 (`git merge-base --is-ancestor`) | `RELEASE_SHA_NOT_IN_MAIN release=<sha>` |
| 5 | runner-live HEAD == `expected_old_sha` (CAS) | `OLD_SHA_MISMATCH current=<sha> expected=<sha>` |
| 6 | `git status --porcelain` 비어 있음 (untracked 포함) | `DIRTY_TREE` |
| 7 | `release_sha:scripts/runner_busy_lib.sh` 의 sha256 == `companion_sha256` | `COMPANION_SHA_MISMATCH` |
| 8 | busy 판정 IDLE (라이브 프로세스 probe + DB 활성 job 0건, 불명은 busy) | `BUSY state=<상태>` |
| 9 | 두 lease 획득 (`RUNNER_LIVE_LEASE_WAIT` 20초) | `LEASE_UNAVAILABLE` |

4 단계 전에 `git fetch origin main`(60초 제한)을 한다. 작업 트리/HEAD 는 건드리지 않고 ref/객체만 갱신하며, 실패해도
이미 가진 객체로 계속 판정한다. 환경변수로 경로를 바꿀 수 없다 — 진입점은 `/root/aads/runner-live`,
`/usr/local/lib/aads-runner/runner_busy_lib.sh`, `/etc/aads/runner-live-release.json`, `/run/aads-runner-maintenance` 를 고정한다.

### 2.3 적용 — 한 lease 트랜잭션 안에서 끝낸다 (`runner_live_apply_locked`)

재시작을 lease 밖에서 하면 틈이 생긴다. lease 를 놓는 순간 QUIESCENT 였던 구 데몬이 `runner_maintenance_checkpoint` 에서
RUNNING 으로 돌아와 같은 메인 루프에서 큐 작업을 claim 한다(`RUNNER_MAINTENANCE_ACTIVE=1` 이라 self-change reexec 도 건너뛴다).
그러면 구 데몬이 새 SHA 의 helper 파일로 작업을 돌리고, 재시작은 busy 로 보류(exit 3)되며 롤백은 lifetime EX 를 못 잡는다.
그래서 checkout → companion 교체 → 재시작 → 새 MainPID 검증을 **전부 두 lease 를 쥔 채** 한다. 새 데몬은
`runner_maintenance_enter` 의 admission `flock -s` 에서 lease 가 풀릴 때까지 기다리므로 claim 하지 못한다.

1. lease 안에서 HEAD/clean 재확인(CAS 를 한 번 더). 어긋나면 `DEFER CHANGED_UNDER_LEASE`.
2. 설치된 companion 바이트와 새 companion 바이트, 그리고 재시작 helper 를 임시 디렉터리(0700)에 보관.
   helper 는 `release_sha` 의 `restart_local_runner.sh` 사본 + 짝이 되는 companion(`restart-new/` = 새 companion, `restart-old/` = 설치돼 있던 companion).
   롤백 대상(old SHA)의 스크립트에 `--lease-held` 가 없을 수 있어 live 트리의 스크립트를 직접 쓰지 않는다.
3. `git checkout --detach <release_sha>` → `rev-parse HEAD` 재확인.
4. companion 원자 교체: 같은 디렉터리의 임시 파일 → `fsync` → `rename` → 디렉터리 `fsync`, 모드 0644. 설치 후 sha256 이 `companion_sha256` 과 같은지 확인.
5. 3~4 단계 어디서든 실패하면 같은 lease 안에서 즉시 `expected_old_sha` 와 옛 companion 으로 복구하고 `ROLLED_BACK`(재시작은 하지 않았으므로 구 데몬이 그대로 산다).
6. 재시작: `bash restart-new/restart_local_runner.sh --service <svc> --lease-held`. 이 옵션은 process probe 와 AWARE preflight 는 그대로 하고,
   자체 `runner_maintenance_transaction` 을 열지 않으며 DB busy 판정을 생략한다(lifetime EX 획득이 곧 작업 0건 보장). 옵션이 없는 호출은 예전과 같다.
   **같은 lock 을 다른 fd 로 EX 요청하면 교착**하므로 lease 를 쥔 콜백은 옵션 없이 이 스크립트를 부르면 안 된다.
7. 새 MainPID 확인(`RUNNER_LIVE_PID_WAIT` 15초): 0이 아님 → 이전과 다름 → runner-live HEAD == `release_sha` →
   `/proc/<pid>/fd/255`(없으면 cmdline)의 스크립트가 runner-live 아래에 있고 `release_sha` 의 같은 경로 블롭과 바이트 동일.
   유닛의 `WorkingDirectory` 가 runner-live 가 아니라(`/root/aads/aads-server`) cwd 는 판정에 쓰지 않는다.
8. 6~7 이 실패하면 **같은 lease 안에서** 파일을 복구하고, MainPID 가 바뀌었을 때만 `restart-old` 로 재시작해 old SHA 소스를 다시 검증한다(`ROLLED_BACK`).
   복구나 복구 재시작이 검증되지 않으면 `ROLLBACK_INCOMPLETE`.

### 2.4 lease 해제 후 새 데몬 RUNNING 확인 (`runner_live_wait_daemon_running`)

트랜잭션이 끝나면 새 데몬이 admission 을 통과해 lifetime 을 잡고 `RUNNING` 을 기록한다. 컨트롤러는 최대 `RUNNER_LIVE_RUNNING_WAIT`(180초) 동안
`actors/<pid>.json` 이 다음을 모두 만족하는지 본다: `protocol=1`, `phase=RUNNING`, boot id·start ticks 가 그 프로세스와 일치, `source_sha256` 이
그 데몬이 실행 중인 파일의 sha256 과 같음. 통과하면 manifest 를 소비하고 `APPLIED`. 실패하면 두 번째 트랜잭션
(`runner_live_rollback_locked`, lease 대기 `RUNNER_LIVE_ROLLBACK_LEASE_WAIT` 60초)에서 old SHA checkout, companion 원복, 재시작을 한 lease 안에서 하고
복구된 데몬도 같은 방법으로 RUNNING 을 확인한 뒤 `ROLLED_BACK reason=NEW_DAEMON_NOT_RUNNING`.

## 3. 상태 전이와 로그

모든 결과는 stdout 한 줄(= journal `aads-runner-live-update`).

| 출력 | 의미 | 종료코드 | manifest |
|---|---|---|---|
| `DEFER runner-live-update reason=…` | 아무것도 바꾸지 않음. 다음 tick 에 재평가 | 0 | 그대로 |
| `APPLIED runner-live-update release= old= prev_pid= pid= manifest=consumed` | 반영·새 데몬 RUNNING 확인 완료 | 0 | `<이름>.applied.<release_sha>.json` 으로 rename |
| `ROLLED_BACK runner-live-update reason= release= restored=` | 실패해 옛 SHA/companion 으로 복구 | 1 | `<이름>.rolledback.<release_sha>.json` 으로 rename |
| `ROLLBACK_INCOMPLETE runner-live-update reason= …` | 복구마저 검증 못함. **사람이 봐야 함** | 4 | 그대로 |
| `APPLIED … manifest=consume_failed` | 반영됐으나 rename 실패 | 5 | 그대로(CAS 가 재적용을 막는다) |

ROLLED_BACK 도 manifest 를 소비하는 것은 요구사항 7 의 확장이다. 소비하지 않으면 실패한 manifest 가 5분마다 재시도되어
재시작이 반복된다. 다시 시도하려면 새 manifest 를 만들어 설치해야 한다.

### 실패 지점별 롤백

시간 순서: ①사전 검사 → ②[lease A] checkout → companion → 재시작 → 새 PID 검증 → ③lease 해제 → 새 데몬 RUNNING 확인 → ④(실패 시)[lease B] 복구 + 재시작.

| 실패 지점 | 상태 | 조치 | 출력 reason |
|---|---|---|---|
| ① 사전 검사(2.2) | 변경 없음 | 없음 | DEFER |
| ② lease 획득 불가 | 변경 없음 | 없음 | DEFER `LEASE_UNAVAILABLE` |
| ② `checkout` 실패 | HEAD 불변 또는 부분 | lease A 안에서 `checkout --force --detach <old>` + companion 복구. 재시작 안 함 | `CHECKOUT_FAILED` |
| ② HEAD 가 release 와 다름 | 위와 동일 | 위와 동일 | `HEAD_NOT_RELEASE` |
| ② companion 설치 실패 / sha 불일치 | HEAD=release | HEAD 와 companion 복구 | `COMPANION_INSTALL_FAILED` / `COMPANION_SHA_MISMATCH` |
| ② 재시작 스크립트가 비0 (busy 로 보류=3 포함) | 파일=release, 프로세스=구버전 | lease A 안에서 파일 복구, MainPID 가 그대로면 재시작 없음 | `RESTART_FAILED` |
| ② MainPID 0 이거나 불변 | 위와 동일 | 위와 동일 | `PID_UNCHANGED` |
| ② 새 PID 의 HEAD/소스가 release 와 다름 | 프로세스=잘못된 소스 | lease A 안에서 파일 복구 + `restart-old` 재시작 + old SHA 소스 재검증 | `HEAD_NOT_RELEASE_AFTER_RESTART` / `NEW_PID_SOURCE_MISMATCH` |
| ② 복구 파일 교체 또는 복구 재시작 검증 실패 | 불명 | 자동 조치 없음 | `ROLLBACK_INCOMPLETE` (수동 점검) |
| ③ 180초 안에 새 데몬이 RUNNING + 소스 해시 일치를 못 보임 | 파일=release, 새 데몬은 떠 있으나 미검증 | lease B(60초 대기) 안에서 old SHA, companion, 재시작을 모두 수행하고 복구 데몬도 RUNNING 확인 | `NEW_DAEMON_NOT_RUNNING` |
| ④ lease B 불가 또는 복구 재시작 검증 실패 | 불명 | 자동 조치 없음 | `ROLLBACK_INCOMPLETE` (수동 점검) |

수동 복구 기준점: `expected_old_sha` 는 manifest(rename 된 사본 포함)에 있다. 사람이 `git -C /root/aads/runner-live checkout --detach <old>` 후
`bash scripts/restart_local_runner.sh` 로 되돌린다.

## 4. companion 핀 갱신 방법

컨트롤러는 companion 을 sha256 핀으로만 신뢰한다(`RUNNER_LIVE_COMPANION_PINS`, 공백 구분 목록). 핀과 companion 은 함께 설계해야 한다.

- 설치본 `/usr/local/lib/aads-runner/runner_busy_lib.sh` 는 10-06 12:43 판(`845f029b…`)이다. 이 저장소의 컨트롤러 핀은 `fad0e8f3` 의 `78e55d7a…` 이다.
  따라서 **새 컨트롤러를 설치하려면 새 companion 을 먼저 설치**해야 한다(§5).
- 이후 companion 이 바뀌는 릴리스는 두 단계다.
  1. 새 companion 해시를 핀 목록에 **추가**(옛 해시 유지)한 컨트롤러를 릴리스·설치한다(companion 은 아직 안 바꿈).
  2. companion 이 바뀐 릴리스를 manifest 로 반영한다. 컨트롤러는 `companion_sha256` 이 핀 목록에 없으면 `COMPANION_PIN_MISMATCH` 로 보류하므로,
     반영 후 companion 이 untrusted 가 되어 컨트롤러가 영구 보류되는 일은 구조적으로 막힌다.
  3. 정리 단계에서 옛 해시를 목록에서 뺀다.
- 이번 릴리스는 `runner_busy_lib.sh` 를 바꾸지 않는다(핀 불변).
- 확인: `git show <sha>:scripts/runner_busy_lib.sh | sha256sum` 이 핀 목록에 있어야 한다.

## 5. 운영 설치 절차 — 별도 CEO 승인 필요 (이번 작업에서는 실행하지 않음)

> 설치 대상은 `/usr/local/sbin/aads-runner-live-update`, `/usr/local/lib/aads-runner/runner_busy_lib.sh` 두 파일이다.
> 수동 `install`/`mv` 대신 저장소의 `scripts/install_runner_live_controller.sh` 하나로 한다(체크섬 CAS·원자적 교체·롤백 내장).
> 실제 실행은 이번 작업 범위 밖이며 승인 후 root 가 한 단계씩 확인하며 실행한다.

### 5.1 설치 스크립트 계약

```
install_runner_live_controller.sh --release-sha <40hex> \
    --expect-controller-sha256 <64hex> --expect-companion-sha256 <64hex> [--dry-run]
```

- 원본: `/root/aads/runner-live` 의 `git show <release_sha>:scripts/runner_live_update.sh` / `:scripts/runner_busy_lib.sh` 커밋 blob 만. 작업 트리 파일은 쓰지 않는다. 먼저 `git fetch origin main`(60초 제한, ref 만 갱신)을 하고 `release_sha` 가 origin/main 의 조상이어야 한다.
- 경로(컨트롤러·companion·`/run/aads-runner-maintenance`·서비스명·runner-live)는 스크립트에 고정이다. 테스트용 경로 주입은 `installer_run` 함수 인자로만 되고 환경변수로는 받지 않는다.
- `--expect-*` 는 **지금 설치돼 있는 파일**의 sha256 이다(CAS). 새 릴리스의 해시가 아니다.

| 순서 | 검사 | 실패 시 (stdout 한 줄, 종료코드 0, 아무것도 쓰지 않음) |
|---|---|---|
| 1 | 인자 형식 (40hex / 64hex 2개, 중복·미지원 옵션 거부) | 사용법 출력, 종료코드 2 |
| 2 | 설치본 두 파일의 sha256 == `--expect-*` | `DEFER reason=INSTALLED_CHECKSUM_MISMATCH controller_current= controller_expected= companion_current= companion_expected=` (없는 파일은 `missing`) |
| 3 | `release_sha` 가 origin/main 조상 | `DEFER reason=RELEASE_SHA_NOT_IN_MAIN release=<sha>` |
| 4 | 새 컨트롤러 blob 의 `RUNNER_LIVE_COMPANION_PINS` 에 새 companion blob 의 sha256 이 있음 (blob 텍스트에서 추출, source/eval 없음) | `DEFER reason=COMPANION_PIN_MISMATCH companion_new=<sha>` |
| 5 | 설치본 companion 을 `--expect-companion-sha256` 로 바이트 검증(root 소유·비쓰기·심볼릭 링크 금지)한 뒤 lease 라이브러리로 사용 | `DEFER reason=COMPANION_MISSING_OR_UNTRUSTED` |
| 6 | 두 lease (admission EX → lifetime EX → quiescent, 대기 20초) — **기존 `runner_maintenance_transaction`**, 새 잠금 없음 | `DEFER reason=LEASE_UNAVAILABLE` |

lease 안에서(콜백 `installer_install_locked`):

1. 설치본 두 파일의 바이트를 비공개 임시 디렉터리(0700)로 복사해 sha256 을 다시 확인한다. 어긋나면 `DEFER reason=CHANGED_UNDER_LEASE`.
2. 백업 `<경로>.prev.<이전 sha 앞 16자>` 를 원자적으로 만든다(컨트롤러 0755, companion 0644). 실패하면 `DEFER reason=BACKUP_FAILED`(아직 아무것도 교체 전).
3. **companion 먼저**, **컨트롤러 나중**. 각각 같은 디렉터리 임시 파일 → `root:root` → 모드(companion 0644 / 컨트롤러 0755) → `fsync` → `rename` → 디렉터리 `fsync`.
4. companion 교체가 실패하면 companion 을 원복하고 `ROLLED_BACK reason=COMPANION_INSTALL_FAILED`. 컨트롤러 `rename` 이 실패하면 companion 을 이전 바이트로 원복하고 `ROLLED_BACK reason=CONTROLLER_RENAME_FAILED`.
5. 교체 후 두 파일의 sha256 을 다시 읽어 새 값과 같은지 확인한다. 다르면 두 파일 모두 원복하고 `ROLLED_BACK reason=POST_INSTALL_CHECKSUM_MISMATCH`.
6. 원복 자체가 실패하면 `ROLLBACK_INCOMPLETE reason=RESTORE_FAILED_RC_<n>`(현재/기대 sha 포함, 종료코드 4) — 사람이 §5.4 로 복구한다.

성공하면 `INSTALLED runner-live-install release= controller_old= controller_new= companion_old= companion_new= backup_controller= backup_companion=` 한 줄(종료코드 0). `ROLLED_BACK` 은 종료코드 1.

`--dry-run` 은 2~5 단계와 AWARE preflight(읽기 전용)까지만 하고 lease 를 잡지 않으며 설치 경로에 아무것도 쓰지 않는다(`git fetch` 가 runner-live 의 ref 를 갱신하는 것은 예외). 출력은 `DRYRUN … writes=none` 한 줄과 실제 설치 명령(`INSTALL_CMD:`), 롤백 명령 두 줄(`ROLLBACK_CMD:`)이다.

### 5.2 승인 후 순서

```bash
REL=<release_sha>      # origin/main 에 push 된 이 변경 이상의 커밋
LIVE=/root/aads/runner-live
INST=/root/aads/aads-server/scripts/install_runner_live_controller.sh   # 또는 git -C $LIVE show $REL:scripts/install_runner_live_controller.sh

# 0. 현재 설치본 해시 확인(= --expect-* 값). 10-14 실측: 컨트롤러 2c42a170c1ca2e11…, companion 845f029b…
CTL=$(sha256sum /usr/local/sbin/aads-runner-live-update | cut -d' ' -f1)
LIB=$(sha256sum /usr/local/lib/aads-runner/runner_busy_lib.sh | cut -d' ' -f1)

# 1. 점검만 (아무것도 쓰지 않음). 출력의 INSTALL_CMD 가 아래 2번과 같아야 한다.
bash $INST --release-sha $REL --expect-controller-sha256 $CTL --expect-companion-sha256 $LIB --dry-run

# 2. 설치
bash $INST --release-sha $REL --expect-controller-sha256 $CTL --expect-companion-sha256 $LIB

# 3. manifest 없이 한 번 실행해 AWARE 와 새 companion 을 확인한다 (기대: …MANIFEST_MISSING…)
/usr/local/sbin/aads-runner-live-update

# 4. manifest 준비(읽기 전용): runner_live_release_prepare.sh 의 stdout 을 사람이 검토
git -C $LIVE show $REL:scripts/runner_live_release_prepare.sh > /root/prepare.sh
bash /root/prepare.sh $REL --approved-by <이름> > /root/runner-live-release.$REL.json
```

설치 스크립트는 `DEFER` 로 끝나도 종료코드가 0 이다. 반드시 stdout 의 첫 단어(`INSTALLED`)로 성공을 판단한다.

### 5.3 유닛 타임아웃과 manifest 설치

- 정상 반영은 수십 초이나 최악(lease 20 + 재시작 90 + PID 15 + RUNNING 180 + 복구 lease 60 + 복구 재시작 90 + PID 15 + RUNNING 180)은 650초를 넘는다 → `/etc/systemd/system/aads-runner-live-update.service` 의 ExecStart 를 `/usr/bin/timeout 900 /usr/local/sbin/aads-runner-live-update` 로 바꾸고 `systemctl daemon-reload`.
- manifest 설치 = 반영 트리거(다음 5분 tick 에 적용). 부모 디렉터리도 root 소유여야 한다.
  `install -d -o root -g root -m 0755 /etc/aads && install -o root -g root -m 0644 /root/runner-live-release.$REL.json /etc/aads/runner-live-release.json`
- 관찰: `journalctl -u aads-runner-live-update -n 20 --no-pager`, `git -C $LIVE rev-parse HEAD`, `systemctl show -p MainPID --value aads-pipeline-runner.service`.

### 5.4 되돌리기

- 설치 직후 되돌리기(스크립트가 만든 백업 사용, `INSTALLED` 줄의 `backup_*` 경로):
  ```bash
  install -o root -g root -m 0644 /usr/local/lib/aads-runner/runner_busy_lib.sh.prev.<companion_old> /usr/local/lib/aads-runner/.runner_busy_lib.sh.rollback \
    && mv -T /usr/local/lib/aads-runner/.runner_busy_lib.sh.rollback /usr/local/lib/aads-runner/runner_busy_lib.sh
  install -o root -g root -m 0755 /usr/local/sbin/aads-runner-live-update.prev.<controller_old> /usr/local/sbin/.aads-runner-live-update.rollback \
    && mv -T /usr/local/sbin/.aads-runner-live-update.rollback /usr/local/sbin/aads-runner-live-update
  ```
  옛 컨트롤러 핀은 옛 companion 과 짝이므로 **두 파일을 함께** 되돌린다. 같은 명령이 `--dry-run` 의 `ROLLBACK_CMD:` 로 미리 출력된다.
- manifest 설치 전이면 `/etc/aads/runner-live-release.json` 만 지우면 즉시 HOLD 로 돌아간다.
- 이 변경 자체(스크립트·테스트·문서)는 커밋 revert 로 되돌린다 — 운영 설치 전에는 운영 영향이 없다.

## 6. 알려진 한계

- 재시작을 lease 안으로 옮겨 "파일 교체와 재시작 사이에 구 데몬이 claim 하는 틈"은 없앴다. 남은 틈은 ③(lease 해제 후 RUNNING 확인)이다.
  이때 새 데몬은 이미 검증된 새 소스이므로 claim 이 일어나도 파일/프로세스가 어긋나지 않는다. 다만 ③ 실패 후 롤백(lease B)은
  새 데몬이 작업을 잡았다면 그 작업이 끝날 때까지(60초) 기다리고, 못 기다리면 `ROLLBACK_INCOMPLETE` 가 된다.
- 재시작 helper 는 `release_sha` 의 `restart_local_runner.sh` 이다. 그 릴리스가 `--lease-held` 를 모르면 스크립트가 종료코드 2 로 끝나
  `RESTART_FAILED` 로 롤백한다(fail-closed). `--lease-held` 가 들어간 커밋 이후만 반영 대상이다.
- helper 의 companion 은 manifest 로 해시가 고정된 새 companion 과, 컨트롤러 핀 검증을 통과한 설치본뿐이다.
- 컨트롤러가 SIGKILL/타임아웃으로 중간에 죽으면 자동 복구되지 않는다(`OLD_SHA_MISMATCH` 로 보류). §5 의 5번 타임아웃 상향이 이를 줄인다.
- 단위 테스트는 `systemctl` 대신 주입한 재시작 함수와 실제 protocol 데몬(fixture)을 쓴다. 실제 systemd 재시작은 운영 설치 후 첫 반영에서 처음 검증된다.
  (참고: 2026-10-14 17:11 KST 에 runner-live 가 5720cd95 로 수동 반영되어 MainPID 635302 로 가동 중이다. `expected_old_sha` 예시는 이 값이다.)
