## 2. 등급 산정 함수

입력은 서버가 가진 값만 쓴다. 클라이언트가 보낸 등급은 무시한다(FR-5).

```python
# app/services/doc_tier.py (신규, 구현 단계)
D1, D2, D3, SPLIT = "D1", "D2", "D3", "SPLIT"
D3_KINDS = {"prd", "contract", "architecture"}
D2_KINDS = {"plan", "design", "spec", "tasks"}   # tasks 는 PRD §9-5 확정
D1_KINDS = {"report", "reference"}

def compute_doc_tier(kind: str, char_count: int, has_goal: bool,
                     *, long_chars: int = 15_000, split_chars: int = 50_000) -> str:
    if char_count > split_chars:
        return SPLIT
    if kind in D3_KINDS or char_count > long_chars:
        return D3
    if kind in D2_KINDS:
        return D2
    return D1            # report, reference
```

- `char_count = len(content)` (파이썬 str 길이 = 유니코드 글자 수. DB `char_length` 와 동일).
- `has_goal` = 개정의 `goal_id` 가 있거나 `project_document_goal_links` 에 해당 head 가 있음.
- 임계값 `long_chars`, `split_chars` 는 설정값(FR-6). 위치는 §5-3.
- `has_goal`은 호환 입력으로만 유지하고 등급에는 반영하지 않는다(PRD §9-2 확정). 목표 연결 유무가 같거나 달라도 같은 종류·길이는 같은 등급이다.
- AC-3 기준선은 2026-10-28 과거 388건의 목표 연결 제외 D1 199 · D2 100 · D3 89다. 이번 작업에서 재실측하지 않았다. 동일 스냅샷으로 재현하며 현재 데이터 수치로 오인하지 않는다.

| 등급 | 작성 순서(기존 행) | 검토 목록(신규 행) | 검토 수 |
|---|---|---|---|
| D1 | `S` | `AI_REVIEW_LIGHT` | 1 (반대편 회사) |

## 3. 회사 판별

```python
def provider_of(model: str) -> str:
    m = (model or "").strip().lower()
    if m.startswith(("claude:", "claude-")):
        return "anthropic"
    if m.startswith("codex:"):
        return "openai"
    if ":" in m:
        return "other:" + m.split(":", 1)[0]     # 예: litellm:gemini-… → other:litellm
    return "unknown"
```

- 현재 코드 검수가 허용하는 모델 접두사(`code_reviewer._is_cli_review_model`)와 같은 집합이라 새 규칙이 기존 허용 범위를 넓히지 않는다.
- `litellm:` 모델은 실제 제공사가 여러 곳이다. 이번 범위는 CLI 중계 모델(anthropic/openai)만 검토 후보로 인정한다(PRD §6). 후보에 `other:*`·`unknown` 이 있으면 건너뛴다.
- 접두사 판별은 모델 ID 규칙이 바뀌면 틀릴 수 있다. 판별 규칙은 한 함수에 모으고 단위 테스트로 현재 DB 의 모든 모델 ID(`claude-sonnet-5-5`, `claude-opus-5-5`, `claude-fable-5-1`, `codex:gpt-6.1-sol`, `codex:gpt-6-astra`, `codex:gpt-6-luna`, `codex:gpt-5.6-luna`)를 고정한다.

## 4. 검토 모델 선택 알고리즘

```python
def pick_reviewers(tier, author_model, tier_list, *, available, upper_models,
                   extra_lists=(), exclude=frozenset()):
    # available은 명시적 비활성/확인된 실패만 제외한다. 미확인은 순서를 보존한다.
    author_provider = provider_of(author_model)
    models = list(dict.fromkeys(m for lst in (tier_list, *extra_lists) for m in lst))

    def first_cross(provider, *, omit=()):  # 지정 회사의 첫 사용 가능 모델
        return next((m for m in models
                     if m not in exclude and m not in omit and m in available
                     and provider_of(m) == provider
                     and (tier != "D3" or m in upper_models)), None)

    if author_provider not in ("anthropic", "openai"):
        # unknown D1/D2도 반드시 두 회사. D3는 양쪽 모두 상위 모델.
        a, o = first_cross("anthropic"), first_cross("openai")
        if not a or not o:
            return [], "blocked_unknown_pair"
        return [ReviewerPick(a, role="unknown_anthropic"),
                ReviewerPick(o, role="unknown_openai")], "ok"

    opposite = "openai" if author_provider == "anthropic" else "anthropic"
    cross = first_cross(opposite, omit={author_model})
    if cross is None:
        return [], "blocked_no_cross"
    picks = [ReviewerPick(cross, role="cross")]
    if tier == "D3":
        same = first_cross(author_provider, omit={author_model, cross})
        if same is None:
            return picks, "blocked_no_second"
        picks.append(ReviewerPick(same, role="same_company_other_model"))
    return picks, "ok"
```

세부 규칙:

1. **작성 모델 미상**은 알고리즘의 선행 분기로 처리한다. D1/D2/D3 모두 두 회사 각 1개 필수이며 한 회사라도 없으면 차단한다. `upper_models`는 승인된 상위 모델 집합(정책 버전에 고정)이며 단순 ID 차이로 상위 모델을 추정하지 않는다.
2. **자동 교체 표시**: 설정 목록의 1순위가 작성 회사와 같으면 화면 배지가 `⚠️ 같은 회사 → <교체될 모델>` 이다. 교체될 모델은 위 알고리즘이 돌려준 cross 역할 값과 같은 함수로 계산해 화면·서버가 어긋나지 않게 한다(서버가 `POST /settings/runner-models/cross-check` 로 미리보기 제공 — §6).
3. **재시도**: 선택된 검토 모델이 실행 실패(인증 오류, 한도)하면 같은 알고리즘을 `exclude` 에 그 모델을 더해 다시 돌린다. 실패한 시도는 검토 기록에 `attempt_failed` 로 남긴다.
4. **차단**: `blocked_*` 이면 `project_document_reviews` 에 `verdict='blocked'` 행을 남기고 기존 알림 경로로 보낸다. 알림 채널(텔레그램·ops)은 구현 단계에서 현행 워치독 규칙(`.claude/rules/watchdog.md`)에 맞춰 확정한다.
5. **예외 승인**: CEO 가 차단을 명시적으로 풀 때만 같은 회사 검토를 허용하며, 검토 기록에 `override_by`, `override_reason` 을 남긴다. 조용한 대체는 없다.
6. **코드 검수**: 문서 이중 검토 분기와 분리해 코드용 단일 교차 선택을 수행하되 `blocked_no_cross` 일 때 차단하지 않고 기존 목록 순서로 진행하며 기록에 `cross=false` 를 남긴다(PRD §9-6).

## 5. DB 변경안 — 두 안 비교와 권장

### 5-1. 검토 설정: 안 A vs 안 B

| 비교 | 안 A: `runner_model_config` 에 `tier` 컬럼 추가 | 안 B: 행 추가 (`AI_REVIEW_LIGHT`·`AI_REVIEW_STD`·`AI_REVIEW_HEAVY`) |
|---|---|---|
| 스키마 변경 | PK 를 `(size)` → `(size, tier)` 로 바꿔야 함. 기존 `ON CONFLICT (size)` 쿼리 전부 수정 | PK·컬럼 변경 없음. 기존 CHECK 확장 후 3행 INSERT 필요 |
| 기존 호출자 | `PUT` 의 `ON CONFLICT (size)`, `_get_db_model_config`(`WHERE c.size = $1`), `code_reviewer`(`WHERE size='AI_REVIEW'`) 모두 영향 | 기존 호출자는 새 행을 모르고 그대로 동작 |
| 구버전 대시보드 | `tier` 없는 PUT 이 PK 충돌/기본 tier 로 섞임 | 알 수 없는 size 를 목록에 그대로 표시(정렬만 앞쪽으로 갈 수 있음). 아래 §6 에서 하위호환 확인 |
| 롤백 | 컬럼·PK 되돌리기(데이터 이동 필요) | 선택 비활성화 후 데이터·확장 CHECK 보존(§8) |
| 표현력 | 한 size 에 여러 tier — 확장성 좋음 | size 이름에 tier 가 들어가 이름 규칙이 필요 |
| 위험 | 운영 중 PK 변경 | TEXT 키이나 API와 DB CHECK 허용 집합을 함께 확장해야 함 |

**권장: 안 B.** 이유는 (1) PK·컬럼은 유지하고 CHECK만 확장하여 변경 범위가 작고, (2) 기존 6개 행과 `AI_REVIEW` 폴백 꼬리(제약 4)를 건드리지 않으며, (3) 구버전 대시보드와 그대로 호환된다. 안 A 의 표현력 이점은 지금 필요 없다(등급이 3개로 고정).

#### 5-1-1. CHECK 확장과 대응 롤백 마이그레이션 계약

구현 시 up/down 짝을 `migrations/` 및 `migrations/rollback/`에 작성한다. 이번 작업에서는 파일·SQL 실행 모두 하지 않는다. 적용 전 운영 카탈로그의 실제 제약명·정의를 읽어 확인하고 예상과 다르면 중단한다.

- up: 한 트랜잭션에서 `runner_model_config_size_chk`를 기존 6키 + `AI_REVIEW_LIGHT`, `AI_REVIEW_STD`, `AI_REVIEW_HEAVY` 허용 정의로 교체·검증한다. 제약 교체에만 `ALTER TABLE … DROP CONSTRAINT`를 사용하며 테이블·컬럼·행 삭제는 없다. 확장 성공 후에만 신규 행을 삽입하고 API 정규식·GET 계산 대상을 함께 확장한다. 기존 6행 값과 PK는 유지한다.
- down: §8의 기능 롤백은 데이터와 확장 CHECK를 그대로 둔다. 구 CHECK 복원이 별도 승인된 경우 먼저 신규 키 선택·쓰기를 끄고 진행 중 작업을 마친다. 신규 키가 한 행이라도 있으면 down은 예외로 중단하며 자동 DELETE하지 않는다. 신규 키 0건이 확인될 때만 같은 트랜잭션에서 기존 6키 CHECK로 교체·검증한다. 즉 감사 데이터 DROP 없는 기능 롤백과 조건부 제약 복원을 구분한다.

신규 행 초기값(구현 단계에서 CEO 승인 후 입력 — 이번 작업은 값을 바꾸지 않음). 현재 DB 값에서 회사가 번갈아 나오도록 자른 **제안**이며 확정이 아니다.

| 행 | 제안 순서 | 근거 |
|---|---|---|
| `AI_REVIEW_LIGHT` | `claude-sonnet-5-5`, `codex:gpt-6-luna`, `codex:gpt-6.1-sol` | 경량: 작성이 codex 면 claude, 작성이 claude 면 luna 로 교체 |
| `AI_REVIEW_STD` | `codex:gpt-6.1-sol`, `claude-opus-5-5`, `codex:gpt-6-astra` | 현재 M 작성 1순위(claude-sonnet-5-5)와 다른 회사가 1순위 |
| `AI_REVIEW_HEAVY` | `claude-opus-5-5`, `codex:gpt-6-astra`, `codex:gpt-6.1-sol`, `claude-fable-5-1` | 양쪽 회사 상위 모델이 앞에 와서 D3 두 검토자가 한 목록에서 나옴 |

기존 `AI_REVIEW` 행은 값 그대로 두고 (a) 작성 체인의 폴백 꼬리, (b) 새 행이 비었을 때의 검토 폴백으로 계속 쓴다.

### 5-2. 개정 기록과 검토 기록

**개정 행(불변)에는 등록 시점에 확정되는 값만 둔다.**

```sql
-- 신규 마이그레이션(구현 단계). 모두 nullable 로 추가 — 기존 631개 개정 행 영향 없음.
ALTER TABLE project_document_revisions
  ADD COLUMN IF NOT EXISTS doc_tier text CHECK (doc_tier IN ('D1','D2','D3','SPLIT')),
  ADD COLUMN IF NOT EXISTS author_model text,
  ADD COLUMN IF NOT EXISTS author_provider text,
  ADD COLUMN IF NOT EXISTS review_policy_version text;
```

- 불변 트리거는 UPDATE/DELETE 만 막으므로 `ADD COLUMN` 은 가능하다(기본값 없는 nullable 추가는 행을 다시 쓰지 않는다).
- 기존 행은 NULL → 화면에 `등급 미산정`. UPDATE 백필 없이 비소급 처리한다. 개정 등록 시 nullable `review_policy_version`도 함께 고정하며 NULL은 종전 정책이다.

**요구 문서의 `review_models jsonb` 는 개정 행에 두지 않는다.** 개정 행이 UPDATE 불가이고, 검토는 개정 등록 *후에* 일어나기 때문이다. 대신 추가 전용 테이블을 둔다.

```sql
CREATE TABLE IF NOT EXISTS project_document_reviews (
  id bigserial PRIMARY KEY,
  tenant_id uuid NOT NULL,
  project_key text NOT NULL,
  head_id uuid NOT NULL,
  revision_id uuid NOT NULL,
  reviewer_model text NOT NULL,
  reviewer_provider text NOT NULL,
  role text NOT NULL CHECK (role IN ('cross','same_company_other_model','unknown_anthropic','unknown_openai','code')),
  cross_company boolean NOT NULL,
  verdict text NOT NULL CHECK (verdict IN ('pass','reject','blocked','attempt_failed')),
  reason text,
  override_by text, override_reason text,
  source_task_id text,                    -- 검토를 수행한 러너 job_id
  created_at timestamptz NOT NULL DEFAULT now(),
  FOREIGN KEY (head_id, revision_id) REFERENCES project_document_revisions(head_id, id)
);
CREATE INDEX project_document_reviews_rev_idx ON project_document_reviews(revision_id, id);
-- 개정과 같은 불변 트리거를 건다(reject_project_document_history_mutation 재사용).
```

- 사용자가 요구한 `review_models jsonb` 의 기능(개정별 검토 모델 목록)은 이 테이블을 개정 ID 로 묶어 조회하면 얻는다. API 응답에서는 `review_models: [{model, provider, verdict, cross_company, at}]` 배열로 합쳐 내려 주어 화면 입장에서는 jsonb 와 같다.
- 대안(검토 요약을 `project_document_heads` 에 비정규화): 목록 화면 성능이 문제일 때만 `heads.review_state text` 를 추가한다. 처음에는 두지 않는다.

### 5-3. 임계값 설정 저장
`app_settings` 류 기존 설정 저장소가 있으면 거기에 `doc_tier.long_chars=15000`, `doc_tier.split_chars=50000` 을 둔다. 없으면 `runner_model_config` 에 `DOC_TIER_RULES` 행(models jsonb 에 객체) 억지 저장은 하지 않고 환경변수로 시작한다 — 구현 단계에서 기존 설정 저장소를 확인해 확정(미결정).

구버전 대시보드 동작 확인점(`src/app/settings/page.tsx`): `SIZE_ORDER.indexOf(a.size)` 가 모르는 size 에 `-1` 을 돌려 새 행이 맨 앞으로 정렬된다. 기능은 깨지지 않지만 순서가 어색하다 → 대시보드 변경(M4)에서 `SIZE_ORDER` 에 새 키를 추가한다. 구버전이 PUT 할 때는 받은 `configs` 를 전부 되돌려 보내므로 새 행 값이 그대로 유지된다(손실 없음).

### 6-2. 정본 문서 API (`/api/v1/projects/{project}/documents`)
- `POST` 등록: 요청 모양 변경 없음. 응답에 `doc_tier`, `author_model`, `author_provider` 추가(FR-7). `author_model` 은 서버 채움(FR-2): `source_task_id` → `pipeline_jobs.actual_model`.
- `GET` 목록·상세: 각 항목/개정에 `doc_tier`, `author_model`, `author_provider`, `review_models[]`, `review_state`(`not_required`·`pending`·`blocked`·`passed`·`rejected`) 추가.
- `GET /review-queue`: D1 제외(FR-13), `SPLIT` 제외(FR-14), 각 항목에 `doc_tier`·`review_state`.
- `POST /{document_key}/review`(초안→검토): §6-4 비소급 조건 확인 후 `review_revision_in_tx` 내부 공통 게이트에서 `D2/D3` 의 `review_state='passed'` 를 확인하고 아니면 `409 cross_review_required`(한글 사유 동봉). `D1` 은 전환 불필요.
- 신규 `POST /{document_key}/cross-review`: tenant/project 접근 및 PM·시스템 권한을 확인하고 비동기 검토 job을 예약(202 + job_id)한다. 초안 등록과 분리하며 실행·기록 순서는 §6-5를 따른다.
- `approve`: §6-4 면제 개정은 종전 승인 흐름 유지. 신규 정책 D2·D3는 필수 역할 모두 통과해야 하며 D3는 단순 pass 2행 개수로 판정하지 않는다.

### 6-3. 채팅 도구 `canonical_document_review` 연결
`canonical_document_tools.review_document` 는 `review_revision_in_tx` 를 직접 부른다. 교차 검토 강제를 **`review_revision_in_tx` 내부 공통 함수** 에 넣으면 API 경로와 도구 경로가 같은 게이트를 지난다(제약 8). 도구 응답에 `doc_tier`·`review_state` 를 추가해 PM 세션이 사유를 한글로 받는다. 도구 스키마(`tool_registry.py`)는 입력이 그대로라 변경하지 않는다.

### 6-4. 비소급 게이트와 기존 검토 대기 보호

- 정책 활성화 이후 생성된 개정에만 `doc_tier`와 `review_policy_version`을 등록 시 고정한다. 기존 개정은 변경하지 않는다. `doc_tier IS NULL` 또는 정책 버전 NULL인 개정은 review·approve·큐 필터 모두 새 게이트에서 면제한다. 길이 초과 기존 문서도 소급 반려하지 않는다.
- 기존 review 대기는 종전 승인 가능 상태를 유지하고 review 재호출의 멱등 성공도 보존한다. 신규 정책의 멱등 반환은 동일 개정·정책의 검토 증거 확인 후에만 허용한다. 새 개정이 만들어졌을 때만 새 정책으로 전환한다.
- 기록 → 등급 → 비동기 실행 검증 → 신규 개정에 한정해 강제 순서로 도입한다. 등록은 모델 장애·상한과 무관하게 초안을 저장한다. 활성화 전후 기존 대기 문서의 key/revision/마지막 상태/승인 포인터를 읽기 전용으로 대조한다. 지시서의 대기 10건은 실측값이 아니다.
- D1은 검토 기록을 유지하되 승인 포인터를 자동으로 올리지 않는다. `approved_brief`는 승인 문서만 반환하는 종전 계약을 유지하고 D1은 일반 정본 목록·상세에서 참조한다.

### 6-5. 잠금 밖 LLM 실행과 기록 무결성

1. 짧은 트랜잭션에서 권한 확인 후 head를 잠그고 tenant/project/head/revision/content_hash/generation/정책 버전·모델 목록·역할을 스냅샷으로 잡는다. 멱등 키는 tenant/project/revision/정책/실행 묶음/역할/시도로 구성한다. 트랜잭션을 종료하고 연결·잠금을 해제한다.
2. 워커가 스냅샷으로 LLM을 호출한다. 모델 대기·재시도 동안 DB 트랜잭션이나 head 잠금을 유지하지 않는다. 기존 CLI 중계 실행 경로를 재사용하고 tenant/user 사용량 문맥을 전달한다. API 모델 확장 시 중앙 `call_llm_with_fallback()` 및 LiteLLM을 사용한다. OAuth AUTH_TOKEN → API_KEY_FALLBACK → Gemini LiteLLM 순서를 유지하며 직접 REST·새 인증 키 참조를 도입하지 않는다.
3. 새 트랜잭션에서 권한과 head 잠금을 재획득하고 스냅샷의 모든 식별자·해시·generation·정책을 재검증한다. 변경됐으면 stale 결과로 격리하여 통과 증거로 쓰지 않고 새 검토를 요청한다. 승인 포인터는 검토 작업에서 변경하지 않는다.
4. 실제 실행 모델·회사를 재판별해 역할과 상위 모델 요건을 검사하고 추가 전용 결과를 기록한다. unknown 실제 모델은 성공으로 인정하지 않는다. 동일 실행 묶음·정책·개정의 필수 역할이 모두 pass여야 통과하며 재시도 중복 pass나 다른 묶음의 pass를 합치지 않는다. reject/실패 후 재검토는 새 묶음으로 수행한다.
5. 구현 시 reviews에 실행 묶음·시도·정책·해시·멱등 고유키를 추가하고 개정의 `(id,tenant_id,project_key)` 복합 FK로 스코프를 강제한다. 후보 없는 blocked는 reviewer 필드를 nullable로 바꾸고 blocked일 때만 NULL을 허용하는 CHECK를 둔다. CEO 예외는 권한·사유와 함께 별도 증거로 남긴다. §5-2 SQL은 이 보완까지 포함해야 구현 완료다.

## 7. 러너와의 연결 (작성 모델 기록)

1. 러너가 문서를 쓸 때 `pipeline_jobs.actual_model` 이 기록된다(기존 컬럼). 등록 API 가 `source_task_id` 로 이를 읽어 `author_model` 을 채운다.
2. 러너 job 이 아닌 경로(채팅 세션, 수동)는 `author_model='unknown'`. 채팅 세션 모델 추적은 M1 범위 밖으로 두고 `unknown` 정책(두 회사 각 1개)으로 안전하게 처리한다.
3. 같은 문서에 러너가 모델 폴백으로 중간에 모델을 바꾼 경우 `actual_model`(최종 실행 모델)을 쓴다. 전환 이력은 job 쪽에 남아 있다.

## 9. 시험 계획 (구현 단계)
- 등급 함수 경계값 표(14,999/15,000/15,001/50,000/50,001자 × 종류 9개 × 목표 연결 유무).
- 회사 판별: 현재 DB 의 모델 ID 7종 고정.
- unknown D1/D2/D3 각각 두 회사 필수, 한 회사 결손 차단, D3 상위 모델·작성 모델 제외 검증.
- 비소급 NULL 개정의 review/approve 및 기존 대기 멱등성, 잠금 해제 중 개정 변경의 stale 차단, 감사 보존 롤백과 CHECK up/down 중단 조건 검증.
- 선택 알고리즘: (작성 anthropic/openai/unknown) × (목록에 한 회사만/둘 다/비어 있음) × (사용 불가 모델 포함).
- 구버전 PUT 재생: 기존 6개 size 만 담은 요청이 그대로 성공, 새 행 값 보존.
- 불변 트리거: 검토 결과를 개정 행에 쓰려는 시도가 실패함을 확인하고, 검토 테이블에는 기록됨을 확인.
