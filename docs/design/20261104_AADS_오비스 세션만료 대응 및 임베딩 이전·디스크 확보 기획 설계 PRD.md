# 오비스 세션만료 대응 및 임베딩 이전·디스크 확보 기획 설계 PRD

- document_key: `aads-session-expiry-embedding-offload-disk-prd-20261104`
- 종류: PRD (기획 설계) · 상태: 초안 · 작성: 2026-11-04 KST
- 대상 서버: contabo116(vmi3267555, AADS 운영) · 보조: 카페24 server-114
- 시각은 모두 KST 다.

## 1. 배경

2026-11-04 대표님이 "오비스(aads)가 계속 세션 만료로 재로그인을 요청한다"고 보고했다.
조사 결과 세션이 실제로 만료된 것이 아니었다. 서버 과부하로 생긴 일시 장애(504)를
대시보드가 로그아웃으로 처리한 것이었다. 그 과부하의 큰 몫이 로컬 임베딩(ollama)이었고,
조사 중 ollama 가 인증 없이 인터넷에 열려 있다는 보안 문제와, 디스크 98% 포화가
함께 드러났다.

## 2. 문제 정의와 실측 근거

### 2.1 반복 재로그인 (P0)

| 관측 | 값 |
|---|---|
| `/api/v1/auth/me` 504 (nginx `upstream timed out`) | 12:17:20, 13:15:56, 13:36:25, 13:38:13, 13:39:13, 13:40:04, 13:48:34 (7회) |
| 401 연쇄 시작 | 6회, 모두 504 직후 1~2초 내 |
| 401 응답 크기 | 73B = "인증이 필요합니다(토큰 없음)" — 토큰 만료/무효(72B/26B)는 0건 |

인과 사슬은 다음과 같다.

1. 호스트 CPU 포화: 8코어, 실행 CPU 30분 평균 98.9%, PSI some 80%.
2. API(uvicorn 워커 1개) 이벤트 루프가 약 30초마다 5~14초 멈춘다(apscheduler "missed by").
3. nginx `location = /api/v1/auth/me` 의 `proxy_read_timeout 15s` 를 넘겨 504 가 난다.
4. 대시보드 `src/lib/auth.ts` `getMe()` 가 `!res.ok` 전부를 `logout()` 으로 처리해 토큰을 지운다.
5. 이후 모든 요청이 토큰 없는 401 이 되고, 화면이 "세션 만료"로 재로그인시킨다.

### 2.2 CPU 포화 기여

| cgroup | CPU (1코어=100%) |
|---|---|
| ollama.service (임베딩) | 약 243% |
| aads-pipeline-runner.service | 약 186% |
| aads-server-green (운영 API) | 약 168% |
| aads-postgres | 약 96% |

임베딩은 30분에 185건을 받았는데, 다수가 5분 대기 한도(`LOCAL_OLLAMA_TIMEOUT_SEC=300`)에서 실패했다.

### 2.3 보안: ollama 외부 노출

- `OLLAMA_HOST=0.0.0.0:11434`, 방화벽 규칙 없음. 외부(114)에서 200 응답을 확인했다.
- 7일간 외부 IP 수십 곳이 생성 요청을 약 1,500건 보냈다(하루 약 250건). 대부분 401/400 이었고 **200 이 44건** 있었다.
- 우리 서버의 정상 외부 사용은 없었다(시험 2건 제외).

### 2.4 디스크 포화

`/` 193G 중 188G 사용(98%, 여유 5.5G)이었고, 조사 시점에 정리 타이머가 돌아 174G(90%)로 내려왔다.
대시보드 이미지 빌드(1.3GB 이미지, 빌드 중 수 GB 사용)조차 위험한 수준이다.

## 5. 설계

### 5.1 A. 대시보드 인증 처리 (G1) — 완료

- `getMe()` 는 401/403 에서만 `logout()` 한다.
- 5xx·네트워크 오류에서는 토큰을 유지하고, 같은 토큰으로 직전에 확인된 사용자를 돌려준다. 관리자 화면이 "권한 없음"으로 튕기는 것을 막기 위해서다.
- 회귀 테스트 `src/lib/authGetMe.test.ts` 9건. 구 코드에서 5건이 실패하는 것을 확인했다.
- 커밋: aads-dashboard `26d115b9607e`. 배포는 deploy_runs #5964, 14:21 cutover(green), 5분 P0/P1 모니터링 통과(14:27). 운영 green·대기 blue 번들 모두에 반영된 것을 확인했다.

### 5.2 B. nginx `/auth/me` 읽기 한도 (G2) — 완료

- `nginx-aads-safe-api-failover.conf` 의 `proxy_read_timeout` 을 15초에서 30초로 바꿨다.
- 공용 nginx 잠금 아래 백업, `nginx -t`, reload 순서로 적용했다(14:06). 백업 파일: `/root/aads/backups/nginx-aads-safe-api-failover.inc.pre_authme30s_20261104`.
- 커밋: aads-server `f0574c4c`, 테스트 `test_auth_me_read_timeout_outlasts_api_stalls`.
- 이것은 보조 조치다. 근본 원인인 이벤트 루프 정체는 5.6 과 별도 과제로 다룬다.

### 5.3 C. ollama 외부 노출 차단 (G3) — 완료

- iptables INPUT 규칙을 추가했다. 기존 `aads-relay-8199` 와 같은 구조다.
  - v4: `lo`, `127.0.0.0/8`, `172.16.0.0/12`(도커) 허용, 그 외 11434 DROP
  - v6: `lo` 허용, 그 외 11434 DROP
- `/etc/iptables/rules.v4|v6` 에 저장했고, 백업은 `*.bak-20261104-ollama11434` 이다.
- 검증: 114 에서 v4/v6 접속 시 000(차단), 컨테이너와 호스트 로컬은 200.
- 5.4 이후 ollama 자체가 `127.0.0.1` 에만 바인딩하므로 이중으로 막힌다.

### 5.4 D. 임베딩 카페24 이전 (G4) — 완료

**구조**

```
aads-server(-green) 컨테이너
  └─ http://host.docker.internal:11434  (= 172.17.0.1:11434)
       └─ aads-ollama-cafe24-tunnel.service (ssh -L, 116 → server-114:7916)
            └─ server-114 ollama 127.0.0.1:11434 (nomic-embed-text, qwen3-embedding:0.6b)
116 로컬 ollama: 127.0.0.1:11434 전용(비상용, 외부·컨테이너에서 안 보임)
```

**코드나 환경변수를 바꾸지 않은 이유.** `LOCAL_OLLAMA_URL` 로 주소를 바꾸려면 API 컨테이너를
다시 만들어야 한다. 지금 API 를 재배포하면 다른 러너가 올려 둔 미배포 커밋(운영 `ebc1cefb` → origin/main)까지
함께 나간다. 그래서 컨테이너가 이미 쓰는 주소(172.17.0.1:11434)를 네트워크 쪽에서 카페24로 연결했다.

**사전 검증**

| 항목 | 결과 |
|---|---|
| 114 사양 | AMD EPYC 7262 8코어, RAM 15G(여유 12G), load 1.5, PSI 1% 미만 |
| 모델 지문 | `nomic-embed-text` 0a109f422b47, `qwen3-embedding:0.6b` ac6da0dfba84 — 116과 동일 |
| 벡터 동일성 | 두 모델 모두 cosine 1.0 |
| 지연 | 카페24 1.1~1.6초 vs 116 로컬 34~74초(같은 입력) |
| RTT | 약 40ms (묶음 처리라 영향 미미) |
| 컨테이너 사용 형태 | 24시간 `/api/embed` 만 3,193건. 생성(`:cloud`) 호출은 없음 |

**전환**: 14:25:43~45, 끊김 약 2초. 영구 저장 호출자는 임베딩 경로가 없으면 예외를 내므로 가짜 벡터가 저장되지 않는다.

**구성 파일**

- `/etc/systemd/system/aads-ollama-cafe24-tunnel.service` (enabled, Restart=always)
- `/etc/systemd/system/ollama.service.d/zz-aads-localhost-only.conf` (`OLLAMA_HOST=127.0.0.1:11434`)
  - 다른 drop-in(`override.conf`, `parallel.conf`)이 `0.0.0.0` 을 지정하므로, 이름을 `zz-` 로 해서 마지막에 적용되게 했다.

**롤백 (1분 이내)**

1. `rm /etc/systemd/system/ollama.service.d/zz-aads-localhost-only.conf && systemctl daemon-reload`
2. `systemctl stop aads-ollama-cafe24-tunnel` → `systemctl restart ollama`
3. 확인: `ss -ltn | grep 11434` 에서 ollama 가 `*:11434`. 방화벽 규칙은 유지한다.

**운영 주의**

- 터널이 끊기면 컨테이너 임베딩이 실패한다. systemd 가 10초 후 재연결한다. 장시간 장애에는 롤백 절차로 로컬로 되돌린다.
- 114 는 보관 서버를 겸한다. 임베딩 부하로 114 PSI 가 20%를 넘으면 `OLLAMA_NUM_PARALLEL` 을 제한하거나 contabo92(12코어·47G, 같은 데이터센터 RTT 1~2ms)로 옮기는 안을 검토한다.

**효과(초기 실측)**: ollama.service CPU 약 243% → 0%, CPU PSI some avg10 80% → 48%. 사후 incident 로 확정한다(9장).

#### 기존 정리 장치가 놓치는 것

1. **태그 달린 옛 릴리스 이미지**: `disk_cleanup.sh` 는 dangling 이미지만 지운다. `aads-server` 옛 태그 3개가 남아 있고, 그중 2개(`1f9f…`, `a55b…`)는 6일·9일째 끝나지 않은 pytest 컨테이너(`sharp_borg`, `jovial_albattani`)가 붙잡고 있다.
2. **빌드 중 정리 보류**: 러너 빌드가 잦아 `disk_cleanup.sh` 가 "build active; deferred" 로 자주 건너뛴다(최근 기록 "Files removed: 0" 반복).
3. **빌드 전 디스크 게이트 없음**: 대시보드 `deploy.sh` 에 여유 공간 확인이 없다. 여유 5G 상태에서도 빌드를 시작한다.
4. **로컬 덤프 유지**: 카페24 오프로드가 검증된 뒤에도 최신 덤프 1부(8.6G)가 루트 디스크에 남는다.
5. **보관 정책 없는 누적**: `logs/archive`, `state/component-releases` 의 보존 기한이 정해져 있지 않다.

### 5.6 F. CPU 우선순위 (G6) — 제안, 승인 필요

- `aads-pipeline-runner.service` 등 비대화형 작업의 systemd `CPUWeight` 를 낮춘다(기본 100 → 예: 30). API·DB 컨테이너가 CPU 경쟁에서 먼저 받게 한다.
- `CPUWeight` 는 CPU 가 남을 때는 제한하지 않는다. 할당량(quota)이 아니다.
- 적용 전후로 `aads-cpu incident` 를 남기고 `aads-cpu record-action` 으로 기록한다. 되돌리기는 drop-in 삭제 후 `daemon-reload` 다.
- 후속 과제(별도 PRD): API 이벤트 루프를 막는 무거운 처리(목표 조회 15~20초 등)를 스레드나 프로세스로 넘긴다. 예약 작업을 별도 프로세스로 분리한 뒤 API 워커를 늘린다.

## 10. 용어

- **임베딩**: 문장을 숫자 벡터로 바꾸는 작업. 문서·채팅 검색에 쓴다.
- **PSI**: CPU 를 기다리느라 작업이 지연된 시간의 비율. CPU 사용률 100%와는 다르다.
- **이벤트 루프**: 요청을 한 줄로 번갈아 처리하는 방식. 하나가 오래 잡으면 뒤의 요청이 모두 기다린다.
- **SSH 터널**: 포트를 외부에 열지 않고 SSH 연결 안으로 다른 서버의 포트를 끌어오는 방식.
- **CPUWeight**: CPU 가 부족할 때 누구에게 먼저 줄지 정하는 비중. 할당량(quota)과 다르다.
