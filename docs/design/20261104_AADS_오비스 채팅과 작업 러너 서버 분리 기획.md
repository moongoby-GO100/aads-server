# 오비스 채팅과 작업 러너 서버 분리 기획

- document_key: `aads-chat-runner-server-split-plan`
- 종류: 기획(plan) · 상태: 초안 · 작성: 2026-11-04 KST
- 관련: `aads-session-expiry-embedding-offload-disk-prd` (같은 날 세션만료·임베딩 이전·디스크 PRD)
- 전제: contabo92 는 GO100 전용으로 추가된 서버라 후보에서 제외한다(대표님 지시 2026-11-04).

## 1. 결론 요약

1. 116 한 대가 **사용자용 오비스 채팅**과 **AADS 작업 러너**를 함께 돌리고 있다. 러너가 CPU의 약 70%를 쓰고, 채팅은 그 경쟁에 밀려 느려진다(오늘 재로그인 사고의 출발점).
2. 옮기기 쉽고 효과가 큰 쪽은 **러너**다. 채팅은 DB(18GB), 컨테이너, 인증서, 도메인, PC 에이전트 연결이 116에 묶여 있다. 러너는 이미 다른 서버(contabo14·카페24)에서 같은 방식으로 돌고 있다.
3. 권장: **AADS 전용 러너 서버를 116과 같은 데이터센터에 새로 두고 러너를 옮긴다.** 116은 채팅 전용으로 남긴다. 배포(블루/그린)는 컨테이너가 있는 116에서 계속 실행한다.
4. 새 서버가 준비되기 전에는 116 안에서 러너 상한과 우선순위를 낮춰 채팅을 보호한다(0단계).

## 3. 대안 비교

| 안 | 내용 | 116 CPU 효과 | 작업량·위험 | 비용 |
|---|---|---|---|---|
| A | 116 안에서 조정: 러너 상한 20→10, 러너 CPUWeight 하향 | 부분(채팅 우선 확보) | 작음·즉시·되돌리기 쉬움 | 없음 |
| **B** | **AADS 러너를 신규 전용 서버로 이전**, 배포만 116에서 | **약 540% 회수**(러너 전부) | 중간(러너 설치 + 배포 연결) | 서버 1대 |
| C | 카페24(114)에 AADS 러너 일부(상한 2~3) | 소폭 | 중간·114 RAM 부족 위험 | 없음 |

D 가 채팅을 가장 깨끗이 떼어내지만, 사용자 서비스 전체를 옮겨야 해서 중단 위험과 작업량이 가장 크다. 116 의 cron·백업·오프로드·nginx·인증서가 모두 채팅 스택을 전제로 짜여 있다. B 는 이미 검증된 원격 러너 방식을 재사용하고, 실패하면 러너를 116에 다시 켜면 된다.

## 4. 권장안: 0단계(A) → 1단계(B), 필요하면 2단계

### 0단계 — 즉시, 비용 없음 (116 내부 조정)

- `runner_host_policy` 에서 vmi3267555(116) `max_concurrent` 를 20 → 10 으로 낮춘다. 러너가 다음 주기에 반영한다. 되돌리기는 값 복원.
- `aads-pipeline-runner.service` 에 systemd drop-in `CPUWeight=30` 을 둔다(기본 100). CPU 가 남을 때는 제한하지 않는다. 적용 전후로 `aads-cpu incident` 와 `record-action` 을 남긴다.
- 기대: 채팅 API·DB 가 CPU 경쟁에서 우선. 러너 대기시간은 늘어난다.

### 1단계 — AADS 전용 러너 서버 (1~2주)

1. 서버 준비: 116과 같은 데이터센터, 12코어·48GB·디스크 400GB 이상(저장소 16GB + 워크트리 + 테스트 이미지·빌드 캐시).
2. 러너 설치: 카페24·contabo14 와 같은 원격 러너 방식.
   - DB: 116 PostgreSQL 로 SSH 터널(PGHOST). 같은 데이터센터라 지연 1~2ms.
   - 인증: `aads-claude-lease-push` 대상에 새 서버 추가.
   - 저장소: aads-server·aads-dashboard 복제, 커밋 훅(서명) 설치.
   - 테스트: 테스트 의존성(`.testdeps`)과 테스트용 이미지 준비. 이미지는 SHA 기준으로 새 서버에서 빌드하거나, 116 이미지를 `docker save | load` 로 전달.
3. 배포 연결(코드 수정): 원격 러너는 `deploy.sh bluegreen` 을 직접 실행하지 않고 116에 배포를 요청한다.
   - 방안 ①: 116 의 기존 DB 배포 대기열(deploy_runs queued + queue worker)에 넣고 결과를 기다린다.
   - 방안 ②: 116 에 SSH 로 `deploy.sh bluegreen` 실행(제한 키·명령 고정).
   - ① 을 권장한다. 배포 직렬화·락·인증 게이트가 이미 그쪽에 있다.
4. 전환: 새 서버 러너를 AADS 상한 2로 시작 → 하루 관찰 → 116 러너 상한을 줄이며 새 서버를 늘린다 → 116 러너 상한 0(배포 대기열 작업자만 유지).
5. 되돌리기: 116 러너 상한 복원, 새 서버 러너 중지. 작업 DB 가 한 곳이라 진행 중 작업은 다른 러너가 이어받는다.

**기대 효과**: 116 CPU 의 약 70%(러너·테스트·도커) 회수 → 채팅 전용으로 여유 확보. 디스크도 /tmp 러너 워크트리(약 13GB)와 빌드 캐시가 빠진다.

### 2단계 — 필요할 때만

- 1단계 후에도 채팅이 부족하면, 그때 D(채팅 스택 이전) 또는 116 사양 상향을 검토한다.
- API 이벤트 루프 정체(목표 조회 15~20초)는 서버를 바꿔도 남는다. 별도 과제로 무거운 처리를 스레드·프로세스로 넘기고, 예약 작업을 분리한 뒤 API 워커를 늘린다.

## 5. 위험과 대응

| 위험 | 대응 |
|---|---|
| 원격 러너의 DB 터널 끊김 | autossh/systemd 재연결. 기존 원격 러너와 같은 방식 |
| 배포 요청-결과 연결 실패로 작업이 멈춤 | 배포 대기열 결과를 작업 상태에 반영하는 시간 상한·알림. 실패 시 116 러너 상한 복원 |
| 테스트 이미지 불일치(새 서버와 116) | 릴리스 SHA 기준 이미지 digest 비교를 테스트 전에 확인 |
| 인증 슬롯 동시 사용 증가 | 서버별 상한 합계를 기존 20 이내로 유지 |
| 116 에 남는 배포 빌드 부하 | 배포는 하루 수 회. 디스크 게이트(오늘 추가)와 빌드 캐시 정책 유지 |

## 6. 결정 필요 사항

1. 0단계(러너 상한 20→10, CPUWeight 30) 즉시 적용 여부
2. 1단계 신규 러너 서버 도입 여부와 사양(권장: 116과 같은 데이터센터, 12코어·48GB·400GB)
3. server-211 의 용도·접속 정보(후보 검토용)
4. 배포 연결 방식(권장 ①: DB 배포 대기열)

## 7. 용어

- **러너**: 대표님이 지시한 개발 작업을 받아 코드 수정·테스트·커밋·배포까지 자동으로 돌리는 작업자.
- **PSI**: CPU 를 기다리느라 작업이 지연된 시간의 비율. CPU 사용률 100%와는 다르다.
- **CPUWeight**: CPU 가 부족할 때 누구에게 먼저 줄지 정하는 비중. 상한(quota)과 달리 남는 CPU 는 막지 않는다.
- **배포 대기열**: 배포 요청을 DB 에 쌓아 두고 116 의 작업자가 하나씩 처리하는 장치. 동시에 두 배포가 돌지 않게 한다.
