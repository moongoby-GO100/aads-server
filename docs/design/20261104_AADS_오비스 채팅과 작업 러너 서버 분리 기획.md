# 오비스 채팅과 작업 러너 서버 분리 기획

- document_key: `aads-chat-runner-server-split-plan`
- 종류: 기획(plan) · 상태: 초안 r2 · 작성: 2026-11-04 KST
- 관련: `aads-session-expiry-embedding-offload-disk-prd` (같은 날 세션만료·임베딩 이전·디스크 PRD)
- r2 변경: 대표님 지시 반영 — "contabo14 만 제외하고 모두 포함, 한가한 서버가 우선 받는 방식". 전용 러너 서버 신규 도입안을 범용 러너 풀로 바꿨다. server-211·jinah244 는 폐기 서버라 후보에서 뺐다.

## 1. 결론 요약

1. 116 한 대가 **오비스 채팅**과 **AADS 작업 러너**를 함께 돌린다. 러너가 CPU 의 약 70%를 쓰고, 채팅은 그 경쟁에 밀려 느려진다(오늘 재로그인 사고의 출발점).
2. 채팅은 116에 둔다. 작업(코드 수정·테스트·커밋)은 **프로젝트와 상관없이** contabo14 를 뺀 모든 서버가 나눠 받는다. **한가한 서버가 먼저 가져간다.**
3. 배포는 그 프로젝트의 서비스가 있는 서버(배포 서버)가 한다. 러너는 배포를 직접 하지 않고 배포 서버에 요청한다.
4. 지금 자원(92·카페24·116)으로 **동시 약 18건**을 처리할 수 있다. 예상 평균(15건 이하)을 새 서버 없이 감당하지만 여유는 크지 않다. 평균이 15건을 꾸준히 넘으면 서버 1대 추가를 검토한다.

### 2.2 116에서 누가 CPU 를 쓰는가 (15:3x KST 측정, 1코어=100%)

| 구분 | 구성 | CPU | 비중 |

### 2.3 지금 러너 구조

```
오비스 채팅(116) ──작업 등록──▶ 작업 DB(116, pipeline_jobs)
                                   ▲  각 러너가 DB 를 보고 작업을 가져감
          ┌────────────────────────┼────────────────────────┐
     116 러너(AADS)          contabo14 러너(GO100)     카페24 러너(SF·NTV2·NAS)
```

- 채팅은 이미 프로젝트와 상관없이 작업을 한 DB 에 등록한다. 원격 러너도 DB 터널로 작업을 가져간다(contabo14·카페24 에서 운영 중).
- 막혀 있는 이유는 두 가지다.
  1. 러너마다 `RUNNER_PROJECTS` 필터로 지정된 프로젝트만 가져간다(`pipeline-runner.sh` 의 `project_filter`).
  2. 작업에 그 서버의 저장소 경로(`TARGET: /root/aads/aads-server`)가 들어 있고, 러너가 배포를 **자기 서버에서 직접** 실행한다(`bash "$worktree_dir/deploy.sh" bluegreen`).

## 4. 수용량 산정

### 4.1 기준

- 작업 1건당 **CPU 약 0.6코어, 메모리 약 0.7GB**. 116에서 11건 실행 중 약 5.4코어를 쓴 실측에서 나왔다. CPU 경쟁 상태의 값이라 전용으로 돌면 더 빨리 끝난다.
- 서버마다 CPU 25%를 여유로 남기고, 그 서버의 기존 업무 몫을 먼저 뺀다.
- AADS 작업을 받는 서버는 저장소(약 20GB)·테스트 이미지·캐시로 **디스크 약 50GB**가 따로 필요하다.

### 4.2 서버별 (2026-11-04 15시대 측정)

| 서버 | 사양 | 현재 상태 | 기존 업무 몫 | 가능 동시 작업 | 시작 상한 |
|---|---|---|---|---|---|
| contabo92 | 12코어·47GB·여유 764GB | load 2~4, PSI 3% | GO100 DB 약 2코어 | 약 10 | 4 |
| 카페24 114 | 8코어·15GB·여유 220GB | load 2.4, PSI 5% | 보관·임베딩 약 2.5코어 | 약 5 | 3 |
| 116 | 8코어·23GB·여유 14GB(93%) | load 19~24, PSI 75% | 채팅 우선 | 약 3 | 3 |
| **합계** | | | | **약 18** | 10 |

- 평균 15건은 여유 있게 처리한다. 몰리면 대기열에 쌓였다가 한가해지는 서버부터 가져간다.
- 116 은 혼자 11~20건 → 3건으로 줄어 CPU 약 4~5코어가 채팅에 돌아간다.
- 평균이 15건을 꾸준히 넘으면 서버를 늘린다. 116과 같은 데이터센터, 8코어·24GB·디스크 400GB 이상이면 약 10건이 늘어난다.

## 5. 구현 계획

### 되돌리기

- 서버별 상한을 0으로 두면 그 서버는 작업을 가져가지 않는다. 116 상한을 원래 값으로 복원한다.
- 작업 DB 가 한 곳이라 진행 중 작업은 남은 러너가 이어받는다.

## 7. 결정 필요 사항

1. 0단계(116 러너 상한 20→10, CPUWeight 30) 즉시 적용 여부
2. 시작 상한(92=4, 114=3, 116=3)과 PSI 기준(40%) 승인
3. 폐기 서버 jinah244 에서 아직 돌고 있는 오비서 서비스의 정리 여부(이 기획 범위 밖, 확인 요청)

## 8. 용어

- **러너**: 대표님이 지시한 개발 작업을 받아 코드 수정·테스트·커밋·배포까지 자동으로 돌리는 작업자.
- **작업 서버 / 배포 서버**: 코드를 고치고 테스트하는 서버 / 실제 서비스를 갱신하는 서버. 이 기획에서 붙인 이름이다.
- **PSI**: CPU 를 기다리느라 작업이 지연된 시간의 비율. CPU 사용률 100%와는 다르다.
- **CPUWeight**: CPU 가 부족할 때 누구에게 먼저 줄지 정하는 비중. 상한(quota)과 달리 남는 CPU 는 막지 않는다.
- **배포 대기열**: 배포 요청을 DB 에 쌓아 두고 배포 서버의 작업자가 하나씩 처리하는 장치. 동시에 두 배포가 돌지 않게 한다.
