### 3-1. 대안 비교와 선택 이유

**(가) 메뉴 구조: 현행 구조 개선안 vs 메뉴 재편안**

| 기준 | 현행 구조 개선(27개 유지, 중복 payroll 제거·상단 탭 정리만) | 메뉴 재편(업무 묶음 5 + 설정 1, 채택안) |
|---|---|---|
| 사용자 이점 | 기존 위치 학습 유지. 단 27개 탐색 부담·"클로브 기능 단위" 경계(A6)는 그대로 | 업무 흐름(검토→확정→마감) 순서로 찾음. 모바일 하단 탭 5개로 대응 가능 |
| 구현 비용 | 작음(라벨·중복 제거). 홈 신설은 별도 | 중간. `data-view` 키는 유지하므로 라우팅·딥링크·테스트는 그대로, 마크업·그룹·라벨만 변경 |
| 성능 | 변화 없음 | 변화 없음(정적 마크업 재배치) |
| 유지보수 | 메뉴 2벌(좌측·상단) 유지 → 한쪽만 고치는 사고 반복 | 하위 탭 하나로 통합, 분기점 4→2개 |
| 위험 | 낮음 | 기존 사용자 재학습, 단일 파일 충돌 → §11·§12 직렬 체인·롤백으로 관리 |
| 선택 | 비채택 | **채택.** 이유: 현행 개선만으로는 A1·A2·A6 중 A6(업무 흐름 불일치)과 모바일 상단 탭 13개 문제가 남는다. `data-view` 키 보존으로 재편 비용과 회귀 위험이 제한되고, 재학습 부담은 라벨 옆 기존 이름 병기와 localStorage 복원으로 줄인다. |

**(나) 집계 방식: 프론트 병렬 집계 vs 서버 집계 API(`/home-summary`)**

| 기준 | 프론트 집계(채택, 1차) | 서버 집계 API(2차 후보) |
|---|---|---|
| 초기 요청 부담 | 홈 진입 시 요청 11개 병렬(§5-1). 브라우저 동시 연결 한도 안이나, 목록 API 가 전체 행을 내려주므로 응답 크기가 큼 | 요청 1개, 응답은 숫자 위주로 작음 |
| 부분 실패 | `Promise.allSettled` 로 카드별 독립 처리 — 실패 카드만 오류 상태(§6), 나머지는 정상 표시 | 한 번의 실패가 전체 실패가 되기 쉬움. 카드별 부분 성공 필드를 따로 설계해야 함 |
| 집계 일관성 | 요청별 시점이 달라 카드 간 수 초 차이 가능. 완화: 요청 시작 시각 1회 고정, 캐시 60초(`HOME_RELOAD_MS`) | 한 트랜잭션·한 시각 기준으로 일관 |
| 구현 비용 | 서버 변경 없음, 기존 권한 의존성 그대로 | 신규 라우터·서비스·권한 검증·테스트, 별도 릴리스 |
| 유지보수 | 집계 규칙이 프론트에 있어 규칙 변경이 정적 파일 배포로 끝남. 단 규칙이 화면 코드에 분산 | 규칙이 서버 한 곳에 모이나 API 계약 변경 시 서버·프론트 동시 배포 |
| 선택 | **1차 채택.** 이유: 기존 API·권한 검증을 그대로 재사용해 위험이 가장 작고 카드별 부분 실패 격리가 쉽다. 응답 크기와 일관성이 문제로 확인되면 2차로 전환한다. |  |

전환 임계값(하나라도 해당 시 서버 집계 착수): 홈 첫 화면 완료 p95 > 1.5초, 또는 홈 요청 합계 응답 크기 > 1MB, 또는 카드 간 불일치 사용자 신고 2건 이상. 측정은 L5 에서 PC/모바일 각 10회 이상 수행한다(현재는 측정 안 함).

## 4. 정보구조(IA)·메뉴 재편

27개 → **업무 묶음 5개 + 설정 1개**(아래 표 기준). 
**개수 기준(혼동 방지)**: 좌측 메뉴 최상위는 업무 묶음 5개(오늘, 돈 흐름, 검토·마감, 사람, 자료함) + 설정 1개 = 6항목이다. 모바일 하단 탭은 5개(오늘·돈 흐름·검토·사람·더보기)이며 "더보기"에 자료함·설정이 들어간다. 이 문서에서 "5개 묶음"은 설정을 제외한 업무 묶음 5개를 뜻한다.

### 5-1. 지표별 서버 API 계약

이 절은 코드를 직접 읽고 쓴 계약이다(경로·함수는 `파일:줄`로 근거를 단다). **코드에서 확인하지 못한 것은 '미확인'** 으로 표기하고 추정으로 채우지 않는다. 코드와 어긋나면 이 표를 먼저 고친다.

**원칙.** §5 의 요구 지표는 줄이지 않는다. 기존 API 로 정확히 만들 수 있는 지표만 기존 경로를 쓰고(A), 정확히 만들 수 없는 지표는 대체하지 않고 **신규 서버 집계 API 계약**(B)을 정의해 §10 의 L 단계 작업으로 구현한다. 구현 전 화면 표시는 §11 을 따른다(숫자 0 으로 두지 않는다).

**공통 사실(코드 확인)**

1. 재무 라우터 prefix 는 `/yeoljeong-finance`(`app/api/obys_finance.py:40`)이고 `/api/v1` 아래에 붙는다. 라우터 전체에 `require_legacy_obys_access` 가 걸린다(obys_finance.py:42, 정의 `app/core/obys_tenant.py:190`). 수집함 라우터는 `/obys-collections`(`app/api/obys_collections.py:21`, `app/main.py:4175` 에서 `/api/v1`).
2. 재무 원장 목록(`/sales` 등)은 서버 페이지네이션 없이 `{키: [...]}` 전체 목록을 준다. 합계·건수를 정확히 얻으려면 전체 행을 내려받아야 하므로, 행 수가 큰 지표는 신규 집계 API 가 맞다.
3. 표의 "전체" 는 스위처가 '전체'일 때의 의미이다. 기존 경로에서는 `business_id` 생략, 신규 집계 API 에서는 **사업자별 호출 후 프론트 합산**(아래 B-0)이다.

#### B. 신규 서버 집계 API 계약 3종

공통: 라우터 `/api/v1/yeoljeong-finance` 에 추가, `GET`, 읽기 전용, 관리자 전용, `business_id` 는 경로 필수. 사업자가 로그인 테넌트 소속이 아니면 404(소속 여부를 알리지 않음), 비관리자는 403. 응답 시각은 모두 `+09:00` 오프셋을 가진 ISO 8601(KST). 하위 집계 하나가 실패하면 그 키를 `null` 로 두고 `errors:[{key, code}]` 를 싣는다 — **0 으로 대신하지 않는다**.

**B-0. '전체' 합산 방식.** 프론트가 `/tenant-registry/businesses` 의 사업자 각각에 대해 호출해 더한다. 일부 사업자 호출이 실패하면 합계 옆에 "N개 사업자 조회 실패" 를 병기하고 합계는 성공분이라고 표시한다. 사업자 4개 기준 3종 × 4 = 12 호출이 추가되므로 L5 에서 §3-1(나) 임계값으로 측정한다.

**B-1. 검토 대기 — `GET /{business_id}/home/review-pending-count`** (정의: §1 의 '미확정 수집 자료')

- 의미를 분리한다. **홈 '검토 대기' 카드 = 수집함의 미확정 자료**(`obys_clobe_item.stage = 'review_box'`, 거래 검토함). **배달 고객 리뷰 답변 대기**(`delivery_reviews.reply_status`)는 서로 다른 데이터이므로 이름을 **'고객 리뷰 답변 대기'(보조 지표)** 로 바꿔 별도 표시하고 합산하지 않는다. 이 보조 지표는 기존 `/reviews`(A형, 위 표)로 계산하며, 행이 많아 §3-1(나) 임계값 대상이다.
- 기존 경로로 되는 부분: `today-overview` 의 `review_waiting.review_box` 는 `data_kind ∈ {bank_transaction, tax_invoice, cash_receipt, card_approval}` 이고 `stage = 'review_box'` 인 건수의 전체 합이다(obys_data_overview_service.py: `stage_rows` 질의와 `review_waiting`). 같은 서비스의 `list_items(stage=review_box)` 응답 `total`(obys_collection_service.py:944, 라우터 obys_collections.py:170)은 사업자 1곳의 건수다. 두 경로에는 **가장 오래된 시각도, 출처별 분해도, 최근 7일 건수도 없다.** 그래서 이 카드의 요구(2단 표기·오래된 항목 표시)는 기존 경로만으로 만들 수 없고 신규 계약이 필요하다.
- 요청: 파라미터 없음.
- 응답: `{"business_id": "...", "count": 123, "recent_7d": 18, "future_dated": 0, "oldest_at": "2026-10-02T09:14:00+09:00", "by_source": [{"data_kind": "bank_transaction", "institution": "신한", "count": 80}], "errors": []}`
- 집계: `obys_clobe_item` 에서 `tenant_id=로그인 테넌트 AND business_id=경로값 AND stage='review_box' AND data_kind ∈ DATA_KINDS`(obys_collection_core.py:20; `channel_revenue` 제외). `count` = 행 수, `oldest_at` = `min(first_seen_at)` 을 KST 로 변환, `recent_7d` = `KST오늘−6일 <= occurred_on <= KST오늘` 인 행 수(`occurred_on` 은 날짜 컬럼이라 변환 없이 비교. **상한 포함 양쪽 경계** — 미래 날짜 행은 `recent_7d` 에서 제외하되 `count` 에는 포함하고, 응답 `future_dated` 에 따로 센다), `by_source` = `data_kind`·`institution` 별 건수. 이전 판본으로 대체된 행은 `stage='superseded'` 라 `review_box` 에 섞이지 않는다.
- 클릭 이동: 검토·마감 › 검토할 거래(미검토 필터).

**B-2. 승인 대기 — `GET /{business_id}/home/approval-pending`**

- 왜 신규인가: 기존 세 경로를 합쳐서는 관리자 기준 합계가 안 된다 — 서명 대기는 관리자에게 항상 빈 목록(위 표), 서류 목록은 가상 행이 섞이고(검수 대기 상태는 `uploaded` 하나로 확정, 아래 표) `business_id` 필터가 경로마다 다르다.
- 응답: `{"business_id": "...", "join_requests": 2, "document_reviews": 5, "document_resubmit_waiting": 2, "unsigned_contracts": 3, "total": 10, "unassigned": {"join_requests": 0, "document_reviews": 0, "unsigned_contracts": 0}, "errors": []}`. `total` 은 세 값의 합(어느 하나가 `null` 이면 `total` 도 `null`).
- 각 항목의 원천·조건(모두 `_tenant_id` 의 테넌트 행만; 원장 이름은 `HR_TENANT_LEDGER_NAMES` svc:758):

| 항목 | 원천 | 조건 | 사업자 판정 |
|---|---|---|---|
| `join_requests` | `employee_join_requests` | `status = 'pending'`, `deleted_at` 없음, `archived` 아님(`_list_join_requests` svc:3260 의 제외 규칙과 동일) | 레코드의 `business_id`. 비어 있으면 `unassigned` |

**B-3. 은행 잔액 — `GET /{business_id}/home/bank-balance`**

- **은행 계좌는 `/bank-accounts`(svc:14073, 은행계좌 원장)이다.** `/accounts`(obys_finance.py:1088)는 배달 플랫폼 계정(`platform_accounts`)이므로 은행 계좌 수·잔액에 쓰지 않는다.
- 잔액 출처(코드 확인): 은행계좌 레코드의 공개 필드(`_BANK_ACCOUNT_PUBLIC_FIELDS`, svc:13780~13803)에 **잔액 필드가 없다.** 잔액은 거래 레코드의 `balance`(거래 직후 잔액, 값이 없으면 `None`; `_normalize_bank_transaction` svc:14479~14492)에만 있다. 따라서 기간 제한(최근 31일)을 두지 않고 **계좌별로 거래 이력 전체에서 `balance` 가 있는 마지막 거래**를 잔액 스냅샷으로 쓴다.
- 응답: `{"business_id": "...", "accounts": [{"account_id": "...", "account_alias": "...", "bank_name": "...", "balance": 1250000, "as_of": "2026-11-06T18:20:00+09:00", "stale": false}], "total": 3400000, "unknown_accounts": 1, "stale_accounts": 1, "today": {"date": "2026-11-07", "total_in": 540000, "total_out": 210000, "transaction_count": 12}, "errors": []}`
- 규칙:
  1. 대상 계좌 = `business_id` 가 같은 은행계좌 원장 행. 계좌 `status` 별 제외 여부는 **미확인**(상태 값 집합 확인 전까지 전부 포함하고 응답에 `status` 를 싣는다).
  2. 계좌의 스냅샷 = `bank_account_id` 가 같고 `balance` 가 `None` 이 아닌 거래 중 `occurred_at` 이 가장 늦은 것(동률이면 `posted_at`, 그다음 원장 파일의 나중 행). 비교는 KST 로 정규화한 시각으로 한다(아래 5번 규칙 — 원본 문자열 사전순 비교 금지).
  3. `as_of` = 그 거래의 `occurred_at`(KST). `stale` = 스냅샷 거래보다 **늦은** 거래가 있는데 그 거래에 `balance` 가 없으면 `true`(잔액이 현재보다 오래됐을 수 있음).
  4. `balance` 가 있는 거래가 한 건도 없는 계좌는 `accounts` 에 `balance: null` 로 두고 `total` 에서 빼며 `unknown_accounts` 에 센다. **합계를 순입출금으로 대신 채우지 않는다.**
  5. `total` = `balance` 가 있는 계좌의 합(stale 계좌 포함). 화면은 합계 옆에 "기준시각 다른 계좌 N"(= `stale_accounts`)과 "잔액 확인 불가 N계좌"(= `unknown_accounts`)를 함께 보인다. '전체' 합산 시 두 값도 사업자별로 더한다.
- **오늘 입금·출금도 이 API 가 서버에서 계산한다(`today`).** 기존 `/bank-summary` 는 쓰지 않는다: 날짜 필터 `_bank_within_range`→`_bank_date_key`(svc:13897~13903)가 시간대 있는 UTC 문자열을 KST 로 바꾸지 않고 앞 10자만 자르므로, 서버 집계에서 이미 빠진 거래는 프론트 변환으로 복구할 수 없다. 기존 경로를 고치면 "기존 응답 불변"(§9)에 어긋나므로 신규 계약에서 처리한다.
  - `today.date` = KST 오늘. 대상 거래 = 대상 계좌의 거래 중 `occurred_at` 을 규칙 5 로 KST 정규화한 날짜가 `today.date` 와 같은 것. `total_in`/`total_out` = `direction` 이 `in`/`out` 인 거래의 `amount` 합(`bank_summary` svc:15920~15921 과 같은 금액·방향 규칙), `transaction_count` = 대상 거래 수.
  - 정규화 실패 행은 합계에서 빼고 `errors` 에 건수를 남긴다(0 으로 가정하지 않음). `/bank-summary` 는 홈 카드에서 호출하지 않는다.

**공통 규칙(기존 경로 계산용)**

4. **KST 날짜 — 날짜 전용 값과 시각을 구분한다.**
   - **날짜 전용 값**(`YYYY-MM-DD` 형식 전체가 일치): 시간대가 없으므로 그대로 달력일로 쓴다. 해당 필드: `occurred_on`·`sales_date`·`settlement_date`·`order_date`·`date`, `pay_date`.
   - **시간대가 있는 시각**(`2026-11-06T15:30:00Z`, `+09:00` 등)과 **시간대 없는 시각**(`2026-11-07 00:30:00`): 먼저 `Asia/Seoul` 로 바꾼 뒤 날짜를 자른다. 예) `2026-11-06T15:30:00Z` → `2026-11-07`, `2026-11-06T15:30:00+09:00` → `2026-11-06`. 시간대 없는 시각은 KST 로 간주한다(은행 거래의 `occurred_at` 정규화가 `YYYY-MM-DD HH:MM:SS` 시간대 없는 형식만 인식하기 때문 — svc:12112 `_transaction_date`). 그 밖의 형식은 `_transaction_date` 가 원문을 그대로 돌려주고 `_bank_date_key`(svc:13897)가 앞 10자만 자르므로, **시간대 있는 UTC 문자열이 저장돼 있으면 날짜가 하루 어긋난다.** 저장 행에 그런 값이 실제로 있는지는 **미확인**이다. 이 서버 한계는 프론트에서 고칠 수 없으므로 홈은 `/bank-summary` 를 쓰지 않고, 신규 `bank-balance`(B-3)가 규칙 5 의 KST 정규화로 오늘 입출금을 직접 집계한다.
   - 현행 프론트 `deliveryRecordDate`(index.html:7463~7475)는 `finished_at → collected_at → updated_at → created_at` 같은 시각 필드도 `slice(0, 10)` 으로 자른다. UTC 시각이면 KST 자정 전후 9시간이 전날/다음 날로 잘못 분류되므로, 시각 필드에는 위 변환을 먼저 적용하도록 L3 에서 고친다.
   - 경계: 오늘 = `kstDate(0)`(index.html:12623, `Intl` `Asia/Seoul`), 어제 `kstDate(-1)`, 전주 같은 요일 `kstDate(-7)`, 최근 7일 = `kstDate(-6)` 이상 `kstDate(0)` 이하(오늘 포함). 비교는 변환을 거친 `YYYY-MM-DD` 문자열 사전순이다.
5. **은행 거래 시각 비교**: 정규화된 `YYYY-MM-DD HH:MM:SS`(KST)로 변환한 값끼리 비교한다. 변환 실패 행은 스냅샷 후보에서 빼고 `errors` 에 건수를 남긴다.
6. **행의 날짜 필드 선택**: `occurred_on` → `sales_date` → `settlement_date` → `order_date` → `date` → `finished_at` → `collected_at` → `updated_at` → `created_at` 중 처음으로 값이 있는 것(index.html:7463). 뒤쪽 세 개(수집·갱신·생성 시각)는 업무일이 아니므로 그 행 수를 툴팁에 "업무일 없는 행 N건(수집일 기준)" 으로 남긴다.
7. **행의 금액 필드 선택**: 숫자 외 문자(`,`·"원")를 제거해 파싱하고 순서대로 보아 0 이 아닌 첫 값. 매출 `gross_amount → order_amount → sales_amount → amount → net_amount`, 정산 `settlement_amount → settlementAmount → net_amount → amount → gross_amount`. 전부 0 이거나 없으면 0.
8. **중복 식별**: 원장 행은 `id` 로 식별하고 같은 `id` 가 둘 이상이면 마지막 한 행만 쓴다. `id` 없는 행은 모두 합산한다.

#### D. 호출 구성과 L3 정적 검사

홈이 부르는 경로는 기존 **8개**(`/sales`, `/settlements`, `/payroll`, `/reviews`(보조 지표), `/collection-status`, 사업자 목록 `/tenant-registry/businesses`, 처리할 일 보강용 `/employees/join-requests`, `/onboarding/documents`)와 신규 **3개**(`review-pending-count`, `approval-pending`, `bank-balance`; 사업자 수만큼 반복)이다. `/contracts/pending-signature`(관리자에게 항상 빈 목록)와 `/bank-summary`(날짜 필터 한계, B-3)는 홈에서 쓰지 않는다. 사업자 4개 기준 최대 요청 수 = 8 + 3×4 = **20개**(사업자 목록·'전체' 선택 시; 개별 사업자 선택 시 8 + 3 = 11개). 카드별 부분 실패는 `Promise.allSettled` 로 격리한다. L3 정적 테스트는 위 경로의 존재와 A형(서버 `business_id` 필터)/B형(없음) 구분이 라우터와 일치하는지 검사하고, 신규 3종의 계약 테스트는 §10 L 단계에서 한다.

#### E. 다른 절과의 관계 (§3-1·§9·§12 는 직전 판본 문구 그대로 둔다)

- **§3-1(나) '서버 집계 API(2차 후보)·서버 변경 없음' 과 '요청 11개'**: 홈 전체를 서버 1호출로 합치는 `/home-summary` 는 여전히 2차 후보이고 §3-1 의 전환 임계값이 그 기준이다. 이와 별개로 **기존 API 로 정확히 안 되는 3개 지표만** 이 절의 신규 3종으로 L6 에서 낸다. 따라서 호출 수는 §3-1 의 11개가 아니라 위 D 의 값(최대 20개)이 유효하다. 충돌 시 §5-1 이 우선한다.
- **§9 '비범위: API 경로, 백엔드 라우터' 와 '범위: 기존 API 병렬 호출 집계'**: L2~L4(정적 `index.html`)에 적용되는 문구다. L6 은 신규 읽기 전용 라우트 3개 추가만 허용하는 별도 범위이며 기존 경로·응답·스키마는 바꾸지 않는다(§10 L6 ⑧ 회귀 테스트).
- **§12 '정적 파일 한 개 복원'**: L2~L4 롤백에 적용된다. L6 롤백은 신규 라우트 revert 이며 §10 L5 와 §11 에 따른다(L3 이후 프론트는 신규 API 실패·미배포 시 '집계 준비 중' 으로 동작하므로 서버 revert 가 프론트를 깨지 않는다).

## 12. 롤백 계획

대상이 단일 정적 파일(`app/static/apps/obys/index.html`)이고 백엔드·DB·API 경로를 바꾸지 않으므로(§9), 되돌리기는 **파일 한 개를 직전 정상 판본으로 되돌리는 것**으로 끝난다. DB 마이그레이션이 없어 데이터 복구는 필요 없다.

| 항목 | 내용 |
|---|---|
| 기준점 | 각 단계(L2·L3·L4) 배포 직전에 현재 서비스 중인 커밋 SHA 를 L5 결과에 기록한다. 개편 착수 전 기준은 origin/main 80a1fd72 의 index.html. |
| 단위·의존성 | L2(CSS·상태 함수)→L3(홈·메뉴)→L4(빈 상태·모바일)는 직렬 의존이다. L3·L4 화면이 L2 가 만든 `.kpi-card/.state/.filter-bar` CSS 와 `renderState()` 를 호출하므로, **커밋을 나눈다고 단계별 독립 revert 가 보장되지 않는다.** 규칙: ① 되돌리기는 마지막 배포 단계부터 역순(L4→L3→L2)으로만 한다. ② 중간 단계(L2 또는 L3)만 단독 revert 하지 않는다 — 후속 단계가 쓰는 CSS·함수가 사라져 추가 회귀가 난다. ③ L4 만 문제면 L4 만, L3 문제면 L4+L3 를 함께 되돌린다. ④ 단독 revert 가 꼭 필요하면 revert 후 후속 단계가 참조하는 클래스·함수가 남아 있는지 정적 테스트(없는 `renderState` 호출·미정의 클래스 검사)로 확인하고 통과해야 내보낸다. 통과 못 하면 ⑤ 로 간다. ⑤ 최후 수단은 기준점 SHA 의 `index.html` 전체 복원(개편 전 판본)이다. |
| 회귀 판정 기준 | 아래 중 하나라도 해당하면 롤백 후보: (a) 로그인 후 홈이 5초 안에 렌더되지 않음 (b) 기존 `data-view` 화면 중 하나라도 열리지 않음 (c) 승인·급여·검토 등 쓰기 동작 실패 (d) 모바일 390×844 에서 하단 탭이 보이지 않음 (e) 콘솔 오류로 빈 화면 |
| 배포 후 점검 | 배포 후 5분 모니터링(PC·모바일 캡처 각 1장, 주요 API 200 확인). 이상 시 즉시 판정 기준에 따라 롤백 후보로 CTO 에게 보고. |
| 롤백 실행 | revert 커밋을 일반 릴리스 절차(PUSH_ONLY → 승인 → Runner 배포)로 내보낸다. 서버 재시작 불필요(정적 파일). 반영 확인은 fb.newtalk.kr 서빙 SHA 일치로 한다. |
| 사용자 영향 | 정적 파일 교체이므로 롤백 중 API 중단 없음. 브라우저 캐시 때문에 새로고침 1회가 필요할 수 있음을 공지한다. |
| 보존 | `localStorage` 에 저장하는 마지막 묶음·필터 키는 신규 접두어(`obys.ui2.`)를 쓴다. 롤백 후 구판이 이 키를 읽지 않아 오작동하지 않는다. |
