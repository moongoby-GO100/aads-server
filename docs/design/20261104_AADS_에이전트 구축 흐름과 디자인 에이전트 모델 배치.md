## 3. 한 건이 처리되는 흐름 (런타임)

```
이벤트 발생(project_created / deploy_succeeded / manual / screen_change_requested / new_screen_requested)
 → design_agent_triggers 에 적재
 → process_one(): 꺼져 있으면 blocked_disabled 로 즉시 종료
 → tenant 단위 advisory lock (같은 tenant 동시 처리 금지)
 → claim_next: 대기 1건 꺼내기
 → check_run: 같은 입력 hash 성공 이력 → skipped_duplicate / 하루 비용 상한 초과 → blocked_budget
 → design_agent_runs 기록 생성
 → 상황(S1~S9) 판별 → 필수 스킬 로드 (실패 시 failed)
 → 처리기 실행 (내부 트랜잭션, 실패 시 쓰기 롤백·감사 기록은 보존)
    · 모델 호출 1회마다 RunBudget.record_call → 15회 초과 시 BudgetExceeded
    · 쓰기는 DesignAgentWriter 경유: 3개 테이블 INSERT·draft 만 허용
 → 상태(succeeded/failed/blocked_budget) + 호출 수·비용 기록
```
[코드 runner.py, budget.py, writer.py]

쓰기 허용 테이블: `design_token_sets`, `design_audit_runs`, `design_modification_requests` — 모두 `status=draft` 고정, 다른 tenant·다른 프로젝트·다른 화면은 거절 [코드 writer.py].

## 4. 모델 배치 — A안 확정 [결정]

원칙 세 가지.
1. **만든 회사와 비평하는 회사를 다르게 한다.** 생성이 폴백으로 다른 회사로 넘어가면 비평도 따라서 바꾼다(같은 회사 금지).
2. **이미지(화면 캡처)를 봐야 하는 업무에는 이미지 입력 지원 모델만 쓴다.** 지원 여부는 하드코딩하지 않고 `llm_models.supports_vision`으로 판정한다. 현재 Gemini 계열 다수가 `false`로 등록돼 있다 [DB].
3. **계산으로 판정할 수 있는 것은 모델을 쓰지 않는다.** 대비·터치 영역은 코드 계산(모델 호출 0회).

| 업무 | 1순위 | 2순위 | 3순위 | 비고 |
|---|---|---|---|---|
| 요구 인터뷰·브리프 정리(텍스트) | Claude Sonnet 5.5 | Codex GPT-6.1 Sol | Gemini 3.1 Pro | 텍스트 전용 |
| 토큰·시안 생성(D2) | Claude Sonnet 5.5 | Codex GPT-6.1 Sol | Gemini 3.1 Pro(텍스트 입력일 때만) | 신규 프로젝트·전면 개편은 1순위를 Opus 5.5로 상향 |
| 정성 비평·감사(D3) | Codex GPT-6.1 Sol | Claude Opus 5.5 | Gemini 3.1 Pro(텍스트 입력일 때만) | 생성 회사와 같으면 그 순위 건너뜀 |
| 대비·터치 감사 | 코드 계산 | — | — | 모델 0회 |
| 수정 요청서 정리(저비용) | Codex GPT-6 Luna | Claude Haiku 4.5 | Gemini 3 Flash | 텍스트 전용 |

단가(100만 토큰 입력/출력) [DB llm_models]: Sonnet 5.5 $2/$10, Opus 5.5 $4/$20(직전 보고 기준), Gemini 3.1 Pro $2/$12, Gemini 3 Flash $0.5/$3. Codex 계열 단가는 이번 조회에서 일부 미등록 → [미측정].

공통 상한: 실행 1건당 모델 호출 15회, tenant 하루 $2.0 (기존 `config.py` 기본값 유지).

구현 방식: 모델 id·순서는 코드에 박지 않고 설정(환경변수 또는 DB)에서 읽는다. 호출은 중앙 경로(`app/core/anthropic_client.call_llm_with_fallback` 등 기존 라우터)를 재사용하며 디자인 에이전트 전용 클라이언트를 새로 만들지 않는다(R-AUTH).

알려진 한계: 중앙 함수가 내부에서 다른 회사로 폴백하면 "실제 응답한 회사"를 알 수 없을 수 있다. 이 경우 실행 기록에 `actual_provider=unverified`로 남기고, 비평 독립성은 요청 기준으로만 보장된다고 표시한다.

## 6. 추가 에이전트가 필요한가

결론: **새 전용 에이전트는 지금 추가하지 않는다.** 막힌 원인은 모두 "에이전트 부족"이 아니라 실행 환경·권한 분리·승인 대기다.

| 후보 | 필요성 | 판정 | 대신 할 것 |
|---|---|---|---|
| 러너 사전조회 대행 | 6건 실패의 직접 원인 | 에이전트 불필요 | 제출 시 사전조회 스냅샷을 지시서에 넣는 절차(코드화 후보) |
| 독립 검수자 | D0·D1 확정 불가 | 역할 지정으로 충분 | 기존 `E2E 검증 시스템관리자` 또는 PM 세션을 판정자로 지정 |
| 디자인 비평자 | 생성·비평 분리 | 별도 에이전트 불필요 | 디자인 에이전트 안에서 **다른 회사 모델**로 호출(4절) |
| 화면 시각 감사 | D3 캡처 기반 감사 | 기존 도구로 충분 | `visual_qa_test`·`capture_screenshot` 결과를 D3 입력으로 사용 |
| 디자인→화면 구현 | 승인본 구현 | 기존 러너가 담당 | D4 인계 어댑터로 러너에 승인 hash 주입 |

재검토 조건: 파일럿 후 프로젝트 3개 이상에서 동시에 디자인 요청이 쌓이거나, 감사가 배포마다 자동으로 돌아야 할 때 "배포 후 감사 전용 에이전트" 분리를 다시 판단한다.
