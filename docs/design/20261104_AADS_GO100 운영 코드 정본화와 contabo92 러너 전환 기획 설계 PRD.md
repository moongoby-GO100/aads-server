## 1. 배경

대표님 지시로 contabo92 를 GO100 러너로 전환하려 했다. 92 쪽 사전 준비(인증·DB 터널·GitHub 권한·원격 배포 판 설치·검증 4종)는 2026-11-04 에 끝났다. 그런데 전환하면 92 가 처리한 GO100 작업의 **백엔드 재기동이 전부 안전장치에 막힌다**(이전 설계 §2.2.2 `remote_sha_not_applied`). 원인은 contabo14 의 GO100 운영 코드가 저장소 정본(origin/main)과 갈라져 있기 때문이다.

### 2.1 문제

1. **운영 전용 커밋 25개가 유실 위험에 있다.** GitHub·다른 서버에 사본이 없다.
2. **GO100 백엔드 배포가 운영에 반영되지 않는다.** 러너(로컬 모드)는 격리 작업 폴더에서 origin 으로 push 한 뒤 `systemctl restart go100` 을 한다. 운영 작업 폴더는 그 push 를 받지 않으므로 재시작하면 옛 코드가 다시 뜬다. 511개 커밋이 쌓인 것이 그 결과다. 이전 설계 §2.1 이 같은 공백을 지적했다.
3. **92 전환이 불가능하다.** 92 의 원격 배포 판은 "운영 HEAD 에 승인 SHA 가 포함됐는지"를 확인하고 아니면 재기동을 거부한다(fail-closed). 위 2번 때문에 항상 거부된다.

## 4. 범위

- 포함: 보존, 통합, 분리 검증, 운영 실행 경로를 고정 릴리스 폴더로 전환, 러너의 GO100 백엔드 배포 경로 정비, 92 전환.

## 5. 설계

### 5.1 1단계 — 보존 (운영 영향 없음)

1. contabo14 에서 운영 전용 커밋을 GitHub 브랜치로 올린다: `git push origin 20d69e3eb:refs/heads/live/contabo14-20261104`.
2. 미커밋 코드 5개는 운영 폴더를 건드리지 않고 별도 작업 폴더에서 같은 브랜치 위 커밋 `live snapshot: uncommitted hotfixes 2026-11-04` 으로 올린다(내용은 운영 파일을 그대로 복사).
3. 백업: `git bundle create` 로 위 브랜치 묶음 + 미커밋 diff 를 카페24 서브디스크 `_go100-archive/live-snapshots/20261104/` 에 보관하고 원격 sha256 을 대조한다.
4. 검증: GitHub 브랜치 HEAD 의 트리 = 운영 HEAD 트리 + 5개 파일(`git diff` 0).

### 5.2 2단계 — 통합 (운영 영향 없음, 러너 작업 + 검수)

1. 통합 후보 브랜치 `integrate/go100-live-20261104` = origin/main 에 `live/contabo14-20261104` 를 병합한다.
2. 충돌은 파일 단위로 판단해 해결하고 근거를 커밋 메시지에 남긴다. 기본 원칙은 다음과 같다.
   - **운영 전용 수정이 origin 의 같은 기능을 이미 대체했으면 origin 판**을 택한다.
   - 그렇지 않으면 운영 판을 살린다.
   - 판단이 어려운 파일은 목록으로 남겨 검수자에게 넘긴다.
3. GO100 단위 테스트·정적 검사를 통과해야 한다.
4. 산출물: 통합 SHA, 충돌 해결 목록, 운영 대비 변경 요약(라우터·서비스·스케줄러별).

### 5.3 3단계 — 분리 검증 (운영 영향 없음)

1. contabo92 에 통합 SHA 로 고정 릴리스 폴더를 만들고 별도 포트(예: 18002)로 기동한다.
2. DB 는 **읽기 전용 계정 또는 검증용 사본**만 쓴다. 실거래 주문 경로는 모의(paper) 설정으로 막는다. 주문 API 키를 넣지 않는다.
3. 확인 항목: `/health`, 주요 조회 API 응답 형식(운영 응답과 키 비교), 스케줄러 기동 로그, 수집기 1회 실행, 프론트에서 API 호출 스모크.
4. 기준: 오류 0, 운영 대비 응답 키 누락 0. 차이는 목록화해 승인받는다.

### 5.4 4단계 — 운영 실행 경로 전환 (운영 영향 있음, 장외 시간)

1. 고정 릴리스 폴더 `/opt/go100/releases/<통합SHA>` 를 clean worktree 로 만든다.
   - `.env`·venv 는 기존 것을 링크하거나 복사한다. 의존성이 바뀌었으면 새 venv 를 쓴다.
   - `var/` 등 실행 산출물 경로는 기존 위치를 그대로 쓰게 링크한다.
2. `go100.service` 의 drop-in 으로 `WorkingDirectory`·`ExecStart` 를 릴리스 폴더로 바꾼다. 기존 유닛 파일은 수정하지 않는다.
3. 전환: 장외 시간(주말 권장)에 `daemon-reload` → `restart go100` 한 번 → 헬스 180초 → 5분 감시.
4. 되돌리기: drop-in 삭제 → `daemon-reload` → `restart` 하면 기존 작업 폴더로 복귀한다. 기존 폴더는 손대지 않는다.
5. 러너 배포 경로 정비(코드): GO100 백엔드 배포 시 "push → 새 릴리스 폴더 생성 → 심볼릭 `current` 교체 → 재기동 → 헬스 → 실패 시 이전 `current` 로 복귀"로 바꾼다. 프론트에 이미 있는 릴리스 워크트리 방식과 같은 형태다. 92 원격 배포 판의 SHA 검증은 `current` 가 가리키는 릴리스 SHA 와 비교하도록 맞춘다.

### 5.5 5단계 — contabo92 GO100 러너 전환

이전 설계 §6 3~5단계를 그대로 따른다.

1. 장 마감 후 contabo14 GO100 신규 수신을 중지한다.
2. contabo14 의 GO100 실행 작업이 0건인지 확인한다.
3. 92 를 대기 필터로 기동해 등록을 확인한다.
4. 92 를 GO100 필터로 전환한다.
5. 첫 작업에서 원격 재기동과 SHA 반영을 확인한다.

## 9. 용어

- **정본**: 저장소의 기준 코드(origin/main). 운영이 이것과 같아야 배포 결과를 믿을 수 있다.
- **고정 릴리스 폴더**: 특정 커밋으로 만든, 수정하지 않는 실행용 폴더. AADS·GO100 프론트가 이미 이 방식을 쓴다.
- **분리 검증**: 운영과 다른 서버·포트·DB 권한으로 새 코드를 띄워 확인하는 것.
- **fail-closed**: 확인할 수 없으면 진행하지 않는 안전 원칙.
