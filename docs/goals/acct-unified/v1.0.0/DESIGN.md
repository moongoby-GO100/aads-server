## 1. 설계 원칙

1. `tenant`는 계약/조직 경계, `company`는 사업자등록번호와 장부 경계다.
2. 조회는 허용 범위 내 통합이 가능하지만 쓰기는 하나의 명시적 `company_id`에서만 허용한다.
3. 업로드 파일은 근거이고 원장 행은 업무 정본이다. 파일 목록만으로 상세 화면을 대신하지 않는다.
4. 확정 데이터는 덮어쓰지 않고 정정 버전과 감사이력을 만든다.
5. 화면의 상태, API 상태, DB 상태 이름을 하나의 상태 머신으로 맞춘다.

## 2. 논리 아키텍처

```text
사용자 브라우저
  ├─ 통합 홈 / 사업자 스위처
  ├─ 4종 재무원장 UI
  └─ 직원계약 / 근태 / 급여 UI
        │ JWT tenant_id + 명시적 company_id
        ▼
AADS FastAPI
  ├─ 인증·멤버십·사업자 권한 게이트
  ├─ 오비서 업무 API
  ├─ 업로드/파서/중복검사
  └─ ACCT 전표 어댑터
        │ 트랜잭션 + 멱등키 + 감사 이벤트
        ▼
obys DB (업무 정본) ── 검증된 확정 이벤트 ──> ACCT DB (회계 정본)
```

## 3. 프런트엔드 화면 계약

### 3.1 공통 셸

- 상단: 현재 사업자, 기간, 동기화 상태, 전체 검색, 사용자 메뉴.
- 좌측/하단 내비게이션: 홈, 매출, 매입, 은행, 카드, 직원계약, 근태, 급여.
- 업무 헤더: 건수·합계·미처리·마지막 동기화, `등록` 기본 행동.
- 목록: 서버 페이지네이션, URL에 필터 보존, 행 클릭으로 상세 패널.
- 상세 패널: 요약→원본/증빙→연결→변경이력 순서.
- 등록 패널: 필수값→증빙→분류/연결→검토→저장 순서.

### 3.2 첫 실행·반복 사용·복구

| 상황 | 화면 동작 |
|---|---|
| 첫 로그인 | 접근 가능한 사업자가 1개면 바로 홈, 여러 개면 최근 사업자를 기본 선택 |
| 반복 사용 | 마지막 사업자·메뉴·필터를 복구하되 서버 권한을 다시 검증 |
| 세션 만료 | 입력 초안을 로컬에 암호화하지 않고 비민감 필드만 임시저장, 재로그인 후 복구 확인 |
| 권한 부족 | 403 설명, 현재 사업자, 요청 가능한 관리자와 돌아가기 제공 |
| 네트워크 실패 | 마지막 성공 시각, 재시도, 오프라인 임시저장 가능 여부 표시 |
| 중복 업로드 | 중복 근거와 기존 건 링크를 보여주고 무시/검토를 선택 |

## 4. API 표면

현재 구현이 확인된 경로와 목표 계약을 구분한다.

| 영역 | 현재 확인된 경로 | 목표 보강 |
|---|---|---|
| 매출 | `GET /sales`, `POST /uploads`, `GET /uploaded-ledger` | `GET/POST /sales/{id}` 계열 상세·수정·정정 |
| 매입 | `acct_purchase` 조회 API, 업로드 원장 | 오비서 사업자 스코프 매입 CRUD와 입고/분개 링크 |
| 은행 | `/bank-accounts`, `/bank-transactions`, import/upload/collect | 건별 상세·수정/정정, 대사 결과와 원본 연결 |
| 카드 | ACCT 카드 조회 API | 오비서 전용 카드 사용 원장, 상세·등록·업로드·취소 |
| 직원 | invites, join-requests, approved, onboarding documents | 계약 버전·검토·서명·보관 상태 완결 |
| 급여 | `GET/POST /payroll` | O12 마감버전 기반 산정·승인·명세서·지급·분개 |

모든 목록 API는 `business_id`, 기간, 상태, 검색어, cursor/limit를 받아야 한다. 모든 쓰기 API는 서버가 토큰의 멤버십과 `business_id/company_id`를 교차검증하고, 클라이언트가 보낸 `tenant_id`는 신뢰하지 않는다.

## 5. 데이터·상태 설계

### 5.1 공통 원장 필드

```text
id, tenant_id, company_id, occurred_at, amount, currency,
counterparty, description, status, source_type, source_id,
source_hash, evidence_ids[], accounting_link_id,
created_by, created_at, updated_at, version
```

원장별 확장 필드:

- 매출: 채널, 주문/정산 ID, 공급가·세액·수수료·취소액.
- 매입: 공급처, 계정과목, 공급가·세액, 입고/재고 링크.
- 은행: 계좌 ID, 입출금 구분, 거래 후 잔액, 원문 적요, 상대 계좌.
- 카드: 카드 ID(마스킹), 사용자/부서, 승인번호, 할부, 취소 원거래.

### 5.2 공통 상태

`draft → imported|submitted → needs_review → confirmed → posted`

- `rejected`: 반려 사유와 재제출 링크 필수.
- `cancelled`: 원거래 보존, 취소 거래 연결.
- `corrected`: 확정본을 수정하지 않고 새 버전과 이전 버전 링크 생성.
- `sync_failed`: 실패 코드, 마지막 시도, 재시도 가능 여부 보존.

## 6. 권한과 보안

| 역할 | 조회 | 등록/수정 | 확정/마감 | 민감정보 |
|---|---|---|---|---|
| owner | tenant 전체/허용 회사 | 가능 | 가능 | 정책 범위 내 원문 |
| manager | 지정 회사/지점 | 운영자료 가능 | 제한 | 계좌·급여 마스킹 |
| finance | 지정 회사 재무 전반 | 가능 | 승인 정책에 따름 | 업무상 필요한 범위 |
| employee | 본인 계약·근태·급여 | 본인 신청/서류 | 불가 | 본인 정보만 |
| accountant | 지정 회사 회계 | 정정 제안 | 마감 권한 시 가능 | 카드/계좌 마스킹 |

- IDOR 방지: 모든 단건 조회도 목록과 동일한 tenant/company 조건을 적용한다.
- 파일: 다운로드 직전 권한 재검증, 추측 불가능 ID, Content-Disposition, MIME/용량 검사.
- 민감값: 카드·계좌·주민/세무 식별값은 저장·로그·목록에서 마스킹한다.
- 감사: 조회가 아니라 중요 다운로드와 모든 쓰기/승인/마감에 행위자·시각·이전/이후 버전을 남긴다.

## 7. ACCT 연계

오비서에서 `confirmed`된 업무 거래만 분개 후보가 된다. ACCT 전표 생성은 `source_system + source_id + source_version` 멱등키를 사용하고, 차변합과 대변합이 맞지 않거나 마감기간이면 전체 트랜잭션을 실패시킨다. 실패 상태는 오비서 원장에 기록하되 업무 원본을 삭제하지 않는다.

## 8. 모바일·접근성

- 390px 기준 가로 스크롤 없이 핵심 업무를 완료한다.
- 터치 대상 최소 44px, 포커스 링과 키보드 닫기/이동을 제공한다.
- 표는 모바일에서 카드형 핵심 필드로 바꾸고 전체 필드는 상세 패널에 둔다.
- 금액은 숫자만으로 상태를 표현하지 않고 부호·색·텍스트를 함께 쓴다.
- 등록 중 앱 재실행 시 비민감 초안을 복구하고 민감 파일은 재선택을 안내한다.

## 10. 롤백

- 문서/목업: 이전 Git tag로 경로를 되돌린다.
- UI: 기능 플래그로 신규 상세·등록 메뉴를 숨기고 기존 읽기 화면을 유지한다.
- API: additive endpoint를 비활성화하되 기존 원장 데이터를 삭제하지 않는다.
- DB: additive schema는 보존하고 쓰기를 중지한다. 데이터 삭제·광범위 DELETE는 롤백 수단으로 사용하지 않는다.
