## 0. 결론 먼저

**만들 수 있습니다.** 단, "회사 자료를 넣으면 ERP가 튀어나오는 시스템"이 아니라
**"회사의 일하는 방식을 데이터로 원자화하고, 그 위에서 자동화를 조립해 주는 시스템"** 으로 만들어야 성립합니다.

| 구간 | 실현 가능성 | 근거 |
|---|---|---|
| 자료(엑셀/문서/이미지/영상) 원자화·1차 저장 | ✅ 높음 | NTV2에서 엑셀 전 계층 원자화 실증 완료 [2026-09-13] |
| 자료로부터 항목·규칙·절차 후보 추출 | ✅ 높음 | LLM+OCR+ASR 조합으로 "제안" 생성은 검증된 기술 |
| 추출 결과를 실무자가 쉽게 확정(동기화) | ⚠️ 설계 난이도 높음 | 여기서 제품 성패가 갈림 — 4장 참조 |
| 확정된 모델로 실제 동작 업무 시스템 생성 | ⚠️ 조건부 | **템플릿+설정 조립** 방식이면 가능. 임의 코드 자동생성은 비권장 |
| SAP급 전사 ERP를 무인 생성 | ❌ 불가 | 회계·세무·원가 규정은 자동 추론 대상이 아님 |

핵심 판단: **"자동 생성"이 아니라 "자동 조립"** 으로 간다. 미리 만들어 둔 검증된 업무 모듈(주문/발주/재고/입출고/정산/승인)을 회사 데이터 모델에 맞게 설정·연결하는 방식이면 품질과 속도를 동시에 얻는다.

## 1. 문제 정의

작은 회사는 다음 상태다.
- 업무가 엑셀·카톡·수기 장부·담당자 머릿속에 흩어져 있다.
- 무엇을 자동화해야 하는지 스스로 정의하지 못한다.
- ERP 도입 실패의 주원인은 기술이 아니라 **현행 업무를 문서화하지 못하는 것**이다.
- 컨설팅 비용(현행 분석)이 개발 비용보다 크다.

AAP는 이 **현행 분석 단계를 자동화**하는 제품이다.

## 2. 제품 구조 — 4계층

```
L1 수집(Capture)      엑셀·한글·PDF·이미지·사진·화면녹화·설명영상·기존DB덤프
        ↓
L2 원자화(Atomize)    모든 입력을 되돌릴 수 있는 최소 단위로 1차 저장 (해석 이전)
        ↓
L3 지식화(Understand) 항목·엔티티·규칙·절차·역할·예외를 후보로 추출 → 실무자 확정
        ↓
L4 조립(Assemble)     확정 모델 → 업무 모듈 설정·화면·워크플로·권한 자동 구성 → 시범운영
```

**L2와 L3의 분리가 이 제품의 핵심**이다. 해석이 틀려도 원본은 손실되지 않으므로, 해석만 다시 하면 된다.
NTV2에서 이 분리 구조가 이미 검증되었다(원자화 계층은 양식 무관 동작, 해석 계층만 양식 종속). [2026-09-13 실측]

## 3. L1/L2 — 무엇을 어떻게 원자화하는가

| 입력 | 원자 단위 | 추출 수단 |
|---|---|---|
| 엑셀/CSV | 파일→시트→행→셀(좌표·원문·수식·캐시값·타입·SHA-256) | PhpSpreadsheet/openpyxl (구현 실증됨) |
| 한글/워드/PDF | 문서→섹션→문단→표→셀 | 텍스트 추출 + 표 구조 인식 |
| 스캔·사진 서류 | 페이지→영역(bbox)→텍스트/표 | OCR (`local_ocr` 보유) |
| 업무 설명 영상 | 구간→발화(타임스탬프)→화면 상태→조작 이벤트 | ASR + 키프레임 + 화면 텍스트 OCR |
| 화면 녹화(실제 작업) | 클릭/입력/화면전환 시퀀스 | 프레임 diff + UI 텍스트 추출 |
| 기존 DB/솔루션 덤프 | 테이블→컬럼→샘플값 프로파일 | 스키마 리버스 + 값 분포 분석 |
| 카톡/메일 업무 대화 | 스레드→메시지→첨부 | 파서 + 첨부 재귀 원자화 |

원자화 결과는 **모두 동일한 저장 규약**을 쓴다.
`source_asset → asset_segment → atom(좌표/시각/영역, 원문, 타입, 해시) → evidence_link`

공통 규칙
- 원본은 절대 수정하지 않는다(WORM). 해석은 항상 별도 테이블.
- 모든 해석값은 원자 ID로 역추적된다(감사 추적).
- 개인정보 필드는 원자화 시점에 태깅하고, 외부 LLM 전송 시 값 제외.

## 4. L3 — 실무자 동기화를 "최대한 쉽게" 만드는 방법

CEO 지적대로 **최초 동기화는 실무자가 해야 한다.** 제품의 승부처는 그 부담을 얼마나 줄이느냐다.

| 부담 요소 | 기존 방식 | AAP 방식 |
|---|---|---|
| 무엇을 알려줘야 하는지 모름 | 컨설턴트 인터뷰 | 시스템이 **질문 목록을 생성**해 순서대로 제시 |
| 빈 양식 작성 | 현행 분석 문서 직접 작성 | **초안이 채워진 상태**에서 승인/수정만 |
| 용어 정리 | 회의로 합의 | 자료에서 쓰인 실제 단어를 후보로 제시(`품명/상품명/제품명`) |
| 정답 확인 불가 | 나중에 발견 | **과거 실제 데이터로 즉시 재현 시뮬레이션** |
| 한 번에 다 해야 함 | 빅뱅 | 업무 하나(예: 발주)만 먼저 자동화, 나머지는 그대로 |

### 4단계 온보딩 (목표: 담당자 총 3시간 이내)
1. **자료 던지기** — 폴더째 업로드. 분류·정리 요구하지 않는다. 시스템이 분류한다.
2. **10개 질문** — "이 표에서 한 줄은 무엇인가요?(주문 1건/상품 1개)" 처럼 **객관식 위주**.
3. **좌우 대조 확인** — 왼쪽 원본, 오른쪽 해석. 틀린 것만 고친다. 고친 내용은 학습된다.
4. **과거 데이터 재현** — 지난달 실제 파일을 새 시스템에 넣어 결과가 장부와 맞는지 자동 대사. **여기서 숫자가 맞으면 실무자가 신뢰한다.**

### 동기화 자동화 장치
- **지문 학습**: 같은 양식 재등장 시 질문 없음
- **별칭 학습**: 한 번 확정한 상품·거래처·계정 매핑은 영구 재사용
- **모순 감지**: 담당자 답변이 데이터와 충돌하면 즉시 되물음("합계가 3건 안 맞습니다")
- **미결 큐**: 모르는 건은 미루고 진행. 나중에 일괄 처리

## 5. L4 — 자동화 시스템 "생성"의 현실적 형태

### 권장: 모듈 조립 방식
| 구성 | 설명 |
|---|---|
| 코어 모듈 | 거래처·품목·재고·주문·발주·입출고·정산·승인·알림 (사전 구현·검증됨) |
| 회사 모델 | L3에서 확정된 엔티티·필드·코드체계·역할 |
| 조립 산출물 | 테이블 설정, 화면(목록/상세/입력), 워크플로(상태전이·승인), 권한, 리포트, 업로드 매핑 |
| 확장 지점 | 회사 고유 규칙은 **규칙 DSL**(조건→동작)로 표현. 임의 코드 생성 금지 |

### 비권장: 요구사항→전체 코드 자동생성
- 검증 불가능한 코드가 대량 생성되어 유지보수 비용이 폭증한다.
- 회계·세무·전자문서 규정은 추론이 아니라 준수 대상이다.
- 대신 **규칙 DSL + 검증된 모듈**로 커버하고, 커버 불가 영역은 사람이 개발한다.

### 산출물 검증 게이트 (모두 통과해야 시범운영)
1. 과거 3개월 실데이터 재현 대사 — 금액·수량 0 오차
2. 필수 업무 시나리오 E2E 통과
3. 권한·개인정보 접근 검사
4. 롤백 가능성 확인(기존 방식 병행 운영 기간 확보)

## 9. 차별점

- **원본 보존 + 역추적**: 자동화 결과의 모든 숫자가 원본 셀/문단/영상 구간으로 되돌아간다. 신뢰 확보의 핵심.
- **재현 대사로 증명**: "잘 될 것 같다"가 아니라 "지난달 장부와 0원 차이"로 설득한다.
- **점진 도입**: 기존 엑셀 업무를 없애지 않고 병행한다.
- **NTV2 실증 자산 보유**: 원자화 계층은 이미 동작하는 코드가 있다.
