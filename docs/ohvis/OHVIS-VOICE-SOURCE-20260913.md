## 1. 결론 아키텍처
OBIS 최적 설계는 **교체 가능한 컴포넌트의 스트리밍 캐스케이드**이지 종단간(speech-to-speech) 모델이 아니다.
종단간 지연 800~2000ms 는 UX 임계 1.5초를 넘고, 고정 침묵 타이머(약 800ms)는 예산을 낭비한다.
**지연의 주범은 턴 감지(endpointing)** 다.

지연 예산: STT 확정 <300ms(중앙값) / TTS 첫 바이트 <200ms / 총 응답 <1500ms.

## 6. 빅스비 ↔ OBIS 연동
가능하다. 단 **OBIS 는 '비서'가 아니라 '정보 제공자'** 로 제한된다.
- 흐름: Bixby → Capsule(Remote Endpoint) → OBIS 서버 호출 → JSON → Bixby 가 사용자에게 보고.
- Bixby 는 앱을 직접 열지 않는다. 보고 형식이 `msg.message` / `msg.image` / `msg.data` 3필드로 제한돼
  OBIS 의 복잡한 오케스트레이션 결과가 압축된다.
- 대체: 삼성 Automation Studio 범용 캡슐로 1~2주 내 PoC 가능(심사 불필요, 표현 제한·베타 표기).
- 권고: OBIS 서버를 **'툴 서버'로 설계**해 Bixby 외 iOS App Intents, MCP 등 다중 진입점을 제공.

## 9. 4장 평가셋 설계
총 300 발화:
A 일정/시간 60 · B 이름/기관 60 · C 숫자/금액/연락처 50 · D 영문 코드스위칭 40 · E 잡음/거리 50 · F 자연대화/휴지 40.
목적은 절대 CER 이 아니라 **STT 상대 순위**와 **엔티티 정확도**.

정규화 규칙(v1.0 고정 후 측정):
숫자→아라비아("세시"→"3시") / 영문 약어→대문자("에이피아이"→"API") / 공백 전부 제거 /
문장부호 제거(물음표는 별도 보존) / 필러(어, 음, 그)는 턴 감지 시험용으로 보존.

측정 스크립트 4모듈: `normalize.py`(jiwer.Compose) → `transcribe.py`(엔진 래퍼, 모델명·지연 기록) →
`evaluate.py`(카테고리별 CER + 엔티티 오류율) → `report.py`(엔진×카테고리 행렬, 빈출 오류어 추출).
엔진 간 beam size 고정.

산출물: 300 오디오 + 엔티티 태깅 정답 전사, 정규화 규칙 v1.0 문서, CER 행렬, 엔티티 오류표, 빈출 오류 목록.

## 판단 근거가 된 수치 두 개
1. **종단형은 아직 느리다.** AssemblyAI 아키텍처 비교 기준 end-to-end 음성 모델 지연 **800~2000ms**.
   "대화가 대화처럼 느껴지는" 경계선 1.5초를 넘나든다. 게다가 중간 텍스트가 없어
   **감사·분석·QA가 의존하는 전사(transcript)를 잃는다.** 원문 평가: "지켜볼 만하지만
   올해 컨택센터를 걸 만하지는 않다."
2. **지연의 주범은 모델이 아니라 턴 감지(endpointing).** 고정 800ms 침묵 대기를 쓰면
   모델을 하나도 호출하기 전에 예산 절반 이상을 소진한다. 가장 흔한 실패 원인.

## 반대 방향 증거 — 종단형 지능 격차는 좁혀지는 중
OpenAI GPT-Realtime-2 발표 내용:
- 컨텍스트 32K → **128K**
- **병렬 툴 호출**
- **프리앰블**("잠시 확인해 볼게요")
- **실패 복구 발화**
- 추론 강도 선택 **minimal ~ xhigh**
- Big Bench Audio에서 GPT-Realtime-1.5 대비 **+15.2%**, Audio MultiChallenge **+13.8%** 주장

→ 결론: 남은 문제는 지능이 아니라 **지연과 관측 가능성**이다. 그래서
**캐스케이드를 기본으로 하되, 종단형으로 갈아탈 수 있는 추상화 계층**을 둔다.

## 판단 근거가 된 수치 두 개
1. **종단형은 아직 느리다.** AssemblyAI 아키텍처 비교 기준 end-to-end 음성 모델 지연 **800~2000ms**.
   "대화가 대화처럼 느껴지는" 경계선 1.5초를 넘나든다. 게다가 중간 텍스트가 없어
   **감사·분석·QA가 의존하는 전사(transcript)를 잃는다.** 원문 평가: "지켜볼 만하지만
   올해 컨택센터를 걸 만하지는 않다."
2. **지연의 주범은 모델이 아니라 턴 감지(endpointing).** 고정 800ms 침묵 대기를 쓰면
   모델을 하나도 호출하기 전에 예산 절반 이상을 소진한다. 가장 흔한 실패 원인.

OpenAI GPT-Realtime-2 발표 내용:
- 컨텍스트 32K → **128K**
- **병렬 툴 호출**
- **프리앰블**("잠시 확인해 볼게요")
- **실패 복구 발화**
- 추론 강도 선택 **minimal ~ xhigh**
- Big Bench Audio에서 GPT-Realtime-1.5 대비 **+15.2%**, Audio MultiChallenge **+13.8%** 주장

→ 결론: 남은 문제는 지능이 아니라 **지연과 관측 가능성**이다. 그래서
**캐스케이드를 기본으로 하되, 종단형으로 갈아탈 수 있는 추상화 계층**을 둔다.
