# 세션 간 협업 — `ask_session` 기획서

- 작성 2026-09-14 KST
- 요청: "#310 전략카드 수익성 개선을 주도담당이 이끌고 각 담당이 조치하며
  서로 확인하게 하라"
- 설계·구현 규격은 [PRD](../prd/20260914_ASK_SESSION_PRD.md)

## 1. 지금 없는 것

세션끼리 말을 걸 방법이 없다. 있는 것은 이렇다.

| 있는 것 | 성격 | 세션 간인가 |
|---|---|---|
| `run_debate` | 한 세션 안에서 여러 관점을 병렬로 돌려 종합 | 아니오 |
| `DiscussionOrchestrator` | 한 세션 안에서 페르소나 다회차 토론 | 아니오 |
| `delegate_to_agent` | AutonomousExecutor 에 위임 | 단방향, 대화 아님 |

담당 다섯을 세워도 서로 물어볼 수가 없으니 각자 혼자 판단한다.
**파동엔진이 "진입을 당기자" 할 때 실매매엔진의 슬리피지 의견을 받을
길이 없다.** 한 담당의 개선이 다른 담당의 지표를 깎는 것이 이 작업의
기본 위험인데, 그걸 잡을 장치가 없다.

## 2. 쓸 수 있는 부품

**세션에 메시지를 넣고 답을 받는 경로는 이미 돈다.** 파이프라인 러너가
쓰는 길이다.

    send_message_stream(session_id, content, intent_override="system_trigger")

7일 실측: **501건 주입 → 483건 응답 (96%)**. 새 인프라가 필요 없다.

없는 것은 이 경로를 도구로 노출한 것과, **답이 물어본 쪽으로 돌아오는 길**이다.

## 3. 반드시 비동기여야 한다

오늘 실측한 응답 시간이 **2분 ~ 61분**이다.

    세션 3d81c01a   129초 후 중단
    세션 5090a247   3,671초(61분) 후 완료
    세션 d3104086   22분간 도구 45회 호출 중

A 가 B 를 기다리면 A 가 먼저 죽는다. 오늘 고친
`llm_first_response_timeout` 이 정확히 그 증상이었다.

그래서 **A 는 영수증만 받고 계속 진행**하고, B 의 답은 나중에 A 세션에
새 메시지로 들어온다. 완료 알림(`showChatStatusAlert`)이 이미 있으므로
그대로 쓴다.

## 4. 무한 루프를 막지 못하면 만들면 안 된다

A 가 B 에게 묻고 → B 가 A 에게 되묻고 → 끝없이 돈다. **사람이 안 보는
사이 두 세션이 서로에게 수백 번 말을 걸 수 있다.**

오늘 같은 종류의 사고가 있었다.

    resume 요청 시간당 1,256회 — 자동 재시도가 스스로를 먹었다

세 겹으로 막는다.

1. **홉 수 제한** — 한 줄기당 왕복 3회. 메시지에 `hop` 을 기록하고
   넘으면 도구가 거절한다.
2. **같은 쌍 동시 진행 금지** — A↔B 가 이미 대화 중이면 새로 못 건다.
3. **원본 추적** — 모든 파생 메시지에 `origin_session_id` 를 달아
   어디서 시작됐는지 남긴다.

## 5. 승인 게이트를 우회하지 못한다

주도가 실매매 변경을 막히면 다른 담당에게 시켜서 우회할 수 있지 않나 —
**막힌다.** 승인 게이트는 `ToolExecutor.execute()` 에 있고, 어느 세션이
부르든 같은 검사를 받는다. 세션을 바꿔도 도구는 같은 문을 지난다.

## 6. 하지 않는 것

- **자동 트리거.** 오류가 나면 담당이 스스로 착수하는 것. 승인 게이트가
  검증되기 전에는 만들지 않는다.
- **세션 자동 생성.** 담당 세션 다섯은 이미 있고 메시지 3,632건의 맥락을
  갖고 있다. 새로 만들면 그걸 버린다.
- **A 의 대화 맥락 전달.** 질문과 공유할 내용만 보낸다. A 의 맥락이 B 에
  섞이면 B 의 다음 대화가 오염된다. 공유할 부분은 부르는 쪽이 고른다.
