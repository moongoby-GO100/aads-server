## 1. 결정 요청과 권장 운영

직원이 출퇴근 버튼으로 기록하고, 잘못되거나 빠진 시간은 수기 정정 요청을 제출하며, 관리자가 확인·승인하는 방안을 권장한다. GPS는 장소 확인의 보조 증거로 사용한다. 위치 거부·오차·통신 실패만으로 결근이나 근로 부정을 확정하지 않는다. 기존 관리자 수기 입력은 보존하며, 직원 요청 경로가 구현되기 전에는 관리자에게 정정을 요청하고 관리자가 사실 확인 후 기존 입력 경로를 사용한다.

승인 요청은 ① 관리자 확인을 통한 최종 확정 원칙 ② 과거 무기록 일정의 확인필요 표시 ③ 마감 후 변경 승인·급여 차액 검토 ④ 위치 수집 범위·보관·열람 정책 ⑤ 단계 전환 측정 기준이다. 모두 제안이며 현재 적용됐다고 보고하지 않는다. 법적 적합성이나 급여 항목의 법정 충족 여부를 확정하는 문서가 아니다.

## 3. 근거의 범위와 운영 DB 확인 제한

코드 근거는 작업 워크트리이며 운영 실측이 아니다. ACCT 대상은 server-114(114.207.244.86, 기대 hostname rfree-0009.cafe24.com)이다. 다른 서버의 근태 데이터로 대체 확인하지 않았다.

승인된 접근 경로는 사업자·직원 범위를 검사하는 records/schedules/clock/state 조회 API와 관리자 위치 조회 API, 전용 OBYS DB 연결이다. 현재 환경에서 OBYS_DATABASE_URL이 없고, server-114의 hostname만 읽는 SSH도 socket Operation not permitted로 실패했다. 원격 명령에는 timeout을 적용했다. 운영 DB SQL·개인정보 조회 및 운영 쓰기는 수행하지 않았다. AADS PG 환경의 읽기 연결 역시 OperationalError여서 작업 DB의 실제 job_id를 재조회하지 못했다.

따라서 10월 일괄 등록 건수·대상·시급 0 분포·급여 확정 상태·현장 위치 정확도는 미확인이다. 후속 검증은 승인된 관리자 조회로 사업자별 기간·source·status·시급 0 건수를 집계하고, 개인정보와 좌표 원본을 보고서에 싣지 않는 방식으로 진행한다. 근태와 명세의 record_ids·계약 버전·금액을 대조하되 초안 생성 POST는 읽기 검증에 사용하지 않는다.

## 4. 직원 화면과 반복 사용 흐름

첫 화면에는 현재 사업자·지점, 오늘 근무예정, 실제 출퇴근 기록, 관리자 확인 상태, 출근 또는 퇴근 버튼을 표시한다. 예정 시간과 실제 시간의 제목을 구분한다. 최초 사용 시 위치 수집 목적·범위와 선택권을 안내하고 로그인 계정의 소속을 확인한다. 위치 동의와 브라우저 권한은 따로 표시한다.

반복 방문 시 서버 clock/state를 먼저 읽어 열린 출근을 복원한다. 요청 중 버튼을 잠그고 응답 후 서버 기록 ID·원본시각·상태를 표시한다. 재방문·새로고침·다른 기기 사용에서도 같은 근무를 이어간다. 사용자가 사업자를 전환하면 이전 사업자의 임시 입력과 위치 상태를 섞지 않는다.

정정 화면은 대상 기록, 변경 전후 시각, 휴게, 사유, 제출 상태를 보여준다. 제안 상태 전이는 작성중→제출→승인/반려/철회이며, 제출 후 변경은 이전 요청을 철회하고 새 버전으로 재신청한다. 승인된 기록의 변경은 새 정정 요청으로 처리한다. 반려 사유를 직원에게 보여주며 원본과 이전 신청은 보존한다. 이 직원 요청·철회·재신청 상태 모델의 완성 여부는 현행 조사에서 확인되지 않았으므로 신규 구현 대상으로 본다.

| 상황 | 권장 복구 및 화면 검증 |
|---|---|
| 로그인 만료·권한 부족 | 로그인 복귀 후 상태 재조회, 타 직원 신원 입력 금지. 401/403에서 성공 표시 금지 |
| 위치 거부·미동의·부정확·지점 좌표 없음 | 위치 없이 기록 또는 수기 요청을 안내하고 관리자 확인 대기로 처리. GPS 실패를 결근으로 표시하지 않음 |
| 오프라인·응답 유실 | 로컬 입력은 미전송으로 표시. 재접속 후 서버 상태를 읽고 동일 요청 키로 재전송. 로컬 탭 시각을 서버 수신시각처럼 표시하지 않음 |
| 퇴근 누락 | 열린 출근을 알려 정정 요청. 임의 자동 퇴근·시간 확정 금지. 현행 퇴근 탐색 창 24시간을 넘으면 관리자 확인 경로 제공 |
| 야간 교대 | 출근 기준 근무일과 KST 절대 시각으로 자정 경계 연결. 다음날 신규 출근과 전일 열린 근무 충돌을 관리자 확인 |
| 중복 탭·수기/PWA 중복 | 기존 기록·요청을 보여 재사용 또는 정정 연결. 두 건의 근로분을 합산하지 않음 |

## 5. 현행과 제안의 차이, 기록·격리 원칙

현행 judge_geofence는 정확도·지점 반경 조건을 만족하는 inside를 approved로 반환한다. check-out도 양쪽 inside이면 approved가 될 수 있다. 권장안의 관리자 최종 확인 원칙과 다르다. 단순 화면 문구 변경으로 자동 승인이 중단된다고 가정하면 안 된다. 이후 정책 승인 후 판정과 최종 승인 상태를 분리해야 한다.

현행 출근은 사업자·직원 잠금, 같은 날 열린 PWA 중복 검사, unique 충돌 409 처리를 사용한다. 이것만으로 겹치는 수기 시간대와 PWA의 의미상 중복이 모두 차단되는지는 확인되지 않았다. 제안은 사업자+직원+근무 세션을 기준으로 원본 이벤트를 연결하고 단일 유효 근태 버전만 급여에 공급하는 것이다. 같은 날 두 교대를 허용해야 하므로 일자 단독 unique로 설계하지 않는다. 서버 멱등키와 기간 겹침 검사를 트랜잭션 안에서 적용하고, 충돌 시 덮어쓰지 않고 정정 대상을 선택하게 한다.

원본 이벤트에는 출처(manual/pwa), 직원·사업자·세션 ID, 원본 발생시각·시간대, 서버 수신시각, 수정 전후 값, 수정이유, 요청자·승인자·승인시각, 반려·철회·재신청 연결을 남긴다. GPS 원본과 최종 근태는 별도 권한으로 관리한다. 현행 source·check_in_at/out·감사 경로를 재사용하되 모든 필드와 전후 버전 보존이 이미 완비됐다고 보지 않는다.

모든 조회·수정·승인·집계에 테넌트와 사업자 조건을 적용한다. 직원은 본인 기록·요청만, 관리자는 자신이 관리하는 사업자만 접근한다. 요청 본문의 직원 이메일을 신원으로 신뢰하지 않는다. 위치 원본은 관리자 제한 조회만 허용하고 감사 기록에는 필요 최소 정보만 남긴다. 보관기간·삭제 및 열람 정책은 별도 승인 대상이다.

## 6. 일정·휴게·급여·마감

계약서의 근무예정은 비교 기준이며 실근로 증거를 대신하지 않는다. 일정 생성이나 계약 가져오기만으로 출근·급여를 확정하지 않는다. 과거 일정에 기록이 없으면 확인필요로 제안하고 관리자가 직원 확인·자료 대조 후 결근을 확정한다. 현행 attendance_schedule_judgment는 과거 무기록에 결근을 반환한다. 개선 정책과 구현 승인 전에는 확인필요가 적용됐다고 표현하지 않는다.

실근로는 승인된 출퇴근과 확인한 휴게로 계산하고, 예정 휴게를 무조건 실휴게로 확정하지 않는다. 주간 집계와 야간분, 급여 초안의 근거 기록 ID를 연결한다. 현행 주간 집계 코드도 계약상 소정근로일 없이는 개근·주휴를 확정할 수 없음을 명시한다. 급여·휴게·수당의 법적 해석은 이 제안에서 확정하지 않는다.

**시급 0의 코드상 영향:** yeoljeong_finance_service.py의 payroll_draft_from_attendance는 서명 완료 계약의 wage를 rate로 사용한다. 시급제 총액은 (승인근로분×rate+30)//60, 일급제는 승인근무일수×rate이다. 근태 hourly_wage=0은 이 경로의 단가로 사용되지 않고 rate_mismatch_records에서도 불일치로 세지 않는다. 계약 단가가 0 이하이면 409, 미확정 근태가 있거나 유효 승인 근태가 없으면 409이다. 기존 확정 명세가 있으면 덮어쓰지 않고 정정 버전을 요구한다.

따라서 10월 일괄 등록의 시급 0만 보고 이 경로에서 급여가 0원이 된다고 결론낼 수 없다. 반대로 안전하다고 보장할 수도 없다. 실제 계약 단가·승인 상태·근로분·중복·사용 급여 경로 및 다른 통계의 행 시급 참조는 미확인이다. 운영 데이터 대조와 승인된 샘플의 예상액 비교가 필요하다.

마감 후 정정은 관리자 사유·승인과 영향 미리보기 후 새 버전으로 반영하도록 제안한다. 원래 명세·지급 이력은 보존하고 차액·정정명세를 연결한다. 근태 CRUD 전 구간의 마감 잠금 보장은 이번 조사에서 입증되지 않았다. 근태 승인·급여 확정·재집계가 동시에 실행되는 경우에도 같은 버전을 보도록 별도 검증한다.

## 8. 구현 우선순위·공유 파일 의존·검증 기준

모든 항목은 후속 구현 제안이며 이번 작업에서 구현하지 않았다. schedule_fix는 독립 진행하되 같은 파일·함수에 닿는 변경은 적용 순서를 합의하고 최종 결합 검증한다. 문서만 작성하는 현재 작업은 해당 파일을 잠그거나 수정하지 않는다.

| 우선순위 | 범위·예상 공유 접점 | API/DB 검증 기준 | 모바일·화면 검증 기준 |

## 9. 보존과 단계별 롤백

테스트 단계에서는 기존 수기를 기준으로 대조하고 기존 기록을 삭제·교체하지 않는다. 위치 문제가 있으면 위치 수집·사용 안내를 중단하고 수기 입력을 계속한다. 병행 단계에서는 새 요청 유입을 중지해도 접수된 요청·감사·기존 승인 근태를 보존하고 관리자가 미처리 건을 이어받는다. 승격 이후 문제 발생 시 수기 중심으로 복귀하고 해당 기간 급여·근태 버전을 대조한다. 확정 급여를 예전 값으로 일괄 덮어쓰지 않는다.

모든 단계에서 위치 데이터와 수기 기록을 자동 병합·삭제하지 않으며 운영 DB 복구는 별도 승인된 절차를 따른다. 원본·버전·대기 요청 수의 전후 비교와 급여 합산 불변 검증 후 복귀를 확인한다. 이번 문서 작업에는 제품 변경이 없어 제품 롤백 조작은 없다.

- 변경: 이 문서 한 파일 신규 작성. 허용 범위 외 파일 변경 사유 없음. 코드 수정 요구의 일반 규칙보다 본 작업의 문서 단일 파일·코드 변경 금지 범위를 적용했다.
- 실제 조사: 기존 근태·GPS·급여·정본·핸드오버 코드 읽기. git status로 시작 시 변경 없음 확인.
- 실패: psql 읽기 명령은 실행 파일 부재(exit 127). psycopg2 AADS 읽기 연결은 OperationalError. server-114 SSH hostname 읽기는 환경의 socket 권한 차단. 우회 서버 사용 없음.
- ACCT 실측: 전용 연결 설정 없음으로 운영 DB 데이터 조회 미실시. 10월 시급 0 실데이터와 운영 적용 판본은 미확인.
- 정본: 기존 키의 현재 판본 조회·초안 등록·등록 후 lookup 미완료. AADS_API_URL과 정본 쓰기 인증이 환경에 없다. 정본 미등록(미완료), 열람 링크 미제공. 10:06 KST 미등록은 지시서의 사전 조회 결과이며 이번 조회 성공으로 간주하지 않는다.
- 후속 등록은 project=AADS, 위 document_key·kind·goal_id·source_task_id·change_summary와 본문을 정상 POST /api/v1/projects/AADS/documents 또는 canonical_document_register에 전달한다. 먼저 기존 키를 lookup하고 기존 판본이 있으면 key·경로 유지, 현재 generation·version으로 갱신한다. 새 문서일 때 expected_generation=0. 충돌 시 재조회하며 승인·승격 API는 호출하지 않는다. 등록 후 lookup의 draft·본문 일치·열람 참조를 확인해야 완료다.
