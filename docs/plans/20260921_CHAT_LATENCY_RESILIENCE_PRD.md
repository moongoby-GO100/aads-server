## 3. 원인 분석 — 코드 지점

### 3.1 한 턴이 모든 것을 짊어진다 (①②의 원인)

지금 구조는 `사용자 입력 → 한 실행(chat_turn_executions 1행) → 도구 N회 →
본문 → 종료` 다. 도구 190회를 도는 조사 턴과 인사 한 줄이 **같은 수명 모델**을
쓴다. 그래서 긴 작업은 채팅 스트림을 20분 붙잡고, 그동안 화면은
`⏳ AI가 응답을 생성 중입니다... (도구 N회 호출 중)` 한 줄뿐이다
(`app/services/chat_service.py` 스트리밍 placeholder 경로).

### 3.2 watchdog 이 진행이 아니라 시계를 본다 (④ `watchdog_timeout` 6.4%)

`app/main.py:904~925` — 정리 대상 판정이 전부 시간 상수다.

```
te.status IN ('running','retrying') AND (
    (last_event_id='' AND started_at < NOW()-'20 min' AND updated_at < NOW()-'10 min')
 OR (last_event_id<>'' AND started_at < NOW()-'45 min' AND updated_at < NOW()-'20 min')
 OR (started_at < NOW()-'30 min' AND actual_model='')
 OR (started_at < NOW()-'90 min')
)
```

마지막 절이 문제다 — **90분을 넘으면 진행 중이어도 끊는다.** `updated_at` 이
약한 진행 대용이지만 도구 실행 중에는 갱신되지 않는 구간이 있어, 일하는 턴이
"멈춘 턴"으로 보인다. 테이블에는 이미 `heartbeat_at`·`lease_expires_at`·
`owner_instance`·`owner_epoch` 가 있는데 **이 판정절이 그것을 쓰지 않는다.**

### 3.3 lease 가 있는데 handoff 가 없다 (④ `superseded` 47.9%)

재개 스캐너가 만료된 lease 를 보면 실행을 **가져가서 새로 시작**한다. 원래
실행이 살아 있으면 그쪽이 `superseded` 로 죽는다. 09-17 에 오인 조건 하나를
좁혔지만(`a94f1cb5`), 구조 자체는 "뺏기"이지 "넘기기"가 아니다.

### 3.4 본문이 메모리에만 있다 (④ `producer_incomplete` 16.1%)

`_archived_partial`·`_has_meaningful_partial_content`·`streaming_placeholder`
경로는 이미 있다(`chat_service.py:300,739,1144,2624,3321`). 그러나 flush 주기가
없어, 도구 루프가 긴 턴은 끊기는 순간 `content_len=0` 으로 통째 유실된다
(09-17 실측 사례: 도구 73회 / 20분 / 본문 0자).

## 4. 설계

### 4.1 축 B — 채팅·백그라운드 작업 분리

**승격 조건**(둘 중 하나): 도구 누적 15회 초과, 또는 경과 60초 초과.

```
사용자 입력
  └ chat turn (수명 ≤ 60초, 항상 5초 내 첫 응답)
        ├ 즉시: 접수 + 계획 + 진행 채널 id
        └ 승격 시: background job 생성 → job 이 도구 루프를 이어받음
                       └ 진행 이벤트 → 같은 버블
                       └ 완료 → 원 버블 content 에 병합 (B-3)
```

핵심 제약: **분리는 유실이 되면 안 된다.** 그래서 B-3(병합)을 B-1과 같은
마일스톤 묶음에 두고, 병합 실패 시 job 결과를 별도 버블로라도 반드시 남긴다.

### 4.2 축 C — 진행 기반 watchdog + lease handoff

1. 실행 루프가 토큰·도구 증가 시 `heartbeat_at` 갱신(이미 컬럼 존재).
2. watchdog 판정을 `heartbeat_at < NOW() - INTERVAL '90 seconds'` 로 바꾸고
   시간 상수는 **상한(예: 6시간)** 으로만 남긴다.
3. lease 만료 시 죽이지 않고 `owner_instance`/`owner_epoch` 를 새 소유자로
   옮긴다(handoff). 이전 소유자는 epoch 불일치를 보면 스스로 물러난다.
4. 배포 컷오버는 이 handoff 를 그대로 쓴다 — 구 슬롯 실행을 신 슬롯이 이어받는다(C-3).

### 4.3 축 D — partial 영속화

- flush 조건: **3초 경과 또는 500자 증가** 중 먼저 오는 쪽.
- 대상: `streaming_placeholder` 메시지 content (이미 재개 경로가 읽는 자리).
- 중단 시: `_archived_partial` 로 확정하되 **본문은 남긴다**.
- 재개 시: partial 을 이어받아 완성한다(D-2). 처음부터 다시 쓰지 않는다 —
  비용과 시간이 두 배가 되고, 사용자는 같은 글을 두 번 본다.
