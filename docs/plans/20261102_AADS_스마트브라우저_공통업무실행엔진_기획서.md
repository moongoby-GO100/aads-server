## 1. 제품 방향
스마트브라우저를 “브라우저 도구를 호출하는 채팅”에서 “프로젝트와 세션, 외부 프로그램이 같은 업무를 요청하고 결과를 인수하는 공통 실행 서비스”로 발전시킨다. UI의 첫 화면은 업무 요청과 진행 중 업무, 지난 결과다. 계정 연결·PC 설정·관리자 권한은 보조 경로다.

핵심 차별화 가설은 세 가지다. 첫째, 업무 기록과 결과가 중앙에 남아 다른 세션에서 권한에 따라 이어 볼 수 있다. 둘째, 프로세스 중단 후 검증된 체크포인트에서 복구하며 이미 수행한 외부 작업을 함부로 반복하지 않는다. 셋째, 같은 기능을 채팅·REST·Python 모듈과 SDK가 동일 계약으로 사용한다. 가설의 입증은 기능 목록이 아니라 비교 시험으로 한다.

## 3. Aside 비교와 입증 범위
2026-11-02 공식 문서를 다시 조회했다. 아래는 공개 문서상 기능이며 직접 업무 성능 측정이 아니다.
- routines: cron과 heartbeat, 겹치는 실행 건너뛰기, 대상 채팅 불가 시 중단. https://docs.aside.com/help/automation
- 개발자 연동: CLI·MCP·REPL, 세션 이어하기. https://docs.aside.com/help/developers
- 장치 연속성: 채팅·작업 기록·프로젝트·루틴·사이트 로그인은 장치 간 동기화하지 않는다고 설명. cloud handoff는 Coming Soon. https://docs.aside.com/help/devices
- 작업 제어: 모드·권한·작업 폴더·모델, 승인과 자격증명 입력 지원. https://docs.aside.com/help/tasks
기존 oby-ceo PC 조사에는 Aside AI 세션 Paused 관측이 남아 있다. 이번 턴 PC 상태를 재확인하지 않았고 현재 로그인 불가라고 단정하지 않는다. 직접 비교는 해당 PC의 실제 AI 응답을 확인한 뒤 진행한다.

## 4. 대상 사용자와 사용자 여정
1. CEO/운영자: “발주 목록을 모아줘” 입력 → 계정과 실행 위치 요약 → 기존 승인 레시피 발견 또는 시험 초안 → 진행 상황 → 데이터·화면 증거 → 예약 제안. 실제 승인 범위를 넘어서는 동작에만 승인 카드.
2. 프로젝트 담당 세션: 현재 프로젝트 권한으로 레시피·결과 검색 → 자신의 업무 실행 요청 → 다른 세션에서도 같은 실행 ID 조회. 실행 소유권과 보는 권한을 분리.
3. 프로그램 개발자: SDK 설정 → 제한된 서비스 인증 → 멱등 키로 실행 → 상태/커서 조회 → 자신의 DB에 record_key로 반영. 타 프로젝트 접근은 명시적 공유 범위만.
4. 장애 복구 사용자: 중단 원인과 마지막 성공 화면 확인 → 필요한 재인증 또는 승인 → 유효성 재검사 → 이어하기. PC를 바꾸면 브라우저 인증은 새 PC에서 다시 확인한다.

## 5. 범위와 단계
이번 구현 범위는 다음 전부다. 하나만 구현하고 제품 전체 완료로 보고하지 않는다.

| 단계 | 산출물 | 의존 | 완료 정의 |
|---|---|---|---|
| D0 | 기획·PRD·설계 정본, 저장소 파일, 계약 명세 | 없음 | 본문 해시·등록 판본·파일 일치 |
| B1 | 공통 실행 원장·권한·fencing·체크포인트·outbox | D0 | 실제 PostgreSQL 경쟁·재시작 시험 |
| B2 | 수집 품질·원자 저장·변경 커서·예약/큐 연결 | B1 | 오류 시 저장 0, 변경량과 커서 대사 |
| B3 | MCP·REST·Python 모듈·원격 SDK | B2 | 세 입구 계약·테넌트/프로젝트 격리 |
| B4 | 관측-계획-행동-검증 및 레시피 복구 후보 | B3 | 제한된 실패 복구·쓰기 승인 보존 |
| U1 | 업무 실행 UI·첫 사용·실패 복구 | B4 | 실제 PC/모바일 캡처·이벤트 복구 검증 |
| V1 | 통합 인수·비교 시험·릴리스 준비 | U1 | 테스트 원본과 미검증 목록·배포 전 점검 |
| E0 | 독립 비교 fixture·정답·평가 도구 | D0와 병렬 가능 | fixture만으로 동작하는 평가기, 실측과 목표 구분 |

같은 player/executor/API 경로를 만지는 B1~B4는 순차. E0는 tests/benchmarks/smart_browser/ 범위만 사용해 병렬 가능. U1은 dashboard 별도 repo의 기존 브라우저/자동화 화면을 확장하며 독립 앱을 새로 만들지 않는다. 최종 V1은 E0와 U1 모두의 실제 완료 SHA를 확인해야 한다. 배치 도구의 단일 depends_on 제한 때문에 여러 선행 조건은 실제 등록한 job_id로 검증하고 선행 미완료를 성공 처리하지 않는다.

## 6. 범위 밖과 연결할 기존 업무
금융/BANKING 경로 이전, 주문·결제 자동 실행, 쿠키의 PC 간 무조건 복사, 봇 방어 우회, CAPTCHA 자동 대행, 운영 전역 자동승인 플래그 변경은 하지 않는다. 쿠팡과 쿠팡이츠의 “로그인 버튼만 마우스로 클릭” 승인은 사이트별 기존 승인 계약을 유지한다. 페이지·계정·장치·후조건이 맞는 경우에만 1회 제출하고 인증 유지가 확인되면 반복하지 않는다. 이 기획이 기존 쿠팡 실측 완료를 의미하지 않는다.

## 7. 품질·운영·비용
- 기본 경로는 승인 레시피 재생이다. 새 화면은 구조화 관측과 제한된 계획을 사용하며 무제한 에이전트 루프를 피한다.
- LLM 호출은 중앙 라우터와 LiteLLM을 사용한다. 모델·토큰·가격을 문서에 고정하지 않는다. 기능 요구 때문에 특정 모델 선택을 강제하지 않는다.
- 비용은 실측 합산; 초기 구현 배치는 누적 $5 초과 예상 시 후속 유료 실행을 멈추고 사유·남은 범위를 보고한다. 비용 미계측 상태는 $0이 아니다. 자동 재작업은 끈다. 시간/개발비는 현재 미측정.
- 기존 모듈과 승인 코드를 재사용한다. 신규 테이블은 실제 기존 스키마와 대조 후 additive migration으로 작성한다. 운영 적용은 별도 릴리스 승인.
- 기능 flag는 기본 비활성, 개발/test 활성화. 코드 push와 운영 활성화를 구분한다.
- 릴리스는 clean SHA·단일 이미지·bluegreen·DB 실행 소유권·동일 digest standby·routed health rollback·5분 P0/P1 감시 계약을 따른다.

## 8. 성공 기준
1. PRD FR-01~FR-18과 AC-01~AC-20의 구현/시험/증거가 추적된다.
2. 두 세션과 서비스 호출자가 같은 권한 규칙으로 요청하고, 같은 멱등 키는 같은 실행을 반환한다.
3. 프로세스 강제 중단·lease 만료·PC 단절 후 외부 작업을 재중복하지 않고 재개 또는 명확한 사람 확인으로 전환한다.
4. 동일 작업 비교는 정상/복구/수집/권한별로 분리한다. 측정 전에는 “Aside보다 뛰어나다”를 완료 문구로 쓰지 않는다.
5. 문서 저장, 코드 테스트, push, 스키마 적용, 서비스 배포, 화면/실업무 인수의 상태를 각각 기록한다.

## 9. 위험과 의사결정
| 위험 | 대응 | 중단 기준 |
