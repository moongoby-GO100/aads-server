# 채팅 신뢰성·검증 체계 PRD — 2026-09-13

작성: 2026-09-13 · 대상: `aads-server` 채팅 스트림, `claude-relay`, 배포 후 검증

## 1. 문제

하루 동안 CEO가 보고한 증상은 네 가지였다.

- 채팅창에 "생성 중" 버블만 뜨고 응답이 오지 않는다
- 같은 지시를 다시 보내도 동일하다
- 응답이 끝난 뒤 보낸 지시가 "추가 지시"로 들어간다
- 특정 세션은 대화 내용이 아예 렌더링되지 않는다

겉으로는 하나의 고장처럼 보였지만 **서로 독립된 결함 일곱 개**였다. 각각이
다른 증상을 만들었고, 일부는 서로를 가렸다.

## 2. 원인 (실측)

### 2.1 CLI 대화가 호출마다 버려졌다 — 가장 큰 원인

릴레이는 CLI를 `docker exec` 로 실행하며 `HOME` 을 호출마다 새로 만든다.

```
-e HOME=/tmp/.claude-relay-slot-<슬롯>-<PID>-<RANDOM>
```

CLI는 대화를 `$HOME/.claude/projects/` 에 쓴다. HOME이 매번 바뀌니 대화는
**임시 디렉터리에 쌓였다가 호출이 끝나면 `rm -rf` 로 지워졌다.**

전날 이미 고쳐 둔 것이 있었다.

| 커밋 | 날짜 | 내용 |
|---|---|---|
| `a41445df` | 09-12 | 대화가 배포를 넘어 살아남도록 볼륨 마운트 |
| `a49eee32` | 09-13 | 슬롯별 자격증명 격리 — 호출마다 전용 HOME |

두 수정 모두 옳은데, 뒤가 앞의 전제를 깼다. 결정적인 한 줄은 이것이다.

```bash
# claude-oauth-wrapper.sh
export HOME="${HOME:-/tmp/.claude-sdk}"   # 래퍼가 HOME 을 넘기면 기본값을 쓰지 않는다
```

**볼륨은 붙어 있는데 아무도 쓰지 않는 상태**였다. 171MB·대화 981건이 그대로
남아 있고 새 대화만 임시 디렉터리로 갔다.

결과: `--resume` 대상이 없어 **매 턴 전체 프롬프트를 재전송**했다.

```
최근 6시간  resume=True 42건 중 18건이 "No conversation found"
프롬프트    bf6f097c 54,244자 · ac5278a7 49,190자 · 7542104d 39,572자
```

### 2.2 첫 응답 타임아웃 30초가 살아 있는 스트림을 끊었다

2.1 때문에 모든 턴이 콜드 스타트가 되자, opus-5가 첫 토큰을 내기 전에
타임아웃이 걸렸다.

```
최근 2시간 7건 / 직전 3일 1건 — 명백한 회귀
7건 전부 claude-opus-5, 전부 31~32초에서 중단
```

CLI는 그 시점까지 살아서 응답을 만들고 있었다. **살아 있는 스트림을 죽였다.**

### 2.3 자동재개가 한 줄에 막혔다

중단 사유 문자열은 이렇다.

```
background_producer_incomplete_exit:CancelledError:mark_interrupted:
llm_first_response_timeout_after_31s:heartbeat ...
```

이 문자열은 재개 대상 prefix 목록과 `producer_incomplete` 분류 **양쪽 모두**에
해당한다. 그런데 그 앞의 `blocked_tokens` 에 있는 `"CancelledError"` 한 줄에
걸려 먼저 거부됐다.

`CancelledError` 는 취소의 *수단*이지 이유가 아니다. 시스템이 스스로 건
타임아웃도 프로듀서를 cancel 해서 끝내므로 같은 토큰이 붙는다.

### 2.4 낡은 실행이 세션을 점유했다

세션 `539a6086` 당일 실행 이력이다.

```
08:51:16 → 22:24:16  running 유지 (13시간 반)
09:00:45 → 09:21:45  completed
09:23:45 → 09:25:09  completed
09:25:31 → 09:41:57  completed
```

낡은 실행이 `is_streaming` 을 붙잡고 있어, 이후 지시가 전부 추가지시 큐로
들어갔다. **13시간 전에 버려진 턴에 새 지시가 붙었다.** 화면이 "응답이
중단되었습니다, 다시 보내주세요"라고 안내한 직후에도 그랬다.

기존 가드 둘은 이걸 못 잡는다. `_empty_stale` 은 진행 내용이 있으면
빠져나가고, `_hard_stale` 은 하트비트가 돌면 `updated_age` 가 작아 빠져나간다.
둘 다 나이와 활동성만 보기 때문이다.

### 2.5 릴레이가 실패 사유를 버렸다

CLI가 `result` 이벤트를 낸 뒤 실패하면, stderr의 실제 사유는 로그에만 남고
앱에는 `"CLI error"` 만 갔다. 상세 전달 경로가 `if not saw_result:` 안에만
있어 이 경우를 타지 못한다.

```
릴레이 로그  CLI stderr(exit=1): No conversation found with session ID: fae76dac
앱이 받은 값  "CLI error"
```

그래서 복구 가능한 세션 매핑 오류가 **모델 강등**(opus-5 → sonnet-4-6)으로
처리됐다. 한도·인증·세션유실이 전부 한 문자열로 뭉개졌다.

### 2.6 한도 배너가 답변 앞에 붙었다

```
You've hit your weekly limit · resets Sep 16, 3am (Asia/Seoul)해당 세션 내용을 확인하겠습니다.
```

공급자 실패 문구 억제가 `all(blocks)` 조건이라, 메시지가 그 문구 하나뿐일
때만 동작했다. 배너 블록과 답변 블록이 함께 오면 둘 다 통과했다. 실제로는
응답이 정상 생성됐는데 사용자에게는 한도 소진으로 보였다.

### 2.7 차트 한 건이 대화창 전체를 못 뜨게 했다

React #31 — `Objects are not valid as a React child (object with keys {label, values})`.

```json
{"type":"bar","data":[{"label":"A 기존 C3","values":[...]},
                      {"label":"B 하락파 차단","values":[...]}]}
```

`InlineChart` 는 `data: number[]` 만 지원하는데 검증이 `Array.isArray` 뿐이라
이 형식이 통과했고, 바 차트가 객체를 그대로 React 자식에 넣어 던졌다.
`ChatErrorBoundary` 가 받아 **대화창 전체**가 오류 화면이 됐다. 메시지 한 건이
904건짜리 세션을 못 뜨게 만들었다.

### 3.1 설계 원칙

**지워야 할 것과 남겨야 할 것을 분리한다(C1).** 자격증명은 호출마다 격리·삭제,
대화는 볼륨에 영속. 한 디렉터리에 섞여 있던 것이 문제였다.

**나이가 아니라 순서로 본다(C4).** 하트비트는 속일 수 있지만 "나중에 만들어진
실행이 있는가"는 속일 수 없다.

**화면에 들어가는 값은 언제나 숫자다(C7).** 정규화할 수 없는 입력은 렌더하지
않고 안내로 대체한다. 알 수 없는 형식이 와도 다시는 던지지 않는다.

**둘 다 필요하다(C2+C3).** C3만 고치면 재개가 또 콜드 스타트라 30초에서 다시
잘려 재개 루프가 된다. C2만 고치면 이미 멈춘 턴이 살아나지 않는다.

## 4. 내가 만든 회귀 두 건

정직하게 남긴다. 둘 다 오늘 내가 넣은 변경이 원인이었다.

### 4.1 `set -E` 가 종료 핸들러를 다시 실패로 만들었다 (`e7fad91c`)

배포 실패의 줄번호를 살리려고 `set -Eeuo pipefail` 로 바꾼 뒤, `cleanup_deploy`
의 `return "$_deploy_rc"` 가 ERR 트랩을 다시 태웠다. 트랩은 EXIT 문맥에서
`LINENO=1`, `BASH_COMMAND="exit 1"` 을 보므로 **실제 원인을 일반 메시지로
덮어썼다.** 이 경로는 실패한 배포 전건에 걸렸다.

재현 스크립트로 `#389` 의 문자열을 그대로 만들어 확인한 뒤, 종료 핸들러
진입 직후 트랩을 해제했다.

### 4.2 디스크 가드가 빌드 중인 릴리스 이미지를 지웠다 (`ad148763`)

```
22:28        배포 #393 시작
~22:38-22:41 이미지 export/unpack (빌드 273초, naming ... done)
22:40:15     disk_guard 정리 실행 (88% → 87%)
그 직후      릴리스 이미지 조회 실패 → 배포 전체 failed
```

갓 만든 이미지는 태그 확정 전 잠시 dangling 으로 보인다. 그때
`docker image prune --filter dangling=true` 가 돌면 지워진다. 배포 락 또는
`deploy.sh`/`docker build` 프로세스가 보이면 정리를 건너뛰도록 고쳤다.

**교훈** — 셸 옵션 변경과 주기적 정리 작업은 영향 범위가 파일·시스템 전체다.
단위 검증만으로는 부족하고, 적용 후 첫 실패 기록을 반드시 확인해야 한다.

## 5. 검증 체계의 결함 — 왜 아무도 몰랐나

위 결함 중 여럿이 오래 방치됐다. 검증 계층이 작동하지 않았기 때문이다.

### 5.1 배포 후 QA 는 한 번도 실행된 적이 없다

```bash
curl -sf -X POST ".../visual-qa/full-qa" -H "Content-Type: application/json" -d '{...}'
```

`Authorization` 헤더가 없다 → 401 → `curl -sf` 실패 → 더미 JSON → `UNKNOWN`
→ "수동 확인 필요". 배포마다 같은 줄이 남았지만 아무도 보지 않았다.

QA 파이프라인 자체는 멀쩡했다. 토큰을 붙이니 200으로 verdict·design_score·
scorecard·screenshots 가 정상 반환됐다.

### 5.2 판정이 미확정을 통과로 읽었다

기존 로직은 `FAIL` 이 아니면 전부 통과로 봤다. QA는 `"CEO 확인 요청"` 같은
사람 판단 요청도 돌려준다. 인증만 붙였다면 그 값이 **"✅ QA 통과"** 로 찍혔을
것이다 — `UNKNOWN` 보다 나쁜 거짓 녹색이다.

### 5.3 QA 브라우저가 로그인하지 않았다

```
스크린샷 4장이 전부 23,241바이트 — 바이트 단위로 동일
/chat 스크린샷을 열어보니 로그인 화면
감리 요약도 "…초기 단계의 로그인 UI입니다"
```

`/`, `/chat`, `/ops` 를 찍는다면서 **로그인 화면을 세 번 채점**하고 있었다.

### 5.4 자격증명 창고가 둘인데 서로를 못 봤다

| | 테이블 | 쓰는 쪽 |
|---|---|---|
| 에이전트 볼트 | `agent_vault_credentials` | 대시보드 UI |
| E2E 볼트 | `e2e_credentials` | `e2e-inject`, 채팅 브라우저 로그인 도구 |

CEO가 UI로 등록한 자격증명은 전부 앞쪽에 저장되는데, 실제로 쓰는 코드는
뒤쪽만 봤다. **AADS의 브라우저 자동화 전체가 CEO가 등록한 자격증명을 읽지
못하는 상태**였다. `e2e_credentials` 에 행을 만드는 API는 어디에도 없어 사실상
죽은 테이블이다.

있으면 저장하지 않는다.

## 7. 남은 것

- **창고 일원화** — V4는 교차 조회까지다. 죽은 `e2e_credentials` 를 걷어내고
  에이전트 볼트로 합치는 작업이 남았다. 범위가 커서 별도 과제다.
- **GenSpark 대화 수집기** — 04-15 이후 한 건도 들어오지 않는다. 연동 코드와
  적재 기록(2만여 건)은 살아 있는데 폴러가 멈췄다. 원인 미조사.
- **`render` 투영의 base64 첨부** — 첨부를 따로 받을 엔드포인트가 없어 지금
  빼면 이미지가 안 보인다. 조회 API 신설이 선행돼야 한다.
