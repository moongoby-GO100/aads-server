**재작업 지적 1 — 지난 판 열 매핑 판정의 오류와 재판정 방법.** 지난 판은 표 한 칸에 "열 전부 매핑"을 적었지만, 한 라우트가 **행 종류(kind)를 여러 개 섞어** 돌려주는데도 종류별로 나눠 대조하지 않았다. 예: `cards` 는 ACCT 원천·카드·업로드 행이 섞이는데 업로드 행의 `display` 에는 카드사·카드번호·가맹점·승인·취소 키가 없다. 이번에는 아래 순서로 기계적으로 다시 대조했다.

1. `admin.html` 을 Node 로 실행해 `configs[route].columns` 의 **최종값**(`Object.assign` 덮어쓰기 `admin.html:119-121` 반영 후)을 뽑았다. 덮어쓰기는 `cards`·`suppliers`·`accounts` 세 곳이다.
2. 서버 `_record`(`obys_workspaces.py:231-407`)를 AST 로 읽어 **kind 별 `display` 키 집합**을 뽑았다(공통 기본 키 + kind 별 `display.update`). kind 는 ledger / acct-source / uploaded / card / bank / bank-account / journal / generic.
3. 라우트가 `_source_rows` 에서 어느 kind 를 돌려주는지 매핑했다(예: `cards` = acct-source + card + uploaded, `tax-evidence` = acct-source + ledger + uploaded).
4. `liveRow`(`admin.html:179`)는 `record.display?.[열]` 이 없으면 첫 열=id, 마지막 열=status, 나머지는 빈 문자열을 쓴다. 따라서 어떤 kind 의 display 에 키가 없는 열은 그 kind 의 행에서 **항상 공란**이다.
5. generic 라우트(`GENERIC_ROUTE_SQL`, `obys_workspaces.py:78`)는 키가 있어도 SQL SELECT 목록에 값 원천 열이 없으면 상수·빈 값이 된다. 이 값 원천 검사까지 해서 "키는 있으나 채울 값이 없는 열"을 따로 센다. 예: `approvals.금액` — 키는 있으나 `_amount` 가 금액 원천 열이 없으면 0 을 돌려줘 항상 "0원".
6. 한계: ledger·uploaded·acct-source·card·bank kind 는 키 존재만 봤다. 그 키가 가리키는 원천 **테이블 열의 실제 값 채움 여부**는 보지 않았고 로그인 후 데이터 캡처도 없다 [미확인]. 운영 서버가 이 코드로 돈다는 것도 [추정]이다(§0.0).

**판정 기준(3단계).**

- **열 매핑**: 데이터 열(첫 열=id·마지막 열=status·`사업자` 열 제외)이 모든 kind 에서 채워지는가 → 전부 / 일부 kind 또는 일부 열 누락 / 모든 kind 에서 공란인 열이 데이터 열의 과반.
- **업무 기능 충족**: 위 열 매핑에 더해 화면 이름·설명이 약속한 계산·판정이 서버에 있는가.
  - **충족** = 열 매핑 전부, 약속한 계산이 조회 수준을 넘지 않음.
  - **부분** = 일부 kind·열이 공란이거나, 약속한 계산·판정(대사·예정·추천·마진·누락·미지급 등)이 없음.
  - **미충족** = 모든 kind 에서 공란인 열이 데이터 열 과반이거나, 화면 제목이 약속한 핵심 열(정산 `입금차이`·입금예정 `예정일`)이 모든 kind 에서 공란이고 그 계산도 없음.
- 이 분류는 **정적 코드 대조**다. 값이 비었는지·적재가 있는지는 보지 않았다(§8.1).

**서브메뉴·라우팅.**

- 서브메뉴는 없다. 한 메뉴 = 한 라우트(해시) 구조이며 하위 탭은 화면 내부 도구상자로 처리한다.
- 라우팅: 해시(`#route`). 초기 진입만 `location.hash` 를 읽는다(`admin.html:307`). 메뉴 클릭(`nav.onclick` `:298`)과 빠른 등록(`:299`)은 `history.replaceState` 로 주소만 **덮어쓴다**. `hashchange`·`popstate`·`pushState` 는 파일에 하나도 없다 [확인: grep]. 결과가 둘이다 — ① 메뉴를 옮겨 다녀도 히스토리 항목이 늘지 않아 **뒤로가기가 이전 메뉴가 아니라 admin 이전 페이지로 나간다**, ② 이미 열린 화면에서 주소의 해시만 바뀌면(외부 링크·수동 편집) 화면이 따라가지 않는다. 그래서 개선은 **히스토리 항목 생성(M-3a)과 해시·popstate 감지(M-3b)를 따로** 해야 한다. `hashchange` 리스너만 달면 ②만 고쳐지고 ①은 그대로다(§4.3).
- 설정 그룹은 일반 업무 메뉴 아래 같은 사이드바에 있으나 "설정" 그룹으로 분리돼 있다.

### 3.1 공통 상태 처리 (`admin.html` `loadLiveRoute`·`renderNav`) — 정정 2

원본은 "스켈레톤·재시도 없음, 403=세션 만료"로 적었다. 코드와 캡처로 다시 보니 아래와 같이 **이미 구현된 복구 동선이 있다.** 이를 개선 대상에서 빼고 "보완" 수준으로 낮춘다.

| 점검 항목 | 현황 | 판정 |
|---|---|---|
| 로딩 | `loadLiveRoute` 진입 즉시 `liveLoading=true`. 상태 박스가 "DB 조회 중 — 현재 조건의 원장을 불러오고 있습니다"를 표시(`admin.html:183`·`:190`). 표 자리 스켈레톤은 없다 | [확인] 코드. 체감은 [가설]. **이미 구현 — 보완만** |

| 빈 상태 | 0건이면 "오비서 DB 실데이터 · 0건 표시 · 샘플 데이터 없음"(`:190`). 원천 미적재와 "0건" 구분은 서버 `source.name` 문구(예: `…:조회조건_전표없음`)에만 있고 화면 문구로는 드러나지 않는다 | [확인] 코드 / 화면은 [가설] |
