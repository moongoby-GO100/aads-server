## CEO 확정 결정 반영 요구

1. D3는 prd·contract·architecture 또는 15,000자 초과만 적용하고 목표 연결은 입력·화면 기준·AC-3에서 제거한다. tasks는 D2로 확정한다. 분할 반려(50,000자 초과)를 먼저 판정한다. 목표 연결 제외 199/100/89는 문서의 과거 표본 주장일 뿐 이번 실측값이 아니다.
2. D1은 승인에서 제외하되 등록과 필수 검토 기록을 유지한다. `approved_brief`는 approved_revision_id만 읽으므로 승인 제외 D1을 어떤 화면·참조에서 어떻게 취급할지 명시한다. 승인 포인터를 자동으로 올리는 우회로는 만들지 않는다.
3. D3 첫 검토자는 다른 회사 상위모델, 두 번째는 작성 회사의 작성 모델과 **다른 상위모델**로 확정한다. FR-9·AC-4는 첫 cross 역할에만 적용한다. 단순히 모델 ID가 다르다고 상위모델임이 보장되지 않으므로 승인된 상위모델 집합/메타데이터가 필요하다.
4. unknown은 등급에 관계없이 두 회사 각 1개가 필요하다. §4 의사코드는 unknown D1/D2를 첫 후보 1개로 통과시킬 수 있고 unknown D3의 same-company는 정의되지 않았다. 별도 분기와 시험을 알고리즘 본문에 넣어야 한다.
5. 코드 검수는 교차 불가 시 차단하지 않고 기존 순서와 `cross=false` 증거를 유지한다. 신규 설정 누락 시 기존 AI_REVIEW로 돌아가는 동작도 명시한다.

## 위험·누락과 보완 조건

### 기존 정본 흐름과 대기 10건 정지 위험 — P1

현행 review는 LLM을 실행하지 않고 상태를 전환한다. 게이트만 먼저 켜면 등록 자체는 성공해도 검토 기록이 없는 문서는 `cross_review_required`로 막힌다. 기존 초안은 새 필드 NULL이고 PRD는 비소급을 약속하지만 설계 게이트에는 grandfather 조건이 없다. approve에도 D3 두 건 조건을 추가하면 이미 review인 문서도 승인되지 않을 수 있다. `review_revision_in_tx`는 마지막 이벤트가 review이면 generation보다 먼저 멱등 성공하므로 게이트를 그 앞/뒤 어디에 놓느냐에 따라 재호출의 차단·우회 결과도 다르다.

적용 시작 시점/정책 버전을 개정 단위로 고정하고 기존 NULL 개정 및 기존 review 대기는 종전 전환·승인을 보존해야 한다. 새 개정만 새 정책을 적용하며 등록 API는 모델 장애와 무관하게 초안을 저장한다. 기록 → 등급 계산 → 검토 실행 성공 확인 → 제한된 새 개정에 강제 순서로 적용하고 실패 시 강제 플래그를 끈다. 기존 대기 10건의 키·revision·마지막 상태를 전후 대조하는 읽기 전용 검증이 필요하다. **10건은 지시서 제공 정보이며 실시간 DB 확인값이 아니다.** `canonical_review_digest.py`의 PER_PROJECT_LIMIT=10은 알림 표시 상한이지 실제 대기 건수 제한이 아니다.

### 실행 경로와 R-AUTH — 현재 경로 적합, 신규 경로 미입증 / P1

현행 `code_reviewer._call_review_model:635` → `directive_draft_service._call_configured_model:527` → Codex `_stream_codex_relay` / Claude `_stream_cli_relay`로 이어진다. CLI 외 후보는 입구에서 거절한다. 외부 REST 직접 호출을 추가하지 않아 지시서의 CLI 중계 원칙에 맞는다. API/LiteLLM 모델용 분기는 `app/core/anthropic_client.py`의 `call_llm_with_fallback`을 사용한다. 검토 경로가 현재 OAuth 두 계정 상태까지 실제로 정상인지는 호출하지 않아 확인하지 못했다.

설계의 신규 cross-review는 실행 또는 예약 중 하나를 확정하지 않았고 공용 실행 함수를 지정하지 않았다. 현행 CLI 경로를 재사용하고 외부 모델 확대 시 중앙 클라이언트/LiteLLM을 거쳐야 한다. 인증 원문이나 새 직접 API 키 참조를 도입하면 안 된다. 일반 폴백이 선택 모델을 다른 회사로 바꿀 수 있으므로 **실제 실행 모델**을 기록·재판별하고 unknown 결과를 교차 성공으로 처리하지 않는다. 사용자·테넌트 문서를 다루는 신규 API는 현행 코드의 tenant_id=None/user_id=None 호출을 그대로 복사하지 말고 권한·사용량 문맥을 전달해야 한다.

LLM 호출 중 head FOR UPDATE 트랜잭션을 유지하지 말고 스냅샷을 읽어 비동기 실행한 뒤 저장 시 tenant/project/head/revision/content_hash/정책 버전을 재확인한다. 신규 endpoint의 PM·시스템 권한과 재시도 멱등 키도 정의해야 한다. 실패 모델 exclude는 의사코드의 함수 인자에 없어 현재 형태로 재시도 계약을 구현할 수 없다. 가용성 판별 실패만으로 정상 후보를 제거하지 않도록 현행 DB 순서 보존 원칙도 유지한다.

### 검토 증거의 무결성 — P1

제안 reviews 테이블 FK는 (head_id, revision_id)만 연결해 tenant_id/project_key 일치를 강제하지 않는다. 개정의 `(id,tenant_id,project_key)` 복합 FK도 필요하다. 단순 pass 두 행 개수로 승인하지 말고 현재 revision의 필수 역할·회사·서로 다른 모델·상위모델·동일 정책 실행 묶음이 충족됐는지 확인해야 한다. 재시도로 같은 검토자의 pass가 두 건 생긴 경우, 다른 시도의 reject와 pass가 섞인 경우를 정의한다. blocked 후보가 없을 때 NOT NULL reviewer_model/provider에 무엇을 남길지, override 권한·사유, unknown의 두 회사 역할도 스키마 계약에 포함한다.

러너의 최종 actual_model은 본문을 작성한 모든 모델을 증명하지 못한다. fallback 중간 작성 이력과 source_task_id 소유권을 확인해야 한다. PRD FR-2의 채팅 실제 모델 추적을 설계는 M1 범위 밖으로 돌려 AC-1 unknown≤5%를 보장하지 못한다.

### 롤백 — 조건부 가능 / P1

강제 플래그 OFF로 종전 흐름 복귀라는 방향은 타당하다. 다만 플래그 저장소·기본값·즉시 적용/캐시·모든 approve/review 경로에서의 효과를 확정해야 한다. 기존 AI_REVIEW와 작성 체인을 유지하고 additive 컬럼·검토 기록은 남기는 롤백이 우선이다. 새 설정 행을 지우고 구 CHECK로 되돌릴 때는 먼저 신규 선택 코드를 끄고 신규 키 데이터가 없는지 확인해야 한다. 설계의 DROP TABLE/DROP COLUMN은 검토 감사 증거를 잃으므로 기본 롤백으로 삼지 말고 별도 보존·승인 대상으로 둔다. 이번 작업은 롤백 SQL을 실행하지 않았다.

### 비용·지연 — 수치 미측정 / P2

목표 연결 제외는 과도한 D3 승격을 줄이지만 unknown은 D1/D2도 두 번 실행하므로 D3 수만으로 비용을 계산하면 과소평가한다. 역할별 입력·출력 토큰, 실제 모델, 재시도/실패, 대기·실행 시간, 구독 한도 및 한도 소진을 함께 기록한다. CLI 비용이 0 또는 누락으로 보고돼도 무료 검토로 해석하면 안 된다. job total_cost는 문서 검토 전용 job과 일대일로 연결되지 않으면 작성 비용과 섞인다. 같은 내용을 두 회사에 보내는 정보 노출 범위·보존 정책도 확인한다.

일일 상한 숫자, 동시 실행 상한, 최대 시도, 실행 deadline, 장애 시 큐 보관·재개 정책을 강제 도입 전에 정해야 한다. 초안 등록은 상한에 막히지 않게 하고 검토 실행만 대기시킨다. 가격·월 비용을 이번 보고서에서 추정하지 않았고 외부 모델 호출도 하지 않았다.
