## 3. 발견한 결함과 수정 (코드+테스트 동시 수정, 테스트 삭제 없음)

### 3.1 change-intake 재전송이 409로 깨진다 (실제 결함)

- 증상: 같은 본문(같은 `idempotency_key`)을 `POST /change-intake`로 두 번 보내면 두 번째가 200(idempotent)이 아니라 `409 idempotency_key_conflict`.
- 원인: `intake_change`는 클라이언트가 `expected_generation`을 안 보내면 현재 head 세대를 채워 넣는다. 첫 호출이 세대를 올리므로, 재전송 때 채워지는 값이 달라지고 `request_changes`가 만드는 요청 해시가 바뀐다. `base_revision_id`(서버가 채움)도 같은 이유로 새 revision이 생기면 달라진다. PRD M18·AC-M18("같은 change_request_id/idempotency_key로 두 번 전송 → 이벤트 증가 0, '이미 접수됨'")을 직접 위반한다. 채팅 재전송·재접속에서 실제로 맞는 경로다.
- 수정(`app/services/mockup_review_service.py`): `request_changes`에 키워드 인자 `rhash`를 추가. `intake_change`는 클라이언트가 보낸 필드(`idempotency_key`, `expected_generation`, `change_request_id`, `source_message_id`, `comment`, `screen_id`)만으로 해시를 만들어 넘긴다. 재전송 응답의 `target.revision_id`는 저장된 응답의 `base_revision_id`를 우선 쓴다. 직접 `/changes` 경로의 해시 계산은 그대로다.
- 테스트: `tests/unit/test_mockup_execution_gate.py`의 `fake_changes` 시그니처를 맞추고, 회귀 `test_intake_idempotency_hash_ignores_server_filled_generation`을 추가했다(세대 3·4에서 같은 해시).

### 3.2 inbox 단언 오류 (테스트 결함)

- `test_replay_does_not_notify_twice_and_inboxes_are_private`가 프로젝트 권한이 전혀 없는 `nogrant` 사용자의 inbox를 `200 + 빈 목록`으로 기대했다. 이 API는 다른 모든 mockup 엔드포인트처럼 read 권한을 요구하므로 `403 project_access_denied`가 맞다(`_authorize`, `app/api/canonical_documents.py:53`). 테스트가 DB에서 실행된 적이 없어 드러나지 않았다.
- 수정: 권한 있는 타인(`foreign`, `reader`, `approver`)은 빈 목록, `nogrant`는 403을 단언하도록 `tests/integration/test_mockup_chat_flow.py`를 고쳤다. 비공개 보장은 약해지지 않고 오히려 두 경우를 구분해 검사한다.

## 5. 미구현·갭의 최소 범위 (이번 작업에서는 만들지 않음)

우선순위는 브리프가 지정한 M15→M18 순으로 본 결과다.

1. **M15 전·후 비교**: 서버에 `GET /{review_id}/revisions/{a}/compare/{b}` 하나. 두 manifest의 자산을 `asset_id`별로 추가/삭제/hash 변경으로 나열하고 `change_report`의 요청별 결과에 연결하면 된다. 화면 단위 시각 diff는 범위 밖.
2. **M16·M18**: 추가 구현 불필요. §3.1로 M18의 마지막 구멍을 막았다.
3. **M17**: 최소는 두 가지다. (a) 서버: `/approve`·`/revoke`는 쿠키 토큰을 거절하고 `Authorization: Bearer`만 받는다(또는 Origin 검사). 이 변경은 `app/auth.py` 경로가 아니라 mockup 라우터 의존성에 한정한다. (b) 대시보드: 승인 버튼은 iframe 밖 채팅 카드/패널에만 두고, 위 거절 동작을 확인하는 테스트 1건을 추가한다. 대시보드 UI가 없으면 (b)는 M13과 같은 작업이다.
4. **M13·M14 UI**: 채팅 카드, 아티팩트 패널(모바일 전체화면), 모호할 때 버전 선택 질문 1회. 서버 계약(대상 결정, 후보 목록, 알림 링크)은 이미 준비돼 있어 대시보드 작업만 남는다. 별도 저장소 작업이므로 서버 작업과 분리해 지시해야 한다.
5. **M05**: 화면의 `requirement_ids`가 연결된 prd 문서 revision 본문에 존재하는지 대조하는 검사. 문서 본문 파싱 규칙이 필요해 최소 범위는 "비어 있지 않음 + 형식 검사"까지만 권한다.
6. **M11**: 구현 화면과 승인 목업을 같은 조건으로 비교한 QA 증거와 사람 판정 기록 저장소가 없다. 독립 작업(스키마 포함)으로 분리해야 하며 이번 범위에서 최소안을 정하기엔 요구가 모호하다.
7. **운영 강제(M09/M10)**: `MOCKUP_GATE_MODE=enforce` 전환은 CEO 승인 사항이며 docker-compose 환경변수 수정이라 점검 창구에서 한다. 전환 전에 UI 작업이 번들을 선언하는 흐름이 실제로 쓰이는지 확인이 먼저다.

## 6. 남은 일과 한계

- **6.3(실제 목업 1건 생성·수정요청·승인 저장)은 하지 않았다.** 승인은 승인권자 몫이고, 이 작업은 운영 테이블에 쓰지 않는다. 테스트 결과는 일회용 DB의 증거이지 운영 사용 증거가 아니다.
