> 어느 DB 가 "정본"인지, AADS 경로가 의도된 운영 경로인지는 이 보고서가 판단하지 않는다. 사실만 기록한다.

### 2.3 `journal_entry`·`journal_line` 의 위치와 `acct_purchase` 의 실제 접속 DB

AAG 브리프의 TABLE_NO_MODEL(P1)은 **이 저장소에 `CREATE TABLE` 정의가 없다**는 정적 분석 결과다. 테이블이 운영에 없다는 뜻이 아니다. 앞 판본(c0ee9a42)은 "obys DB 두 곳에 테이블이 없다 → 엔드포인트 오류 가능성"이라고 연결했는데, 그 DB 들은 `acct_purchase` 가 읽는 DB 가 아니므로 근거가 되지 않았다. 코드가 실제로 고르는 접속을 따라가 다시 확인했다.

| 단계 | 근거 | 결과 |
|---|---|---|
| 엔드포인트가 쓰는 함수 | `acct_purchase.py` 204–206 `_fetch_acct_journals` → `query_acct_database`, 427행 `FROM journal_entry` | `OBYS_DATABASE_URL`(조사한 obys 사본)을 쓰지 않는다 |
| 접속 경로 선택 | `ceo_chat_tools_db.py` 1159–1202 `_resolve_acct_connection`: `ACCT_APP_DATABASE_URL` → `ACCT_DATABASE_URL` → `ACCT_DB_APP_USER/PASSWORD`+SSH 터널 | 이번 실행에서 `aads-server` 컨테이너: 앞 두 DSN **미설정**, `ACCT_DB_APP_USER`·`ACCT_DB_APP_PASSWORD` **설정** → **SSH 터널 모드**(값은 읽지 않고 존재 여부만) |
| 터널 대상 | 컨테이너 `ACCT_SSH_HOST` 가 114 호스트와 같은지만 비교(값 미출력), `ACCT_SSH_PORT=7916`, `ACCT_DB_NAME=obys` | 서버 114, DB 이름 `obys` |

| 114 `acct-pg` 의 DB 3종 (11:30:56) | `to_regclass` 만 | **`acct` DB 에는 두 테이블 모두 있음**, `obys`·`obys_auth` 에는 없음 |

해석과 한계.

- **확인된 것**: `aads-server` 가 `acct_purchase` 전표 조회에 쓰는 접속은 DB `obys` 로 붙고, 거기에는 `journal_entry`·`journal_line` 이 없다. 두 테이블은 같은 114 `acct-pg` 의 DB `acct` 에 있다.
- **그래서**: 코드상 `acct_purchase` 의 전표 조회 엔드포인트는 AADS 경로에서 실패(코드는 502 "ACCT 전표 조회 실패")할 가능성이 높다. **엔드포인트 응답 자체는 인증 계정이 없어 호출하지 못했다 — 미검증.**
- **원인은 미확정**: `ACCT_DB_NAME=obys` 설정이 의도인지(전표 조회용 DB 이름이 `acct` 여야 하는지)는 이 보고서가 판단하지 않는다. 전표가 `acct` DB 에 있다는 사실과 `ACCT_DB_NAME=obys` 가 맞지 않는다는 사실만 기록한다.
- 114 standalone 의 `acct-purchase`(11 경로 탑재)가 어느 DB 로 붙는지는 **미조사**.
- 등급: P1(기능 장애 가능성, 데이터 노출 아님). 완료 기준은 §5.6.5 의 항목 6.

### 4.1 현황 (체인)

1. 작성: 관리자만 `save_contract`(6196). 서명 완료 행은 409(6204 부근). 내용이 바뀌면 `requested`→`draft` 로 되돌리고 토큰 폐기(`_revoke_contract_signature_request` 6190). 클라이언트가 보낸 `signed_pdf_seal` 은 버린다.

### 4.4 서명 불변성 설계

앞 판본들의 두 주장을 **철회**하고 설계를 다시 쓴다.

1. (ee6561f3) 공통 업서트에 `status <> 'signed'` 가드를 일괄 추가 — 철회.
2. (c0ee9a42) "DB 트리거를 앱 배포보다 먼저 넣어도 구 코드의 서명·교부가 깨지지 않는다" — **철회**. 번들 롤백이 깨진다(아래 철회 사유 2).

#### 철회 사유 1 — 일괄 가드는 서명 후 정당한 쓰기까지 막는다

공통 업서트 `_db_upsert_ledger` 의 계약 분기(1079–1134)를 서명 경로와 교부 경로가 **같이** 쓴다.

- `_persist_contract_delivery`(7235–7238)는 `_write_hr_record("contracts", contract, user)`(1528) → 같은 업서트를 먼저 호출하고 그 뒤에 `_db_update_contract_delivery_columns`(6879)를 부른다. 서명 직후 PDF 메타(`_store_signed_contract_pdf` 7321)와 첫 다운로드의 `delivered_at`(`signed_contract_pdf_for_download` 7405)이 모두 이 경로다.
- 업서트에 `AND status <> 'signed'` 를 넣으면 signed 행에서 `DO UPDATE` 가 적용되지 않아 `INSERT 0 0` 이 되고, `_write_hr_record` 는 이를 404 로 바꾼다(1533–1535). **서명 후 PDF·교부 메타 저장이 막힌다.**
- 서명 자체(`_sign_contract_locked` 6427, 번들 6775)는 기존 행이 `requested` 라 가드와 충돌하지 않는다. 막히는 것은 서명 이후의 정당한 쓰기들이다.

#### 철회 사유 2 — 서명 후 되쓰기(번들 롤백)는 트리거와 충돌한다

현행 번들 서명(`_sign_contract_bundle_locked` 6709–6790)은 **트랜잭션이 아니라 보상 쓰기**로 "전부 아니면 전무"를 지킨다.

- 계약마다 `_apply_contract_signature` → `_write_hr_record`(6775)를 따로 호출한다. 각 호출은 자기 DB 연결에서 단문 업서트로 즉시 커밋된다(`_db_upsert_ledger` 925 가 호출마다 `asyncpg.connect`).
- 중간에 실패하면 `_restore_contracts`(6704–6708)가 `attempted` 의 원본(deepcopy, `status='requested'`, 서명 필드 없음)을 **같은 업서트**로 되쓴다(6778). 이때 앞서 커밋된 행은 이미 `signed` 이므로 이 쓰기는 **`signed → requested`** 전이다.
- 앞 판본이 제안한 트리거는 `OLD.status='signed'` 에서 `NEW.status` 변경을 거부한다. 그러면 이 롤백 쓰기가 DB 에서 막히고, 곧바로 이어지는 실패 처리가 문제를 숨긴다. `_run_db`(599–620)는 예외를 삼켜 `None` 을 돌려주고 → `_write_hr_record` 는 404 를 올리고(1533–1535) → `_restore_contracts` 는 `except Exception` 으로 `logger.exception` 만 남기고 계속한다 → 호출부(6779–6782)는 그래도 **"한 건도 서명되지 않았습니다"** 라는 409 를 응답한다. 결과: 일부 계약만 `signed` 로 남고, 사용자에게는 반대로 안내된다.
- 앞 판본의 T10(구 코드의 **전 필드 동일** 통짜 업서트가 트리거를 통과)은 이 경로를 검증하지 못한다. 롤백은 전 필드 동일이 아니라 상태를 되돌리는 쓰기다. 현행 회귀 테스트 `test_write_failure_midway_rolls_back_already_signed_contracts`(`test_obys_contract_bundle_sign.py` 289행, 이번 실행 통과)가 바로 이 동작을 지키고 있다 — 트리거는 이 테스트가 보호하는 동작과 충돌한다.
- 구 코드는 지금도 여럿 돈다: 114 의 후보 r38~r44 7개와 AADS `aads-server`(`ad0d89d9`) — 모두 이 `_restore_contracts` 를 가진 코드다(§0 `docker ps`). 따라서 "트리거 선적용 시 구 코드 호환"은 성립하지 않는다.

롤백 실패의 거짓 안내 자체(`_restore_contracts` 가 실패를 삼키고 호출부가 "한 건도 서명되지 않았다"고 답함)는 **트리거와 무관하게 현재도 존재하는 결함**이다(DB 순단 때도 같다). F-13 으로 따로 둔다.

따라서 "서명 완료 행은 어떤 쓰기도 막는다"가 아니라 **무엇을 못 바꾸게 하고 무엇을 허용하는지를 필드 단위로 나누고**, 서명 후 되쓰기가 필요 없도록 **번들을 한 트랜잭션으로 옮긴 뒤에** 트리거를 넣어야 한다.

#### 필드 분류 — 서명 이후 쓰기 경로가 필드를 달리 건드린다

`yeoljeong_contracts` 는 컬럼(`status`, `signed_at`, `signer_*`, `sign_token_hash`, 교부 컬럼 `CONTRACT_DELIVERY_COLUMNS`)과 `contract_payload`(JSONB, 레코드 전체 — `_db_payload_record` 906 은 계약을 걸러내지 않고 그대로 돌려준다)에 값이 나뉘어 있다. 아래 분류는 payload 키 기준이다.

**(a) 서명 원본 불변 필드** — `signed` 가 된 뒤에는 어떤 경로로도 바뀌면 안 된다.

| 필드 | 만드는 곳 |
|---|---|
| `signature_data_uri`, `signature_sha256` | `_apply_contract_signature` 6358–6400 |
| `signature_consent`, `signature_audit`(서명 시각·서명자·IP·UA, 번들이면 `bundle_id`) | 같은 함수 |
| `status='signed'`, `signed_at`, `signer_name`, `signer_email`, `sign_token_hash` | 같은 함수 |
| `signed_pdf_seal`(서버 동결 도장 입력) | 같은 함수. 스냅샷 해시에서는 제외돼 있다(357–374) → 별도 보호 필요 |
| `signed_snapshot`, `signed_snapshot_sha256`(계약 본문 스냅샷) | `_signed_contract_snapshot` 6040 |
| 계약 본문 전체 | = `signed_snapshot` 의 키들. **불변식: `payload − CONTRACT_SNAPSHOT_EXCLUDED_FIELDS` 의 정렬 JSON sha256 == `signed_snapshot_sha256`** |

**(b) 서명 후에도 갱신을 허용하는 교부 메타데이터** — 트리거가 허용하는 키는 **신규 상수 `CONTRACT_POST_SIGN_MUTABLE_FIELDS`** 로 정의하며, 해시 제외 목록 `CONTRACT_SNAPSHOT_EXCLUDED_FIELDS`(357–374)와 **같지 않다.**

**허용 목록과 해시 제외 목록의 분리 (리뷰 b83a2843 P1-1 반영)**

`CONTRACT_SNAPSHOT_EXCLUDED_FIELDS` 의 의미는 "스냅샷 해시를 계산할 때 빼는 키"이지 "서명 뒤에 바꿔도 되는 키"가 아니다. 조사 SHA `0f6d184e` 의 상수(357–374)를 grep 으로 읽은 실제 값은 14개이고, 두 부류가 섞여 있다.

| 부류 | 키(실측) | 해시 | 서명 후 트리거 |
|---|---|---|---|
| **해시 제외 + 불변** (6) | `sign_token`, `sign_token_hash`, `signed_snapshot`, `signed_snapshot_sha256`, `signature_data_uri`, `signed_pdf_seal` | 제외 | **변경·추가·삭제 모두 거부** |
| **해시 제외 + 갱신 허용** (8, 신규 `signed_pdf_history` 포함 시 9) | `updated_at`, `signed_pdf_path`, `signed_pdf_sha256`, `signed_pdf_bytes`, `signed_pdf_generated_at`, `signed_pdf_error`, `delivered_at`, `delivery_channel` (+ `signed_pdf_history`) | 제외 | 허용. `delivered_at` 은 set-once, `signed_pdf_history` 는 append-only(아래) |
| 해시 포함 | 위 14개를 뺀 나머지 전부 — 계약 본문 키, `status`, `signed_at`, `signer_*`, `signature_sha256`, `signature_consent`, `signature_audit` 등 | 포함 | 변경 거부 |

- **정의**: `CONTRACT_POST_SIGN_MUTABLE_FIELDS` = "해시 제외 + 갱신 허용" 행의 9개 키(위 8개 + `signed_pdf_history`). 불변 6개는 이 상수에 **넣지 않는다.**
- **관계**: `CONTRACT_POST_SIGN_MUTABLE_FIELDS ⊂ CONTRACT_SNAPSHOT_EXCLUDED_FIELDS`(진부분집합). 허용 키는 해시에서 빠져야 PDF 재생성 뒤에도 해시가 흔들리지 않으므로 ⊆ 가 필요조건이다. 반대 방향(제외 ⊆ 허용)은 **성립하지 않으며**, 차집합 `EXCLUDED − MUTABLE` 이 정확히 위 불변 6개여야 한다.
- **왜 같게 쓰면 안 되나**: 트리거의 payload 비교는 `NEW.contract_payload − 허용키 == OLD.contract_payload − 허용키` 이다. 허용 키에 `EXCLUDED` 를 그대로 쓰면 `signature_data_uri`·`signed_snapshot`·`signed_snapshot_sha256`·`signed_pdf_seal` 이 양변에서 함께 지워져 **이 필드 변조가 비교에서 빠지고 T4(서명 원본 보호)가 성립하지 않는다.** 이 키들은 스냅샷 해시로도 보호되지 않는다(해시에서 빠져 있다) — `signed_snapshot` 과 `signed_snapshot_sha256` 을 서로 맞게 함께 고쳐 쓰면 F-3 의 재계산 검증도 통과하고, `signed_pdf_seal` 에는 다른 다이제스트가 아예 없다. 즉 이 4개는 **트리거의 불변 비교가 유일한 방어선**이다.
- **마이그레이션 생성**: 트리거 함수의 허용 키 `text[]` 는 `CONTRACT_POST_SIGN_MUTABLE_FIELDS` 에서 생성한다(`EXCLUDED` 에서 생성 금지). `jsonb − text[]` 는 최상위 키만 제거하므로 해시의 `_signed_contract_snapshot`(6040–6043, 최상위 키 필터)과 같은 층위다.

| 필드 | 쓰는 곳 | 규칙 |
|---|---|---|
| `signed_pdf_path`, `signed_pdf_sha256`, `signed_pdf_bytes`, `signed_pdf_generated_at`, `signed_pdf_error` | `_store_signed_contract_pdf` 7321–7358 | 갱신 허용(MUTABLE). 이전 값은 새 키 **`signed_pdf_history`**(append-only)에 보존(F-4). **새 키는 제외 목록과 MUTABLE 둘 다에 넣어야 한다 — 아래 "제외 필드 갱신 절차"** |
| `signed_pdf_history` (신규) | 같은 함수 | 항목 = `{sha256, bytes, generated_at}` 만. 기존 항목 수정·삭제·재배열·배열 초기화 금지 — **트리거가 접두부 보존으로 강제**(아래 "이력 append-only 강제") |
| `delivered_at`, `delivery_channel` | `signed_contract_pdf_for_download` 7405–7440 | **최초 1회만 기록**(코드는 `if not contract.get("delivered_at")` 로 지킨다). 이후 값 변경 불가 |
| 열람 시각 | 알림 로그 `yeoljeong_contract_notifications` | 계약 행이 아니라 로그 테이블에 append-only |
| `updated_at` | 업서트 | 허용(MUTABLE). 해시 제외 목록에는 이미 있음 |
| 교부 컬럼 `signed_pdf_path`·`signed_pdf_sha256`·`signed_pdf_bytes`·`delivered_at`·`delivery_channel` | `_db_update_contract_delivery_columns` 6879–6909 | 이미 **별도 UPDATE**(`WHERE id AND tenant_id AND deleted_at IS NULL`)다. 단 `delivered_at` 을 레코드 값으로 무조건 덮어쓰므로 DB 쪽 set-once 보호가 없다 |

**제외 필드 갱신 절차 (`signed_pdf_history` 때문에 필요 — 빠뜨리면 정상 PDF 재생성이 다운로드를 막는다)**

불변식은 payload 에서 `CONTRACT_SNAPSHOT_EXCLUDED_FIELDS` 키를 뺀 나머지를 해시해 `signed_snapshot_sha256` 과 비교한다. 이 목록에 없는 새 키가 payload 에 생기면 재계산 값이 달라져 **불일치로 오판**한다. F-3 의 "다운로드·재생성 시 해시 불일치면 오류" 를 구현하면, 정상적으로 PDF 를 한 번 재생성한 계약이 이후 다운로드에서 막힌다.

1. `signed_pdf_history` 를 쓰는 코드와 같은 변경에서 `CONTRACT_SNAPSHOT_EXCLUDED_FIELDS`(357–374)와 `CONTRACT_POST_SIGN_MUTABLE_FIELDS` **두 곳 모두**에 이 키를 추가한다. 한 변경으로 묶지 않으면 안 된다. 제외 목록에만 넣으면 트리거가 이력 갱신을 거부하고, MUTABLE 에만 넣으면 해시가 흔들린다.
2. 기존 서명 행의 스냅샷 해시는 영향받지 않는다 — 이 키는 어떤 기존 payload 에도 없고, 제외 목록 확장은 해당 키가 payload 에 있을 때만 결과를 바꾼다. 적용 전에 `contract_payload ? 'signed_pdf_history'` 인 행이 0건인지 읽기 전용으로 확인한다.
3. DB 트리거의 허용 키 목록은 `CONTRACT_POST_SIGN_MUTABLE_FIELDS` 와 **같은 출처**여야 한다(해시 제외 목록이 아니다 — 위 "허용 목록과 해시 제외 목록의 분리"). 손으로 두 벌 유지하지 않는다 — 마이그레이션 파일을 MUTABLE 상수에서 생성하거나, 트리거 키 목록 == MUTABLE 이고 MUTABLE ⊂ 제외 목록(진부분집합)이며 `EXCLUDED − MUTABLE` 이 불변 6개와 일치하는지 비교하는 테스트(T-K)를 둔다.
4. 구 코드와의 공존: 구 코드는 해시를 검증하지 않고(F-3) 레코드 전체를 읽어 그대로 되쓰므로 `signed_pdf_history` 를 지우지 않는다(`_db_payload_record` 가 키를 거르지 않음). 구 코드가 PDF 를 재생성하면 이력 항목이 하나 빠질 뿐 해시는 흔들리지 않고, 접두부 검사도 통과한다(기존 항목은 그대로이고 새 항목만 없는 쓰기). 단 구 코드가 **오래된 읽기본으로 되쓰면** 최신 항목이 줄어 접두부 검사에 걸린다 — 이는 의도된 거부이며 구 코드 드레인(롤아웃 단계 2) 뒤에는 발생하지 않는다.
5. 앞으로 서명 후 payload 에 키를 추가하는 모든 변경은 같은 절차를 따른다. T-K 가 "`_store_signed_contract_pdf`·`_persist_contract_delivery`·다운로드 경로가 서명 후 새로 쓰는 키 ⊆ `CONTRACT_POST_SIGN_MUTABLE_FIELDS` ⊂ 제외 목록"을 실행해 확인하게 한다.

**이력 append-only 강제 — 트리거의 접두부 보존 검사 (리뷰 b83a2843 P1-2 반영)**

`signed_pdf_history` 를 허용 키에 넣기만 하면 트리거는 "이 키는 바뀌어도 된다"까지만 말한다. 과거 항목을 고치거나 지우거나 배열을 비워도 통과하므로 "append-only" 가 DB 에서 성립하지 않는다. 두 방안 중 **A(같은 트리거에서 접두부 보존 검사)를 고른다.**

| 방안 | 내용 | 판단 |
|---|---|---|
| **A. 접두부 보존 검사(채택)** | 이력을 payload 의 배열로 두고, 트리거가 `OLD` 배열이 `NEW` 배열의 접두부(앞쪽 n개)와 같은지 검사 | 채택 |
| B. 별도 append-only 테이블 | `yeoljeong_contract_pdf_history` 신설, UPDATE/DELETE 거부 트리거 | 미채택 |

채택 이유: ① PDF 메타 교체(`signed_pdf_*`)와 이력 추가가 **같은 행의 한 UPDATE** 로 원자적으로 끝난다. B 는 다른 테이블이라 같은 트랜잭션을 별도로 보장해야 한다. ② 앞서 합의한 "제외 필드 갱신 절차"·T-H·구 코드 공존(레코드 전체 되쓰기가 이력을 보존)을 바꾸지 않는다. B 는 이 셋을 모두 다시 써야 하고 두 DB 에 테이블을 하나 더 배포한다. ③ 항목이 `{sha256, bytes, generated_at}` 약 100바이트이고 재생성은 드문 사건이라 payload 비대화가 문제되지 않는다. 대가: 비교가 jsonb 배열 원소 단위라 트리거가 복잡해진다. 이력이 길어지거나 보존 기간·열람 권한이 별도로 필요해지면 B 로 옮기는 것을 다시 검토한다.

트리거(`OLD.status='signed'` 일 때) 검사 의사코드(제안, 미적용):

1. `o := COALESCE(OLD.contract_payload->'signed_pdf_history','[]')`, `n := NEW.contract_payload->'signed_pdf_history'`.
2. `n` 이 JSON 배열이 아니면 거부(`n` 이 없는 경우 포함) — **키 삭제·`null`·객체로 바꾸기**를 막는다. 단 `OLD` 에도 이 키가 없었다면 이력을 건드리지 않는 쓰기이므로 통과한다.
3. `jsonb_array_length(n) >= jsonb_array_length(o)` 아니면 거부 — **삭제·`[]` 초기화**를 막는다.
4. `o` 의 모든 원소 `e`(위치 `i`)에 대해 `n -> i = e`. 하나라도 다르면 거부 — **과거 항목 수정·재배열**을 막는다. (`NOT EXISTS (SELECT 1 FROM jsonb_array_elements(o) WITH ORDINALITY t(e,i) WHERE n -> (i::int-1) IS DISTINCT FROM e)`)
5. 추가분은 한 UPDATE 에 **최대 1개**, 키는 정확히 `sha256`(64자리 hex)·`bytes`·`generated_at` 이어야 한다 — 임의 필드 삽입과 대량 추가를 막는다.

앱 쪽: 이력 추가는 파이썬에서 읽고 이어 붙여 되쓰는 방식이 아니라 한 UPDATE 안의 `COALESCE(contract_payload->'signed_pdf_history','[]') || $새항목` 으로 한다. 동시 재생성 두 건이 서로의 항목을 덮어쓰지 않게 하기 위해서다. 감시 모드(롤아웃 단계 3)에서는 위반 쓰기를 거부하지 않고 `contract.immutability_violation` 로 기록하며, 강제 모드에서만 `RAISE EXCEPTION` 한다.

**(c) draft→sent(requested)→signed 조건부 상태 전이** — 전이는 "읽고 판단 후 통째로 덮어쓰기"가 아니라 **조건부 UPDATE** 로 한다.

| 전이 | 현재 경로 | 설계 |
|---|---|---|
| (신규) → draft | `save_contract` 6227 | `INSERT`. 기존 행이면 `WHERE status IN ('draft','requested')` 조건부 UPDATE, 0행이면 409 |
| draft → requested | `request_contract_signature` 6243 | `UPDATE … SET status='requested', sign_token_hash, requested_at WHERE id AND tenant_id AND status IN ('draft','requested') RETURNING id` |
| requested → draft | `save_contract`(내용 변경), 계좌 자동입력 7096 | `WHERE status='requested'` 일 때만 |
| requested → signed (단건) | `_sign_contract_locked` 6427 | `UPDATE … SET status='signed', signed_at, payload(a 필드) WHERE id AND tenant_id AND status='requested' AND sign_token_hash=$토큰해시 AND deleted_at IS NULL RETURNING id`. 0행이면 409(이미 서명됨/무효 토큰). 이 한 문장이 프로세스 로컬 `threading.Lock` 을 대체한다 |
| requested → signed (**번들**) | `_sign_contract_bundle_locked` 6709–6790, 롤백 6704 | **한 DB 트랜잭션** 안에서 위 UPDATE 를 계약 수만큼 실행하고, 하나라도 0행이면 예외 → 트랜잭션 롤백. 커밋되기 전에는 어떤 행도 `signed` 가 아니므로 **서명 후 되쓰기가 존재하지 않는다.** `_restore_contracts` 는 DB 경로에서 제거하고 파일 폴백 경로에만 남긴다 |
| signed → 어떤 상태 | 없음 | 허용 전이 없음 |
| 감사 기록 | 없음(F-5) | 전이 UPDATE 와 **같은 트랜잭션**으로 `yeoljeong_audit_logs` 에 `contract.requested`/`contract.signed`/`contract.pdf_regenerated`/`contract.delivered`(from→to, 행위자, 서명 이미지 sha 만, 이미지 본문은 넣지 않음) |
| 보상 쓰기 실패 보고 (파일 폴백 경로) | `_restore_contracts` 가 실패를 삼킴 | 복원 실패가 한 건이라도 있으면 "한 건도 서명되지 않았다"고 답하지 않는다 — 부분 서명 상태를 오류 응답과 `logger.error`·감사 행에 남긴다(F-13) |

#### 구현 방향 (제안, 이번 작업에서는 구현하지 않음)

1. **앱 — 교부 분리**: `_persist_contract_delivery` 에서 `_write_hr_record` 호출을 제거하고 (b) 전용 `UPDATE … SET contract_payload = contract_payload || <b 키만 담은 JSON>, 교부 컬럼 … WHERE id AND tenant_id AND status='signed'` 로 바꾼다. 파일 폴백 경로에도 같은 허용 키 목록을 적용한다. `delivered_at` 은 `COALESCE(delivered_at, $v)` 로 set-once.
2. **앱 — 번들 트랜잭션**: `_db_sign_contracts_atomic(items)` 신설(한 연결, `conn.transaction()`). 단건 서명도 같은 조건부 UPDATE 를 쓴다. 번들 응답 모양(`bundle_id`·`contract_ids`·`contracts`·`primary_id`)은 유지.
3. **앱 — 제외 목록·허용 목록·이력**: 위 "제외 필드 갱신 절차" 1~5 와 `CONTRACT_POST_SIGN_MUTABLE_FIELDS` 신설(제외 목록과 분리). 이력은 한 UPDATE 로 원자적 추가.
4. **DB 백스톱 트리거** `BEFORE UPDATE OR DELETE ON yeoljeong_contracts`: `OLD.status='signed'` 이면 ① DELETE 거부 ② `NEW.status/signed_at/signer_*/sign_token_hash/tenant_id` 가 OLD 와 같고 ③ `deleted_at` 이 NULL→값으로 바뀌지 않고 ④ `NEW.contract_payload − MUTABLE` 이 `OLD.contract_payload − MUTABLE` 과 같고(`MUTABLE` = `CONTRACT_POST_SIGN_MUTABLE_FIELDS` 에서 생성한 `text[]`, **해시 제외 목록이 아니다** — `signature_data_uri`·`signed_snapshot`·`signed_snapshot_sha256`·`signed_pdf_seal` 이 비교에 남아 변조가 거부된다) ⑤ `delivered_at` 이 OLD 에 있으면 변경 불가이며(payload 키와 컬럼 모두) ⑥ `signed_pdf_history` 의 기존 배열이 새 배열의 접두부로 보존될 때(위 "이력 append-only 강제")만 통과. **`signed → requested` 예외는 두지 않는다**(예외를 두면 서명 이후의 서명 취소 경로가 DB 에 열린다). 마이그레이션은 DB 가 둘(ACCT 114 `obys`, AADS 68 `obys`)이므로 둘 다 적용하고 rollback `.down.sql` 을 둔다. 적용 순서는 운영 승인 사항이다.
5. **불변식 검증**: 다운로드·재생성 시 `signed_snapshot_sha256` 재계산(제외 목록 반영 후), `signature_data_uri` 디코드 sha256 == `signature_sha256`(F-3).

### 5.3 개선안 (신규/수정 제안)

- **P1/검증 필요**: 원천세·4대보험 계산은 공식 자료 확인 후 구현(P-11). 이 보고서는 요율 수치를 확정하지 않는다.

- **P1**: 회계 라우터 권한 보강(§5.6).

### 5.4 선행 의존·병렬

#### 5.6.2 AADS 경로 평가

- **인증**: 라우터 단위 `dependencies=[Depends(require_legacy_obys_access)]`(`obys_accounting.py` 20–24)와 엔드포인트 단위 `get_current_user`. 비인증 요청은 전역 미들웨어에서 401(위 표).
- **미들웨어 우회 가능성**: 미들웨어는 `X-Monitor-Key` 헤더가 **어떤 값이든** 있으면 통과시킨다(`main.py` 3953 부근). 그러나 라우트의 `get_current_user`(`app/auth.py` 1751–1791)는 특수값 `internal-pipeline-call` 을 `/pipeline/` 경로에서만 인정한다 → 회계 경로에서는 우회가 아니다. **코드 근거만, 런타임 헤더 재현은 하지 않았다.** 다만 미들웨어가 방어 심층을 약화하는 구조이므로 P2 로 기록.
- **테넌트 격리**: `require_legacy_obys_access`(`obys_tenant.py` 105–130)는 **JWT 의 `tenant_id` 가 허용 목록에 있는지만** 본다. 환경변수 `OBYS_LEGACY_TENANT_IDS` 는 컨테이너에 **미설정**이라 기본값(허용 테넌트 1개)이 적용된다. 허용 테넌트의 활성 멤버는 **owner 2명뿐**(§2.2). 다른 테넌트는 코드상 403(`test_obys_tenant_gate.py` 16 passed). **운영 실계정으로 403 을 확인하지는 못했다(미검증).**
- **관리자·역할 권한**: 라우터에 역할 검사가 **없다**(역할 검사 부재 자체는 코드로 확인됨). 다만 **현재 무엇이 실제로 쓰기 가능한지는 대상별로 다르다.**
  - **전표(`yeoljeong_accounting_entries`) 쓰기 — 현재 차단**: `create_entry`(`yeoljeong_accounting_service.py` 142)·`update_entry`(202)·`delete_entry`(235)·`auto_classify`(250)가 첫 줄에서 `require_journal_write_enabled()`(`obys_upload_service.py` 879–885)를 호출한다. 이 함수는 `OBYS_JOURNAL_WRITE_FROZEN` 이 `0/false/no/off` 가 아니면 **409(`journal_write_moved_to_acct`)** 를 낸다(`journal_writes_are_frozen` 870–876, **기본값 `"true"` = 차단**). 이번 실행(11:38 KST) `aads-server` 컨테이너 환경에서 이 변수는 **미설정**이었으므로 현재 기본값에 따라 차단 상태다. 해제 스위치는 환경변수 하나이고, 배포 시 값이 바뀌면 상태가 달라진다 — 보고서 시점 이후의 값은 보증하지 않는다. `test_obys_ledger_details.py` 21 passed(기본·해제 동작 포함). **따라서 "허용 테넌트 멤버 누구나 분개를 수정·삭제할 수 있다"는 현재 사실이 아니라, 동결을 해제했을 때의 구조다.** 114 standalone 에는 이 라우터가 없어 환경값 확인 대상이 아니다.
  - **세금신고서 쓰기 — 동결 밖**: `create_tax_report`(525)·`update_tax_report`(570–600, `submitted` 로컬 선언 포함)에는 `require_journal_write_enabled` 호출이 **없다**(grep: 호출처는 142/202/235/250 네 곳과 `obys_upload_service` 내부뿐). 분류규칙 `create_category_rule`(642)·`delete_category_rule`(666)도 같다. 동결은 **전표 4개 함수에만** 걸려 있다.
  - **그래서 역할 검사 부재의 현재 영향**: 허용 테넌트의 어떤 멤버든 세금신고서·분류규칙을 쓸 수 있는 구조다(코드 근거). 현재 멤버는 owner 2명(§2.2). 이 테넌트에 직원·매니저가 추가되면 곧바로 위험이 된다. 전표 쓰기는 동결 해제 시점에 같은 위험이 추가된다. 같은 서비스의 계약 쪽은 `_is_admin`(서비스 2276)을 쓰는데 회계 쪽에는 대응물이 없다. **운영에서 실제 호출해 확인하지는 못했다(미검증).**
- **사업자·객체 단위 격리**: `business_id` 는 쿼리 파라미터(기본 `biz-mia`)이고, 단건 엔드포인트는 `WHERE id = $1`(`yeoljeong_accounting_service.py` 212, 242, 609)로 사업자·테넌트 조건이 없다. 허용 테넌트 안에서 다른 사업자의 분개·신고서를 id 로 수정·삭제·계산할 수 있다(코드 근거).
- **변경 감사**: 분개 삭제·신고서 수정에 감사 행이 없다(§2.1 감사 집계에 회계 행 0).
- **데이터 현황**: AADS 경로 DB 는 114 가 아닌 68 의 `obys` 사본이고 분개 0행·세금신고서 0행(§2.2). **현재 이 경로로 새어 나갈 회계 데이터는 없다.** 그러나 DB 연결은 환경변수 하나(`OBYS_DATABASE_URL`)로 바뀐다.
- **`acct_purchase`·`acct_sales`**: 모든 엔드포인트가 `get_current_user` + `_authorized_acct_scope`(테넌트·사업자 매핑 후 403, `acct_sales.py` 33–40)로 스코프된다. 양호(코드 근거). 예외는 `acct-purchase/ui` — 데이터 없는 HTML 셸을 **의도적으로 공개**했다(`main.py` 면제 목록, `acct_purchase.py` 476–488). 응답 본문은 확인하지 않았다.
- **docstring 오류**: `obys_accounting.py` 1–6행은 "main.py 미등록"이라 적었으나 실제로 등록돼 있다. 이런 낡은 문구가 "아직 안 연결됨"이라는 오판을 부른다.

#### 5.6.3 standalone(ACCT 114) 경로 평가

- 회계 라우터(`yeoljeong-accounting`)와 `acct-sales` 는 **탑재돼 있지 않다**(openapi 0, `app/yeoljeong_main.py` 에 `obys_accounting` import·include 없음). 따라서 관리자·테넌트 권한 위험은 **현재 이 경로에는 없다.** 라우트 자체가 없는 것이다.
- 그러나 운영 화면(`index.html` 이 로드하는 `modules/store-assistant-v2.js` 7행, 312행)은 `/api/v1/yeoljeong-accounting/summary`·`/tax-reports` 를 호출한다. 이 호출은 standalone 에서 인증 후 404 일 것으로 **추정**된다. 로그인 상태 호출을 하지 못해 **실제 응답과 화면 영향은 미검증(가설)** 이다.
- `acct-purchase` 는 11 경로가 탑재돼 있으나 `/ui` 는 면제 목록에 없어 비인증 401 이다(AADS 와 다른 동작).
- 만약 이 라우터를 standalone 에 그대로 탑재하면 §5.6.2 의 문제(역할 검사 없음, 객체 단위 스코프 없음)를 114 의 **운영 DB** 위로 그대로 가져가게 된다. 탑재는 5.6.5 의 권한 보강 이후에만 해야 한다.

**완료 판정 기준**(모두 충족):
