## 1. 원인

2026-10-18 12:02 KST 회차에서 단하루의 get_scraping_status 가 isError 로 답했다. 클라이언트는 응답 문구를 버리고 ClobeError("tool_error") 로 바꿨고, _preflight 는 재인증·일시 장애 외의 모든 ClobeError 를 권한 거부로 보고 permission_ok=FALSE 를 기록했다. 스케줄러는 permission_ok IS NOT FALSE 인 회사만 수집하고 FALSE 를 되돌리는 경로가 없어, 클로브의 일시 오류 한 번이 4일치 수집 공백이 됐다(같은 회차의 오비와이 은행도 tool_error 였으나 다음 회차에 정상).

## 4. 권한 거부 판정 기준

저장소 안에 클로브의 실제 권한 거부 응답 샘플이 없다(테스트 픽스처는 가짜가 "forbidden" 이라는 예외를 던질 뿐). 그래서 문구 기반으로 보수적으로 정했다. 마스킹한 오류 문구가 다음 중 하나를 담으면 권한 거부다: permission, forbidden, not a member, not authorized/authorised, access denied, no access, 권한, 접근 불가/거부/할 수 없/이 없. 이 외 모든 isError 는 일반 도구 오류(일시 오류 취급)다.

- 이 목록이 실제 응답을 놓치면(거짓 음성) 진짜 거부가 일반 오류로 읽혀 매 회차 clobe_tool_error 로 실패한다. 상태는 틀리게 박히지 않고, 로그의 detail 로 문구를 확인해 목록에 더하면 된다.
- 반대로 문구에 permission 같은 단어가 섞인 일시 오류는 FALSE 로 기록되지만, 아래 재확인이 되돌린다.

마스킹: 공백 정리 후 Bearer 값, token/secret/password/api_key/code 등 키=값, 24자 이상의 토큰 모양 문자열을 *** 로 가리고 200자로 자른다(마스킹이 먼저라 잘린 토큰 조각이 남지 않는다). str(exc) 는 여전히 "tool_error" 또는 "permission_denied" 분류 코드만이다.

## 5. 재확인 동작

대상: link_status=linked, permission_ok=FALSE, permission_error 가 absent_from_context 가 아닌 행.

- 마지막 확인(permission_checked_at) 이후 간격이 지나면 get_scraping_status 1회 호출. 성공하면 permission_ok=TRUE, permission_error=NULL 로 복귀하고, 같은 회차의 load_state 가 그 뒤에 돌므로 즉시 수집 대상이 된다.
- 간격: 환경변수 OBYS_CLOBE_PERMISSION_RECHECK_HOURS, 기본 6시간. 0 이하면 재확인을 끈다. 숫자가 아니면 기본값.
- 실패(권한 거부·도구 오류): FALSE 유지, permission_checked_at 갱신, 연속 실패 횟수 +1. 다음 간격은 기본 간격 × 2^실패횟수(실패 4회 이후는 ×16 = 96시간에서 고정).
- 연속 실패 상한: OBYS_CLOBE_PERMISSION_RECHECK_MAX_FAILS, 기본 5. 상한에 닿으면 자동 재확인을 멈춘다(수동 조치 대상). 기본값으로 첫 실패부터 상한까지 약 7.5일.
- 실패 횟수는 컬럼을 늘리지 않으려고(마이그레이션·권한 부여 없이) permission_error 끝의 ;recheck_fail=N 꼬리표에 싣는다. 성공하면 permission_error 가 NULL 이 되어 초기화된다.
- 재인증 필요·일시 장애는 회사 문제가 아니므로 횟수를 올리지 않고 그 회차 재확인을 접는다. 한 회사의 예외는 다른 회사를 막지 않고, 조회 실패도 정기 수집을 막지 않는다. 재확인은 수집과 같은 시간 예산(840초) 안에서만 돈다.
- 재확인 결과의 FALSE 유지는 종료코드를 바꾸지 않는다(예상된 상태).

## 7. 운영 영향과 후속

- 이미 FALSE 로 박힌 운영 행(단하루)의 1회 복구는 이 작업 범위가 아니다(CEO 승인 대기). 코드가 배포되면 단하루는 permission_checked_at(10-18 12:02 KST)이 이미 6시간을 넘었으므로 다음 스케줄러 회차에서 get_scraping_status 1회 재확인을 받고, 성공하면 TRUE 로 돌아와 같은 회차에 수집 대상이 된다. 즉 수동 복구 없이 자연 복구된다. 단 단하루의 permission_error 에 꼬리표가 없으므로 실패 횟수는 0에서 시작한다.
- 새 환경변수 두 개(OBYS_CLOBE_PERMISSION_RECHECK_HOURS, OBYS_CLOBE_PERMISSION_RECHECK_MAX_FAILS)는 선택이다. 설정하지 않으면 기본값이 적용된다.
- 배포 뒤 첫 회차의 스케줄러 JSON 출력에서 permission_rechecks 와 로그의 clobe_preflight_tool_error detail 로 실제 클로브 오류 문구를 확인해, 권한 거부 문구 목록을 실측으로 보정할 수 있다.
