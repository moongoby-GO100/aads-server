### 3.5 일자 축(dateBasis) 확정 전 표시 정책과 확정 방법

#### 확인한 사실

- 도구 `get_monthly_revenue` 의 저장 스키마에서 `dateBasis` 는 `string|null` 이고 **JSON `enum` 이 없다.** 허용값은 설명 문구에만 있다: `SETTLEMENT_DATE`(정산 예정일 = 입금 예상 기준, **기본**) / `SALE_DATE`(매출 발생일). `startDate/endDate` 도 "dateBasis 기준"이라고 적혀 있다. `timeUnit` 도 enum 없이 DAILY(기본)/WEEKLY/MONTHLY/QUARTERLY 만 문구로 안내된다(부록 A-6).
- 수집기 `pick_date_basis`(`obys_collection_core.py:706`)는 enum 이 있을 때만 값을 고르고, enum·default 가 없고 환경변수 `OBYS_CLOBE_CHANNEL_DATE_BASIS` 도 없으면 `(None, None)` 을 돌려 **`dateBasis` 를 보내지 않는다.** 그래서 저장 행은 `date_basis=DEFAULT`(응답에도 기준이 없어 기본값 표기), `grain=DAY` 다. 37/37 행이 같다(부록 A-1).
- 결과: 서버 기본값인 `SETTLEMENT_DATE` 일 **가능성이 높지만, 응답 자체가 기준을 말해 주지 않아 확정이 아니다.** 근거는 도구 설명뿐이다.
- 화면 `basisLabel()` 은 `DEFAULT` 를 "집계 기준 미상"으로 보여 준다(`data-overview.js:338`). 화면에 "어제 매출" 문구는 코드에 없다(`어제` 검색 0건). "어제 매출"은 이 문서 §5 의 제안 문구다.

#### 정황 증거 (확정 아님)

| 관측 | 값 | 해석 |
|---|---|---|
| 수집 시각 11:00 에 이미 들어 있는 당일(10-16) 배민 행 | 2개 사업자 합 3,795,500원 / 174건 | 영업 시작 직후 매출로는 크다. 정산 예정일 축이면 설명 가능 |
| 10-14 배민 4개 사업자 합 | 20,856,100원 / 967건 (10-13: 4,284,200 / 189, 10-15: 3,690,100 / 159) | 인접일의 약 5배. 정산 예정일 축에서 휴일 묶음 정산이면 설명 가능 |
| 10-15·10-16 은 행이 2개 사업자뿐 | 4개 사업자 행은 10-13·10-14 | 아직 정산 예정일이 안 온 사업자 행이 없는 것일 수 있다 |

세 관측 모두 "정산 예정일 축" 가설에 부합하지만 "매출 발생일 축 + 수집 지연"으로도 일부 설명되므로 **가설**로 둔다.

#### 확정 방법

1. **자체 수집 주문일 합계와 대조(비파괴).** 같은 사업자·같은 날짜에 대해 클로브 `gross`(DEFAULT) 와 자체 수집의 `occurred_on` 별 주문 합계를 비교한다(부록 A-8).
   - 매출 발생일 축이면 일별 값이 거의 같아야 한다. 정산 예정일 축이면 같은 값이 영업일 기준으로 뒤로 밀려 나타난다(주문일 합계를 +N영업일 이동해야 일치).
   - 판정 기준(제안): 3개 이상 사업자·7일 이상 구간에서 일 단위 값이 ±1% 이내로 일치하는 이동 일수 N(0 또는 정산 주기)을 찾는다. N=0 이면 매출 발생일 축, N>0 이면 정산 예정일 축.
   - **지금은 겹치는 날짜가 없다.** 클로브 금액 있는 행은 10-13~10-16, 자체 수집 주문 행은 08-03~09-09(요약행은 09-12까지)라서 겹치는 사업자-일이 **0건**이다(A-8). 자체 수집이 재개되어 3일 창과 겹쳐야 이 방법을 쓸 수 있다.
2. **SALE_DATE 대조 호출(승인 필요).** 같은 회사·같은 기간을 `dateBasis=SALE_DATE` 와 `SETTLEMENT_DATE` 로 각각 호출해 일별 합계 차이를 본다. 두 응답이 같으면 기준 차이가 없는 것이고, 다르면 현재 DEFAULT 값이 어느 쪽과 일치하는지로 확정한다. 외부 호출이고 저장하지 않더라도 이번 범위(수집 실행 금지)를 넘으므로 승인 후 Runner 가 수행한다.
3. **명시 전송.** 확정 후에는 환경변수 `OBYS_CLOBE_CHANNEL_DATE_BASIS` 로 값을 지정하면 코드 변경 없이 `dateBasis` 를 보낼 수 있다(`pick_date_basis` 의 `pref` 경로). 단 `source_key` 에 기준이 들어가므로 `DEFAULT` 행과 새 기준 행이 따로 쌓여 합산 시 이중 집계될 수 있다 → 적용 전에 `list_channel_revenue` 의 기준별 그룹 동작을 확인해야 한다(**검증 필요**). 운영 환경 변경이라 이번 범위 아님.

#### 표시 정책 (기준 확정 전)

| 화면·문구 | 정책 |

| "어제 매출", "오늘 매출", "월 매출" | 클로브 금액에는 **사용하지 않는다.** |

## 4. 항목 7 — 배달앱 수집 처리 상세 점검

### 4.1 수집 처리 흐름과 병목

1. 클로브 경로: 타이머 → 임대(lease)·펜싱(`owner_epoch`) → `get_scraping_status` → 호출 → 정규화 → 저장 → 상태 갱신. 실패는 상태 테이블에 `last_error_code`, `consecutive_failures`, `next_retry_at` 으로 남는다.
2. 자체 수집 경로: PC Agent/스마트 브라우저 → `yeoljeong_delivery_*` 5개 테이블 + `collection_status`. 상태 값(누적, 부록 A-7): `action_required` 3,975 / `succeeded` 458 / `failed` 321 / `partial` 78 / `credential_required` 55 / `portal_action_required` 50 / `stale` 24 / `upload_required` 12.
3. 오류 사전(`ohvis_wiki_error_book`)과의 대조는 이 점검에서 실행하지 않았다(`error_book.py` 는 DB 쓰기 가능성이 있어 보류).

### 4.3 개선 요약과 완료 판정

- 수집 상태 표시: 원천 증거(어느 도구·어느 기간), 수집 건수, 오류 코드, 마지막 성공, 재시도 예정, 승인 필요 여부를 한 화면에서 보이게 한다. 완료 판정: 오류 코드 각각이 화면에서 조치 문구로 바뀌고, 마지막 성공 시각이 항상 보인다. 의존: 오류 코드 목록 확정(위 표).

### A-3. 배민 주문 중복 +35% (5,832,050 vs 7,877,950)

필터: `deleted_at is null`, 배민, 요약행 제외(`order_status <> 'dashboard_summary'`), 주문번호 있는 행만. 사업자 필터 없음(4개 전체). 기간 필터 없음(전체 수집분 08-03~09-09).
```sql
with o as (
  select row_id, business_id, payload->>'order_id' as oid,
         (payload->>'gross_amount')::numeric as g,
         (payload->>'collected_at')::timestamptz as ca
  from yeoljeong_delivery_sales
  where payload->>'service' = 'baemin' and deleted_at is null
    and coalesce(payload->>'order_status','') <> 'dashboard_summary'
    and nullif(payload->>'order_id','') is not null
),
l as (                                   -- 주문번호별 최신 collected_at 1건
  select distinct on (oid) * from o order by oid, ca desc, row_id desc
)
select (select count(*) from o)               as rows_as_is,
       (select count(*) from l)               as rows_dedup,
       (select sum(g) from o)::bigint         as gross_as_is,
       (select sum(g) from l)::bigint         as gross_dedup,
```

```sql
                          - (payload->>'vat_amount')::numeric - (payload->>'settlement_amount')::numeric) <= 1) as nonzero_identity_ok,
```

### A-8. 일자 축 대조 (3.5) — 겹치는 구간 확인과 대조 쿼리

```sql
with c as (
  select occurred_on as d, business_id, sum(amount) as g, sum((payload->>'count')::numeric) as n
  from obys_clobe_item
  where data_kind='channel_revenue' and stage <> 'superseded' and amount is not null and institution = '배민'
  group by 1,2),
o as (
  select (nullif(payload->>'occurred_on',''))::date as d, business_id,
         sum((payload->>'gross_amount')::numeric) as g, count(*) as n
  from yeoljeong_delivery_sales
  where payload->>'service'='baemin' and deleted_at is null
    and coalesce(payload->>'order_status','') <> 'dashboard_summary'
    and nullif(payload->>'occurred_on','') is not null
  group by 1,2)
select (select min(d) from c) as clobe_min, (select max(d) from c) as clobe_max,
       (select min(d) from o) as own_min,  (select max(d) from o) as own_max,
       (select count(*) from c join o using (d, business_id)) as overlap_biz_days;
```
