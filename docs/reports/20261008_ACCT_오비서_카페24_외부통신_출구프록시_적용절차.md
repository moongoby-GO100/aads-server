- 상태: 코드·스크립트·테스트·문서 완료. **카페24 운영에는 아무것도 적용하지 않았다**(컨테이너·네트워크·Apache·Cloudflare 불변). 아래 절차는 별도 승인 후 실행한다.

## 1. 배경과 목적

오비서 앱(`acct-app-candidate-rN`)은 `--network container:acct-pg` 로 돈다. `acct-pg` 의 네트워크 `acct_net` 은 `internal=true` 라서 앱에서 `api.clobe.ai` 해석이 실패한다(클로브 연결 0건).

임시 조치로 bridge 네트워크 `acct_egress` 를 만들어 `acct-pg` 에 붙였는데, 이러면 **DB 컨테이너의 네트워크 네임스페이스 전체**(앱 포함)가 어디로든 나갈 수 있다. 이 구성은 그것을 대체한다.

```
앱 (netns = acct-pg) --HTTPS_PROXY--> acct-egress-proxy:8888 (acct_net 에도, acct_egress_out 에도 붙음)
                                          └─ CONNECT 허용: api.clobe.ai:443 뿐 → 인터넷
acct-pg 자체는 acct_net(internal) 에만 남는다 → 직접 외부 연결 불가
```

## 3. 구성 요소

### 3.1 프록시 (`deploy/acct-egress/`)

- tinyproxy(alpine). `FilterDefaultDeny Yes` + `FilterURLs Off`(호스트명 기준) + `FilterType ere` + `ConnectPort 443`. 허용 목록에 없는 호스트의 CONNECT 는 403, 로그에 남는다(`docker logs acct-egress-proxy`).
- 허용 목록: `ACCT_EGRESS_ALLOW` (쉼표/공백 구분, 기본 `api.clobe.ai:443`). 호스트명만 허용 — **443 외 포트, 와일드카드, IP 주소는 거부**하고 목록이 비면 실패한다(fail-closed). 포트를 443 으로 고정한 이유: tinyproxy 는 호스트와 포트를 따로 걸러서 `(호스트 × 포트)` 곱집합이 되기 때문이다.
- 컨테이너 격리: `--read-only`, `--cap-drop ALL`(+SETUID/SETGID — tinyproxy 가 `tinyproxy` 사용자로 내려가는 데만), `no-new-privileges`, 메모리 128m, pids 64, 포트 publish 없음. 설정은 `/root/acct-egress/` 에서 읽기 전용 마운트.
- 네트워크 두 개: 내부 `acct_net`(internal=true 확인 후 진행), 외부용 `acct_egress_out`(없으면 생성, internal 이면 거부). **임시 조치 네트워크 `acct_egress` 와 이름이 달라야** 하며 같으면 스크립트가 거부한다.

### 3.2 배포 스크립트 옵션

| 변수 | 기본 | 설명 |
|---|---|---|
| `ACCT_APP_EGRESS_PROXY_URL` | (비움 = 비활성) | 예 `http://acct-egress-proxy:8888`. 형식 `http://<컨테이너이름>:<포트>` 만 허용, 그 컨테이너가 실행 중이어야 함(아니면 exit 8, 원격 코드 94) |
| `ACCT_APP_NO_PROXY` | `localhost,127.0.0.1,acct-pg` (`ACCT_PG_CONTAINER` 가 다르면 함께 추가) | 문자 `A-Za-z0-9._:,-` 만 허용 |

활성화되면 후보 컨테이너 env 의 기존 `HTTPS_PROXY/HTTP_PROXY/NO_PROXY`(소문자 포함)는 지우고 새 값으로 쓴다. 활성화하지 않으면 **이전 컨테이너 env 를 그대로 복사**하므로, 한 번 켠 프록시 설정은 이후 릴리스에도 유지된다(끄려면 아래 §5 롤백).

## 4. 운영 적용 절차 (승인 후, 카페24)

모든 명령은 카페24(`server-114`)에서 root 로. `<N>` 은 현재 운영 후보 번호.

### 단계 0 — 현재 상태 기록
```bash
docker network inspect acct_net acct_egress -f '{{.Name}} internal={{.Internal}}'
docker inspect acct-pg -f '{{range $k,$_ := .NetworkSettings.Networks}}{{$k}} {{end}}'   # acct_net acct_egress 로 보여야 함
docker ps --format '{{.Names}}' | grep acct-app-candidate
```

### 단계 1 — 프록시 기동
```bash
# 68 서버에서 파일 전송 (예: ssh server-114 'mkdir -p /root/acct-egress-src')
tar -C deploy -cf - acct-egress | ssh server-114 'tar -C /root/acct-egress-src -xf -'
# 카페24
cd /root/acct-egress-src/acct-egress
ACCT_EGRESS_ALLOW=api.clobe.ai:443 bash acct_egress_proxy.sh render /tmp/acct-egress-preview && cat /tmp/acct-egress-preview/allow.list
bash acct_egress_proxy.sh up
bash acct_egress_proxy.sh status      # running, nets=acct_egress_out acct_net
docker logs --tail 20 acct-egress-proxy   # 기동 오류(설정/사용자 전환)가 없어야 함
```
롤백: `bash acct_egress_proxy.sh down` (프록시 컨테이너만 제거. 네트워크 `acct_egress_out` 은 필요하면 `docker network rm acct_egress_out`).

### 단계 2 — 앱 env 를 바꾸기 전에 프록시 동작 확인 (게이트)
현재 운영 앱 컨테이너 안에서 프록시를 env 로만 지정해 시험한다(컨테이너 변경 없음).
```bash
docker exec -e HTTPS_PROXY=http://acct-egress-proxy:8888 -e NO_PROXY=localhost,127.0.0.1,acct-pg acct-app-candidate-r<N> python3 - <<'PY'
import httpx
for u in ("https://api.clobe.ai/", "https://example.com/"):
    try:
        print(u, httpx.get(u, timeout=10).status_code)
    except Exception as e:
        print(u, type(e).__name__, e)
PY
docker logs --tail 20 acct-egress-proxy
```
기대: `api.clobe.ai` 는 HTTP 응답 코드(200/401/404 등 무엇이든 응답이 오면 통과), `example.com` 은 `ProxyError`(403) 와 프록시 로그에 거부 기록. **둘이 다르게 나오지 않으면 여기서 멈추고 단계 1 롤백.** (tinyproxy 의 CONNECT 필터·로그 출력은 이 세션에서 실제로 돌려 보지 못했다 — 이 단계가 그 검증이다.)

### 단계 3 — 앱 env 반영 배포
```bash
ACCT_APP_EGRESS_PROXY_URL=http://acct-egress-proxy:8888 \
  bash scripts/deploy_acct_app_cafe24.sh "<release_sha 40hex>" "<run_id>"
```
(ops 큐 경유 시 위 환경변수가 스크립트까지 전달되는지 확인한다.) 출력에 `egress proxy enabled for acct-app-candidate-r<N+1>` 가 보여야 한다.
롤백: `bash scripts/deploy_acct_app_cafe24.sh rollback acct-app-candidate-r<N> "<run_id>"` — 이전 컨테이너는 중지·삭제되지 않으므로 Apache 포트만 되돌린다.

### 단계 4 — 새 컨테이너에서 연결 확인
```bash
docker exec acct-app-candidate-r<N+1> env | grep -i proxy      # 6개 + NO_PROXY 에 acct-pg
docker exec acct-app-candidate-r<N+1> python3 - <<'PY'
import httpx
print(httpx.get("https://api.clobe.ai/", timeout=10).status_code)
PY
```
오비서 화면에서 클로브 연결 시작(`start_authorization`)이 `ConnectError` 없이 인가 URL 을 돌려주는지, DB 접속이 정상인지(`/api/v1/health`)도 확인한다. 롤백은 단계 3 과 같다.

### 단계 5 — 임시 조치 제거
**단계 4 가 통과한 뒤에만.**
```bash
docker network disconnect acct_egress acct-pg && docker network rm acct_egress
```
롤백(다시 임시 개방 — 프록시가 고장 났을 때의 비상용):
```bash
docker network create acct_egress && docker network connect acct_egress acct-pg
```
참고: 프록시 env 가 없는 예전 컨테이너(r<N> 이하)로 롤백하면 이 시점부터 클로브 연결은 다시 안 된다(임시 조치 이전 상태와 같다).

### 단계 6 — 차단 확인
```bash
# (a) 프록시 경유 다른 목적지는 거부
docker exec acct-app-candidate-r<N+1> python3 -c "import httpx; httpx.get('https://example.com/', timeout=10)"   # ProxyError 기대
docker logs --tail 5 acct-egress-proxy                                                                           # 거부 기록
# (b) 프록시를 우회한 직접 연결은 불가
docker exec -e HTTPS_PROXY= -e HTTP_PROXY= -e https_proxy= -e http_proxy= acct-app-candidate-r<N+1> \
  python3 -c "import httpx; httpx.get('https://api.clobe.ai/', timeout=10)"                                      # ConnectError(DNS) 기대
# (c) DB 컨테이너 네트워크
docker inspect acct-pg -f '{{range $k,$_ := .NetworkSettings.Networks}}{{$k}} {{end}}'                           # acct_net 만
```

## 5. 프록시를 끄고 원래대로 돌아가려면

- 프록시 env 가 있는 컨테이너에서 파생된 새 후보는 그 env 를 복사하므로, `ACCT_APP_EGRESS_PROXY_URL` 을 비워 재배포해도 프록시 설정이 남는다. 이 작업은 "끄는 옵션"을 만들지 않았다.
- 되돌리는 방법은 프록시 도입 전 컨테이너(r<N>)로 `rollback`(단계 3) 하는 것뿐이다. 필요하면 단계 5 롤백으로 임시 개방을 되살리고 `bash acct_egress_proxy.sh down` 으로 프록시를 내린다.

## 6. 허용 목적지 추가

`ACCT_EGRESS_ALLOW="api.clobe.ai:443,<호스트>:443" bash acct_egress_proxy.sh up` (컨테이너만 재생성되며 앱은 재배포 불필요). 잘못된 항목이 하나라도 있으면 아무것도 쓰지 않고 실패한다.

## 7. 검증 결과와 한계

- 단위 테스트: `bash scripts/run_unit_tests.sh tests/unit/test_acct_egress_proxy.py tests/unit/test_acct_app_cafe24_release.py` → 101 passed. ruff F821/F811 이상 없음.
- **실제 docker/카페24에서는 실행하지 않았다.** tinyproxy 설정(`Filter`/`ConnectPort`/`LogFile "/dev/stdout"`/사용자 전환)과 이미지 빌드는 단계 1·2 에서 처음 검증된다.
- 평문 HTTP(80) 는 필터가 호스트 기준이라 허용 호스트에 한해 통과할 수 있다. 앱은 HTTPS 만 쓰므로 현재 영향은 없다.
- 프록시를 켜면 `NO_PROXY` 에 없는 모든 외부 호출이 `api.clobe.ai` 이외에는 막힌다. 클로브 외에 앱이 부르는 외부 주소가 있으면 앱 로그의 `ConnectError`/`ProxyError` 로 드러나며, 목록에 추가(§6)해서 해결한다.
