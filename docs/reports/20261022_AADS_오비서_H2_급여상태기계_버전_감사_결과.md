## 5. 한계와 남은 일

- DB 업서트 가드 SQL 은 운영 DB 로 실행해 검증하지 못했다. 가드에 걸린 쓰기는 기존 규칙대로 대상 없음(404)으로 나온다. 서비스 계층이 먼저 409 로 막으므로 정상 경로에서는 닿지 않는다. DB 의 행 삭제 경로 자체에는 가드를 넣지 않았다(서비스 계층이 막음).
- 교부 멱등 잠금은 프로세스 안 락이다. 다중 워커에서 같은 명세를 동시에 교부하면 이론상 중복 발송이 가능하다. DB 유니크 제약이나 어드바이저리 락은 마이그레이션이 필요해 이 범위에서 넣지 않았다.
- 대시보드 화면에 확정 버튼, 이력 보기, 수신 동의 UI 는 추가하지 않았다. API 만 제공한다.
- 외부 채널 발송(알림톡·SMS·메일)은 구현하지 않았다. 사내 알림만 보낸다.
- 근태 기반 단가는 현재 유효한 계약의 시급·일급을 쓴다. 월 중간에 계약이 바뀐 경우 월별 단가 분리는 하지 않았다. 근태 행의 시급이 계약과 다르면 attendance_basis 의 rate_mismatch_records 에 건수만 남긴다.
- 근태 기반 초안은 DB 모드에서만 동작한다. 근태 저장소가 DB 뿐이라 파일 모드에서는 503 을 돌려준다.
- 근태 초안은 4대보험·원천세를 계산하지 않는다(공제는 0 또는 기존 draft 값 유지). 세금 계산은 H3 범위다.

## 6. P-8 이관 53행 읽기 전용 조회 설계

운영 DB 는 건드리지 않았다. 아래는 승인 후 읽기 전용 트랜잭션에서 돌릴 조회 설계다. 대상은 yeoljeong_payroll_statements 의 삭제되지 않은 행이다.

1. 분포: status, payroll_month 별 건수. 전부 draft 인지 재확인.
2. 이메일 연결: employee_email 이 비어 있는 행 수(교부 불가 대상).
3. 금액 건전성: gross_pay, tax_withholding, insurance_deduction, other_deduction, net_pay 중 음수인 행, net_pay 가 총지급액-공제와 다른 행, 공제가 모두 0인 행(세부 공제가 없는 이관 행 의심).
4. 중복: business_id, 직원(이메일 또는 이름), payroll_month 가 같은 행이 둘 이상인 조합.
5. 이관 표지: statement_payload 의 JSON 키 목록 분포(이관 표지와 계약 기본값 적용 여부 확인).
6. 월 형식: payroll_month 가 YYYY-MM 형식이 아닌 행(period 와 혼용된 흔적).

실행 방법은 BEGIN READ ONLY 트랜잭션 안에서 SELECT 만 쓰고, 개인 식별 값은 집계로만 내며 출력에 이메일 원문을 싣지 않는다. 결과에 따라 재입력 전 신고 원천에서 제외할 행을 정한다(제외 판정은 H3 입력).
