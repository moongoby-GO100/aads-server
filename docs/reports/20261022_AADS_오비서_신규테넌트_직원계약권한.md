# 오비서 신규 테넌트 대표의 승인 직원·계약 화면 권한

- document_key: `obys-tenant-owner-contracts-gate`
- 작업: AADS-OBYS-TENANT-OWNER-APPROVED-CONTRACTS-GATE-20261022
- 범위: 서버(`app/core/obys_tenant.py`, `app/services/yeoljeong_finance_service.py`)와 테스트. 프론트·DB 스키마·마이그레이션은 건드리지 않았다.

## 1. 증상과 원인

신규 테넌트 대표가 직원 가입요청을 승인해도 '승인 직원 계약'과 '계약·인사증빙' 화면이 403 으로 열리지 않았다.
`app/core/obys_tenant.py` 의 `require_legacy_obys_access` 가 `/employees/approved*`, `/contracts`, `/business-documents` 를
레거시 테넌트(15055cac…)에만 열어 두었기 때문이다. 서명 경로(`_CONTRACT_SIGNING_WHITELIST`)와 초대 경로(`_INVITE_ADMIN_WHITELIST`)만 신규 테넌트에 열려 있었다.

## 3. 화면이 부르는 호출 (grep 근거)와 열린 경로

| 화면 호출 | 출처 | 게이트 |
|---|---|---|
| `GET /employees/approved` | `admin.html`, `modules/contract-editor-v41.js` | 열림 |
| `GET /contracts`, `POST /contracts` | 위 두 곳 | 열림 |
| `POST /contracts/{id}/request-signature`, `/resend-signature-notice` | `contract-editor-v41.js` | 열림 |
| `GET /contracts/{id}/signed-pdf`, `POST /contracts/{id}/signed-pdf/regenerate` | `contract-editor-v41.js` | 열림 |
| `GET /onboarding/document-types`, `GET·POST /onboarding/documents`, `GET /onboarding/documents/{id}/download` | `contract-editor-v41.js` | 열림 |
| `GET·POST /business-documents` | `admin.html` (`financeApiV41`) | 열림 |
| `GET /tenant-registry/businesses` | `contract-editor-v41.js` | 이미 열려 있음 |
| `employee-portal.js` 의 서명 보기·서명 | | 이미 서명 화이트리스트에 있음 |

경로는 모두 (메서드, `fullmatch` 정규식) 쌍이고 id 는 UUID 형식만 받는다. 접두어 매칭은 쓰지 않는다.

열지 않은 것과 이유:

- `DELETE /contracts/{id}`: 화면이 부르지 않음. 삭제는 열 이유가 없다.
- `/employees/approved/{id}/role|assignment|resync-employment|employment-history`: 화면 호출 없음, 권한 변경 성격.
- `PATCH·DELETE·download /business-documents/{id}`: 화면 호출 근거를 확인하지 못했다.
- `/onboarding/documents/{id}` 의 review·삭제·bankbook-extract: 같은 이유.
- `/businesses/{id}/registration-document`: 화면이 부르지만 이번 범위가 아니다(아래 7절 후속).

## 4. 테넌트 격리 근거

- 읽기: `_read_hr` 가 SQL 에서 JWT 테넌트로 거른다. 파일 모드에서도 `tenant_id` 로 거른다. DB 읽기 실패(None)는 빈 목록이지 타 테넌트 행이 아니다.
- 비레거시 호출자는 활성 멤버십이 있어야 하고 관리자(대표)만 통과한다. 신규 테넌트의 직원 member 는 열린 경로 전부에서 403 이다.
- 계약 작성: `employee_request_id` 가 호출자 테넌트 가입요청에 있어야 하고, `business_id` 는 DB 사업자-테넌트 매핑이 `True` 여야 한다. 매핑을 못 읽으면(`None`) 403 으로 닫는다. 타 테넌트 직원과 존재하지 않는 직원은 같은 403 이라 존재 여부가 드러나지 않는다.
- 계약 저장 SQL 의 `WHERE tenant_id = EXCLUDED.tenant_id` 가 타 테넌트 계약 id 덮어쓰기를 한 번 더 막는다.
- id 로 지정하는 작업(서명 요청 등)이 타 테넌트 계약을 가리키면 기존대로 404 다.
- 사업자 문서는 서비스가 이미 관리자 필수·테넌트/매핑 SQL 바인딩·타 테넌트 403 이다. 파일 모드에서는 비레거시 호출자를 403 으로 닫았다.
- 레거시 테넌트의 판정과 응답은 바꾸지 않았다. 서명 화이트리스트도 그대로다.

## 5. 설계 결정

- `_require_owner_path_admin` 은 호출자가 보낸 `tenant_id` 가 아니라 `_tenant_id(user)` 로 검증된 멤버십 테넌트로 레거시 여부를 본다.
- 신규 테넌트 직원 member 의 입사서류 본인 업로드는 이전과 같이 403 이다. 게이트가 `POST /onboarding/documents` 를 역할과 무관하게 열기 때문에 서비스가 관리자만 허용하도록 닫았다. 직원 본인 업로드를 신규 테넌트에 열려면 별도 결정이 필요하다.
- 계약서의 사용자(employer_*) 정보는 화면이 `/tenant-registry/businesses` 에서 채워 payload 로 보낸다. 서버는 canonical 사업자에 없는 신규 사업자의 employer 정보를 만들지 않는다.

## 7. 프론트 후속 필요 (이번에 하지 않음)

- `/businesses/{id}/registration-document` 는 아직 게이트에서 닫혀 있다. 화면의 사업자등록증 보기·등록이 신규 테넌트에서 계속 403 이다.
- 신규 테넌트 직원의 입사서류 본인 업로드(5절).
- 이 변경이 실제 서비스에 반영되는 시점의 검증은 승인 후 Runner 의 빌드 검증 대상이다.

## 8. 등록 상태

- 정본 문서 등록(project_document_heads): 이 세션에서는 등록 도구·API 를 쓰지 않았다. **정본 미등록(미완료)**. 열람 링크 미제공.
- DB 핸드오버(`handover_write`, project=AADS, entry_type=verification, entry_key=runner:<job_id>): 이 세션에서는 호출하지 않았다. **미기록(미완료)**.
- 커밋·푸시는 Runner 가 승인 후 수행한다. 이 세션에서는 하지 않았다.
