# 카페24 오비서 클로브 수집 구성

- document_key: `acct-clobe-cafe24-collect-config`
- 작업: ACCT-CLOBE-CAFE24-COLLECT-20261008 (목표 df479771, 오비서 카페24 독립 운영 이전)
- 상태: 코드·마이그레이션·테스트 완료. **운영에는 아무것도 적용하지 않았다**(배포·GRANT·환경변수·OAuth·수집 모두 CEO 승인 후).
- 정본 등록: 정본 미등록(미완료) — 이 세션에 정본 등록 경로(인증 토큰·DB)가 없다. 승인 후 Runner 또는 후속 세션이 이 문서를 초안으로 등록한다.

## 1. 원인 (실측)

카페24 오비서에서 클로브 수집이 못 도는 원인은 세 겹이다.

1. **권한.** 앱 런타임 역할 `acct_business_runtime_r5` 에 `obys_clobe_*` 6개 테이블 권한이 없다(소유자 `acct_admin`). `svc.approve_link` 가 permission denied.
2. **토큰 저장소 위치.** `clobe_mcp_client` 는 공유 풀(`get_pool()` = `DATABASE_URL`)로 `clobe_mcp_*` 4개 테이블을 읽는다. 그런데 오비서 독립 실행(`app/core/obys_runtime.py` `RuntimeSettings.apply()`)은 `DATABASE_URL` 을 **인증 DB(`OBYS_AUTH_DATABASE_URL`)로 덮어쓴다.** 즉 이전 그대로 배포해도 업무 DB 가 아니라 인증 DB 를 본다. 그리고 그 테이블은 contabo116 aads DB 에만 있다.
3. **암호화 키.** 토큰은 Fernet 으로 암호화된다. 독립 실행은 `VAULT_ENCRYPTION_KEY` 를 **읽지 않고** `OBYS_VAULT_KEY` 만 읽는다(2026-09-30 분리, `docs/operations/OBYS_VAULT_SEPARATION_RUNBOOK.md`). 지시서의 "카페24 전용 VAULT_ENCRYPTION_KEY" 는 카페24 컨테이너에서는 **`OBYS_VAULT_KEY`** 라는 이름으로 주입해야 한다.

추가로 클로브 API 는 `clobe_mcp_*` 가 없는 DB 에서 `ensure_schema()` 의 `CREATE TABLE IF NOT EXISTS` 를 시도하는데, 앱 역할에는 스키마 CREATE 권한이 없고 이 구문은 테이블이 있어도 스키마 권한을 먼저 본다. 그래서 독립 실행에서는 DDL 을 돌리지 않고 테이블 존재만 확인하게 바꿨다.

## 3. 저장소 선택 규칙

`store_mode()`:

1. `CLOBE_STORE_DATABASE_URL` 이 있으면 **obys** (이 DSN 사용).
2. 없고 오비서 독립 실행(`credential_vault.is_standalone_vault()`)이면 **obys** (`OBYS_DATABASE_URL`).
3. 아니면 **aads** — 기존 `DATABASE_URL` 공유 풀 그대로. contabo116 AADS 본체는 변화 없다.

obys 모드에서 DSN 이 없으면 `store_database_url_missing` 으로 실패한다. AADS 풀로 폴백하지 않는다(`obys_db.py` 와 같은 원칙). 전용 풀은 최대 5 커넥션이다(토큰 갱신이 advisory lock 커넥션을 쥔 채 같은 풀에서 하나를 더 쓴다).

금고 키(`OBYS_VAULT_KEY`)가 없으면 `start_authorization`, `handle_callback`, `_valid_access_token` 이 `vault_disabled` 분류 오류로 끝난다. 예전에는 `VaultUnavailableError` 가 그대로 올라와 500 이 됐다.

## 4. 마이그레이션 `20261008_obys_clobe_mcp_store.sql`

- `clobe_mcp_oauth_client / oauth_state / connection / tools` 를 `CREATE TABLE IF NOT EXISTS`. 빈 상태로 생긴다 — contabo116 의 값은 옮기지 않는다.

  - `clobe_mcp_oauth_client`: SELECT, INSERT
  - `clobe_mcp_oauth_state / connection / tools`: SELECT, INSERT, UPDATE
- DROP·DELETE·TRUNCATE·ALTER 없음, `BEGIN;…COMMIT;` 단일 트랜잭션. `deploy_acct_app_cafe24.sh` 의 `migration_scan` 을 통과한다(단위 테스트로 고정).

## 5. 배포 스크립트 변경 사유 (지시서에 없던 부분)

후보 컨테이너는 이전 컨테이너 환경을 **그대로 복사**한다. 그러면 새 환경변수(`OBYS_VAULT_KEY`)를 넣을 방법이 없다. 그래서 `R_START_CANDIDATE` 에 선택적 훅을 넣었다.

- 카페24 `/root/acct-app-extra.env` 가 있으면 읽는다. 경로 고정, **root 소유 0600 이 아니면 거부(93)**.
- 허용 이름만: `OBYS_VAULT_KEY`, `OBYS_PUBLIC_BASE_URL`, `CLOBE_OAUTH_REDIRECT_URI`, `CLOBE_STORE_DATABASE_URL`. 그 외 이름·빈 값은 거부.
- 같은 이름이 이전 환경에 있으면 덮어쓴다. 파일이 없으면 동작은 예전과 같다.
- 값은 저장소·스크립트·로그에 나오지 않는다(테스트가 출력에 값이 없음을 확인).

이 훅은 되돌려도 다른 기능에 영향이 없다(파일이 없으면 무동작).

## 7. 승인 후 실행 순서

각 단계는 앞 단계 확인이 끝나야 다음으로 간다.

1. **배포** — Runner 가 `deploy_acct_app_cafe24.sh` 로 릴리스 SHA 배포. 이때 백업(pg_dump) → 마이그레이션 3개 중 미적용분 적용 → 후보 → cutover → 5분 관찰이 자동으로 돈다.
2. **GRANT 확인** — acct-pg 에서 읽기로만:
   `SELECT has_table_privilege('acct_business_runtime_r5', 'public.'||t, 'SELECT,INSERT,UPDATE') FROM unnest(ARRAY['obys_clobe_company_link','obys_clobe_collection_lease','obys_clobe_collection_run','obys_clobe_collection_state','obys_clobe_item','obys_clobe_ledger_entry','clobe_mcp_oauth_state','clobe_mcp_connection','clobe_mcp_tools']) t;` 전부 `t`, `clobe_mcp_oauth_client` 는 `SELECT,INSERT` 만. 기존 `obys_clobe_company_link` 5건(언니냉면 등)이 그대로인지도 본다.
3. **키 주입** — §8 절차. 같은 파일에 `OBYS_PUBLIC_BASE_URL=https://fb.newtalk.kr` 도 넣을 수 있다(기본값이 같아 생략 가능). 파일을 만든 뒤 **다시 배포(같은 SHA 후보 재생성)** 로 후보 컨테이너가 환경을 읽게 한다. 기동 로그에 `vault_key_configured source=OBYS_VAULT_KEY enabled=True` 가 보여야 한다.
4. **CEO OAuth 재연결** — CEO 가 fb.newtalk.kr 에 관리자로 로그인해 `POST /api/v1/integrations/clobe/reauth`(상태가 `not_connected`) 로 인가 URL 을 받아 클로브에서 동의한다. 리디렉트는 `https://fb.newtalk.kr/api/v1/integrations/clobe/oauth/callback` 이고 클라이언트는 이 URI 로 새로 동적 등록된다(contabo116 client_id 재사용 없음). `GET …/status` 가 `connected`, `POST …/verify` 가 회사 수를 돌려주는지 확인.
   - **fb.newtalk.kr 경로 확인 필요:** 콜백 `/api/v1/integrations/clobe/oauth/callback` 이 contabo116 nginx → 카페24 apache → 앱으로 지나가는지 이 세션에서는 확인하지 못했다(`/api/v1/auth/*` 가 지나가는 같은 경로라 통과할 가능성이 높다). 4단계 전에 `curl -s -o /dev/null -w '%{http_code}' 'https://fb.newtalk.kr/api/v1/integrations/clobe/oauth/callback'` 이 401/404 가 아니라 400(앱이 응답) 인지 본다.
5. **언니냉면 1개월 shadow(미리보기) 수집** — `POST /api/v1/obys-collections/companies/{clobe_company_id}/runs` 에 `{"mode":"shadow","period_start":"<1개월 전>","period_end":"<오늘>"}`. 언니냉면 clobe 회사 ID 는 `34Z94VTurI79xxWyAKq4H`(`biz-eonni-naengmyeon` 에 linked). `mode` 기본값이 `live` 이므로 **반드시 `shadow` 를 명시**한다. 한 회사·최근 1개월만.
6. **결과 검토** — 항목 수·중복·오류 코드(`last_error_code`), `obys_clobe_collection_run` 상태, 원장 미반영을 확인하고 CEO 에게 보고. 확정 수집은 별도 승인.

## 8. 카페24 전용 `OBYS_VAULT_KEY` 생성·주입 (절차만 — 값은 이 문서·저장소·채팅에 남기지 않는다)

원칙: contabo116 의 `VAULT_ENCRYPTION_KEY`·토큰·`oauth_client` 값은 옮기지 않는다. 카페24 키는 카페24 에서 만들고 거기서만 쓴다. R-KEY: `.env`/환경 파일 경유만, 소스·compose·yaml 에 쓰지 않는다.

```bash
# 카페24 (server-114), root. 값은 화면에 출력하지 않는다.
umask 077
KEY=$(python3 -c 'from cryptography.fernet import Fernet; print(Fernet.generate_key().decode())')
printf 'OBYS_VAULT_KEY=%s\n' "$KEY" >> /root/acct-app-extra.env
unset KEY
chown root:root /root/acct-app-extra.env && chmod 600 /root/acct-app-extra.env
stat -c '%a %U' /root/acct-app-extra.env            # 600 root
grep -c '^OBYS_VAULT_KEY=' /root/acct-app-extra.env  # 1 (값 출력 금지)
```

- 이미 `OBYS_VAULT_KEY` 가 r17 환경에 있으면(오비서 비밀번호관리자 분리로 주입했다면) **새 키를 만들지 말고 그 값을 그대로 쓴다.** 키를 바꾸면 기존 vault 암호문(`e2e_credentials`)이 풀리지 않는다. 확인은 값이 아니라 존재만: `docker inspect -f '{{range .Config.Env}}{{println .}}{{end}}' acct-app-candidate-r17 | cut -d= -f1 | grep -x OBYS_VAULT_KEY`.
- 키 백업은 CEO 가 지정한 비밀 저장소에만 둔다. 잃으면 클로브 토큰은 복구되지 않고 재연결(4단계)로 해결한다(토큰만 잃는다).
- 키 회전은 `docs/operations/VAULT_KEY_ROTATION_RUNBOOK.md`(AADS 용)와 다르다 — 오비서는 단일 키라 회전하면 재연결이 필요하다.

## 10. 남은 위험

- SQL 을 실제 Postgres 에 돌려 보지 못했다 → §7 단계 2 에서 확인.
- 콜백 경로의 프록시 통과는 미확인 → §7 단계 4 사전 점검.
- `clobe_mcp_oauth_state` 의 만료 행은 지우는 코드가 없다(기존 동작과 동일, DELETE 권한도 주지 않았다). 양이 늘면 소유자 역할의 별도 정리 작업이 필요하다.
- 역할 이름(`r5`) 고정. 회전 시 새 GRANT 마이그레이션 필요.
- contabo116 의 클로브 access 토큰은 10-06 18:54 KST 에 만료됐다. 본체 쪽 재연결은 이 작업 범위 밖이다.
