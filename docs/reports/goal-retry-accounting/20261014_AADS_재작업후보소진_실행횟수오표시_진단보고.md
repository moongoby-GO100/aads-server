## 1. 결론

"재작업 후보 2회 소진 — 사람이 확인해야 한다"는 문구는 **재작업을 2번 실행했다는 뜻이 아니다.** 코드가 세는 것은 "재작업 후보로 올린 제안(카드·대기열) 건수"이고, 러너 시작이나 모델 호출은 세지 않는다. M9에서는 실행이 한 번도 없었다.

소진을 만든 원인은 세 겹이다.

| # | 원인 | 확정도 |
|---|---|---|
| A | 한도 계산이 실행이 아니라 제안을 센다 | 확정(소스 `goal_failure_retry.py:142`) |
| B | 같은 대기열 ID가 15분 중복막이에 걸려 재사용되고, 재사용도 새 후보로 합산된다 | 소스 + 시각 13/13 일치. 당시 실행 로그 직접 확인은 못 함 |
| C | 자동 재작업 지시문이 **실패한 job 자신의 id**를 담고 있어, 2026-10-01 도입된 stale 가드가 배달 직전에 "이미 종결된 job"으로 보고 건너뛴다 | 확정(DB 45/45) |

C는 기존 가설에 없던 새 사실이고 가장 큰 영향을 준다. 이 가드가 켜진 뒤로 자동 큐 방식 재작업 후보는 한 건도 실행되지 않았다.

## 2. 실측 근거

### 2.1 운영 슬롯과 저장소 코드 일치

- `aads-server`, `aads-server-green` 두 슬롯 모두 이미지 `aads-server:1b74c6c2ae75`이고 저장소 HEAD는 `1b74c6c2`.
- `goal_failure_retry.py`, `next_step_proposals.py`, `chat_service.py`, `goal_manager.py` 네 파일의 md5 앞 12자리가 저장소와 두 슬롯에서 모두 같다(`64902941bc87`, `9ad57cc1b7af`, `01ab599e1d39`, `c697d4175eef`).
- 따라서 운영 코드와 저장소 코드는 **같다.** 차이로 설명되는 현상이 아니다. (해시만 대조했고 환경변수·시크릿은 읽지 않았다.)

### 2.2 한도 계산 소스 (읽기 전용 확인)

- `_MAX_RETRY = min(2, max(0, int(GOAL_FAILED_LINK_RETRY_MAX 기본 2)))` — `goal_failure_retry.py:16`.
- `ensure_retry_candidate`는 마일스톤 전체 `retry_candidates`에서 `bool(card_id) or not failed`를 합산해 `>= _MAX_RETRY`이면 `retry_exhausted`와 소진 문구를 쓴다 — `:142-151`. 실패 계보(`failed_task_id`)로 나누지 않고, 고유 `card_id`로 중복을 걷지도 않는다.
- `_refresh_candidates`는 만료·거절·종료된 후보를 `failed=true`로 바꾸지만 `card_id`는 지우지 않는다 — `:51-88`. 그래서 실패 처리된 후보가 한도를 계속 소비한다(`bool(card_id)`가 참).
- 카드가 만들어지지 않은 제안 실패는 별도 규칙이다: 10분 backoff, 같은 실패 계보당 실패 3회 — `:134-139`. 이것을 소진 한도(2)와 섞으면 안 된다.
- `AUTO_REWORK_ROUND:n/m`(`pipeline_auto_rework.py`), 러너 `max_cycles`(`pipeline_runner_service.py:635`)는 **다른 카운터**다. 이 문서의 "2회"와 무관하다.

### 2.5 원인 B의 근거 (중복 큐 집계)

- `enqueue_next_step_reaction`은 같은 `dedupe_key`의 가장 최근 행이 `reuse_seconds=900` 이내면 **상태와 무관하게** 그 행을 돌려준다 — `chat_service.py:12454-12468`. `skipped_stale`·`failed`인 죽은 행도 그대로 재사용된다.
- `propose`는 반환된 `queue_id`를 `queued=true`로 취급해 `auto`에 넣고(`next_step_proposals.py:442-444`), `ensure_retry_candidate`는 그것을 새 `card_id`로 후보에 기록한다 — `goal_failure_retry.py:197-199`. 재사용 여부(`created=false`)는 후보에 전달되지 않는다.
- 후보 1이 failed 처리된 뒤 10분 backoff가 풀리는 시점(≥600초)이 대기열 생성 후 900초 안이면 같은 큐 ID가 다시 후보가 된다.
- 실측: 중복 card_id 13개 그룹 전부 두 번째 후보 시각이 큐 생성 후 **623~744초**로 900초 안이다(13/13).
- 승인 카드 방식(`agent_permission_requests`)은 재사용 조건이 `decision='pending' AND expires_at>now()`라서, 살아있는 카드만 재사용되고 죽은 카드는 새로 만들어진다. 중복 card_id 13건이 전부 auto_queue 종류라는 것과 일치한다.
- 미확정: 당시 `propose`의 `created=false` 응답 로그는 확인하지 못했다. 소스와 시각 분포는 일치하지만 로그로 닫은 증거는 아니다.

### 2.6 원인 C의 근거 (stale 가드와 충돌)

- 재작업 제안의 제목과 본문에 `실패한 job id: {failed_task_id}`가 들어간다 — `goal_failure_retry.py:183-191`.
- 배달 직전 `annotate_or_skip`은 본문의 모든 `runner-xxxx`가 종결(`done/error/rejected_done/cancelled`)이면 `stale_jobs`로 건너뛴다 — `deferred_reaction_freshness.py:58-62`, 호출은 `chat_service.py:12604-12631`. 재작업 지시문이 가리키는 job은 정의상 이미 실패한 job이라 **항상 종결**이다.
- 가드 도입 커밋 `97e73863`(2026-09-30). 2026-10-01 이후 생성된 auto_queue 재작업 후보 큐는 `skipped_stale` 45건이고, 같은 날 먼저 생성된 `completed` 2건은 가드 배포 이전 생성으로 추정한다(배포 시각은 직접 확인하지 않았다). 45건 모두 `error_message`가 `stale_jobs: <실패 job>=<그 job의 현재 상태>`와 정확히 같다(45/45).
- 즉 2026-10-01 이후 auto_queue 경로의 재작업 후보는 만들어지자마자 버려졌다. 후보는 합산되는데 실행은 불가능한 상태다. 승인 카드 경로가 같은 가드를 타는지는 이번에 확인하지 않았다(미확정).

### 2.7 별개 사례: 제출 단계 범위 파서 오판 (실행 실패와 구분)

- 이 작업의 최초 제출 `runner-050876df`·`runner-262fd3e4`는 DB상 둘 다 `status=error`, `phase=error`, `started_at` 없음, 생성 시각 동일(11:40:48), `error_detail` 빈 값이다.
- `_SCOPE_TOKEN_RE`는 ASCII 문자만 허용한다(`pipeline_runner.py:322-325`). 한글 파일명 토큰은 `_parse_scope_token`에서 None이 되어 선언 전체가 비명시 모드(legacy)로 되돌아가고, 읽기·금지 문구가 쓰기로 오판되어 가짜 의존이 생긴다(`_parse_write_scope`의 `error` 경로). 운영자가 부여한 정황이고, 소스의 ASCII 제한과 job 행으로 두 사실은 확인했다.
- 이 사례는 **재작업 실패도 모델 시작도 아니다.** 실행 한도 회계에서 "시작 전 제출 거절"로 분류해 차감하지 않아야 한다. 코드는 수정하지 않았다.

## 3. 사용자 영향

1. 소진 문구가 마일스톤이 `completed`가 된 뒤에도 남는다(52건 중 6건). 사람은 "2번 해봤는데 안 됐다"고 읽지만 실제로는 0번인 경우가 있다.
2. 비완료 마일스톤 소진 문구가 목표를 `blocked`로 묶는다(14개 목표). 실행 근거 없이 사람 개입을 요구한다.
3. 후보가 이미 실행 불가능(원인 C)인데도 사용자 화면에는 "후보 N개"로 보인다.
4. 같은 실패를 가리키는 중복 후보가 합산되어 계보 하나가 한도 전부를 쓴다. 다른 계보의 실패가 같은 마일스톤에 생겨도 재작업 기회를 잃는다.

## 4. 개선 우선순위 (구현 미실행 — 승인 후 별도 작업)

### P0
- **P0-1 지시문과 stale 가드 충돌 해소.** 재작업 지시문에서 실패 job id를 "대상 job"으로 판정하지 않게 한다(가드가 `RETRY_OF_LINK`·`실패한 job id` 줄의 id를 제외). 해소 전에는 auto_queue 경로가 구조적으로 작동하지 않는다.
- **P0-2 제안 한도와 실행 한도 분리.** 제안은 기존 backoff·3회 제한을 유지하고, 실행 한도(기본 2)는 실제 러너 시작만 센다. 대기·claim·의존성 대기·cancelled·skipped·expire·승인만은 차감하지 않는다.
- **P0-3 시작 시 원자 차감.** 고유 key(러너 job id)당 한 번만 차감하고 중복 claim은 한 번으로 센다.

### P1
- **P1-1 중복 큐 재사용 정정.** 재사용된 큐가 종결(`skipped_stale/failed/…`)이면 새 후보로 세지 않거나 새 dedupe_key로 새 큐를 만든다. 고유 card_id/queue_id로 센다.
- **P1-2 실패 계보별 독립 예산.** `failed_task_id`별로 센다.
- **P1-3 유효 승계 선검사.** 활성 후속 job이 있으면 재제출하지 않고(`already_active`), 완료된 승계가 있으면 소진 판정을 건너뛴다.
- **P1-4 완료 마일스톤의 차단 문구 격리.** 완료 마일스톤의 소진 문구는 현재 blocker가 아니며 이력 영역으로 옮긴다. 증거 삭제는 하지 않는다.
- **P1-5 사용자 문구.** 고유 후보 · 실제 실행 · 남은 한도 · 다음 행동을 함께 표시한다. 예(M9): "고유 후보 1건(대기열 만료로 미실행) · 실제 재작업 실행 0/2 · 남은 한도 2 · 다음 행동: 승계 job runner-9b9c2cb6 완료로 종료".
- **P1-6 제출 단계 거절 분리.** 범위 파서 거절·시작 전 오류는 실행 한도에서 제외하고 사유를 표시한다.

### 하지 말 것
- 상한(`GOAL_FAILED_LINK_RETRY_MAX`)만 올리는 것: 원인 B·C를 가리고 전역 anti-loop을 약화한다.
- 실패 증거(`retry_candidates`, 큐 행, 오류 문구) 삭제.

## 6. 수용 테스트

세부는 짝 문서 `aads-goal-retry-accounting-acceptance`에 있다. 요지: 같은 큐 ID 2회 → 고유 후보 1·실행 0 / stale 취소 → 0 / 승인만 → 0 / 단일 실제 job 모델 시작 → 1 / 중복 claim → 1 / 다른 failed_task 계보 독립 예산 / 활성 후속 발견 → 재제출 0 / 완료 마일스톤 현재 blocker 0·이력 보존 / 테넌트 분리. **새 테스트 코드는 작성하지 않았다.**

## 7. 오류 사전 (R-ERRBOOK)

- 조회: `error_book.py match`는 이 증상에 맞는 항목이 없었다. 지시서가 언급한 `deploy.autoheal_handoff_read_as_failure`는 별개 원인이다.
- 확정한 원인 A·C를 `goal.retry_candidate_counted_as_execution`으로 등록한다. **prevention과 이번 수정 상태를 구분한다: 분석만 수행, 코드 미수정, 수정 커밋 없음.** B는 로그 미확인이라 사전에 "정황"으로만 남기고 원인으로 단정하지 않는다.
- 이후 코드 수정이 들어가면 그 커밋으로 fix 필드를 채운다.
