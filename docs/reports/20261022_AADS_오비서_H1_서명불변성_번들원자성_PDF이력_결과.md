## 5. 한계 (솔직하게)

- **실제 Postgres 에서 SQL 을 실행하지 않았다.** 이 환경에는 로컬 Postgres 가 없고 운영 DB 는 건드리지 않는다. DB 경로 테스트는 asyncpg 인메모리 대역(FakePg/FakeConn)으로, 조건부 UPDATE 의 의미와 트랜잭션 롤백을 흉내 낼 뿐 **SQL 문법·`jsonb_set`·COALESCE/CASE 의 실제 동작은 검증하지 못했다.** 승인 후 Runner 빌드 검증 대상이며, 스테이징 DB 에서 서명·재생성 1회씩 확인하는 것을 권한다.
- PDF 생성은 설계대로 커밋 **후** best-effort 다. 서명 트랜잭션은 UPDATE + 감사까지만 감싼다.
- 계약 감사는 파일 모드에서 별도 로그(`contract_audit_logs`), DB 모드에서 `yeoljeong_audit_logs` 로 간다. `contract.delivered` 감사는 작업지시 범위 밖이라 추가하지 않았다.
- F-11(옛 코드 드레인)과 DB 트리거는 의도적으로 미반영. 마이그레이션 파일도 없다. 트리거는 드레인 후 별도 작업이다.
- 레거시 서명본 중 스냅샷이 없는 행은 다운로드·재생성 시 `snapshot_missing` 으로 409 가 된다. 운영 데이터에 그런 행이 있는지는 확인하지 못했다(운영 DB 미접촉).

## 교훈

- 보상 쓰기(복구 루프)는 실패했을 때 가장 취약하다. 원자 커밋 하나로 바꾸면 "복구 실패" 자체가 사라진다.

- 무결성 검사를 추가할 때는 같은 해시 제외 목록이 정상 재생성 이력까지 막지 않는지 먼저 확인한다(T-H).
