## RESULT — 반려 7건 대응

1. **turn key 호환**: `_turn_key` 본문은 바꾸지 않았다. d3254e03(seq 8)와 c5973979(seq 10)의 키는 서로 다르다. 단일 사용자 원문과 생성 본문·제목이 모두 같고 tenant/project/session/goal/milestone이 같으며 composer가 없을 때 기존 초안·판본을 반환한다. 기존 저장 키·원문 출처를 덮어쓰지 않는다. 같은 키에서 생성 본문이 달라지는 의도적 재생성은 기존 동작대로 판본을 추가한다. 다른 ID로 내용/맥락/생성 결과가 달라지거나 composer를 추가하면 별도 초안이다. 사람이 동일 원문을 의도적으로 다시 보냈다는 사실만으로 의도를 추론할 수는 없다. 완전히 동일 입력·동일 생성 결과는 중복으로 처리한다. 사용자 확인 의도 자체를 판정했다고 주장하지 않는다.
2. **metadata 화이트리스트**: create/update가 공통 helper로 세 키만 분류에서 가져온다. 기존 turn_kind 이름·문자열 형태를 보존하고 decisions/evidence가 없거나 null이면 키를 생략한다. 기존 출처 metadata(source_message_ids, create의 composer_draft)는 유지한다. classification 전체를 판본에 펼치지 않는다.
3. **update 방어**: `_serialize_row(current)` 호출 없이 분류 JSON을 한 번 해석한다. classification 필드 누락, None, 빈 객체, 잘못된 JSON, JSON null, list, 일부 null 키를 테스트했다.
4. **fixture 조회**: 모든 특정 턴은 seq 조회 함수로 선택한다. 코퍼스 ID/label/기대값 파일은 수정하지 않았다. MD5는 전체 원문의 식별값이며 발췌 text_head의 해시로 주장하지 않는다.
5. **실DB 스키마**: 테스트는 사전 migration된 *_test DB만 사용한다. 자체 schema 생성·migration 이어 붙이기 없음. 임의 tenant/session/workspace/goal로 격리하고 원래 메시지 ID/시간/발췌를 삽입한다. 조회·정리는 생성한 tenant에 한정한다. 원본 ID가 이미 존재하면 덮어쓰지 않고 실패한다. 기존 참조 테스트의 URL 설정 및 *_test 검사/skip 경계를 따른다.
6. **실DB 4건**: corpus는 13턴과 중복 쌍·출처·목표 스냅샷, concurrency는 서로 다른 원본/재전송 ID 5요청의 단일 초안·판본, update_trace는 1/2/3 판본의 출처·결정·근거 및 승인 이벤트, binding은 다른 tenant/session/goal 거절을 검증한다. 생성만 fallback으로 대체한다. PermissionError/OSError/연결 timeout은 skip이며 운영 접속으로 우회하지 않는다. SQL/스키마/assert 오류는 실패로 남긴다. HTTP 인증/상태 코드 검증은 하지 않는다.
7. **검증/핸드오버**: 아래 실제 실행 결과와 DB 기록 시도를 구분한다. HANDOVER.md는 수정하지 않았다.
