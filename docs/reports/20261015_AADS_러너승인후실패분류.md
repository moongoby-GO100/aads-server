  PRD 의 "승인 후 실패 31건" 과 5건 차이가 난다 — PRD 집계 시점 이후 늘어난 건수로 보이나 확인하지 못했다.
- 분류 키: `phase` + `error_detail` (40자 SHA 는 `<sha>` 로 치환해 묶음). 승인~실패 소요는 `updated_at - approved_at`.

## 관찰

- stale_base 계열(순위 1·2)이 20건으로 전체 실패의 56%다. 두 phase 는 같은 원인이고, 러너가 AADS 는 `deploy_isolated_push_state` 로, 그 외는 `push_stale_base` 로 기록한 차이다 (`scripts/pipeline-runner.sh` 의 `classify_push_state`).
- stale_base 는 승인 후 11~14초 만에 드러나는 건도 있어, 승인 버튼을 누르기 전에 같은 조상 관계 판별을 하면 막을 수 있다.
- 순위 3 이하는 배포(build_fail)·락 단계 결과라 승인 전에는 알 수 없다. 사전검증은 이 중 `deploy_lock_fail` 에 대응하는 "같은 프로젝트 배포 진행 중"만 경고(warn)로 보여 준다.
- 이 조회로는 PRD 의 "승인 직후 커밋 단계 실패 17건"을 따로 가려내지 못했다 (커밋 단계 phase 값이 위 표에 없다). 17건의 근거는 확인하지 못했다.

## 사전검증 반영

- `base_freshness` — 러너 커밋이 origin/main 위에서 fast-forward 가능한지, 아니면 origin/main 이 같은 파일을 건드렸는지 판별한다. 겹치는 파일이 있으면 `fail`(러너의 자동 rebase 가 겹침이 있으면 멈추는 것과 같은 기준), 겹침이 없으면 `warn`(자동 rebase 가능).
- `deploy_in_progress` — 같은 프로젝트에 `deploying` 인 다른 작업이 있으면 `warn`.
- 한계: git 판별은 API 프로세스가 볼 수 있는 저장소의 로컬 `origin/main` 기준이며 네트워크를 쓰지 않는다. 운영 컨테이너 `aads-server` 에는 `/root/aads/aads-server/.git` 이 마운트되어 있지 않다 (`fatal: not a git repository` 확인). 이 경우 DB 근사(같은 프로젝트에서 이 작업 시작 이후 완료된 다른 작업이 같은 파일을 바꿨는지)로 `warn` 만 낸다 — 증명이 아니므로 `fail` 로 올리지 않는다.
