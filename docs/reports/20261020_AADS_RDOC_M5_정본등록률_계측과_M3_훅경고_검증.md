## 3. 지표 정의 (spec 16항이 정본)

- **A (문서 단위)**: 분모 = 그날(KST) 새로 추가된 `docs/reports/**/*.md`. 분자 = 같은 tenant·project 의 revision 에 `source_path` 와 `content_hash` 가 모두 일치. 경로만 같으면 `path_only` 로 따로 센다. 제외 사유(이름 바꿈, 재추가, 같은 내용 사본, 빈 파일, md 아님)는 행에 개수로 남긴다.
- **B (게이트 ok 비율)**: `canonical_gate_events` 의 ok / (ok+missing_canonical+unknown). A 와 별도 행이다.
- **분모 0 → N/A** (비율 NULL, status=not_applicable). 수집하지 않은 날은 `not_collected` 이며 0% 도 성공도 아니다.
- **품질**: on_time / late_backfill / partial_day / unverified_source. 7일 연속은 on_time 만 센다. `on_time` 행은 늦은 재수집이 덮어쓰지 않는다. 기존 행의 `first_collected_at` 은 보존한다.
- **멱등**: 키 (tenant_id, project_key, kst_date, metric) 의 `ON CONFLICT DO UPDATE`.

## 5. M3 — 실제 staged fixture 로 확인한 것

임시 저장소에 훅의 정본 게이트 블록만 설치하고 git 이 직접 훅을 부르게 했다(`git worktree add`, `git commit` 은 pytest tmp 경로 안에서만 썼다).

- 보고서 md 커밋: 노란 경고 1회, CGv1 9칸 로그 1줄, 커밋 성공.
- png·`docs/specs`·루트 `reports/`: 경고 없음. `docs/design`: 여전히 경고.
- 링크드 워크트리 커밋: 로그가 공용 `.git` 에 남고, 워크트리를 지워도 남는다.
- 스크립트 없음 / 스크립트 rc=7: 경고하고 커밋은 성공.
- `CANONICAL_GATE_MODE` 가 shadow·enforce·임의값: 미등록 문서로 커밋이 막히지 않는다. off: 무음.
- 경고 모드를 유지했다. 미등록 때문에 차단으로 올리지 않았다.

M3 의 한계:
- 운영 체크아웃의 `.git/hooks/pre-commit` 설치본은 **갱신하지 않았다**(공용 `.git/hooks` 를 건드리지 않음). 반영 전까지 설치본 동기화 테스트가 호스트 체크아웃에서 실패할 수 있다. 반영: `cp scripts/hooks/pre-commit .git/hooks/` (별도 승인).
- 호스트 체크아웃에는 `scripts/canonical_gate_commit.py` 가 없었던 것(이전 결함 1)이 origin/main 반영 전까지 그대로다.
- DB 의 `commit` 진입점 이벤트가 0건인 것은 훅이 DB 에 닿지 않는 설계라서 정상이다. 훅 경고의 근거는 로컬 로그와 이 fixture 테스트이다.

### P1-1 최초추가 판정 — 재현과 교정

- 재현(임시 git): 10-01 최초추가 → 10-18 삭제 → 10-19 같은 경로 재추가. `collect_new_reports(since=10-19)` + `classify_new_files` 는 docs=1, excluded=[] 를 냈다(실제 실행으로 확인). 원인: `--since` 이후 A 이력만 읽어 `seen_paths`·`seen_content` 에 과거가 없었다.
- 교정: `collect_report_history` 가 전체 이력을 읽고 `classify_new_files(…, since=)` 가 전체 이력으로 판정한 뒤 출력만 창으로 자른다. 같은 날짜는 하루 창과 여러날 창에서 같은 분모·제외 사유를 낸다. 동일내용은 git blob id 로 대조해 과거 본문을 읽지 않는다.
- 비용: git 호출은 파일 수와 무관하게 5회(`rev-parse`, `log --raw`, `cat-file --batch-check`, `ls-tree`, `cat-file --batch`). 무제한 `git show` 반복을 없앴다(`test_history_does_not_spawn_git_show_per_file`). 이 저장소 기준 docs/reports 추가 이력은 192건이고 `git log` 는 약 0.2초였다. 본문은 창 안 문서와 그 HEAD 본만 읽는다.
- 얕은 clone 은 최초추가를 알 수 없으므로 예외로 실패시킨다(`test_shallow_clone_fails_closed`). 신규로 오인하는 것보다 수집 실패가 낫다.
- 유지한 의미: 이름 바꿈은 신규가 아님, 같은 경로 재추가·같은 내용 사본·빈 파일·md 아님 제외, 분모 0 → N/A.
- 회귀 테스트(실제 git): 재추가가 창 시작 후 보일 때 `readded_path` 로 제외 / 하루 창·1일 창·여러날 창에서 같은 날짜 결과 일치(재추가·과거와 같은 내용 사본·진짜 신규 혼합) / git 호출 수 상한 / 얕은 clone 실패.

### P1-2 tenant 검증 — 재현과 교정

- 재현: fake trusted=11111111-…, requested=22222222-… 에서 `report()` 가 다른 tenant 의 `DAILY_ROWS_SQL` 을 2번 호출하고 성공(rc=0)했다(교정 전 신규 테스트가 그대로 실패). `collect()` 의 검사 `trusted and tenant != trusted` 는 trusted 가 비면 건너뛰었다.
- 교정: `resolve_trusted_tenant(trusted, requested)` 공용. 신뢰 tenant 가 있고 UUID 이며 요청과 같을 때만 통과, 요청이 없으면 신뢰 tenant 사용. 없음·불일치·UUID 아님은 지표 SELECT·쓰기 0회로 실패(종료코드 1). `--tenant-id` 형식 오류는 DB 연결 전에 거부(빈 문자열 포함). 대소문자만 다른 같은 UUID 는 정규화해 통과.
- DB 읽기 전용 연결은 tenant 경계를 대신하지 않는다고 보고 별도 검증으로 두었다.
- 테스트: 실제 CLI 진입점 `main()` 을 거쳐 가짜 DB 연결의 SELECT·쓰기·연결 횟수를 센다. 불일치 / trusted 없음+요청 있음 / 둘 다 없음 / trusted 가 UUID 아님 / 잘못된 UUID 4종 / collect --apply 불일치 3종(쓰기 연결을 열지 않음) / 정상 tenant 의 report·dry-run·apply 가 trusted tenant 로만 읽고 쓴다.
- 지표 B 한계 유지: `canonical_gate_events` 에 tenant 열이 없어 project 단위이며 행의 `detail.tenant_scope` 와 spec 16.2 에 적었다. 내부 tenant 행에 저장돼도 그 tenant 의 개인 지표로 보고하지 않는다.
