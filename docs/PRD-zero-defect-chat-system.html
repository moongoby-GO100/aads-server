3. 근본 원인 분석

핵심 결론

반복 회귀의 근본 원인은 단일 코드 버그가 아니라 구조적 방어막의 부재입니다. 12,000줄+ 단일 파일에 테스트 0건, CI 게이트 없음, 프론트-백엔드 이중 필터 — 이 3가지가 동시에 존재하면 어떤 수정이든 기존 기능을 파손할 확률이 높습니다.

3.1 구조적 원인 상세

원인 1: 초거대 단일 파일 (God Object)

현상: page.tsx 12,484줄에 366개 함수가 한 파일에 집중. 채팅의 모든 로직(상태관리, SSE 파싱, 메시지 렌더링, 필터링, resume, 아티팩트, 파일 업로드, 설정 등)이 하나의 React 컴포넌트에 응축.

영향: 한 줄 수정해도 366개 함수 중 어디에 영향을 주는지 예측 불가. 코드 리뷰로도 side effect를 잡기 어려움.

근거: Git 이력상 7일간 27회 수정 중 핫픽스/롤백이 7회 — 수정의 26%가 이전 수정의 부작용을 고치는 데 소모됨. [Git 조회]

원인 2: 자동 테스트·CI 게이트 전무

현상: 프론트엔드에 jest/vitest/playwright/cypress 미설치, 테스트 파일 0건, Dockerfile에 build 단계만 존재.

영향: 어떤 변경이든 기존 기능 파손을 배포 전에 잡을 방법이 전혀 없음. "빌드 성공 = 정상"이라는 착각에 의존.

근거: find로 *.test.*, *.spec.* 검색 결과 프로젝트 소스에 0건, node_modules 내부만 존재. package.json에 test 관련 의존성 없음. [코드 확인]

원인 3: 프론트-백엔드 이중 필터, 공유 계약 없음

현상: 메시지 숨김 판정이 두 곳에서 독립적으로 수행됨.

  • 백엔드: _visible_message_filter (chat_service.py:8225) — SQL intent whitelist
  • 프론트: isHiddenSystemChatMessage (page.tsx:539) — JS intent list

영향: 새 intent 추가 시 한쪽만 반영 → 시스템 메시지가 사용자에게 노출되거나, 정상 AI 응답이 숨겨짐. interrupted_partial 버블 소실이 정확히 이 패턴.

원인 4: SSE 이벤트 핸들러 3중 중복

현상: stream_start/이벤트 파싱 로직이 page.tsx 내 3곳(line 4732, 7308, 8650)에 각각 독립 구현.

영향: 한 곳만 수정하면 나머지 2곳과 동작 불일치 → 특정 시나리오(새 세션/재연결/백그라운드 완료)에서만 "멈춤" 발생.

원인 5: Resume 실패의 무통보 흡수

현상: ResumeFencedOut 발생 시 상태만 pop하고 종료, SSE 클라이언트로 push되지 않음. ResumeAttemptLimitExceeded도 범용 except로 흡수.

영향: AI가 "멈춘 것처럼" 보이지만 로그에만 남음. 프론트 폴링이 발견해야만 노출되는데, 폴링 타이밍 불일치 시 무기한 "생성중" UI로 방치.

근거: chat_turn_executions에서 resume_exhausted 95건 확인. [DB 조회]

원인 6: 채팅 계층 모니터링 공백

현상: error_log 테이블에 채팅 관련 에러가 0건. watchdog 항목(service_down_http_health 등)만 존재.

영향: 채팅 장애가 발생해도 중앙 에러 로그에 집계되지 않아, 사전 감지·추이 분석·알림이 불가능. CEO가 직접 발견해서 보고해야만 인지됨.

4.2 안전한 분할 전략 (Strangler Fig Pattern)

핵심: 한 번에 전체를 재작성하지 않습니다. 기존 page.tsx를 유지하면서 하나씩 모듈을 추출하고, 추출된 모듈은 기존 코드와 동일하게 동작하는지 테스트로 검증한 후 교체합니다.

  1. Step 1: 타입 추출 — types/chat.ts에 인터페이스/타입을 먼저 분리. 기존 코드는 import로 교체. 동작 변경 없음.
  2. Step 2: 순수 함수 추출 — chatFilters.ts, sseEventSchema.ts 등 상태에 의존하지 않는 로직을 먼저 분리. 단위 테스트 즉시 작성 가능.
  3. Step 3: 커스텀 훅 추출 — useChatStream, useChatMessages 등을 순서대로 추출. 각 추출 후 통합 테스트로 기존 동작 검증.
  4. Step 4: 렌더링 컴포넌트 추출 — MessageBubble, MessageList, Composer 등을 분리. Storybook 또는 스냅샷 테스트로 렌더링 검증.
  5. Step 5: page.tsx를 조합 레이어로 — 최종적으로 page.tsx는 ~300줄의 조합 컴포넌트만 남김.

5.3 SSE 스트리밍 E2E 테스트 (Playwright)

SSE 테스트가 특별한 이유

일반 HTTP 요청과 달리 SSE는 연결이 열린 상태에서 서버가 점진적으로 데이터를 보냅니다. Playwright의 page.evaluate()로 EventSource를 감시하거나, page.route()로 SSE 응답을 모킹하여 테스트합니다.

핵심 E2E 시나리오

#시나리오검증 포인트
1메시지 전송 → SSE 스트리밍 → 완료버블 생성, 스트리밍 텍스트 표시, 완료 표시
2스트리밍 중 연결 끊김 → 재연결기존 텍스트 보존, 이어서 스트리밍
3Resume 실패 → 사용자 알림"다시 시도" 버튼 표시, 에러 메시지
4시스템 메시지 필터링시스템 intent 숨김, AI/CEO 메시지 표시
5세션 전환 → 메시지 로드이전 세션 메시지 정상 표시

SSE 모킹 전략

// Playwright SSE 모킹 예시
await page.route('**/api/v1/chat/*/stream', async route => {
  const body = [
    'event: stream_start\ndata: {"execution_id":"test-1"}\n\n',
    'event: content_delta\ndata: {"text":"안녕하세요"}\n\n',
    'event: stream_end\ndata: {"status":"completed"}\n\n',
  ].join('');
  await route.fulfill({
    status: 200,
    headers: { 'Content-Type': 'text/event-stream' },
    body,
  });
});

5.4 시각적 회귀 테스트 (Visual Regression)

도구: Playwright의 toHaveScreenshot() 내장 비교 기능 또는 Chromatic/Percy 연동

대상: MessageBubble (일반/코드/에러/시스템), ChatComposer (빈 상태/파일 첨부), ArtifactPanel (각 탭)

전략: 각 컴포넌트의 "골든" 스크린샷을 저장하고, PR마다 비교. 차이 감지 시 리뷰어에게 알림.

# --- 목표 Dockerfile (5단계 게이트) ---
FROM node:20-alpine AS deps
COPY package*.json ./
RUN npm ci

FROM deps AS quality-gate
COPY . .
RUN npm run lint          # ① ESLint
RUN npm run typecheck     # ② TypeScript strict
RUN npm run test          # ③ Vitest unit tests
RUN npm run build         # ④ Next.js build

FROM deps AS e2e
COPY . .
RUN npx playwright install --with-deps chromium
RUN npm run test:e2e      # ⑤ Playwright E2E

FROM node:20-alpine AS production
# quality-gate와 e2e 모두 통과해야 여기에 도달
COPY --from=quality-gate /app/.next ./.next
# ...

6.3 deploy.sh 통합

현재 deploy.sh bluegreen은 빌드 성공만 확인합니다. 다음 게이트를 추가합니다:

  1. Pre-build check: npm run lint && npm run typecheck 실패 시 배포 중단
  2. Post-build check: npm run test 실패 시 배포 중단
  3. Post-deploy check: Blue/Green 전환 후 5분 이내 health-check + 핵심 API 응답 검증. 실패 시 자동 롤백.

8.2 Feature Flag 설계

목적: 채팅 UI의 신규 변경을 코드 배포와 기능 노출을 분리하여, 문제 발생 시 롤백 없이 플래그만 끄면 즉시 원복.

// lib/featureFlags.ts
export const CHAT_FLAGS = {
  NEW_MESSAGE_FILTER: 'chat.new_message_filter',    // v2 필터 로직
  RUNNER_BADGE:       'chat.runner_badge',            // 러너 상태 배지
  RESUME_NOTICE:      'chat.resume_failure_notice',   // resume 실패 알림
} as const;

// 사용
const useNewFilter = useFeatureFlag(CHAT_FLAGS.NEW_MESSAGE_FILTER);
const messages = useNewFilter
  ? filterMessagesV2(rawMessages)
  : filterMessagesLegacy(rawMessages);

Flag 저장: chat_feature_flags 테이블 (flag_key, enabled, rollout_pct, updated_by) — API로 실시간 변경 가능.

8.3 자동 롤백 기준

배포 후 5분 이내 아래 조건 중 하나라도 충족되면 자동으로 이전 슬롯으로 복귀:

  • 인터럽트율 > 30% (현재 baseline 대비 2배 이상 급증)
  • SSE 연결 실패율 > 10%
  • API 5xx 응답률 > 5%
  • Health-check 연속 3회 실패

9.1 채팅 계층 전용 메트릭

메트릭수집 방법알림 기준대응

미분류(null) 인터럽트 interrupt_category IS NULL 집계 > 10건/일 분류 로직 보완 알림

9.2 error_log 연동

채팅 계층의 모든 에러를 error_log 테이블에 자동 기록하는 미들웨어를 추가합니다:

  • source = 'chat_service'
  • error_type: resume_exhausted, producer_incomplete, sse_disconnect, filter_mismatch 등
  • context: session_id, execution_id, model, 실행 시간
  • auto_recoverable: resume 가능 여부
