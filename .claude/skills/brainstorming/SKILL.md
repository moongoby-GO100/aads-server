# 구현 전 요구 정리와 대안 비교

만들기 전에 **무엇을 왜 만드는지** 가 정리되어 있어야 한다. 잘못된 것을 정확하게 만드는 것이 가장 비싼 실패다.
이 스킬은 정리 순서와 보고 형식만 안내한다. 파일 쓰기·실행 권한은 주지 않는다.
정리 결과는 응답으로 내거나, 호출한 세션이 가진 권한으로 문서에 남긴다.

## 먼저 판단 — 이 스킬이 필요한가
- 요청에 목적, 범위, 완료 기준이 모두 있고 접근이 하나뿐이면 **건너뛴다.** 바로 `writing-plans` 로 간다.
- 중요한 정보가 빠졌거나 접근이 갈리면 아래를 진행한다.
- 사용자가 이미 "이렇게 해라" 고 정했다면 대안을 다시 열지 않는다. 위험이 있을 때만 한 번 짚는다.

## 1단계 — 이미 있는 것부터 본다 (묻기 전에)
사용자에게 물을 수 있는 것을 코드와 문서에서 먼저 찾는다.
- 비슷한 기능이 이미 있는가 (`Grep`/`Glob`), 있다면 확장인지 신규인지.
- 관련 규칙·설계 문서·오류 사전: `scripts/error_book.py match` 로 알려진 함정이 있는지.
- 확인한 것은 확인했다고, 확인하지 못한 것은 "미확인" 이라고 구분해 둔다.

## 2단계 — 질문은 적게, 구체적으로
- 한 번에 하나의 열린 질문부터 한다. 사용자 자신의 말로 설명하게 한다.
- 알아야 할 것: 무엇이 목적인가, 왜 지금인가, 성공은 어떤 모습인가, **목표 / 비목표 / 실패로 볼 것**, 현재 상태, 써 본 대안과 평가.
- 질문은 이 프로젝트에 맞게 구체적으로 한다. 일반론 질문 목록을 읽어 내려가지 않는다.
- 이미 대화에 답이 있는 것은 다시 묻지 않는다.

## 3단계 — 대안 정리
의미 있게 다른 접근을 **2~3개** 낸다. 각 안마다:
- 한 줄 요약과 동작 방식
- 장점 / 단점 / 위험
- 비용(작업량, 운영 부담, 기존 기능에 미치는 영향)
- 기존 구현과의 관계 — 유지 / 수정 / 신규 / 삭제(사유)

시각적으로 달라지는 선택(화면, 흐름)은 글보다 간단한 도식이나 표가 낫다. 작은 시험 구현(스파이크)으로 불확실성을 줄일 수 있으면 제안한다.

## 4단계 — 권장안 1개 지정 (R-APPROVAL-REC)
대안을 나열하고 끝내지 않는다. **권장안을 하나** 지정한다.
```
## 권장안 (R-APPROVAL-REC)
권장: <안 이름> — <한 줄 이유>
### 권장 사유 (근거)
1. <확인한 사실 또는 측정값, 출처 표시>
2. ...
### 비권장 사유 (안별 한 줄)
- <안>: <이유>
### 승인 시 바뀌는 것
| 파일/시스템 | 변경 |
### 승인 요청
이 안으로 진행해도 되는가. 되돌리는 방법: <...>
```
- 근거에는 **실측한 것과 계산·추정한 것을 구분**해 표시한다. 확인하지 않은 수치를 사실처럼 쓰지 않는다.
- 사용자만 답할 수 있고 답에 따라 설계가 바뀌는 것은 "결정 필요" 로 따로 모은다. 합리적 기본값으로 정해도 되는 작은 것은 기본값을 정하고 알린다.

## 5단계 — 되돌려 말하기
정리한 내용을 목적·범위·비범위·제약·선택한 안 순으로 짧게 요약해 맞는지 확인받는다. 승인 전에는 구현에 들어가지 않는다.
승인되면 `writing-plans` 로 이어 가서 지시서(D-022)로 만든다.

## 작업 크기에 맞추기
- 작은 변경: 3~5줄 요약 + 권장안.
- 중간: 목표/비목표/제약/대안 표.
- 큰 작업: 설계 문서로 남기고, 새 문서는 한글 제목과 영문 kebab-case 문서 키를 붙인다 (R-DOC).
계획이 요구보다 몇 배 길어졌다면 줄인다.

## 피해야 할 것
- 요구를 다 안다고 가정하고 바로 구현하는 것.
- 질문을 한꺼번에 쏟아내는 것.
- 대안이 사실상 하나인데 억지로 여러 개를 만드는 것.
- 권장 없이 "어떻게 할까요" 로 넘기는 것.
- 승인 없이 DB 쓰기, 릴리스, 재시작 같은 되돌리기 어려운 일로 넘어가는 것.

## 승격 조건
현재 `status: candidate`. 아래를 모두 만족해야 `active` 로 올린다.
1. 이 스킬을 따라 요구 정리·대안 비교를 수행한 **사용 증거 2건** — 세션 id 또는 러너 job_id 를 각각 기록한다.
2. 두 건 모두 권장안 1개와 실측/추정이 구분된 근거가 남아 있고, 승인 여부가 기록되어 있다.
3. 위험 등급이 `read` 로 유지된다 (`infer_risk_tier` 확인).
승격은 증거 확인 후 사람이 승인한다. 이 문서는 스스로 승격하지 않는다.
