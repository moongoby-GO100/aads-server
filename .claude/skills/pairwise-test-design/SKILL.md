# 쌍별(Pairwise) 테스트 케이스 설계

장애의 대부분은 입력 **한 개 또는 두 개의 값**이 만날 때 드러난다. 그래서 "모든 조합" 대신
**어떤 두 항목을 골라도 그 값의 모든 쌍이 최소 한 번은 나오는** 작은 집합을 시험한다.
이 스킬은 설계 방법만 안내한다. 코드 실행 권한은 주지 않으며, 외부 도구도 설치하지 않는다 — 손으로 표를 만들고 손으로 검증한다.
테스트 파일을 쓰고 실행하는 일은 호출한 세션이 가진 권한으로 수행한다.

## 언제 쓰고 언제 쓰지 않나
- 쓴다: 독립적인 입력 3개 이상, 각 값이 2개 이상이라 전체 곱이 10건을 넘을 때. 설정 플래그, 권한×상태×모드, 요청 파라미터 조합.
- 쓰지 않는다: 항목이 2개뿐(전수로 충분), 값이 서로 순서 의존적인 절차(상태 전이 시험이 맞다), 3개 이상 값이 동시에 맞아야 터지는 결함이 알려진 경우(해당 조합은 따로 추가).

## 1. 항목과 값 정리
1. 시험 대상 함수·엔드포인트를 `Read` 로 읽고 **입력 항목**을 뽑는다. 추측하지 말고 코드에 실제로 있는 분기 조건에서 뽑는다.
2. 항목마다 값을 **동치 구간**으로 나눈다. 같은 방식으로 처리되는 값은 대표 하나로 줄인다.
   - 범위값: 경계(최소, 최소-1, 최대, 최대+1)와 정상 대표 하나.
   - 열거값: 코드가 분기하는 값 전부 + 알 수 없는 값 하나.
   - 선택 항목: 있음 / 없음, 필요하면 빈 값도 별도 값으로.
3. 결과를 `항목 | 값1, 값2, …` 표로 적는다. 항목 순서는 **값이 많은 순**으로 둔다 — 6단계의 구성이 쉬워진다.

## 2. 제약 정리
- 함께 올 수 없는 값 쌍(예: 특정 결제수단은 특정 통화를 지원하지 않음)을 목록으로 적는다. 근거는 코드나 명세의 줄 위치.
- 제약에 걸리는 쌍은 **덮어야 할 쌍에서 제외**하고, 대신 "거부되는지" 를 확인하는 부정 케이스를 별도로 한두 건 둔다.

## 3. 덮을 쌍 세기
- 항목이 n 개면 항목 쌍은 n(n−1)/2 개. 각 항목 쌍마다 `값 수 × 값 수` 개의 값 쌍이 있다. 전부 더한 것이 **덮을 쌍의 총수**다.
- 케이스 수의 하한은 값이 가장 많은 두 항목의 곱이다. 이보다 적게는 불가능하니, 이 수에 가까우면 잘 줄인 것이다.

## 4. 표 만들기 (손 구성)
1. 값이 가장 많은 두 항목으로 전수 표를 먼저 만든다. 이것이 뼈대 행이다.
2. 나머지 항목은 열을 하나씩 추가하며, 아직 덮이지 않은 쌍이 가장 많이 채워지는 값을 행마다 고른다.
3. 항목이 하나 늘 때마다 `덮임 확인표`(5단계)를 갱신한다.
4. 마지막까지 덮이지 않은 쌍이 남으면 그 쌍만 가진 행을 추가한다. 빈 칸은 어떤 값이든 허용한다.

### 작은 예시
`결제수단{카드,계좌,포인트}`, `통화{KRW,USD}`, `쿠폰{있음,없음}` — 전수 12건, 덮을 쌍 16개, 하한 6건.
| # | 결제수단 | 통화 | 쿠폰 |
|---|---|---|---|
| 1 | 카드 | KRW | 있음 |
| 2 | 카드 | USD | 없음 |
| 3 | 계좌 | KRW | 없음 |
| 4 | 계좌 | USD | 있음 |
| 5 | 포인트 | KRW | 있음 |
| 6 | 포인트 | USD | 없음 |
6건으로 16쌍이 모두 덮인다 (12건 → 6건). 만약 "포인트는 USD 불가" 제약이 있으면 6번 행을 `포인트, KRW, 없음` 으로 바꾸고 `포인트 × USD` 는 부정 케이스로 뺀다. 그러면 `통화 × 쿠폰` 의 `USD × 없음` 은 2번 행이 덮는다.

## 5. 덮임 검증 (반드시)
- 항목 쌍마다 작은 격자를 그리고, 각 칸에 그 값 쌍이 나온 행 번호를 적는다. **빈 칸이 하나라도 있으면 미완성**이다.
- 격자를 그리는 대신 세션에서 쓸 수 있으면 아주 짧은 계산 코드로 모든 쌍 집합과 표의 쌍 집합의 차집합이 비었는지 확인해도 된다. 단, 결과 숫자를 실제로 본 뒤에만 "덮였다" 고 적는다.

## 6. 예상 결과 정하기
- 행마다 **기대 결과**를 명세나 코드에서 도출해 적는다. 구현 출력을 복사해 기대값으로 삼지 않는다 — 그러면 버그까지 정답이 된다.
- 기대 결과를 정할 수 없는 행은 "명세 확인 필요" 로 표시하고 사용자에게 올린다.

## 7. 사내 테스트로 옮기기
- 위치는 `tests/unit/` 아래 기존 관련 테스트 파일. 같은 대상의 파일이 있으면 거기에 추가하고 새 파일을 늘리지 않는다 (`Glob tests/unit/test_*.py` 와 `Grep` 으로 확인).
- 표의 행을 `pytest.mark.parametrize` 의 케이스로 옮기고 `ids` 에 행 번호와 값 요약을 넣어 실패 시 어느 조합인지 바로 보이게 한다.
- 표 자체(항목, 값, 제약, 덮을 쌍 수, 케이스 수)를 테스트 파일 상단의 짧은 주석이나 docstring 한 줄로 남긴다.
- 실행은 `bash scripts/run_unit_tests.sh tests/unit/<파일>.py`. 종료코드 0 통과, 1 실패, 2 실행 불가(게이트 미작동 — 통과로 치지 않는다). 테스트가 실패하면 삭제하지 말고 코드나 기대값 가운데 틀린 쪽을 고친다.
- 부정 케이스(제약 위반 입력)는 별도 테스트로 둔다.

## 보고 형식
`항목·값 표 / 제약 / 전수 N건 → 쌍별 M건 / 덮을 쌍 수와 덮인 수 / 부정 케이스 / 실행 결과(종료코드)`.

## 자주 틀리는 것
- 값 나누기를 대충 해서 같은 동작을 하는 값을 여럿 넣는다 — 케이스만 늘어난다.
- 제약을 무시해 실행 불가능한 행을 만든다.
- 덮임을 확인하지 않고 "쌍별이다" 라고 한다.
- 기대값을 구현 출력에서 베낀다.

## 승격 조건
현재 `status: candidate`. 아래를 모두 만족해야 `active` 로 올린다.
1. 이 스킬로 테스트 케이스를 설계한 **사용 증거 2건** — 세션 id 또는 러너 job_id 를 각각 기록한다.
2. 두 건 모두 덮임 검증 결과가 보고에 있고, `run_unit_tests.sh` 종료코드 0 이 확인되었다.
3. 위험 등급이 `read` 로 유지된다 (`infer_risk_tier` 확인).
승격은 증거 확인 후 사람이 승인한다. 이 문서는 스스로 승격하지 않는다.
