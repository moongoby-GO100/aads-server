# 프롬프트 자산 작성·개선

프롬프트는 코드와 같이 **바꾸면 모든 대화에 영향이 가는 설정**이다. 이 스킬은 쓰는 법과 확인하는 법만 안내하며,
DB 쓰기·마이그레이션 적용 권한은 주지 않는다. 변경은 마이그레이션 파일 또는 승인된 경로로만 반영한다.

## 구조 먼저 이해하기
- 저장소는 `prompt_assets` 테이블이다 (`migrations/058_create_prompt_assets.sql`). 핵심 열: `slug`(고유), `layer_id`(1~5), `content`, `workspace_scope`, `intent_scope`, `role_scope`, `target_models`, `model_variants`, `priority`, `enabled`.
- 레이어 이름은 `app/services/prompt_compiler.py` 의 `LAYER_NAMES` 가 정본이다: **L1 global, L2 project, L3 role, L4 intent, L5 model**. 쓰기 전에 이 파일을 `Read` 로 다시 확인한다.
- 컴파일러는 `layer_id`, `priority`, `slug` 오름차순으로 이어 붙이고, 범위 열이 비어 있거나 `*` 이거나 요청 값이 들어 있는 자산만 고른다. 정확한 조건은 같은 파일의 조회 부분에서 확인한다.
- 적용 이력은 `compiled_prompt_provenance` 에 `applied_assets`(slug, layer, priority, 글자 수)로 남는다.

## 1. 어느 레이어에 넣을지
| 질문 | 레이어 |
|---|---|
| 모든 프로젝트·역할에 같은 규칙인가 | L1 |
| 특정 프로젝트(워크스페이스)만의 사실·금지인가 | L2 |
| 특정 역할(CTO, PM 등)의 판단 기준인가 | L3 |
| 특정 요청 종류(intent)에서만 필요한가 | L4 |
| 특정 모델의 습성을 보정하는가 | L5 |
- **가장 좁은 레이어**에 넣는다. 넓은 레이어에 넣을수록 모든 대화의 앞부분이 길어지고 다른 규칙과 부딪힐 위험이 커진다.
- 같은 규칙을 두 레이어에 복제하지 않는다. 한쪽이 낡으면 모순이 생긴다 (R-RELEASE 와 같은 이유).
- 이미 있는 자산을 먼저 찾는다: `Grep -r "slug" migrations scripts` 로 기존 slug 와 내용을 확인하고, 있으면 새로 만들지 말고 그 자산을 고친다.

## 2. 범위와 priority
- 범위(`workspace_scope`, `intent_scope`, `role_scope`)는 **필요한 만큼만 좁힌다.** 비워 두거나 `*` 면 전부에 적용된다.
- priority 는 같은 레이어 안의 순서다. 낮은 숫자가 앞에 온다. 앞쪽에 있는 문장이 더 강하게 읽히므로, 다른 자산의 전제가 되는 규칙을 앞에 둔다.
- 범위를 고칠 때는 어떤 workspace·intent·role 값이 실제로 쓰이는지 코드에서 확인한다. 존재하지 않는 값으로 좁히면 자산이 **아무 데도 적용되지 않는다.**

## 3. 본문 작성 원칙
1. **한 자산에 한 주제.** 제목만 보고 무엇인지 알 수 있어야 한다.
2. **행동으로 쓴다.** "정확하게 답한다" 가 아니라 "수치를 말할 때는 조회한 출처와 시각을 함께 적는다".
3. **이유를 한 줄 붙인다.** 이유가 있으면 모델이 예외 상황에서 스스로 판단한다. 실제 사고 사례가 있으면 날짜와 함께 한 줄로 쓴다.
4. **금지는 대안과 함께.** "하지 마라" 만 쓰면 모델이 빈칸을 엉뚱하게 채운다.
5. **번호는 순서가 있을 때만.** 순서 없는 규칙은 점 목록이나 짧은 문단.
6. **강조 남발 금지.** 모든 문장이 "반드시" 면 어느 것도 강조가 아니다.
7. **길이를 아낀다.** 프롬프트는 매 대화의 입력 토큰이다. 늘어난 만큼 비용과 앞선 규칙의 영향력 희석이 생긴다. 새 규칙을 넣을 때 낡은 규칙 하나를 빼는 것을 먼저 검토한다.
8. 사내 규칙은 **복사하지 말고 원본 위치를 가리킨다.** 원본이 바뀌면 복사본이 낡는다.
9. 예시는 한두 개만, 실제 사용 흐름에서 가져온다. 예시가 많으면 모델이 예시를 그대로 따라 한다.

## 4. 개선할 때 순서
1. **증상을 먼저 적는다.** 어떤 입력에 어떤 응답이 나왔고 무엇이 틀렸는가. 증상 없는 개선은 취향 다툼이 된다.
2. 현재 적용된 본문을 읽고, 증상의 원인이 **프롬프트의 빈틈 · 모순 · 모호함 · 모델 한계** 중 무엇인지 가른다. 모델 한계라면 프롬프트를 늘려도 풀리지 않는다.
3. 가능한 가장 작은 수정을 한다. 문장 하나 추가 · 하나 교체 · 하나 삭제.
4. **전후 시험**: 증상을 낸 입력과, 증상이 없던 인접 입력 2~3개를 수정 전후로 비교한다. 인접 입력이 나빠졌으면 수정이 과하다.
5. 수정 사유와 시험 결과를 변경 기록(커밋 메시지 또는 마이그레이션 머리 주석)에 남긴다.

## 5. 적용 확인 (provenance)
자산이 DB 에 있다는 것과 **실제 대화에 적용됐다는 것은 다르다.** 보고에서 둘을 분리한다.
1. 존재: `prompt_assets` 에서 해당 slug 가 `enabled=true` 인가.
2. 범위: 시험하려는 대화의 workspace · intent · role 이 자산의 범위에 들어가는가.
3. 적용: `compiled_prompt_provenance.provenance` 의 `applied_assets` 에 해당 slug 가 있는가. 시험 대화 직후의 행(`created_at`, `session_id`)으로 찾는다.
4. 효과: 적용이 확인된 뒤에야 응답이 달라졌는지 본다.
이 확인에는 읽기 전용 질의만 쓴다 (`safe-db-query` 스킬 참고). 근거(행 id, 시각)가 없으면 "적용 확인 못 함" 이라고 쓴다.

## 6. 반영 경로와 금지
- 반영은 새 마이그레이션 파일(`migrations/`)로 한다. 파일은 저장소에만 두고 **운영 DB 적용은 별도 승인된 창구**에서 사람이 한다.
- 기존 자산 본문을 바꾸는 마이그레이션은 기대하는 기존 본문(해시)과 같을 때만 적용되게 하고, 원본을 백업하며, 롤백 파일을 같이 둔다. 선례: `migrations/20261006_l1_doc_storage_rule_activate.sql`.
- 시드 데이터를 바꾸는 `scripts/seed_prompt_assets*` 를 실행하지 않는다. 읽고 참고만 한다.
- 새 자산은 `enabled=false` 초안으로 먼저 넣고, 확인 뒤 활성화하는 두 단계를 기본으로 한다.

## 승격 조건
현재 `status: candidate`. 아래를 모두 만족해야 `active` 로 올린다.
1. 이 스킬을 따라 프롬프트 자산을 쓰거나 고친 **사용 증거 2건** — 세션 id 또는 러너 job_id 를 각각 기록한다.
2. 두 건 모두 레이어 선택 사유, 전후 시험 결과, provenance 확인(또는 "확인 못 함" 명시)이 보고에 있다.
3. 위험 등급이 `read` 로 유지된다 (`infer_risk_tier` 확인).
승격은 증거 확인 후 사람이 승인한다. 이 문서는 스스로 승격하지 않는다.
