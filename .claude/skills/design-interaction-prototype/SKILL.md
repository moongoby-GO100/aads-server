# 화면 상호작용 설계

문서 키: `design-interaction-prototype`. 이 스킬은 검토·질문 지침이며 외부 쓰기 권한을 부여하지 않는다.

## 입력·산출물과 진행 규칙

입력: {screen, tasks, data_shape, device, constraints}.
산출물: {states: [{id, visible_content, actions}], transitions: [{from, action, to}], keyboard_flow, acceptance_cases}.
상태 6종은 정상·로딩·빈 화면·오류·권한 없음·처리 중으로 고정한다. 부분 성공은 추가 상태로만 허용하며 필수 6종을 대체할 수 없다. 검색·필터·정렬·페이지 이동의 상태 보존과 취소·복구를 설계한다.
세션 만료 시 재인증 경로와 입력 보존·복구를 정의한다. 처리 중 중복 제출 방지를 위해 제출 동작을 잠그고 재시도 시 중복 처리 여부를 확인한다. 위험 행동은 영향 설명과 확인/취소를 제공하며 취소 시 원래 상태로 복귀한다. 각 상태에 진입·이탈 조건, 포커스·오류 안내, 재시도 가능 여부를 기록한다.
실패·질문 조건: 데이터 규모나 핵심 과업이 없으면 질문한다. 실행하지 않은 프로토타입을 검증 완료로 표시하지 않는다.

## 정본 실행 계약 보완

- 각 스킬에 입력 스키마, 실행 단계, 산출물 스키마, 실패/질문 조건, 허용 도구, 금지 권한, 검증 fixture를 모두 둔다.
- 입력: 프로젝트/tenant, 사용자/역할, 핵심 업무, 대상 화면/route, 현재 상태, 허용/금지 범위, 성공 기준, 참조 문서·승인본 판본/hash. 해당하지 않는 필드는 이유를 명시하고 누락과 구분한다.
- 출력: 판단·근거 참조, 미확인 항목, 다음 질문/복구 행동, 승인 필요 여부, 적용 단계, 입력 및 산출물 판본 참조, 실제 로드한 skill version/hash. 필드명은 구현에 맞춰도 의미와 추적 가능성은 유지한다.
- 허용 도구는 필요한 읽기·초안 생성·명시된 검증으로 최소화한다. CEO 승인 대행, 운영 DB/토큰 덮어쓰기, 승인되지 않은 구현 러너 인계, 배포·재시작, 외부 원문 실행은 스킬 자체 권한으로 허용하지 않는다.
- candidate 작성, 스키마 통과, fixture 통과, 실물 UX 검토, 활성화 승인, 운영 반영은 각각 별도 상태다. JSON 통과를 UX 합격으로 치환하지 않는다.
- 정상 fixture는 명시된 조건이 충족될 때만 해당 단계의 합격 가능이다. 누락·충돌·실패 fixture는 올바른 중단/질문/복구가 관측되어야 fixture 테스트가 통과한다. 이는 작업 산출물이 합격했다는 의미가 아니다.
- 설명만 있고 코드 강제가 없는 항목은 '지침만 있음'으로 표시한다. D1.5 스킬 계약과 D1.6 게이트 증거를 구분한다. 아직 구현되지 않은 후속 게이트를 현 단계가 제공한다고 보고하지 않는다.
- 새 화면 Q1~Q10과 S3 축소 질문을 구분한다. S3는 적용 범위/유지할 것/완료 기준의 최소 3영역이다. 이미 확정된 답을 근거 없이 다시 묻지 않되 판본·출처 연결과 현재 요청에 대한 확인을 생략하지 않는다.
- 답변 출처 정본 표기는 CEO 선택 / CEO 직접 입력 / 권장값 수락 / 추정값 확인이다. 기존 CTO 기록의 enum 대응은 ceo_choice / ceo_input / recommended_accepted / estimate_confirmed이며 구현 후보와의 일치 여부는 후속 검수 대상이다. '잘 모름' 자체는 확정 출처가 아니다. 제시된 권장값의 수락 또는 추정값 확인 증거가 필요하다.
- 시각 검수는 실제 화면 근거가 필요하다. 캡처 실패 시 HTTP→API→프로세스 폴백을 기록해 기능 상태를 확인하되, 시각 검수는 미완료로 남긴다. 44px는 프로젝트 터치 기준이며 접근성 전체 준수를 의미하지 않는다.
- 이하의 업무 복구/입력 보존/의미 토큰 구분 등 상세 UX fixture는 UX 담당의 검수 제안이다. rev4 원문에 동일 문장이 모두 존재한다고 주장하지 않는다.

실행 단계: 진입→행동→결과→실패 복구 경로 및 정상·로딩·빈 화면·오류·권한 없음·처리 중의 상태 6종을 정의한다. 세션 만료·중복 제출·네트워크 실패에서 입력 보존, 재시도, 진행/결과 인지, 키보드 포커스와 모바일 조작을 확인한다. 위험 행동에는 확인·취소를 제공한다. 데이터 많은 화면은 단위·필터·정렬·갱신 상태를 구분한다.
반려·복구 조건: 정상 경로만 제공, 오류 후 입력 소실, 처리 중 중복 실행, 키보드 막힘, 권한·세션 실패 시 막다른 화면, 위험 행동 즉시 확정, 로딩과 처리 중을 근거 없이 누락하면 반려한다.

## 검증 fixture

출처: design-agent-d15-ux-acceptance-rev4-57980cb2 revision 2. 정적 계약이며 실제 모델·화면 실행은 미검증이다.

### 정상 fixture

ID: UX04-N
입력: 승인함의 6개 상태, 키보드 이동, 모바일 주요 행동, 세션 복구와 위험 행동 확인/취소를 시연한다.
기대: 합격 가능: 상태별 진입·동작·결과와 화면/조작 증거를 연결한다.
관측: 상태 정의와 실제 조작 성공을 분리해 기록하고 둘 다 확인한다.

### 누락 fixture

ID: UX04-M
입력: 오류 또는 권한 없음 상태와 복구 버튼이 없다.
기대: 반려·보완: 누락 상태와 복구 경로를 설계·검증한다.
관측: 정상 화면만으로 전체 prototype 합격을 내리지 않는다.

### 충돌 fixture

ID: UX04-C
입력: 사용자는 읽기 권한만 있으나 화면에는 활성 승인 버튼이 보이고 서버는 거절한다.
기대: 반려: 권한 표시와 실행 계약을 일치시키고 이유·복구 경로를 제공한다.
관측: 클라이언트 버튼만 숨긴 것을 서버 권한 보장으로 보고하지 않는다.

### 실패 fixture

ID: UX04-F
입력: 폼 제출이 실패한 뒤 재시도하거나 응답 지연 중 버튼을 다시 누른다.
기대: 복구 성공 시 합격 가능: 입력 보존·중복 실행 방지·실패 상태·재시도 결과를 확인한다.
관측: 중복 작업 생성, 입력 유실, 실패를 성공 토스트로 표시하면 반려한다.

## 추가 회귀 사례 (supplemental)

기대: 검색 로딩·0건·오류 상태, 필터 보존, 키보드 이동 사례.
입력: {screen: 목록, tasks: []}
기대: 핵심 과업 질문.

위 fixture는 기대 동작 명세다. 실제 모델 수행 검증·사용 증거와 사람 승인 전에는 active로 승격하지 않는다.
