# 디자인 비평과 재작업

문서 키: `design-critique`. 이 스킬은 검토·질문 지침이며 외부 쓰기 권한을 부여하지 않는다.

## 입력·산출물과 진행 규칙

입력: {brief, screens, feedback, acceptance_criteria}.
산출물: {findings: [{evidence, criterion, severity, suggestion}], priorities, unresolved, recheck_cases}.
취향과 과업 실패를 구분한다. 각 반려 의견을 기존 기준과 연결하고 서로 충돌하면 드러낸다.
높은 심각도부터 수정 제안을 정하고 재확인 사례를 남긴다. 문서 합의는 document-coauthoring으로 넘긴다.
실패·질문 조건: 기준이 없거나 피드백이 모순이면 결정을 질문한다. 계산 없는 접근성 통과 판정은 하지 않는다.

각 지적을 승인 기준·판본 hash·화면 위치·사용자 영향·심각도·재검증 조건에 연결한다. 취향은 제안으로 분리하고 충돌한 피드백은 승인자에게 질문한다. 근거 없는 점수·자동 승인·인계 금지.

## 정본 실행 계약 보완

- 각 스킬에 입력 스키마, 실행 단계, 산출물 스키마, 실패/질문 조건, 허용 도구, 금지 권한, 검증 fixture를 모두 둔다.
- 입력: 프로젝트/tenant, 사용자/역할, 핵심 업무, 대상 화면/route, 현재 상태, 허용/금지 범위, 성공 기준, 참조 문서·승인본 판본/hash. 해당하지 않는 필드는 이유를 명시하고 누락과 구분한다.
- 출력: 판단·근거 참조, 미확인 항목, 다음 질문/복구 행동, 승인 필요 여부, 적용 단계, 입력 및 산출물 판본 참조, 실제 로드한 skill version/hash. 필드명은 구현에 맞춰도 의미와 추적 가능성은 유지한다.
- 허용 도구는 필요한 읽기·초안 생성·명시된 검증으로 최소화한다. CEO 승인 대행, 운영 DB/토큰 덮어쓰기, 승인되지 않은 구현 러너 인계, 배포·재시작, 외부 원문 실행은 스킬 자체 권한으로 허용하지 않는다.
- candidate 작성, 스키마 통과, fixture 통과, 실물 UX 검토, 활성화 승인, 운영 반영은 각각 별도 상태다. JSON 통과를 UX 합격으로 치환하지 않는다.
- 정상 fixture는 명시된 조건이 충족될 때만 해당 단계의 합격 가능이다. 누락·충돌·실패 fixture는 올바른 중단/질문/복구가 관측되어야 fixture 테스트가 통과한다. 이는 작업 산출물이 합격했다는 의미가 아니다.
- 설명만 있고 코드 강제가 없는 항목은 '지침만 있음'으로 표시한다. D1.5 스킬 계약과 D1.6 게이트 증거를 구분한다. 아직 구현되지 않은 후속 게이트를 현 단계가 제공한다고 보고하지 않는다.
- 새 화면 Q1~Q10과 S3 축소 질문을 구분한다. S3는 적용 범위/유지할 것/완료 기준의 최소 3영역이다. 이미 확정된 답을 근거 없이 다시 묻지 않되 판본·출처 연결과 현재 요청에 대한 확인을 생략하지 않는다.
- 답변 출처 정본 표기는 CEO 선택 / CEO 직접 입력 / 권장값 수락 / 추정값 확인이다. 기존 CTO 기록의 enum 대응은 ceo_choice / ceo_input / recommended_accepted / estimate_confirmed이며 구현 후보와의 일치 여부는 후속 검수 대상이다. '잘 모름' 자체는 확정 출처가 아니다. 제시된 권장값의 수락 또는 추정값 확인 증거가 필요하다.
- 시각 검수는 실제 화면 근거가 필요하다. 캡처 실패 시 HTTP→API→프로세스 폴백을 기록해 기능 상태를 확인하되, 시각 검수는 미완료로 남긴다. 44px는 프로젝트 터치 기준이며 접근성 전체 준수를 의미하지 않는다.
- 이하의 업무 복구/입력 보존/의미 토큰 구분 등 상세 UX fixture는 UX 담당의 검수 제안이다. rev4 원문에 동일 문장이 모두 존재한다고 주장하지 않는다.

실행 단계: 사용자 핵심 업무를 기준으로 근거 화면·요소 위치·판본·심각도·사용자 영향·수정 권고·재검증 조건을 제시한다. 취향/가설과 검증 결함을 구분하고 반려 의견은 구조·시각·문구·동작으로 분류한다. 차단 결함은 총점과 독립적으로 처리하고 S8은 미승인 시안의 해당 단계만 재작업한다.
반려·복구 조건: 취향을 객관 결함으로 단정, 근거 없는 점수, 차단 결함을 미적 점수로 상쇄, 판본 다른 캡처 비교, 피드백을 이유 없이 누락, 비평을 CEO 승인으로 취급하면 반려한다.

## 검증 fixture

출처: design-agent-d15-ux-acceptance-rev4-57980cb2 revision 2. 정적 계약이며 실제 모델·화면 실행은 미검증이다.

### 정상 fixture

ID: UX09-N
입력: 승인 버튼 식별·실패 복구·긴 문구·모바일 화면을 증거 위치와 연결해 검토한다.
기대: 합격 가능: 결함별 심각도·영향·수정·재검증 조건을 기록하고 미검증은 구분한다.
관측: S8 피드백 항목마다 전후 근거를 남기며 원래 승인 범위를 임의 확대하지 않는다.

### 누락 fixture

ID: UX09-M
입력: 스크린샷/route 또는 검토 대상 판본이 없다.
기대: 판정 보류·근거 요청: 평가 범위를 명시한다.
관측: 실물을 보지 않고 UX 합격/점수를 확정하면 반려한다.

### 충돌 fixture

ID: UX09-C
입력: 시각 품질은 높지만 핵심 승인 행동이 불가능하고 다른 평가자는 총점으로 통과시킨다.
기대: 반려: 차단 결함을 총점과 무관하게 유지한다.
관측: 핵심 업무 회복과 해당 증거 확보 전 합격으로 바꾸지 않는다.

### 실패 fixture

ID: UX09-F
입력: 검토 화면 캡처가 실패하거나 전후 이미지가 서로 다른 판본으로 확인된다.
기대: 비교 중단·재수집: 확보 근거와 실패를 기록하고 화면 검증은 미완료로 둔다.
관측: 접속 성공 또는 이전 판본 증거로 현 판본 검토를 완료하면 반려한다.

## 추가 회귀 사례 (supplemental)

정본 40건에 합산하지 않는다.


입력: {brief: 빠른 검색, screens: [검색 없는 목록], feedback: 찾기 어려움}
기대: 과업 근거가 있는 검색 누락 finding과 재확인 사례.
입력: {feedback: [밀도 높여라, 더 여백 줘라], acceptance_criteria: []}
기대: 충돌 unresolved와 우선순위 질문.

위 fixture는 기대 동작 명세다. 실제 모델 수행 검증·사용 증거와 사람 승인 전에는 active로 승격하지 않는다.

### supplemental 정상 fixture

입력: {brief: 빠른 검색, screens: 검색 없는 목록, acceptance_criteria: 검색 가능}
기대: 근거·심각도·재확인 사례.

### supplemental 누락 fixture

입력: {acceptance_criteria: []}
기대: 기준 질문, 확정 판정 중단.

### supplemental 충돌 fixture

입력: {feedback: [밀도 높임, 여백 확대]}
기대: unresolved, 우선순위 질문.

### supplemental 실패 fixture

입력: {screens: 접근 실패}
기대: 평가 중단, 화면 요청.
