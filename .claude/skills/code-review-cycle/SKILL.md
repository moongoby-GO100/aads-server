# 검수 요청과 피드백 반영

검수는 **일찍, 자주** 받는 편이 싸다. 그리고 받은 지적은 **검증하고 나서** 반영한다.
이 스킬은 판단 순서만 안내한다. 코드 수정·명령 실행은 호출한 세션이 가진 권한 안에서만 한다.
커밋·푸시·재제출은 러너가 맡는 세션이 많으므로, 직접 하지 않는 것은 "러너 수행 대상" 으로 적는다.

## 1부 — 검수 요청

### 언제
- 필수: 하나의 지시서 작업이 끝났을 때, 여러 파일에 걸친 변경 뒤, 인증·결제·배포 같은 핵심 경로를 건드렸을 때.
- 권장: 막혀서 새 시각이 필요할 때, 큰 리팩터링 전후.

### 요청에 담을 것
1. **무엇을 했는가** — 지시서 TASK_ID 와 한 단락 요약.
2. **요구가 무엇이었나** — 완료 기준 항목 목록.
3. **변경 범위** — 변경 파일과 `유지 / 수정 / 신규 / 삭제` 분류. 지시서에 없는 파일을 건드렸다면 사유.
4. **실제 검증 결과** — 실행한 명령과 종료코드 (실행하지 않은 것은 "미실행" 으로).
5. **미완료·위험** — 하지 못한 것, 확신이 없는 곳. 숨기지 않는다.

### 요청 전 자가 점검
- 완료 기준을 한 줄씩 대조했는가 (`verification-before-completion`).
- 사내 규칙 위반이 없는가: 하드코딩된 키(R-KEY), 인증 방식(R-AUTH), 훅 우회, `HANDOVER.md` 수정(R-001), 기존 테스트 삭제.
- 검수자가 이 요청만 읽고 이해할 수 있는가. 대화 기록을 가정하지 않는다.

## 2부 — 피드백 반영

### 절차 (지적마다)
1. **읽기**: 전체를 끝까지 읽는다. 일부만 보고 반응하지 않는다.
2. **이해**: 요구를 내 말로 다시 적는다. 이해되지 않는 항목이 있으면 **그것만 먼저 질문**한다. 일부만 이해한 채 나머지를 구현하지 않는다 — 항목들이 서로 얽혀 있을 수 있다.
3. **검증**: 지적이 코드 현실과 맞는지 `Read`/`Grep` 으로 확인한다. 가리킨 줄이 정말 있는가, 호출처가 정말 그렇게 쓰는가.
4. **평가**: 이 코드베이스에서 타당한가. 지적을 따르면 기존 기능이 깨지지 않는가. 지적자가 전체 맥락을 모르고 있지 않은가.
5. **응답**: 타당하면 고친 내용으로, 아니면 근거를 든 반박으로 응답한다.
6. **반영**: 한 번에 하나씩 고치고 항목마다 테스트한다.

### 반려 사유 유형별 처리
| 유형 | 처리 |
|---|---|
| 명백한 버그·규칙 위반 | 재현 또는 근거 확인 후 우선 수정 |
| 지시서에 없는 범위 요구 | 지시서 범위와 대조해 필요 시 별도 작업으로 제안 |
| 쓰지 않는 기능을 "제대로" 만들라는 요구 | 실제 호출처를 `Grep` 으로 확인. 쓰는 곳이 없으면 만들지 않는 쪽을 제안 |
| 기존 동작과 충돌하는 요구 | 충돌 지점을 제시하고 어느 쪽을 택할지 확인 |
| 근거가 틀린 지적 | 코드·로그·테스트 결과를 인용해 정중하게 반박 |
| 모호한 지적 | 무엇을 기준으로 판정하는지 질문 |

### 반영 순서
막는 문제(깨짐, 보안) → 단순한 수정 → 복잡한 수정. 각 수정 후 해당 테스트를 돌려 회귀가 없는지 본다.

### 하지 않는 것
- 확인 없이 "맞습니다" 로 수용하지 않는다. 지적이 틀렸는데 따르면 코드가 나빠진다.
- 지적을 감정으로 방어하지 않는다. 틀렸다면 사실로 반박한다.
- 감사 표현을 늘어놓지 않는다. 고친 내용을 말하면 충분하다.
- 반려 사유 한 줄만 보고 테스트를 삭제하거나 검사를 끄는 식으로 통과시키지 않는다 (R-QUALITY).
- 지적 일부를 조용히 빼먹지 않는다 — 반영하지 않는 항목에는 이유를 남긴다.

### 반박이 틀렸을 때
검증해 보니 내가 틀렸다면 변명 없이 사실만 적는다: "확인했더니 지적이 맞다. 이유는 ~, 수정했다."

## 3부 — 재작업 반복
러너 검수 반려는 재작업으로 이어지며 횟수에 제한이 있다. 같은 지적이 반복되면 코드만 고치지 말고 **왜 이전 수정이 통하지 않았는지** 를 먼저 설명한다.
세 번 이상 같은 곳이 반려되면 설계 가정을 사용자와 다시 논의한다 (`systematic-debugging` 의 구조 재검토 기준).

## 승격 조건
현재 `status: candidate`. 아래를 모두 만족해야 `active` 로 올린다.
1. 이 스킬을 따라 검수 요청 또는 피드백 반영을 수행한 **사용 증거 2건** — 세션 id 또는 러너 job_id 를 각각 기록한다.
2. 두 건 모두 지적별 검증 결과(수용 / 반박 / 질문)가 남아 있고, 반영 후 테스트 결과가 있다.
3. 위험 등급이 `read` 로 유지된다 (`infer_risk_tier` 확인).
승격은 증거 확인 후 사람이 승인한다. 이 문서는 스스로 승격하지 않는다.
