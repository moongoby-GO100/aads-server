# 독립 작업 병렬 분배

독립된 문제 하나에 작업자 하나를 붙이면 동시에 진행된다. 그러나 **서로 간섭하는 작업을 병렬로 돌리면** 충돌과 재작업만 늘어난다.
이 스킬은 나누고 합치는 판단 기준만 안내한다. 작업 제출·실행 권한은 주지 않는다.
실제 제출은 호출한 세션이 가진 권한(러너 배치 제출 등)으로 하거나, 제출할 내용을 정리해 승인 단계에 넘긴다.

## 병렬로 해도 되는가
병렬 후보 조건을 **모두** 만족해야 한다.
- 작업 사이에 공유 상태가 없다 (같은 파일, 같은 DB 행, 같은 설정을 고치지 않는다).
- 한 작업의 결과가 다른 작업의 입력이 아니다.
- 한 작업을 이해하는 데 다른 작업의 맥락이 필요하지 않다.
- 각 작업이 단독으로 검증된다.

병렬로 하면 안 되는 경우:
- 실패들이 한 원인에서 나왔을 수 있다 (하나를 고치면 나머지가 풀리는지 먼저 본다).
- 아직 무엇이 깨졌는지 모르는 탐색 단계.
- 시스템 전체를 이해해야 풀리는 문제.
- **같은 파일을 둘 이상이 수정**한다 → 순차로 둔다. 병행 러너가 같은 파일을 고쳐 `stale_base` 가 반복된 사례가 있다.

## 1단계 — 독립 영역 나누기
1. 해야 할 일을 목록으로 적고, 각 항목이 건드릴 **파일·테이블·설정**을 `Grep`/`Glob` 으로 확인해 옆에 적는다.
2. 겹치는 항목을 묶는다. 겹치면 같은 작업이거나 순서가 있는 작업이다.
3. 겹치지 않는 묶음이 병렬 후보다. 하나뿐이면 병렬이 아니다.
4. 공용 파일(테스트 목록, 설정, 인덱스)에 모든 작업이 한 줄씩 추가해야 하는 구조라면, 그 공용 파일 수정은 **마지막 통합 작업 하나**로 분리한다.

## 2단계 — 작업 지시서 만들기
각 작업은 **혼자 읽어도 이해되는** 지시서여야 한다 (`writing-plans` 의 D-022 포맷).
- 범위가 좁다: 파일 하나 또는 문제 하나. "전부 고쳐라" 는 길을 잃는다.
- 맥락이 들어 있다: 오류 메시지, 테스트 이름, 관련 경로.
- 제약이 있다: "이 파일만 수정", "운영 코드는 건드리지 않음", 금지 사항.
- 출력이 정해져 있다: 무엇을 보고해야 하는가 (원인 요약, 변경 파일, 검증 결과).

## 3단계 — 러너 배치로 분배
Pipeline Runner 는 배치 제출에서 작업마다 아래 필드를 받는다.
| 필드 | 의미 | 사용 기준 |
|---|---|---|
| `key` | 배치 안의 작업 식별자 (A, B, C …) | 짧고 겹치지 않게 |
| `depends_on_key` | 먼저 끝나야 하는 같은 배치 내 작업의 key | 순서가 있을 때만 |
| `parallel_group` | 같은 그룹은 동시 실행 허용 | 독립 작업끼리만 같은 그룹 |
| `size` | 작업 크기 | 한 번의 실행에 담길 만큼 |

- `depends_on_key` 로 가리키는 key 가 배치에 없으면 제출이 거절된다. 순환 의존을 만들지 않는다.
- 같은 그룹이 아닌 작업은 프로젝트 잠금 때문에 동시에 돌지 않는다. 그룹을 일부러 넓게 잡아 충돌을 만들지 않는다.
- 같은 파일을 수정하는 작업은 `depends_on_key` 로 **순서를 이어** 순차로 둔다.
- 마지막에 통합·전체 검증 작업을 두고, 앞선 모든 작업에 의존하게 한다.
- 제출은 기존 중복 방지(같은 지시서 해시) 규칙을 따른다. 같은 지시서를 반복 제출하지 않는다.

## 4단계 — 결과 통합
1. **각 보고를 읽는다.** 무엇이 바뀌었는지 이해한다.
2. **충돌을 본다.** 같은 코드를 건드린 작업이 없는지 변경 파일 목록을 대조한다.
3. **전체를 함께 검증한다.** 개별 통과가 합친 뒤 통과를 보장하지 않는다. `bash scripts/run_unit_tests.sh <관련 테스트들>` 종료코드 0.
4. **표본 점검한다.** 작업자가 체계적인 실수를 했을 수 있다. 완료 보고만 옮기지 않는다 (`verification-before-completion`).

## 하지 않는 것
- 병렬이라는 이유로 지시서 맥락을 줄이지 않는다.
- 원본이 권하는 방식이라도 작업 트리 분리를 직접 조작하는 명령(git worktree 직접 사용)을 지시서에 넣지 않는다. 격리는 러너가 맡는다.
- 훅 우회, 직접 릴리스·재시작, `HANDOVER.md` 수정을 지시하지 않는다 (R-COMMIT, R-001).
- 상태를 짧은 간격으로 반복 조회하며 기다리지 않는다. 완료 알림을 받는다 (R-BG).

## 예시 (구조만)
세 파일의 서로 다른 테스트 실패가 있고 원인이 독립적이라면: 작업 A·B·C 를 같은 `parallel_group` 으로 제출하고,
작업 D(전체 테스트 실행과 공용 목록 갱신)는 `depends_on_key` 로 A·B·C 중 마지막에 이어 둔다.
의존 키는 하나만 받으므로 여러 선행이 필요하면 A → B → C → D 처럼 사슬로 잇거나 D 를 둘로 나눈다.

## 승격 조건
현재 `status: candidate`. 아래를 모두 만족해야 `active` 로 올린다.
1. 이 스킬을 따라 작업을 분배한 **사용 증거 2건** — 세션 id 또는 러너 job_id 를 각각 기록한다.
2. 두 건 모두 겹침 분석표가 남아 있고, 병렬 작업 사이 충돌이 없었으며 통합 검증이 있다.
3. 위험 등급이 `read` 로 유지된다 (`infer_risk_tier` 확인).
승격은 증거 확인 후 사람이 승인한다. 이 문서는 스스로 승격하지 않는다.
