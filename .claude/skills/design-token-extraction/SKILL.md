# 디자인 토큰 추출

문서 키: `design-token-extraction`. 이 스킬은 검토·질문 지침이며 외부 쓰기 권한을 부여하지 않는다.

## 입력·산출물과 진행 규칙

입력: {artifacts, existing_tokens, mode, provenance}.
산출물: {tokens: [{name, value, unit, evidence, confidence}], aliases, conflicts, unknowns}.
색·서체·간격·반경을 읽고 원본 위치를 증거로 남긴다. 기존 의미 토큰을 우선 대응하고 픽셀 관측값과 추정값을 구분한다.
실패·질문 조건: 이미지에서 정확한 값 계산이 불가능하면 unknowns로 남기고 코드·원본을 요청한다. 추정값을 확정 토큰으로 발행하지 않는다.

의미 역할·원본 위치·단위·추출 방법·신뢰도를 함께 기록한다. 기존 의미 토큰과 충돌하면 자동 교체하지 않고 질문한다. 승인 전 코드나 공용 토큰에 적용하지 않는다.

## 정본 실행 계약 보완

- 각 스킬에 입력 스키마, 실행 단계, 산출물 스키마, 실패/질문 조건, 허용 도구, 금지 권한, 검증 fixture를 모두 둔다.
- 입력: 프로젝트/tenant, 사용자/역할, 핵심 업무, 대상 화면/route, 현재 상태, 허용/금지 범위, 성공 기준, 참조 문서·승인본 판본/hash. 해당하지 않는 필드는 이유를 명시하고 누락과 구분한다.
- 출력: 판단·근거 참조, 미확인 항목, 다음 질문/복구 행동, 승인 필요 여부, 적용 단계, 입력 및 산출물 판본 참조, 실제 로드한 skill version/hash. 필드명은 구현에 맞춰도 의미와 추적 가능성은 유지한다.
- 허용 도구는 필요한 읽기·초안 생성·명시된 검증으로 최소화한다. CEO 승인 대행, 운영 DB/토큰 덮어쓰기, 승인되지 않은 구현 러너 인계, 배포·재시작, 외부 원문 실행은 스킬 자체 권한으로 허용하지 않는다.
- candidate 작성, 스키마 통과, fixture 통과, 실물 UX 검토, 활성화 승인, 운영 반영은 각각 별도 상태다. JSON 통과를 UX 합격으로 치환하지 않는다.
- 정상 fixture는 명시된 조건이 충족될 때만 해당 단계의 합격 가능이다. 누락·충돌·실패 fixture는 올바른 중단/질문/복구가 관측되어야 fixture 테스트가 통과한다. 이는 작업 산출물이 합격했다는 의미가 아니다.
- 설명만 있고 코드 강제가 없는 항목은 '지침만 있음'으로 표시한다. D1.5 스킬 계약과 D1.6 게이트 증거를 구분한다. 아직 구현되지 않은 후속 게이트를 현 단계가 제공한다고 보고하지 않는다.
- 새 화면 Q1~Q10과 S3 축소 질문을 구분한다. S3는 적용 범위/유지할 것/완료 기준의 최소 3영역이다. 이미 확정된 답을 근거 없이 다시 묻지 않되 판본·출처 연결과 현재 요청에 대한 확인을 생략하지 않는다.
- 답변 출처 정본 표기는 CEO 선택 / CEO 직접 입력 / 권장값 수락 / 추정값 확인이다. 기존 CTO 기록의 enum 대응은 ceo_choice / ceo_input / recommended_accepted / estimate_confirmed이며 구현 후보와의 일치 여부는 후속 검수 대상이다. '잘 모름' 자체는 확정 출처가 아니다. 제시된 권장값의 수락 또는 추정값 확인 증거가 필요하다.
- 시각 검수는 실제 화면 근거가 필요하다. 캡처 실패 시 HTTP→API→프로세스 폴백을 기록해 기능 상태를 확인하되, 시각 검수는 미완료로 남긴다. 44px는 프로젝트 터치 기준이며 접근성 전체 준수를 의미하지 않는다.
- 이하의 업무 복구/입력 보존/의미 토큰 구분 등 상세 UX fixture는 UX 담당의 검수 제안이다. rev4 원문에 동일 문장이 모두 존재한다고 주장하지 않는다.

실행 단계: 원본 스타일 값과 의미 토큰의 매핑, 색/서체/간격/형태의 역할, 컴포넌트 상태·라이트/다크 테마·예외·추출 신뢰도를 남긴다. 추출 범위와 미추출 영역, 프로젝트·tenant·원본 판본/hash를 고정하고 승인 토큰과 충돌을 분리한다.
반려·복구 조건: 같은 색이라는 이유로 다른 의미를 병합, 한 화면 추출을 전체 시스템 확정으로 보고, 테마·상태 누락 은폐, 타 tenant 토큰 혼합, 추출 실패를 빈 토큰 정상 결과로 처리하면 반려한다.

## 검증 fixture

출처: design-agent-d15-ux-acceptance-rev4-57980cb2 revision 2. 정적 계약이며 실제 모델·화면 실행은 미검증이다.

### 정상 fixture

ID: UX07-N
입력: 버튼·경고·배경의 상태별 스타일과 라이트/다크 화면을 추출한다.
기대: 합격 가능: 원본 값→의미 토큰→상태/테마/사용처를 추적하고 범위·신뢰도를 남긴다.
관측: 추출안은 승인 전 초안이며 미관측 상태는 미확인이다.

### 누락 fixture

ID: UX07-M
입력: 기본 테마 화면만 있고 hover·disabled·dark 자료가 없다.
기대: 부분 추출·평가불가 표시: 누락 영역의 추가 자료를 요청한다.
관측: 전체 상태/테마 추출 완료로 보고하면 반려한다.

### 충돌 fixture

ID: UX07-C
입력: 브랜드 강조와 위험 경고가 같은 색이고 승인 토큰 값은 다른 값이다.
기대: 의미 분리·충돌 보고: 역할별 토큰을 유지하고 승인값 변경은 별도 판단으로 남긴다.
관측: 색상 일치만으로 병합하거나 승인값을 자동 교체하면 반려한다.

### 실패 fixture

ID: UX07-F
입력: CSS 변수 해석이 순환하거나 원본 스타일을 읽지 못한다.
기대: 실패 항목 분리·중단/재시도: 원본 경로와 실패 이유를 기록한다.
관측: 해석 불가 값을 임의 색/0으로 채워 계산 가능한 것처럼 만들면 반려한다.

## 추가 회귀 사례 (supplemental)

정본 40건에 합산하지 않는다.


입력: {artifacts: ["button {border-radius: 8px}"], existing_tokens: {radius_button: 8px}}
기대: 8px 근거와 기존 radius_button 별칭, 중복 토큰 없음.
입력: {artifacts: [흐린 스크린샷]}
기대: 정확한 색 unknowns, 원본 요청.

위 fixture는 기대 동작 명세다. 실제 모델 수행 검증·사용 증거와 사람 승인 전에는 active로 승격하지 않는다.

### supplemental 정상 fixture

입력: {artifacts: radius 8px 코드, existing_tokens: radius_button 8px}
기대: 근거와 별칭, 중복 없음.

### supplemental 누락 fixture

입력: {provenance: null}
기대: 출처 요청, 확정 중단.

### supplemental 충돌 fixture

입력: {existing_tokens: radius_button 4px, artifacts: 8px}
기대: 충돌 기록, 교체 승인 질문.

### supplemental 실패 fixture

입력: {artifacts: 흐린 이미지}
기대: unknowns, 원본 요청.
