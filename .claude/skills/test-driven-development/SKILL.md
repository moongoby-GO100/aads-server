# 테스트 먼저 작성하기 (TDD)

## 대원칙
**실패하는 테스트를 먼저 쓴다. 그 테스트가 실패하는 것을 직접 보지 못했다면, 그 테스트가 옳은 것을 검사하는지 알 수 없다.**
테스트를 나중에 쓰면 "지금 코드가 하는 일" 을 확인하게 되고, 코드가 해야 하는 일을 확인하지 못한다.

이 스킬은 순서와 판단 기준만 안내한다. 파일 수정과 테스트 실행은 호출한 세션이 가진 권한 안에서 하고,
권한이 없으면 작성할 테스트 본문과 실행해야 할 명령을 정리해 넘긴다. 실행하지 않은 결과를 적지 않는다.

## 언제 쓰나
항상: 새 기능, 버그 수정, 리팩터링, 동작 변경.
예외(사용자와 합의 후): 일회성 점검 스크립트, 생성된 코드, 설정 파일 수정.
"이번만 건너뛰자" 는 생각이 들면 그것이 멈춰야 할 신호다.

## 순서: 빨강 → 초록 → 정리

### 1. 빨강 — 실패하는 테스트 한 개
- 원하는 동작 **하나**를 검사하는 가장 작은 테스트를 쓴다. 이름은 동작을 문장으로 말한다.
- 가능하면 실제 코드를 호출한다. 흉내(mock)는 피할 수 없을 때만 쓴다 — 흉내 객체의 동작을 검사하는 테스트가 되기 쉽다.
- 위치는 `tests/unit/` 아래 기존 테스트 파일의 구조를 따른다. 비슷한 테스트를 먼저 읽는다.

### 2. 빨강 확인 — 반드시 실행
```
bash scripts/run_unit_tests.sh tests/unit/test_x.py
```
종료코드 0=통과, 1=실패, 2=실행 불가. 이 단계에서는 **1 이면서 이유가 맞아야** 한다.
- 통과한다 → 이미 있는 동작을 검사하고 있다. 테스트를 고친다.
- 오류로 죽는다(오타, 임포트) → 오류를 고치고, 의도한 이유로 실패할 때까지 다시 실행한다.
- 종료코드 2 → 게이트 자체가 못 돈 것이다. 결과로 쓰지 말고 원인을 해결한다.

### 3. 초록 — 통과시키는 최소 코드
- 테스트를 통과시키는 데 필요한 만큼만 쓴다. 미래 요구를 위한 옵션·추상화를 얹지 않는다.
- 테스트가 실패하면 **코드**를 고친다. 테스트를 코드에 맞춰 약하게 만들지 않는다.

### 4. 초록 확인 — 반드시 실행
- 새 테스트가 통과하고, **프로젝트 테스트 전체(최소한 영향 범위의 파일들)** 가 계속 통과한다.
- 다른 테스트가 깨졌다면 지금 고친다. 방치하면 테스트 시스템 전체가 무력해진다 (R-QUALITY).

### 5. 정리
통과 상태를 유지한 채 중복 제거, 이름 개선을 한다. 동작을 새로 더하지 않는다. 그 뒤 다음 동작으로 반복한다.

## 사내 규칙과 연결
- 테스트가 실패하면 **삭제하지 않는다.** 코드와 테스트를 함께 고쳐 같이 커밋한다 (R-QUALITY, R-COMMIT).
- 런타임 이미지에는 pytest 가 없어 컨테이너에서 직접 `pytest` 를 부르지 않는다. 위 스크립트가 운영 이미지와 작업 트리 마운트로 실행한다.
- 커밋 시 hook 이 단위 테스트를 다시 돌린다. 막히면 우회하지 말고 원인을 고친다 (`--no-verify` 금지).
- 자동 생성 코드를 쓴 뒤에는 반드시 테스트를 돌린다 (들여쓰기·소속 오류가 생길 수 있다).
- 버그 수정은 **재현 테스트가 먼저**다. 원인 조사는 `systematic-debugging` 스킬을 따른다.

## 좋은 테스트의 기준
| 성질 | 좋은 예 | 나쁜 예 |
|---|---|---|
| 하나만 검사 | 이름에 "그리고" 가 없다 | 여러 동작을 한 테스트에 섞음 |
| 이름이 명확 | `빈_이메일은_거부한다` | `test1` |
| 의도가 보임 | 입력과 기대가 한눈에 보임 | 흉내 설정이 테스트의 대부분 |
| 독립 | 다른 테스트의 순서·상태에 기대지 않음 | 전역 상태·모듈 캐시 오염 |

## 자주 나오는 변명
| 변명 | 답 |
|---|---|
| "너무 단순해서 테스트가 필요 없다" | 단순한 코드도 깨진다. 테스트는 30초면 쓴다 |
| "나중에 테스트를 쓰겠다" | 처음부터 통과하는 테스트는 아무것도 증명하지 못한다 |
| "이미 손으로 확인했다" | 손 확인은 기록도 되풀이도 되지 않는다 |
| "코드를 이미 짰으니 버리기 아깝다" | 매몰 비용이다. 검증되지 않은 코드를 두는 쪽이 빚이다 |
| "테스트하기 어렵다" | 설계 신호다. 사용하기 쉬운 인터페이스를 다시 생각한다 |
| "탐색 중이다" | 탐색은 해도 된다. 결과를 버리고 테스트부터 다시 시작한다 |

## 멈추고 처음부터 다시 해야 하는 신호
- 테스트 전에 코드를 썼다.
- 처음 실행에서 테스트가 바로 통과했다.
- 왜 실패했는지 설명하지 못한다.
- "이번만", "비슷하니까 괜찮다" 라는 생각이 든다.

## 완료 확인
- 모든 새 함수·동작에 테스트가 있다.
- 각 테스트가 구현 전에 실패하는 것을 보았고, 이유가 기대와 같았다.
- 전체 관련 테스트가 통과(종료코드 0)하고 출력이 깨끗하다.
- 경계값(빈 값, 오류 경로)이 다뤄졌다.
체크리스트를 채우지 못하면 TDD 를 건너뛴 것이다. 완료 보고는 `verification-before-completion` 기준을 따른다.

## 승격 조건
현재 `status: candidate`. 아래를 모두 만족해야 `active` 로 올린다.
1. 이 스킬을 따라 변경을 수행한 **사용 증거 2건** — 세션 id 또는 러너 job_id 를 각각 기록한다.
2. 두 건 모두 빨강 확인(실패 출력)과 초록 확인(종료코드 0)이 기록으로 남아 있고, 삭제된 테스트가 없다.
3. 위험 등급이 `read` 로 유지된다 (`infer_risk_tier` 확인).
승격은 증거 확인 후 사람이 승인한다. 이 문서는 스스로 승격하지 않는다.
