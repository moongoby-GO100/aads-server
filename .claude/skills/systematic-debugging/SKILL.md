# 체계적 디버깅

## 대원칙
**근본 원인을 확인하기 전에는 수정하지 않는다.**
증상만 가리는 수정은 원인을 남겨 두고, 다음 사람이 같은 추적을 처음부터 반복하게 만든다.
이 서버에서는 그 비용이 실제로 컸다 — 같은 실패를 세 세션이 "러너 계정 문제" 로 보고했지만
원인은 호스트/컨테이너 경로 불일치였다 (R-ERRBOOK 도입 배경).

이 스킬은 **진행 순서와 판단 기준**만 다룬다. 파일 수정·셸 실행 권한은 주지 않으며,
아래의 실행 단계는 호출한 세션이 이미 가진 권한 안에서만 한다. 권한이 없으면 실행 결과를 사용자·러너에게 요청한다.

## 언제 쓰나
- 테스트 실패, 운영 오류, 예상 밖 동작, 빌드·러너·push 실패, 성능 문제.
- 특히: 시간에 쫓길 때 / "한 줄만 고치면 될 것 같을 때" / 이미 한 번 고쳤는데 안 될 때 / 원인을 정확히 모를 때.
- 간단해 보여도 건너뛰지 않는다. 단순한 버그에도 원인은 있고, 서두르면 재작업이 더 오래 걸린다.

## 0단계 — 이미 아는 오류인가 (먼저, 1분)
오류 출력을 파일로 두고 사전을 조회한다 (표준입력은 `-`).
```
python3 scripts/error_book.py match <오류파일|->
```
- 일치하면: 사전의 원인·예방·수정 커밋을 읽고, **지금 상황이 그 원인 조건과 정말 같은지** 증거로 확인한다. 이름만 비슷한 다른 문제일 수 있다.
- 일치하는 것이 없으면: 새 문제다. 1단계로 간다. (`--record` 는 원인 미상 후보로 남기는 옵션이다 — 후보는 확인된 원인이 아니다.)
- 읽기 전용 세션이라 실행할 수 없으면 `Grep` 으로 `scripts/error_book.py` 와 관련 문서를 읽고, 조회 결과를 요청한다.

## 1단계 — 근본 원인 조사 (수정 금지 구간)
1. **오류를 끝까지 읽는다.** 스택 트레이스 전체, 파일 경로, 줄 번호, 오류 코드. 경고도 건너뛰지 않는다. 답이 거기 적혀 있는 경우가 많다.
2. **재현한다.** 정확한 절차와 입력을 적고, 매번 발생하는지 본다. 재현이 안 되면 추측하지 말고 로그·상태를 더 모은다.
   간헐적이면 조건(시각, 동시 실행, 입력 크기, 계정, 서버)을 바꿔 가며 빈도를 비교한다.
3. **최근 변경을 본다.** 직전 커밋, 설정, 의존성, 환경 차이. 같은 파일을 고친 병행 러너가 있었는지도 본다.
4. **구성요소 경계마다 증거를 모은다.** 요청이 여러 층(API → 서비스 → DB, 러너 → 훅 → git)을 지나면
   각 경계에서 "들어온 값 / 나간 값 / 환경·설정이 전달됐는가" 를 확인해서 **어느 층에서 처음 틀어지는지** 좁힌다.
   한 번 돌려서 전 층의 증거를 얻고, 실패한 층만 깊이 판다.
5. **값의 출처를 거슬러 올라간다.** 잘못된 값이 어디서 만들어졌는지, 누가 그 값으로 호출했는지를 위로 추적해서 **원천에서** 고친다. 증상 지점에서 고치지 않는다.

여기서 나오는 산출물은 코드 변경이 아니라 **"무엇이 / 어디서 / 왜 틀어지는가" 에 대한 증거 목록**이다.

## 2단계 — 패턴 비교
- 같은 저장소에서 **비슷하게 동작하는 코드**를 찾는다 (`Grep`/`Glob`).
- 참고 구현이 있으면 훑지 말고 끝까지 읽는다.
- 동작하는 것과 깨진 것의 차이를 **사소해 보여도 전부** 나열한다. "이건 상관없겠지" 는 가설이지 사실이 아니다.
- 의존하는 설정·환경변수·마운트 경로·가정을 적는다. 호스트와 컨테이너의 경로 차이는 이 서버에서 반복된 원인이다.

## 3단계 — 가설과 검증
1. **가설은 한 번에 하나**, 문장으로 쓴다: "X 가 원인이다. 왜냐하면 Y 라는 증거가 있기 때문이다."
2. **가장 작은 변화로** 검증한다. 여러 개를 동시에 바꾸면 무엇이 효과였는지 알 수 없다.
3. 결과가 가설을 지지하면 4단계로, 아니면 **가설을 버리고** 새 가설을 쓴다. 기존 수정 위에 수정을 쌓지 않는다.
4. 모르는 것은 모른다고 적는다. 아는 척 채우면 다음 가설이 틀린 전제에서 출발한다.

## 4단계 — 수정
1. **실패를 재현하는 테스트를 먼저** 만든다 (가능한 가장 작은 형태). 고치기 전에 실패하는 것을 눈으로 확인한다.
2. **원인 하나에 수정 하나.** 보이는 김에 하는 정리·리팩터링을 섞지 않는다.
3. 수정 후 그 테스트와 영향 범위 테스트를 실행한다: `bash scripts/run_unit_tests.sh <테스트파일>` (종료코드 0=통과, 1=실패, 2=실행 불가 — 2는 게이트 미작동이다).
   깨진 기존 테스트는 삭제하지 말고 코드와 함께 고친다 (R-QUALITY, R-COMMIT).
4. 훅이 막으면 우회하지 말고 막은 이유를 고친다. `--no-verify` 를 쓰지 않는다. 서명 문제로 push 가 막히면 강제로 밀기 전에
   `git reflog` 로 rebase 흔적부터 본다 (R-PUSH).

## 실패가 쌓일 때
- 수정이 **1~2번** 실패: 1단계로 돌아가 새 증거로 재조사한다.
- **3번 이상** 실패했거나 수정할 때마다 다른 곳이 깨진다: 개별 버그가 아니라 **구조 문제**일 가능성이 높다.
  더 고치지 말고 멈춰서 설계 가정이 맞는지 사용자와 논의한다.
- 다음 생각이 나오면 멈추고 1단계로 돌아간다: "일단 이렇게 해 보자" / "여러 개 한꺼번에 바꿔 보자" / "재현은 나중에" /
  "아마 이게 원인일 것" / "한 번만 더 고치면 될 듯".

## 이 서버 특유의 함정
- 호스트와 컨테이너 경로가 다르다. "계정 문제" 로 보이는 실패의 상당수가 경로 불일치였다.
- 문서가 "돈다" 고 적은 검사가 실제로는 건너뛰어지고 있을 수 있다 (예: 린터 미설치). 게이트가 실제로 실행됐는지 로그로 확인한다.
- 병행 러너가 같은 파일을 고쳐 `stale_base` 가 반복된다. 인수인계 기록은 DB 에만 쓴다 — `HANDOVER.md` 를 수정하지 않는다 (R-001).
- 백그라운드로 띄운 작업은 시간 상한을 걸고 출력이 늘어나는지 본다 (R-BG). 중첩 반복 정규식은 대용량 입력에서 멈춘 것처럼 보일 수 있다.
- 증상 보고만 믿지 말고 로그·DB 상태·파일 해시 등 **직접 관측한 값**으로 판단한다.

## 끝낸 뒤 — 오류 사전에 남기기 (R-ERRBOOK)
원인을 확인했으면 기록한다. 기록하지 않으면 다음 사람이 처음부터 다시 추적한다.
```
python3 scripts/error_book.py list --candidates
python3 scripts/error_book.py promote --key auto.xxxx --cause "..." --prevention "..." \
    --fix-commit <sha> --fix-file <경로> --fix-note "무엇을 고쳤나"
python3 scripts/error_book.py register --key <영역>.<증상> --symptom "..." --cause "..." \
    --prevention "..." --signature "<정규식>" --fix-commit <sha> --fix-note "..."
```
- **확인한 원인만** 넣는다. 추측이면 후보(candidate)로 남긴다. 틀린 사전은 없느니만 못하다.
- `prevention`(앞으로 이렇게 하라)과 `fix`(이번에 무엇을 고쳤나, 커밋)를 구분한다.
- 코드가 막는 것과 문서 규칙인 것을 구분해 적는다. "규칙으로만 기록" 된 항목은 다시 일어날 수 있다고 읽는다.
이 스킬이 읽기 전용이므로 위 명령은 호출 세션이 실행하거나, 실행할 값을 정리해 승인된 단계에 넘긴다.

## 완료 보고 형식
`증상 / 재현 절차 / 근본 원인(증거) / 수정 내용 / 검증 결과(실행한 명령과 종료코드) / 오류 사전 반영 여부`.
실행하지 않은 검증을 통과로 적지 않는다.

## 승격 조건
현재 `status: candidate`. 아래를 모두 만족해야 `active` 로 올린다.
1. 이 스킬을 따라 실제 문제를 해결한 **사용 증거 2건** — 세션 id 또는 러너 job_id 를 각각 기록한다.
2. 두 건 모두 보고에 "근본 원인(증거)" 와 "오류 사전 반영 여부" 가 있고, 수정이 재현 테스트로 검증되었다.
3. 위험 등급이 `read` 로 유지된다 (`infer_risk_tier` 확인).
승격은 증거 확인 후 사람이 승인한다. 이 문서는 스스로 승격하지 않는다.
