# 사내 스킬 작성·검증

스킬은 "이 상황에서는 이렇게 하라" 를 모델이 필요할 때만 읽도록 떼어 둔 지침 파일이다.
이 스킬은 **작성·검증 방법**만 안내한다. 파일을 쓰거나 명령을 실행하는 권한은 주지 않는다 —
호출한 세션이 가진 권한 안에서 수행한다.

## 시작 전 네 가지 질문
쓰기 전에 답이 없으면 스킬이 모호해진다. 대화에 이미 답이 있으면 사용자에게 다시 묻지 말고 거기서 뽑는다.
1. 이 스킬이 있으면 모델이 **무엇을 할 수 있게 되는가**?
2. **어떤 말·상황**에서 불려야 하는가?
3. 결과물의 **형식**은? (표, 보고서 템플릿, 체크리스트 등)
4. 결과가 객관적으로 검증되는가? 검증되면 시험 케이스를 만들고, 문체·판단처럼 주관적이면 사람 검토로 대신한다.

이미 같은 일을 하는 스킬이 있는지 `Glob .claude/skills/*/SKILL.md` 와 `Grep` 으로 먼저 확인한다.
겹치면 새로 만들지 말고 기존 것을 고친다 (슬러그 중복도 여기서 걸러진다).

## 파일 구조
```
.claude/skills/<슬러그>/SKILL.md      # 필수. 슬러그 = 디렉터리명 = frontmatter name
```
- 슬러그는 소문자·숫자·하이픈. **디렉터리명과 `name` 이 다르면** 스캐너가 보는 이름과 DB 에 적재되는 이름이 갈라진다.
- 본문은 500줄 안쪽. 넘치면 참고 문서를 따로 두고 "언제 그 문서를 읽는지" 를 본문에 적는다.

## frontmatter 항목
| 키 | 필수 | 내용 |
|---|---|---|
| `name` | 예 | 슬러그와 동일 |
| `description` | 예 | 한글. **무엇을 + 언제 쓰는지**. 따옴표로 감싼다(콜론 때문에 YAML 이 깨진다) |
| `allowed-tools` | 예 | 쉼표 구분. 읽기 전용이면 `Read, Grep, Glob` |
| `risk_tier` | 권장 | 낮은 순서로 read, write, 배포, auth, financial, destructive (정확한 값 이름은 `skill_file_import.py` 의 `_RISK_ORDER`). 아래 판정 규칙 참고 |
| `status` | 권장 | `candidate` → `active` |
| `executor` | 권장 | 실행 주체. 모델이 지침을 읽고 따르는 방식이면 `model-instructions` |
| `source`, `license`, `adapted` | 외부 방법론을 각색한 경우 필수 | 원본 URL, 확인한 라이선스, 각색일 |

### description 쓰는 법
- 스킬이 불리는지는 거의 전적으로 이 문장에 달려 있다. "언제 쓰는지" 는 본문이 아니라 여기에 둔다.
- 기능 설명(무엇을)과 상황 목록(언제)을 둘 다 적는다. 사용자가 실제로 쓸 법한 표현과 증상을 넣는다.
- 모델은 스킬을 **덜 부르는 쪽**으로 틀리기 쉽다. 경계가 애매한 상황도 "~할 때도 쓴다" 로 포함시킨다.
- 너무 넓게 쓰면 엉뚱한 때 불린다. 인접 스킬과 겹치면 "그 경우는 <다른 스킬>" 을 본문에 적는다.

## 본문 작성 원칙
- 명령형 짧은 문장. 순서가 중요한 것은 번호, 아닌 것은 점 목록.
- **왜 그렇게 해야 하는지** 한 줄을 붙인다. 이유를 알면 모델이 예외 상황에서 스스로 판단한다. 대문자 강조나 "절대" 남발은 효과가 약하다.
- 특정 예시에만 맞는 좁은 규칙보다, 새 상황에도 적용되는 원칙을 쓴다.
- 산출물 형식이 있다면 템플릿을 그대로 보여준다.
- 놀라움 없음: 이름과 설명에서 예상 못 할 동작(외부 전송, 파일 삭제 등)을 본문에 숨기지 않는다.
- 사내 규칙은 요약하지 말고 **원본 위치를 가리킨다**. 규칙을 두 벌로 쓰면 한쪽이 낡는다 (R-RELEASE).

## 위험 등급 판정
등급은 `app/services/skill_file_import.py` 의 `infer_risk_tier` 가 계산하며 **명시값으로 낮출 수 없다**.
| 신호 | 결과 |
|---|---|
| `allowed-tools` 에 Bash, Edit, Write, MultiEdit, NotebookEdit 중 하나 | 최소 `write` |
| 본문에 배포 스크립트·무중단 전환·원격 반영·컨테이너 일괄 기동을 가리키는 표지 문자열 (목록은 `skill_file_import.py` 의 마커 상수) | 배포 등급 |
| 본문에 영문 배포 동사가 단순 언급됨 | 최소 `write` |
| `risk_tier` 를 더 높게 명시 | 명시값 |
읽기 전용 스킬이 `write` 로 잡히면 의도치 않은 문자열이 본문에 있다는 뜻이다.
`risk_reasons` 로 근거를 확인하고 **본문을 고친다** — 등급 계산을 우회하지 않는다.
검증은 `infer_risk_tier(parse_frontmatter(text), text)` 를 테스트로 돌려 `read` 를 확인하는 것이다
(예: `tests/unit/test_skill_public_candidates.py` 의 방식).

## 시험 케이스
스킬을 쓰고 나면 **실제 사용자가 할 법한 요청 2~3개**를 만든다.
1. 요청 문장, 기대하는 결과(또는 결과의 필수 요소)를 적는다. 정답 판정이 가능한 것만 단언으로 만든다.
2. 가능하면 같은 요청을 **스킬 없이** 한 번, **스킬과 함께** 한 번 수행해 차이를 본다. 차이가 없으면 스킬의 존재 이유가 약하다.
3. 결과를 양쪽 다 읽는다. 실패 원인이 지침 모호함인지, 모델이 지침을 무시한 것인지, 지침이 틀린 것인지 구분한다.
4. 고친 뒤 같은 케이스를 다시 돌린다. 한 케이스에만 맞춘 땜질이 되지 않았는지, 다른 케이스가 깨지지 않았는지 본다.
5. 호출 여부 시험도 한다: 불려야 할 요청 3개, 불리면 안 되는 인접 요청 3개로 description 이 알맞게 반응하는지 본다.

시험 결과는 `요청 / 기대 / 실제 / 판정` 표로 남긴다. 승격 근거로 쓰인다.

## 자주 틀리는 것
- 본문이 길어질수록 중요한 지침이 묻힌다. 같은 말을 반복하지 말고 줄여라.
- description 에 "~입니다" 식의 소개만 쓰고 언제 쓰는지를 빠뜨린다.
- 읽기 전용이라면서 `Edit`/`Bash` 를 allowed-tools 에 넣는다.
- 외부 원문을 문장째 옮긴다. 방법론을 이해한 뒤 새로 쓰고, 출처·라이선스·변경 사실을 끝에 고지한다.
- 존재하지 않는 경로·도구 이름을 적는다. 쓰기 전에 `Glob`/`Grep` 으로 실재를 확인한다.
- DB 에 적재된 스킬의 executor 는 현재 대부분 `ohvis.contract-echo`(아무것도 하지 않는 자리표시)다. 새 스킬이 그것에 기대면 실행되지 않는다.

## 적재와 승격
- 적재는 `python3 scripts/import_file_skills.py` 가 한다. 기본 `--dry-run` 은 DB 를 바꾸지 않고 계획만 보여준다.
  `--apply` 는 승인된 단계에서만 쓴다. 이 스킬 작성 단계에서는 실행하지 않는다.
- 이 스크립트는 `slug`, `title`, `description`, `risk_tier` 와 파일 해시만 옮긴다. `status`/`executor` 가 DB 의
  `ops_skill_versions` 에 어떻게 반영되는지는 적재 경로가 별도로 지원해야 하므로, 안 되면 **고치지 말고 보고**한다.
- 파일이 바뀌면 해시 불일치(`file_drift`)로만 표시되고 DB 내용을 덮어쓰지 않는다. 내용 갱신은 별도 승인 절차다.

## 승격 조건 (candidate → active)
1. 시험 케이스 표가 있고, 실패 케이스가 없거나 알려진 한계로 기록되어 있다.
2. 위험 등급이 의도한 값과 일치한다.
3. 실제 사용 증거 **2건** (세션 id 또는 러너 job_id). 시험용 호출은 증거로 세지 않는다.
4. 같은 일을 하는 기존 스킬과 중복이 아님을 확인했다.
5. 사람의 승인. 스킬이 스스로 자기 상태를 바꾸지 않는다.
현재 이 스킬 자신도 `candidate` 이며 위 조건을 같은 방식으로 충족해야 한다.
