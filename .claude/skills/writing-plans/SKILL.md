# 계획·지시서 작성과 단계 실행

계획은 **처음 보는 실행자가 추측 없이 따라 할 수 있을 만큼** 구체적이어야 한다.
이 스킬은 쓰는 법과 실행하는 법의 기준만 다루며, 파일 쓰기·실행 권한은 주지 않는다.
계획서 파일은 호출한 세션이 가진 권한으로 만들고, 쓸 수 없으면 본문을 응답으로 낸다.

## 쓰기 전 확인
1. 요구가 모호하거나 대안이 있으면 먼저 `brainstorming` 스킬로 정리한다.
2. 범위가 서로 독립된 하위 작업 여러 개이면 하나로 뭉치지 말고 나눈다 (`parallel-agent-dispatch` 참고).
3. 오류 사전을 조회해 이미 알려진 원인이 있는지 본다: `scripts/error_book.py match <오류파일|->`.
4. 기존 구현을 먼저 조사한다. 대상 파일의 함수·엔드포인트·DB 접점을 읽고 각 항목을 **유지 / 수정 / 신규 / 삭제(사유)** 로 분류한다.
   기존 구현을 통째로 갈아엎는 계획은 필요한 개선분만 반영하는 계획보다 위험하다.

## 지시서 포맷 (D-022)
지시서 첫머리에 아래 항목을 둔다.
```
TASK_ID: <프로젝트>-<주제>-<날짜>
TITLE: <type(scope): 한글 요약>
PRIORITY: P0 | P1 | P2 | P3
SIZE: S | M | L
```
- `TASK_ID` 는 겹치지 않게, `TITLE` 은 한 줄로 결과가 드러나게 쓴다.
- `SIZE` 는 한 번의 러너 실행에 담길지로 판단한다. 크면 쪼갠다.
- 파일 경로, 테이블, 함수는 **실제로 확인한 이름**만 쓴다. 확인하지 못한 것은 "미확인" 으로 표시한다.
- 새 문서는 한글 제목과 영문 kebab-case 문서 키를 붙인다 (R-DOC).

## 한 단계의 모양
각 단계는 **한 가지 행동과 확인 가능한 결과**를 가진다.
- 파일: 만들 것 / 고칠 것(줄 범위) / 테스트할 것을 정확한 경로로 적는다.
- 인터페이스: 이 단계가 앞 단계에서 받는 것, 뒤 단계가 기대하는 것(함수 이름·인자·반환)을 적는다. 단계 사이 이름이 어긋나지 않게 한다.
- 검증 단계: 실행할 명령과 "무엇이 나오면 통과인가" 를 함께 적는다. 예: `bash scripts/run_unit_tests.sh tests/unit/test_x.py` 종료코드 0.
- 코드 단계: 시그니처와 동작을 적는다. 결정이 필요한 곳을 "적절히 처리" 로 남기지 않는다.
- 실패하는 테스트를 먼저 쓰는 순서를 기본으로 한다 (`test-driven-development`).

## 검증 기준은 필수
- 완료 기준은 **관측 가능한 항목**으로 쓴다: 테스트 종료코드, 응답 값, 화면 근거, 커밋 SHA.
- "잘 동작한다" 같은 서술은 기준이 아니다.
- 되돌리는 법(예: 커밋 revert)과 금지 사항(DB 쓰기, 재시작, 규칙 우회)을 명시한다.
- 사내 규칙과 충돌하는 지침은 넣지 않는다: 훅 우회(`--no-verify`), `HANDOVER.md` 수정, 전체 스택 재기동, 직접 재시작.

## 작성 후 자기 점검
1. 요구의 각 항목에 대응하는 단계가 있는가 — 빠진 요구를 목록으로 적는다.
2. 단계마다 실행자가 한 가지로만 해석할 수 있는가.
3. 앞뒤 단계의 이름·시그니처가 일치하는가.
4. 입력이 비었을 때, 실패했을 때, 권한이 없을 때를 다루는 단계가 있는가.
5. 계획이 요구보다 몇 배 길다면 실행 기록이 되어버린 것이다 — 코드는 필요한 곳에만 둔다.

## 계획을 실행할 때
- 계획에 이미 판단이 담겨 있으니 **그대로 실행**한다. 단계마다 확인을 구하며 멈추지 않는다.
- 단계를 시작하기 전에 해당 단계의 기대 결과를 다시 읽고, 끝난 뒤 실제 출력과 대조한다.
- 어긋남이 생기면 원인을 가른다.
  - **코드가 틀렸다** → `systematic-debugging` 으로 근본 원인을 찾아 고친다.
  - **계획이 틀렸다**(단계가 요구와 모순, 인터페이스가 맞지 않음) → 계획을 고치고, 바꾼 사실과 이유를 기록한다.
  - **판단이 필요하다** → 가장 작은 변경을 택하고 그 결정을 기록한다. 사용자의 결정이 꼭 필요한 경우만 멈춘다.
- 계획에 없던 파일을 건드려야 하면, 바꾸기 전에 사유를 보고에 적는다.
- 단계가 끝날 때마다 해당 검증 명령을 실제로 실행한다. 끝났다는 보고는 `verification-before-completion` 기준을 따른다.

## 승격 조건
현재 `status: candidate`. 아래를 모두 만족해야 `active` 로 올린다.
1. 이 스킬을 따라 계획·지시서를 작성하거나 실행한 **사용 증거 2건** — 세션 id 또는 러너 job_id 를 각각 기록한다.
2. 두 건 모두 D-022 항목과 관측 가능한 완료 기준이 있고, 실행 결과가 기준과 대조되어 있다.
3. 위험 등급이 `read` 로 유지된다 (`infer_risk_tier` 확인).
승격은 증거 확인 후 사람이 승인한다. 이 문서는 스스로 승격하지 않는다.
