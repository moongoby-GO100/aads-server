# 전자계약 시스템 기획 보고서

- 작성일: 2026-06-15 11:59 KST
- 대상: 직원 근로계약서, 프리랜서/외주 계약서, 뉴톡 입점계약서, NDA/개인정보처리위탁/정산 부속합의서
- 작성 목적: 뉴톡/AADS 운영에서 반복 발생하는 계약 업무를 전자계약 기반으로 표준화하고, 법적 증거력·업무속도·계약 추적성을 확보한다.
- 주의: 본 문서는 시스템 기획안이며 최종 계약 조항은 노무사/변호사 검토가 필요하다.

## 1. 핵심 결론

전자계약 도입 방향은 "AADS/뉴톡 자체 전자계약 서비스 구축"을 1차 목표로 한다. 외부 전자계약 서비스는 기본 방향이 아니라 휴대폰 본인확인, 알림톡/문자 발송, 신뢰시각확인, 장기보존/WORM 스토리지처럼 법적 증거력과 운영 안정성을 보강하는 인프라로만 선택 연동한다. 직원 근로계약은 고용노동부 전자근로계약서 가이드라인과 근로기준법 제17조의 교부 요건을 충족해야 하므로, 단순 PDF 업로드보다 "본인확인 + 전자서명 + 교부증적 + 보존"이 모두 남는 구조가 필요하다.

권장안은 다음과 같다.

| 구분 | 권장 방식 | 이유 |
|---|---|---|
| 직원 근로계약 | 자체 전자계약 + 교부증적 필수 | 근로조건 명시·교부·3년 보존·감사추적 증적이 중요 |
| 프리랜서 계약 | 자체 템플릿 + SOW + 전자서명 | 근로자성 오인 리스크를 조항·운영 증적으로 분리해야 함 |
| 뉴톡 입점계약 | 자체 계약 플로우와 뉴톡 관리자 온보딩 직접 연동 | 사업자정보, 통신판매, 정산계좌, 수수료, 반품/CS 책임이 가입 프로세스와 연결됨 |
| 외부 연동 | 본인확인·알림·타임스탬프·장기보존 보조 인프라로 제한 | 자체 구축 속도를 유지하면서 증거력 취약 지점을 보강 |

## 2. 최신 법령·공식 근거

| 영역 | 확인 내용 | 시스템 반영 |
|---|---|---|
| 전자문서 효력 | 전자문서는 전자적 형태라는 이유만으로 법적 효력이 부인되지 않는다. 전자문서법 제4조 | 전자계약 PDF/원본문서/감사로그를 원본성 있게 보존 |
| 전자문서의 서면요건 | 열람 가능하고 작성·송신·수신·저장 당시 형태 또는 재현 가능한 형태로 보존되면 서면으로 볼 수 있다. 전자문서법 제4조의2 | 계약 완료본 다운로드, 해시, 시점, 변경불가 저장 필요 |
| 전자서명 효력 | 전자서명은 전자적 형태라는 이유만으로 서명·서명날인·기명날인 효력이 부인되지 않는다. 전자서명법 제3조 | 서명자 식별, 서명 의사, 서명 시점, 인증수단 기록 필요 |
| 근로계약서 교부 | 근로기준법 제17조는 임금·소정근로시간·휴일·연차 등을 명시하고 서면으로 교부하도록 하며, 여기에는 전자문서가 포함된다. | 근로자에게 이메일/알림톡/포털함 등으로 완료본을 실제 교부 |
| 근로계약 서류 보존 | 근로기준법 제42조는 근로자 명부와 근로계약 중요서류를 3년간 보존하도록 한다. | 퇴직/계약종료 후 최소 3년 보존 정책 |
| 미작성/미교부 리스크 | 고용노동부 안내는 근로계약서 서면 체결·교부 위반 시 500만원 이하 벌금, 기간제·단시간은 500만원 이하 과태료 가능성을 안내한다. | "서명 완료"와 별개로 "교부 완료" 상태를 별도 관리 |
| 개인정보/주민등록번호 | 개인정보보호법은 주민등록번호 처리를 제한한다. 법령 근거 없는 수집은 피해야 하며 전자보관 시 암호화가 필요하다. | 주민번호 미수집 원칙, 필요한 경우 별도 암호화 필드와 접근통제 |
| 입점계약 표준 | 공정거래위원회는 온라인쇼핑몰 표준거래계약서 등 표준유통거래계약서를 배포한다. | 뉴톡 입점계약의 정산·수수료·판촉·반품·해지 조항 기준으로 활용 |

## 3. 계약 유형별 설계

### 3.1 직원 근로계약서

목표는 근로계약 체결 전후 분쟁 방지와 근로기준법상 명시·교부·보존 요건 충족이다.

필수 구성:

| 항목 | 내용 |
|---|---|
| 당사자 | 회사명, 대표자, 사업장, 근로자 성명, 연락처 |
| 근로조건 | 임금, 소정근로시간, 휴게, 휴일, 연차 유급휴가, 업무내용, 근무장소 |
| 계약형태 | 정규직, 기간제, 단시간, 수습 여부, 계약기간 |
| 임금상세 | 기본급, 고정수당, 성과급, 지급일, 지급방법, 공제항목 |
| 부속동의 | 개인정보 처리 동의, 보안서약, 영업비밀/NDA, 저작물·직무발명 귀속 |
| 교부증적 | 근로자 수신 채널, 수신/열람/다운로드 이력, 완료본 해시 |
| 보존정책 | 근로관계 종료일부터 최소 3년, 분쟁 가능 문서는 5년 이상 권장 |

운영 리스크:

- 계약서 서명만 받고 완료본을 근로자에게 교부하지 않으면 교부의무 문제가 남는다.
- 근로계약 변경 시 "기존 계약 수정"이 아니라 버전 신규 발행으로 이력을 남겨야 한다.
- 전자계약 시스템 안에만 저장하고 근로자가 접근할 수 없는 구조는 교부로 보기 어렵다. 근로자에게 이메일/알림톡/포털함 등 수신 가능한 경로를 지정하게 하고, 완료본 접근권을 유지해야 한다.

### 3.2 프리랜서/외주 계약서

목표는 결과물·대금·지식재산권·비밀유지·개인정보 처리 책임을 명확히 하되, 실제 운영이 근로관계처럼 보이지 않게 하는 것이다. 계약서 제목이 "프리랜서"라도 지휘·감독, 근무시간/장소 구속, 전속성, 고정급 등 실질이 근로관계에 가까우면 근로자성 문제가 발생할 수 있다.

필수 구성:

| 항목 | 내용 |
|---|---|
| 업무범위 | SOW, 산출물 정의, 검수 기준, 납기 |
| 대금 | 총액/단가, 마일스톤, 세금계산서/원천징수 방식, 지연 지급 조건 |
| 독립성 | 업무 수행 방식 자율, 대체인력/재위탁 가능 여부, 장비·장소 |
| 검수 | 재작업 범위, 검수 기한, 승인 간주 조건 |
| IP | 결과물 저작권/사용권/2차 활용권, 포트폴리오 공개 여부 |
| 보안 | NDA, 접근권한 회수, 소스/데이터 반납·폐기 |
| 개인정보 | 처리위탁 여부, 개인정보 접근 범위, 재위탁 금지, 사고 통지 |
| 해지 | 중도해지, 위약금, 기성고 정산, 자료 인수인계 |

운영 리스크:

- 매일 출퇴근, 회사 장비·계정 상시 사용, 지시형 업무, 고정 월급, 휴가 승인 구조를 만들면 프리랜서 계약서만으로 방어가 어렵다.
- 개발/디자인 결과물은 "대금 지급 시 권리 이전" 또는 "검수 완료 시 사용권 부여" 등 권리 귀속 시점을 명확히 해야 한다.
- 개인정보를 다루는 외주라면 개인정보처리위탁 계약/부속합의가 별도로 필요하다.

### 3.3 뉴톡 입점계약서

목표는 입점사 온보딩, 상품등록, 판매, 정산, CS, 반품, 제재를 하나의 계약 체계로 묶는 것이다.

필수 구성:

| 항목 | 내용 |
|---|---|
| 입점자격 | 사업자등록, 통신판매업, 대표자/담당자, 정산계좌, 세금계산서 정보 |
| 판매범위 | 취급 가능/금지 상품, 브랜드/IP 권리 증빙, 중국사입/도매처 구분 |
| 수수료 | 판매수수료, PG수수료, 프로모션 비용, 쿠폰 부담 주체 |
| 정산 | 정산주기, 보류/차감/환불, 지연이자, 증빙 제공 |
| 상품책임 | 상품정보 정확성, 원산지/인증/표시광고, 위조상품 금지 |
| 배송/반품 | 배송지연, 교환/환불, 고객 CS 책임분담, 회수비 |
| 콘텐츠 | 이미지/상세페이지 사용권, AI 생성 이미지 사용 고지, 초상권/상표권 책임 |
| 개인정보 | 주문자 개인정보 사용 목적 제한, 배송 목적 외 사용 금지, 유출 통지 |
| 제재 | 판매중지, 정산보류, 계약해지, 손해배상, 분쟁처리 |
| 부속정책 | 판매자 운영정책, 금지상품 정책, 정산정책, 광고/라이브 정책 |

뉴톡 특화 설계:

- 입점계약은 "한 번 서명"으로 끝내지 말고 약관/운영정책 버전 동의 이력을 계속 쌓아야 한다.
- 입점사는 사업자 정보 변경, 계좌 변경, 대표자 변경 시 변경계약 또는 부속동의를 다시 받아야 한다.
- 뉴톡이 판매대금을 수령한 뒤 정산하는 구조라면 정산 근거와 차감 근거를 계약서·관리자 화면·정산명세서에서 일치시켜야 한다.

## 4. 전자계약 시스템 기능 요구사항

### 4.1 사용자 역할

| 역할 | 권한 |

| CEO/관리자 | 템플릿 승인, 계약 발송, 상태 확인, 다운로드, 해지 |

| API/Webhook | 자체 계약 API, 뉴톡 관리자, HR/정산 시스템, 본인확인·알림·타임스탬프 보조 API 연동 |

### 4.3 상태값

계약은 반드시 서명 상태와 교부 상태를 분리한다.

```text
DRAFT
  -> APPROVED
  -> SENT
  -> VIEWED
  -> SIGNED_PARTIAL
  -> SIGNED_ALL
  -> DELIVERED
  -> ACTIVE
  -> EXPIRED / TERMINATED / VOIDED / SUPERSEDED
```

중요한 점은 `SIGNED_ALL`이 최종 완료가 아니라는 것이다. 직원 근로계약은 `DELIVERED`까지 확인되어야 운영상 완료로 본다.

## 5. 자체 구축 중심 설계

| 기준 | 자체 전자계약 서비스 | 외부 보조 인프라 |
|---|---|---|
| 도입 속도 | MVP-1은 템플릿 3종, PDF 생성, 이메일 링크 서명, 감사로그부터 시작 | 휴대폰 본인확인/알림톡/TSA는 필요한 시점에 붙임 |
| 법적 증거력 | 문서 해시, 이벤트 체인, 교부 기록, 접근 로그를 직접 보존 | 본인확인, 신뢰시각확인, WORM 보존으로 보강 |
| 비용 | 초기 개발비와 유지보수 필요, 건당 벤더 비용은 절감 | 인증/문자/보존 사용량 기반 비용 |
| 커스터마이징 | 뉴톡 입점, 정산, HR, 외주 권한과 직접 통합 가능 | 표준 API 범위 내 보조 기능 |
| 리스크 | 증적 설계 미흡 시 분쟁 대응 약함 | 벤더 장애/비용/약관 변경 리스크 |
| 권장 용도 | 1차 구현 본체 | 법적 증거력과 발송 안정성 보조 |

권장 결론:

1. 0~2개월: AADS/뉴톡 자체 전자계약 MVP를 구축한다.
2. 2~4개월: 휴대폰 본인확인, 알림톡/문자, 신뢰시각확인, 장기보존 연동을 선택 적용한다.
3. 4개월 이후: 입점계약, 운영정책 재동의, 정산계좌 변경합의, 프리랜서 SOW 갱신을 자체 UI에서 자동화한다.

## 6. 외부 연동 후보와 사용 범위

외부 전자계약 벤더를 기본 계약 엔진으로 쓰지 않는다. 아래 후보는 자체 구축 중 부족한 본인확인, 알림 발송, 감사증적 보강, 레퍼런스 검증 용도로만 비교한다.

| 후보 | 사용 가능 범위 | 자체 구축에서의 위치 | 주의 |
|---|---|---|---|
| 모두싸인 | 기능/증적 구조 벤치마크, 필요 시 예외 발송 | 대체 벤더 또는 백업 플로우 | 주 엔진으로 쓰면 벤더 종속 발생 |
| 이폼사인 | 서식형 입력, 알림/본인확인 방식 참고 | 신청서·첨부서류 UX 벤치마크 | API/요금 조건 별도 확인 필요 |
| 본인확인/TSA/알림 API | 휴대폰 인증, 알림톡, 신뢰시각확인 | 자체 서비스의 보조 인프라 | 개인정보·비용·실패 재시도 설계 필요 |

1차 추천은 "자체 계약 엔진 + 외부 신뢰 인프라 선택 연동"이다. 자체 구현 범위는 템플릿, 변수 병합, PDF 렌더링, 서명 세션, 이벤트 로그, 완료본/증적 보존, 뉴톡 권한 연동까지 포함한다.

2. 자체 전자계약 MVP를 구현한다.

   - 서명 링크 발송

3. 뉴톡 관리자에 계약 상태 필드를 먼저 추가한다.
   - `contract_status`: none, sent, signed, delivered, active, expired
   - 입점사 `active` 전환 조건에 `contract_status = active`를 추가한다.

4. 외부 연동은 보조 인프라로 제한한다.
   - 휴대폰 본인확인, 알림톡, 신뢰시각확인, 장기보존은 필요 시 API로 붙인다.
   - 계약 생성, 서명 플로우, 증적 패키지, 계약함, 뉴톡 권한 연동은 자체 서비스가 담당한다.

## 14. 자체 전자계약 서비스 구축 보완안

### 14.1 구축 원칙

자체 구축의 목표는 단순 PDF 서명 기능이 아니라 "계약 생애주기 관리(CLM) + 전자서명 + 증적 보존 + 뉴톡 권한 연동"이다. 외부 전자계약 서비스를 대체하려면 다음 요건이 반드시 충족되어야 한다.

| 요건 | 자체 구현 내용 | 외부 의존 가능 영역 |
|---|---|---|
| 서명자 식별 | 이메일/휴대폰 인증, 관리자 초대, 서명 링크 토큰 | 휴대폰 본인확인, 카카오/네이버 인증 |
| 서명 의사 확인 | 서명 전 약관 동의, 체크박스, 전자서명 입력, 서명 완료 버튼 | 없음 |
| 문서 무결성 | 원본문서와 완료본 SHA-256 해시, 버전 잠금 | 공인전자문서센터 또는 장기보존 서비스 |
| 시점 증명 | 서버 서명시각, DB 이벤트, 타임스탬프 로그 | TSA/전자서명인증사업자 API |
| 교부 증적 | 이메일/알림톡/포털함 교부, 열람/다운로드 기록 | 알림톡/문자 발송 대행 |
| 감사추적 | IP, User-Agent, 이벤트 체인, 변경 불가 로그 | 외부 WORM 스토리지 |
| 보존/검색 | 계약함, 만료/갱신 알림, 정책 버전 동의 이력 | 백업 스토리지 |

### 14.2 자체 구축 아키텍처

```text
Admin UI
  -> Template Manager
  -> Contract Builder
  -> Signature Session
  -> Evidence Pack Generator
  -> Delivery Manager
  -> Contract Repository
  -> NTV2 Seller/HR/Freelancer Permission Gate
```

핵심 설계는 이벤트 소싱 방식이다. 계약 문서를 직접 수정하지 않고 `contract_events`에 발송, 열람, 서명, 교부, 다운로드, 무효화, 변경계약 발행 이벤트를 누적한다. 완료본은 immutable object로 저장하고, 새 버전이 필요하면 `SUPERSEDED` 상태의 새 계약 인스턴스를 만든다.

### 14.3 자체 구축 MVP 범위

| 단계 | 포함 | 제외 |
|---|---|---|
| MVP-1 | 템플릿 3종, 변수 입력, PDF 생성, 이메일 링크 서명, 감사로그, 완료본 저장 | 휴대폰 본인확인, 알림톡, 공인 타임스탬프 |
| MVP-2 | 휴대폰 OTP/알림톡, 계약함, 만료 알림, 뉴톡 입점 active 차단 | 공인전자문서센터 연동 |
| MVP-3 | 정책 재동의, 변경계약, 대량발송, 외부 TSA/WORM 보존 | 대체 불가능한 공인 인증 주장 |

MVP-1은 내부 계약 운영을 시작하기 위한 최소 범위다. 다만 직원 근로계약은 법적 분쟁 가능성이 높으므로 MVP-1만으로 운영을 시작하더라도 완료본 교부와 다운로드 기록은 반드시 남겨야 한다.

## 16. 별도 SaaS 서비스화 전략

CEO의 후속 지시에 따라 전자계약을 뉴톡 내부 기능에만 묶지 않고, "모두싸인처럼 별도 서비스"로 확장하는 사업화 방향을 보완한다. 결론은 별도 서비스화가 가능하다는 것이다. 다만 범용 전자서명 도구로 바로 경쟁하면 브랜드·보안·영업 장벽이 높으므로, 1차 포지션은 "입점/외주/근로계약 운영을 업무 권한과 연결하는 도메인 특화 계약 OS"로 잡는다.

### 16.5 요금제 초안

요금제는 "플랫폼 월정액 + 계약 완료 건수 + 신뢰 인프라 실비"로 구성한다. 이폼사인 공개 단가처럼 본인확인·타임스탬프·보관은 원가성 항목이므로 기본 요금에 숨기지 말고 별도 usage line item으로 분리하는 편이 안전하다.

| 플랜 | 월 이용료 초안 | 포함 | 초과/별도 |
|---|---:|---|---|
| Free/Internal | 0원 | 내부 테스트, 월 20건, 템플릿 3개 | 외부 발송 제한 |
| Starter | 19,000원 | 월 50건, 템플릿 10개, 이메일 발송, 기본 증적 | 본인확인/알림톡/TSA 별도 |
| Team | 49,000원 | 월 200건, 팀 권한, Webhook, 정책 재동의 | 초과 건당 과금 |
| Business | 149,000원 | 월 1,000건, API, SSO 후보, 감사 리포트 | 장기보존/TSA/전담지원 별도 |
| Enterprise | 견적 | 전용 보관, 전용 도메인, SLA, 법무 검토 워크플로우 | 별도 계약 |

초기에는 가격보다 레퍼런스가 중요하다. 뉴톡 내부 운영에서 월간 발송량, 완료율, 미서명 회수율, 계약당 처리시간을 실측한 뒤 2차 요금제를 조정한다.

### 16.7 go-to-market

1차 고객은 "계약이 완료되지 않으면 업무가 시작되면 안 되는 조직"이다. 단순 서명보다 운영 통제가 중요한 고객에게 집중한다.

| 타깃 | 문제 | 제안 |
|---|---|---|
| 쇼핑몰/마켓플레이스 | 입점계약, 정산계좌, 판매자 정책 동의가 흩어짐 | 입점 active gate와 정책 재동의 자동화 |
| 외주/콘텐츠 제작사 | SOW, 검수, IP, NDA 누락 | 프로젝트별 계약 패키지와 착수 권한 연동 |
| 소규모 HR | 근로계약 교부/보존/갱신 누락 | 근로계약 발송, 교부증적, 만료 알림 |
| AI 에이전시 | 작업 범위·저작권·데이터 처리 책임 불명확 | AI 작업계약 템플릿과 산출물 검수 계약 |

초기 영업 메시지는 "전자서명 서비스"가 아니라 "계약 완료 전 업무를 막아주는 계약 운영 자동화"로 잡는다.

### 16.8 리스크와 대응

| 리스크 | 영향 | 대응 |
|---|---|---|
| 범용 전자계약 강자와 비교됨 | 신뢰/브랜드 열세 | 범용이 아닌 커머스·외주·정책동의 특화로 시작 |
| 법적 증거력 오해 | 분쟁 시 방어 약화 | 전자문서법/전자서명법 근거, 증적팩, 외부 TSA/WORM 선택 연동 |
| 개인정보/계약서 보관 부담 | 보안 사고 리스크 | 테넌트 암호화, 접근로그, 다운로드 워터마크, 보존/파기 정책 |
| 외부 고객 지원 부담 | 운영 비용 증가 | 내부 실증 후 베타 고객 제한, SLA는 Enterprise부터 제공 |
| 기능 범위 과확장 | MVP 지연 | 입점계약/프리랜서/SOW/근로계약 3종과 Webhook에 집중 |

최종 권고: NewSign은 독립 서비스로 설계하되, 출시는 뉴톡 내부 계약 허브에서 시작한다. 내부 실증 지표가 확보되면 외부 베타를 열고, API/Webhook과 도메인 템플릿을 앞세워 "모두싸인 대체"가 아니라 "업무 게이트형 계약 OS"로 포지셔닝한다.
